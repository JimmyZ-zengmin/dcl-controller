# 硬件在环（HIL）上位机 —— 演示

> 板子：STM32H723 + TB6600 + 闭环步进（AS5600 编码器）+ T8 丝杆
> 上位机：`tools/hostsim/bridge.py`（桥接层）+ `index.html`（three.js 3D 视图）
> 截图：2026-09-22 实测，板子在环，非回放

## 这是什么

浏览器里看到的**不是轨迹动画，是板上真实编码器驱动的运动**：

```
[板子 COMxx] --pyserial--> bridge.py（内置 http.server）
                                 ├── GET /        → index.html（three.js 场景）
                                 └── GET /state   → JSON（板子实读）
[浏览器] 每 ~40 ms fetch('/state') → 更新 电机 / 丝杆 / 滑台 + HUD + 曲线
```

解算链：`raw(SENSOR[0], 12 位绝对角) → 解绕成累计 counts → revs → pos_mm = revs × 导程`
⇒ 丝杆转角、滑台位置**都由真实编码器推出**，不是模型时间轴。

## 怎么跑

```bash
python tools/hostsim/bridge.py --live COM21 --pitch 8     # 打开 http://127.0.0.1:8765
python tools/hostsim/recorder.py --secs 30                # 顺带落盘数据（historian）
python tools/hostsim/demo_capture.py                      # 命令行版：起运动 + 记录 + 算速度
```

### ★ `02-running-ramp.png` 为什么最重要

设定：峰值 **2000 Hz**、斜坡 **250 Hz/s** ⇒ 从 0 爬到 2000 需要 **8 s**。

曲线里：
- **橙虚线（命令）**：一条平直线在顶部（命令早已给到位）
- **绿实线（实测）**：从 0 爬升，**8 s 的斜坡窗与设定完全吻合**，逐渐追上橙线

⇒ 这一张同时证明了三件事：
1. **斜坡限幅真的在固件里执行**（不是上位机画出来的）；
2. 爬升窗 = 8 s，与 `2000 / 250` 一致 ⇒ **上位机的横轴确实是板子的设备时间**；
3. 命令与实测**两个独立来源**能画在一起并互相印证。

## ★★★ 口径（三处，都在界面上标出来了）

### 1. 时间戳来自板子，不来自 PC
`SHM+0x08 HEARTBEAT` **每拍 +1**（实测 10 s：**10 001 Hz vs 期望 10 000，差 0.0%**）。
速度用 `Δcounts / (Δtick × 拍长)` —— **分子分母同为设备口径** ⇒ 免疫 PC 侧拍频。
（改前 `bridge.py` 用的是 PC 墙钟 `dt`，那是噪声；详见 `MEMORY.md` §5.27 / `RULES-DETAIL.md` §26.1）

### 2. 速度有**两个独立来源**，都显示
| HUD 行 | 来源 | 2000 Hz 时的值 |
|---|---|---|
| 命令线速 | `2000 / 1574.4 × 8` | 10.16 mm/s |
| **实测线速 · 板** | 板子 `g_step_rate_hz`（`op=19 sub=14 +16`） | **10.16 mm/s** |
| 实测线速 · 位 | 板子 tick 差分位置 | **10.03 mm/s** |

★「板」与「位」差 **−1.3%** —— 这就是 `MEMORY.md` §一 那条挂账
「**−1.6% 固定比例因子归属不可分**」在界面上的直接呈现（两次独立实验 7.50 / 7.51 mm/s 亦同）。
⇒ **不用再猜**：两个口径摆在同一个屏幕上，差多少一眼可见。

### 3. "命令"必须按运动源自适应
- 程序面模式：命令 = `WIRE[12]`（③层程序写的）
- **脚手架模式：命令 = 上位机下发的值** —— 因为 `WIRE[12]` 此时是**残留值、没人维护**

## 本轮修掉的四个真 bug（都是靠"真跑一遍"才暴露的）

1. **`#bar` 状态条盖住"开跑"按钮** —— `#ctl`（左下，`flex-wrap` 向右延伸）与 `#bar`
   （`bottom:18px; left:50%` 底部居中）重叠，而 `#bar` 在 DOM 里靠后 ⇒ 默认在上层。
   **实测：`agent-browser click "#go"` 完全无效，而手动调 `/motion` 一切正常** ⇒ 后端没问题，是**点不到**。
   ⇒ `#bar` 挪到右下角（那里本来就空），并给 `#ctl` 加 `z-index:20`。
2. **`slope` 参数在脚手架模式下被静默忽略** —— 原实现只在"程序面"路径发 `sub=17`（斜坡），
   而固件注释明写它**是全局的**（"脚手架 `sub=1` 与程序面 `wire[12]` 两条通路**同时受益**"）。
   ⇒ JSON 里回显 `"slope": 200` 却什么都没做 —— **ACK ≠ 生效**。
3. **"命令"曲线画的是没人维护的槽** —— 脚手架模式下 `WIRE[12]` 恒为残留值（实测 6.0 Hz），
   ⇒ 曲线是一条贴 0 的平线，看起来像"命令没跟上"，**一张假图**。⇒ 按 `mosrc` 自适应。
4. **两条曲线在稳态下完全重合 ⇒ 命令那条被整条盖住**（画序在后）⇒ 图例写着两条、图上只有一条。
   ⇒ 实测在下（实线）、命令在上（**虚线**）。

## 边界（没做的，如实）

- 通信仍是 `0x22` 请求-应答，**实测读 1 字也要 10 ms**（4 B 载荷只值 0.35 ms ⇒ **96.5% 是固定开销**）
  ⇒ 上位机刷新率上限 ≈ 6~12 Hz，**不是 25 Hz**（HUD 里的 "PC 采样率" 如实显示）。
- 要看**每拍波形**得走板内环 + 事后整块拉（`recorder.py` / 黑匣子），
  不能靠"每拍上传" —— 带宽差 28 倍（见 `RULES-DETAIL.md` §26.2）。
- `SENSOR_MAP` / `WIRE_MAP` 仍**硬编码**（不在 `0x64` 自报目录里）
  ⇒ 由 `bridge.py` 的 `sanity()` 量纲自检兜底：读错区就**响亮地停**，不会把别的浮点数当位置画出来。
