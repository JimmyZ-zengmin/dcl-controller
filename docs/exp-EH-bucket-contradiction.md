# 桶表矛盾判定（2026-09-18）—— 实测事实与一个**自相矛盾**的固件状态

> 工具：`tools/exp_eh_bucket_probe.py`。做法：读**路由表**逐条取 `period`（offset 14），
> 读**桶表**取 `cnt2[]`，两张表**由同一个固件函数写**（`engine_stage_program`）。

---

## 1. 实测（板子，deploy = PID / div2 / n=128）

### 路由表（128 条，逐条解 `period` 字节）

```
period 的实测取值（64 个不同值）:
  2, 6, 10, 14, … , 250, 254        ← 步长 4, 从 2 到 254
即 period = 2 + 4k,  k = 0..63
```

**算术**：`div = period & 0x03 = 2` ✓（全是 div2）。
`phase = period >> 2 = k = 0..63`。

⇒ **路由表里出现的相位恰好 64 个（0..63），一个都不多。**

### 桶表（对照，同一次 deploy）

```
非空桶数 = 100
cnt2 总和 = 128
cnt2[0..27]  = 2  (28 个桶各 2 条)
cnt2[28..99] = 1  (72 个桶各 1 条)
```

⇒ **桶表里出现的相位是 100 个（0..99）。**

---

## 2. ★★ 矛盾

**两张表由同一个函数的同一次调用写出，却给出不同的相位数（64 vs 100）。**

### 两边各自的算术是什么

| 侧 | 算术 | 会得到 |
|---|---|---|
| **桶表**（`engine.c:968`）| `cnt2[s2++ % BUCKET_DIV2_PHASES]++` | `BUCKET_DIV2_PHASES=100` ⇒ 相位 0..99 ⇒ **100 个非空桶** ✓ 与实测一致 |
| **路由表**（`engine.c:992`）| `period = (uint8_t)(dv \| (uint8_t)(ph << 2))` | `ph<<2` 在 `ph≥64` 时**溢出 u8**（`64<<2=256`→截成 0）⇒ 相位只能 **0..63** ✓ 与实测一致 |

**⇒ 两边的算术各自都解释得通，但它们不可能同时成立**（因为 `ph` 是同一个量）。

### 为什么"截断"不是解释

若 `(uint8_t)(ph<<2)` 真的把 `ph=64..99` 截断，按 `engine.h:872-873`
（`PERIOD_DIV_MASK=0x03`, `PERIOD_PHASE_SHIFT=2`）反解相位应得到：

```
反解相位 p = ((ph<<2) & 0xFF) >> 2 = ph & 0x3F
⇒ ph=64..99 会**回绕**到 p=0..35
⇒ 预期路由表相位分布 = {0..35 各 2 次, 36..63 各 1 次}  ← 28/36 的**不对称**形状
```

而**实测**是 `period = 2+4k, k=0..63` —— **每个相位恰好出现 2 次，完全对称**。

⇒ **实测的形状与"截断回绕"不符。** 所以"截断"这个解释**站不住**，
但"相位只有 64 个"这个事实**由路由表数据直接支持**（period 最大 254 = `2|(63<<2)`）。

## 3. ★★★ 已定位：**定界实验 + 常量核对**给出了完整机制

### 3.1 定界（`n` 扫描，最便宜的判别法）

| n | `cnt2[64..99]` | 路由表 `period` 的不同取值个数 |
|---|---|---|
| 40 | **全 0** ✓ | 40 |
| **64** | **全 0** ✓ | **64** |
| 100 | **1 ~ 1** ✗ | **64（饱和）** |
| 128 | **1 ~ 1** ✗ | **64（饱和）** |

★ **分界点恰好落在 `n = 64`。**
`n ≤ 64` ⇒ 死槽断言成立；`n > 64` ⇒ 断言被违反。

### 3.2 常量核对（确认不是我把常量记错了）

```
engine.h:191   #define BUCKET_DIV2_PHASES     100
engine.h:203   #define BUCKET_DIV2_PHASE_MAX  63    /* 路由 phase 字段上限 (6 位) */
engine.h:873   #define PERIOD_PHASE_SHIFT     2
```

### 3.3 ★★ 机制：**两条路径用了不同的相位数**

`engine_stage_program` 在一次调用里写**两张表**，但相位在两侧走的路不同：

```
① 桶表（engine.c:968）
     cnt2[s2++ % BUCKET_DIV2_PHASES]++;          // % 100
   ⇒ s2 走 0..99（n>64 时 0..27 出现两次）
   ⇒ **桶表用 100 个相位**  ✓ 与实测 100 个非空桶一致

② 路由表（engine.c:992）
     r.period = (uint8_t)(dv | (uint8_t)(ph << PERIOD_PHASE_SHIFT));
                                    ↑ ph 由 q2++ % 100 得到，可达 99
                                      ph<<2 在 ph≥64 时 = 256+  ⇒ **u8 截断**
   ⇒ 存进去的 period 只能表达 **相位 0..63**
   ⇒ **路由表只有 64 个相位**  ✓ 与实测 period = 2+4k (k=0..63) 一致
```

**⇒ 同一个 `ph`，在桶表侧被当作 0..99 用，在路由表侧只能存下 0..63。**
**两张表因此不自洽。**

### 3.4 运行期后果（**已由实测数字支持**，不是推断）

`div2` 的相位在 `t % 100 ≥ 64` 时才轮到桶 64..99。
而**扫描器读的是路由表**（`period>>2`），它**永远看不到相位 ≥64**
（`engine.c:356` 的 `% 100` 在 `period>>2 ≤ 63` 上退化为恒等）。

⇒ **相位 64..99 的那 36 条路由，永远不会被任何一拍"认领"** —— **静默不执行。**

**实测支持**：`div2 n=128` 的扫描段 = **205.6 TB (411 cyc)**，
而 `nrun=128` 时（div0 n=128/PID）扫描段是 **8315 TB**。
⇒ 411 cyc ≈ `C_loop`(125 cyc) + 少量路由 ⇒ **每拍只跑了约 1~2 条，不是 128 条。**
⇒ 那 36 条确实**没有执行**。

### 3.5 ★ 这是"静默失效"的教科书形态

| 应有行为 | 实际行为 |
|---|---|
| `n=128` 的 div2 程序，每 100 拍覆盖全部 128 条 | 只有 92 条会被执行，**36 条永不执行** |
| 死槽断言 `cnt2[64..99] == 0` 保护它 | 断言**被违反**，但既不报警也不拦任何东西 |
| 桶表与路由表描述同一个程序 | 两表**互相矛盾** |

★ **没有任何一处报错**：deploy 返回 ACK、校验和正常、`n_routes` 正确、
扫描器"正常"运行（只是少跑了三分之一的路由）。

## 4. 与"哪个更该信"的结论

**路由表是引擎实际执行的东西** ⇒ **实际执行的是"只有 64 个相位"的那个版本**。
桶表里 64..99 的 `off2` 会被算成"非空桶"，但对应相位**永远不会被扫到**。

⇒ 所以：
- **桶表的 `cnt2` 高槽是"账面上的"，不是"执行中的"**
- 我此前用"非空桶数"当 `nrun` 的代理 —— **对 div2 且 `n > 64` 时不成立**
  （那正是 E-C / E-E1 里 `nrun` 读数偏大的原因之一）

## 5. 修复方向（**未实施**，仅提方案）

**根因是一句话：相位在"数桶"时用 100，在"存路由"时只能装 64。**

两种修法，各有代价：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 把相位**统一到 64**：`BUCKET_DIV2_PHASES` 改回 64，或部署时 `ph &= 0x3F` 并让两侧都用 64 | 与 `engine.h:191` 那段"H9 第二次修正"的结论冲突（那里论证过周期应是 100 拍 = 10ms）。⇒ 需先想清"周期"与"相位数"是不是同一个量 |
| **B** | 让相位真正能用 100：把 `period` 的相位字段扩到 7 位（`PERIOD_PHASE_SHIFT=1` 且 div 占 1 位；或把 phase 挪到 `reserved` 字节） | 动 SHM 里的路由表格式 ⇒ 影响 S3 兼容与既有校验和 |

★ **在修之前必须先做的一件事**：确认"相位只有 64 个"是不是**已知并被接受**的设计。
`engine.h:181` 的注释写着 `(BUCKET_DIV2_PHASES = 64, 与 6 位字段一一对应)` ——
而 `191` 行又把常量改回了 **100**。
**这两行注释互相矛盾**，很可能就是缺陷的来源：
**一次"改回 100"的修正，把"相位数"与"周期数"当成了同一个量。**

## 6. ★★★ 根因确认（读完 `engine.h:178-203` 之后）

### 6.1 设计意图是**明确的、且写下来的**

`engine.h:179-184`：
> **H723 的修法: 让宣称等于实现 —— div2 相位严格取 64 个
> (BUCKET_DIV2_PHASES = 64, 与 6 位字段一一对应)。**
> 桶表仍按 S3 的 220 × u16 保留 100 槽…但 **槽 64..99 恒为 0 是被断言的**。

`engine.h:199-202`：
> **现在: 周期 = 100 拍 (10ms) ✓; phase 字段仍 6 位 (0..63), 相位 64..99 恒空
> —— 这正是 S3 的真实形态。**

⇒ **意图是"相位数 = 64，槽 64..99 恒空"。** 这一点没有任何歧义。

### 6.2 但代码里"相位数"这个量被**一常量两用**，而两个用法要的值不同

```
engine.h:191   #define BUCKET_DIV2_PHASES  100     ← 被当成"相位数"用
engine.h:203   #define BUCKET_DIV2_PHASE_MAX 63    ← 路由 phase 字段上限（意图=64 个相位）
```

**同一个"相位数"，有两个常量，值不同（100 vs 64）**，而代码在两套地方各用一个：

| 位置 | 用哪个 | 因而产生的相位数 |
|---|---|---|
| `engine.c:991` `q2++ % BUCKET_DIV2_PHASES` （**生成路由相位**）| **100** | **100** ✗ |
| `engine.c:968` `s2++ % BUCKET_DIV2_PHASES` （数桶）| **100** | 100（与上面一致，但错在同一个地方）|
| `engine.c:591`/`501` `tick % BUCKET_DIV2_PHASES` （**扫描选相位**）| 100（但读的是 `period>>2 ≤ 63`）| 实际只有 64 会被选中 |
| `engine.c:409` 死槽检查 | `PHASE_MAX+1 .. PHASES` = **64..99** | 断言这 36 个必须为 0 |

★ **`engine.h:885` 还留着一条旁证**：
```c
#define OP_COST_DIV2  64   /* ★ 不是 100 (H9) */
```
**预算侧早就改成 64 了，并明确标注"不是 100"。而相位生成侧没跟着改。**

⇒ **同一个语义（div2 一个周期有多少拍／多少个相位）被存放在三处，取值 100 / 64 / 63。**

### 6.3 结论

> **这是一次"改了一半"的修正**：
> `engine.h:191` 把 `BUCKET_DIV2_PHASES` 从 64 改回 100（为了让**周期** = 10 ms），
> 但 `BUCKET_DIV2_PHASES` **同时**被当作"**相位数**"用于相位生成
> ⇒ 相位生成跟着变成了 0..99，而路由的 phase 字段仍只有 6 位
> ⇒ **槽 64..99 被填了（违反自己的断言），且那 36 条路由永不执行。**
>
> **`OP_COST_DIV2 = 64`（并注明"不是 100"）说明有人已经意识到这个分歧，
> 但只改了预算侧，没改相位生成侧。**

★ 这正是本项目最常记的那一族：**同一个语义两处（这里是三处）存放 ⇒ 静默失效。**

### 6.4 与实测的四条对齐（全部吻合）

| 预测（由根因推出） | 实测 |
|---|---|
| `n ≤ 64` ⇒ 相位 0..63 ⇒ 槽 64..99 恒空 | n=40/64：**全 0** ✓ |
| `n > 64` ⇒ 相位到 99 ⇒ 槽 64..99 被填 | n=100/128：**全 1** ✓ |
| 路由表 `period` 的相位被截到 0..63 | period = 2+4k，k=0..63 ✓ |
| 每拍只有 64 个相位可能被选中 | div2 n=128 扫描段 **205.6 TB ≈ 1~2 条**，不是 128 条 ✓ |

### 6.5 修复方案（**未实施**）

**最小改动**：把**相位生成**改用"相位数 = 64"，与意图和预算侧对齐。
即 `engine.c` 中 `q2++ % BUCKET_DIV2_PHASES`（生成相位处）应为
`q2++ % (BUCKET_DIV2_PHASE_MAX + 1)`，同理 `s2++ % ...`（数桶）与
`engine_fill_tables` 的 `g % BUCKET_DIV2_PHASES`（`engine.c:687`）。

★ **但"周期 = 100 拍"与"相位数 = 64"是两个不同的量**，
修的时候必须显式分开，例如引入 `BUCKET_DIV2_PERIOD_TICKS = 100` 与
`BUCKET_DIV2_PHASES = 64` 两个常量 —— **否则下一次还会有人把它们当成一个。**

★ **修完必须验证的三条判据**：
1. `n=128` 时 `cnt2[64..99]` **恒 0**（死槽断言重新成立）
2. 路由表 `period>>2` 覆盖 **0..63 各 2 次**（不再截断）
3. ★ **反证**：`n=128` 的 div2 程序，100 拍内**全部 128 条各跑 2 次**
   （当前是只有 92 条各跑 1~2 次）—— 这条要用 `nrun` 的**逐拍**统计来验，
   不能只看均值。

### 3.1 与固件自身不变量的冲突

`engine.c:400` `engine_bucket_dead_slots()` 断言：
> "死槽 = 相位 64..99（路由的 6 位 phase 字段到不了那里）… 这 72 个槽必须恒 0"

实测 `cnt2[64..99]` **全为 1** ⇒ **该函数此刻返回的不是 0（至少 36）**。

**⇒ 这条不变量在真实运行中可被违反，而它既没有报警、也没有拦住任何东西。**

### 3.2 一个已排除的解释

我此前猜 `q2`（写相位的计数器）是**跨 deploy 累积的静态变量**。
**已排除**：`engine.c:982` 是 `uint16_t cur0 = 0, q1 = 0, q2 = 0;` —— **局部变量，每次调用从 0 起**；
`cur1/cur2` 也每次从 `off1/off2` 重建（`978-980`）。

## 5. 与本轮主线的（不）关系

**这件事与"能不能算执行时间"没有直接关系**，但有两处牵连：

1. `engine_bucket_dead_slots` 是**死槽不变量的载体**；
   若它可被违反而不报警，那"桶表按设计构造"这条前提就少了一层保护
2. 我的模型用 `nrun = 非空桶数` 作为自变量 —— 而"非空桶数"正是**桶表**给的。
   若桶表与路由表不一致，**模型的自变量可能不是引擎实际跑的东西**
   ⇒ 这解释了 §4 里"低 `nrun` 区测不动"的一部分：**自变量本身可能就有噪声。**

⇒ **建议在继续做"能不能算"之前，把这个矛盾定界（用上面的第 1、3 条，都很便宜）。**

### 7.4 ★★ 残留代价（**已被 E-J 修正** —— 原文写错了）

> ⚠️ **本小节原文写的"每周期执行 1 或 2 次（抖动 2×）"是错的。**
> 由 `docs/exp-EJ-throughput.md` 的行为实测修正如下。

原文推理是"相位数 64 与周期 100 拍不整除"。**但周期根本不是 100 拍** ——
扫描器选相位用 `ph2 = tick % BUCKET_DIV2_PHASES_USED`，即 **`% 64`**
⇒ **一个完整周期是 64 拍**。

E-J 行为实测（`Δroutes / Δticks`）：

| 配置 | 实测吞吐 | 预测 | 偏差 |
|---|---|---|---|
| div0 n=128（反证）| **128.0000** | 128.00 | +0.00% |
| div1 n=128 | **12.8000** | 12.80 | −0.00% |
| **div2 n=128** | **2.0000** | 2.00 | +0.00% |
| div2 n=64 | **1.0000** | 1.00 | +0.00% |

实测桶表：64 个相位 × **每个恰好 2 条** ⇒ **每一拍都跑 2 条，没有空拍、没有抖动。**

⇒ **残留代价不是"抖动"，而是**：

```
div2 的实际扫描周期 = 64 拍 = 6.4 ms
而 DT_SLOW = 0.01f   = 10 ms        ⇒ dt 偏大 56%
```

**跑在 div2 上的 `TIMER`/`LPF`/`RATE`/`PID` 拿到的 `dt` 系统性偏大 56%**
（PID 的 `D = Kd*(err-prev)/dt` ⇒ D 项只有预期的 64%）。**且这是静默的。**

★ **这条已在同一天修掉**（见 §7.9）—— 修法是让 `DT_SLOW` **从扫描周期导出**，
而不是再写一个手写常量。

**权衡（修正后）**：
- **好处**：没有路由被静默丢弃；`dt` 与实际周期一致（派生，不可能各自漂移）
- **代价**：`div2` 的实际周期是 **6.4 ms**，与 `engine.h` 里"div2 = 10ms"的**宣称不符**
  ⇒ 若要让周期真等于 10ms，需要 100 个可寻址相位（phase 字段 7 位）。
  ⚠️ **但该后续项已被降级**：用户明确"周期后续会做成**可调**的"
  ⇒ 届时正确的做法是让 `dt` 跟着**选定周期**走（本节的派生式正好接住），
    **而不是**把相位字段扩到 100 去迁就一个固定的 10ms。

### 7.5 要彻底干净需要什么（**已降级**，见下）

**原方案**：把 phase 字段扩到 7 位 ⇒ 100 个相位可寻址 ⇒ 每相位每周期恰好 1 次、
周期真等于 100 拍。

可行性：`div` 只占 **1 位**即可，因为**索引 3 已被 `engine_route_validate` 拒绝**
（`engine.c:907`）⇒ `period` 是 u8 ⇒ `1 + 7 = 8` 位，**正好装下 100 个相位**。

⚠️ **但用户已明确：周期后续会做成"可调"的。**
⇒ 届时正确的做法是让 `dt` 与各档实际周期**跟着选定周期走**
（§7.9 的派生式正好接住），**而不是**把相位字段扩到 100 去迁就一个固定的 10ms。

**⇒ 本方案降级为"若将来仍需固定 10ms 周期才考虑"。**

---

### 7.9 ★★★ `dt` 与扫描周期错配 —— 已修（让 `dt` **派生**，不再手写）

**缺陷**：`DT_SLOW = 0.01f`（10 ms），而 div2 的实际扫描周期是 `64 拍 × 100µs = 6.4 ms`
⇒ **dt 偏大 56%**，跑在 div2 上的 `TIMER`/`LPF`/`RATE`/`PID` 全部受影响，**且静默**。

**修法**（`engine.h`）：**让 `dt` 由决定它的两个量算出来**

```c
#define TICK_PERIOD_US   100u      /* 拍长（µs）—— ★ 规划中此项将变为可配 */
#define DT_SLOW  ((float)BUCKET_DIV2_PHASES_USED * (float)TICK_PERIOD_US / 1000000.0f)
/* 展开 = 64 × 100 / 1e6 = 0.0064 s = 6.4 ms ✓ */
```

★ **为什么"派生"比"改成 0.0064f"好**：三者（**相位模数 / 拍长 / dt**）
从此**不可能各自漂移**；而且**正好接住"周期要变成可调"的规划** ——
调 `TICK_PERIOD_US` 或相位模数时 `dt` 自动跟着变，不需要有人记得同步改一个手写常量。

★ **两条编译期闸门**（能失败）：
```c
_Static_assert((float)BUCKET_DIV2_PHASES_USED * TICK_PERIOD_US <= 10000.0f,
               "div2 实际扫描周期超过标称 10ms ⇒ dt 语义会漂, 见 exp-EJ-throughput.md");
_Static_assert(BUCKET_DIV2_PHASES_USED > 0, "div2 相位模数不得为 0");
```

### 7.10 顺带确认：**预算侧本来就是对的**

`OP_COST_DIV2 = 64`（并注明"不是 100"）—— 它与**实际周期 64 拍**一致。
⇒ **预算侧无需改动；错的只有 `dt` 侧。** 这也解释了那条注释为什么会在那里：
**有人当时只把预算侧改对了，`dt` 侧漏了。**
