## 0. 先把边界说清楚：我们要的是**两层**，不是一层

```
┌────────────────────────────────────────────────────────────────────┐
│ ① 引擎核心 (Engine Core)          ← 烧录 (build.sh → pyocd flash)   │
│    boot / TIM2 硬拍 / ISR / 引擎扫描 / 19 原语 / 各外设驱动 / 协议栈 │
│    ★ 它是"平台"，不是"程序"。改它 = 换固件 = 一台新机器             │
├────────────────────────────────────────────────────────────────────┤
│ ② DCL 程序 (Program)              ← **通信上传** (0x10 / 0x44 / 0x41)│
│    路由表 + 参数 + 状态 + (顺序域) + (macro 字节码)                  │
│    ★ 它是"用户资产"。改它 = 一条命令，不碰 flash 代码区              │
├────────────────────────────────────────────────────────────────────┤
│ ③ 持久介质                        ← 掉电不丢，且**不是**代码区       │
│    现状：内 flash sector 6/7 双副本；★ 当前被降级 (见 §2.1)          │
└────────────────────────────────────────────────────────────────────┘
```

**这条分界就是你说的"不能走传统 flash 烧录"的正确形式** ——
烧录的是 ①，上传的是 ②，落盘的是 ③（③ 只碰数据区，从不碰代码区）。

★ 但 **这套分界目前只存在于代码里，没有任何一份文档把它写成契约**。
v2 最该补的就是这一份。

## 2. 五个必须先解决的硬事实

### 2.1 ★★★ 「程序持久化」现在是**不成立的** —— 交付档明确 NAK

```c
src/persist.h:87   #define DCL_PERSIST_SAVE 0    /* 0 = 保存不可用 (降级) */
src/main.c:2686    #if !DCL_PERSIST_SAVE
                       nak("persist: save disabled on this platform"
                           " (flash erase vs WDT; see docs/audit/H723-PERSIST-WDT-DEFECT.md)");
```

**原因**：擦 128KB 内部 flash 期间 **ISR 卡死 210.6 ms**（LA 实测）⇒ 喂狗停 ⇒ 看门狗复位
⇒ 旧行为是"**点保存 = 重启机器，且配置从未落盘**"。
现在的处置是**诚实降级**（宁可 NAK 也不谎报）—— 处置正确，但**功能确实没有**。

⇒ **v2 若宣称"程序可持久化"，第一件事就是把它修回来，或换介质。** 见 §4.1。

### 2.2 ★★★ 满配程序**刚好等于最大帧载荷** —— 一个字节的余量都没有

```
0x10 载荷 = [nr:u16][np:u16][ns:u16] + nr×16B + np×16B + ns×16B
          = 6 + 128×16 × 3 = 6 + 6144 = **6150**

FRAME_PAYLOAD_MAX = **6150**
```

**⇒ 满配程序塞不进任何额外字段**：没有版本、没有 CRC、没有清单、没有 program_id。
⇒ 想加"程序清单"，**必须同时改帧上限**（`FRAME_TOTAL_MAX = 6156`），或改成**分片上传**。

### 2.3 ★★ 三个**程序模型并存**，规则各不相同 —— 这是标准化最大的乱点

| 模型 | 上传命令 | 能热更新? | 要求 STOP? | 落盘? | 驱动位置 |
|---|---|---|---|---|---|
| 路由表（连续/逻辑域） | `0x10` | ✅ ≤1 拍 | ❌ | 登记 dirty（曾） | **ISR** |
| 顺序域 | `0x44` | ❌ 不热重载 | ✅ 必须 STOP | 登记 dirty（曾） | **ISR** |
| macro 字节码 | `0x41` | — | — | ⚠️ **口径未决**（`ARCH-H723.md` §11.1 #10） | **主循环** |

★ **macro 的循环由主循环驱动，间隔 = `max(loop_ms,10)×10` 拍** ——
这与我们刚定案的 **D2/D4（时基挂在主循环上）是同一条病**。
⇒ 若标准里保留 macro，必须先决定它算不算"实时程序"。

### 2.4 ★★ 能力位里**没有"外设"这一类** —— 这正是 I2C 事件的制度性原因

现有能力位（`DCL_CAP_H723_IMPL = 0x0DF7`）：`MULTICYCLE / HOTRELOAD / PERSISTENT /
STATE_COLD / WIRE2_FLAG / VERINFO / SEQ / FORCE / COMM / HMI / AI / MACRO`。

**没有 I2C、没有 SPI、没有 SD、没有 RTC、没有 CAN/ETH。**
⇒ 一个"要读 AS5600"的程序**无法声明自己的需求**，上位机**无法在下载前拒绝**，
只能跑起来之后才知道——而按本项目自己的判据纪律（"未实现的能力必须在**下载期**失败，
不能运行时静默给假值"，见 `SRC_HMI` 的处置），**这是不合规的**。

### 2.5 ★ 架构里其实**已经埋了正确的解法**，只是没做

```
macro VM 指令表 (ARCH-H723.md §8.1):
  0x20-0x23   SPI  **未迁移 → 返回 -4**     ← ★ 说明"通用外设事务 op"的思想早就有了
  0x10 load(addr) / 0x11 store(addr,val)     ← 通用内存访问
  0x06/0x07  忙等 N 周期 / N ms
```

⇒ **I2C 本可以做成 macro VM 的一个通用事务 op**（`0x20-0x2F` 区段：`START/STOP/WRITE/READ`），
那样"支持新传感器"就**不再需要改引擎核心**。
而实际走的是"**写一个专用驱动 `as5600.c` + 两条专用诊断命令 `0x39 op=17/18`**"——
**恰好是绕过了这条分界**（外设能力被做进了核心）。

## 3. 由此得到的**四层模型**（建议 v2 采用）

```
① 引擎核心 Engine Core        烧录        改它 = 换固件（要重新认证/回归）
② 外设能力 Peripheral Ops     随核心发布, **版本化 + 能力位声明**
   ← 通用事务型原语 (I2C/SPI/UART/CAN 事务), 而不是"每个芯片一个驱动"
③ DCL 程序 Program            **通信上传 + 持久化**
   路由表 / 顺序域 / (macro)
④ 程序工程 Project            上位机侧: .dcl 源 + 清单 + 编译产物 + 版本
```

**判据（用来决定"某个需求该放哪一层"）**：

| 问题 | 放哪层 |
|---|---|
| 它是"怎么算"（逻辑/连续/顺序）？ | ③ 程序 |
| 它是"和某个外设怎么说话"？ | ② 外设能力（**通用事务 op**），不是新的专用驱动 |
| 它需要新的**每拍**行为 / 新的实时保证？ | ① 引擎核心（**必须走 A/B 对照 + 12 套回归**） |
| 它只是"给上位机看的量"？ | 进 SHM + `obs_anchor()` 登记，**不是**加一条协议 op |

## 4. 建议（按优先级，供 v2 取舍）

### P0-A **持久化要有一条能走通的路**（三选一）

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **① SD 裸块存程序（推荐）** | 程序写成固定块（如 block N..N+k），用现成的 SD 裸块读写（黑匣子已验证） | **完全绕开内部 flash 擦除** ⇒ 不碰 ISR 卡死；**可拔插 ⇒ 程序可搬运**；天然是"程序文件"形态 | 需要 SD 在位；掉电时序要设计（双块 + seq，照抄现有 A/B 范式） |
| ② 修 ISR 卡死 | 继续追 210.6 ms 的真因（已排除 5 条静态假设） | 保内 flash 方案 | 未定案，工期不可控 |
| ③ 擦除与 ISR 解耦 | 擦除只在**深度停机**做，且把 ISR 的喂狗路径彻底移出 AXI | 保内 flash | 本质仍是"擦除期间系统不可响应" |

★ **我倾向 ①**：它同时满足你说的"不走传统 flash 烧录"，而且**把程序变成可携带资产**。
★ 无论选哪个，**判据必须是"掉电中断在任意时刻 ⇒ 重启后程序仍完整"**（A/B 单调 seq 已经给了结构性保证，照搬即可）。

### P0-B **给程序一个"包"和一份"清单"**

```
<name>.dclp  (程序包, 上位机侧)
├── manifest
│     prog_id / prog_version / author / created_at
│     min_fw_version          ← 低于此版本拒绝上传
│     required_caps (u32)     ← 缺位即在**上传期**拒绝
│     required_prims[]        ← 用到的原语清单（核心缺哪个就拒）
│     n_routes / n_params / n_states / payload_len / crc32
├── program.bin               ← 就是现在的 0x10 载荷（或分片后的形式）
└── source.dcl                ← 可选: 源文本, 便于现场改一行重编译
```

★ **能力位必须从 u16 扩到 u32**，并补上 `I2C / SPI / SD / RTC / CAN / ETH` 等位。
★ 上传协议建议改成**事务式**：`BEGIN(total_len, crc32) → DATA(chunk)×N → COMMIT`
⇒ 顺带解决 §2.2 的"零余量"问题（清单单独走一帧，不进程序载荷）。

### P1-A **把"外设能力"通用化**（I2C 事件的制度性修复）

- 在 macro VM（或新的"外设事务"区段）里定义 **通用事务 op**：
  `I2C_START/STOP/WRITE/READ`、`SPI_XFER`、`UART_TX/RX`，参数走现有 param 槽。
- ⇒ "支持一个新传感器" = **写一段程序**，而不是"改固件 + 重新烧录 + 重跑 12 套"。
- ⇒ 同时消掉 `0x39 op=17/18` 这种"专用诊断命令长在协议上"的形态。
- ★ 安全边界不变：仍受 macro VM 现有的**裸地址守卫 / 非有限值守卫 / pc 越界检查**约束。

### P1-B **三个程序模型收敛出口径**

至少要在文档里写死：**哪个是"一等程序"，哪些是"辅助"**。建议：

- **一等 = 路由表 + 顺序域**（走 ISR、有预算门、有静态校验、可热更新/可持久化）；
- **辅助 = macro**（走主循环 ⇒ **明确标注"不保证实时"**，并且**不参与持久化**，
  或者干脆把它也移进拍内 —— 二选一，别含糊）。

### P2 **统一"未实现能力"的失败语义**

沿用 `SRC_HMI` 已经立下的好范式：
> **未实现的能力必须在下载/上传期失败，不得在运行时静默给一个恒 0 的合法值。**

推广到：能力位、原语、外设事务 op、程序清单里的每一项"要求"。
并且**每一项都要配一条能失败的判据**（本项目铁律 2）。
