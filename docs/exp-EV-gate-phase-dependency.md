# exp-EV —— 闸门摊薄口径的**隐含依赖**：它凭什么成立，以及它差一点被我改错

> 一句话：我一度认定预算闸门有个"真洞"（闸门算**摊薄**、运行期约束是**每拍**），于是把闸门改成"最坏相位桶"口径；
> 实测把我推翻了 —— 128 条 PID **全部写成 phase 0** 部署进板子，实测扫描段最大只有 **262 cyc**（若真挤在一个相位应是 ~10⁴ 量级）。
> 根因：`engine_stage_program` 尾部**覆写**载荷里的相位。结论有两条，都不是我原先想的那条：
> ① 摊薄式**是对的**（前提是轮转铺开，而固件确实轮转）；② 而那个前提是**另一处的一个未声明性质** —— 一条看不见的跨函数依赖。
> 我按"载荷相位"重写的那一版会**误拒**合法程序，最多差 **64×**。已回退，并把依赖写成判据（本工具）。

- 工具：`tools/exp_ev_gate_worst_phase.py`
- 指纹：`6daa7e65…`（未改一行固件；本项**纯判据 + 一行注释**）
- 相关：`docs/PLAN-completion-2026-09-18.md` 3.1 · `RETRACTIONS.md` P31 · `MEMORY.md` 5.92

## ① 我原先的判断（**错的**）

`engine_prog_budget()` 用 `Σ ceil((op_cost + src)/mult)` 估预算 —— **摊薄**口径：一条 div2 路由按 `成本/64` 计入。
而运行期判据 `EXEC_BUDGET_CYCLES` 是**每拍**口径（一拍内实际跑了多少）。

⇒ 我当时的推理：**若某档路由挤在同一个相位，那一拍要跑全部**，而闸门只算了 `1/64` ⇒ 闸门放过了会超载的程序。
听起来无懈可击，而且"闸门静默放宽"正是本项目最怕的一类（P24/P25 同族）。

**实测否掉了它。** 128 条 PID、`per = div2 | (0 << 2)`（全 phase 0）部署：

| 量 | 实测 |
|---|---|
| 部署结果 | ACK，device budget 384 |
| 扫描段最大 | **262 cyc**（若真挤在一个相位，应是 128×200 ≈ 2.5×10⁴ 量级） |
| 桶表 cnt2 前 6 槽 | `[2, 2, 2, 2, 2, 2]` —— **均匀铺开**，不是 `[128, 0, 0, …]` |

## ② 根因：`engine_stage_program` 覆写相位

`src/engine.c` 装载尾部（约 1071 行）：

```c
uint32_t ph = q2++ % BUCKET_DIV2_PHASES_USED;   /* ★ 固件自己轮转到达度 */
r.period = dv | (ph << 2);                       /* ★ 载荷带的相位被丢弃 */
```

即：**固件按"桶内到达序"轮转铺相**，载荷里那 6 位相位**被忽略**。
⇒ 于是两条真结论：

1. **摊薄口径是对的** —— 它成立的前提正是"轮转铺开"，而固件确实这么做；
   而且 `ceil()` 的取整方向使它成为最坏桶的**上界**，余量 ≤ 一条路由的成本（实测 94 ≤ 145 cyc）。
   ⇒ **已验过的边界（FLASH DIRECT 105/106、PID 60/61）不受任何影响。**
2. ★★ **但那个前提是"另一处的一个未声明性质"**：闸门与 staging 之间有一条**看不见的依赖**，
   没有任何断言牵连它们。若哪天有人把轮转改成"按载荷相位分配"（一个看起来更尊重用户意图的改动），
   闸门就会**静默变宽 64×**，而两条判据都不会响。

## ③ 被我回退的那一版会干什么

按"载荷相位"算最坏桶 ⇒ 128 条 PID div2 = `128 × 432 = 55296` ⇒ 超门 26000 ⇒ **NAK**。
它会**误拒**这条实际最坏桶只有 `2 × 432 = 864 cyc` 的合法程序 —— 差 **64 倍**。
⇒ 拿"被忽略的输入"去算一个本该由固件分配的量，是把**不可控**当成**可控**；已回退。
`src/engine.c` 的摊薄公式恢复原状（指纹回到 `6daa7e65…`，逐字节不变），并在 `engine.c` / `engine.h` 各留一段注释，
把这条依赖**写下来**。

## ④ 判据（都能失败）

| # | 判据 | 凭什么能失败 |
|---|---|---|
| V1 | div0-only 程序：设备预算 == 摊薄式（`mult` 就是 1，∴ 与最坏桶式**逐位相等**） | 若有人把 div0 也除以相位数，这里立刻不等（**本工具第一版就是这么错的**） |
| V2 | ★★ 载荷相位被忽略：同一程序全 phase 0 与全 phase 63 ⇒ **同一张桶表** | 若 staging 改成尊重载荷相位，两张表立刻不同 |
| V2′ | 两次部署的 device budget 也相同 | 同上 |
| V3 | 轮转铺开：`cnt2[i]` 与 `i % 64` 的轮转分布**逐槽吻合**（n=128 ⇒ 每槽 2 条） | 任何非轮转分配都会逐槽不等 |
| V3′ | 死槽 `cnt2[64..99]` 恒 0（桶表有 100 槽、只用 64 槽） | 若固件写了 64 槽以外，和 ≠ 0 |
| V4 | ★ 摊薄式 ≥ 最坏桶（实测 384 ≥ 2×145 = 290） | 这是"闸门是不是上界"的直接检验；改错口径这里就 FAIL |
| V4′ | 余量 ≤ 一条路由成本（94 ≤ 145）—— `ceil` 取整的固有松弛 | 若余量能超过一条路由，说明摊薄式**不是**紧上界 |
| V5 | FLASH 档：128 条 PID div2 摊薄式 896 ≥ 轮转最坏桶 2×432 = 864（不会误拒） | 单条成本与桶条数都**现读/现算**，成本表一变判据跟着变 |

**结果：9 项判定 / 0 FAIL / 0 SKIP。**

> ★ 本工具的 V5 **不写死任何 cyc 数**：单条成本读 `k_op_cost_flash[PID]`，桶条数算 `ceil(128/相位数)`。
> 第一版 docstring 里手写过一个 `452`（真值 432）—— 同一文件里一个会漂移的硬编码，已删。

## ⑤ 诚实标注

- 闸门仍是**静态**判据（部署时判），运行期判据是 `EXEC_BUDGET_CYCLES`（`ov` 计数器），二者**不可互相替代**（P25）。
- 本项**没有**让闸门变得更严或更松：它证明的是**改它会是错的**。真正的交付物是那条**依赖的显式化**。
- 交付档（ITCM）闸门**结构性不触发**：算得边界 464 > `MAX_ROUTES=128` ⇒ `128×56 = 7168` = 门的 28%（E-U ⒂）。
  本条只对 FLASH 档有实际约束力。
