5期间抓到的真缺陷（审计重点）

★★ 外部审计 8 项发现（2026-09-11，全部核实为真并已处置）
A(P2) 工具类型 bug：h723_w1.py:128 的 bytes(buf[1]) 对 int 求 bytes → sts != STS_ACK 恒真 → T0 永远 FAIL、直接 return → W1 六条命令此前一行判据都没执行过。修复后 28/28 PASS。
危害不在"工具坏了"，而在它让纪律静默失效，且失败信息把人引向"串口/固件"（方向相反）。

B(P2) 6 项判据与固件语义不符：S5 预算算错（128×140=17920 < 26000，与 persist T24 自相矛盾）、 S2 用错量（读的是拍中断数，STOP 不停拍）、S1b 读非对齐地址被守卫正确拒绝、 R2 未考虑引擎每拍覆写 WIRE_MAP、R9 地址其实没越界、R1 归因到固件。

C/D/E/F/G/H (P3)：MAGIC 未写 · 条数双来源不一致 · 寿命注释差 10 倍 · flash_lock() 漏在失败路径 · 成本注释未同步 · GPIO 掩码位映射语义错。

★ 增量：把 C 做系统化自查后，另查出 10 个同类死字段 （VERSION / HEARTBEAT / TIMING×6 / GPIO_MASK）—— "定义了却从不写入"是一类问题，不是孤例。
★ 采纳审计建议：新增 T0c 工具自检闸门（未实现命令必须回 NAK）， 直接防住 A 那一族 —— 只要 sts 通道退化就当场失败，不再让 40+ 判据白跑。

详见 docs/audit/H723-W1W2W3-RESPONSE.md（含我方接受的 3 处更正）
W3 · 步号镜像初值缺失（移植遗漏，已修）
S3 main.c:918 在 START 时写 wm[out_wire] = 1.0f，H723 第一版漏了这句。 后果不是"少个功能"，而是宣称≠实现：停在 step0 期间 out_wire 上是上一个程序的残值（实测 boot profile 的 0.01）。 语义层"镜像反映当前步号"是假的；功能层若译码路由写 CMP(步号<1.5) 或 DIRECT，第一步期间会读到残值并输出错误的执行器信号 —— 只有 CMP(>1.5) 是恰好正确的。
抓出方式：T28.B1「起点快照」判据（期望 1.0，实测 0.01）。只测"推进后对不对"永远发现不了这类缺陷。
W2/W2.4/W3 · 能力位三处不同步（已修）
tools/h723_proto.py 的 EXPECT_CAP 停在 0x0033，三次落地（PERSISTENT / FORCE / SEQ）都漏同步。 属 A4 事故同族 —— "两处手工同步，改一处必忘另一处"。已改为 0x00F7，并写明纪律。
审计建议：检查是否还有第三处手工同步的能力位副本。
W2.4 · H7 Flash 编程粒度（已修，含判据）
H7 编程粒度是 32B 的 8×u32 连续写，非 32 位独立写。错误标志 PGSERR(bit18) + INCERR(bit21) = 编程序列被打断。 修复后掉电判据（擦除中复位）5 项全绿。
W3 · 单核竞争窗口（设计修正，非缺陷）
S3 是 core0 写 / core1 扫，靠 memw 排序，顺序是"先置 RUN 再写 ctrl"。 H723 单核：先置 RUN 会让 ISR 在写完 ctrl 前推进步号，随后被写回的 step_cur=0 静默吞掉一次真实推进。 ⇒ 改为"先把 ctrl 与镜像备好，最后才开 RUN 门"，竞争窗口归零。 这是照搬语义、不照搬时序的判例。
