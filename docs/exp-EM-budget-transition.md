# E-M 把转变项加进门的预算（2026-09-18）

> 背景：E-L 实测证明 `engine_prog_budget()` 的**纯可加**形式**系统性低估、永不反向**
> ⇒ **它不是上界** ⇒ 做门会**放行实际超载的程序** —— 与项目前两代成本模型
> （标量 3.03、`min` 口径表，`RETRACTIONS.md` P24/P25）**同一方向的错**。

---

## 1. 改动

### 1.1 `engine.h`：新增 `OP_TRANS_COST`

```c
#define OP_TRANS_COST          25    /* cyc；每次"相邻 op 不同"计入一次 */
```

**取值依据（不是拟合值）**：

| | 值 |
|---|---|
| E-L 实测每转变成本 | 8.50 → 5.56 cyc（随块变小而降），严格交替 **1.29** |
| **最小安全系数**（使 `纯可加 + k×转变数 ≥ 实测` 处处成立） | **17.8 cyc** |
| **本常量** | **25 cyc** = 17.8 × **1.40** |

★ 为什么不用拟合值：每转变成本**不是常数**（是"程序形状"的函数，见 E-L §3），
所以取"最小安全系数 × 余量"。1.4× 的余量与项目别处的口径一致（65% 门、80% 预算）。

### 1.2 `engine.c`：`engine_prog_budget()` 加转变项

```c
uint8_t prev_op[3];  uint8_t have_prev[3] = {0,0,0};
for (...) {
    ...
    per += ⌈(engine_op_cost(r.op) + s + mult - 1) / mult⌉;
    uint32_t g = (dv <= PERIOD_DIV_IDX_SLOW) ? dv : 0u;      // 按 division 分组
    if (have_prev[g] && prev_op[g] != r.op) trans++;          // 组内按到达序
    prev_op[g] = r.op;  have_prev[g] = 1u;
}
return per + trans * OP_TRANS_COST;      // ★ 转变代价**不除 mult**
```

★ **计数口径与计算口径一致**：按 division 分三组、组内按到达序 ——
与 `engine_stage_program` 的分桶**同一口径**（它也是按档分别 `q1++/q2++` 轮转）。

★ **转变代价不除 `mult`**：每次转变是在**某一拍内**真实发生的（该组本拍执行），
⇒ 它已经是"每拍"口径，与 `per` 同量纲，直接相加。

★ **代价**：部署期一次 O(nr) 扫描，**零运行期代价**。

## 2. ★★★ 验证：预算算术**逐位相等**（M-1 通过）

`engine_prog_budget` 的返回是**纯算术**（无测量参与）⇒ 每个配置都能手算，
与固件回读的 ACK budget **逐位比对**：

| 配置 | 条数 | 转变数 | 手算 | 固件 | |
|---|---|---|---|---|---|
| 全 PID | 128 | 0 | 18560 | **18560** | ✅ |
| 全 DIRECT | 128 | 0 | 7168 | **7168** | ✅ |
| 64 PID + 64 DIRECT | 128 | 1 | 12889 | **12889** | ✅ |
| 2 PID + 2 DIRECT | 4 | 1 | 427 | **427** | ✅ |
| 1 PID + 1 DIRECT | 2 | 1 | 226 | **226** | ✅ |

**M-2 反证**：混合程序（12889）**大于**全 DIRECT（7168）⇒ 与 E-L 实测方向一致 ✅
**M-3 门仍不具约束力**：128×(145+25) = **21760 ≤ 26000** ⇒ 绊线断言保持 ✅

### 2.1 ★ 脚本自己抓出了我一个错误假设（值得单独记）

第一版脚本**手写** `SRC_COST = 20`，结果 5 个配置**全部差 `n × 20`**：

```
全 PID      手算 21120  固件 18560  差 -2560 = -128×20
全 DIRECT   手算  9728  固件  7168  差 -2560
```

**"差一个与 n 成正比的量"正是 `src_cost` 项的特征** ⇒
脚本内置的反推（`budget/128 − 145`）把它抓了出来：**`k_src_cost[CONST] = 0`**。

读源码确认：`static const uint16_t k_src_cost[4] = { 0, 0, 0, 0 };`

⇒ **修法**：脚本改成**从源码读常量**（`k_op_cost_itcm` / `k_src_cost` / `OP_TRANS_COST`），
不再手写。**改完 5/5 逐位相等。**

★ **教训**：**验证脚本里的常量必须从被测源码读，不能手写。**
这与本次会话里"硬编码 SHM 地址 / 硬编码跳转表地址"是**同一族的第三次** ——
手写的常量会在源码变更时**静默失效**，而失效的表现是"判据报错"，看起来像被测对象坏了。

## 4. 意义与边界

### 4.1 这一步是什么性质

**是安全性修复，不是优化。**

- 交付档（ITCM）的门**本来就不具约束力** ⇒ 本改动对交付行为**零变化**
- 它的作用是：**在扩容 / 加重量级原语 / 换 FLASH 档时，不让门变成"会放行超载"的假门"**
- FLASH 档的门**是具约束力的**（128×432 = 55296 > 26000 ⇒ 它真的会拦）
  ⇒ 那里加转变项让拒绝更保守，**方向正确**
