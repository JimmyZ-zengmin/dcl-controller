# exp-EY —— 3.4 `LUT` 的最小验证：**表到底住在哪**（先量，再决定架构）

> 一句话：PLAN 3.4 原来只有一句**侦察结论**（"表不在程序里"）。本项把它变成**能失败的事实**：
> `0x23` 今天就能把表写进板子，但 **`0x10 deploy` 不碰它、SD 程序包不带它、`0x13 RESET` 清零它**，
> 而 `engine_fill_tables()` 会在冷启动时用**斜坡**覆盖它。⇒ 表现在是**一块无主的易失内存**。
> 三条架构路线的代价已在下面摆开；**本轮不做决定**（PLAN 明说这是架构决定）。

- 工具：`tools/exp_ey_lut_provenance.py` —— **8 项判定 / 0 FAIL / 1 SKIP（历史依赖，显式排除）**
- 改动：**零**（纯验证；固件与 dclc 都没动，指纹 `6daa7e65…`）

---

## ① 实测事实（都能失败）

| # | 判据 | 实测 |
|---|---|---|
| Y1s | `engine_reload_active()`（deploy 的生效路径）**不含** LUT | 正文 30 行，出现 LUT 的行 = **0** |
| Y2s | 持久化镜像 payload 只覆盖 routes+params+states | `PERSIST_PAYLOAD_MAX = ((MAX_ROUTES+MAX_PARAMS+MAX_STATES)*16u)` = **6144 B**，无 LUT |
| Y3s | 程序包唯一的附加段是 dev_bind | `dev_bind_pack` 追加一段；全仓**无** `LUT_SEG` |
| Y4s | ★ `engine_fill_tables()` **会写 LUT 斜坡** `lu[i]=(i&0x3F)*0.1f` | 在；而 `g_reinit=1` 全仓**无人写**（钩子在，路径存在） |
| Y5 | ★ 主机能把表写进板子 | `0x23` ⇒ **ACK**，回读 **0/256 字不同** |
| Y6 | ★ `0x10 deploy` 之后 LUT **逐字节不变** | 不变 = True |
| Y6′ | 负对照：同一次 deploy 之后 **routes 区确实变了** | 变了 = True（否则"不变"可能只是"整块 SHM 都没动"） |
| Y7 | ★ `0x13 RESET` 之后 LUT **全 0** | 非 0 个数 = **0** |

⇒ **表的生命周期**（全部由源码+实测确认）：

```
冷启动:  cold_start_reset() 整段 memset ⇒ LUT = 0
         有持久化配置 → persist_load() 只恢复 routes/params/states ⇒ LUT 仍是 0
         无持久化配置 → engine_fill_tables() 铺**斜坡** ⇒ LUT = (i&0x3F)*0.1
0x23:    主机写什么就是什么（今天唯一能设置表的途径）
0x10:    不碰 LUT
0x13:    整段 memset ⇒ LUT = 0（表没了）
掉电:    没了（RAM）
SD A/B:  不带表 ⇒ 上电装载后也不会恢复表
reinit:  若哪天有人启用 g_reinit ⇒ fill_tables 会把主机写的表**静默覆盖成斜坡**
```

## ② 一条被**显式排除**的观察（★ 这是计划 4.3 的现场样本）

第一次跑本工具时，"现状"读到的是 **冷启动斜坡**（`0.000 / 0.100 / 0.200 / 0.300 …`）；
第二次跑读到**全 0** —— 因为第一次跑完的 Y7 刚做过 `0x13 RESET`。

⇒ 这条观察说的是**板子的历史**，不是**固件的性质**，且**无法在单次会话内复现**（要一次真实掉电）。
按纪律它**不能进判据表**（否则会周期性"看起来像回归"，同 `h723_step_ramp_test.py` 的 R5）：
本工具把它打成 `[SKIP]` 并在表外单列。**这是 PLAN 4.3 要机制化的东西的第一个真实样本。**

## ③ 三条架构路线（代价摆开，本轮**不拍板**）

| 路线 | 做法 | 代价 | 代价的**证据** |
|---|---|---|---|
| **A. 扩 deploy 载荷**（推荐） | 在 deploy 载荷**尾部追加一个 LUT 段**（与 dev_bind 段的现有约定完全同款：末尾段 + 长度字 + 魔术字 + 老包无段则跳过） | 固件：段解析 + 校验（可复用 `dev_bind_unpack` 的形态）；`dclc`：多输出一段 | 载荷上限 `DEPLOY_REQ_MAX` / `PROG_PAYLOAD_MAX 7680 B` —— 1024 B 的表装得下；老包兼容有现成范式（`DB_SEG_NONE`） |
| B. 进持久化镜像 | 扩 `PERSIST_PAYLOAD_MAX` 含 LUT | 镜像格式改 ⇒ **版本升级 + 老镜像兼容**；且 `0x13 RESET` 清 SHM 后要么重填、要么"复位即丢表" | `PERSIST_VERSION 0x0200` 是**要动的字段** ⇒ 影响 A/B 双副本与单调 seq |
| C. 声明"表由上位机每次重下" | 零固件改动；把"deploy + 上传表"做成工具侧约定 | ★ **表与程序会不同步**：有人只 deploy ⇒ 程序读到**上一张表或零表**（静默错，LUT 原语会把 0 当合法值） | 本次实测：deploy 之后 LUT 保持旧值 ⇒ 这个风险是**可达的**，不是理论 |

**推荐 A 的理由**（只说可核对的部分）：deploy 已经是"配置生效"的**唯一入口**；
把表并进去 ⇒ "程序生效"与"表生效"**同一时刻、同一原子性**，不留第二条路径；
且**不需要**碰持久化格式（掉电后表与程序一起丢，二者仍然一致）。
★ 但 A 仍要回答一个语义问题：**`0x13 RESET` 之后表该不该回来**（照现在的语义：不回来，与 routes 一致）。

## ④ 诚实标注

- 本项**没有**让 LUT 变得可用：它证明的是"**今天它住在无主的易失内存里，且能被静默覆盖**"。
  `LUT` 原语本身一直是通的（`prim_lut` 线性插值，越界夹取），缺的只是**表的所有权**。
- `fill_tables` 覆盖 LUT 这件事**今天不可达**（`g_reinit` 无人置 1）—— 如实标注，
  它的意义是"路线 A/B 都必须顺手决定 reinit 的语义"，而不是"现在就有一个 bug"。
- 本轮**没做** `MOD`（引擎无此模式）与 `LUT` 暴露的**实现**（等架构决定）。
