# PLAN-consistency-v1 —— 把"一致性"从人身上搬到机器上

- 日期：2026-09-16
- 起因：`docs/RETRO-standardization-2026-09-16.md`（设计目标已达成，但暴露 1 个结构性缺口 + 4 项挂账）
- 性质：**执行稿**。与 `PLAN-DEV-continuous.md`（W1–W5 迁移，已完成）**不重叠**：那份解决"命令覆盖"，
  这份解决"**改完之后还对不对得上**"。

---

## 0. 我的判断（先说结论，再说依据）

**这个项目现在的瓶颈不是功能，是"一致性"**。依据是这一轮的实测分布：

| 现象 | 次数 | 说明 |
|---|---|---|
| 真正"功能没做"的缺口 | **1**（GAP-11 绑定表持久化）| 其余全是"做了但对不上"|
| **契据 vs 实现不一致** | **5** | 两轮独立审计查出；全部是**人能发现、机器没发现**的 |
| **静默错数据类真缺陷**（无报错、只有值错） | **6** | 全部是"判据存在但不覆盖那条路径"|
| **我自己引入又自己修** | **3** | 说明判据在起作用，但也说明**一次成形率不高** |

⇒ **推论**：继续加功能，收益会被"漂移 + 静默错"吃掉。**先把一致性变成机器的事，再谈功能。**
这也是我把 C1 排在最前面的唯一理由 —— **它零行为变化，却保护后面每一次改动。**

## 1. C 线（P0）：契据可机检化 —— 把人工审计变成第 5 道闸门  ✅ **已完成（2026-09-16）**

> 落地物：`docs/claims.md`（五类可机检主张）· `tools/ref_claims_check.py`（含 `--selftest` 7 用例 + 覆盖度自报）
> · `build.sh` 第 5 道闸门。实测：真仓库 **RC=0**（A 12/B 7/C 11/D 43/E 10 全达标，13 条行号漂移告警）；
> 自测 7 用例全对（1 绿=0 / 5 注入=2 / 1 覆盖不足=1）。
> ★ 首次接入即**报出真发现**：`DB_RC_NOSEQ` 在 `src/*.c` 里从未被赋值；2 份文档引用了本仓不存在的文件。
> ★ 现有 3 项**显式声明**的未覆盖（`DB_RC_SEQ` / `DB_RC_DST` / `DB_RC_NOSEQ` 的判据，以及 §3.8.8-3/6）
>   —— 全部带理由，无一条"沉默地留着"。

### 1.1 为什么
现在"契据 §X 说要 A、代码里到底有没有 A"**只能靠人读**。两轮审计各查出数条不一致，
其中还有**契据自相矛盾**（"拒绝也回 `done_seq`" vs 码2"不回 `done_seq`"）——
这种矛盾人工读两遍都可能放过，**机器一跑就红**。

### 1.2 做法：`docs/claims.md`（主张登记表）+ `tools/ref_claims_check.py`
每条主张写成**可机检形式**，分五类：

| 类 | 机检形式 | 例 |
|---|---|---|
| **A. 结构** | 契据声称的每个 `OFF_*` 必须在 `src/engine.h` 出现，**且被至少一条 `_Static_assert` 引用** | `OFF_DEV_BIND` ✓ |
| **B. 拒绝码** | 每个 `DB_RC_*` 必须：① 定义 ② 在 `.c` 被赋值 ③ **验收脚本里有一条判据会读到它** | 本轮发现 `DB_RC_DST`/`DB_RC_NOSEQ` 是**死码** ⇒ 必须标 `uncovered` 而不是默认"已验证" |
| **C. 能力位** | 每个 `DCL_CAP_*` 必须：① 定义 ② 在 `DCL_CAP_H723_IMPL` 里 ③ `proto_dispatch` 有对应 `case` | 防 A4 事故（实现了却不报 / 报了却没实现）|
| **D. 文档引用** | 文档里的 `src/x.c:NNN` 必须**仍指向同一符号**（漂移检测）| 本轮多处 `file:line` 已随改动漂移 |
| **E. 判据存在性** | 契据"能失败的判据表"里每个编号，必须在验收脚本里 grep 到同名 `record("…")` | §3.8.8 的 8 条 ⇄ `h723_dev_bind_test.py` |

### 1.3 验收（每条都能失败）
- **闸门接入 `build.sh`（第 5 道）**，规格与既有两个闸门**相同**：`--selftest` + **覆盖度自报**
  （覆盖不足 ⇒ 判 **无效**，不是"干净"）。
- **能失败的对照（必须做）**：故意在契据里加一条"声称存在但代码里没有"的字段 ⇒ 闸门必须红；
  故意把某个 `DB_RC_*` 的判据删掉 ⇒ 该类必须报 `uncovered`。
- **零行为变化**：只读源码 + 文档，不碰固件逻辑。

★ **它顺带解决一个更隐蔽的问题**：今天"契据里写了但代码没做"（如 §3.8.5）只能靠人发现，
**而人一旦没发现，下一个人就会按契据去改，从而改坏**（本项目原话："契据漏写等于下一次有人照契据改就会改坏"）。

## 2. W 线（P1）：线上格式 v1 —— **三件事捆成一次迁移**  ✅ **已完成（2026-09-16）**

> 落地物：v2 帧（`0xC2`/`0xC3`，应答回显 `CMD+SEQ`）· `0x05 FRAME_MODE` 协商 ·
> 能力位 `DCL_CAP_FRAME_V2=0x4000`（实现字 `0x3DF7` → **`0x7DF7`**）· `0x39 op=24`（读设备侧模式）。
> 验收 `tools/h723_frame_attrib_test.py` **18 PASS / 0 FAIL**；契约 **§9.4**；**GAP-12 closed**。
> ★ **v1 一字未改**（与本工具独立构造的期望帧逐字节相同）⇒ 老上位机零改动。
> ★ 副产品：填掉 `s_txbuf` 越界 2 字节的风险；C2 完整性闸门第一次在真实场景生效（抓到我漏登记新能力位）。

### 2.1 为什么必须捆在一起
`GAP-3`（能力位扩 u32）与 `GAP-12`（应答带归属）**都要动帧格式**。
分两次做 = 付两次迁移成本、且两次都要重新验证所有上位机。**一次做完。**

### 2.2 GAP-12 为什么现在必须做（它的危害已被实测）
应答里**没有命令码回显、也没有序号** ⇒ 客户端"收到任何合法帧就当应答"。
本轮**首次拿到解码过的现场实例**：密轮询 `0x22` 读 1 个字时，读回值位型 `0x1DF70200`
= 低16位 `fw_ver 0x0200` + 高16位 `cap 0x1DF7` —— **一条 `0x01` 的应答被当成了 `0x22` 的读取值**。
★ 最坏巧合：`0x22` 读 **1 个字**的应答**也是 4 字节**，与 `0x01` 完全相同 ⇒ **长度判据也分不开**。
⇒ 这类故障**不可自动归因**（我为此花了半小时解码），而且会**直接污染判据**（它已经污染过一次）。

### 2.3 方案：**新帧类型 + 协商**（旧上位机零改动）
```
新命令  0x05 FRAME_MODE  [mode:u8]   mode=1 ⇒ 进入 v2 帧
```
★ **`0x05` 已核为空闲**（实测 `src/transport.h` 现有命令码：`0x01` · `0x10–0x13` · `0x20–0x24` ·
`0x36–0x39` · `0x40–0x4A` · `0x51–0x53` · `0x60–0x62`；`0x05` 无定义、全仓 0 处引用）。
★ 选**新的小号段**而不是往 `0x20`/`0x40` 里塞：请求"进入另一种帧格式"是**传输层**的事，
   与业务命令分层（本项目的分层纪律同样适用于协议本身）。
```
v1 帧   [SYNC 0xC0/0xC1][CMD][LEN:2][PAYLOAD][CRC16]              ← 今天的样子, 不协商就一直用它
v2 帧   [SYNC 0xC2][CMD][SEQ:u8][LEN:2][PAYLOAD][CRC16]           ← 应答与请求都带 [CMD][SEQ]
能力位  DCL_CAP_FRAME_V2 = 0x2000
```
- **旧上位机**：不知道 `0x05`（会 NAK）⇒ **行为逐字节不变**（这是本项目对"协议一变上位机全废"的既有纪律）。
- **新上位机**：协商后每条应答都带 `[CMD][SEQ]` ⇒ 可以**判归属**、"乱序重排"、"重复丢弃"。
- ★ 为什么不用"给热点命令各加一条带归属的变体"：那只护住用了它的路径，**其余仍是弱判据**（就是今天的现状）。

### 2.4 验收（每条都能失败）
1. **不协商** ⇒ 帧与 v1 **逐字节相同**（A/B：同一请求两版客户端抓包比对）。
2. **协商后** ⇒ 每条应答带 `[cmd][seq]`；客户端能判"这条是不是我的"。
3. ★ **决定性对照**：跑 T8 那种密轮询时，**另开一个进程**发 `0x01`
   ⇒ **v2 客户端必须拒收那条杂帧**（v1 客户端会误收 ⇒ 这一对就是"能失败"的证明）。
   —— 这就把本轮那个"花半小时解码"的假故障，变成一个**当场失败**的判据。
4. 能力位 `DCL_CAP_FRAME_V2` 走 C 类机检（定义 / 并入 / 有 case）。
5. `cap` 扩 u32：`0x01` 在 v2 模式下返回 u32；v1 模式**保持 u16**（兼容）。

## 4. 进程修正（**立即生效，不排期**）—— 4 条全是本轮真踩的

1. ★★★ **串口是独占资源**：同一时刻**只允许一个** worker/脚本使用。本轮我让两个 worker 抢 `COM21`，
   结果**一个错误以三种面貌出现**（一次串帧假故障 / G6-2 顺序依赖被误读 / 一次 `SENSOR[15]=7.5` 假命中）。
   ⇒ 套件加"端口占用即退让重试"；任务模板写明"板子独占"。
2. ★★ **新判据自检三问**（写进套件模板，缺一条不许合）：
   ① 这条判据**能失败**吗？什么条件下红？ ② 它用的**槽/寄存器还有谁在写**？
   ③ 它区分的是哪两个假设（**回归判据 ≠ 归因判据**，后者必须钉住版本与前置状态）？
3. ★★ **状态复原放 `finally`**（判据 FAIL 时也要还原）；**新增判据必须配变异对照**
   （复用 `h723_dev_bind_test_selftest.py` 的假固件模式）。
4. ★ **提交前 `git diff --cached` 核对**，提交信息只描述"代码里实际是什么"；
   **契据改动必须同时落一条可机检断言**（C 线的入口）。

★ 另：**技能整理** —— `h723-baremetal-port` 与 `baremetal-periph-align-to-vendor-ref` 边界已重叠，
建议合并；我只提醒，不擅自改别人的技能。

## 5. 顺序与理由

| 序 | 做什么 | 为什么排这里 |
|---|---|---|
| **1** | **C 线**（机检闸门）| **零行为变化、零风险**，且它保护后面每一次改动；越晚做，欠的"人工审计"越多 |
| **2** | **P1-1**（绑定表持久化）| 唯一的"功能真缺口"，且**不碰线上格式**，可以独立交付 |
| **3** | **W 线**（v1 一次性迁移）| 等 C 线就位后再动线上格式 ⇒ 迁移期每条断言都可机检（否则迁移本身就制造漂移）|
| **4** | **P2-2 / P2-3** | 文档生成与诊断补齐，可与 W 线并行（不同文件面）|
| **5** | 技能整理 | 不影响交付，最后做 |

## 6. 明确**不做**（避免把力气花在收益量不出来的地方）

- **不新增 ③层程序语言特性**：一致性没解决前，加功能只会**放大漂移面**。
- **不改已发布的持久化格式**：`LOG_VERSION` **绝不升**（升了 `sd_log_open` 会当新卡重建 ⇒ 从 LBA1 覆写**毁卡**）。
- **不为 G6-5 投入**（把 as5600 迁到状态机）：`REF` §3.6.1 已实测收益量不出来（`loop_gap_max_undecl=0`、
  ISR 2.11 µs、超预算 0），而代价是"同一件事两份实现"。
- **不做"擦掉再重建"式的迁移**（PLAN §0 纪律 4）。

## 7. Definition of Done（**什么条件下可以宣布标准化完结**）

1. `bash build.sh` 含 **5 道闸门**全绿，且**每道都自带 `--selftest` 与覆盖度自报**
   （覆盖不足 ⇒ 判**无效**，不是"干净"）。
2. **契据里可机检的断言：0 未覆盖**（`uncovered` 必须为 0，或逐条写明"为什么允许"）。
3. **协议 v2 可用**，且"不协商 ⇒ 与 v1 逐字节相同"有 A/B 证据。
4. **挂账 4 项全清**，或明确标注"不做"并给理由（**不允许沉默地留着**）。
5. **回归与变异对照全绿**，并且**套件自带板态前置条件**（不靠人记 —— 本轮 `--wipe` 就吃过一次）。
