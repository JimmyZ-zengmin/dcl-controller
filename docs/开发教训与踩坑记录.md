## 1. STM32H723 vs H743 寄存器差异 (严重)

**教训**: H723 (Value Line, RM0468) 和 H743 (Performance Line, RM0433) 的寄存器布局**不能互换**。直接照搬 H743 代码会导致功能失效。

### 1.1 PWR VOS 控制寄存器

| 项目 | H743 (RM0433) | H723 (RM0468) |
|------|---------------|---------------|
| VOS 控制寄存器 | `PWR_D3CR` (+0x18) 或 `PWR_CR1` (+0x00) SVOS[15:14] | `PWR+0x0C` VOS[5:4] |
| VOS 就绪标志 | `PWR_D3CR` bit 13 (VOSRDY) 或 `PWR_CR1` bit 13 (ACTVOSRDY) | `PWR+0x0C` bit 6 (VOSRDY) |
| LDO 使能 | `PWR_CR3` (+0x08) bit 1 (LDOEN) — 需手动启用 | 硬件自动，无需软件控制 |
| `PWR_CR3` @ +0x08 | 可读写控制寄存器 (LDOEN, BYPASS, SCUEN) | **只读状态寄存器**，所有位读回 0 |
| `PWR+0x0C` | `PWR_CSR1` 状态寄存器 | **VOS 控制寄存器** (可读写) |

**踩坑过程**:
1. 代码用 `PWR_CR1` SVOS 位设 VOS 并等 `ACTVOSRDY` → 永远等不到
2. 尝试使能 LDO (`PWR_CR3` bit 1 @ +0x08) → 写入无效，读回全 0
3. 以为是 PWR 时钟未使能 → 遍历所有 RCC 寄存器，都不是
4. **根本原因**: H723 的 `PWR+0x08` 是只读寄存器，`PWR+0x0C` 才是 VOS 控制

**正确做法** (已验证):
```c
// H723 VOS 控制 — 直接操作 PWR+0x0C
#define PWR_VOSCR  (*(volatile uint32_t *)(0x58024800UL + 0x0C))
PWR_VOSCR = (PWR_VOSCR & ~(3UL << 4)) | (0UL << 4);  // VOS0
while (!(PWR_VOSCR & (1UL << 6))) {}                   // 等 VOSRDY
```

**参考**: `firmware/h723-core0-1us/main.c` 第 19, 285-286 行有正确实现。

### 1.2 RCC 外设时钟使能偏移

| 外设 | H743 偏移 | H723 偏移 |
|------|-----------|-----------|
| TIM1 (APB2ENR) | 0x110 | 0x0F0 |
| DMA1/DMA2 (AHB1ENR) | 0x0D8 | 0x0D8 (相同) |
| GPIO (AHB4ENR) | 0x0E0 | 0x0E0 (相同) |

**教训**: APB2ENR 偏移不同！用 H743 的 0x110 写入 H723 会写到错误寄存器。

## 2. 寄存器地址 vs 只读寄存器

**教训**: 向只读寄存器写入不会报错，但也不会生效。调试时如果发现"写入无效"，先确认寄存器是否可写。

**排查方法**: 写 0xFFFFFFFF 后读回，看哪些位是可写的。
```python
# pyocd 诊断
t.write32(addr, 0xFFFFFFFF)
val = t.read32(addr)  # 可写位 = 1, 只读位 = 0
```

## 3. DMA 寄存器偏移量计算错误 (严重)

**现象**: DMA2 所有 Stream 的 M0AR 写入 0x200000E0，读回 0x000000A0（复位默认值）。S1PAR 和 S5PAR 写入正确，说明 EN=0 时 PAR 可写，但 M0AR 写入被忽略。

**根因**: STM32H7 DMA 的寄存器布局与 F4/H743 不同。**头 4 个寄存器是 LISR/HISR/LIFCR/HIFCR，占偏移 0x00-0x0C。Stream0 从 0x10 开始，每个 Stream 间隔 0x18。**

代码错误地假设 Stream0 从 0x00 开始，导致所有偏移量差了 **0x10**：
```
代码写的:  S1M0AR = DMA2_BASE + 0x24 → 实际地址是 S0_FCR（错误寄存器！）
正确地址:  S1M0AR = DMA2_BASE + 0x34

代码写的:  S5M0AR = DMA2_BASE + 0x84 → 实际地址是 S4_FCR（错误寄存器！）
正确地址:  S5M0AR = DMA2_BASE + 0x94
```

**正确偏移量** (STM32H723 RM0468):
```
DMA2_BASE = 0x40020400

LISR  @ +0x00  (Stream0-3 低半)
HISR  @ +0x04  (Stream4-7 高半)
LIFCR @ +0x08  (清除低半标志)
HIFCR @ +0x0C  (清除高半标志)

Stream N 基地址 = DMA2_BASE + 0x10 + N × 0x18

S0: +0x10(CR) +0x14(NDTR) +0x18(PAR) +0x1C(M0AR) +0x20(M1AR) +0x24(FCR)
S1: +0x28(CR) +0x2C(NDTR) +0x30(PAR) +0x34(M0AR) +0x38(M1AR) +0x3C(FCR)
S2: +0x40(CR) +0x44(NDTR) +0x48(PAR) +0x4C(M0AR) +0x50(M1AR) +0x54(FCR)
S5: +0x88(CR) +0x8C(NDTR) +0x90(PAR) +0x94(M0AR) +0x98(M1AR) +0x9C(FCR)
```

**排查过程**:
1. 写 M0AR → 回读为 0xA0（复位默认值）→ 怀疑写保护
2. 先清 NDTR 再写 M0AR → 仍然失败
3. 改用 AXI SRAM 地址 → **成功**！说明不是写保护，是写到了错误地址
4. 重新核对 RM0468 寄存器表 → 发现偏移量差 0x10

**教训**:
- **永远不要假设 DMA Stream 从 offset 0 开始**
- STM32H7 DMA 头部有 4 个中断寄存器 (16字节)
- 公式: `Stream_N_offset = 0x10 + N × 0x18`

## 4. DMA Stream5 无法访问 DTCM (架构级问题)

**现象**: DMA2 Stream5 M0AR=0x200000E0 (DTCM) 时，DMA_HISR bit 25 (DMEIF5) 置位，EN 被硬件自动清零。M0AR=0x24000000 (AXI SRAM) 时，DMA 正常启动。

**根因**: STM32H723 的 DTCM (0x20000000) 挂在 Cortex-M7 私有总线 (DTCM bus) 上，**不是 AHB/AXI 总线的一部分**。DMA 控制器是 AHB 主设备，无法通过 CPU 私有总线访问 DTCM。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  CPU Core    │     │  DMA1/DMA2   │     │  DMA1/DMA2   │
│  (DTCM bus)  │     │  (AHB bus)   │     │  (AHB bus)   │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │ 直接访问           │ 无法访问           │ 正常访问
       ▼                    ▼                    ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  DTCM        │     │  DTCM        │     │  AXI SRAM    │
│  0x20000000  │     │  0x20000000  │     │  0x24000000  │
│  128KB       │     │  ← 受限!     │     │  64KB        │
└──────────────┘     └──────────────┘     └──────────────┘
  CPU零等待            Direct Mode Error     DMA可访问
```

**注意**: 这个限制**仅限于 DMA Direct Mode**。在某些配置下 DMA 可能通过 AHBS 桥访问 DTCM，但行为不保证，本项目实测 Direct Mode 下必报 DMEIF。

**影响**:
- `SHADOW_GPIO` 定义在 DTCM (0x200000E0) → DMA Stream5 无法从这里搬运到 GPIOE_ODR
- `ADC_RAW` 定义在 DTCM (0x200000F0) → DMA Stream1 无法将 ADC1_DR 搬运到这里
- CPU 写 DTCM 是零等待 (优势)，但 DMA 无法访问 (劣势)

**解决方案 (二选一)**:

1. **镜像方案**: SHADOW_GPIO 定义在 AXI SRAM (0x24000000+)，ISR 直接写 AXI SRAM。代价是 ISR 多 1-2 个总线周期延迟。
2. **双写方案**: ISR 同时写 DTCM（CPU读取用）和 AXI SRAM（DMA读取用），DMA 从 AXI SRAM 搬运。

**推荐方案 1**，因为 AXI SRAM 的延迟对 100μs 周期影响可忽略（1-2 周期 @544MHz = ~4ns）。

**教训**: STM32H7 的内存域隔离是真实存在的。设计 DMA 数据流时，源和目标地址**必须**在 DMA 能访问的总线上。DTCM/ITCM 是 CPU 私有，DMA 不能访问。

## 5. DMA FCR DMDIS 位含义

**现象**: DMA Stream5 配置后 EN=1，但 100μs 后读回 EN=0，DMEIF 置位。

**根因**: 代码注释写"直通模式(无FIFO)"，但实际设置了 `DMDIS=1`（=**启用 FIFO**）。在 FIFO 模式下，如果配置不完整会触发 FIFO Error。

```
DMDIS = 0 → Direct Mode (直通，无FIFO) ← 这是简单传输需要的
DMDIS = 1 → FIFO Mode (启用FIFO) ← 需要额外配置 FIFO 阈值等
```

**正确做法**:
```c
DMA2_S5FCR = 0;  /* DMDIS=0: 直通模式 (Simple DMA, 无FIFO) */
```

## 6. SystemInit 双 PLL 切换顺序

**现象**: 代码配置 544MHz PLL (VCOSEL=0) 后，CPU 卡在 SystemInit 内。SWD 无法连接（高速下失效）。

**根因**: 代码先尝试禁用 PLL1 (`PLL1ON=0`)，再切 HSI (`SW=HSI`)。**但 SWS=PLL1 时，硬件拒绝 PLL1ON=0 的写入**（参考 RM0468: "PLL1 can be switched off only when it is not used as system clock"）。导致 PLL1 一直保持第一阶段配置 (288MHz VCOSEL=1)，第二阶段的 PLLCKSELR/PLL1DIVR/PLLCFGR 写入被硬件忽略。

**正确顺序**:
```c
// 1. 先切到 HSI（必须先切！）
RCC_CFGR = (RCC_CFGR & ~0x07) | 0x00;  // SW=HSI
while (((RCC_CFGR>>3)&7) != 0) {}      // 等 SWS=HSI

// 2. 现在可以安全禁用 PLL1
RCC_CR &= ~(1 << 24);                  // PLL1ON=0
while ((RCC_CR & (1<<25))) {}           // 等 PLL1RDY=0

// 3. 重新配置 PLL1
RCC_PLLCKSELR = ...;
RCC_PLL1DIVR  = ...;
RCC_PLLCFGR   = ...;
```

**教训**: **必须先切时钟源，再禁 PLL**。顺序反过来会导致 PLL 寄存器写入被静默忽略。

## 7. SWD 在 544MHz 下失效

**现象**: CPU 切到 544MHz 后，pyOCD 读写全部超时 (WAIT ACK/FAULT ACK)。reset_and_halt 也无法工作。

**根因**: SWD 时钟 (通常 1-10MHz) 与 CPU 544MHz 之间存在时钟域交叉问题。当 CPU 频率远高于 SWD 频率时，调试端口的异步桥可能无法正确采样 SWD 请求。

**影响**: 无法在 544MHz 运行时通过 SWD 读取寄存器、内存、halt CPU。

**解决方案**:
1. 调试阶段先用 272MHz (DIVP=2)，SWD 正常工作
2. 用 DTCM 标记位记录执行进度，复位后读取（DTCM 掉电前保持）
3. 验证完成后切回 544MHz

**调试标记方案**:
```c
// SystemInit 完成
*(volatile uint32_t *)(DTCM_BASE + 0x0000) = 0xAA000000;
// GPIO 初始化完成
*(volatile uint32_t *)(DTCM_BASE + 0x0000) = 0xBB000000;
// 全部初始化完成
*(volatile uint32_t *)(DTCM_BASE + 0x0000) = 0xCC000000;
```

复位后 DTCM 内容保持（只要不掉电），可通过 SWD 读取标记确认执行到了哪一步。

## 8. `=` vs `|=` 写 RCC 寄存器

**现象**: PLL 锁定后切时钟死锁

**根因**: `RCC_PLLCFGR = (1<<18)` 用 `=` 而非 `|=`，清零了其他关键位

**教训**: 对 RCC 寄存器，除非明确要覆盖全部位，否则一律用 `|=` 和 `&= ~` 操作。

## 9. H723 专用寄存器地址速查

```
PWR_BASE  = 0x58024800
  +0x00  PWR_CR1     (R/W, 但 H723 VOS 不用这里)
  +0x08  PWR_CR3     (只读! 全零!)
  +0x0C  PWR_VOSCR   (R/W, VOS[5:4], VOSRDY[6])  ← VOS 控制在这里

RCC_BASE  = 0x58024400
  +0x0F0  RCC_APB2ENR (TIM1EN 等)  ← 非 H743 的 0x110!

FLASH_ACR = 0x52002000

DMA2_BASE = 0x40020400
  +0x00  LISR    (Stream0-3 状态)
  +0x04  HISR    (Stream4-7 状态)
  +0x08  LIFCR   (清除低半标志)
  +0x0C  HIFCR   (清除高半标志)
  +0x10  S0_CR   (Stream0 从 0x10 开始!)  ← 不是 0x00!
  +0x28  S1_CR
  +0x40  S2_CR
  +0x88  S5_CR
```

## 10. 编译链接: nano.specs 与 -lnano

**现象**: `cannot find -lnano`

**根因**: `-specs=nano.specs` 已自动选择 nano C 库，再显式加 `-lnano` 会冲突。

**正确做法**: 用 `-specs=nano.specs` 即可，不要重复加 `-lnano`。
