## 1. 三条**不可协商**的要求（不是"好不好"，是"必须"）

| # | 要求 | 为什么不可协商 |
|---|---|---|
| **R1** | **程序必须能走通信上传，且上传后必须正确** | 这是"不烧录"的全部意义。上传错了 = 现场停机且无人知道 |
| **R2** | **引擎核心与 DCL 程序必须物理隔离**（核心走烧录，程序走通信+持久介质） | 否则"改一个程序"就要冒"换一台机器"的风险 |
| **R3** | **核心与程序必须能互相确认对方的版本与能力** | 否则版本错配只能在运行期以"行为不对"的形式暴露 |

⇒ 本文的一切设计都必须同时满足 R1/R2/R3。

## 2. 四层模型（`[已定]`）

```
① 引擎核心 Engine Core       烧录        改它 = 换固件(必须重新回归)
② 外设能力 Peripheral Ops    随核心发布、**版本化 + 能力位声明**
   ★ 做成"通用事务 op"(I2C/SPI/UART 事务) + 具名设备驱动, 而不是"每个芯片一个专用命令"
③ DCL 程序 Program           **通信上传 + 持久化到 SD**
④ 程序工程 Project           上位机侧: .dcl 源 + 清单(manifest) + 编译产物
```

**层间判据**（决定某个需求该放哪一层）：

| 问题 | 放哪层 |
|---|---|
| 它是"**怎么算**"（逻辑/连续/顺序）？ | ③ 程序 |
| 它是"**和外设怎么说话**"？ | ② 外设能力（通用事务 op 或具名设备） |
| 它需要**新的每拍行为 / 新的实时保证**？ | ① 核心（必走 A/B + 12 套回归） |
| 它只是"**给上位机看的量**"？ | 进 SHM + `obs_anchor()` 登记，**不是**加协议 op |

## 3. ★★ 持久化：SD 分区方案（`[已定]`）

### 3.1 先取证：现在这张卡上**没有任何空地方**

```c
src/sd.c:   LBA0            = 日志头
            LBA1 .. cap-1   = 数据区, **环形回卷**
            h[5] = 1u;                  /* 数据区起始 LBA —— 硬编码, 不可配 */
            h[6] = g_sd_capacity_blocks - 1u;   /* 数据区块数 = 整张卡 */
            s_log_blk += nblk;
            if (s_log_blk >= cap_data) { s_log_blk = 0u; s_log_wrapped = 1u; }  /* 回卷 */
```

⇒ **黑匣子日志占用了 LBA1 到卡末尾的全部空间，并且会回卷覆盖。**
⇒ **你担心的"记录满了会覆盖程序"是必然会发生，不是可能。**
⇒ 所以在做任何持久化之前，**必须先给卡划区**。

### 3.2 ⚠️ 顺手挖出的两个"陈旧注释会害人"的实例

| 位置 | 注释说的 | 代码做的 | 危害 |
|---|---|---|---|
| `src/sd.c:6-7` | "写在卡的**末尾区**（LBA 3000000 起，约 1.46GB 处），不碰盘头的分区表" | 从 **LBA1** 开始**线性回卷** | ★★ 照这句注释去安排布局的人，会把程序区放在**卡开头**——那正是日志第二个回卷周期最先覆盖的地方 |
| `src/sd.c:949` | （无注释） | `sd_write_multi(3000000u + i, ...)` —— 真的写 LBA 3000000 | 那落在**日志区内**（卡 ≥1.46GB 时）⇒ 一次吞吐自检就把日志数据打穿 |

★ 第二条是**单写者原则**被破坏的结果：同一张卡上有两个写者，一个从 LBA1 回卷、一个写 LBA3000000。
（虽然是调试器显式触发的一次性自检，但"用活数据区当靶子"这件事本身就该禁止。）

### 3.3 分区方案（`[已定]`）

**建议布局（512B 块，LBA 从 0 起）**：

| 区 | LBA 范围 | 大小 | 写者 | 内容 |
|---|---|---|---|---|
| **LOGHDR** | 0 | 1 块 | `sd_log` | 日志头（沿用现有 h[0..15] + 扩展段） |
| **LOG** | 1 … `LOG_END` | 可配 | `sd_log` | 黑匣子环形数据区（**上限由分区表限定**） |
| **PROG_A** | `PROG_A` … `PROG_A+N-1` | N 块 | `prog_store` | 程序副本 A |
| **PROG_B** | `PROG_B` … `PROG_B+N-1` | N 块 | `prog_store` | 程序副本 B |
| （尾部保留） | … cap-1 | | — | 卡容量增长时的余量 / 未来扩展 |

**关键一步：把日志关进笼子。** 现在 `h[6]` = 整卡容量−1，改法：

- 新增一个**头部扩展字段** `LOG_END`（放在 h[0..15] **之外的扩展段**，
  与既有"加字段不升版本"的做法一致 —— 注释里已经写明这个纪律）。
- **向后兼容**：旧头没有该字段 ⇒ 读回 0 ⇒ **退化为现有的 `capacity-1`**（行为不变，不毁卡）。
- 有该字段 ⇒ 日志容量 = `LOG_END - 1`，回卷在 `LOG_END` 处折返。
  ⇒ **一条改动，日志从此碰不到程序区。**

★ 分区边界的确定方式：**由容量决定、写进日志头**（不是写死在代码里），
这样换卡、换容量都自洽；同时给一个最小值检查（`cap >= 1024` 已有）。

### 3.4 ★「上传到 SD 的程序必须正确，不能漏错」—— 五道闸（`[已定]`）

你这句话是本次最硬的要求。**单靠一道 CRC 不够**，必须五道，且每一道都要有"能失败的对照"：

| # | 闸 | 判据（能失败的） | 失败时 |
|---|---|---|---|
| **1** | **传输层 CRC16**（已有） | 帧被篡改/截断 ⇒ 坏帧 | 拒收，报错 |
| **2** | **清单级 CRC32 + total_len** | 分片重组后长度或 CRC 不符 | 拒绝 COMMIT |
| **3** | ★ **写完立即回读比对**（`memcmp`） | 读回与写入不等 | **这一份作废**，不更新 seq |
| **4** | ★★ **A/B 双副本 + 单调 seq** | 任意时刻掉电 ⇒ 至少一份完整 | 开机取 seq 大且 CRC 通过的那份 |
| **5** | ★★★ **装载前重跑"上传时同一套静态校验"** | 校验不过 ⇒ **拒绝装载并明确报错** | 保持旧程序运行，绝不半装载 |

**第 5 条是容易被漏、也最要命的一条**：
程序在卡上躺了几个月，可能因为写坏、位翻转、或者**换了一个不同版本的固件**而失效。
⇒ **开机装载时必须重跑与上传时完全相同的 10 道门 + `engine_route_validate` 13 项**，
**校验不通过就不装载**（而不是装进去让它跑出奇怪行为）。

★ 并且：**"程序有效"这件事必须有一个可被外部读走的量**（例如 `prog_state`：
`EMPTY / LOADED / REJECTED(原因码)`），否则"装载失败"在观测面上不可见。

## 4. ★ macro 的定位 —— 按我们的架构与设计目的来判（`[已定]`）

你问"要不要用 macro"。我按**我们自己的四条公理**逐条对，结论很清晰。

### 4.1 逐条对公理

| 公理 / 不变量 | macro 的实际情况 | 判定 |
|---|---|---|
| **公理① 一切数据都在 SHM；通信=写我自己的槽** | macro 有 `0x10 load(addr)` / `0x11 store(addr,val)`，**可写任意 SHM 地址** | ❌ **突破单写者** |
| **公理② 单写者原则** | 同上：它可以写别人的槽 | ❌ |
| **公理③ 计算即查表** | macro 是一段**字节码**，不是路由表；没有"一条规则 = 输入槽→原语→输出槽"的结构 | ❌ 另一种范式 |
| **公理④ 时间预算是一等公民** | macro 的状态有 **`0x06 忙等 N 周期` / `0x07 忙等 N ms`**，由**主循环** `macro_tick` 驱动；**没有标价、没有静态门、没有动态门** | ❌❌ **最严重** |
| **不变量③ 每拍必须发生的动作不得挂在分支里** | macro 的循环**挂在主循环**上（`interval = max(loop_ms,10)*10 拍`） | ❌ |
| **持久化口径** | `ARCH-H723.md` §11.1 #10 **明确标为"未决"** | ❌ 无法满足 R1 的"持久化" |

### 4.2 关键论据：它坐在**主循环**上，而主循环正是我们本轮定案的病根

- 本轮零运动实测：**主循环一圈 1.28~1.54 ms**，而拍是 **100 µs** ⇒ 差 13~15 倍。
- `step_tick`（限时）与 `macro_tick` **挂在同一个环上** ⇒
  限时"慢 26% 且随负载变"（D2）与 macro 的"忙等"是**同一条病**。
- ⇒ **把一个带"忙等"的字节码放在主循环里，等于给一条已经超载的环再加负荷。**
  这直接违反公理④，也让"确定性"这句宣称不再成立。

### 4.3 但它不是没有价值 —— 价值在**别处**

macro 真正的独特能力是：**它允许用户上传"代码"（字节码），而路由表只能表达"规则"。**
这对 **② 外设能力** 恰好是天然的落点（见 §5）：
I2C/SPI 事务本身是"过程性"的（START → 地址 → 数据 → STOP），
用路由表表达很别扭，用一小段可上传的字节码却正合适。

### 4.4 结论与建议（**分三种情形，我给推荐**）

| 情形 | 建议 |
|---|---|
| **A. 作为控制回路的一部分** | ❌ **禁止**。它违反公理④，且无法持久化 |
| **B. 作为上位机的调试/探测脚本**（非实时、非持久） | ✅ **允许**，但必须在文档与应答里**显式标注"不保证实时"**，并且**禁止写 SENSOR/ACTUATOR/WIRE 之外的地址**（收紧 `0x10 store` 的裸地址守卫） |
| **C. 作为"通用外设事务"的承载**（未来） | ✅ **推荐方向**，但**前提是先把它从主循环搬走** —— 改成"每拍由 ISR 推进的状态机"或"独立 DMA 驱动的引擎"，并给它**标价 + 预算门** |

> **一句话判据**（给你现场决策用）：
> **"它是不是控制回路的一部分？"** —— 是 ⇒ 必须进拍内；
> 否 ⇒ 只能当调试工具，且必须在应答里自报"非实时"。

**⇒ `[已定]`：本轮 macro 定位为 B（调试工具），并在文档与能力位里标注"非实时、不持久化"。
C 作为下一步的候选，但要先做预算门。**

## 5. ★ 外设能力的边界 —— 权威资料怎么说（`[已定]`）

你让我去查权威做法。查了三类来源（IEC 61131-3 / 现场总线标准 / 嵌入式驱动模型），
**结论高度一致**。

### 5.1 三条权威共识

**① 逻辑与硬件必须分成两半 —— 硬件那半由"平台专属的函式库/驱动"承载**

> IEC 61131-3 的设计：把控制动作分为**逻辑运算**与**硬件动作**两部分，
> 逻辑部分用统一描述格式标准化，**硬件动作则针对各硬件设计专属之固件函式库**。
> （科普中国·IEC 61131-3 词条）

**② 程序侧只引用抽象符号；物理映射只出现在单独的一层**

> CODESYS 的可移植做法：**两层架构** —— 可移植的应用层用**内部符号**，
> **唯一的平台相关文件是 I/O Mapping POU**；厂商专属的 FB **只留在映射层**。
> "The application POUs **never** reference physical I/O addresses."
>
> Zephyr 的同一条：**"设备树是硬件信息的唯一真相源。驱动代码不应该包含任何具体的
> 引脚号、地址等硬件信息。"** 应用调用**通用子系统函数**，驱动管寄存器，设备树管接线。

**③ 能力必须**有描述、有版本、可预检**——而且**预检发生在编译/组态期**，不是运行期**

> 每一种现场总线都**强制要求设备描述档**：EtherCAT = **ESI**（XML，ETG 标准 schema）、
> PROFINET = **GSDML**、CANopen/DeviceNet/EtherNet-IP = **EDS**、IO-Link = **IODD**。
> 内容包含 **Vendor ID / Product Code / Revision / PDO 映射选项 / OD 条目 / 邮箱配置**。
> 作用：**身份识别 + 数据格式 + 通信规则**。
> Zephyr 的版本：**bindings(YAML) 在编译期校验设备树，不匹配则构建失败** ——
> "a safety mechanism that catches configuration errors **before they reach the physical hardware**".

**④ 能力/参数的标准做法是"对象字典"式的分区命名空间**

> CANopen **CiA 301** 把对象字典按**区间**分区：
> `0x1000–0x1FFF` 通信 profile ／ **`0x2000–0x5FFF` 厂商专属** ／
> **`0x6000–0x9FFF` 标准器件 profile**（CiA 402 驱动 / CiA 401 I/O）。
> 每台设备**必须有** `0x1000 Device Type`、`0x1001 Error Register`、
> **`0x1018 Identity（Vendor ID / Product Code / Revision / Serial）`**。
> 并且 `0x1010 Store Parameters` 区分 **_Save all / _Save Communication / _Save Application**
> （写魔数 `0x65766173`="save" 才保存）。

### 5.2 所以"外设能力的边界"定在哪（**我们的落法**）

**⇒ 边界 = "程序里不得出现任何物理引脚号或总线地址"。**
这一条同时被 IEC/CODESYS（"never reference physical I/O addresses"）和
Zephyr（"驱动代码不应包含引脚号/地址"）两边独立确认。

**⇒ 分三档（对应 CiA 301 的三个区间）**：

| 档 | 类比 | 我们对应什么 | 程序能不能用 |
|---|---|---|---|
| **标准区** | `0x6000–0x9FFF` | **19 个原语 + 顺序域 + SENSOR/WIRE/ACTUATOR 槽** | ✅ 随便用，这是"程序语言" |
| **厂商专属区** | `0x2000–0x5FFF` | **具名设备与能力包**：`as5600` 角度、`tb6600` 步进、`sd_log`、`rtc`、未来的 `i2c_bus` / `spi_bus` | ✅ 按**名字 + 版本**引用，**声明依赖** |
| **低层直通** | 非标准 | I2C/SPI **事务**原语 | ⚠️ **允许，但只能出现在"设备驱动"内部**，不作为程序面；若要以 macro 形式开放，须标注"厂商专属、不保证跨平台" |

**⇒ 具体动作（这就是 I2C 事件的制度化修复）**：

1. **能力位扩到 u32**，补 `I2C / SPI / SD / RTC / CAN / ETH` 等位；
   ★ **每位配一个"厂商专属设备 ID"**（`Vendor ID / Product Code / Revision` 三件套，
   照抄 `0x1018` 的语义），程序用**名字**引用它，不引用引脚。
2. **告一个"设备描述"**（我们的 ESI 等价物）：一份**机器可读**的表，
   列出本核心**具备哪些能力、哪些具名设备、各自版本**。
   上位机在**上传期**用它做预检 ⇒ **缺能力就拒绝上传**（而不是跑起来才发现）。
3. **通用事务 op 进 ② 层**（`i2c_start/stop/write/read`、`spi_xfer`），
   让"支持一个新传感器 = 写一段程序"，而不是"改固件 + 重新烧录 + 12 套回归"。
   ★ 安全边界不变：沿用 macro 现有的裸地址守卫 / 非有限值守卫 / pc 越界检查。
4. **I2C 那次的做法（专用驱动 `as5600.c` + 专用诊断命令 `0x39 op=17/18`）
   归入"② 层未成熟时的临时形态"** —— 保留可用，但**必须登记进能力位**，
   并**明确它属于厂商专属区**（不是核心的一部分）。
