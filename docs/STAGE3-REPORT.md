# 阶段 3 报告（一）— 档桶分档调度（S3 OA15 治本语义）

日期: 2026-09-10 · 项目: 9.10 H723newest · 平台: STM32H723ZGT6 @400MHz
上游: `STAGE2-REPORT.md`（阶段 2 = 全表扫，明确是占位）
对应 S3 资产: OA15「治本重构（桶化分档）」+ OA12/OA22「成本模型族」

---

## 0. 一句话结论

> **同一份 128 条的三档程序，只切换扫描方式（全表 vs 分档），
> 每拍成本从 6762 → 2606 cyc（DIRECT）/ 10878 → 4208 cyc（19 原语混合）：
> 便宜 2.59 倍** —— 因为分档后每拍只需执行 47~49 条，而不是 128 条。
>
> 而且这个"47 条"不是靠数出来的：**桶表校验和与 Python 独立预测逐位吻合，
> 本拍条数落在桶表允许的可行值集合内** —— 若退回全表扫，判据立刻失败。

---

## 1. 做了什么

### 1.1 语义（与 S3 逐字一致）

路由按 `(div, phase)` 归组重排：`[div0 全部]` → `[div1: phase 0..9 各成桶]`
→ `[div2: phase 0..63 各成桶]`。ISR 每拍只跑三段：

```
div0 段 = [0, off1[0])                                 每拍全跑
div1 段 = [off1[tick%10],  +cnt1[...])                 每 10 拍 1 次
div2 段 = [off2[tick%64],  +cnt2[...])                 每 64 拍 1 次
```

桶表 `[off1[10]][cnt1[10]][off2[100]][cnt2[100]] = 220×u16` 放在
`OFF_ROUTE_BUCKETS = 0x4480`（**与 S3 同偏移**，迁移不变量）。

### 1.2 实现要点

| 处 | 内容 |
|---|---|
| `engine_build_buckets()` | 归组重排 + 建桶索引。**幂等**：对源表按序扫描再落桶 = 稳定排序，对已归组的表再跑一次是恒等变换；桶表**先清零**（不清会把上一轮计数叠上来） |
| 暂存 | 用 `OFF_ROUTE_STAGING`（2KB）当重排暂存 —— 它本来就是为"重排/热重载"预留的 |
| `engine_tick()` | 放在 **ITCM**，按 tick 算 `m10/m64` 三段调度，返回校验和与本拍执行条数 |
| 两种扫描方式**运行期可切** | `g_scan_mode`：0 = 全表扫（阶段 2 基线）/ 1 = 分档调度。同一会话内对照，排除环境差异 |
| 表填充 | 新增 profile 3（三档·全DIRECT）/ profile 4（三档·19原语轮转）；`fill_tables` 末尾无条件调 `build_buckets`（非三档 profile 也调 —— 保证桶表一定被建立，不会出现"某档忘了建桶 → 每拍空扫"的静默失效） |

## 2. 结果：分档 vs 全表（同一份程序，只切扫描方式）

`build/stage3_run4_final.txt`（ITCM、I-cache 关、400MHz、拍长 40000 cyc）：

| 组 | 程序 / 扫描方式 | eng_min | 本拍条数 | 最坏占拍 |
|---|---|---|---|---|
| **G1** | 三档·全DIRECT / **分档** | **2606** | 48 | **7.15%** |
| G2 | 三档·全DIRECT / 全表 | 6762 | 128 | 17.21% |
| **G3** | 三档·19原语混合 / **分档** | **4208** | 48 | **11.86%** |
| G4 | 三档·19原语混合 / 全表 | 10878 | 128 | 27.93% |

```
DIRECT : 条数比 2.67×   成本比 2.59×
混合    : 条数比 2.61×   成本比 2.60×   ← 两者一致 ⇒ 成本确实由"执行条数"决定
```

**同批对照（阶段 2 的口径仍在）**：ITCM 全表 128 条混合 = `C2 11299~11432`
（28.89%）→ 分档三档程序 `G3 4208`（11.86%）。**128 条满表从"贴着上限"降到
"留 88% 余量给通信域/顺序域/热重载"。**

顺带（本轮又一次撞见落位效应）：`C1` FLASH·全表·混合 = `39481~40893` →
**最坏占拍 102.48% ★超载**，而同一个程序在上一版构建是 98.28%。
加上 `engine_tick` 就把它推过了线 —— 与 `REF-flash-placement.md` 完全一致。

## 3. ★ 移植期发现 S3 的一个真缺陷（宣称≠实现）

### 3.1 现象

S3 把 div2 相位声明为 **100 个**：

```c
/* shared_mem.h */
#define PERIOD_PHASE_MASK    0x3F      /* ← 6 位, 只能表达 0..63 */
/* 桶表 100 槽 */  off2[100] / cnt2[100]
/* 注释 */        "phase 0-99"

/* main.c deploy */
ph = q2 % 100;                          /* ← 可以到 99 */
tw.period = (uint8_t)(dv | (ph << PERIOD_PHASE_SHIFT));   /* ← (uint8_t) 截断! */
```

`ph = 99` 时 `ph << 2 = 396`，`(uint8_t)` 只保留低 8 位 → 存进 `period` 的
phase 位实际是 `ph & 0x3F`。ISR 侧再 `ph = (period >> 2) & 0x3F` → **只可能 0..63**：

```
· 桶表槽 64..99 **恒空** (前缀和算得出来, 但永远没有路由落进去)
· q2 = 0 与 q2 = 64 落到**同一个相位** → div2 超过 64 条时相位重叠
```

### 3.2 为什么没被发现

`tools/verify_capacity.py` 的「慢档 PID×128 (满表)」正好是 **127 条 div2** ——
会触发重叠。但该用例只看 `emax` 是否超预算（127 条 PID 摊到 64 个相位也就每拍
2 条 ≈ 1200 cyc，离 16000 的门差得远），所以**从未暴露**。

### 3.3 影响

部署门 `EXEC_DEPLOY_BUDGET` 对 div2 路由按 `ceil(cost/100)` 计费（即假设
"每 100 拍摊到 1 拍"）。相位重叠后实际每拍最坏是 `ceil(n_div2/64)` 条 ——
**低估最坏拍成本**，余量被静默吃掉。属审计里那组「成本模型族」（OA12/OA22：
"成本模型每引入一个新维度都要重算，否则静默突破部署门"）。

### 3.4 H723 的修法：让宣称等于实现

```
BUCKET_DIV2_PHASES = 64        /* 与 period 的 6 位 phase 字段严格一致 */
div2 phase = seq % 64
```

- 桶表**仍保留 S3 的 220×u16 / 0x4480 偏移**（迁移不变量），但**槽 64..99 恒为 0
  是被断言的**（见 §4 的 `g_bucket_zero_slots`）
- 副产品：未来 deploy 预算模型对 div2 的摊薄系数必须**除以 64 而不是 100**
  （div2 每条每拍成本 +56%）。这是对 S3 模型的一处**修正**，已登记为阶段 3.2 的必做项

## 4. 判据（这一节是本报告的"可失败性"证明）

新增三个**能失败**的判据，全部逐组比对、22 项全绿：

| 判据 | 做法 | 若失效会怎样 |
|---|---|---|
| **桶表正确** | 固件 `engine_bucket_checksum`（FNV-1a over 220×u16） vs **Python 独立复刻 `engine_build_buckets`** 重算 | 三档/混合任一档的桶边界错 → 数值立刻不等 |
| **H9 断言** | `g_bucket_zero_slots` = 槽 64..99 的非零个数，期望 0 | 谁把相位数改回 100 而不加宽字段 → 立刻非 0 |
| **分档行为** | 本拍执行条数 `g_eng_routes_last` 必须 ∈ 桶表允许的**可行值集合** `{47,48,49}`；累计均值 `g_eng_routes_total/g_eng_ticks` 也必须落在 `[47,49]` | **退回全表扫 → 条数变 128, 不在集合里 → 报 ✗** |

同批复用的旧判据：整表校验和（逐字节）、`ACTIVE==128`、栈哨兵、`div0==0`、
`sel/n` 生效性。本批 **22 个 ✓ / 0 个 ✗**。

```

校验和 0x89C79BD2 ← C1/C2                     (profile 1)
校验和 0xFF09DAF8 ← E                         (profile 2)

```

## 5. 途中踩的两个坑（都是"判据太松"造成的）

### 5.1 表校验和：字段位重叠 + 漏掉 `period`

第一版（阶段 2 的 H1 修复产物）是**字段位拼装**：

```c
v = op | (flags << 8) | (src_type << 16) | (state_offset << 20);
```

两个问题：
- `state_offset << 20` 与 `src_type << 16` 在 **bit 20-23 重叠** ——
  不同 `(src_type, state_offset)` 组合可能撞同一个 `v`
- **完全没覆盖 `period`** —— 也就是档位/相位分配不在校验范围内

**改法**：对**整个 16 字节条目逐字节**做 FNV-1a。无重叠、天然覆盖全部字段，
而且因为字节序参与哈希，**顺带覆盖了归组重排**（表序错了哈希就变）。

### 5.2 `period` 在 offset **14**，不是 15

`RouteEntry_t` 有 15 个字段 + `aligned(4)` ⇒ `sizeof` 补齐到 16，
**offset 15 是编译器的尾部填充字节**，`period` 在 offset 14。
Python 复刻时按"最后一个字节"写成 `b[15]`，于是 profile 3/4（period ≠ 0）
预测对不上、profile 0/1/2（period = 0）却对得上 —— 这种"部分对得上"的错最难查。

**改法（固件侧）**：把那个填充字节**显式命名**为 `uint8_t reserved;` ，
使逐字节校验和**不依赖填充内容**。否则任何"逐字段赋值"的改动都会让填充变脏、
校验和漂移 —— 而这正是 5.1 引入逐字节哈希之后新引入的脆弱点。

> 这两条都是**更严的判据自己抓出来的**：如果校验和还停在"字段位拼装"版，
> 5.2 这个 offset 错位永远不会被发现。
