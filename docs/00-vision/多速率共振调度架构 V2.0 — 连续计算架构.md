# 多速率共振调度架构 V2.0 — 连续计算架构

> 本文档记录 DCL 控制器体系的**下一代**调度架构。
> 状态：**前沿研究**（未实现，基于 V1.x + DTCM 双端口洞察的架构跃迁）
> V1.x 参见：[多速率共振调度架构](多速率共振调度架构.md)

---

## 0. 版本说明

| 版本 | 名称 | 驱动模式 | 最小时钟分辨率 | CPU 模式 | 状态 |
|------|------|---------|--------------|---------|------|
| V1.0 | 单速率火车模型 | ISR + DMA | 100μs | 突发计算 | ✅ 已实现 |
| V1.1 | 多速率共振调度 | ISR(优化)+DMA | 1μs (120 tick) | ISR 状态机 | 📄 已设计 |
| **V2.0** | **连续计算架构** | **DMA 纯驱动** | **100ns~1μs** | **自由循环** | 🌱 本文 |

V2.0 不是 V1.x 的增量改进，而是**范式转换**：
- V1.x: CPU 被中断打断 → 爆发式计算 → 等待 → 再被打断
- V2.0: **CPU 永远在算，DMA 永远在搬，两者互不干扰**

## 1. 核心洞察：DTCM 双端口为何是革命性的

STM32H723 的 DTCM 有两个独立端口：

```
                  CPU(D-bus)                DMA(AHB矩阵)
                  │ 64-bit                     │
          ┌───────┴───────┐          ┌─────────┴─────────┐
          │  DTCM Port 0  │          │   DTCM Port 1     │
          │ (CPU独占,0WS)  │          │ (DMA/其他主机访问)  │
          └───────┬───────┘          └─────────┬─────────┘
                  └──────────┬───────────────-─┘
                             │
                          DTCM RAM
```

**关键事实：这是两个物理上独立的端口，无需总线仲裁。**

| CPU 在做什么 | DMA 在做什么 | 总线冲突？ |
|-------------|-------------|-----------|
| 读 DTCM 数据 (Port 0) | ADC→DMA→DTCM (Port 1) | ❌ 无冲突 |
| 写 DTCM SHADOW (Port 0) | DTCM→GPIOE_ODR (Port 1) | ❌ 无冲突 |
| 读 ITCM 指令 (I-bus) | 任意 DMA 操作 | ❌ 完全独立总线 |
| 读/写 AHB1 外设 | DMA 访问 DTCM | ❌ 不同目标 |

> **结论：CPU 可以 100% 时间全速计算，DMA 可以 100% 时间全速搬运，两者在 DTCM 上零仲裁。**

这个事实在 V1.x 中未被充分利用——V1.x 仍然保留了 ISR，意味着 CPU 仍然被周期性打断。

## 2. V2.0 架构总览

### 2.1 与 V1.x 的直观对比

```
V1.x (多速率共振调度):

  TIM2 (1μs) ─── ISR ─── CPU 算一点 ─── 退 ISR ─── 等下一个 1μs ─── ISR ...
                 ↑                     ↑
             160ns 开销          计算时间片 < 840ns
             CPU 被中断夺走      CPU 工作在"片段模式"


V2.0 (连续计算架构):

  CPU: [算][算][算][算][算][算][算][算][算][算][算][算]... 永不停止
         ↑                          ↑
       ADC+DMA 在后台写 DTCM     SHADOW+DMA 在后台读 DTCM

  DMA: ----ADC→DTCM------ADC→DTCM------ADC→DTCM-----→  (输入)
       --------SHADOW→GPIO---SHADOW→GPIO---SHADOW→GPIO→ (输出)
       
  TIM2(UIE=0): 不产生中断，仅作为 DMA 触发源
```

### 2.2 三要素解耦

V2.0 的核心突破是：**输入、计算、输出三者完全解耦，各自运行在独立的节奏上。**

```
输入速率 (受ADC/外设限制)
  └── ADC:  每 3.28μs 更新一次 DTCM (DMA Stream1)
  └── WIRE: 每 1-10μs 更新一次 DTCM (ETH/UART DMA)
  └── 数字IO: 每 50-100ns 可更新一次

计算速率 (受CPU指令数限制)
  └── CPU 自由循环: 每 50-500ns 完成一次计算迭代
  └── 读 DTCM → 算 → 写 DTCM SHADOW
  └── 不等待、不检查、不中断

输出速率 (受定时器分辨率限制)
  └── SHADOW→GPIO: 每 100ns~1μs 由 TIMx 触发 DMA
  └── PWM CCR: 每个 TIM1_UDE 硬件锁存
  └── 输出与算率无关，由硬件决定
```

**类比：工厂流水线**
- 原料工位（输入）以 A 速率供货
- 加工工位（计算）以 B 速率不停地加工
- 包装工位（输出）以 C 速率打包出货
- 三个工位独立运行，中间用缓冲区（DTCM）连接

## 3. 无中断连续计算模型

### 3.1 CPU 代码结构

```c
// V2.0 核心循环 — 无中断版本
// TIM2_UIE = 0 (永远不开中断)
// TIM1_UIE = 0 (不开中断)
// 所有 I/O 由 DMA 完成

void continuous_compute_loop(void) {
    /* DTCM 中的数据布局 (由 DMA 维护):
     *   ADC_RAW_BASE    ← DMA Stream1 每 3.28μs 写入
     *   WIRE_MAP        ← ETH/UART DMA 随时写入
     *   SENSOR_MAP      ← CPU 在需要时换算
     *
     * DTCM 中的输出缓冲区 (DMA 读取):
     *   SHADOW_GPIO     ← CPU 写入, DMA Stream5 定时搬运
     *   TIM1_CCR1/2/3   ← CPU 写入, TIM1 硬件自动锁存
     */

    while (1) {
        /* 1. 读输入 — 全部 DTCM, 单周期 */
        uint32_t raw_adc  = *(volatile uint32_t *)ADC_RAW_BASE;
        uint32_t wire_val = WIRE_MAP[src_idx];
        
        /* 2. 计算 — 纯 DTCM 运算, 无外设访问 */
        uint32_t result = compute(raw_adc, wire_val, param);
        
        /* 3. 写输出 — 写 DTCM, DMA 负责搬运 */
        SHADOW_GPIO = result & 0xFFFF;    // DMA 在下一个子周期点搬走
        TIM1_CCR1   = result >> 16;        // TIM1 硬件自动锁存
        
        /* 4. 继续 — 没有等待, 没有检查, 没有 WFI */
    }
}
```

### 3.2 没有 ISR 的理由

V1.x 保留 ISR 是基于两个假设，这两个假设在 V2.0 中被推翻：

| V1.x 的假设 | V2.0 的修正 |
|------------|------------|
| "CPU 必须知道何时有新的输入数据" | **CPU 不需要知道** — 每次迭代读 DTCM 相同的地址，DMA 写新的值，CPU 读到什么算什么 |
| "某个 tick 必须触发特定计算" | **所有 tick 都是计算 tick** — CPU 每 50-500ns 算一次，DMA 每 100ns~1μs 搬一次，两者完全独立 |

**没有 ISR 意味着：**
- 零压栈开销（省 40-160ns/次）
- 零上下文切换（省 Cache/TLB 污染）
- 零中断延迟抖动（确定性 = CPU 时钟周期级）
- CPU 利用率从 60% → **接近 100%**

### 3.3 那 TIM1 的 100μs 周期呢？

TIM1 的 100μs 周期在 V2.0 中**仍然存在**——但它不再是"计算周期"，而是纯粹用来做：
1. ADC 触发（OC4REF at CCR4）
2. SHADOW→GPIO 的 DMA 触发（CC4DE）

事实上，在 V2.0 模型中，**任何定时器都可以作为 DMA 触发源**，它们的周期完全独立于 CPU 的计算速度：

```c
// 定时器配置 (仅 DMA 触发, 不产生中断)
TIM1_CR2 = (4 << 4);         // MMS=100 → TRGO=OC4REF
TIM1_DIER = (1 << 12);       // CC4DE=1 (DMA), UIE=0 (不开中断)
// ↑ UIE=0 是关键：CPU 永远不会被 TIM1 打断

TIM2_DIER = (1 << 8);        // UDE=1 (DMA), UIE=0 (不开中断)
// ↑ TIM2 只做 DMA 触发，不产生 ISR
```

## 4. DMA 子周期调度

### 4.1 问题：1μs 内如何安排多个 DMA 操作？

在无中断模型下，DMA 触发的时机决定了输入什么时刻到达、输出什么时刻更新。我们需要一种机制在微秒内产生多个精确的触发点。

**方案：利用 TIMx 输出比较通道 + DMAMUX 实现多阶段触发**

```
TIM2 配置:
  ARR = 239    (1μs @ 240MHz TIM_CLK)
  UIE = 0      (不中断 CPU)
  UDE = 1      (UPDATE 时做全局 DMA)

  CH1: CCR1 = 24   (100ns)   → DMAMUX → DMA: 读 WIRE_MAP
  CH2: CCR2 = 72   (300ns)   → DMAMUX → DMA: 读第二个输入
  CH3: CCR3 = 168  (700ns)   → DMAMUX → DMA: 预处理触发
  CH4: CCR4 = 216  (900ns)   → DMAMUX → DMA: SHADOW→GPIO 输出
```

**子周期触发点：**

```
TIM2_CNT: 0──24──48──72──96──120──144──168──192──216──239
          │   │   │   │   │    │    │    │    │    │    │
DMA出发:  ↑       ↑              ↑         ↑         ↑
         CH1     CH2            CH3       CH4      UPDATE
         输入1   输入2           预处理    输出锁存  ADC触发
                    (ADC/DMA已经在后台持续运行)
```

### 4.2 DMAMUX 的灵活性

STM32H723 的 DMAMUX 可以**将任意外设事件路由到任意 DMA 流**。这意味着：

| DMAMUX 请求 | 触发源 | DMA 流 | 作用 |
|------------|-------|--------|------|
| ADC1 完成 | ADC1 | DMA1_Stream1 | ADC→DTCM（持续） |
| TIM2_CH1 | TIM2_CC1 | DMA1_Stream2 | 子周期输入读 |
| TIM2_CH4 | TIM2_CC4 | DMA2_Stream5 | SHADOW→GPIO（子周期输出） |
| TIM2_UP | TIM2_UEV | DMA2_Stream3 | 周期同步操作 |
| TIM1_CC4 | TIM1_CC4 | DMA2_Stream5 | 100μs 硬周期输出锁存 |

### 4.3 多级 DMA 级联

超低周期下（100-200ns），单个 TIMx 的通道数可能不够。可以用**两个定时器级联**：

```
TIM3 (100ns 快速)  ── CH1:50ns, CH2:100ns  → 细粒度触发
  │
  └── 每 10 个周期触发一次 TIM4
      TIM4 (1μs 慢速) ── CH1: 250ns, CH2: 500ns, CH3: 750ns, CH4: 1000ns
```

这样可以在 1μs 内产生 10 × 2 + 4 = 24 个不同的触发点。

## 5. 三速率独立运行模型

### 5.1 数学描述

定义三个速率：

```
R_in  = 输入数据刷新率 (Input Update Rate)
        ADC:   1 / 3.28μs  ≈ 305 kHz
        WIRE:  1 / 1μs     ≈ 1 MHz (取决于外设)
        数字IO: 1 / 50ns   ≈ 20 MHz

R_cpu = CPU 计算迭代率 (Compute Rate)
        简单路由: 1 / 50ns  ≈ 20 MHz
        复杂 PID: 1 / 200ns ≈ 5 MHz

R_out = 输出更新率 (Output Update Rate)
        GPIO: 由 TIMx_CH4 决定, 1 / 100ns = 10 MHz
        PWM:  由 TIM1 决定, 1 / 100μs = 10 kHz
```

**核心关系：R_out 可以独立于 R_in。**

这意味着即使 ADC 只有 305 kHz 更新率，输出仍然可以以 10 MHz 更新。控制器的输出在每个 100ns 子周期都用"当前已知的最新输入"重新计算一次。

### 5.2 这对控制质量意味着什么

对于**数字 IO 控制**（振镜、步进、脉冲发生器）：
- 输入变化率可以很慢（位置指令每 1ms 更新一次）
- 但输出可以以 100ns 分辨率执行脉冲序列
- 这允许在指令之间做**微步插值**

对于**模拟控制**（PID、滤波器）：
- ADC 每 3.28μs 提供新样本
- PID 每 100ns 算一次（用相同的 ADC 值连算 32 次）
- 输出 PWM 以 100ns 分辨率更新
- 积分累加仍然正确（因为积分的是控制输出，不是输入）

### 5.3 流水线深度与延迟

```
输入采样 (97.5μs of cycle) → DMA搬运 → DTCM就绪 → CPU读取 → 计算 → SHADOW → DMA输出
  ├── ADC 转换: 3.28μs                          │
  ├── CPU 计算: 50-500ns                        │
  ├── SHADOW→GPIO DMA: ~20ns                    │
  └── 总延迟: 3.3-4.0μs (输入到输出)             │
                                                │
  但输出更新率: 每 100ns 一次                     │
  → 输出仍然每 100ns 更新一次                     │
  → 只是输入值每 3.28μs 才变化一次                  │
  → 对于控制而言: 延迟 3.3μs, 但更新率 10MHz      │
```

## 6. 周期极限分析

### 6.1 各周期的实际含义

| 周期 | CPU 周期 (480MHz) | 能做什么 | 瓶颈 |
|------|------------------|---------|------|
| 1μs | 480 cyc | 完整 PID + 路由 + 通讯 | V1.x 已实现 |
| 500ns | 240 cyc | 简单 PID + 查表 | CPU 计算量 |
| 200ns | 96 cyc | 直接映射 + FMAC + 2 条路由 | CPU 计算量 |
| **100ns** | **48 cyc** | **Load→Compute→Store 循环体** | **DMA 触发精度** |
| 50ns | 24 cyc | 仅存/取 + 1 次运算 | 定时器分辨率 |
| 30ns | 14 cyc | 不够做有用计算 | CPU 极限 |

### 6.2 100ns 级别的代码分析

在 100ns（48 个 CPU 周期 @480MHz）内可以做这些：

```c
// 100ns 内能完成的操作 (48 cyc):
void fast_iteration(void) {
    LOAD r0, [ADC_RAW]       // 1 cyc: 读 ADC 输入
    LOAD r1, [WIRE_MAP]      // 1 cyc: 读 WIRE 输入
    MUL  r2, r0, scale       // 1 cyc: 缩放
    ADD  r3, r1, r2          // 1 cyc: 合并
    CMP  r3, threshold       // 1 cyc: 比较
    IT   GT                   // 1 cyc: 条件
    MOV  r3, max_val         // 1 cyc: 钳位
    STR  r3, [SHADOW_GPIO]   // 1 cyc: 写输出
    STR  r3, [TIM1_CCR1]     // 1 cyc: 写 PWM
    B    fast_iteration      // ~3 cyc: 循环
                             // ─────────────
                             // ~12 cyc ≈ 25ns 实际执行
                             // 剩余 36 cyc ≈ 75ns 余量
}
```

真实场景下（加上循环展开、查表、条件分支），100ns 约能执行 **1-2 条路由计算**或**1 个 PID 运算**。

### 6.3 50ns 的极限挑战

50ns（24 个 CPU 周期）是 Cortex-M7 架构的实际下限：

```
制约因素:
  load + store = 2 cycles (L1 DTCM)
  FMAC = 1 cycle (乘加)
  分支预测 = 1-2 cycles
  最小循环体 ≈ 6-8 cycles
  ─────────────
  有效运算 ≈ 16-18 cycles
  
在 16 个可用周期内能做:
  - 1 次 32-bit 乘法 + 1 次加法 + 1 次条件判断
  - 或 2 次查表操作
  - 不能再多了
```

### 6.4 推荐工作区

```
              ┌──────────────────────────────────────┐
              │    绝对不可能 (<20 cyc 不够做控制)      │
              │  20-40 cyc (42-83ns): 极限(纯数字IO)   │
   实践下限───│──────────────────────────────────────│
              │  40-96 cyc (83-200ns): 推荐(数字+简单) │
              │  96-240 cyc (200-500ns): 舒适(所有运算)│
              │  240+ cyc (>500ns): 非常宽松            │
              └──────────────────────────────────────┘
```

**建议实际开发起点：200ns**（96 cyc），充分验证后再压到 100ns。

## 7. 输入输出模型

### 7.1 输入模型

V2.0 的输入更新完全由硬件决定，CPU 不做任何同步：

| 输入类型 | 更新方式 | 更新时间 | CPU 如何读取 |
|---------|---------|---------|------------|
| ADC 采样 | DMA Stream1 循环写入 DTCM | 3.28μs/次 | `*ADC_RAW` 直接读 |
| WIRE 数据 | ETH/UART DMA 写入 DTCM | 1-10μs | `WIRE_MAP[i]` 直接读 |
| 传感器换算 | CPU 自己算 | 自由循环中 | `SENSOR_MAP[i]` |
| 数字输入 (GPIO) | DMA 读 GPIO_IDR→DTCM | 100ns-1μs | `*GPIO_BUF` 直接读 |

**关键原则：CPU 读到什么算什么，不做检查。** DMA 新数据到来时自动覆盖 DTCM 中旧值。CPU 下一次迭代自然会读到新值。

### 7.2 输出模型

输出也完全由 DMA/硬件管理：

| 输出类型 | 写入方式 | 硬件输出时刻 |
|---------|---------|------------|
| GPIO | CPU 写 `SHADOW_GPIO` | DMA Stream5 在 TIM2_CH4 或 TIM1_CC4 触发时搬 |
| PWM | CPU 写 `TIM1_CCR1/2/3` | TIM1 下次 UPDATE 硬件自动锁存 |
| 高速脉冲 | CPU 写 SHADOW, DMA 直出 | 每 100ns 更新 |

**注意：SHADOW 可以在 DMA 搬走之前被 CPU 多次覆盖。** 只有最后一个写入的值会被搬走。

```
CPU:  写 SHADOW=0x01  │ 写 SHADOW=0x02  │ 写 SHADOW=0x04  │ ...
      t0              │ t0+50ns         │ t0+100ns        │
                      │                 │                 │
DMA:                  │                 │ ↑ CH4触发, 搬0x04│
   (等待 CH4 触发)    │                 │                 │
```

这意味着 CPU 每 50ns 更新一次 SHADOW，但 DMA 每 200ns 才搬一次——输出的是**最新值**，中间值被覆盖了也没关系。

### 7.3 多输出阶段的复杂场景

对于需要精确时序的多路输出：

```
DMA 子周期输出时序 (1μs 周期):
  
  TIM2_CH1 @ 100ns → DMA: 从 DTCM 搬 4 字节到 GPIOA_ODR (快轴#1)
  TIM2_CH2 @ 300ns → DMA: 从 DTCM 搬 4 字节到 GPIOB_ODR (快轴#2)
  TIM2_CH3 @ 600ns → DMA: 从 DTCM 搬 4 字节到 GPIOC_ODR (快轴#3)
  TIM2_CH4 @ 900ns → DMA: 从 DTCM 搬 16 字节到多个 GPIO (同步锁存)

每个触发点前，CPU 已经在 SHADOW 缓冲区中写好了对应的值。
```

## 8. 实施路线

### Phase 0：验证 DTCM 双端口并发（1-2 天）

```
目标: 在现有硬件上验证 CPU + DMA 可零冲突并发

步骤:
  1. 配置 DMA2_Stream1: DTCM → DTCM (内部搬移, 持续循环)
  2. 在 CPU 主循环中反复读取同一块 DTCM, 统计无等待延迟
  3. 用 GPIO 翻转测量: CPU 读 DTCM 的延迟是否因 DMA 活动而变化

输出: DTCM 双端口零仲裁的实测数据
```

### Phase 1：去掉 ISR，改用自由循环（1 周）

```
目标: 将现有 TIM1 ISR 逻辑搬到主循环

步骤:
  1. TIM1_DIER.UIF = 0 (关中断)
  2. 将 ISR 代码移到 main() 的 while(1) 中
  3. 保留 ADC→DMA(Stream1), SHADOW→DMA(Stream5) 不变
  4. 验证: 100μs 周期下行为一致 (只有 DMA 触发, CPU 循环算)

风险: 
  - 如果计算量 > 100μs → CPU 还没算完一轮就被下一个更新覆盖
  - 解决方案: 用 SHADOW 双缓冲, 或增加看门狗
```

### Phase 2：引入子周期 DMA 触发（2 周）

```
目标: 在 1μs 内通过 TIM2 输出比较产生子周期触发

步骤:
  1. TIM2_CH1..CH4 分别配置触发点 (100ns, 300ns, 600ns, 900ns)
  2. DMAMUX 将 TIM2_CH1..CH4 路由到不同的 DMA 流
  3. ADC 输入仍然用原 DMA Stream1 (独立于 TIM2)
  4. 输出用 TIM2_CH4 触发 SHADOW→GPIO

验证:
  - 示波器量 GPIO 输出边沿: 抖动 <10ns?
  - ISR 条目: 0 (确认 CPU 从未被中断)
```

### Phase 3：压周期（2 周）

```
目标: 逐步降低 TIM2 的 ARR, 测试极限

步骤:
  1. TIM2 ARR = 239 → 1000ns (基准, 验证 DMA 子周期正常)
  2. TIM2 ARR = 119 → 500ns  (验证计算量够用)
  3. TIM2 ARR = 47  → 200ns  (验证 CPU 循环体足够紧凑)
  4. TIM2 ARR = 23  → 100ns  (极限测试, 纯数字 IO)
  5. TIM2 ARR = 11  → 50ns   (探索性测试, 可能失败)

每步验证:
  - CPU 能在周期内完成一次计算迭代
  - DMA 能在子周期点正确触发
  - GPIO 输出抖动 <10ns
  - 无总线仲裁异常
```

## 9. 与 V1.x 代码的兼容性

### 9.1 可以保留的部分

| 组件 | 保留？ | 说明 |
|-----|-------|------|
| DMA2_Stream1 (ADC→DTCM) | ✅ 完全相同 | 输入路径不变 |
| DMA2_Stream5 (SHADOW→GPIO) | ✅ 完全相同 | 输出路径不变 |
| DTCM memory_map | ✅ 完全相同 | `ADC_RAW_BASE`, `SHADOW_GPIO` 地址不变 |
| WIRE_MAP, SENSOR_MAP | ✅ 完全相同 | 计算数据结构不变 |
| TIM1 TRGO (OC4REF→ADC) | ✅ 完全相同 | ADC 触发时机不变 |

### 9.2 需要改变的部分

| 组件 | 改变 |
|-----|------|
| TIM1_DIER | UIE=1→0 (关中断, 仅留 CC4DE=1) |
| TIM2_DIER | UIE=1→0 (关中断, 仅留 UDE=1) |
| main loop | 从"配置完进 idle"改为"配置完进连续计算循环" |
| ISR 代码 | TIM1_UP_IRQHandler 的内容移到 while(1) 中 |
| DMAMUX 配置 | 新增 TIM2_CH1..CH4 到对应 DMA 流的路由 |
| 通讯处理 | 从 ISR/特定 tick → 主循环中均匀穿插 |

### 9.3 升级路径

```
V1.0(100μs ISR) 
    ↓ 第一阶段: 多速率
V1.1(1μs ×120 tick, UIE/UDE 分离) 
    ↓ 第二阶段: 去 ISR 化
V2.0-1μs(关 ISR, 连续计算, 1μs DMA 触发)
    ↓ 第三阶段: 压周期
V2.0-100ns(连续计算, 100ns DMA 子周期)
```

## 10. 风险与应对

| 风险 | 严重性 | 缓解措施 |
|------|--------|---------|
| CPU 计算超期 → DMA 搬走了旧 SHADOW | 中 | 计算量要有 50% 余量; 或启用 SHADOW 乒乓缓冲 |
| DMA 触发点错位 → 输出时序混乱 | 高 | DMAMUX 配置严格验证; 示波器测量每个触发点 |
| 总线仲裁在 D2-D3 桥出现 | 低 | 避免 AHB→AXI 跨域; 所有数据放在 D1 DTCM |
| ADC 转换未完成 → CPU 读到旧值 | 低 | 本来就是异步设计, 读到旧值下次迭代自然读到新的 |
| 调试困难 (无 ISR 断点) | 高 | 保留一个调试用 GPIO 翻转 (有条件编译); 用 DMA 的 FIFO 做 trace |

---

## 11. 总结

V2.0 的核心价值不是"把周期从 1μs 压到 100ns"，而是**打破了"周期 = 中断间隔"的思维枷锁**：

| 旧思维 | 新思维 |
|--------|--------|
| "周期由定时器中断周期决定" | "周期由 CPU 循环体执行时间决定" |
| "输入输出在特定时刻" | "输入输出持续进行, 由 DMA 管理" |
| "CPU 在 ISR 中工作" | "CPU 永远是主循环, DMA 是后台" |
| "周期降低受 ISR 开销限制" | "周期降低受 CPU 指令数限制" |
| "100ns 不可能(Cortex-M7)" | "100ns 有可能(48 cyc 足够做一次控制运算)" |

**事实：DTCM 双端口 + DMAMUX + 无中断设计 让 100ns 周期在 H723 上成为可能。**

下一步是 Phase 0 的验证——用现有硬件实测 DTCM 双端口是否真的零仲裁。如果验证通过，V2.0 的架构基础就稳了。
