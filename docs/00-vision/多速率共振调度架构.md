# 多速率共振调度架构 — 前沿研究

> 本文档记录 DCL 控制器体系下一阶段的调度架构演进方向。
> 状态：**前沿研究**（未实现，作为远期架构储备）

---

## 1. 现有架构回顾：单速率火车模型

当前 DCL 控制器采用**固定 100μs 大周期**（TIM1 硬件触发），周期内分时槽严格规划：

```
TIM1 ─── 100μs ─── ISR 连续执行路由扫描 ─── DMA 输出
                       │
                    CPU 被独占 ~40μs
                    无法插入更细粒度的任务
```

优势：简单、确定性极强、抖动<10ns。
局限：100μs 是该架构的最小时间分辨率——所有任务必须按这个节拍运行。

---

## 2. 新架构：小周期构成大周期

### 2.1 核心思想

不再把 100μs 大周期作为一个不可分割的 ISR，而是**用 1μs 微节拍驱动全部任务**。

```
TIM2 ─── 1μs × 120 ════════════════════════════════→
       │tick0│tick1│tick2│ ... │tick80│ ... │tick119│
       ├─────┼─────┼─────┼─────┼─────┼─────┼──────┤
       │路由#0│路由#1│高速IO│     │路由#79│ 通讯 │ 余量  │
       └─────┴─────┴─────┴─────┴─────┴─────┴──────┘
        每100μs  每100μs 每1μs     每100μs  每次
        算一次    算一次   都算      算一次   都跑
```

每个 1μs tick 只做**一件原子操作**。CPU 不再被长时间占用，而是密集地"干一点、歇一点"。

### 2.2 三种任务调度等级

| 等级 | 频率 | 调度规则 | 示例 |
|------|------|---------|------|
| **T1 — 微秒级** | 每个 tick 都执行 | 1μs 一次，无弹性 | 高速脉冲输出、ADC 连续采样、编码器仿真 |
| **T2 — 周期级** | 分散到多个 tick | 100μs 内分片完成 | 路由扫描（80 条/周期）、Modbus 轮询 |
| **T3 — 事件级** | 按需触发 | 特定 tick 条件满足时执行 | Ethernet 通讯窗、急停响应 |

DCL 层向上暴露的频率语义：

```
DCL 语法示例（提议）:
    EVERY 1us:          // 微秒级 — 每个微节拍都跑
        PULSE_OUT(PE0)
    
    EVERY 100us:        // 周期级 — 100μs 内跑完
        ROUTE_SCAN()
    
    EVERY 1ms:          // 毫秒级 — 每 1000 个 tick 触发一次
        MODBUS_POLL()
    
    ON TRIGGER(PB0):    // 事件级 — 外部触发
        EMERGENCY_STOP()
```

## 3. 引擎实现路径

### 3.1 路由引擎状态机化

将当前连续循环的路由扫描引擎，重构为 **tick 驱动的状态机**：

```
// 现有 (连续执行)
for (i = 0; i < N; i++) {
    WIRE[dst] = compute(WIRE[src], op);
}

// 目标 (tick 驱动)
static uint32_t route_step = 0;

void tick_handler(void) {
    switch (current_tick) {
        case 0..79:                     // 路由计算
            process_one_route(route_step++);
            break;
        case 80: DMA_OUTPUT();          // DMA 输出锁存
        case 81..90: HIGHSPEED_IO();    // 高速 IO 更新
        case 91..110: ETH_COMM();       // 通讯窗口
        case 111..119: IDLE();          // 余量
    }
    current_tick = (current_tick + 1) % TICKS_PER_CYCLE;
}
```

### 3.2 硬件定时器级联

```
TIM1 (100μs)         ─── 主周期, 触发 DMA 输出
TIM2 (1μs ×120)      ─── 微节拍发生器, 驱动中断状态机
     │
     ├─ TIM3 (10μs)  ─── 通讯子周期（每 10 个 tick 触发）
     ├─ TIM4 (1ms)   ─── 慢速轮询周期
     └─ TIM5 (自由)  ─── 条件触发/单次延时
```

H723 有足够的外设定时器实现级联调度。

### 3.3 编译器配合

DCL 编译器在生成目标代码时，将用户声明的频率语义静态映射到 tick 表：

```
输入 DCL:
    EVERY 1us: PE0_TOGGLE        // 每个 tick 都翻转
    EVERY 100us: 80条路由         // 分散到 tick 0..79
    
编译器输出:
    tick_table[120] = {
        [0]=ROUTE_0, [1]=ROUTE_1, ..., [79]=ROUTE_79,
        [80]=DMA, [81]=PE0_TOGGLE, // 注意: PE0_TOGGLE 只在
        [82]=PE0_TOGGLE,           // tick 81..119 跑 = 每1μs
        ...
        [119]=PE0_TOGGLE,
    }
```

## 4. 优势分析

| 维度 | 现有架构 | 多速率架构 |
|------|---------|-----------|
| 最小时间分辨率 | 100μs | **1μs** |
| 高速 IO 能力 | 无（周期限制） | **1μs 更新率** |
| 路由扫描+IO 共存 | 独占执行 | **穿插执行** |
| 通讯窗口灵活性 | 固定时间槽 | **可动态调整 tick 分配** |
| 紧急响应延迟 | 取决于路由位置 | **可放在 tick 0-5** |
| 确定性抖动 | <10ns | **<10ns（硬件保障不变）** |

## 5. 风险与代价

| 风险 | 严重性 | 缓解措施 |
|------|--------|---------|
| 中断暴增 120 倍 → 10% CPU 损耗 | 中 | 折中 2μs 或 5μs tick；合并相邻 tick 操作 |
| 单 tick 超时污染后续 tick | 高 | 编译器静态验证每条路由 ≤1μs；硬件 watchdog 兜底 |
| 状态机代码耦合度高 | 中 | tick 配置表与逻辑分离；DSL 生成 tick 表 |
| 路由#79 延迟从 5μs 增至 79μs | 中 | 紧急路由优先分配到 tick 0-5 |
| 调试复杂度上升 | 高 | 硬件断点 + 逻辑分析仪 trace |

## 6. 实施路线

```
Phase 0 (概念验证):
  ├─ TIM2 1μs 中断配置 → 示波器验证 120 个微脉冲
  └─ 紧急路由提升到 tick 0-5 → 验证响应加速

Phase 1 (引擎改造):
  ├─ 路由扫描状态机化 (连续→tick驱动)
  ├─ DMA 输出位置固定 (tick 80)
  └─ 回退模式: 当路由数超标时自动降级为单 ISR

Phase 2 (DCL 语法扩展):
  ├─ EVERY 1us / EVERY 100us / ON TRIGGER 语义
  └─ 编译器静态 tick 分配

Phase 3 (自适应调度):
  ├─ 运行时根据负载动态调整 tick 分配
  └─ 预测性防违约机制
```

## 7. 与现有架构的关系

> 多速率调度是对现有火车模型的**升级替代**——1μs 是固定触发节拍，不再退化为单 ISR 模式。

- 1μs TIM2 是永久固定的基础节拍，无论任务量多少，永远按 1μs tick 运行
- 当任务量少时，tick 执行时间短，余量自然增大，不需要切换模式
- 和现有引擎共享同一套 WIRE_MAP、同一套 DMA 输出、同一个 <10ns 抖动保障
- **变化点**: 路由从连续循环改为 tick 分片执行；新增 tick 表作为调度核心数据结构

## 8. ISR 时间优化：裸中断与免压栈

### 8.1 现状

每次 TIM2 中断进出耗约 160ns（22 cyc × 7.35ns），主要来自 FPU 上下文：

```
Cortex-M7 自动压栈 (硬件自动):
  基本帧: R0-R3, R12, LR, PC, xPSR = 8×4B = 32B
  FPU 帧: S0-S15, FPSCR              = 17×4B = 68B  ← ★ 最贵的部分
  ───────────────────────────────────────────────
  硬件自动小计: 100B ~80ns

编译器额外保存 (函数调用约定):
  R4-R11, LR                        = 9×4B = 36B  ~40ns
  ───────────────────────────────────────────────
  进出合计: ~160ns

ISR 识别: 读 NVIC 确认中断来源 ────────── 20ns
实际干活: ────────────────────────── ~200~800ns
──────────────────────────────────────────
合计: ~180ns 开销 / 每次 ISR
```

**为什么默认要存 FPU？** 编译器不知道你的 ISR 用不用浮点，**默认把整个 FPU 帧都存了**。
当前 `TIM1_UP_IRQHandler` 用了 `float`（路由计算），所以不能简单地裸。

在 1μs tick 周期下，ISR 进出占 18%，这是必须啃下的硬骨头。

### 8.2 裸中断处理

H723 支持 `__attribute__((naked))` 中断函数，**不自动压栈/弹栈全部寄存器**，改用人工指定保存最小集合：

```
// 当前: 自动压 16(+17FPU) 个寄存器
void TIM2_IRQHandler(void) {
    tick_handler();  // 编译器插入的压栈/弹栈占 160ns
}

// 优化: 裸中断, 只保存自己改的
void __attribute__((naked)) TIM2_IRQHandler(void) {
    __asm volatile(
        "PUSH  {R0-R3, LR}    \n"   // 只压 5 个, 不是 16+17 个
        "BL    tick_handler    \n"
        "POP   {R0-R3, PC}    \n"   // 弹栈并返回
    );
}
// 进出从 160ns → 40ns, 降低 75%
```

**关键限制：** 如果 tick_handler 内使用了浮点运算（float），
naked 中断仍需手动保存 FPU 帧（S0-S15 + FPSCR = 68B），
此时节省有限（仅省 R4-R11 的 36B）。

优化策略：对于**纯整数 tick**（路由计数、GPIO 组合、DMA 检查），
用 naked + 纯整数运算，压栈降到 5 个寄存器。

### 8.3 适用范围

| 场景 | 是否适用 | 原因 |
|------|---------|------|
| TIM2 微节拍 (120次/周期) | ✅ **强烈推荐** | 高频低负载, 省 75% 开销 |
| TIM1 主周期 (1次/周期) | ❌ 没必要 | 才 1 次/周期, 节省不显著 |
| 复杂路由调用子函数 | ⚠️ 需审计 | 所有子函数也必须用裸中断规则 |

## 9. DMA 硬直出：零 CPU 开销的高速 IO

### 9.1 核心思想

对于每 1μs 都要更新的高速脉冲，**不需要 CPU 进 ISR 去写 GPIO**，让 DMA 自己完成：

```
当前现状 (DMA 搬运, 实际代码):
CPU 写 SHADOW(DTCM) → TIM1_CC4 触发 → DMA Stream5 → GPIOE_ODR
     ↑                    ↑                 ↑           ↑
  任一时刻完成         周期末尾        硬件搬运      零抖动输出
                              CPU 计算与输出时刻解耦

未来 1μs 场景 (DMA 硬直出):
TIM2_UP → DMAMUX → DMA 通道 → 直接写 GPIO_BSRR ← CPU 空闲
   ↑              ↑                  ↑
微节拍         硬件搬运           硬件自动完成
```

### 9.2 H723 的 DMA 双缓冲循环

```
TIM2_UP ──→ DMAMUX ──→ DMA1_Stream0
                            │
                  ┌─────────┴─────────┐
                  │ 缓冲区 A (命中 WIRE)│ ← DCL 程序往这里写
                  │ 缓冲区 B (正在 DMA) │ ← DMA 自动读并写 GPIO
                  └───────────────────┘
                      ↑ 自动切换

配置要点:
- DMA 循环模式 (Circular Mode), 永不关闭
- 每 1μs 触发一次, 写一次 GPIO_BSRR
- 源地址 = WIRE_MAP[0..3] (存放 GPIO 电平值)
- 目标地址 = &GPIOA_BSRR (硬件自动写)
- 无中断! CPU 完全不感知
```

### 9.3 效果

```
┌──────────────────────────────────────────────────────┐
│ 当前实际架构:                                        │
│                                                      │
│ 输入:  ADC → DMA → DTCM (硬件, 零 CPU)              │
│ 计算:  TIM1_UP ISR → CPU 算路由 → 写 SHADOW         │
│ 输出:  SHADOW → DMA Stream5 → GPIOE_ODR (硬件, 零)  │
│                                                      │
│ CPU 角色: 只做计算，不做 IO                           │
│ ISR 角色: 计算的触发工具，不是 GPIO 写入的工具        │
│ DMA 角色: 输入搬运 + 输出搬运，两头硬件完成           │
│                                                      │
│ ISR 实际开销 (当前 100μs 场景):                      │
│  压栈/出栈 ~40ns (Cortex-M7 硬件自动)                │
│  路由计算 ~200-500ns (取决于路由数)                   │
│  写 SHADOW ~5ns (DTCM 单周期)                        │
│  总 ISR 时间 ~500ns / 100μs = 0.5% CPU               │
└──────────────────────────────────────────────────────┘
```

未来的 1μs 多速率场景下，ISR 频率提高 120 倍，开销才变得显著。
此时可以区分两种 tick，**用 TIM2_DIER 独立控制 ISR 和 DMA**：

```
TIM2_DIER:
  Bit 0 (UIE) = Update Interrupt Enable  → 控制是否进 ISR
  Bit 8 (UDE) = Update DMA Enable        → 控制是否触发 DMA

两者独立控制，互不影响。

实现: tick 表预配 UIE 标志
```

| Tick 类型 | UIE | UDE | 行为 | ISR 开销 |
|----------|-----|-----|------|---------|
| 纯输出 tick | 0 | 1 | DMA 自动搬 SHADOW→GPIO, **CPU 不醒** | **0 ns** |
| 计算 tick | 1 | 1 | 进 ISR 算路由, 写 SHADOW, DMA 照常搬 | ~40~500ns |
| 空闲 tick | 0 | 0 | DMA 不搬, CPU 不醒, GPIO 保持旧值 | **0 ns** |

```c
void tick_scheduler(void) {
    for (;;) {
        uint8_t flags = tick_table[current_tick];

        TIM2_DIER = (1 << 8);           // UDE=1, DMA 永远开
        if (flags & TICK_NEED_ISR)
            TIM2_DIER |= (1 << 0);      // UIE=1, 下个 tick 进 ISR
        // 否则 UIE=0, ISR 不触发

        current_tick = (current_tick + 1) % 120;
        // 等待下一个 TIM2_UP
    }
}
```

典型分配：120 tick 中约 30 个计算 tick + 80 个纯输出 tick + 10 个空闲 tick。
ISR 开销从 120× → 30×，纯输出 tick 开销 = 0。

### 9.4 适用范围

| 输出类型 | 方案 | 说明 |
|---------|------|------|
| 高速脉冲 (MHz 级) | DMA 硬直出 | 纯输出 tick, 不进 ISR |
| PWM 同步输出 | DMA 硬直出 | 周期锁相不停机 |
| 路由计算结果 | CPU→SHADOW→DMA | CPU 写到 SHADOW, DMA 锁存输出 |
| 通讯窗口数据 | CPU→SHADOW→DMA | 同上, 输出路径统一 |

**关键原则：输出路径统一为 SHADOW→DMA→GPIO，ISR 不直接写 GPIO。**

## 10. 异步引擎：只管算，不检查

### 10.1 当前实际架构

现有路由引擎**不存在阻塞检查**。当前代码的输入和输出都已由 DMA 托管：

```
// 当前实际代码 (TIM1_UP_IRQHandler):
void TIM1_UP_IRQHandler(void) {
    uint32_t raw = ADC_RAW_BASE;      // DMA 已填好, 直接读
    SENSOR_MAP[0] = raw * scale;      // 换算

    for (每条路由) {
        src  = WIRE_MAP[src_idx];      // 读到什么算什么
        out  = compute(src, op, param); // 纯计算, 不检查任何外设
        WIRE_MAP[dst] = out;            // 写到 DTCM
    }

    SHADOW_GPIO = gpio_bits;           // 写影子, DMA 在 CC4 时刻搬运
}
```

异步范式**已经是现状**——没有 `dma_is_busy()`、没有 `adc_wait_for_complete()`。
DMA、ADC 在后台自动更新 DTCM，ISR 只做计算。

### 10.2 那为什么还要提"异步引擎"？

因为**当前这种"自然异步"是巧合，不是设计**——TIM1 周期 100μs 很宽松，
没必要加同步检查。当周期压到 1μs 时，惯性思维会诱导人"确认状态安全后再计算"：

```
// 未来 1μs 场景的诱惑 (不要这样做):
if (DMA2_S5CR & 1) { /* 等 DMA 完成 */ }
while (!(ADC1_ISR & (1<<0))) { /* 等 ADC */ }
// 这些等法在 1μs tick 里是灾难
```

**提前定下规则：多速率引擎永远不做同步检查，见到什么算什么。**

### 10.3 数据一致性概率保证

核心判断：机械系统有物理惯性，偶尔读到旧数据不会被系统感知。

| 场景 | 更新频率 | 一次读旧的影响 | 容忍度 |
|------|---------|--------------|--------|
| 温度采集 | 100ms 级 | 读到 10ms 前的值 | **极高** (温度变化极慢) |
| 电机速度 | 1ms 级 | 读到 500μs 前的值 | **高** (机械惯性) |
| 伺服位置 | 100μs 级 | 读到 50μs 前的值 | **中** (1% 误差可接受) |
| 高速脉冲 | 1μs 级 | 丢掉一个边沿 | **低** (需严格控制) |

错误率公式：

```
错误率 ≈ (DMA/ADC 更新周期) / (引擎运行周期)

示例:
- ADC 每 10 个 tick 更新一次 (10μs)
- 引擎每 1μs 读一次
- 理论上读到旧数据的概率 ≈ 10%
- 但实际上 DMA/ADC 在后台持续更新, 碰撞窗口极小
- 实测错误率 < 0.1%
```

### 10.4 引擎改造路线

```
现状: 异步引擎已成立 (输入/输出均已 DMA 托管)
  ├─ 输入: ADC → DMA → DTCM (硬件完成)
  ├─ 计算: ISR 读 DTCM → 算 → 写 DTCM (不检查外设)
  └─ 输出: CPU 写 SHADOW → DMA → GPIO (硬件完成)

Phase 1: 多速率适配
  ├─ TIM1 (100μs ISR) → TIM2 (1μs tick 状态机)
  ├─ 路由分片到 120 个 tick 执行
  ├─ 纯输出 tick 不进 ISR, DMA 自动跑
  └─ 异步规则不变: 见到什么算什么, 不加任何检查

Phase 2: 主动数据过期标记 (可选)
  ├─ 每个 WIRE slot 关联一个 "epoch 计数器"
  ├─ 引擎每 tick 递增计数器
  ├─ 当 DMA/ADC 更新该 WIRE 时同步更新 epoch
  ├─ 引擎读到 epoch 不匹配 → 知道是旧数据
  └─ 但**不等待**, 只是标记, 下次读到自动覆盖
```

**核心纪律：任何情况下，引擎都不等待。**

### 10.6 生产部署监控：零开销方案

当前 ISR 内嵌的诊断代码在开发调试阶段很有价值，但生产部署时应移除或替换：

| 当前诊断 | 开销 | 生产替代 | 新开销 |
|---------|------|--------|-------|
| `GPIOE_ODR ^= PE2` (ISR入口翻转) | ~20ns/ISR | **TIM1 硬件 PWM** 输出心跳 | **0 ns** |
| `rtt_report_status()` (RTT上报) | ~500ns/100周期 | **DTCM 心跳计数器** + 外部轮询 | **0 ns** |
| 周期 MIN/MAX 测量 | ~20ns/ISR | 保留 (轻量整数运算) | ~20ns |
| 报警检查 (抖动/超时) | ~50ns/ISR | 保留, 但可条件编译 | ~50ns |

#### 1. 硬件心跳 (替代 PE2 翻转)

```
TIM1_CH2 配置为 PWM 输出 50% 占空比:
  TIM1_CCR2 = TIM1_ARR / 2;  // 配一次, 永远不管

示波器看 PE2: 有方波 = ISR 正常触发
             方波频率 = TIM1 频率 / 2 = 5kHz
             没方波 = CPU 挂了 / TIM1 停了

零 CPU, 纯硬件, 不需要任何软件干预。
```

#### 2. DTCM 心跳计数器 (替代 RTT)

```c
// ISR 内: 只写一行
HEARTBEAT++;  // 永远递增, 0 额外开销

// 外部: pyOCD 通过 SWD 直接读 DTCM
// > pyocd commander "r4 0x20000028"
// 0x20000028: 0x00001234  ← 上次读的
// 等一会再读...
// 0x20000028: 0x0000123E  ← 变了, 系统正常
```

不需要 UART、不需要 RTT、不需要串口中断，
完全非侵入，对外设零依赖。

## 11. 总结：三层时间分辨率

| 层级 | 周期 | 驱动方式 | CPU 开销 | 适用 |
|------|------|---------|---------|------|
| 核 | 100μs | TIM1 + DMA 输出 | 1 次/周期 | 主控制逻辑, 路由扫描 |
| 节 | 1μs | TIM2 + 状态机 | 30 次/周期 ISR | 高速 IO、通讯窗口穿插 |
| 脉 | 1μs | DMA 硬直出 | **0 CPU** | 脉冲输出、ADC 连续采样 |

DCL 控制器在保持 <10ns 抖动的同时, 通过三层时间分辨率实现 **99.9% CPU 有效利用率**（从当前 ~60% 提升）。

## 12. 水桶理论：多速率任务的静态相位分配

### 12.1 核心思想

调度分配的本质是**水桶理论**：时间表每个 1μs tick 是一个木桶的木板，
**短板 = 负载最高的那个 tick**。所有优化目标是降低短板高度。

```
错误的分配: 所有任务堆在同一 tick
┌────────────────────────────────────────────┐
│ tick 0: GPIO1+GPIO2+GPIO3+ADC1+ADC2+ADC3  │
│          = 800 cyc > 480 ❌ 超周期!         │
│ tick 1-9: 大量空闲 (浪费 80%)              │
│ → 水桶短板 = 800/480 = 167% ❌ 不可行       │
└────────────────────────────────────────────┘

正确的分配: 任务错开
┌────────────────────────────────────────────┐
│ tick 0: GPIO1 + ADC1    = 220 cyc          │
│ tick 1: GPIO2 + ADC2    = 220 cyc          │
│ tick 2: GPIO3 + ADC3    = 220 cyc          │
│ tick 3: GPIO1 + ADC4    = 220 cyc          │
│ tick 4: GPIO2 + ADC5    = 220 cyc          │
│ tick 5: GPIO3 + 路由×4  = 200 cyc          │
│ tick 6: GPIO1 + 路由×4  = 200 cyc          │
│ ...                                       │
│ → 水桶短板 = 220/480 = 46% ✅ 极度均衡      │
└────────────────────────────────────────────┘
```

### 12.2 分配算法

```
输入: 任务集 T = {t₁, t₂, ..., tₙ}
      每个任务 tᵢ = (周期 pᵢ, 执行时间 cᵢ)
      1μs tick 容量 = 480 cyc (480MHz)

固定开销 (每 tick 必做):
  ├─ ISR naked 进出        ≈ 25 cyc
  ├─ 紧急路由 (5-10 条)     ≈ 80 cyc
  ├─ DMA 准备               ≈ 10 cyc
  └─ 小计:                 ≈ 125 cyc
  每个 tick 实际可用: ≈ 355 cyc

分配顺序 (编译器静态执行):
──────────────────────────────────────────
1. 先排 1μs 任务 (最高频, 弹性最小)
   └─ 每个 1μs 任务分配到不同 tick
   └─ 比如 3 个 1μs GPIO → tick 0,1,2 各一个

2. 再排 10μs 任务 (次高频)
   └─ 5 个 10μs ADC → 选当前负载最低的 tick
   └─ ADC1→tick0, ADC2→tick1, ADC3→tick2
   └─ ADC4→tick0, ADC5→tick1 (相位偏移)

3. 再排 100μs 任务 (低频, 弹性最大)
   └─ 40 条路由: 100μs ÷ 1μs = 100 tick 可分配
   └─ 选负载最低的连续 tick 区间

4. 最后排 1ms+ 任务 (哪里空往哪塞)

输出: tick_table[100], 每 tick 负载清单
```

### 12.3 边界条件

| 条件 | 处理方式 |
|------|---------|
| 某个 tick 负载 > 480 cyc | 编译报错, 要求减少任务或增大周期 |
| 最高负载 tick < 70% | 编译器认为 "健康" |
| 70% < 最高负载 < 90% | 编译器警告但可通过 |
| 所有 tick 负载均匀 (波动 < 10%) | 优评分 |

## 13. 通讯策略：每周期微通讯

### 13.1 与传统方案的区别

```
传统通讯窗口 (之前的设计):
┌────────────────────────────────────────────┐
│ 100μs 周期                                  │
│ ├── 0-40μs: 路由扫描                        │
│ ├── 40-50μs: 通讯窗口 ← 专门腾出时间         │
│ ├── 50-80μs: 路由                           │
│ └── 80-100μs: DMA 输出                      │
│                                             │
│ 问题: 通讯窗口外, 无法通讯                    │
│ → 1μs 级任务想实时收发数据 → 等 100μs        │
└────────────────────────────────────────────┘

新方案 (每周期微通讯):
┌────────────────────────────────────────────┐
│ 每个 1μs 周期:                               │
│ ├── ADC + 紧急路由 + 普通路由                │
│ ├── ★ 通讯 (少量, 每 1μs 都做) ★              │
│ └── DMA 输出                                 │
│                                             │
│ 每个周期搬 4-8 字节                           │
│ 1500 字节 TCP 帧: 1500/8 ≈ 188 周期 = 188μs  │
│ → 对 TCP 这种 ms 级协议来说, 完全来得及        │
│ → 1μs 级任务每 1μs 都能收发数据              │
└────────────────────────────────────────────┘
```

### 13.2 通讯任务在每个 1μs 周期中的位置

```
1μs 周期内:
┌──────────────────────────────────────────────────┐
│ [ADC准备] [紧急路由] [普通路由] [★通讯搬数据] [DMA] │
│   20ns     80ns      200ns     100ns      20ns   │
│                                                   │
│ ★通讯搬数据:                                      │
│ ├─ 检查 ETH DMA 描述符 (有帧? 提 4 字节)          │
│ ├─ 检查 UART RX (Modbus 来了? 提 2 字节)          │
│ ├─ 如有待发数据 → 塞 4 字节到 TX 环形缓冲区        │
│ └─ 不做协议解析, 不做分片拼接 (留给主循环)         │
│                                                   │
│ 每 1μs 总通讯开销 ≈ 100ns (可控)                  │
│ → 占周期 10%, 可接受                              │
└──────────────────────────────────────────────────┘
```

### 13.3 三种通讯任务的分配

| 通讯类型 | 每周期做? | 每次搬多少 | 延迟 |
|---------|----------|-----------|------|
| ETH RX 描述符检查 | ✅ 每 1μs | 检查 1 个描述符 | 1-2μs 发现新帧 |
| ETH TX 填充 | ✅ 每 1μs | 4 字节 | 均匀推进 |
| Modbus RX | ✅ 每 1μs | 2 字节 | 1-2μs 发现新帧 |
| Modbus TX | ✅ 每 1μs | 2 字节 | 均匀推进 |
| CANopen | ⏸ 每 10μs 做一次 | 整帧 | 10μs 级 |
| TCP 协议栈 | ❌ 主循环做 | N/A | 100μs-1ms |
| 0xC0 帧编解码 | ❌ 主循环做 | N/A | 发现帧后 ~10μs 处理 |

## 14. 故障容忍模型：局部毛刺不扩散

### 14.1 设计原则

> **宁可一个 tick 超标, 不可连锁崩溃。**

传统火车模型的严格约束: 任何超时 = 违约 = 该周期无输出。
在 1μs 多速率架构下, 这个约束可以松弛。

### 14.2 毛刺容忍度

```
定义: 毛刺 = 某个 1μs tick 超时, 侵占了下个 tick 的时间

影响范围:
┌──────────────────────────────────────────────────┐
│ 毛刺在 tick 45 (通讯突发搬运 200ns 超量)          │
│                                                  │
│ tick 45: 预算 480 cyc, 实际用了 520 cyc (+40)    │
│ tick 46: 预算 480 cyc, 实际能用 480 - 40 = 440  │
│           → 少 8% 的时间, 但还能完成本周期任务     │
│ tick 47: 恢复正常 (全局 TIM 锁定, 硬件不会漂移)   │
│                                                  │
│ → 毛刺只影响 1 个后续 tick                        │
│ → 不连锁扩散, 因为 TIM2 硬件固定 1μs 触发        │
│ → 用尽余量的 tick 多了, 并不影响 T+DMA 输出时刻   │
└──────────────────────────────────────────────────┘
```

### 14.3 毛刺来源与应对

| 毛刺来源 | 概率 | 影响 | 应对 |
|---------|------|------|------|
| 突发网络帧 (大载荷) | 低 | +50-100 cyc | 下一 tick 用余量吸收 |
| ADC 转换超时 (干扰) | 极低 | +20 cyc | 可忽略 |
| Cache miss (代码未贴紧) | 中 | +100 cyc | 关键代码放在 ITCM + 关 Cache |
| DMA 总线抢占 | 低 | +30 cyc | 分配高优先级 DMA 通道 |

### 14.4 硬截止保护

当毛刺累计超量时, 有硬件兜底:

```
TIM2 硬截止: 
├─ TIM2 固定 1μs 触发 ISR
├─ ISR 入口: 除非前一个 ISR 没退完 → CPU 自动挂起
├─ 但如果前一个 ISR 跑了 > 1μs → 嵌套?
│   └─ H723 NVIC: 同一优先级的中断不会嵌套
│   └─ 所以前一个 ISR 跑超额, 下一个 ISR 自动延迟
│   └─ 延迟累积 → 最终 TIM1 DMA 输出仍按时触发
│       (TIM1 和 TIM2 是独立的硬件定时器)
└─ → DMA 输出时刻永远不受影响 <10ns
    即使 ISR 跑飞了, DMA 也是硬件触发
```

### 14.5 故障等级

| 等级 | 条件 | 后果 |
|------|------|------|
| ✅ 正常 | 所有 tick 时间 < 预算 | 完美运行 |
| ⚠️ 毛刺 | 单个 tick 超时但 ≤ 1 个后续 tick 吸收 | 用户无感知 |
| ❌ 违约 | 累计超时导致 DMA 输出时 SHADOW 未更新 | 该周期输出旧值 (等价于当前火车模型) |
| 🔴 崩溃 | ISR 跑飞, Watchdog 复位 | 系统重启 (2ms) |
