日期: 2026-09-11 · 项目: `D:\STM\8.29 AIAutoFactior\9.10 H723newest`

## 0. 一句话

S3 回归的**最后一个真缺口 T26 已转绿** (套件 21/30 → **22/30**, 脚本零改动)。
关键不是"把 flush 加回去" (那件事失败过三次), 而是**换掉触发权的归属**;
顺带把一个更深的结构性缺陷修掉了 —— **中断向量表原本在 FLASH, 擦除期间取向量也会被 stall**。

T15 是**半可修**: 落盘半段已修好 (`持久化=ok`), 剩下的"上电自动加载"判据需要一次**真实复位**,
而 CH340 的 RTS **没有接到 H723 的 NRST** ⇒ 只能手按板上 RST。

## 1. T26 要什么 (S3 `tools/test_dcl.py:540-573` 逐条)

| 判据 | 含义 |
|---|---|
| `dirty_pending` | RUN 中 deploy 只热重载 + 标 dirty |
| `still_pending` | 再过 1s dirty **仍挂起** ⇒ 运行期 0 flash 操作 (PERSISTENT 语义) |
| `no_freeze` | 运行期 `pmax < 300000` ⇒ 无 ~28ms 巨拍 |
| `flushed` | **STOP 后 dirty 自动被清** |
| `WIRE1 == 2.0` | START 后新表真在工作 |

前四条 H723 早就满足,**卡死在 `flushed`**: S3 靠 FreeRTOS 后台任务 `persist_task` 落盘,
H723 是裸机单循环, 只有 `0x43 mode=1` 显式落盘与 `g_persist_req` 两条路。

## 2. 为什么前三次都失败 (以及本次为什么不重蹈)

三次尝试 (每 0.5s 重试 / 闩锁只试一次 / 闩锁+可观测计数) **都把套件从 21/30 打到 5/30**。

最小复现给出的机制: erase 一个 128KB 扇区要 ~1s 量级 (实测丢 **8153 拍** ≈ 816ms 的拍),
期间**整机失聪** —— 而套件里几十次 deploy/STOP 会把这 1s×N 叠成级联失败。

三次的共同点: **固件自己按时间猜窗口**。而裸机上唯一知道"现在可以安全阻塞 ~1s"的是**上位机**
—— 它才是发 `0x12 STOP` 的那一方, 也是那个正在每 20ms 轮询 `0x43` 等结果的 `wait_flush`。

### 本次的触发权归属 (两段式, 每段都可被外部读回)

```
登记 (h_persist_w2):  收到 **载荷为空** 的 0x43 (纯查询) 且 dirty==1  →  g_persist_auto = 1
裁决 (主循环):        引擎 RUN? → g_persist_auto_gate++ (放弃, dirty 保持)
                      否则     → persist_save()         (g_persist_auto_runs++)
```

三条硬要求, 每条都有理由:

1. **只登记, 不落盘** —— 该 0x43 的 ACK 必须**先完整移出** (`uart1_write` 等 TC 才返回),
   主循环随后才动手。反过来的顺序会把 ACK 卡在 erase 里 ⇒ PC 看到的第一帧就是丢帧, 判据直接失败。
2. **裁决放主循环** —— 第一版把 `ENGINE_RUN==0` 写进登记条件, 结果 `g_persist_auto_gate`
   **恒为 0**: 一个**不可能失败**的判据, 等于没测。拆开之后, "T26 在 RUN 中被问两次都放弃"
   这件事本身就成了可读回的证据。
3. **不做任何自由重试** —— 没被问就绝不落盘; 被问一次最多落一次 (成功后 dirty 清零)。
   影响面 = 整个套件**全部 5 个** 0x43 调用点。

★ 与"S3 语义"的关系: S3 的 `persist_task` 在"引擎不跑的窗口"落盘; H723 把"窗口在哪"
交给上位机判定。**语义等价物**, 不是绕过 —— 而且更确定 (停顿时刻可被上位机控制)。

## 3. 配套修的结构性缺陷: 向量表原本在 FLASH

`VTOR` 原值 = `0x08000000` (FLASH), 而 **sector erase 会 stall 从 FLASH 取指**
⇒ 擦除期间**中断根本进不来**。注意: "ISR 代码已经放进 ITCM"**不够** ——
**取向量这一步本身也要过 FLASH**。

修法 (两处):
- `ld/STM32H723ZG_FLASH.ld`: `.isr_vector` 导出 `_siv`/`_eiv`; 新增 `.itcm_vectors (NOLOAD)`
  1KB (128B 对齐, 符号 `_vtor_itcm`)。
- `src/main.c`: `main()` 开头 (使能任何中断之前) 把表拷进 ITCM, 设 `SCB->VTOR`,
  并把实际值写进 `g_vtor`。**容量不足就点灯停机**, 不做"静默只拷一部分"。

实测 (H723: 167 个向量 = 668B; ITCM 副本区 1KB):

| | VMA | 结果 |
|---|---|---|
| `_siv` / `_eiv` | `0x08000000` / `0x0800029C` | 668B, 167 向量 |
| `_vtor_itcm` | `0x00001800` | 128B 对齐, 紧跟 `.itcm_text` 结束 (0x17C8), 不重叠 |
| 运行期 `SCB->VTOR` | `0x00001800` | ✅ 不再是 `0x08000000` |
| ITCM 副本 vs FLASH 原件 | 头尾逐字比对 | ✅ 一致 |

### ★★ A/B: 判据能失败才算判据

`-DDCL_VTOR_ITCM=0/1` (交付默认 1, `build.sh` 每次显式传)。两份固件用**同一套测量方法**:
停掉引擎 → 请求落盘 → 每 100ms 采一次 `g_tick_count`, 标称 1000 拍/槽。

| 构建 | 向量表位置 | 每槽增量 | 累计丢失 |
|---|---|---|---|
| `-DDCL_VTOR_ITCM=0` | FLASH | 前 6 槽 ~1010, **第 7~14 槽 Δ=0**, 第 15 槽 Δ=798 | **8153 拍** |
| `-DDCL_VTOR_ITCM=1` (交付) | ITCM | 每槽 1009~1015, 全程无 Δ=0 | **0 拍** |

⇒ `tools/h723_tick_erase.py`。**对照组真的量到缺口**, 所以交付版的"零缺口"才是证据,
而不是"我记得改前是什么"。

## 4. T15 为什么是"半可修"

S3 的 T15 = 落盘半段 + **重启半段**。重启半段靠 `dcl.ser.setRTS(True)` 拉 EN 复位 ESP32。

实测 (2026-09-11): 在 H723 上做同样的 RTS 翻转, `samples` 从 **20031 继续涨到 31602**
⇒ **板子根本没复位** (CH340 的 RTS 没有接到 NRST)。套件自己也提示 `否(请手动按RST重试)`。

修复后 T15 的详情变成: `持久化=ok, 重启=否(请手动按RST重试), routes=1` ——
**落盘半段已修好** (以前 `持久化=fail`)。要全绿只需**一根线** (CH340 RTS → 板上 RST)
或**手按一次 RST**。为过测去伪造"重启证据" = 造假, 不做。

## 6. 顺手修掉的两个"假故障"类问题

### 6.1 验收脚本自己把自己崩掉 (编码)

`audit_m234` / `w1` 在 GBK 控制台上因 print 里一个 `⇒` 触发 `UnicodeEncodeError`,
**整份结果都没打出来** —— 数据已经量到了, 却崩在"打印结论"这一步, 症状看起来像"脚本坏了"。
⇒ 19 个 `tools/h723_*.py` 统注入入口守护 (`stdout.reconfigure(errors="replace")`)。
修完立刻暴露真相: `audit_m234` **12/12**、`w1` **28/28** 本来就是绿的。

### 6.2 套件的隐含前提 (跑测顺序依赖)

`w2_probe` 假定"上电态 = bench": 无持久化配置 (RUN=1, 表 = 128 条)。但固件在**有**持久化
配置时上电**保持 STOP** (安全语义)。⇒ 它只要排在 T15/T26/persist 后面就**全线失败**
(实测 13 PASS → 6 PASS), 而失败原因与被测的 Force 语义毫无关系。
修: 脚本**自己建立前提** (写 `RUN=1` + 让主循环按 bench profile 重填表, 都走真固件机制),
并新增 `PRE` 判据验证前提真的成立; 前提不成立时打印可执行的补救命令。

### 6.3 build.sh 的 TEMP 依赖

GCC 的中间文件走 `TMP/TEMP`; 环境里若指向 `C:\WINDOWS`, 构建会以
`cc1.exe: fatal error: can't open 'C:\WINDOWS\ccXXXX.s'` 失败 —— **与代码完全无关**,
极易误判成"我刚改坏了"。⇒ `build.sh` 把 `TMP/TEMP` 显式钉到 `build/tmp/`。

---

### 6.4 ★ 顺带查出一个更隐蔽的缺陷: 计时统计被"跨纪元样本"污染

这是被 **T26-3a 那条新加的"采样器还活着吗"判据**抓出来的 —— 如果只写 `pmax < 300000`,
它会**空过** (见 §7 的方法论)。

**现象** (烧录后直接发一条 `0x38`, 不改任何东西):
```
samples=11070  pmin=39992    pmax=4251616895 ← 垃圾
                emin=0        emax=224
```
**"pmin 正常而 pmax 是垃圾"** 就是它的指纹。

**机制** (两条事实叠加):
1. 这些计时量住在 **DTCM**, 而 **DTCM 跨复位不丢** ⇒ 它们是上一轮启动的残留;
2. `dwt_enable()` 会把 **`DWT_CYCCNT` 清零** (标定要求)。

⇒ 新"纪元"的第一个周期样本 = `t0(≈0) − g_per_prev(上一纪元的值)` = **负增量**
(无符号看是十亿级巨值), 被 `max` 记住后**永久污染**。`emin=0` 同源:
`di = t1 − t0 == 0` 意味着"整段 ISR 期间 CYCCNT 一个数都没走", 对真实 ISR 不可能。

**修复** (两处, 都在 `TIM2_IRQHandler` 的统计段):
- 周期样本: 增量为**负** ⇒ 判为**时钟不连续**, 单独计数 (`g_per_glitch_n`), **不并入 min/max**。
  理由: 合法的"拍变长"一定是正数 (超载也只在几十万 cyc 量级)。
- ISR 时长: `di == 0` 同族处理 (原实现让 `emin` 恒为 0 —— 那个量在撒谎)。
- **boot 处补 `stats_reset()` + `g_per_prev = 0`** (冷启动 = 两个钟一起归零, 同起点)。

**验证** (同一操作序列, 修前 → 修后):
| | samples | pmin | pmax | emin | emax |
|---|---|---|---|---|---|
| 修前 | 11070 | 39992 | **4251616895** | **0** | 224 |
| 修后 | 11305 | 39992 | **40012** | **126** | 217 |

★ 口径说明: `g_per_glitch_n` **保留**这个异常的证据 —— 不是把它藏起来, 而是不让它
冒充测量结果。这与本项目"噪声要清零、异常要留痕"的一贯做法一致。

## 8. 方法论沉淀 (本轮新增)

- ★★ **"判据不能失败" = 判据不存在**: 自动落盘第一版把 `RUN==0` 写进"登记"条件,
  于是"因 RUN 放弃"的计数器**恒为 0**。⇒ **登记 / 裁决要分开**; 凡"某观测量永远是 0/1",
  先怀疑它是空判据。**本次这个教训当场又救了一次** —— 见下条。
- ★★ **"零冻结"这类判据必须先证"采样器是活的"**: T26-3 原本只写 `pmax < 300000`。
  实测在某个启动态下 `pmax` 恒为 0 ⇒ **判据空过**。加了 T26-3a (`pmin>0 && pmax>0`) 之后,
  同一个启动态立刻 FAIL ——**顺着这条线才挖出 §6.4 那个跨纪元污染的缺陷**。
  ⇒ **"没测到异常" 与 "测不出来" 必须能分开。**
- ★★ **结构性修复必须配"能失败的对照构建"**: `-DDCL_VTOR_ITCM=0` 那一半存在的唯一意义
  就是证明另一半的"零拍丢失"不是巧合。**对照组量不到缺口 ⇒ 判据无效, 不是"修复成功"。**
- ★ **环境类故障的症状总像"我改坏了代码"**: TEMP 指向 `C:\WINDOWS` / GBK 控制台打不出 `⇒` /
  `attach` 模式初始化不了 AP —— 这三件事的报错都与被测对象无关。
  **先问"这个症状能不能由我的改动产生", 再动被测对象。**
- ★ **读数前先问"这个观测方法本身会不会改变/抹掉证据"**: 读 DTCM 全局量必须用**不复位**的
  连接 (`-c reset` 会让固件启动时把它们清零 = 自己把证据擦掉); `attach` 在本探针上不可用,
  要用 `connect_mode=halt`。
- ★ **同一文件的多个编辑必须串行**: 本轮又踩一次 —— 并行两个 Edit 到 `src/main.c`,
  两次都报"成功", 但声明那一处**丢写**了 (编译立刻报 undeclared)。
