# EXP-2026-09-18-OVERLOAD —— 超载实验：预算门**能不能拦住超载**？

> **这是一次"补判据"的实验**，不是功能开发。
> 起因：`docs/ARCH-GUARANTEE-MAP.md` 的 **G3（拍内按时完成）** 只有一个缺口 ——
> `src/engine.h:832-855` 的绊线断言写着：
>
> ```
> 128 条上限 × 最贵原语 145 cyc = 18560 cyc = 拍长的 46.4%
> ⇒ 在 MAX_ROUTES=128 的前提下，任何合法程序都不可能把拍吃满，预算门当前永远不会触发。
> ⇒ 一旦断言失败（门变成真门），届时必须做一次超载实验
>    （构造 >门 的程序，确认 NAK + 确认拍没被拉长），而不是相信一个从没被触发过的判据。
> ```
>
> 本实验就是那次超载实验。**判据必须能失败** —— 所以每个结论都配了对照样本。
> 板：COM22（CH340）· 交付固件 `fw=0x0200` / `cap=0x7DF7` / `h723_proto 12 PASS 0 FAIL`。

## 0. 先读代码（不拿猜的模型设计实验）

| 事实 | 出处 |
|---|---|
| 静态门 `EXEC_DEPLOY_BUDGET = 26000`（下载期，预判，不等式） | `engine.h:813` |
| 动态门按**时间**表达 80 µs：`EXEC_BUDGET_TB`（0 档 32000 DWT cyc / **1 档(TIM5) 16000 tick**） | `main.c:1446` + `engine.h:825` |
| 每拍成本 = `Σ_ACTIVE ceil((op_cost + src_cost) / mult)`；mult: div0=**1** / div1=10 / div2=64 | `engine.c:807-822` |
| **`k_src_cost[4] = {0,0,0,0}`** —— 四种源类型成本**全为 0** | `engine.c:799` |
| 成本表最大值 = **PID = 145**（`OP_MAX=0x12`） | `engine.c:771-773` |
| 越界 op 的成本兜底 = `145 × 2 = 290` | `engine.c:804` |
| `0x10` ACK 载荷 = **`[seq:u16][budget:u32]`** ⇒ **能把算出的预算读回来** | `main.c:1899-1902` |
| `prog_validate` 门序：`short → counts → payload short → ①参数有限 → ②逐条 validate+dst冲突 → ②b rate mismatch → ③预算门` | `main.c:1786-1848` |

### ★ 解析结论（实验设计的依据）

1. **静态门不可达**：`128 × 145 / 1 = 18560 < 26000`（src_cost 全 0、div0 的 mult=1、PID 是表内最大值）。
   余量 **26000 / 18560 = 1.40×**。
2. **唯一的"超额来源"也被门序挡住**：让某条路由成本变 290 的**唯一**途径是 `op > 0x12`，
   而 `engine_route_validate`（**第 ② 步**）的白名单会先返回 `"bad op"`，**永远走不到第 ③ 步**。
   ⇒ `128 × 290 = 37120 > 26000` 这个理论超额**结构上无法表达**。
3. ⇒ **"构造一个 >门 的程序"在交付配置下做不到**（不是"没试过"，是**做不到**）。
   ⇒ 实验改成：**用可读回的 `budget` 实测最重合法载荷，把"不可达"从断言变成实测事实**。

## 1. OVL-2 —— 静态门（源码无关：不改固件、不烧录）

脚本 `.tmpctl/ovl_static.py` · `.tmpctl/ovl_heavy.py` · `.tmpctl/ovl_o2b.py`

| 载荷 | 手算期望 | **实测 ACK 的 `budget`** | 判定 |
|---|---|---|---|
| 128 × DIRECT(56) div0 | 128×56 = **7168** | **7168** | ✅ 精确命中 |
| 128 × PID(145) div1 | 128×ceil(145/10)=128×15 = **1920** | **1920** | ✅ 精确命中（÷10 摊薄生效）|
| **128 × PID(145) div0**（★最重合法） | 128×145 = **18560** | **18560** | ✅ 精确命中；**ACK（未被拒）** |
| 128 × op=0xFF（若按 290 计 = 37120） | — | **NAK `bad op`** | ✅ **不是** `exec budget exceeded` ⇒ **门序确实挡住了** |

**辅助判据**：被 NAK 的那次 `n_routes` 前后不变（**拒绝无副作用**）。
**注**：op=0xFF 那条在两次运行间出现过一次 TIMEOUT。隔离实验（正对照：1 条 op=PID ⇒ ACK；
1 条 op=0xFF ⇒ TIMEOUT；128 条 op=0xFF ⇒ NAK "bad op"）表明是**传输层偶发丢应答**
（端口打开会 DTR/RTS 复位板子 ⇒ 首次事务易撞上启动窗），**与 op 是否非法无关**。

### 1.1 顺带量到的：最重合法程序的真实成本

`emax` 与 `EXEC_BUDGET_TB` 同域（TIM5 @200 MHz ⇒ **1 tick = 5 ns**）；动态门 = **16000 tick = 80 µs**；拍长 = 20000 tick = 100 µs。

| 程序 | `budget` | `n_routes` | `emax` | µs | **占动态门** | **占拍长** | `ov` | `pmin/pmax` |
|---|---|---|---|---|---|---|---|---|
| 基线（`0x13 RESET` 后空引擎） | — | 0 | **632** | 3.2 | 4.0% | 3.2% | 0 | 19988/20012 |
| 128 × DIRECT div0（ITCM 档） | 7168 | 128 | **6240** | 31.2 | 39.0% | 31.2% | 0 | 19988/20012 |
| **128 × PID div0（最重合法，ITCM 档）** | 18560 | 128 | **10682** | **53.4** | **66.8%** | **53.4%** | **0** | 19988/20012 |
| 收尾（回 bench） | — | 0 | 632 | 3.2 | 4.0% | 3.2% | 0 | 19994/20006 |

1. **拍没被拉长** ✅ —— `pmax` 在"空引擎 / DIRECT×128 / PID×128"三种负载下**完全相同（20012 tick）**
   ⇒ 拍仍由硬件定时器决定。这正是 `engine.h` 要求的"**确认拍没被拉长**"。
2. **动态门对合法程序也不可达** —— 最重合法只吃到门的 **66.8%**（余量 1.50×），`ov=0` 与 `emax≤门` **自洽**。
3. ★★ **由此暴露一条更本质的事实**：`ov == 0` 对任何合法程序**都不可能失败** ⇒ **它仍是空判据**
   —— 只是原因从"字段被写死 0"（09-11 修掉的那个）变成"**门比最坏合法负载还高 50%**"。
   ⇒ **两个门是冗余的**：静态门保证动态门永不触发。动态门的真正用途只能是
   **"模型外负载"的兜底** —— 这正是 OVL-1 要验的。
4. **成本模型误差的上界**：实测扫描 ≈ 10050 tick（= 20100 DWT cyc）vs 模型预测 18560 ⇒ **实测/预测 ≈ 1.083**。
   ★ 边界：`emax` 是"**相位撞在一起的那一拍**"（含热重载、顺序域/通信域/传感域在该相位的份额），
   所以 **+8% 是扫描成本误差的上界，不是点估计**。

## 2. OVL-1 —— 动态门（需要"模型外负载"）

**目的**：`ov` 在 **TIM5 时基**下是否仍能触发。
**为什么必须验**：09-11 量到 `ov = 18343` 是在 **DWT 时基**下；之后交付档换成 TIM5，`di` 的单位从
DWT cyc 变成 TB tick，阈值改走 `EXEC_BUDGET_TB`。**若换算错了，`ov` 会永远为 0 而无人察觉**
—— 而 `ov == 0` 是 `h723_jitter`/T9 的判据之一。

### 2.1 第一次尝试失败（并且这本身是发现）

用 09-11 的同款配置 `-DDCL_BOOT_SEL=0 -DDCL_BOOT_PROFILE=2`
（构建 RC=0，`programmed 68608 bytes`）⇒ 复位后 **板子完全不答协议**，
等 12 s 仍 `h723_proto` 全 SKIP。

**隔离**：换成 `-DDCL_BOOT_SEL=0 -DDCL_LOOP_RESET=0`（**BOOT_PROFILE 保持 0**）⇒ 空引擎下
**12 PASS / 0 FAIL**。
⇒ **不应答是 `BOOT_PROFILE=2` 造成的，不是 `BOOT_SEL=0`**。机理：profile 2 的负载让 ISR 长期
超过拍长 ⇒ 主循环被饿死 ⇒ 撞 `DCL_LOOP_RESET`（1.2 s 停滞）⇒ **复位循环**，而复位会清零
`ov`/`samples` ⇒ **这个配置根本测不到 `ov`**。
★ **教训**：要测"超载下的计数"，必须**先关掉会因超载而复位板子的自愈机制**，
否则观测手段会毁掉被观测对象（与铁律 0 同源）。

### 2.2 受控超载（FLASH 扫描路径 = 成本模型外的负载）

配置：`-DDCL_BOOT_SEL=0`（扫描走 **FLASH**，每条约 3.6× 慢；成本表 `k_op_cost_itcm` **只为 ITCM 标价**）
`-DDCL_LOOP_RESET=0`。负载由协议侧逐档部署 N 条 PID div0 控制。

脚本 `.tmpctl/ovl1b_sweep.py`：

| N（PID 路数） | `emax` | µs | **占动态门** | 占拍长 | `ov` | `pmax` |
|---|---|---|---|---|---|---|
| 40 | 10108 | 50.5 | 63.2% | 50.5% | 0 | 20010 |
| 48 | 11864 | 59.3 | 74.2% | 59.3% | 0 | 20018 |
| 56 | 13564 | 67.8 | 84.8% | 67.8% | 0 | 20010 |
| 64 | 15320 | 76.6 | **95.8%** | 76.6% | **0** | 20012 |
| **72** | **17118** | **85.6** | **107.0%** | 85.6% | **1** ★ | 20010 |

- **M0 时基活着**：`0x39 op=21` ⇒ 档=**1(TIM5)**、`TB_HZ=200000000`、自检 Δ=**6040 ≠ 0** ✅
- **M1 `emax` 随路数单调上升** ✅（负载真的在加）
- **M3 反向保护** ✅ —— 未超过门的 4 档 `ov` **全为 0**（阈值换算没反）
- **M2 ★ 动态门触发** ✅ —— `ov` 从 0 跳到 1，跳变点**正好卡在门=16000 tick** 上

### 2.3 `ov=1` 是瞬态还是持续？（决定性的一刀）

脚本 `.tmpctl/ovl1c_growth.py`：

| N | 观察 | 判定 |
|---|---|---|
| **72** | `emax=17020` 恒定；`ov` **保持 1 不变**（`samples` 从 19,152 涨到 109,955，跨 10.6 s）| ⇒ **唯一那次超载是瞬态** |
| **80** | `emax=18748`；`ov` **线性增长** 16,987 → 65,364（与 `samples` 同步，比值 80→94%）| ⇒ **持续超载**；约 8 s 后协议不再应答（主循环饿死；因 `LOOP_RESET=0` 未复位）|

⇒ ★ **`ov` 是"每拍超了就 +1"的真计数**（不是布尔、不是每段一次），实测与 `samples` 同步线性增长。
⇒ ★★ **瞬态那次是"热重载那一拍"**：`reload` 让该拍多花 ~720 tick，足以把 N=72 的
持续态（≈16,400 tick）顶过 16,000 的门。
**这是"热重载要吃掉预算余量"的直接实测证据** —— 也正是 `engine.h:810` 给热重载那一拍留
14000 cyc (35 µs) 的理由。
⇒ **拍周期始终没被拉长**：N=72（ISR 85.6 µs）时 `pmax` 仍 = 20010 tick，与空引擎相同。

## 3. 结论

| # | 结论 | 证据 |
|---|---|---|
| **C1** | **静态门 `EXEC_DEPLOY_BUDGET` 结构上不可达** | 解析（max=128×145=18560<26000）+ 实测（最重合法载荷 ACK 且 `budget` 精确读回 **18560**）+ 实测（唯一超额路径被门序挡住：NAK **`bad op`** 而非 `exec budget exceeded`）|
| **C2** | **动态门在 TIM5 时基下有效，阈值精确** | `ov` 在 `emax` 跨过 16000 tick 的那一档从 **0→1**；未过门的 4 档全为 0 |
| **C3** | **`ov` 是真计数**（每拍 +1），不是布尔 | N=80 时与 `samples` 同步线性增长（16,987→65,364）|
| **C4** | **拍周期未被 ISR 拉长**（门要求的第 2 条只证） | 空引擎 / DIRECT×128 / PID×128 / FLASH×72 四种负载 `pmax` 均 ≈20010 tick |
| **C5** | ★ **`ov == 0` 对合法程序仍是空判据** | 最重合法只到门的 66.8% ⇒ 该判据**不可能失败** ⇒ 动态门只是**模型外负载的兜底** |
| **C6** | **热重载那一拍本身就是一次超载来源** | N=72 持续态在门下，`ov` 却为 1；N=80 持续超载时 `ov` 线性增长 |

**对 G3 的处置**：G3 那个缺口**已闭合**。原来的表述是"**设计成立、未压力验证**"，
现在两个门都从"假定"变成"**实测过**"：
- 静态门：**不可达**（且已证明唯一超额路径被门序阻断）
- 动态门：**可达且有效**（需模型外负载：FLASH 扫描路径 / 热重载拍 / 事后新增的 ISR 服务）
