# 实验做法的梳理 & 标准化评估 —— **我们做实验时，遵循了系统架构吗？**

- 日期：2026-09-15
- 对照基准：`docs/CORE-ENGINE.md`（4 条设计公理 + 8 条不变量 + 数据链契约）、
  `docs/ARCH-H723.md`、`docs/FRAMEWORK-MAP.md`
- 被评估对象：`docs/exp-2026-09-14-mdma-trigger/`、`docs/audit/`（14 份文档 + 9 个脚本）、
  以及 2026-09-14-15 的"闭环伺服"这一整条线

---

## 0. 结论速查

| 维度 | 评级 | 一句话 |
|---|---|---|
| **实验归档规范** | ✅ **好，且已自发形成事实标准** | `exp-<日期>-<主题>/` 有 README + 固件 patch + raw 原始数据 + 分析脚本；审计 doc 有 AUDIT/RESPONSE 配对；每条数字给复跑命令 |
| **判据纪律** | ✅ **好，且明显强于一般工程实践** | 形状判据 > 幅度判据、同一性对照、能失败的判据、量纲、**多次自我撤回**（D5 / 累积丢步 / §10 编码器假象） |
| **实验与固件的边界** | ✅ **好** | 运行期动作**复位即恢复**、未污染持久化；有 `DCL_DO_LATCH` 这类**能失败的对照构建**意识 |
| **对 CORE-ENGINE 架构的遵循** | ⚠️ **明显偏离** | **但偏离是"绕过"，不是"破坏"** —— ISR 拍时序 / 引擎扫描一次都没动过 |
| **诊断面的标准化** | ❌ **差** | `0x39 op=1..19` + 多个 sub 是"长在协议上的第二套架构"，**未进 SHM、无 `obs_anchor`、无布局静态断言** |

> **一句话总结**：**实验方法学（怎么测）是 A 级的；架构一致性（测的东西放在哪）是 C 级的。**
> 而且这两个评级**有因果** —— 绝大多数已发现的缺陷（D2/D3/D6/D10、C1/C2/C4）**都是"绕开架构"的直接后果**。

## 1. 之前的几个实验，是怎么做的

按"证据从哪来"分成四条线。

### 1.1 线 A：MDMA 锁存触发源归因（`docs/exp-2026-09-14-mdma-trigger/`）

**这是最规范的一次实验，可以直接当模板。**

| 产物 | 内容 |
|---|---|
| `README.md` | 11 节：问题 → 假设 → 配方 → 8 档扫描 → 判定 → 结论 → 未解释的残留 |
| `firmware-experiment.patch` | **457 行实验期固件改动，独立成 patch，不合并** —— 实验代码与交付代码物理隔离 |
| `raw/` | 8 档逻辑分析仪原始数据 |
| `analyze_sweep.py` + `analysis.txt` | 分析脚本 + 一次性结果留档 |

**做法上的三个亮点**：
- **A/B 用"可读回的量"定案**：四个否决性实验（拆 DMAMUX / 拆 DIER / 停 DMA2_S0.EN / 扫 TSEL 0..15）逐个排除，
  最后定位到 `TSEL=8` 的请求线自己常高。
- **判据用形状不用幅度**：用"整段平移"这类不受量化影响的判据。
- **量化伪影先判掉**：直方图上间距恰等于采样网格的簇 = 量化，不是抖动。

### 1.2 线 B：引脚抖动 / 确定性（2026-09-14，多个提交）

- 先用 LA 测（16 MS/s / 24 MS/s 两档复采，**证明两个采样率给出同一个 σ** ⇒ 结论不依赖采样率）。
- LA 测不动 20~60 ns 量级 ⇒ **改在固件里累積**（`Σ(d−40000)` 与 `Σ(d−40000)²`，u64，`op=16` 读回）。
- **两轮完全一致** ⇒ 可复现才下结论。
- ★ 这一步的方法学价值：**主动识别"测量手段的分辨率不够"，换手段而不是硬报数。**
  （同一个意识在 `H723-MOTION-QUALITY-AUDIT.md` §7.4 再次出现：明确声明"可测速度上限 ~43800 Hz，
  ≥40000 Hz 不上报"。）

### 1.3 线 C：闭环伺服 / 接线定案（2026-09-15）

**做法链条**：接线表 → 万用表静态电平 → 固件内自检 → SWD 直读 → 定案 → 改接线 → 复测。

关键手段：
- **静态电平探针**（`op=19 sub=7/8/9/10`）：把定时器引脚摘下来输出确定电平 —— 因为万用表 DC 档量方波读的是平均值。
- **`GPIOx_IDR`**：区分"我在驱动"与"引脚高阻被外部上拉"（唯一硬判据）。
- **固件内自检**（`op=17` 引脚通路自检）：不依赖任何外部仪器。
- **SWD 直读**（`h723_i2c_diag.py`）：当协议面说谎时，绕过协议直接读硬件。
- ★ **两次"用户直感 vs 我的读数"冲突，最后都是读数错**（编码器读路径挂掉、轴不动的假象）
  ⇒ 这条被写进报告：**数据与现场直感冲突时，先怀疑判据/工具。**

### 1.4 线 D：运动品质审计（2026-09-15，`H723-MOTION-QUALITY-AUDIT.md`，1263 行）

**做法**：上位机在环 + 编码器做尺子。2 min 长跑 / 往返 10 轮 / 位置锁定 / 速度扫描 / 扭矩代理法。

**亮点**：
- **三个互相独立、各有失效边界的估计量**（最短弧 / 强制单向解卷绕 / **占用角域**），
  用其中"无失效边界"的那个做**裁决量** ⇒ 推翻了同一份报告前面几个伪造的速度值。
- **可证伪的预测被证实**：模型说"瓶颈在命令通路 55 ms"，于是改上位机（命令延时补偿 + 行程自适应降速），
  `hold` 从"61 次修正不收敛"变成"+0.176° / 25 s 零修正"。**先预测、后验证**，这是最硬的一种证据。
- **主动撤回**：D5（使能回读竞争）、"累积丢步 −1.23°"两条都是自己的测试方法造成的假象，都撤了。

## 3. ★ 与系统架构的逐条对照（`CORE-ENGINE.md`）

### 3.1 四条设计公理

| 公理 | 步进这条线实际怎么做的 | 判定 |
|---|---|---|
| **① 一切数据都在 SHM 里；通信 = 写我自己的槽** | 步进的**频率/限时**完全不在 SHM：它们住在 `step.c` 的静态变量 + `TIM3_ARR/CCR1` 硬件寄存器里。上位机只能靠 `0x39 op=19` 的**手工打包应答**读回 | ⚠️ **偏离**（方向/使能走了 SHM，脉冲率没走） |
| **② 单写者原则** | `OFF_CTRL_GPIO_MASK` 按 `CORE-ENGINE.md` 的权威写者是"协议"；而 `step_init()` **又写了一次**（`step.c:46`）。`OFF_DO_SHADOW` 在 A 档下**没有写者**，但 MDMA 还在读它（C2） | ❌ **违反两处** |
| **③ 计算即查表（16B 路由 → 19 原语）** | **位置环在 PC 上**，不在固件。引擎的 128 条路由 / PID / TIMER / RATE 原语**一个都没参与** | ❌ **完全绕开**（实测代价见下） |
| **④ 时间预算是一等公民（静态门 + 动态门）** | `step_tick()` 是**主循环**里的一个调用，**没有标价、没有静态门、没有动态门**。实测主循环一圈 **0.37 ms**（2026-09-16 **直接实测**；原 1.28~1.54 ms 是**反推值**，已作废）（我本轮实测），而拍是 100 µs | ❌ **违反** |

**公理③的代价被量化了**（审计 §9.1/§9.2/§15.5）：

| | 上位机在环（现状） | 固件内环（架构本来的样子） |
|---|---|---|
| 环频 | **13.5 Hz**（实测 26.3 命令/s ÷ 2） | 100 µs 拍 ⇒ ~10 kHz |
| 等效滞后 | **80~100 ms**（实测） | ~0.1~1 ms |
| 1 Hz 轨迹跟随误差 | **±25°**（其中 22° 是纯滞后） | <1° |
| 可承载算法 | L2（只够慢轴） | L3/L4 |

> ★ 也就是说：**DCL 架构最值钱的那一项性质（100 µs 确定性）在这条线上被丢掉了 ~700 倍。**
> 而这不是"引入了 bug"，是"**没走架构**"。

### 3.2 八条不变量

| 不变量 | 实际情况 | 判定 |
|---|---|---|
| ① 单写者 | `GPIO_MASK` 两个写者；`g_step_arr/ccr1`（缓存）与 `TIM3_ARR/CCR1`（硬件）**两个存放点**（C1 的观测盲区）；`TIM3_CH1` 出现"两个驱动者 + 让路门"（`hil_out_apply` 有门 / `hil_outputs_safe` 无门 = C1） | ❌ |
| ② ISR 段顺序 = 数据依赖 | 未破坏。但步进**横跨两个执行上下文**：方向/使能走 ISR 里的 `do_poll`，频率/限时走**主循环** | ⚠️ |
| ③ 每拍必须发生的动作不挂分支 | 未破坏。但**限时递减不是"每拍发生"**，它挂在主循环上 —— 于是它的速率随主机负载变（D2/D3） | ⚠️ |
| ④ 新 SHM 字段 ⇒ 布局静态断言 | 步进**没有新 SHM 字段**，所以没触发；但它也**因此失去了布局保护** | ➖ |
| ⑤ 新观测变量 ⇒ `obs_anchor()` 登记 | `0x39 op=19` 的 96 字节应答**未登记**、**不进 SHM**、**无静态断言** | ❌ |
| ⑥ 静态门常量与成本表同源 | 不适用（没有进入引擎的成本模型） | ➖ |
| ⑦ 跨拍状态用 u32 | ✅ 遵守（`g_step_deadline_tick` 是 u32） | ✅ |
| ⑧ 判据必须能失败 | ✅ 遵守得很好（但这更多是**人的纪律**，不是架构强制） | ✅ |

### 3.3 输出链契约（`CORE-ENGINE.md` §3.4）

> **"一个输出面一个驱动者"；输出面必须注册进 `eng_register_output_surface`；STOP 时各面归零。**

实际：
- ✅ 方向/使能走 `ACTUATOR[8..9]` → `do_poll` → BSRR ⇒ **完全合规**，而且 `PE8..PE11` 通过 `GPIO_MASK` 纳入管辖（这个设计是对的）。
- ❌ **脉冲（TIM3_CH1）没有注册成独立输出面**，而是从 HIL 的输出面上"抢"过来的。
  为了让它工作，被迫在 `hil_out_apply` 里加 `g_step_owns_tim3` 让路门 —— 这就是
  **C1（`hil_outputs_safe` 漏了同一个门）的根因**。
  ★ **C1 不是"忘了加一行"，而是"绕开架构之后必然出现的双写者问题"。**

### 3.4 诊断面的位置

架构里诊断/观测的正规位置：**SHM + `obs_anchor()` 登记 + `0x20/0x22` 读写命令**。

实际：`0x39 op=1..19`，其中

| op | 用途 |
|---|---|
| 1–4 | 引脚码型 / 统计 / 让路 / 黑匣子 |
| 5–13 | 触发源 / 自证 / 校时 / 注入 / 桥透视 / 原始写 / 双写 / TC 速率 |
| 14–16 | 锁存宽度 / 重配 / σ 累积 |
| 17–18 | AS5600 扫描 / 运行态 |
| 19 | 步进控制 **+ 静态探针 + 开漏 + IDR/实时寄存器透视**（sub 0–10） |

**⇒ 事实上的第二套架构：每遇到一个问题就加一个 op / 一个 sub。**
它带来的具体代价：

- **`uint8_t r[40]` 写 68 字节的栈越界**（已修）—— 若走 SHM + 布局静态断言，
  这类错误**在编译期就炸**，而不是靠人肉数偏移。
- **"缓存 vs 实时寄存器"盲区**（C1 差点漏掉）—— 因为应答是手工拼的，
  "报缓存还是报硬件"没有契约约束。
- **`probe od` 的假报警**、**`safe` 判据写死 PE8~PE11** —— 都是"判据长在工具里、
  而工具不在架构的约束范围内"的产物。

## 4. 因果链：**"绕开架构" → 具体缺陷**

这一节是本文最重要的一节 —— 它说明架构不是纸上规矩，**绕开它的代价是具体的 bug**。

| 绕开的地方 | 直接导致的缺陷 |
|---|---|
| 脉冲不是"输出面"，从 HIL 抢 TIM3 | **C1**（`hil_outputs_safe` 无门 ⇒ 清 CCR1 ⇒ 脉冲变恒定低） |
| 频率/限时不在 SHM，靠自定义协议字段 | **D10**（频率静默下界 15.26 Hz，请求 4/10 Hz 都跑成 15.24）<br>**D6**（复位后 `enapol` 默认 0 与接线语义相反 ⇒ 发"使能"得到"失能"） |
| 限时递减挂在**主循环**（不是拍） | **D2**（时基慢 26% 且随负载变 —— 真因 = 每次 `dt/10` 取整）<br>**D3**（小限时被提前吃光 ⇒ 变无限跑）<br>**D4**（上位机在环 ⇒ 定位精度钉死 ±0.57°） |
| 位置环在 PC 上，不在引擎里 | **§9.1/§9.2/§15.5**：环频 13.5 Hz / 滞后 80 ms / L3 做不到 |
| 应答手工拼、未进 SHM | 栈越界、"缓存 vs 实时"盲区、两处假报警 |
| `GPIO_MASK` 两个写者、`OFF_DO_SHADOW` 无写者 | **C2**（A 档下 MDMA 仍在把恒 0 的影子搬进 `ODR` ⇒ `PE0..PE7` 恒低） |

> ★ **六个已编号缺陷（C1/C2、D2/D3/D4/D6/D10）全部落在"架构边界要么被绕开、要么被动过"的地方。**
> 而**没有一处**落在"遵守了架构的那部分"（方向/使能走 ACTUATOR → BSRR，一直没问题）。

## 5. 建议（按优先级）

### P0 —— 把步进变成**引擎的一个输出面**，而不是"从 HIL 抢 TIM3"

1. 新增 `step_outputs_safe()` 并 **`eng_register_output_surface()`** 注册；
   `hil_*` 里那两处 `g_step_owns_tim3` 门**一起删掉** —— 让"谁拥有 TIM3"只在一处表达。
   ⇒ **一次修掉 C1**（并消灭"同一个语义守一处漏一处"这个族）。
2. 频率/限时/方向/使能**全部搬进 SHM 的 CTRL/ACTUATOR 槽**，`0x39 op=19` 降级为
   **"读 SHM + 写 SHM"的薄壳**，不再直接碰 `TIM3_*` / `GPIOA_*`。
   ⇒ 顺带解决 D6（上电默认值进入 SHM 初值表，可持久化）与 D10（下界在写槽时校验并上报）。

### P0 —— 闭环下沉到固件（这是 DCL 架构存在的理由）

3. 用**已有的** `PID` / `RATE` / `TIMER` 原语 + 新的步进输出面，在 100 µs 拍里做位置/速度环；
   AS5600 的 `SENSOR[0]/[1]` 已经在 SHM 里（我上一轮加的），**数据链是通的，只差一条路由**。
4. 上位机退回"规划 + 整定 + 日志"。

### P1 —— 时间量必须活在拍上

5. 限时/定长改成**目标拍号 + `armed` 位**（不做除法、不依赖主循环）；
   ⇒ **一次收掉 D2 + C4 + D3**，并为 D4（"走 N 步"）打好时间基。
6. 加减速（梯形/S 曲线）进固件 ⇒ 恢复被砍掉的 47% 转速（627 → 1170 rpm）。

### P1 —— 诊断面收敛回架构

7. 诊断量**进 SHM + `obs_anchor()` 登记**；`0x39 op=19` 保留为兼容壳，但**文档里明确标注
   "它是临时脚手架，不是架构的一部分"**，并给它加**布局静态断言**。
8. 凡是"数据"应答，长度与字段偏移必须在 `.h` 里定义 + `_Static_assert`，
   **不允许在 handler 里手工 `put32(r+off)`**。

### P2 —— 把方法学写成文

9. `RUNBOOK-experiment.md`：目录模板（README/patch/raw/脚本/analysis）、
   "每个数字必须带复跑命令"、"必须先声明测量上限"、"AUDIT/RESPONSE 配对"。
10. 把 `CORE-ENGINE.md` §6 的 8 条不变量做成**评审清单**，
    其中 4 条（布局断言 / `obs_anchor` / 成本同源 / 单写者）**可以做成 CI 检查**。

## 6. 一页检查清单（下次开实验前过一遍）

| # | 问题 | 若答"否" |
|---|---|---|
| 1 | 这个量**住在 SHM 的哪个槽**？谁是**唯一写者**？ | 你在造一个旁路 |
| 2 | 它是**每拍该发生**的，还是"服务命令时才发生"的？ | 别挂在主循环上 |
| 3 | 它**进引擎的成本模型**了吗？静态门怎么办？ | 你在绕过预算 |
| 4 | 它是不是**一个输出面**？注册了吗？安全态里它会归零吗？ | 迟早出 C1 那类缺陷 |
| 5 | 观测它时，报的是**硬件寄存器**还是**软件缓存**？ | 会有看不见的盲区 |
| 6 | 应答的数据结构有**布局静态断言**吗？ | 迟早栈越界 |
| 7 | 这次的**测量上限**是多少？判据**能不能失败**？ | 结论不可用 |
| 8 | 实验代码**独立成 patch** 了吗？运行期改动**复位能恢复**吗？ | 污染交付物 |
