# FIX-REPORT — USART1 BRR 公式错误 (波特率差 16 倍)

日期: 2026-09-11
级别: **P1** — 协议物理层整体不可用, 且极隐蔽
状态: 已修 + 实机双向验证通过

---

## 1. 症状 (现象层)

- 板子跑 `min_uart` / 主固件, PC 侧串口 (CH340 COM14 / DAPLink CDC COM11)
  **一个字符都收不到**, 或只收到打开端口瞬间的一次性 `0x00` 突发。
- 所有"配置类"检查**全绿**:
  - `USART1_CR1 = 0x0D` (UE|RE|TE 全开)
  - `USART1_ISR = 0x006000D0` (**TXE=1, TC=1**)
  - `GPIOA_MODER` PA9/PA10 = AF, `GPIOA_AFRH` AFSEL=7
  - `RCC_APB2ENR` USART1EN=1, `DWT_CYCCNT` 递增 (核在跑)
- 结论: 固件"看起来完全正常", 线索指向"接线问题" —— **这是陷阱**。

## 2. 根因

`BRR` 公式写错 16 倍。

```c
/* 错 (原代码, uart.c 与 min_uart.c 两处都有) */
s_brr = (pclk2_hz * 16u + baud / 2u) / baud;

/* 对 */
s_brr = (pclk2_hz + baud / 2u) / baud;
```

USART 默认 **OVER8=0 (16 倍过采样)**。此模式下 `BRR` 就是**分频值本身**:

```
BRR = fCK / baud
```

乘 16 的写法属于 "OVER8=1 时 BRR 低 1 位放小数" 的另一套算法, 套错了地方。

实测数据 (SWD 读回):

| | 值 | 实际波特率 |
|---|---|---|
| 修复前 | `0x22B9` = 8889 | 64e6/8889 = **7199** (~7200) |
| 修复后 | `0x022C` = 556 | 64e6/556 = **115108** |

8889 / 555 = **16.02** —— 整整差 16 倍。

### 为什么极隐蔽

1. 波特率错了 16 倍, 但**所有寄存器状态都是"正确"的**: UE/TE 开着、TXE=1、TC=1。
   TC=1 说明移位器确实空闲 —— 因为字节**确实推出去了**, 只是推的节拍是 7200 而非 115200。
2. `uart.c` 的注释里有一条**自洽的假验证**:
   > `100MHz × 16 / 115200 = 13889 = 0x3641`, 误差 0.0004%

   这个数字**算得没错**, 但它是"16 倍分频"的值。注释用它"证明"公式正确,
   反而把错误锁死了 3 轮排障 (第一轮怪接线, 第二轮怪线材, 第三轮怪驱动)。
3. 现象与"线没接上"**完全一样**: PC 侧 0 字节。
   按常规排障路线 (先查线、查驱动、查共地) 会一路查下去, 永远查不到固件。

## 3. 定位手法 (可复用)

**关键一步: 用 SWD 直接驱动 GPIO 翻转, 做四组对照。**

```
A  PA9 恒低不动   → COM14 收到  0 字节
B  PA9 手摇方波   → COM14 收到 13 字节
C  PA9 恒高不动   → COM14 收到  0 字节
D  PA9 手摇(重复) → COM14 收到 13 字节
```

只有"动的时候有、不动的时候没有" ⇒ 排除悬空噪声, **锁死因果在线本身**。
这一步把"接线是否通"和"固件是否对"**彻底解耦**:
- 若 A/C 也收到字节 ⇒ 是噪声, 之前的"收到"全是假的
- 若 B/D 收不到 ⇒ 线断或接错脚, 与固件无关
- 实测 B/D 有、A/C 无 ⇒ **线是通的**, 问题在固件 ⇒ 下一步只需查寄存器

随后读 `USART1_BRR` 一眼看出 `0x22B9` vs 期望 `0x22B`, 当场结案。

**教训: "配置全对" ≠ "功能可用" 的又一次复现。**
本次比 A1 (NVIC_ISER 位移溢出) 更隐蔽 —— A1 至少 GCC 会报警告,
本次**编译器完全无话可说**, 因为语法、类型、逻辑都没有问题, 只是数学错了 16 倍。

## 4. 修复

| 文件 | 改动 |
|---|---|
| `src/uart.c` | `s_brr = (pclk2_hz + baud/2) / baud` + 顶部注释勘误 |
| `src/uart.h` | `uart1_brr()` 注释 `100MHz/115200 → 0x364` (原写 0x3641) |
| `src/min_uart.c` | BRR 公式 + 详细踩坑注释 |

三处均加**显式勘误注释**, 写明症状与错误值, 防止未来被"修正"回去。

## 5. 验证 (实机, 双向)

### 5.1 最小固件 — 单向接收
```
COM14 [COM14] \n==== MIN UART (no engine, no IRQ, HSI 64MHz) ====\n
             PA9=TX PA10=RX  115200 8N1  BRR=0x022C\n
[PASS] 命中: ['MIN UART', 'PA9=TX']
```
注意横幅里自报 `BRR=0x022C` —— 现在与理论值、与 SWD 读回值三者一致。

### 5.2 最小固件 — 全双工回声
```
发 'H723ECHO' × 5 次 → 5 次全部逐字节原样返回
★★★ 全双工通: H1-6(PA9)→CH340-RXD ✅   H1-5(PA10)←CH340-TXD ✅
```

### 5.3 主固件 (DCL 引擎 + 协议层) — 协议栈全量
```
串口 COM14 @ 115200
[PASS] T0  链路活性 (GET_VERSION→ACK)   payload=00 02 33 00
[PASS] T1.1~T1.4  fw=0x0200  cap=0x0033 (宣称=实现)
[PASS] T2  未知命令 → NAK 'bad cmd'
[PASS] T3  CRC 错 → 无响应
[PASS] T3b 阳性对照: 之后仍能响应
[PASS] T4  长度超限 → 无响应
[PASS] T4b 阳性对照: 之后仍能响应
[PASS] T5  分片慢发 → 仍解析成功
[PASS] T6  连发两帧 → 收到两帧
结果: 12 PASS / 0 FAIL / 0 SKIP
```

**这是本项目第一次在真实串口上跑通完整协议栈。**
此前全部协议验证都只能经 SWD 间接进行。

## 6. 附带确认

- **H1 脚位 (实测确认, 修正旧的猜测)**:

  | 脚 | 信号 | 实测 |
  |---|---|---|
  | 5 | USART1_RX_PA10 | ✅ CH340-TXD 接此, 回声成功 |
  | 6 | USART1_TX_PA9 | ✅ CH340-RXD 接此, 收到横幅 |
  | 7 | RST (串 1K) | 原理图确认 (旧文档误标为 PA9) |
  | 8 | 3.3V | — |

  ★ 此前 `docs/HARDWARE-PINOUT.md` 把 5/6 写反了 (5=PA9, 6=PA10), **已修正**。

- **DAPLink 自带 CDC (COM11)** 收到 1 字节 `0x00` —— 判断为打开端口瞬态, 
  **不是**有效数据。DAPLink 的 RXD/TXD 是否引到板子上仍**未确认**,
  但已不需要: CH340 全双工已验证可用。

- **时钟树假设成立**: HSI 64MHz, SWS=HSI, HPRE=1, D2PPRE2=1 → PCLK2=64MHz。
  `min_uart.c` 的"复位默认"假设经 SWD 实测确认。
