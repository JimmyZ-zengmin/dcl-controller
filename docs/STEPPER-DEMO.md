# 闭环步进 —— 我们做到了什么、怎么复跑、**以及它是什么**

> 面向第一次拿到这块板子的人。目标是让你 **15 分钟内自己复跑出同一批数字**。
> 完整数据与逐项判据：`docs/audit/H723-MOTION-QUALITY-AUDIT.md`（§1–§18）。
> ★ 本页**不复制状态**（避免两份互相矛盾）；状态以那份报告与 `docs/claims.md` 为准。

---

## 0. ★★★ 先说清楚它"是什么" —— 三句话，避免误会

| 层 | 是什么 | 语言 |
|---|---|---|
| **固件侧** | `0x39 op=19` 命令族（脉冲频率 / 方向 / 使能 / 限时 / 极性 / 只读状态） | **C**（`src/step.c`）|
| **上位机侧** | 验收套装与探针（速率、丢步、往返、位置锁定、转速上限、失速形态） | **Python**（`docs/audit/*.py`）|
| **闭环**（位置环 / 位置锁定 / 位置控制） | **跑在 PC 上**（"上位机在环"），**不是** DCL 程序 | Python |

> ### ⛔ **本项目目前没有"闭环步进的 DCL 程序"。**
> **而且现在也写不出来** —— 原因见 §4（这是一条**架构缺口**，不是"忘了写"）。

★ `0x39 op=19` 在本项目里的定位是**诊断脚手架**，**不是架构的一部分**：
未进 SHM、无 `obs_anchor()` 登记、**不占能力位**、**③层程序不得依赖它**
（见 `docs/SUPPORTED-SCOPE.md` §3 禁区）。

## 1. 我们做到了什么（全部实测，空载 · 8 细分 1600 步/圈 · 24 V）

| 项 | 实测 | 怎么复跑 |
|---|---|---|
| **速率精度** | 250/500/1000 Hz 偏差 **≤0.4%**；3 轮复现 500.2/500.2/499.9 脉冲/s | `h723_motion_probe.py rate` · `repro` |
| **2 分钟长跑** | 13496.5° vs 理论 13500.0° = **−0.0%**；速度波动 0.1% | `h723_stepper_motion.py longrun 500 120` |
| **丢步** | 10 轮往返：**换向不对称 −0.079°**、首末累积 **−0.35 步/轮**（符号随机，无系统性丢步） | `... roundtrip 500 1000 10` |
| **位置锁定** | 到位 **+0.176~0.264°（≈1 微步）**；**25 s 零修正、零漂移**；峰峰 **0.088° = 1 LSB** | `... hold 90 25` |
| **位置控制** | +90°/−45°/+180° ⇒ 2~4 次迭代、误差 **≤2°** | `... pos 90` |
| **最高转速（带斜坡）** | **≈31000 Hz ≈ 1100 ± 90 rpm**（临界区，三次 1134/998/1110） | `... ramp 31000 3000 2.0` |
| **最高转速（突加）** | 16650 Hz ≈ **627 rpm**（固件无加减速 ⇒ 被砍 47%） | `... speed 18000 2000 1.5 14000` |
| **失速形态** | 17000 Hz 起 **占用角域 0.2°** ⇒ "嗡嗡响但轴不动"（**扭矩不足**的直接观测） | `... slip 17000 2.0` |
| ★★★ **闭环在片内（100 µs / 抖动 90 ns）** | 环整条在 ③ 层每拍执行；实测 **min/max = 19990/20008 拍**（名义 20000 @200 MHz，跨 **40 万拍**恒定）⇒ **抖动 90 ns** | `examples/h723_step_bounded_position.dcl` |
| ★★★ **闭环定位到位保持** | 目标 320° ⇒ 到位 **误差 0.08°**、`hz=0` 自停、**峰峰 0.000°（零漂移）** | 同上（`op=19 sub=13 arg=1` 切程序面）|
| **使能极性 / 按轴保力矩** | `hold=1 ⇒ PE9=1(通电保持)` / `hold=0 ⇒ PE9=0(断电松开)`；未声明极性 ⇒ **拒绝使能** | `h723_motion_probe.py devcfg` · `h723_stepper_motion.py stophold` |

**精度天花板（实测）**：闭环 **≈0.2°** —— 已经贴着物理下限
（半微步 0.1125° + 编码器 1 LSB 0.0879°）。⇒ **瓶颈已从"微步量化"转移到"编码器分辨率"。**

## 2. 15 分钟复跑（按顺序，串口独占）

```bash
export PATH="/usr/bin:/bin:/mingw64/bin:/c/Windows/System32:$PATH"
cd <repo>
bash build.sh                                   # 6 道闸门（零警告 + ISR 树 + 应答缓冲 + ③层静态 + 契据可机检）
pyocd flash -t stm32h723xx -O connect_mode=under-reset build/dcl_h723.hex
# ★ 烧完让板子自己重启（断电/按 RESET）；此后**全程只走协议**

python docs/audit/h723_motion_probe.py asdiag     # ① 编码器看得见吗（接线/器件）
python docs/audit/h723_motion_probe.py devcfg     # ② 驱动器真的使能了吗（极性是否声明 / 指令 vs 引脚实读）
python docs/audit/h723_motion_probe.py pulcheck 500  # ③ 脉冲出来了吗
python docs/audit/h723_stepper_motion.py longrun 500 20   # 才谈运动结论
```

★ **开工顺序（血证换来的，缺一步就会误判）**：
`asdiag` → `devcfg`（极性声明 + `PE9` 实读）→ `pulcheck` → 运动结论。
**跳过第②步 ⇒ 整轮数据都在"失能"下产生，而且与"驱动器坏了"完全同形。**

★ **别在测量期间跑别的东西**：命令通路是**上位机墙钟**定时的，你加载 CPU = 直接改变被测对象
（实测同一条 `roundtrip`：忙时累积 −11.69°、空机 −0.79°）。

## 3. 一块板子上的"最小闭环"长什么样

```
        DCL 引擎（拍内 100 µs）                      上位机（PC，Python）
   ┌──────────────────────────────┐          ┌────────────────────────────────┐
   │ 0x39 op=19  →  TIM3_CH1 = PUL │          │  读编码器（0x39 op=18/19）      │
   │              PE8 = DIR        │          │     ↓                           │
   │              PE9 = ENA        │  UART    │  算误差 → 再下发 (频率,方向)     │
   │ SHM: AS5600 原始角            │◀────────▶│     ↑                           │
   └──────────────────────────────┘ 115200   └────────────────────────────────┘
                 └── 闭环在这一侧闭合 ──────────────────┘
```

★ **这正是当前的瓶颈所在（实测）**：命令通路 **26.3 命令/s** ⇒ 在环环频 **≈13.5 Hz**、
等效滞后 **≈80 ms** ⇒ 只能控**慢轴**。想上 L3（轨迹插补/多轴联动）必须把环搬进固件。

## 4. ★★★ 为什么"闭环步进的 DCL 程序"现在写不出来（架构缺口）

**DCL 程序的"面"是**：写 `sensor[i]` / `wire[j]` / `actuator[k]`（+ 路由/参数/状态表/LUT）。
**不允许出现任何物理引脚号或总线地址**（`tools/dcl_static_check.py` 编译期拒绝）。

而步进要做三件事，目前只有一件在"面"上：

| 要什么 | 现在从 ③层（DCL 程序）能做吗 | 说明 |
|---|---|---|
| **方向 / 使能**（PE8/PE9）| ⚠️ **部分可以** | 它们在 DO 面管辖（`STEP_DO_MASK=0x0F00`）⇒ 程序可写 `actuator[8]/actuator[9]`。**但** `step.c` 也在写同样的槽 ⇒ **单写者风险**（本项目红线 2）|
| **脉冲频率**（PA6 = TIM3_CH1）| ❌ **不能** | 只有 `step_set_rate()`（`op=19 sub=1`）能改；而 `op=19` **是诊断脚手架**（不占能力位、③层不得依赖）|
| **读编码器** | ✅ 可以 | AS5600 已在 SHM/SENSOR 面（含拍内状态机 + 就绪门）|

⇒ **缺的那一件是"运动原语"**：把"走 N 个脉冲 / 以某频率走 / 走到编码器位置 P"做成
**②外设能力（通用事务 op 或具名能力 + 能力位）**，而不是留在诊断脚手架里。

★ 这也正好回答了一个更一般的问题：**为什么这套系统的"算法"都跑在 PC 上** ——
不是不会写，而是**运动这件事还没进 DCL 的架构面**。

**要补齐的话，建议的顺序**：
1. **把"运动"提为②能力**：具名设备 + 能力位（`DCL_CAP_STEP`），并把 `op=19` 的**诊断脚手架与能力面分开**；
2. **加确定性运动原语**（审计 P0 指出的两条，任选其一或都做）：
   - **脉冲计数原语**：`走 N 个脉冲，到位自停`（N 由固件数，与命令服务解耦）；
   - **位置闭环原语**：`走到编码器位置 P，误差带 ±e 自停` ⇒ 直接消掉"上位机读→算→再发"那一整圈时延；
3. **加减速（梯形/S 曲线）进固件**（突加上限 627 rpm vs 带斜坡 1100 rpm = **被砍 47%**）；
4. 之后才谈"用 DCL 程序写闭环" —— 那时闭环是"写几行走位指令"，而不是"PC 在环"。

## 5. 已知边界（别踩）

- **空载数据**。带载 / 垂直轴的上限会显著更低（力矩随转速下降）。
- **`0x39 op=19` 是脚手架** ⇒ 产品代码不要依赖。
- **`0x39 op=19 sub=11` 的 `mismatch_n`（指令 vs 引脚实读）**是非零过的（曾到 32.7 万）
  ⇒ 说明**历史上的窗口里有别的代码在驱 PE9**（与挂账未收的 `hil.c` 输出臂缺门同族）。
  ⇒ **现在它冻结为 0 增长，但来源未定案**：判定任何"使能相关"结论前先看 `devcfg`。
- **按轴保力矩**：本台（水平空载）交付档 = `DCL_STEP_STOP_HOLD=0`（休息态**断电**，不发热）。
  **垂直轴必须改回 1**（去使能 = 掉力滑车）。
