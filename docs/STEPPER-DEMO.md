## 0. 先说清楚三条路（避免误会）

**这块板子上"闭环"有三种做法，别混为一谈**：

| 路线 | 环在哪 | 实测环频 | 怎么切 |
|---|---|---|---|
| **① PC 在环** | PC 读编码器 → 算 → 下发频率 | **≈13.5 Hz**（命令通路 26.3 命令/s）| `op=19 sub=13 arg=0`（**默认**）|
| **② 脚手架直控** | 无环，工具直接设频率/方向/使能 | — | `sub=1/2/3`（验收套件用）|
| **③ 片内程序面**（★ 本页重点）| **环整条在 ③ 层 DCL 程序里，每拍执行** | 执行 10 kHz；带宽 ≈550 Hz（拍内反馈）| `op=19 sub=13 arg=1` + 上传 `.dcl` |

★ `0x39 op=19` 在本项目里的定位是**诊断脚手架**，**不是架构的一部分**：
未进 SHM、无 `obs_anchor()` 登记、**不占能力位** ⇒ 产品代码不要依赖它（见 `SUPPORTED-SCOPE.md` §3 禁区）。
★ 但 **③ 路线本身是合法的架构用法**：程序写 `wire[12..15]`（运动请求），由固件侧消费 —— 见 §4 的现状与缺口。

**现成的 `.dcl` 例程**（`python tools/dclc.py <文件>` 即可编译上传）：

| 文件 | 是什么 | 状态 |
|---|---|---|
| [`../examples/h723_step_stall_recover.dcl`](../examples/h723_step_stall_recover.dcl) | ★ **失步自动检测 + 恢复** | ✅ 上机通过 |
| [`../examples/h723_step_traj_tri.dcl`](../examples/h723_step_traj_tri.dcl) | 三角波速度曲线 | ✅ 程序运行，形状待黑匣子 |
| [`../examples/h723_step_traj_sine.dcl`](../examples/h723_step_traj_sine.dcl) | 阶梯正弦速度曲线 | ✅ 程序运行，形状待黑匣子 |
| [`../examples/h723_step_bounded_position.dcl`](../examples/h723_step_bounded_position.dcl) | ★ **有界闭环定位**（最短弧 + 双极性 + 幅值钳位 + 误差带自停）| ✅ 已跑通 |

## 1. 我们做到了什么（全部实测：单轴 · 空载 · 8 细分 1600 步/圈 · 24 V）

| 项 | 实测 | 怎么复跑 |
|---|---|---|
| **速率精度** | 250/500/1000 Hz 偏差 **≤0.4%**；3 轮复现 500.2/500.2/499.9 脉冲/s | `h723_motion_probe.py rate` · `repro` |
| **2 分钟长跑** | 13496.5° vs 理论 13500.0° = **−0.0%**；速度波动 0.1% | `h723_stepper_motion.py longrun 500 120` |
| **丢步** | 10 轮往返：**换向不对称 −0.079°**、首末累积 **−0.35 步/轮**（符号随机，无系统性丢步）| `... roundtrip 500 1000 10` |
| **位置锁定** | 到位 **+0.176~0.264°（≈1 微步）**；**25 s 零修正、零漂移**；峰峰 **0.088° = 1 LSB** | `... hold 90 25` |
| **位置控制** | +90°/−45°/+180° ⇒ 2~4 次迭代、误差 **≤2°** | `... pos 90` |
| ★★★ **闭环在片内** | 环整条在 ③ 层**每拍**执行；`period_min/max = 19990/20008` ⇒ **拍周期抖动 90 ns**（跨 40 万拍恒定）| `../examples/h723_step_bounded_position.dcl` |
| ★★★ **闭环定位到位保持** | 目标 320° ⇒ 到位 **误差 0.08°**、`hz=0` 自停、**峰峰 0.000°（零漂移）** | 同上（`sub=13 arg=1` 切程序面）|
| ★ **失速边界（可预测）** | **从静止突加到 >16500 Hz 必失速**（拐点 **16500~16750 Hz = 619~628 rpm**）；**已在转动时突跳到 31 kHz 完全正常**；带斜坡 **≥50000 Hz** | `../tools/h723_stall_edge.py` |
| ★ **失速不自愈** | 突加 20000 Hz 后 0.4 s / 2.0 s 都是 **0 rpm** ⇒ **持续通电流**（响 + 热 + 轴不动 = 同一物理态）| `../tools/h723_stall_edge.py`（组 C）|
| ★★★ **失步自动检测 + 恢复** | 突加 18000 Hz ⇒ **1.17 s 触发**、降额 0.25、**轴恢复转动 99.2%** | 部署 `h723_step_stall_recover.dcl` → `../tools/h723_stall_detect_verify.py` |
| ★ **频率可预测** | `rate_actual = 1e6/floor(1e6/f)`，**7/7 精确命中**（1 µs 周期量化）| `../tools/h723_motion_calib.py` |
| ★ **跟随线性度** | 1~60 kHz 共 28 点，**无随速度增长的丢步，线性度 ≤0.5%** | `../tools/h723_stall_sweep.py` |
| **走 N 个脉冲自停** | 另一个定时器**硬件数脉冲**（零中断/零 DMA/零 ITCM）；`N=1000` ⇒ 硬件计 **1001**（多走 1 步 = 主循环停的延迟，**已知量**）| `../tools/h723_step_pulsecount_test.py` → **7/0** |
| **装置配置 fail-closed** | 极性未声明 ⇒ **拒绝使能**；"指令 vs 引脚实读"的失配**有归因计数** | `../tools/h723_step_failclosed_test.py` · `../tools/h723_do_mask_owner_test.py` |
| **使能极性 / 按轴保力矩** | `hold=1 ⇒ PE9=1(通电保持)` / `hold=0 ⇒ PE9=0(断电松开)` | `h723_motion_probe.py devcfg` · `h723_stepper_motion.py stophold` |

**精度天花板（实测）**：闭环 **≈0.2°** —— 已贴着物理下限
（半微步 0.1125° + 编码器 1 LSB 0.0879°）。⇒ **瓶颈已从"微步量化"转到"编码器分辨率"。**

> ### ⚠️ 已撤回的数字（**请勿再引用**）
> - "带斜坡 ~1100 rpm、突加 **627 rpm** ⇒ 可用转速 **+75%**" —— **混叠伪影**。那组数来自 31000 Hz 下
>   2 s 走 38 圈的采样，而命令通路只有 **26 命令/s** ⇒ 角度解卷绕必然混叠（套件自己会打印
>   `⚠ 最短弧已混叠`，当时引用者没看那行）。
> - "**17000 Hz 起原地抖动、突加被砍 47%**" —— 同上；且它把"**拉起拐点**（627 rpm）"与
>   "**突加可用转速**"混为一谈。**今天的实测：超过拐点突加 = 0 rpm；带斜坡 ≥50000 Hz 正常。**
> - ★ 一般化教训：**判定"高速段"结论时，PC 侧差分测速在本装置上不可用**（编码器回填率与 PC
>   轮询率发生**采样拍频**）⇒ 必须用**片内黑匣子**（1 kHz）记录。见 §5。

## 2. 15 分钟复跑（按顺序，**串口独占**）

```bash
export PATH="/usr/bin:/bin:/mingw64/bin:/c/Windows/System32:$PATH"   # shell 初始化脚本坏了, 必须显式 export
cd <repo>
bash build.sh                                   # 6 道闸门
pyocd flash -t stm32h723xx -O connect_mode=under-reset build/dcl_h723.hex
# ★ 烧完让板子自己重启（断电/按 RESET）；此后**全程只走协议**

python ../tools/h723_motion_probe.py asdiag              # ① 编码器看得见吗（接线/器件）
python ../tools/h723_motion_probe.py devcfg              # ② 驱动器真的使能了吗（极性声明 / 指令 vs 引脚实读）
python ../tools/h723_motion_probe.py pulcheck 500        # ③ 脉冲出来了吗
python ../tools/h723_stepper_motion.py longrun 500 20    # ④ 才谈运动结论
```

★ **开工顺序（血证换来的，缺一步就会误判）**：
`asdiag` → `devcfg`（极性声明 + `PE9` 实读）→ `pulcheck` → 运动结论。
**跳过第②步 ⇒ 整轮数据都在"失能"下产生，而且与"驱动器坏了"完全同形。**

★ **想跑"今天的成果"**：
```bash
python ../tools/h723_stall_edge.py            # 失速拐点（突加 vs 运行中突跳的决定性对照）
python ../tools/h723_motion_calib.py          # 步/圈 + 拍长 + 频率量化（7/7）
python ../tools/h723_stall_sweep.py           # 1~31 kHz 全频段跟随线性度
python ../tools/dclc.py ../examples/h723_step_stall_recover.dcl   # 上传失步自检程序
python ../tools/h723_as5600_bind.py --port COMxx                  # ★ 部署会清掉反馈绑定 ⇒ 必须写回
python ../tools/h723_stall_detect_verify.py   # 8 条判据（含反向判据）
```

★ **别在测量期间跑别的东西**：命令通路是**上位机墙钟**定时，你加载 CPU = 直接改变被测对象
（实测同一条 `roundtrip`：忙时累积 −11.69°、空机 −0.79°）。

## 3. "最小闭环"长什么样（两条路并排）

```
    ③ 片内程序面（★ 我们做到的）                       ① PC 在环（默认，也是被对比的对象）
┌───────────────────────────────┐               ┌────────────────────────────────┐
│ DCL 程序（每拍，100 µs）        │               │ PC：读编码器 → 算 → 下发         │
│  读 sensor[1]（AS5600 角度）    │  UART 115200  │   环频 ≈13.5 Hz（26.3 命令/s）   │
│  → 算误差 → 钳幅值 → 定方向      │◀────────────▶│   等效滞后 ≈80 ms                │
│  → 写 wire[12..15]（运动请求）   │               │                                │
│  固件：step_service_motion() 消费 │               │                                │
└───────────────────────────────┘               └────────────────────────────────┘
        └── 环在这一侧闭合（片内）──┘                  └── 环在这一侧闭合（PC）──┘
```
★ **同一个判据下的对比（阶段 1 的 A/B）**：片内阶跃响应 **0.635 s** vs PC 在环 **2.115 s** = **3.3×**
（两侧 ±2.5% 可复现）；机制不是"纯滞后"，而是 **PC 的 ~110 ms 周期 + 频率下限 ⇒ 极限环**。

## 4. ③ 层现在能写什么、**还缺什么**（本节的更正说明）

> ★★ **上一版这里写着"闭环步进的 DCL 程序现在写不出来"—— 那句已过期。**
> 实际情况：**运动请求面已经有了**，闭环程序**已经能写、且已经跑通**（§0 的例程表）。
> 下面把它写成**当前事实**，并把"真正还缺什么"单列出来。

| 要什么 | ③层能做吗 | 怎么做的 / 缺在哪 |
|---|---|---|
| **读编码器** | ✅ | `sensor[0]`(raw) / `sensor[1]`(角度)，由**绑定表**每 N 拍回填（含拍内状态机 + 就绪门）|
| **下频率 / 方向 / 使能 / 限时** | ✅ | 程序写 `wire[12..15]`；`op=19 sub=13 arg=1` 切到程序面 |
| **"走 N 个脉冲自停"** | ✅（固件侧已实现）| `op=19 sub=15`；正解 = 另一个定时器**硬件数脉冲**（见 §1）|
| **加减速 / 斜坡限幅** | ⚠️ **只能"够到"，不能"设置"** | 斜坡存在（`sub=17 arg=Hz/s`），但它是**全局设置、③层够不到** ⇒ 轨迹程序只能**依赖外部先设好斜坡**（三角波例程就依赖这一点，已如实写进程序头）|
| **查表（`LUT`）** | ❌ **工具链没暴露** | 引擎有 `prim_lut`（带线性插值），但 `tools/dclc.py` 没有 `LUT` 关键字 ⇒ 正弦只能用"阶梯表 + `SEL` 链"逼近（**补它比在程序里凑划算**）|
| **多轴** | ❌ | 见 §5 与 [`PLAN-multi-axis-v1.md`](PLAN-multi-axis-v1.md)（三个真阻塞）|

**⇒ 真正还缺的三件（都不是"不会写"，是"面还没铺到"）**：
1. **运动面未占能力位**：`wire[12..15]` 这套约定**目前仍是"在诊断脚手架之上的一层约定"**，
   没有 `DCL_CAP_STEP` ⇒ 换一块板/换一个版本，程序面契约没有机器可检的保证。
2. **斜坡是全局设置**：轨迹规划要"每轴/每段可配的斜率"，现在只能靠外部设一次。
3. **`LUT` 未暴露**：任意曲线（正弦/自定义）目前只能阶梯逼近。

★ 补齐顺序建议：**① `LUT` 暴露**（纯工具链、代价最小、立刻解锁正弦正解）→
**② 运动面能力位 + 契约**（让程序面成为**可机检的**对外契约）→ ③ 斜坡进请求面。

## 5. 已知边界（别踩）

- **空载数据**。带载 / 垂直轴的上限会显著更低（力矩随转速下降）。
- **`0x39 op=19` 是脚手架** ⇒ 产品代码不要依赖（但 **`wire[12..15]` 程序面**是合法用法，见 §4）。
- ★★ **`mismatch_n`（指令 vs 引脚实读）曾到 32.7 万 —— 已定案**（2026-09-17）：
  真因是**上位机把 `GPIO_MASK` 换掉了**（`h723_do_hold_test.py` 注入 `0x00FF`、`h723_w1.py` 注入越界值）
  ⇒ `do_poll` 不再驱 `PE9` ⇒ 引脚冻在旧电平。**不是"有别的代码在驱 PE9"。**
  修法：保留位 `PE8..PE11` **不可被上位机掩码剔除**（`DCL_DO_MASK_UNION`，对照档实测 +1747 / 交付档 +0）；
  归因观测面 `op=19 sub=24`。
- ★★ **PC 侧差分测速在本装置上不可用**：编码器回填率与 PC 轮询率发生**采样拍频**
  （实测 `Δt` 稳定 37 ms 而 `Δraw` 中位 **2**，1200 Hz 应有 123）⇒ **极值/分位数全不可信**，
  只有 `ΣΔraw/总时长` 免疫。⇒ **形状类判据一律走片内黑匣子（1 kHz）。**
- ★ **③ 层的三个口径坑**：`SEQ` 步号**1 起**（不是 0）；`OUTPUT` **不接受 `PERIOD=`**；
  `SRC_HMI` 在 H723 上**未实现**（写 `hmi[n]` 的程序**上传期被拒**）。
- **按轴保力矩**：本台（水平空载）交付档 = `DCL_STEP_STOP_HOLD=0`（休息态**断电**，不发热）。
  **垂直轴必须改回 1**（去使能 = 掉力滑车）。
- ★ **判据自身的纪律**（今天换来的）："**期望为 0**"的判据必然假绿 ⇒ **先配正对照**；
  **差分量的分子分母必须同口径**；**测量期间不许做别的事**。
