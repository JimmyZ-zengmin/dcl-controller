# RS-485 单向不通 —— 问题总结（拿去请教硬件/通信的人）

> 日期: 2026-09-13
> 平台: STM32H723ZGT6 最小系统板，固件为自研裸机工程（无 RTOS），COM14/COM15 为本机 USB 串口
> 一句话问题: **板子→PC 方向逐字完好；PC→板子方向一个字节都到不了 MCU。**
> 请重点回答第 6 节的问题。

## 0. ★★★ 已结案：根因是**固件**，不是接线（2026-09-13 傍晚更新）

**本文件 §1–§7 写于误判期，结论已被推翻并作废；请以本节的结论为准。**
权威报告：`docs/audit/H723-485-RX-AUDIT.md`（提交 `14fe5c6`）。

### 真正的根因（两个叠加的软件缺陷，都在 `src/modbus.c`）

**① `ORE` 溢出标志从未被清除 → 接收自锁死**
`mb_pull_rx()` 物理口分支只查 `RXNE`：一旦出现 **`ORE=1` 且 `RXNE=0`**（实测常态），
循环直接 `break`、**永不读 RDR** ⇒ ORE 永不清；而 **H7 在 ORE 置位期间丢弃所有新收到的字符**
⇒ `RXNE` 再也不置位 ⇒ **自锁死**。症状正是"偶尔收到一点点，然后就没有了"
（本项目在 USART1 的 `uart.c` 里已修过同一族问题，**USART2 漏了**）。

**② ORE 为什么必然发生：单字节 RDR + 100µs 轮询 > 86.8µs 字节间隔**
字节间隔 = 10bit/115200 = **86.8µs**，拍周期 = **100µs** —— **拍比字节慢**，
相位每字节漂 13.2µs ⇒ **周期性"一拍内到 2 字节"** ⇒ 单字节 RDR 必然溢出。
`modbus.c` 里那句"每拍最多到达 1.15 字节"是**平均值不是上界**，正是它把这条缺陷藏了整轮排查。

### 修复（已固化进源码 + 重编烧录 + 端到端验收）

| 改动 | 位置 |
|---|---|
| 打开 `CR1.FIFOEN`（深度 8 吸收拍间积压） | `mb_uart_enable()` |
| **每拍无条件清接收错误标志**（不只在拉字节循环里 —— EXEC/BUILD/TX 期间 `mb_pull_rx` 根本不跑） | `mb_tick()` 入口 |
| 拉字节循环内"先清错误再判 RXNE"，**不 break 不 continue** | `mb_pull_rx()` |
| 新增可观测量 `MbDiag[15]` = **清错误次数**（原来只有"见过什么错"，无法把"反复清掉"与"从未出现"分开） | `src/modbus.c` |
| 补 `USART_CR1_FIFOEN` 宏 | `src/regs.h` |
| 最小固件同族缺陷（错误分支 `continue` 跳过 RDR ⇒ 静默丢字节） | `src/min_uart485.c` |

**验收结果**（`tools/mb_master_test.py --port COM15`）：**T0/A/B/C/D/E/F/G 全部 PASS**，
写 40065=0x1234 回读一致，写只读区正确回异常 02，坏 CRC 静默，错站号静默。
字节级：30 帧合法请求 **Δbytes = 240/240（一个字节不丢）**、`maxrx=8`（整帧不再被切）、
`frames_rx=30`、`frames_tx=30`、**`erracc=0x00`（一次 ORE 都没有）**。

### ★ 顺带纠正两个**测试工具**的缺陷（它们曾把正确行为判成 FAIL）

1. ★★ **本文件 §0 旧版（被推翻的那段）** —— 我当时用"485 收发器驱动总线时会**本地回显**到
   自己的 TXD"来推断"PD6 没接到模块 TXD ⇒ 两线接反"。**这条推理无效**：多数半双工收发器
   **在发送期间（DE=1）会同时禁用接收**，本来就不回显 ⇒ "板子发时 PD6 不动"**不能**证明接错脚。
   ⇒ 教训: **判据依赖的器件特性必须先被验证，不能在推理里当公理用。**
2. **`mb_master_test.py` 两个缺陷**（均已修）：
   · 写区地址少加 1（`0x9C80`=40064 落进只读区）⇒ 固件的正确拒绝被读成"写不进去"；
   · 写只读区的异常判据写死 `0x83`，而该项发的是 **0x06** 请求（异常码应为 `0x86`）⇒ 该项**永远 FAIL**。

## 1. 物理拓扑（引脚级）

```
                       ┌──────────────────┐
  PC(COM15) ──USB──▶ │ USB↔RS485 dongle │ ── A / B ──┐
                       └──────────────────┘             │   双绞
                                                        ▼
                                             ┌────────────────────┐
                                             │ RS485↔TTL 模块      │
                                             │ 485 侧: A+ / B+     │
                                             │ TTL 侧: RXD / TXD   │
                                             └────────────────────┘
                                                    │       │
                              RXD ◀──────────────────┘       └──────────────▶ TXD
                               │                                              │
                            PD5 (USART2_TX)                              PD6 (USART2_RX)
                            STM32H723

  PC(COM14) ──USB──▶ USB-TTL(CH340) ── TXD ──▶ PA10 (USART1_RX)   ← 观察窗
                                      ◀─ RXD ── PA9  (USART1_TX)   ← 观察窗
  三方共地 (PC GND / 模块 GND / 板子 GND)
```

- 两端模块丝印（用户实读）:
  - USB↔485 dongle: `A`、`B`、`GND`、`5V`（dongle 自身由 USB 供电）
  - RS485↔TTL 模块: `A+`、`B+`、`GND`、`VCC`、`GND`、`RXD`、`TXD`
- 供电: dongle 由 USB 供电，5V → 模块 VCC
- 波特率: 115200 8N1（两端一致）
- **A/B 极性: 已由"板子→PC 方向工作"间接证明是正确的**（见 §3）

## 2. 已彻底排除的（别再往这些方向查）

### 2.1 板子侧软件全部无嫌疑 —— 有读回证据
| 检查项 | 读回值 | 判读 |
|---|---|---|
| USART2 CR1 | `0x0000000D` | UE+TE+RE 全开 |
| USART2 BRR | `0x00000364` (=868) | 与 100MHz 时钟匹配，无 7200/115200 类错误 |
| USART2 PRESC | `0` | ÷1 |
| GPIOD MODER | `0x0000EBFF` | PD5/PD6 = AF 模式 |
| GPIOD AFRL | `0x07700000` | PD5、PD6 **都=AF7**（USART2 正确复用） |
| GPIOD PUPDR | `0x00001000` | PD6 = 上拉 |
| 状态机调用计数 | `g_mb_ticks` 每 100µs 拍 +1，与拍计数**完全同步** | 接收状态机每拍都在跑 |
| 通信域使能 / RX 源 | `enabled=1`、`src=0` | 走**物理口**，不是软件隧道 |

→ 结论: **"代码把通信挡住了"可以排除。**

### 2.2 观测工具不可靠这个可能 —— 也已排除，并已换掉观测方式
本项目调试探针（CMSIS-DAP）**每次 pyocd 会话开始与结束都会复位目标 MCU**，
而诊断数据在 DTCM（复位清零）。
⇒ 早期所有"收到 0 字节"的读数**都不可信**（读到的其实是"我刚复位后的值"）。
现已改为：**诊断数据从板子的协议口(USART1/COM14)读，全程不开调试器**，
并额外用一块**只有 200 行的最小固件**（无中断、无协议、无引擎）复测，
两种方式结论一致。

### 2.3 引脚选错 / 插错排针 —— 已用"全端口扫描"排除
在 PC 持续发送 485 数据（**灌了 20262 帧**）期间，
用固件把 **GPIOA…GPIOG 全部 112 个引脚**逐个设成"输入+下拉"并各采样 40 万次，
统计每个脚的高电平比例与**跳变次数**：

| 结果 | 数量 |
|---|---|
| **有翻转（trans ≥ 300）的脚** | **0 个** |
| 静态高（high=100%, trans=0） | PA10、PC8/9/10/11、PD2、PD5、PG15 |
| 悬空/接地（high=0%, trans=0） | 其余全部 |

（判读依据: 115200 下真数据线的翻转率 ≈ baud/2 ≈ 57600 次/秒，
每脚 40 万次采样约 37ms ⇒ 真数据线应出现 ≈2000 次跳变；
悬空脚拾取串扰通常只有几十~几百次。所以 300 这个阈值能有效区分信号与噪声。）

**⇒ 不是"接错了引脚"，而是信号根本没有到达 MCU 这一侧。**

## 3. 已确证: 板子→PC 方向完全正常

用最小固件让板子从 **PD5** 反向发一段可识别文本（`DCL485TX-0123456789\r\n` × 200 遍）：

- 板子侧: `TX timeouts=0`（3800 字节全部发出，无阻塞）
- PC 侧在 **COM15**（即那个 485 dongle）上收到: **几千遍完整的 `DCL485TX-0123456789`，逐字无误**

⇒ 这一条同时证明了:
1. **COM15 确实就是那个 USB↔485 dongle**（否则收不到），即本文的前提成立；
2. 模块的 **TTL→485 发送器** 正常；
3. **485 总线 A/B 接线与极性正确**（极性错的话这个方向也会失败）；
4. dongle 的 **485 接收器** 正常；
5. 共地正常。

## 4. 已确证: PC→板子方向一个字节都到不了

| 测量 | 方法 | 结果 |
|---|---|---|
| PD6 电平 | 固件连续采样 **4,000,000** 次（PC 正在发数据） | **低电平 0 次 = 0.0%**，PD6 恒定高 |
| PD6 有无驱动 | 整口输入+下拉，PD6 读回 | **0**（有驱动的话空闲应读到高） |
| PD6 有无跳变 | 逐脚采样 40 万次 | **trans = 0** |
| 全 MCU 112 脚 | 同上 | **无一有跳变** |
| 通信域收到的字节（DTCM 缓冲） | 协议口直读原始字节 | **全 0，一个字节都没进过 DTCM** |

四条独立测量一致: **模块的 TXD 引脚上没有出现任何数据（或它没有接到 MCU 的任何脚上）。**

## 5. 剩下的两个嫌疑（请重点看这一节）

把 §3（成功）与 §4（失败）两条路径的元件逐个对消，**未被任何一次成功测量覆盖的只有两个**：

```
 PC→板子 路径:  PC → [dongle 的 485 发送器] → 485总线(A/B✅) → [模块的 485→TTL 接收器] → 模块TXD → PD6
                            ↑ 嫌疑①                                      ↑ 嫌疑②
      已排除: A/B 接线✅  共地✅  模块TXD在MCU侧的落点(全端口扫描)✅  板子侧固件与引脚配置✅
```

- **嫌疑①** = USB↔485 dongle 内部的 485 **发送**方向（驱动芯片/使能/方向控制/损坏）。
  *注: 廉价 USB-485 dongle 有些靠 RTS 或自动方向控制，方向控制失效时表现就是"收得到、发不出"。*
- **嫌疑②** = RS485↔TTL 模块内部的 **485→TTL 接收**方向（接收器/使能/损坏）。
- （次要可能）模块 TXD 那根线**物理上没有真正接到 PD6**（接触不良/断线/丝印认错）。
  *已确认的是: PD6 上确实没有任何信号，且 PD5（模块 RXD 侧）读回为静态高 —— 即 PD5 那根线是接上的。*

## 6. 请对方回答 / 建议的下一步测量

**核心问题: 上面两个嫌疑怎么用最少的手段分开？**

建议的判别方法（我们手头有: 万用表、Saleae Logic2 逻辑分析仪、杜邦线、DAPLink）:

1. **在 PC 持续发送时，用万用表/示波器量 485 总线的 A-B 差分电压。**
   - 若 A-B 随着发送**在正负之间翻转** ⇒ dongle 的发送器正常 ⇒ 嫌疑②（模块接收器）。
   - 若 A-B **静止不动** ⇒ 嫌疑①（dongle 发送方向）。
   *关键点: 这一步能把两个嫌疑一次分开，而且不需要动任何接线。*
2. **用逻辑分析仪夹在 RS485↔TTL 模块的 TXD 引脚（对模块 GND）上，PC 端持续发送。**
   - 有 115200 波形 ⇒ 模块接收器正常 ⇒ 问题在"TXD→PD6 这一根线"。
   - 无波形（恒定高） ⇒ 确认是 §5 的嫌疑①或②。
   *（此前曾用逻辑分析仪在此处量到过 44,679 次跳变、位宽 8.7µs = 115200，
     所以**这条通路曾经是通的**——如果现已不通，请判断是接触退化还是元件损坏。）*
3. **关于 485 侧的电平: 模块标注 `A+ / B+`, dongle 标注 `A / B`。**
   请确认这种标注下 A↔A+、B↔B+ 的接法是否正确（是否存在"标注习惯不同"导致的隐性反接）。
   *（我们的推理是: 反接会让两个方向都失败，而板子→PC 是成功的，
     所以据此认为极性没问题——如果这个推理有漏洞请指出。）*
4. **5V 供电是否需要更硬的去耦 / dongle 的 5V 是否真的能带动模块**（模块 TTL 侧 3.3V 电平是否足够被 H723 的 PD6 识别为高）。

## 8. 本次顺手修掉的两个自研缺陷（与主问题无关，但会污染判据）

1. **诊断钩子会自己造出"到过字节"的假证据**
   `mb_line_test` / `mb_line_probe` 恢复引脚时先写 MODER（接回 AF7）再写 PUPDR（还停在下拉），
   中间那一瞬 RX 脚被下拉成低 = 一个 break 条件 ⇒ USART 必然收到 **1 个 0x00 + 1 次帧错**。
   症状: 每跑一次线检，字节计数就 +1、错误计数就 +1，看起来像"真的有数据来了"。
   **已修**（恢复顺序改为: AF 选择 → 上拉 → 最后才接 AF）。
2. **`build.sh` 的"生效开关"清单漏列了结尾带数字的开关**（正则 `[A-Z_]*` 不含数字）,
   而这一段的目的正是"别被 CMake 缓存骗"。**已修**。
