## 2. ★ A（P2）`h723_w1.py` 一行类型 bug → W1 的 6 条命令**从未被验证**

```python
# tools/h723_w1.py:128  (Link.xact 的返回)
return bytes(buf[1]), bytes(buf[4:need - 2])
#      ^^^^^^^^^^^^ buf[1] 是 int
```
`bytes(0x00)` = `b''`；`bytes(0xFF)` = 255 个零字节。于是 T0 的判据 `sts != STS_ACK` **恒为真**：

```
── T0 链路活性 ──
      TX: C0 01 00 00 AC FB                    ← 帧正确
      RX: C1 00 04 00 00 02 F7 00 59 13        ← 响应正确 (ACK, cap=0x00F7, CRC 通过)
  [FAIL] T0 链路不活 —— 后续全部无法判定        ← 但判定失败
```

**修这一行后 W1 立刻能跑（18 PASS / 7 FAIL，见 §3）。**

**为什么这条重要**：他们的开发纪律 #1 是"任何命令实现后**立刻跑对应的 Python 验证脚本**，绿了才继续"。而 `h723_w1.py` 是 W1 六条命令（`0x11/0x12/0x13/0x20/0x21/0x22/0x23`）**唯一的验证工具**。它恒 FAIL 在 T0、直接 `return 2`，**后面 40 多项判据一行都没执行过**。

⇒ **这是"先开发后审查"暴露的最典型风险**：工具坏了不等于纪律被违反，但**它让纪律静默失效**。而且失败信息（"T0 链路不活"）会把人引向"串口/固件有问题"，与真因（工具自己）相反 —— 与 A1/BRR 事故**同一个模式：故障现象指向错误的方向**。

**唯一的幸运**：我修好它之后，W1 的固件侧大部分是好的（18/25 通过）。但如果不修，**"W1 已完成"这个声称就没有任何证据支撑**。

## 3. B（P2）W1 工具的 6 项判据与固件语义不符

修掉 §2 的 bug 后 W1 得 **18 PASS / 7 FAIL**。逐项核过，**7 项里 6 项是工具判据问题**：

| 项 | 现象 | 判定 | 依据 |
|---|---|---|---|
| **S5** F11 兜底 | "超预算表 → START 居然 ACK 了!" | **工具算错** | 工具注释写"128 条 PID (140/条 → 远超 26000)"，但 **128×140 = 17920 < 26000**。★ **同一项目的 `h723_persist.py` T24 明确记录了这件事**（"128×140 = 17920 < 26000 —— 全 PID 也不超预算! 这正是 engine.h 那条绊线断言说的"）⇒ **两个工具口径自相矛盾** |
| **S2** STOP 后停止 | s1=1058806 → s2=1062871 仍在涨 | **用错量** | 判据读的是 `0x38 r[0:4]` = `g_isr_n`（**拍中断**次数）。STOP 只停引擎、不停拍 → 该量本就应继续增长。应改用 `g_eng_ticks`/`g_eng_routes_total` |
| **S1b** RESET 后 RUN=0 | `run=None` | **工具用了非法地址** | 它读 `shm+0x0D`（`ENGINE_RUN` 是 u8，**非 4 对齐**）→ 被 `eng_valid_addr` 的对齐守卫拒绝。**固件行为正确**（读 `shm+0x0C` 一次拿 4 字节即可） |
| **R2/R2b** 写 WIRE_MAP | 写 3.14159 → 读回 0 | **未考虑引擎覆写** | `BOOT_GATE=1` 时引擎每拍写 128 条路由的 dst；`WIRE_MAP[0]` 正是被路由持续覆写的地址 ⇒ 写完即被覆盖。测 SHM 写应先在 STOP 态，或选非引擎区地址 |
| **R9** burst 越界 | 期望 NAK 却 ACK | **地址没越界** | 测的是 `shm+0x7F00` 起 64 字 = `[0x7F00, 0x8000)` —— **恰好落在 `SHM_SIZE=0x8000` 内**，不是越界，ACK 正确 |
| **R1** MAGIC 非零 | magic=0x00000000 | **★ 固件问题** | 见 §4 |

> **这 6 项的共性**：判据"看起来在报问题"，实际是工具对**本平台的量/地址/语义**的假设没跟上（引擎 RUN 下会覆写、预算门不具约束力、u8 字段不对齐、SHM 边界值）。这正是审计里那组"判据族"缺陷（OA23 / M1 / S5 同族）。

## 4. C（P3）`OFF_CTRL_MAGIC` 从不被设置

```c
/* engine.h:48 */
#define OFF_CTRL_MAGIC   0x00   /* u32 */
```
全 `src/` 里**只有这一行定义 + 一条 `_Static_assert`，没有任何赋值**。对照 S3：

```c
/* esp32-core0/main/main.c:979 */
SHM_U32(OFF_CTRL_MAGIC) = CTRL_MAGIC;
```

⇒ H723 的 SHM 控制块首字**恒 0**。后果：`0x20` 读 SHM 首字永远得 0，"SHM 是否已初始化/就绪"这类外部判据失去依据（W1 的 R1 就是这么发现的）。

**修法**：在 `cold_start_reset()` 之后、`engine_fill_tables()` 里（或 main 的 ③ 步）写一次 `'DCL1'` 之类的魔数，与 `PROG_MAGIC` 同款；并把"SHM 已就绪"的定义写进注释。

## 5. D（P3，实测坐实）`g_active_routes` 双来源不一致 → `0x38`/`0x43` 报陈旧条数

实测（deploy 8 条 DIRECT 后）：

```
SHM N_ROUTES (0x0E) 真相      = 8
0x38 r[20:22] (引擎报告条数)   = 128   ← 陈旧
0x43 r[1:2]   (persist 报告)  = 128   ← 陈旧
```

根因：`g_active_routes` 只在**启动**(main.c:1710) 与 **reinit**(main.c:1822) 更新，**`h_deploy` 路径没有更新**；而 `h_engine_status`(r[20]) 与 `h_persist_w2`(r[1:2]) 都用它。

★ **这正是他们自己在 `engine.c:650` 修过的同一个缺陷**（注释原文："两处'条数'不一致导致…判据被静默跳过"）。当时修的是 SHM 侧 `N_ROUTES`，**C 全局这一半漏了**。

★ 另外 `h_persist_w2` 手里就有 `PersistInfo_t info`（`persist_probe` 已填 `n_routes`），**却没用它** —— 而 `0x43` 的 `r[1:2]` 语义应是"**持久化的**条数"，用当前 ACTIVE 数本就是错的。

**影响**：上位机读"程序装了几条/落盘几条"会得到错值（本次 128 而非 8）。工具当前主要在上电恢复路径用它（那里是对的），所以没暴露。

**修法**：`h_deploy` 成功后同步 `g_active_routes`（或**统一以 SHM `N_ROUTES` 为唯一来源**，C 全局降级为纯观测）；`h_persist_w2` 的 `r[1:2]` 改用 `info.n_routes`。

## 6. 我自己的两处更正（必须记录）

### 6.1 ★ BRR 错 16 倍是**我上一轮漏掉的 P1**

上一轮我读到报告 §2.1 的 `BRR = round(PCLK2 × 16 / baud)`、复核了寄存器 `0x3641` 与公式一致，**却从未质疑公式本身**。而这条公式的注释正是一条**"自洽的假验证"**：

> `100MHz × 16 / 115200 = 13889 = 0x3641`, 误差 0.0004%

数字算得没错，但那是 **16 倍分频**的值（OVER8=0 时 `BRR = fCK/baud = 868 = 0x364`）。实际波特率变成 **7200 而非 115200**。**我的长期记忆里就记着这条教训**（"注释里的自洽假验证最危险…把错误锁死了三轮排障"），我仍然漏了。

**教训**：复核"数值与公式一致"不等于复核"公式正确"。**公式必须回到权威定义（RM0468 USART BRR 一节 / OVER8 位语义）**。

### 6.2 我"CH340 未接线"的归因是错的

上一轮我据"LA 在 PA9 上看到真实 UART 波形 + PC 收到 200 字节全 0x00"推断 **CH340 的 RXD 没接 PA9**。**错了**：

- 他们随后实测确认 H1 脚位并跑通**全双工回声**（`H723ECHO` × 5 全部原样返回）—— **接线一直是对的**
- 而"LA 有波形 + PC 收到全 0x00"这个组合，**波特率差 16 倍**就能完整解释（对端以 115200 采样 7200 的信号 → 解出连续 0x00/乱码）
- 我当时排除了"接线"，却没把 **"波形存在但解码全错"** 指向波特率 —— 这是**只考虑了"通/不通"两种状态，漏掉了"通但参数不对"这第三种**

**教训**：外部仪器给的是"信号存在性"，PC 给的是"内容正确性"。两者矛盾时，**"参数不匹配"与"接线问题"是并列候选**，不能只挑一个。

### 6.3 我本轮一个候选被**证伪**

我怀疑 `eng_valid_addr` 的白名单上界 `0x40025000` 过宽（H7 的 APB2 在 `0x4001_FFFF` 结束，`0x4002_0000+` 未映射）→ 会 BusFault。**实测证伪**：`0x20` 读 `0x40020000` 返回 **ACK + 0**（H7 对保留区返回 0，不触发 Fault）。宽松但无害，降级为 P3 提示。

## 8. 结论与建议

**这一批的工程质量整体很高**：5 个套件全绿（12/26/27/13 + 零警告），且**掉电判据、Sequencer、Force 都带阳性/阴性对照**——对上一轮"判据恒真"的批评是**结构性回应**（不只是补一个用例）。基础修复（A1/A3/A4/A5 + H1-H11）全部落地且大多比建议更彻底（`NVIC_ISER` 名字直接删除、`LSYM_ADDR` 宏化、`build.sh` 每次显式传全默认值 + 零警告闸门、`DCL_CAP_H723_NOTYET` 断言）。

**要收的三条（按序）**：

| 序 | 动作 | 成本 | 理由 |
|---|---|---|---|
| **1** | **修 `h723_w1.py:128`** 的 `bytes(buf[1])` → `buf[1]` | 一行 | 否则 **W1 六条命令至今没有任何验证证据**；且它的失败信息会把排查引向"串口/固件" |
| **2** | **修 W1 的 6 项判据**（S5 预算算错 + S2 用错量 + S1b 非对齐 + R2 未考虑覆写 + R9 地址没越界） | 小 | 其中 S5 与 `h723_persist.py` T24 **自相矛盾**——两个工具对同一件事给出相反期望，必须统一 |
| **3** | 修 C（写 `OFF_CTRL_MAGIC`）+ D（`0x38`/`0x43` 条数改用单一来源） | 几行 | D 是他们**自己修过一半**的缺陷的另一半；C 是"定义了却不设置"的死字段 |

**流程建议**（针对"先开发后审查"这个模式）：这次的教训不是"不该先开发"，而是**"验证工具本身也需要一道闸门"**。建议加一条最低成本的自检：**每个验证脚本开头的 T0 类判据，必须在"故意断链"时失败、在"链路正常"时通过**——换言之，给工具自己也配一个阳性对照。`h723_proto.py` 的 T3b/T4b 已经这么做了，把那个模式推广到每个工具的 T0 即可。
