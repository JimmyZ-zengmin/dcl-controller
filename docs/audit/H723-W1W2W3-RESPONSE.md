## 1. A（P2）`h723_w1.py` 类型 bug —— 已修 + 加闸门

### 1.1 确认与修复

```python
# 原 (tools/h723_w1.py:128)
return bytes(buf[1]), bytes(buf[4:need - 2])     # bytes(0x00) = b"" → b"" != 0 恒真
# 修
return buf[1], bytes(buf[4:need - 2])            # buf[1] 本就是 int
```

复核行为（Python 实测）：

```
bytes(0x00) = b''        → b'' != 0  → True   ← ACK 帧被判为"非 ACK"
bytes(0xFF) = 255 字节零 → 也不是 0xFF         ← NAK 帧同样解不出
⇒ T0 判据恒 FAIL，工具 return 2，后续 40+ 项判据一行都没执行过
```

### 1.2 ★ 不只修 bug，加了一道**工具自检闸门**（采纳审计建议）

审计建议"给工具自己也配一个阳性对照"。已落地为 T0c：

```python
# T0 通过后立刻验证"sts 判据真的能失败"
s_bad, _ = L.xact(0x7F)          # 未实现命令 → 固件应回 NAK
record("T0c ★工具自检: 未实现命令(0x7F)必须回 NAK (证明 sts 判据能失败)", s_bad == STS_NAK)
if s_bad != STS_NAK:
    print("!! sts 判据不可信 —— 后续判据的 FAIL 不能归因到固件。提前终止。")
    return 2
```

**它为什么能防住 A 这一族**：A 的本质是"sts 的解析通道退化，但判据照跑"。
无论退化形式是恒 `b''`、恒 ACK 还是别的，只要 ACK/NAK **不能双向可辨**，T0c 就当场失败
—— 而不是让后面 40 条判据白跑、再把人引向"串口/固件"。

实测输出：
```
[PASS] T0c ★工具自检: 未实现命令(0x7F)必须回 NAK (证明 sts 判据能失败)   sts=0xFF (期望 0xFF=NAK)
```

## 2. B（P2）W1 的 6 项判据 —— 逐条处置

| 项 | 审计判定 | 处置 |
|---|---|---|
| **S5** 预算 | 工具算错（128×140=17920 < 26000），且与 `persist.py` T24 **自相矛盾** | 见 §2.1 |
| **S2** 用错量 | 读的是 `g_isr_n`（拍中断），STOP 不停拍 | 见 §2.2 |
| **S1b** 非对齐 | 读 `shm+0x0D`（u8）被守卫正确拒绝 | 改读对齐字 `0x0C` 取 bit8 |
| **R2/R2b** 覆写 | `WIRE_MAP[0]` 被引擎每拍覆写 | 改**先 STOP** 再测写路径 |
| **R9** 没越界 | `shm+0x7F00` 读 64 字**恰好落在** `SHM_SIZE=0x8000` 内 | 改读 **128 字** → 跨出 0x100 |
| **R1** MAGIC | 归因到固件 | 由 C 项修复覆盖 |

### 2.1 S5 —— 把"不可能失败的判据"改成**具备可失败性**

原判据期望"超预算 → START 被拒"，但 128×140 = 17920 < 26000，**门根本不会触发**
⇒ 该判据**测的是一件不会发生的事**，永远 FAIL。而 `persist.py` T24 早已记录同一算式。

处置不是"删掉它"，而是**反过来写**：

```
最贵可装程序: 128 条 × 140 cyc = 17920 cyc  vs  预算门 26000
⇒ 17920 < 26000 ⇒ 预算门不被触发
[PASS] S5 ★F11 预算门不具约束力: 17920 < 26000 ⇒ START 应 ACK (可失败)
```

**这样"我知道门不触发"从一句断言变成一条能被推翻的判据** —— 若实测被拒，说明预算模型与
固件不一致，那才是要查的。（比 T24 的"如实标注"更进一步：T24 只标注，这里做成了正向判据。）

### 2.2 S2 —— 换用正确的量，并把"曾经的错误"变成**正面判据**

审计指出根因：`0x38 r[0:4]` 是**拍中断**次数，STOP 只关引擎门、ISR 照跑。
更深的根因是：**"引擎在不在跑"当时在外部根本不可观测**（HEARTBEAT 字段恒 0，见 C 项）。

C 项修好后，S2/S3/S4 改用 HEARTBEAT，并**新增一条对照判据**：

```
[PASS] S2  STOP 后引擎心跳停止 (HEARTBEAT 不增长)        HEARTBEAT 0→0
[PASS] S2b ★对照: 同时刻拍中断数仍在增长 (证明两量语义不同)  samples 39372→43480
[PASS] S3  START 后引擎心跳恢复增长                    HEARTBEAT 3038→7076
[PASS] S4  二次 START 幂等 (HEARTBEAT 不回退, OA13)    h4=7076 → h5=8148
```

**S2b 是把"审计指出我用错了量"这件事本身变成了一个正面判据** —— 它同时证明
① ISR 活着（不是"因为整机死了所以不动"）② 两个量语义确实不同。
两个量成对使用可区分三种状态：

```
samples↑ HEARTBEAT↑   → 引擎在跑
samples↑ HEARTBEAT=停 → ISR 在跑但引擎已 STOP（正常停机态）
samples=停            → ISR 都没了（固件死了/未启动）
```

## 3. C（P3）MAGIC 未写 —— 已修，并**系统化查出另 10 个同类死字段**

### 3.1 单点修复

写在 `cold_start_reset()`（**单一入口**）而不是 main 里写一次：

```c
void cold_start_reset(void) {
    memset(g_shm, 0, sizeof(g_shm));
    SHM_U32(g_shm, OFF_CTRL_MAGIC)   = CTRL_MAGIC;          /* 'DCL1' */
    SHM_U32(g_shm, OFF_CTRL_VERSION) = SHM_LAYOUT_VERSION;
}
```

**为什么必须在单一入口**：`cold_start_reset` 是"清零的唯一入口"（本项目既有纪律），
main 上电 / `0x13 RESET` / `engine_fill_tables` / deploy 装载**都走它**。
若写在 main 里，一次普通 RESET 之后 MAGIC 又变 0 ⇒ "SHM 已就绪"这个外部判据
**在一次 RESET 之后就不成立了**，而 PC 只看到"读到 0"。

已验证清零路径完整性：全 `src/` 只有一处 `memset(g_shm, ...)`（在 `cold_start_reset` 内），
三处调用（`engine_fill_tables` / `h_reset_w1` / `main`）全覆盖。

### 3.2 ★ 把审计的单点发现做成**自查**，发现另 10 个死字段

写了一个正则自查（扫"宏是否被用于赋值左侧"），结果：

```
只定义/从不写入的字段 (11 个):
  OFF_CTRL_MAGIC, OFF_CTRL_VERSION, OFF_CTRL_HEARTBEAT,
  OFF_TIMING_SAMPLES, OFF_TIMING_PERIOD_MIN, OFF_TIMING_PERIOD_MAX,
  OFF_TIMING_EXEC_MIN, OFF_TIMING_EXEC_MAX, OFF_TIMING_LAST_PERIOD, OFF_TIMING_LAST_EXEC,
  OFF_CTRL_GPIO_MASK
```

审计只报了 MAGIC 一个，**实际有 11 个**。逐条定性并处置：

| 字段 | 定性 | 处置 |
|---|---|---|
| MAGIC | 该写没写 | ✅ 写（就绪判据） |
| VERSION | 该写没写 | ✅ 写（字段语义版本，回答"我认不认得这块 SHM"） |
| HEARTBEAT | 该写没写 | ✅ 写（引擎拍计数，在 `gate && RUN` 内递增） |
| TIMING × 6 | 权威数据在 C 全局，SHM 区是**镜像** | ✅ 主循环周期同步（让 PC 一条 burst 取走整个计时视图） |
| GPIO_MASK | **语义未定**（见 H） | ⛔ 不写 + 观测 + 断言（宁可不做，不做错的） |

**这一条比审计原发现更重要**：它说明"定义了却没人写"不是孤例，而是一类。
若无这次系统化，剩下的 10 个会在将来某天以"为什么这个字段恒 0"的形式重新冒出来。

## 4. D（P3）条数双来源不一致 —— 已修（三处）

**根因**：同一个量有两个来源且更新时机不同
- SHM `N_ROUTES`（ISR 真正扫的）—— 由 `engine_stage_program` / reload / fill_tables 更新
- C 全局 `g_active_routes` —— **只在启动/reinit 更新，deploy 路径漏了**

修复（**统一以 SHM 为唯一权威**）：

| 位置 | 原 | 改 |
|---|---|---|
| `h_engine_status` r[20:22] | `g_active_routes` | **SHM `N_ROUTES`**（ISR 真正用的那个） |
| `h_persist_w2` r[1:7] | `g_active_routes` + SHM 参数数 | **`info.n_routes/n_params/n_states`** |
| `g_active_routes` | 两处更新 | 降级为**纯观测面** + 主循环周期重扫 |

**`0x43` 的语义修正尤为重要**：它是 PERSIST_STATUS，该回答"**flash 里持久化了几条**"，
而不是"当前 ACTIVE 表有几条"。两者在"deploy 了新程序但还没落盘"时会**合法地不同** ——
报当前值等于**谎报持久化状态**（PC 会以为新程序已经存好了）。
`persist_probe` 已经填好了 `info.*`，直接用即可，不依赖任何内存全局的新鲜度。

**为什么 `g_active_routes` 不直接复制 SHM 值**：它是 SHM `N_ROUTES` 的**独立旁证**
（真去扫表的 flags 数出来），复制就失去校验意义。改为周期性重扫 ⇒ deploy 热切表后
它会自己追上，不需要在 deploy 里猜"ISR 什么时候切完"（那个时机由 ISR 决定，上层猜不准）。

### 4.1 实测验证（串口 COM14，本轮）

审计方提供的探针 `docs/audit/audit_probe_w1w2w3.py --port COM14` 复跑结果：

```
SHM base = 0x20008180
deploy 8 条 DIRECT -> ACK=True

SHM  N_ROUTES (真相)     = 8
0x38 r[20:22] (引擎报告) = 8      ← ★ 修复前是 128 (陈旧)
0x43 r[1:2]   (persist)  = 0      ← 尚未落盘, "持久化 0 条"是**正确**答案
```

★ **但探针仍判 PASS，且打印"0x38/0x43 报陈旧值"—— 这条判据已过时**：
它写死了"两者与 SHM 不一致"这个**修复前**的现象，于是修复后依然 PASS。
它**不具备区分力**（不能分辨"128 陈旧"与"0 是正确的持久化条数"）。
这正是本项目一直在批评的那类判据 —— 我们用它的输出作为证据，但**不采信它的判定**。

补充验证（探针未覆盖、且能区分真伪）—— 落盘前/后对比：

```
【落盘前】SHM=8   0x38=8 ✓(==SHM)   0x43=0 ✓(未落盘, 持久化条数本就是 0)
落盘请求(0x43 mode=1) -> ACK, 耗时 0.84s
【落盘后】0x43 = 8 ✓  ← 报的正是"持久化了几条"
```

这就是 D 项两处修复都能被区分的证据：`0x38` 跟随 SHM，`0x43` 报 flash 里的条数。

### 4.2 ★ 顺带发现：`0x43` mode=1 的 ACK 延迟 = 擦除耗时

第一次测时用默认 `timeout=0.6s`，收到超时 → 脚本判"NAK"。**但 flash 里确实已经写好了 8 条**。

⇒ 事实：**`0x43 [mode=1]` 的 ACK 要等擦除完成，实测 0.84s（可达数秒）**。
PC 侧 timeout 必须 ≥ 4s，否则会把"正在擦除"误判成失败 —— 又是"**命令没回 ≠ 命令没做**"。
已写入 `src/transport.h` 的 `CMD_PERSIST` 注释（PC 侧须知）。

（对照：`h723_persist.py` 走 pyocd 直写 `g_persist_req`，不受串口 timeout 影响，
所以此前没暴露这个事实。）

## 5. E / F / G / H（P3）—— 处置

### E 寿命数字：已更正 + **声明 3 项未做的事**

`persist.h` 原写"扇区寿命 **10 万次**量级"，ST 标称 H7 Flash endurance 是 **10 kcycles**（差 10 倍）。
已更正，并**如实声明当前没有做的三件事**（避免读者以为有）：
- 无磨损计数、无寿命告警、无坏块管理
- A/B 轮换是**朴素均衡**（写 seq 小的那份），高频落盘时两扇区同步磨损 —— 不构成磨损均衡
- 每次落盘擦整个 128KB（H7 最小擦除粒度），无法只擦用到的 6KB

结论（32 位 seq 不回绕）仍成立，但**余量比原注释说的小 10 倍**，这点必须如实。

### F `flash_lock()` 漏在失败路径：改为**单一出口**（结构性）

不是"在三个 return 前各补一句"—— 补三句只修好今天已知的三条路径，
明天新增第四条 return 同样会漏，**缺陷的类别没被消灭**。改为：

```c
    if (r != FL_OK) { ...; goto out; }
    ...
out:
    flash_lock();          /* 成功/擦除失败/写失败/回读失败 都落锁 */
    return r;
```

新增任何失败分支都自动经过 `out:`，漏不掉。（同族做法：`build.sh` 每次显式传全默认值、
`DCL_CAP_H723_NOTYET` 的断言。）

### G 注释数字：已更正

原注释"最贵原语 **145** cyc = 18560"，实际 `OP_COST_MAX_MEASURED = 140`（128×140 = **17920**）。
**注释数字与常量不一致本身就是一种"自洽的假验证"** —— 读者复核"145×128=18560"算得没错，
于是不会再去质疑 145 这个**输入**是不是当前值（与 BRR 那条"算得对但公式错 16 倍"同族）。
已改正并写成引用常量名的同源表述。

### H GPIO 掩码：**不执行错语义** + 加观测面

原实现 `mask >> (p*2) & 0xFFFF` 每 port 只取 **2 位**，而每 port 有 16 引脚 —— 语义对不上。
根因：掩码需覆盖 GPIOA..GPIOK 共 11 port × 16 pin = **176 位**，`u32` 装不下。

**处置原则（宣称必须等于实现）：宁可不做，不做错的。** 保留一个已知错误的位映射比什么都不做
更危险 —— 一旦有人往 GPIO_MASK 写值，它会**去清错误的引脚**，把安全功能变成事故源。

改为只做观测：

```c
if (mask) g_safe_mask_nonzero++;     /* 非 0 ⇒ 有人写了未定语义的字段 ⇒ 必须查 */
```

`g_safe_mask_nonzero` 是"该字段当前不可达"这个**否定性声称的外部证据**：它恒 0 ⇔
从没人写过 GPIO_MASK。**按本项目纪律，否定性声称同样需要可被核对的证据。**

接真实 GPIO 前的**前置条件**（二选一，必须先定案）：① 扩成 u32[6]；② 明确"只支持 GPIOA" + 断言。

## 6. 我方接受的 3 处更正

### 6.1 "CH340 未接线"—— **我在全景图里的归因也是错的**

我在 `docs/PANORAMA-2026-09-11.html` 写了"PC 侧串口全程未接线 → W1/协议层验收未闭合"。

1. **`h723_w1.py` 自身的类型 bug**（A 项）→ T0 恒 FAIL → 我据"T0 链路不活"推断"串口没通"
2. 更早的 BRR 波特率错 16 倍 → "LA 有波形 + PC 收到全 0x00" 被误读成接线问题

**我漏掉的第三种状态**：我当时只考虑了"通/不通"，没有把"**通但参数不对**"作为并列候选。
外部仪器给的是"信号存在性"，PC 给的是"内容正确性"；两者矛盾时，"参数不匹配"与"接线问题"
是**并列候选**，不能只挑一个。

已更正全景图（见 §7）。

### 6.2 BRR 错 16 倍 —— 我在上一轮同样漏掉了

审计 §6.1 的自我更正对我同样适用：我当时复核了 `BRR = round(PCLK2 × 16 / baud)` 与寄存器

公式必须回到权威定义（RM0468 的 USART BRR 一节 / OVER8 位语义）。

### 6.3 结论：这次的真正教训不是"不该先开发"
