# 迁移保真度审查报告 — 对照老范本 `esp32-core0`

日期: 2026-09-11 · 被审: `9.10 H723newest`
对照范本: `esp32-core0`（ESP32-S3，成熟 / 15 轮外部审计 / 30 套板上 + 34 项离线回归）
审查目标: **理念是否相同、可靠性是否降低**（不要求逐字相同）

---

## 0. 一句话

**原语层 19/19 逐字一致、协议/Modbus/宏 VM 的语义与边界可逐条对上、多处防护比范本更强**
（回读校验 / 单一出口加锁 / A-B 双副本 / pc 越界检查 / MB_TX_SIZE 拆分）；
但**有一条范本里被定为 P1、修好并有实机判据的核心可靠性不变量，在迁移线上以新形态失守**，
另有**三处"同址反义 / 迁址 / 越界"级缺陷**，以及**一条被判据掩盖的空判据**。

## 3. 一级发现（必须修）

### #1 ★★★ 停机安全态在**真实输出**上失守 —— 范本里被定为 P1 的不变量

**范本的不变量**（`AUDIT-dcl-plc.md` P1-2，已修 `959b0dc`，T23 实机判据 `1/0/1/0`）：
> 「CMD_STOP / CMD_RESET 只清 ENGINE_RUN 和计时区，**不清 GPIO 输出寄存器**……
> **执行器不会断开**。工业语义下「停机」默认应进入安全态，否则 STOP 之后电机/阀门/加热仍在动作。」

**H723 现状**（三条叠加）：
1. ISR **不再驱动任何物理输出**：范本每拍 `apply_gpio(act, 64)`（`core0_isr.c:279`），
   H723 只写 SHM 数组 `ac[ai] = res`（`engine.c:276-277`），**全 ISR 无 actuator GPIO 写**。
2. 安全清位**被明确停用**：`eng_outputs_safe()` 把 GPIO 清位降级为"只观测"
   （`engine.c:1044-1067`，因 H723 是 11 port × 16 pin = 176 位，u32 掩码语义不成立）⇒
   `OFF_CTRL_GPIO_MASK` 恒 0、那段代码**不可达**（H723 自己注明）。
   ⇒ **H723 目前没有任何"停机清物理输出"的实现**。
3. **但 H723 新增了真实物理输出**：`hil_tick()` 在**主循环无条件**（不在 `gate && RUN` 内）
   每 10ms 把 `WIRE[20]` 写进 **`TIM3_CCR1`**（真实 PWM，PA6）(`main.c:2369` / `hil.c:62-69`)；
   而 `h_stop_w1` 只归零 ACTUATOR 数组、**不碰 TIM3**（`main.c:1544-1556`）。

⇒ **STOP 之后：引擎停扫 ⇒ `WIRE[20]` 冻结 ⇒ PWM 保持最后占空比不动，且 `hil_tick` 仍在回写它。**
**"停机 = 进安全态"在 H723 的真实执行器上不成立。**

**为什么回归没抓到**：范本的 T23 判据读的是 **ESP32 的 GPIO 寄存器 `0x60004004`**，
在 H723 上被标为 N/A ⇒ **新输出面没有对应的停机安全判据**。

**建议**（三处，缺一不可）：
① 给 HIL 加安全态：STOP/RESET ⇒ `TIM3_CCR1 = 0`（并回写 `OFF_HIL_DUTY` 镜像，保持"写过的状态必须可读走"）；
② 把 `eng_outputs_safe()` 的契约改成"覆盖**全部**物理输出面"，并在其中显式调用 HIL 安全态
   （否则下次再新增一个输出面又会漏 —— 把纪律变成结构）；
③ 补一条**平台等价判据**替代 N/A 的 T23：START→输出非零 → STOPE→输出归零 → 恢复；
   证据用 `OFF_HIL_DUTY` 镜像（零接线可验）+ LA 抓 PA6（有 LA 时）。
④ 顺带：`engine_route_validate()` **缺**范本的两条 actuator 校验
   （`actuator_idx>=32` 拒绝 / 受保护引脚拒绝，`core0` 的 `main.c:338-342`）⇒
   部署带执行器的程序会"配置被接受但物理无输出"。要么补校验，要么明确 `actuator_idx` 在 H723 的**新语义**
   （仅 SHM 浮点槽，不是物理脚）并写进能力声明。

### #2 ★★★ `0x08` / `0x18` 两个 SHM 量**同址反义**（+ 注释把错误锁死）

**范本**（`core0_isr.c:352-358`，**本人复核**）：
```c
/* OA14: 心跳必须在 run 门外无条件翻 — 停机也翻 (外部可观测 CPU+定时器存活) */
SHM_U32(OFF_CTRL_HEARTBEAT) += 1;
if (!run) { s_last = t_entry; return false; }   /* OA13: STOP 冻结统计 */
SHM_U32(OFF_TIMING_SAMPLES) += 1;
```
⇒ **范本：HEARTBEAT = 每拍无条件（STOP 也翻）；SAMPLES = 仅 RUN 拍**。

**H723**：`g_isr_n`(samples) 在 ISR 尾部**每拍都加**（`main.c:711`，今天的容量测量实测确认：
STOP 态 samples 仍在涨）；HEARTBEAT 只在 `gate && RUN` 内（`main.c:663`）⇒ **恰好对调**。

**更糟**：H723 的 `engine.h:75-79` 注释写着"S3 的 samples STOP 后仍增长" —— **与范本源码相反**。
这正是本项目最怕的"**自洽的假验证**"：注释算得对、读起来顺，却把错误锁死了。

**影响**：任何按"心跳看存活 / samples 看本次运行段"读的外部工具在 H723 上**语义互反**；
且 `test_dcl.py` 的 T1/T9/T15 都依赖二者语义（它们之所以还能过，是因为
"samples 会随 RESET 清零"这一点两侧相同 —— **巧合掩盖**）。

**建议**：按范本语义实现（`0x18`=RUN 拍数，另设字段承载 ISR 计数），或**改址并抬
`SHM_LAYOUT_VERSION`**，同时**订正注释**。二者择一，不能维持现状。

### #3 ★★ FORCE 迁址 —— 迁移理由被老工具**直接证伪**

`engine.h:225-227` 宣称"没有任何 S3 工具按绝对偏移读 force"，据此把 `FORCE_MASK/VAL`
从 `0x3A00/0x3A10` 迁到 `0x47F0/0x4800`。**本人复核：该宣称是假的** ——
`tools/verify_force.py:50` 直读 `shm + 0x3A10`，`:109` 直读 `shm + 0x3A00`。

⇒ "S3 脚本一行不改"这个承诺在 force 这条判据上**已经破了**：老脚本会读到 H723 的保留洞（恒 0），
判据静默误判"未强制"。

**建议**：把 force 放回 `0x3A00/0x3A10`（范本偏移是**对外契约**），或把 `verify_force.py`
列入"必须改址"清单并在 README 显式声明破例。**不能维持"宣称未破"的现状。**

### #4 ★★ div2 相位分配越界 ⇒ **两条建桶路径互相矛盾**（迁移引入）

- `period` 是 **u8**：bits[1:0]=div，bits[7:2]=**phase（6 位，0..63）**（`engine.h:511-512`）。
- 范本的相位受 6 位约束（`shared_mem.h:185` 明写 `phase 0-63`），div2 桶表是 100 槽但 **64..99 是空表**
  （范本建桶器也读 `period` 的相位：`core0_isr.c:465-466`，`ph<100` 是恒真的死条件）⇒ **范本自洽**。
- H723 在 T17 修正把周期改为 100 拍后，**把"周期"与"相位分配模"混为一谈**：
  `engine_stage_program` 用 `ph = q2++ % BUCKET_DIV2_PHASES`（**=100**）定槽 `cur2[ph]`，
  再把 `ph << 2` 写进 u8（`engine.c:884-885`）⇒ **`ph≥64` 截断**（64<<2=0x100 → &0xFF=0）。
- 而 `engine_build_buckets`（另一条构造路径）按 `period` 的相位归组（`engine.c:346-347`）
  ⇒ **同一份程序经两条路径产出不同的桶**；且**违反死槽不变量**
  （H723 自己的断言宣称 `off2/cnt2[64..99]` 恒 0，而 deploy 会往 64..99 里填路由）。

**影响**：路由的**执行相位由槽决定**（运行行为基本仍对，≈10ms），但
① `period` 记的相位是垃圾 ⇒ 任何"按 period 反推桶"的独立校验必错；
② 死槽判据/桶校验和与独立预测不符 ⇒ **桶表类判据可能假红/假绿**；
③ 现有没有用例覆盖（T17 只有 1 条 div2 ⇒ phase=0 不触发）。

**建议**：把"**周期数**"与"**相位模**"分成两个常量（范本本来就是分开的），
相位分配用 6 位域上限（64）；或把 phase 挪到 `RouteEntry_t` 的空闲字节（`reserved`）以支持 100 相位。
并补一条"div2 路由数 > 64"的回归。

## 4. 二级发现（应修）

### #5 ★★ `ov`（超预算计数）恒 0 ⇒ S3 套件 **T9 的一半是空判据**
`test_dcl.py:283` 的 T9 判据含 `s9["ov"] == 0`；而 H723 `main.c:1366` 是
`put32(r + 27, 0u);  /* overrun: H723 暂未实现超预算计数 */` ⇒ **这一半不可能失败**。
⇒ 我们汇报的"S3 套件 22/30"里，**T9 是打折的**（范本用该量做 A5 超预算早期告警）。
**建议**：实现 overrun 计数（ISR 已有 `t_exit-t_entry` 与预算，成本极低），
或在 0x38 用能力位**显式声明不支持**（而不是填 0 冒充"没超预算"）。

### #6 `0x3854` TICK_STATS 语义漂移
范本：本拍该档有路由执行则 **+1（拍计数）**（`core0_isr.c:275-277`）；
H723：`+= 桶内条数`（`engine.c:556/559/562`，**条次**）。两者仅在"同相位多条"时分叉，
而 T17 用例恰好落在重合分布上 ⇒ **潜伏漂移被巧合掩盖**。且 `engine.h:189` 声称"照 S3"与事实不符。
**建议**：二选一并在 `engine.h` 写明真实语义。

### #7 确定性可被一个外部旋钮**关闭**
扫描体是**函数指针**调用（`main.c:607-614`），`g_engine_sel` 可被 pyocd 运行期改写；
`sel=0` 时拍内取指走 FLASH + L1 I-cache ⇒ **拍长随缓存历史漂移**。
范本全部 `IRAM_ATTR`，无此路径。默认（`BOOT_SEL=1`）安全，但"拍内确定性"成了**可关闭**的性质。
**建议**：把该旋钮编译期化，或在其被置 0 时点亮一个"确定性已关闭"的可读状态。

### #8 桶扫**丢了 `nr` 上界**（纵深防御少一层）
范本三重保护：`if (run)` + `if (nr>0)` + 循环内 `i<nr`；H723 只有 `gate && RUN`（`main.c:592`），
桶扫仅靠 `engine_scan_*` 内夹取 `MAX_ROUTES`。正常路径无碍，但桶计数一旦失真，
H723 会扫到 `nr` 之外的残留 ACTIVE 行，范本不会。

### #9 `OP_COST_DIV2 = 64` 与周期 100 的**语义混用**（+ 注释残留）
`engine.h:524` 的 `OP_COST_DIV2=64` 是**预算摊薄系数**（保守方向，安全），
但 `engine.c:466`/`engine.c:645` 注释仍写"64"，而 `BUCKET_DIV2_PHASES=100`。
当前后果为零（该门不具约束力），但**后人照注释把宏改回 64 就会重演 H9**（周期变 6.4ms）。
**建议**：注释改为引用宏名 + 在 `OP_COST_DIV2` 处写明"保守取 64，真实周期 100"（与 #4 一并处理）。

## 6. H723 **比范本更强**的地方（理念在加强，需一并记录）

- **persist 全面加固**：A/B 双副本 + 单调 seq（擦除中掉电不丢）+ **整段回读校验**（范本无回读）
  + **单一出口 `flash_lock()`**（范本无 flash 层）+ 状态表**先清零再拷**（M2）+ 落盘快照与 SHM 解耦
- **macro VM 加固**：pc 越界检查（范本无）、裸地址限 SHM 窗口（范本可任意地址）、
  出错**自停不刷错**、未实现 op 返 -4 显式拒绝
- **Modbus 加固**：`MB_TX_SIZE` 与 `MB_MAX_FRAME` **拆成两个语义常量**（修掉范本的 P1 形态）
  + BUILD 未完成保护（丢帧计数 + 回 IDLE）
- **transport 加固**：`_Static_assert` 保证能力位 impl∩notyet 为空；保留码 `DCL_RESERVED`
  机器可读标记（落 default 显式 NAK）
- **uart 加固**：RX 环形缓冲满**丢弃并计数**（不覆盖）；**逐标志**清 PE/FE/NE/ORE 并计数
- **SHM 断言密度更高**：把范本的手写常量断言升级为 `==` **精确相接**断言，另补"ctrl 块不越界"、
  "deploy 字段精确填"、洞穴尺寸哨兵、桶死槽判据、预算绊线断言
- **`engine_fill_tables` 的"填表不改运行态"**：修掉范本同族风险（范本 `core0_engine_start` 只逐字段清一次，无运行期整段 memset）
- **新增能力**：Modbus RTU / 顺序域(Sequencer) / macro VM / DI·AI·HIL —— 范本侧对应项在能力位上是 0/留位

## 7. 顺带发现的**范本自身的债**（不影响 H723，但值得回填）

1. ★ 范本 `shared_mem.h:150` 的 `MB_MAX_FRAME=128` **一个常量两用**（请求上限 + 响应组装界限，
   `modbus.c:267`）⇒ 合法 `qty≥63` 的读请求即可让通信域**永久 busy**。
   H723 已按"两个语义不同的量必须两个常量"拆开 ⇒ **老范本这一侧未回填**。
2. 范本的 `apply_gpio` 只覆盖 GPIO0-31（位图 u32），而 `MAX_ACTUATORS=64` ⇒ 32..63 静默无效；
   范本后来在**校验侧**补了拒绝（`main.c:338-342`），但驱动侧仍是 32 ⇒ 属于"校验拦住了、实现没扩"。
3. `period` 的 phase 只有 6 位而 div2 桶有 100 槽（空表无害，但设计口径不一致）。

## 9. 建议的收口顺序（按"可靠性收益 / 成本"排）

| 序 | 项 | 为什么排这个位置 |
|---|---|---|
