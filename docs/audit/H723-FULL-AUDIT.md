## 一、轴 1: 判据可失败性

### F1 (P2, 已修) 链路活性判据用「有没有字节」而不是「内容匹配」

`tools/h723_audit_m234.py: serial_alive()` 原实现：
```python
d = s.read(64)
if d:
    return True          # ← 有任何字节就算"链路活"
```
**为什么这是缺陷**：噪声、波特率不匹配、打开端口的瞬态**都会产生字节**，但产生不出
"状态字节 = ACK + 长度合法 + CRC 通过"的帧。本项目 BRR 事故就是被这个形态带偏一整轮的
（"AB 两端都收不到"与"时基全错"在 PC 侧表现完全一样）。
**修法**：新增 `h723_client.link_alive()` —— 必须**解析出 ACK 帧**且 **cap 与期望一致**
（cap 一致还额外证明"对端就是这台固件"，而不是别的设备在回话）。
★ 对 M4 的语义没有削弱：核被 halt 时不会有任何合法帧 ⇒ 仍判"死"。

### F2 (P2, 已修) 「阳性对照」判据写死 `True`

`tools/h723_w2_probe.py` 原实现：
```python
record("A' 阳性对照: A 的值确实会因引擎改而不同 (排除'恒等于初值')",
       True,   # ← 字面量常量
       "见 B/C/E/D 的四次值变化")
```
**判据写成常数就等于"不可失败"**，与"A' 阳性对照"这个名字完全矛盾 ——
阳性对照的**全部意义**就是"它能被推翻"。
**修法**：用**已采到的值真算** —— 6 个采样点（A1/A2/B1/C1/E1/D1）里至少出现 **3 个互不相同的值**。

### F3 (P3, 已修) 「先检查后无条件记 PASS」

`tools/h723_w1.py` 的 T0 原形态是：`if 不通过: return 2` → 然后**无条件** `record(..., True, ...)`。
形态上就是恒真。机械审计抓到它**是对的**：只要将来有人把那个 guard 改成 `print` 而不 `return`，
这行会继续报 PASS。
**修法**：把**解析结果本身**当判据（ACK + 载荷够长 + **cap 与期望一致**），失败才 return。

### 附带: 审计工具自己的「自指假阳性」

`h723_audit_full.py` 的 1.1 第一版把 **它自己判据名里那个描述模式的字符串**（`record(...,True)`）
也当成了命中 ⇒ 18 处假阳性，真问题（3 处）被淹掉。
**修法**：扫描前先剥掉**字符串字面量**。
★ 这正是本项目「噪声不清零，真警告必被漏掉」的同一条纪律 —— 审计工具也不例外。

### INFO: 观测面引用率 89/169

80 个固件观测量**没有任何工具引用**。口径说明：**"没人读" ≠ 缺陷**（可能是内部量/预留），
所以这条**只列清单不给判决**。它属于**整洁性债**，建议加一条规则：
**新增观测面必须同时给出消费者（工具或判据），否则不写进 `obs_anchor()`**。

## 二、轴 2: 宣称 = 实现

### PASS: 能力位与实现一一对应

- `DCL_CAP_H723_IMPL` 展开 = **0x0DF7**（10 个位），**每一位都有对应命令被 `proto_dispatch` 派发**
- **未实现的能力位确实没被声明**：`DCL_CAP_STATE_COLD`(0x0008) 与 `DCL_CAP_HMI`(0x0200)
  仍是留位，`impl` 表达式里没有它们 —— **留位 ≠ 实现**，这一点是诚实的

### F4 (P3, 已修) 保留码"看着可用"

`transport.h` 里 `CMD_DISPLAY_INIT/FILL/TEXT`（0x51/0x52/0x53）是 S3 的 ST7735 TFT 命令，
本平台不迁，但**宏留在交付头文件里像已实现**。
**行为本身是诚实的**（落到 `default: nak("bad cmd")` = **显式 NAK 而非 TIMEOUT**），
但使用者容易误读。
**修法**：给这三个宏加**机器可读标记** `DCL_RESERVED`，并让审计工具核验：
「带标记的宏**应当**不被派发；不带标记的宏**必须**被派发」。
⇒ "保留"与"声称已实现"从此可区分，且**这个区分会随漂移被审计抓到**。
（为什么保留号段而不删：这三个码是 S3 协议的一部分，删掉会让他们被将来某个新命令
复用成语义完全不同的东西 —— 同一个码两种语义才是真危险。）

## 三、轴 3: 对端视角

### PASS ×4（全部只看线上字节，不读固件任何内部状态）

| 判据 | 实测 |
|---|---|
| 命令码 **0x00–0x7F 全集**每个码都必须有明确应答 | ACK 9 / NAK 119 / **TIMEOUT 0** |
| 所有应答**帧结构完好 + CRC（独立实现）通过** | 畸形/截断帧 **0** |
| 注入**坏 CRC 帧**后解析器不被毒死 | 坏帧后 `0x01 → ACK` |
| `read_burst` qty 扫**合法区**（1..256，M1 教训：只测"超上限"是盲区） | 11 个取样点全部合规 |

★ 为什么必须独立实现 CRC：S3 审计里"组帧 CRC 覆盖少一字节"藏了 3 轮，**因为一直在固件内部验证**。
★ 为什么扫**全集**而不是只扫已知命令：任何落到"没有 default 分支"的码会变成 TIMEOUT，
而那与"固件挂了"在 PC 侧**无法区分**。

### F5 (P2, 记录未修) `op_needs_wire2()` 对 CNT 过严 —— 与 S3 的行为分歧

**跨线对照发现的**（读 `esp32-core0/AUDIT-dcl-plc.md` 第十三轮 OA1）：

| | S3 结论 | H723 现状 |
|---|---|---|
| `CTU` 不写 `R=` 端 | OA1 判定 `wire2=None`（**无第二输入**）是**正确**编码，`cnt=1.0` ✅ | A3 审计把 `op_needs_wire2()` 从"只拦 AND/OR"补成含 **CNT** ⇒ **拒收**该形状 |

**影响面**：
- 经 `dclc` 编译的程序**不受影响**（阶段6 已由"补一根恒 0 wire"绕过，语义等价）
- 但**直接构造原始帧的客户端**会遇到：同一帧 **S3 ACK / H723 NAK** 的行为分歧
- 为什么一直没被发现：S3 套件里 **从不 deploy `di_demo.dcl`**（它含 `CTU`）⇒ 端到端覆盖缺口，
  直到阶段6 做端到端验收才炸出来

**为什么不改**：A3 的收紧是**有理由**的（拦"漏给第二输入"的静默语义错误），
而 NAK 比"静默接受一个歧义编码"更安全 —— **收紧 > 放宽**。
**本轮动作**：把分歧**显式记录**在这里，不再让它藏在"cap 是超集所以完全兼容"的假设下。
**若将来要精确化**：按 `param.value_a` 的 mode 区分（CTU/CTD 允许 `wb=0`，CTUD 必须给 CD）。

## 四、轴 4: 成本表受控对照

### F6 (P2, 已修) ★★ 复核路径**断了** —— 工具量的是"上一次会话遗留的表"

`tools/h723_op_sweep.py` 的测量链原本是 `reset → 注入 → 读`，**整程没有 `go`**。
而实测（pyocd 0.45.1）:

```
-c reset 之后:  tick 0x7c738  ──400ms──>  tick 0x7c738    ← 核停在 halt, 完全没跑
加 -c go 之后:  tick 0xf91                                ← 才在跑
```

⇒ `main()` 从未执行 ⇒ **表根本没被填过**；读到的全是**上一次会话遗留的 DTCM 值**。
症状：19 个原语量到**完全相同**的 7292、`cyc/条 = 0.00`、工具报 **`0 / 19 原语数据可信`**。

★ **工具拒绝认证是对的**（比"报个 0"好得多）—— 但它让"成本表是实测的"这条宣称
**失去了可复核路径**。这正是铁律 2 存在的意义：*代码一动必须重测*，而重测路径断了就无从谈起。

**修法**：严格三段式（本项目 pyocd 纪律第一条的正向执行）：
`reset → go → sleep(BOOT) → halt`（让 main 跑完 boot）→ 注入 → `go → sleep(dur) → halt` → 读回。
**复测结果**：**`19 / 19 原语数据可信`**，各原语值互不相同且量级合理（PID 占拍 42%、DIRECT 最便宜）。

### F7 (P2, 已修) ★★ 成本表**系统性偏低** —— 差值是「每条恒定 +5~6 cyc」

复核路径修通后，与固件里的表逐项对照：

| 原语 | 旧表 | 重测 | 差 | 原语 | 旧表 | 重测 | 差 |
|---|---|---|---|---|---|---|---|
| DIRECT | 50 | 56 | +6 | LUT | 83 | 89 | +6 |
| CMP | 70 | 76 | +6 | CNT | 78 | 83 | +5 |
| HYST | 74 | 79 | +5 | TIMER | 75 | 80 | +5 |
| CLAMP | 68 | 74 | +6 | ARITH | 68 | 74 | +6 |
| LPF | 91 | 97 | +6 | SCALE | 61 | 67 | +6 |
| **PID** | 140 | **145** | +5 | AND | 71 | 77 | +6 |
| RATE | 62 | 68 | +6 | OR | 72 | 78 | +6 |
| DEADBAND | 70 | 76 | +6 | NOT | 65 | 71 | +6 |
| MUX | 64 | 70 | +6 | SR | 79 | 85 | +6 |
| EDGE | 82 | 87 | +5 | | | | |

★ **判读要点**：19 个原语**全部**只差 5 或 6 —— **不是"某些原语变慢了"**，
而是**扫描循环多了一项常量开销**的指纹（比值 1.036~1.120 只是"常数 ÷ 不同基数"的假象）。

**根因**：表上方的历史注释自己写着「**代码一动就要重测**，否则预算模型用的是上一版代码的数」，
而 **W2~W5 的改动从未回填** ⇒ 违反铁律 2。
**后果**：预算门（`EXEC_DEPLOY_BUDGET = 26000`）用偏小的成本 ⇒ **系统性偏松约 8%** ⇒
"该拒的没拒"，属于 F11（合规程序让设备变砖）风险的同一族。

**修法**：把表回填成**当前实测值**；同步 `OP_COST_MAX_MEASURED` 140 → 145
（`128 × 145 = 18560` cyc = 拍长 **46.4%**，仍低于 26000 的门 ⇒ 门仍不具约束力，
那条"绊线断言"继续通过）。
**方向性**：偏大 = **偏保守**，对预算是安全方向 ✓

**★ 诚实标注（未隔离项）**：造成这个常量项的**具体改动尚未定位**。
表上注释记载"此前 A3 优化曾让全部原语便宜约 10%（DIRECT 56→50）"，
而**现测回到 56** ⇒ 那条优化的效果在当前代码上不再成立。
本轮只做到"确认差异是常量项 + 回填正确值"，**没有**做到隔离到具体改动，因此不写成结论。
隔离方法（留给下次）：用 `-D` 开关逐项排除 W2 Force / W3 顺序域 / W4 通信域 / W5 外设域
在**扫描宏内**加的东西，用同一套两点法对照。

### 新增机械检查 4.3: 常量与表同源

`OP_COST_MAX_MEASURED == k_op_cost_itcm[OP_PID]`。
**为什么需要它**：本项目已经**错过两次**"注释/常量与表各自漂移"（BRR 那条"算得对但公式错 16 倍"
的注释、以及 A3 重测后注释仍写 145 而常量已是 140）。**把这类漂移做成会失败的机械检查**，
比再写一句"记得同步"有用。

## 八、下次改代码怎么复用本次审计

```bash
python tools/h723_audit_full.py          # 12 项机械检查 (离线项 + 在线对端视角)
python tools/h723_op_sweep.py --dur 0.3 --json build/op_cost.json   # 成本表重测 (约 60s)
```

- **改协议/命令** → 轴 2/3 会红（命令↔cap↔dispatch 三方一致性 + 对端帧校验）
- **改扫描/ISR** → 必须重跑 `op_sweep` 并回填表（轴 4.3 会盯常量与表同源）
- **改判据** → 轴 1 会红（恒真判据/字面量常数）
- **改硬件接线利用（如 RTS→NRST）** → 见 `tools/h723_modbus.open_serial()` 的防御说明
