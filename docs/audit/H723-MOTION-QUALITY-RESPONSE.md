   「开漏被数据手册否决（`TT_ha` ≠ FT）」、以及「E4 与 C1 的逻辑矛盾」。这三条我复核过，**成立**。

   它把根因从"驱动能力不足"重新定位到"**供电域与逻辑高电平不一致**"，一步解开两条死路。

2. **更正 D2 的根因**：不是"扫描节拍/分频器按错时钟"，而是 `src/step.c: step_tick()` 里
   **每次调用都做一次 `dt / 10u` 取整**。已用**零运动**实验复现，并给出量化指纹。

## 2. ★★ D2 根因更正：不是时钟错，是**每次调用取整**

### 2.1 为什么原归因不成立

原文 §D2 写：*"1.26× 很像**扫描节拍或分频器按错时钟算的**"*。

**一个恒定的时钟/分频错误只能给出恒定的倍率。**
但你们的实测同时给出两个事实：

- 倍率 **≠ 1**（慢 26%）
- 倍率**随主机轮询密度变化 21%**（1.236 s ↔ 1.504 s，同一个请求）

⇒ **第二条件直接排除"固定倍率的时钟错误"。** 必须是"**丢多少取决于负载**"的机制。

### 2.2 真因（`src/step.c`）

```c
void step_tick(uint32_t tick_now) {
    if (s_sync) { s_last = tick_now; s_sync = 0u; return; }
    uint32_t dt = tick_now - s_last;      /* 拍; 1 拍 = 100µs */
    s_last = tick_now;
    if (dt > 1000u) { dt = 1000u; }
    if (g_step_deadline_tick == 0u) { return; }
    uint32_t dm = dt / 10u;               /* ★★★ 每次调用都取整, 小数被丢掉 */
    if (dm == 0u) { return; }
    if (g_step_deadline_tick > dm) { g_step_deadline_tick -= dm; }
    else { g_step_deadline_tick = 0u; step_stop_safe(); }
}
```

`dt` **不是固定的 1 ms** —— 它是"**本次调用距上次调用的拍差 ≈ 主循环一圈**"。
于是每次调用丢掉 `frac(dt/10)`：

- 累计消耗 **永远 ≤ 真实** ⇒ **只会慢、永远不会快**（与实测方向一致）
- 丢多少 **取决于主循环一圈有多长** ⇒ 主机轮询变 ⇒ 一圈变 ⇒ 倍率变（与实测一致）

### 2.3 零运动实测（本轮新增，可复跑）

**关键设计**：`g_step_deadline_tick` 的递减发生在 `step_tick()` 里，**与 `CC1E` 无关**
⇒ 可以**不开脉冲、不使能、不碰电机**地量它。
⇒ 任何偏差都只能来自"拍记账"，**脉冲通路 / 光耦 / 驱动器 / 编码器全部被排除**。

```
python docs/audit/h723_limit_tick_probe.py 8

  静默(不轮询)   8.01s  消耗 5200 / 应 8013  ⇒  648.9 / 真实秒  (应 1000, -35.1%)  raw漂移 0  CC1E=0  dt_max=684
  密轮询         8.02s  消耗 6332 / 应 8024  ⇒  789.1 / 真实秒  (应 1000, -21.1%)  raw漂移 0  CC1E=0  dt_max=684
                                   差异 21.6%       （两次独立运行: 21.6% / 20.1%）
```

| 判据 | 结果 |
|---|---|
| ① 速率应 ≈1000/秒 | ✗ **648.9 / 789.1** ⇒ 慢，且**从不快** |
| ② 慢的幅度随主机负载变化 | ✅ **21.6%** ⇒ **排除固定倍率时钟错误** |
| ③ 轴完全不动 | ✅ `raw` 漂移 0 ⇒ 与运动无关 |
| ④ `dt_max = 684 < 1000` | ✅ **未撞钳位** ⇒ `if (dt>1000) dt=1000` 不是本次成因 |

**量化指纹（反推主循环一圈）**：若 `dt = 10k + r`（`k = floor(dt/10)`），每秒消耗 `= 1000·k/(k + r/10)`：

| 档 | 实测/秒 | 反推 `k` | 反推主循环一圈 |
|---|---|---|---|
| 静默 | 648.9 | **1** | **15.4 拍 = 1.54 ms** |
| 密轮询 | 789.1 | **1** | **12.8 拍 = 1.28 ms** |

★ **两档都落在 `k = 1`** —— 正是"**每次记 1 ms，而真实过了 1.3~1.5 ms**"的指纹。
（这也解释了为什么是 −35% / −22% 这个量级：1/1.54 ≈ 0.649、1/1.28 ≈ 0.781。）

### 2.4 修法（两行，且比现在更稳）

把"限时"从 **ms 计数**改成 **目标拍号**，用一次减法判到期，**彻底不做除法**：

```c
/* 武装 */  s_dl_armed = 1u;  s_dl_tick = tick_now + ms * 10u;
/* 判据 */  if (s_dl_armed && (int32_t)(tick_now - s_dl_tick) >= 0) { /* 到期 */ }
```

⇒ **无除法、无累计误差、无取整损失、与主循环快慢完全无关**，且不需要 `dt > 1000` 的钳位。
（若只想最小改动：把 `dt/10` 的余数累加到一个静态量里，凑够 10 再记 1 ms。
 但那仍然依赖主循环在跑 —— **拍号方案才是根治**。）

## 3. ★★ D3 机制：**顺序 × 一个值两个语义**

### 3.1 原文只测到现象，没给机制

原文 §D3：*"units ≤10 时根本不生效（2 单位跑了 54°）"* —— 现象准确，**机制缺**。

机制在 `cmd_units` 的**命令顺序**里：

```python
d.limit(units)     # ← 第 1 条帧
d.rate(500)        # ← 第 2 条帧（两条独立帧, 中间隔着主循环）
```

`step_tick()` 在主循环里跑，**与有没有脉冲无关** ⇒ 小限时会在 `rate()` 那一帧到达**之前**就被吃光；
而吃光时走的是 `step_stop_safe()`，它把 `g_step_deadline_tick` 置 **0** ——
**而 0 的语义是『不限时』**（`step_tick` 的 `if (g_step_deadline_tick == 0u) return;`）。
⇒ **紧接着的 `rate(hz)` 就是无限跑**，直到下一条命令 ⇒ 正好是你们测到的"2 单位跑了 54°"。

### 3.2 零运动复现（本轮新增）

忠实复刻那一对命令的顺序，但**全程 `ENA = 0`** —— 这块 TB6600 是「光耦导通 = 失能」，
所以脉冲再多**驱动器也是失能的，轴保证不动**：

```
② `limit(2)` 后紧跟 `rate(20)`, 等 0.35s:
   CC1E=1   tleft=0   stop_n=101(+1)

   ⇒ ★★★ 定案: **通道还开着(CC1E=1) 而限时已经是 0(不限时)**
      · `step_stop_safe()` 在 `rate()` 那一帧到达**之前**就跑过了 (stop_n +1)
      · 它把 tleft 置 0 = 『不限时』(C4) ⇒ 脉冲**不会自己停**
```

### 3.3 与 C4 是同一处

**D2 与 D3 出在同一个函数的两面**：

| | 表现 | 机关 |
|---|---|---|
| **D2** | 限时"变慢"，且随主机负载变 | `dm = dt/10` 每次调用取整 |
| **D3** | 小限时"不生效"，变成无限跑 | `0` 同时表示『不限时』与『已到期』 |

⇒ **§2.4 的那一次修改（限时改成目标拍号 + 独立的 `armed` 位）可以同时收掉 D2、C4、D3 的上游。**

## 4. 两处**工具**判据更正（原文 §8.6 指出，**已修**）

原文 §8.6 点的两条都在我写的 `tools/h723_stepper_test.py` 里。**都确认成立，已改：**

| # | 原判据 | 问题 | 改后 |
|---|---|---|---|
| 1 | `probe od`/`probe af` 报 *"通道关断但 IDR=1 ⇒ AF/通道没真正接到引脚上"* | **假报警** —— 与 E2 直接矛盾：`AF + CC1E=0` 时引脚**本来就是高阻**，`IDR` 被外部上拉读到 1 是**正常**的。判"AF 通路通不通"**必须在有脉冲时判** | 改为 *"✅ AF+关通道 ⇒ 引脚高阻(正常)"*，并指向 `idrwatch` |
| 2 | `safe` 判据写死 *"`PE8~PE11` 全 1"* | 在 `enapol=1` 时 **PE9=0 才是"不导通"** ⇒ 该判据变成一条**永远失败**的判据 | 改为**跟着 `enapol` 走**，并改用 **`IDR`（引脚实际电平）** 而不是 `ODR` |

★ 实测：`enapol=1` 时旧判据必然误报，新判据正确通过。
★ 第 2 条的一般化：**凡是"不导通/安全态"这类判据，只要有效极性可运行期切换，判据就必须跟着极性走**
—— 否则它会在某一极档下**静默变成空判据或永远失败的判据**（本项目已记录族）。

## 5. 对报告其余部分的三条保留意见

1. **§3 方法学错误表第 2 条**（`dir=1 ⇔ 角度增大` 是假设不是约定）
   建议把实测结论**落进代码常量的注释里**（`h723_stepper_motion.py` 的 `dirn()`），
   否则下一个人（或下一个会话）还会重新假设一次。**教训写进报告 ≠ 教训不再发生。**

2. **§8.4(b) 的"上位机天花板 ≈ 1627 °/s²"** 依赖 `CMD_BIAS_S = 0.0553`，
   而 55.3 ms 这个命令通路延时**本身就是 D4 的产物**。
   报告已在 §5 注明"待固件修好后重测"，建议再加一句更硬的：
   > **`CMD_BIAS_S` / `LIMIT_SCALE` 这两个常数不得用于任何验收判据** ——
   > 它们是"当前固件缺陷"的度量，不是系统的性质。

   （★ 本轮已实测：`LIMIT_SCALE` 不仅"不可靠"，它的真因已定案为 §2 的取整 ⇒ 该常数应当**作废**。）

3. **D5（使能回读时序竞争）** 建议固件在应答里**分开给两个量**：
   `target_ena`（我们要求的目标位）与 `pin_snapshot`（引脚快照）。
   现在两者共用一个字段 ⇒ 上位机无法区分"命令没生效"与"读到的瞬间正好在翻转"。

- **未改任何源码**；只改了两处上位机工具判据（§4）。

  下一个"只开通道不设频率"的操作会以 **20 Hz** 起振。顺手可作为该条的现场证据。
