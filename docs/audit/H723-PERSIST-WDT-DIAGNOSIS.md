# 真因定位：**ISR 调用树里有 7 个函数落在 FLASH**

- 送审文档：`docs/audit/H723-PERSIST-WDT-DEFECT.md`（状态：真因未定案）
- 定位依据：`18c4946` 的构建产物（`build/dcl_h723` = 板上固件）
- 日期：2026-09-13
- **判据是静态的：不需要板子、不需要逻辑分析仪，一条 `nm` 就能复跑。**

---

## 0. 结论

真因不是"擦除 stall 取指"这个**泛化**说法，而是**可以逐条列出来的 7 个函数**：

> **拍 ISR 每拍都会走到它们，而它们编译在 FLASH ⇒ 擦除期间取指被 stall ⇒
> ISR 永不返回 ⇒ 拍中断不再触发 ⇒ 喂狗停 ⇒ 200ms 后 IWDG 复位。**

**关键时序**：`wdt_feed()` 在 ISR **第 65 行**（很靠前），而卡点在第 **228 行之后** ——
所以**那一拍的狗喂到了，但那之后 ISR 再也不返回，后续每一拍都不会来**。
这解释了为什么"闲时喂狗计数单调涨、一落盘就停摆"。

**真正的原因是另外 7 个"后来加进 ISR 的新功能函数"。**

七个函数源码里**没有任何段属性**（`void do_poll(...)` / `void di_poll(...)` / …），所以编译器把它们放在 `.text` = FLASH。

## 2. 为什么这能解释全部观测

| 送审文档的观测 | 本假设的解释 |
|---|---|
| 落盘后 **≈217~221ms** 复位 | ISR 卡住 → 200ms 后 IWDG 超时（+ 传输/复位开销） |
| 复位源 = `IWDG1` (`0x04420000`) | 唯一在跑的是 IWDG（IWDG 走 LSI，与 CPU 无关） |
| 闲时喂狗计数单调涨、一落盘就停 | 卡点在 ISR 内，**ISR 一卡，后续所有拍（含喂狗）都不再执行** |
| `writes=0 / erase_ok=0`（从未落盘） | 复位发生在擦除**期间或之后不久**，且复位清掉了 PERSIST_STAT —— 所以**连 `writes++` 都没机会记上** |
| 收到的 4 字节帧形状像启动横幅 | 那是**复位后新一轮启动输出**（送审文档 §1 的推断 ✅ 成立） |
| `上一轮 最后拍` 三次不同（199777 / 226658 / 87739） | 每次落盘被复位打断的拍号本来就随机 |

## 3. 为什么你们的两次修复无效（这段最关键）

| 修复 | 依据 | 为什么无效 |
|---|---|---|
| **1. `fl_wait_qw` 内每轮喂狗** | "合法长操作不该给上界" | **主循环根本拿不到 CPU** —— 它被卡住的 ISR 占着。在拿不到 CPU 的代码里加喂狗，等于零。 |
| **2. `fl_wait_qw`/`fl_cyccnt` 进 ITCM** | "擦 flash 会 stall 取指" | **搬错了地方**：这两个函数在**主循环**路径上（`persist_save → flash_erase_sector → fl_wait_qw`）。你们实测 `fl_wait_qw@0x15bc` 确实进了 ITCM，但**ISR 路径上一个都没动** —— 所以当然还复位。 |

**这正是"修复了一个真实的机制、但没修复本次的成因"** —— 和你们自己在 `wdt.h` 里
对"关闸"那条的处理（保留但注明"未被证明是成因"）是同一个分寸问题。
（`persist_save` 本身还在 `0x08005060` = FLASH，主循环的阻塞仍在，那是**另一个**问题。）

## 4. 为什么 LA 实验做不出结果 —— 判据设计问题

**你们的设计**（送审 §6）：抓 `CH0 = 拍心跳（PB0，常态 10 Hz）`，落盘期间看它是否变平。

**这条判据会被"短暂停顿 + 恢复"骗过**：

- 10 Hz ⇒ 周期 100 ms；**停 200 ms 只丢 2 个沿**；
- **复位后心跳立刻恢复** ⇒ 长采集里"前面一切正常、中间少两个沿、后面正常"，
  粗看就是"**仍在跳**" ⇒ 判据说"假设被否" ⇒ **得出反向结论**。
- 判据本身是"存在性"的（还在不在跳），不是"量"的（停了多久）—— **正是本项目一直在消的那类弱判据**。

### 改进（决定性，改动很小）

**把 GPIO 语义从"每拍翻转"换成"ISR 入口置高 / 出口拉低"**：

```c
ISR_PLACE void TIM2_IRQHandler(void)
{
    pin_set(HB_PORT, HB_BIT, 1);      /* ← 入口置高 */
    ...
    pin_set(HB_PORT, HB_BIT, 0);      /* ← 出口拉低 (所有 return 路径都要走到) */
}
```

- **正常**：100 µs 窄脉冲（占空比 ~5%），周期 100 µs；
- **卡住**：**保持高电平直到复位** ⇒ LA 上看到一条**长高电平**；
- **判据（可量化、能失败）**：`最大高电平宽度 > 1 ms ⇒ 某次 ISR 卡住`，并可直接读出卡了多久
  （本例预期 ≈200 ms —— 正好等于看门狗超时，**两个独立量对上就是铁证**）。
- LA：采样 1 MS/s、采 5 s 足够（信息量比现在高一个量级）。

> 顺带：**PB0/PB1 双心跳**（`03a1ca7`）如果一个是 ISR、一个是主循环，那么这次故障下
> **ISR 心跳会停在最后一个沿，主循环心跳会停更早** —— 两个一起抓能一次分清"谁先死"。

## 5. 修复建议

### 5.1 治本：ISR 可达的**代码**与**数据**都进 ITCM

1. 给这 7 个函数（或至少其热路径）加 `ATTR_ITCM`；
2. **★★ 但只搬代码不够** —— 这是送审文档没提到的半：
   **ISR 若读 `.rodata`（常量表、字符串、LUT），那次读同样 stall。**
   ⇒ 要么给这些数据也加段属性（`ATTR_ITCM_DATA`），要么确认 ISR 里的常量都是**立即数编码**。
   **"ISR 的代码在 ITCM" ≠ "ISR 不碰 flash"。**
3. 搬完**必须复验**：再跑一次 `nm` + 实机落盘。

### 5.2 或者：把"擦除"定义成**显式停机窗口**（语义诚实）

擦除期间**显式屏蔽拍中断**，并在宣称里写清"落盘 = 主循环接管窗口，节拍暂停 ~X ms"。
- 优点：不依赖"把所有东西搬 ITCM"这条易漏的路；
- 代价：与"100 µs 硬拍"宣称冲突 ⇒ **必须写进文档**，不能默认。

### 5.3 介质换 SD（你们 §9 方案 A）

SD 是**外设**，CPU 只是等它，**不存在"取指被 stall"** ⇒ 结构性避开本缺陷。
- ⚠️ 但 `sd_log_poll` 实测有 ~816ms 主循环阻塞（**另一个机制**），仍需单独处理；
- 且要加"无卡/读失败 ⇒ 默认配置 + 上报"的降级。

**我的倾向：5.1 + 5.2 组合**（保实时性 + 对"必然长阻塞"的操作诚实标注），
5.3 作为产品化方向。**但如你们所说，真因定案前不宜据此改架构** —— 现在可以改了（见 §1/§2）。

## 6. 机制改进：让这类回归再也藏不住（比修这一处更重要）

**"ISR 调用树必须全在 ITCM" 目前没有任何机制保证** —— 它靠人记得。
T26 当年的结论是"向量表 + ISR 代码 + 表都搬离 flash ⇒ 0 拍缺口"，
**而此后每加一个"在 ISR 里 poll 一下"的新功能（DI/ADC/DO/HIL/RTC/blackbox），这条不变量就被悄悄破坏一次**
—— 直到今天以"落盘就重启"的形式爆出来。**这是标准的集成回归。**

建议加**构建期检查**（三选一，都在你们已有做法的射程内）：

- **方案 A（最直接）**：链接后扫 `.map`，凡**在 `.text` 且被 ISR 可达**的符号 ⇒ **构建失败**。
- **方案 B**：给 ISR 调用树里的函数统一用一个宏 `ISR_SAFE`（展开为 `ATTR_ITCM`），
  并在 `engine.h` 的布局断言区加一条"该段必须落在 ITCM"的编译期/链接期断言。
- **方案 C（最轻）**：把 §1 的 `nm` 检查写成一个脚本，进 `build.sh` 的"零警告闸门"旁边
  —— **你们已经有"闸门"这个先例**（`build.sh` 的警告扫描）。

**推荐 A 或 C**：它把"我记得要加 ATTR_ITCM"变成"忘了就构建不过"。

## 7. 回答送审文档 §11 的五个问题

**Q1. §6 的机制假设成立吗？判定实验有无漏洞？**
**机制成立**（就是本报告），但**定位对象要换**：不是 `engine_scan_flash`（未启用），
而是另外 7 个函数。**判定实验的漏洞**是判据太弱（§4）："心跳是否变平"会被
"停 200 ms 又恢复"骗过；改成"ISR 入口/出口电平 + 最大高电平宽度"即可一次判死。

**Q2. 若假设成立，"屏蔽拍中断"与"ISR 全调用树进 ITCM"哪条更符合 PLC 语义？**
**不是一个二选一**：ITCM 解决"能不能带着实时性做完"，屏蔽中断解决"这件事本来就不该在线做"。
建议 **ITCM 化（保实时性）+ 对擦除这种必然长阻塞显式停机并写进宣称**。
★ 另外提醒：**ITCM 化必须连"数据"一起**（5.1 第 2 点），否则还是会在某个 `.rodata` 读上 stall。

**Q3. §7 的三条验收项够不够？**
三条都是对的（`erase_ok == writes` / `writes` 单调 +1 / 落盘前后启动次数不变）。
**再补三条**：
- ④ **落盘期间不得复位**（已含）**且"ISR 心跳的最大间隔"不得超阈值** —— 把机制本身变成验收项；
- ⑤ **ISR 调用树落位检查**（§6 的构建期闸门）—— 这条能防住**整族**回归，不只这一次；
- ⑥ **`0x43[1]` 的应答形态必须匹配**（应为 24 字节；收到 4 字节即"这不是应答，是重启横幅"）
  —— 你们 §1 已经推断对了，把它变成本轮就报警的判据。

**Q4. §9 的 A/B/C 三个方案，从"当 PLC"角度倾向哪个？**
**A（换 SD）+ B（把 flash 落盘定义成停机维护窗口）组合**，**不要 C**。
理由：PLC 需要"配置能掉电保持"这个能力（A 给），而 flash 的擦除窗口物理上就是毫秒到秒级，
**把它诚实标注比删掉能力更符合工业语义**。C 会让产品少一块能力，且"删能力"不解决"ISR 里
为什么有 flash 代码"这个**根本**问题 —— 那个问题会在别的地方再冒出来。

**Q5. 本文档中哪些结论只有推断没有实测？**
你们已标了 §1 末尾、§5-4、§6。**我再指出两处**：
- **§3-4 的否定**（"等待循环在 flash 里"被否掉）是**有效否定，但对象不对**：
  它否掉的是**主循环**路径的假设，而真凶在 **ISR** 路径 —— 建议在文档里补一句
  "本次否定的范围仅限主循环路径"，否则后来人会据此认为"flash 取指理论已被推翻"。
- **§4 表格第 3 行**（`PERSIST_BLOCK_TICKS` 2.5s→8s）写的是"顺带修掉一个**潜在**二次缺陷"，
  其中"3s 的擦除会在 2.5s 处被停滞自愈复位"**是推断**（因为擦除根本没跑到 2.5s 就被看门狗复位了）。
  建议标注为推断，等真因修好后**才能**验证这条。

## 8. 附：本次定位为什么"一条命令就出来了"

送审文档做了 4 次实机实验、两次修复尝试，方向都对，但都**假设**"是某段代码在 flash"——
**没有人去把 ISR 的调用树逐个查地址**。而那是**静态的、零成本的、一次列全的**。

> **教训（与你们项目既有家族同源）**：
> **"哪些代码在 flash" 是一个可以**枚举**的事实，不该用实验去反推。**
> 先枚举事实（`nm`），再设计实验去验证**结论**，而不是用实验去猜**事实**。
