## 2. 我不同意 / 要补充的地方

### (a) ISR 侧"串口 TXE 发心跳"有**互斥风险**，不能这么直接做

主循环在组帧/发帧（`proto_poll` 的响应路径）时，ISR 往**同一个 UART** 插 2~3 字节
⇒ **会把一帧劈开**，PC 解析器要么丢帧、要么把心跳字节当帧头错位。
（今天刚在 485 上吃过同族亏：帧内容必须"对端视角"才算数。）
⇒ 两条路，选一：
* **UART 心跳**：必须让 ISR 只在"**TX 空闲 且 不在帧中**"时发 —— 需要一个**原子预留位**
  （主循环发帧前置起、发完清掉；ISR 只在位为 0 时插字节）。这是**协议层设计**，不是"非阻塞 TXE"一句话。
* **GPIO 心跳**（我更推荐）：ISR 翻转一根脚，**完全不碰协议流**，且我们有 LA 可做**外部独立证据**
  （skill `saleae-la-verify` 现成）。代价：一根线 + 一个脚位预算。
  ⇒ 且它天然满足铁律 0（观测不改变被测对象）—— 比往数据流里插字节更干净。

### (b) 阈值：用"**带截止时间的已知阻塞窗口**"，不是调大数字（同意审计方向，补足形状）

审计说"正确做法是刷盘期间暂停判据，不是调大阈值" —— 方向对。但要写成正确形状：
若窗口标记由主循环维护，**主循环死在窗口内 ⇒ 标记永远挂着 ⇒ 判据永远被抑制**（又是一个空判据）。
⇒ 形状必须是**截止时间**：

```c
/* 主循环在"已知会阻塞"的段前后设置 */
g_block_expected_until = g_tick_count + BLOCK_WINDOW_TICKS;   /* 进段 */
/* ... 阻塞段 ... */
g_block_expected_until = 0;                                    /* 出段 */

/* ISR 判据 */
} else if (++s_hb_stall >= 12000u) {
    fault_record(...);                                  /* 先留痕, 与是否复位无关 */
    if (!block_window_active()) { /* 含"窗口过期即恢复" */ ... }
}
```
★ 窗口过期自动恢复 —— 这样"死在阻塞段里"仍然会被抓到。**阈值本身不该动**（同意审计：
调大只会让真卡死也检测不到）。

### (c) 负向对照要**能归因**，否则补了还是不闭合

审计指出正向判据与"注入引发别的异常"同形（§1 已证实）。那负向对照同样有这个问题：
`WDT=0 + 注入 ⇒ 永久卡死` 只能证明"有东西把它搞死了"，**不能证明"搞死它的正是设计的那个死循环"**。
⇒ 补一个**归因锚点**（成本几行）：

```c
if (g_hang_isr) {
    *(volatile uint32_t *)0x24000500u = 0x474E4148u;   /* 'HANG' —— 写进 AXI(NOLOAD, 跨复位不丢) */
    for (;;) { __asm__ volatile("nop"); }
}
```
于是三档读数变成**可归因**的：
| 构建 | AXI 标记 | RSR | 结论 |
|---|---|---|---|
| WDT=1 + 注入 | `HANG` | IWDG1RSTF | 走到设计的死循环, 看门狗救场 ✓ |
| WDT=0 + 注入 | `HANG` | 无复位(卡死) | 注入真的生效, 且**没有**看门狗就回不来 ✓ |
| 不注入 | 无标记 | 正常 | 基线 ✓ |
⇒ 这才把审计指出的那个缺口真正闭合（否则三档里有两档长得一样）。

### (d) `eng_outputs_safe(g_shm)` 签名不对，且它的能力比设想的**小**

实际签名是 `void eng_outputs_safe(void)`（`engine.h:1118`）。
更要紧的是它的覆盖范围：`engine.h:1115-1117` 自己写明 —— **H723 当前没有 GPIO 执行器输出**，
`OFF_CTRL_GPIO_MASK` 不可达，真正在动的是**注册进来的物理面**（当前 = HIL PWM）。
⇒ "先 `eng_outputs_safe()` 再复位"这条**能做的比审计设想的少**，而且"复位即安全态"目前
**缺外部下拉**（已在 `wdt.h` 边界里写明）。
⇒ 结论：**语义决策（复位 vs 保持输出）可以定，但宣称必须是"复位 = 停止驱动"**，
不能写成"复位进安全态"。

## 3. 优先级（我的排序，与审计略有不同）

1. **P1② 负向对照 + §2(c) 的 `HANG` 锚点** —— 不动源码逻辑（只加 3 行锚点），成本最低，
   且它是 P1① 的**前提**（① 的判据依赖"注入能真的卡死"这件事被证明）。**建议先做。**
2. **P2④ 首例哨兵** —— 加 `f_first_valid` 位，几行，去掉一个无判据可查的坑。
3. **P3 工具三项** —— `sync_ok` 极性 / `--raw` / SD_CFG 魔数判读（今天我就被无魔数判读坑过一次）。
4. **P1① 主循环失活** —— 需要先做两个决定/一次验证：
   ① 语义决策（复位 = 停止驱动，要写进宣称）；
   ② 先验证 `SD_DIAG[60]` 的覆盖范围，再定窗口长度；
   随后才落 §2(b) 的窗口形状 + §2(a) 的观测通道（推荐 GPIO 心跳）。

## 4. 我接受、但要说清边界的

* **"主循环失活是唯一不能自愈的失效模式"** —— 同意，这是准确的批评。台账的读取依赖主循环，
  "实时可观测"与"非侵入"在这处撞在一起，审计点得很准。
* **"首例 freeze-frame 是本次最值钱的一条"** —— 同意，且它的价值**已经被验证过一次**：
  今天注入挂死后 `--boot` 直接给出"上一轮停在 stage=7 / 最后拍 345434 / 台账 total=0"，
  不需要调试器、不需要猜。这正是它该有的样子。
* **自描述只到"区"没到"字段"** —— 同意，且**今天已经踩过这个类的实例**：
  工具按硬编码 `PR=4/RLR=99` 判读，换 `PR=6` 档立刻变成假报警（已改为固件自报）。
  ⇒ 我修的是**一个实例**，不是**这一类**。审计的"加一层字段描述符 / 至少一个对账校验和
  （照 `BB_DIAG[37]` 的先例）"是对的方向。

## 5. 一句话

审计的三条"做对了"我认；两条 P1 我认，且其中一条（负向对照）**比审计说的还更该补**
—— 因为现有正向读数与"注入引发别的异常"**完全同形**，不补就是判据缺口而不是工作量缺口。
主循环失活那条，我同意它是留白；但落地前要先解决"复位 = 停止驱动 ≠ 安全态"这个宣称问题，
以及心跳通道的帧互斥（或改走 GPIO）。
