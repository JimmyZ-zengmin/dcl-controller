# H723 RS-485 接收故障定位报告

- 平台：STM32H723ZGT6 最小系统板，自研裸机工程（无 RTOS）
- 端口：PD5=USART2_TX / PD6=USART2_RX，115200 8N1
- 现象（用户描述）：**板子能发，收不到；PD6 偶尔短暂收到一点点，之后就没有了**
- 审计基准：`733bce4`（2026-09-13 10:11）
- 日期：2026-09-13

---

## 0. 结论先行

故障**不是接线，也不是 PD6 没信号**。是两个叠加的软件缺陷：

### 根因①（直接杀手）`ORE` 溢出标志从未被清除 → 接收锁死

`src/modbus.c` 的 `mb_pull_rx()` 物理口分支只检查 `RXNE`：

```c
while (n < max_n) {
    uint32_t isr = USART_ISR(USART2_BASE);
    if (!(isr & USART_ISR_RXNE)) break;      /* ★ 只看 RXNE */
    dst[n++] = (uint8_t)(USART_RDR(USART2_BASE) & 0xFFu);
    ...
}
```

一旦出现 **`ORE=1` 且 `RXNE=0`**（实测就是这个状态），循环**直接 break、永不读 RDR**
⇒ `ORE` 永不清除。而 **H7 在 ORE 置位期间丢弃所有新收到的字符**，于是 `RXNE` 永远不再置位
⇒ **自锁死**。实测：

```
清 ORE 前：USART2_ISR = 0x006000D8  → ORE=1, IDLE=1, RXNE=0, TC/TXE=1
           读一次 RDR 后再读 ISR → 仍 0x006000D8 （ORE 没被读掉）

清 ORE 后（写 ICR=0x1FF）：ISR = 0x00600080（ORE/IDLE 消失）
           立刻灌帧 → 物理口字节 0 → 4    ★ 接收当场复活
```

**对照：USART1（协议口）在 `uart.c` 里已经修过同一族问题**（"只清 ORE 导致每帧 6 字节只收到 1 个"，后补了 FE/NE 逐个清除）。
**USART2（modbus）没有做这件事** —— 同一族缺陷只修了一半。

### 根因②（ORE 为什么必然发生）单字节 RDR + 100µs 轮询周期 > 86.8µs 字节间隔

`modbus.c` 里有一段**关键的错误推理**：

```c
/* ★ 顺带: 不使能 H7 的 FIFO (CR1.FIFOEN=0, 单字节缓冲) 也完全够 ——
 *   115200 @ 100µs/拍 → 每拍最多到达 1.15 字节, 单字节缓冲不会溢出。
 *   不开 FIFO 少一处配置, 确定性更好。 */
```

**"每拍最多 1.15 字节"是平均值，不是上界。** 实际是：
- 字节间隔 = 10 bit / 115200 = **86.8 µs**
- 拍周期 = **100 µs**（TIM2 100µs 中断里跑 `mb_tick`）

拍**比字节慢**，于是相位持续漂移（每字节漂 13.2 µs），**周期性出现"一拍内到达 2 个字节"**。
而 RDR 只有 1 字节深 ⇒ 第 2 个字节到达时第 1 个还没被读走 ⇒ **必然 ORE**。

**实机对照（决定性）**：

| 发送方式 | 字节间隔 | 结果 |
|---|---|---|
| 慢发（逐字节，间隔 2000 µs ≫ 拍周期） | 2000 µs | **8/8 全收** ✓ |
| 快发（正常连续写） | 86.8 µs < 100 µs | **6/8，丢 2 个** ✗ |

**慢发全收这一条同时证明：链路物理上完好、PD6 上有信号、USART2 能收** —— 问题纯粹在接收节奏。

## 1. 完整证据链（全部实机）

### 1.1 PD6 上确实有信号

固件自带 PD6 波形采样（`mb_line_probe`，把 PD6 临时配成输入+上拉、紧循环采样）：

```
pd6_low = 19210 / 400000 = 4.80% 低电平
```

PC 连发 258 帧、帧间隔约 11.6 ms、每帧 694 µs ⇒ 理论占空比 ≈ 6%。**实测 4.8% —— 吻合**（说明 PD6 上跑的就是 PC 的 Modbus 数据流）。

### 1.2 引脚配置读回正确（排除"写过了就算"）

```
GPIOD MODER = 0xEBEF   → PD5/PD6 = AF(10b) ✓
GPIOD AFRL  = 0x07700C00 → PD5=AF7, PD6=AF7 ✓（0xC00 是 PD2=AF12，SDMMC，与本故障无关）
GPIOD PUPDR = 0x1010   → PD6 = 上拉 ✓
USART2 CR1 = 0x0D (UE|TE|RE)   BRR = 0x364 (=868)   PRESC = 0
```

### 1.3 字节流动的实际形态

```
RESET 到干净状态 → 灌 12 帧（96 字节）:
  Δ物理口字节 = 0      ← 完全收不到（此时 ORE 已置位且未清）

清 ORE 后灌 8 帧:
  Δ物理口字节 = 4，maxrx = 4，erracc = 0x08(ORE)   ← 收 4 个又被 ORE 锁死

清 ORE 后灌 1 帧（8 字节）:
  Δ物理口字节 = 7，maxrx = 4，short = 1，last_byte = 0x9C(帧第3字节)
  ⇒ 帧被切成 "4 + 3" 两段：第 4 字节后 ORE 丢字节 → 400µs 静默 → 状态机按 4 字节结算
```

**这三组读数与用户描述的"偶尔收到一点点、后面就没了"完全一致。**

## 2. 修复

### 2.1 主修复：打开 USART2 的 RX FIFO（已实机验证）

`src/modbus.c` 的 `mb_uart_enable()`：

```c
/* ④ 使能: UE | TE | RE + ★ FIFOEN
 *   ★★ 为什么必须开 FIFO (2026-09-13 实测):
 *     RDR 只有 1 字节深, 而拍周期 100µs > 字节间隔 86.8µs ⇒ 相位漂移导致
 *     **周期性"一拍到 2 字节"** ⇒ 第 2 个被丢 ⇒ ORE。
 *     原注释"每拍最多 1.15 字节"是**平均值不是上界** —— 实测快发 8 字节丢 2 个。
 *     FIFO 深度 8 能吸收拍间积压, 实测开 FIFO 后 32/32 全收、响应正常。 */
USART_CR1(USART2_BASE) = USART_CR1_UE | USART_CR1_TE | USART_CR1_RE | USART_CR1_FIFOEN;
```

**注意**：H7 要求 `FIFOEN` 在 `UE=0` 时配置——所以要先关 UE 再改（当前代码是直接整写 CR1，顺序天然满足）。

**运行期等价验证（不改固件，用 pyocd 写寄存器）**：

```
① write CR1 = 0x00000000 (关 UE)
② write CR1 = 0x2000000D (FIFOEN | UE|TE|RE)   → 读回 0x2000000D ✓
③ 清 ORE → 快发 4 帧:
     bytes 21 → 53 (Δ=+32/32)      ★ 全收
     maxrx = 8                     ★ 完整帧, 不再被切
     COM15 收到 4 次完整响应: 010314000000...0000a367 (CRC 正确)
```

### 2.2 配套修复：每拍主动清错误标志（防"清了 FIFO 仍会 ORE"）

FIFO 只是把 ORE 的**阈值**从 2 字节推高到 9 字节，**并没有消除 ORE**（实测 `erracc` 仍为 0x8）。
而"ORE 未清 ⇒ 接收锁死"这条路径**依然存在**，所以必须同时补上清错误：

```c
static int ATTR_ITCM mb_pull_rx(uint8_t *base, uint8_t *dst, int max_n)
{
    ...
    while (n < max_n) {
        uint32_t isr = USART_ISR(USART2_BASE);
        /* ★★ 必须先清错误标志 (2026-09-13 实测):
         *   若只剩 "if (!(isr & RXNE)) break;" —— 一旦 ORE 置位且 RXNE=0,
         *   就永远 break、永不读 RDR ⇒ ORE 永不清 ⇒ H7 丢弃所有新字符 ⇒ 接收锁死。
         *   实测: 清 ORE 前收 0 字节; 清后立刻收 4+ 字节。 */
        if (isr & (USART_ISR_PE | USART_ISR_FE | USART_ISR_NE | USART_ISR_ORE)) {
            USART_ICR(USART2_BASE) = 0x1FFu;          /* 写 1 清 (实测有效) */
            d[MB_DIAG_ERRACC] |= (isr & (USART_ISR_PE | USART_ISR_FE
                                        | USART_ISR_NE | USART_ISR_ORE));
        }
        if (!(isr & USART_ISR_RXNE)) break;
        dst[n++] = (uint8_t)(USART_RDR(USART2_BASE) & 0xFFu);
        ...
    }
    return n;
}
```

**更稳的位置是 `mb_tick()` 入口**——因为 `mb_pull_rx` 只在 `MB_ST_IDLE/MB_ST_RX` 状态被调用；
状态机处在 `EXEC/BUILD/TX` 期间完全不读 RDR，那段时间的 ORE 同样会锁死接收。

### 2.3 `min_uart485.c` 有同一族缺陷（干净固件里也有一份）

```c
if (isr & (PE|FE|NE|ORE)) { USART_ICR = 0x1FFu; ...; continue; }   /* ★ 跳过 RDR */
if (isr & USART_ISR_RXNE) { b = RDR; ... }
```

错误分支 `continue` **跳过了 RDR 读取**——FE/NE 时数据仍在 RDR 里且会被丢。
（它至少写了 ICR，所以不会像 `modbus.c` 那样彻底锁死，但会丢字节。）

## 3. 为什么 USART1 没有这个问题

| | USART1（协议口） | USART2（Modbus） |
|---|---|---|
| 接收方式 | **中断** + 环形缓冲（`uart.c`） | **轮询**（在 100µs 的 TIM2 ISR 里） |
| 响应延迟 | µs 级（RXNE 中断立即进） | 最多一个拍周期 **100 µs** |
| 抗抖动 | 环形缓冲（深） | RDR **1 字节**（原设计） |
| 错误处理 | 已有 FE/NE/ORE 清除 | **无** |

USART1 的即时中断 + 深缓冲天然规避了这个问题；USART2 选轮询是为了"WCET 有上界、不引入新中断源"
（见 `modbus.h` 的设计说明）——这个取舍本身合理，**但必须配 FIFO + 清错误**才成立。

## 4. 给测试的教训（与本项目既有家族同源）

1. **"平均值推理"不能当上界用**。`"每拍最多 1.15 字节"` 看着无懈可击，但它掩盖了
   **相位漂移 ⇒ 周期性"一拍 2 字节"**。这和 BRR 那条"算得对但公式错 16 倍"是同一族：
   **数字本身没错，错在它回答的不是这个问题。**
2. **同类缺陷只修一处 = 埋雷**。USART1 的清错误修好了，USART2 没修——
   而这次故障恰恰发生在没修的那个口上。
3. **"字节到了但框不成帧"需要独立的观测面**。本项目的 `MB_DIAG` 字节级计数
   （这次正是它给出了"bytes=4 / maxrx=4 / erracc=ORE"这三条决定性数字）**方向完全正确**——
   建议再补一格：**ORE/错误被清的次数**（当前 `erracc` 只记"见过"，不记"清过"）。
