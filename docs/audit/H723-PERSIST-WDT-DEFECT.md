## 0. 一句话

**每次真实落盘（`0x43[1]`）都会让板子复位一次**（复位源 = IWDG1 看门狗），
此后 `PERSIST_STAT` 的 `writes/erase_ok` 全为 0
⇒ **配置从未真正写进 flash；而现场语义是"操作员按保存 → 机器重启"**。

---

## 1. 现象（可复现）

前置：引擎已停机（`0x38` 读 `run==0`）、配置已标脏（`0x10` 部署后 `0x43` 查询 `dirty=1`）。

```
发 0x43 载荷 [1]  →  客户端在 ≈0.217~0.221 s 收到一个 **4 字节**帧（payload `00 02 F7 0D`）
                     板子启动次数 +1；`--boot` 报 复位原因 = ★ 独立看门狗 IWDG1 复位 (RSR 0x04420000)
                     复位后 PERSIST_STAT 全 0（cmds=0 saves=0 writes=0 erase_ok=0 dirty=0）
```

四次独立尝试的耗时高度一致（0.217 / 0.219 / 0.219 / 0.221 s），与看门狗超时
`DCL_WDT_MS=200`（PR=4 ⇒ 2ms/步 × RLR=99 ⇒ ≈200ms）在同一量级。

★ 注意 `0x43` 的**查询**（空载荷）一切正常：状态 ACK、payload **24 字节**。
而 `mode=1` 按代码应当也回 `ack(r,24)`
⇒ **我们收到的 4 字节帧不是 0x43 的应答**（形状与 `0x01`/启动横幅一致，含能力字 `0x0DF7`）
⇒ 更可能是**复位后新的一轮启动输出**。这一条是推断，但它与"落盘刚开始板子就重启"自洽。

## 2. 判据与证据

| # | 判据 | 观测 | 结论 |
|---|---|---|---|
| ① | 落盘会复位吗 | 启动次数 +1、RSR = `0x04420000`（IWDG1） | **会** |
| ② | **对照组**：不落盘会不会自己复位 | 只 `0x12` 停机 + 连做 3 次 `0x10` 部署，**4 秒内启动次数不动** | 排除"后台自复位" ⇒ 复位由落盘引起 |
| ③ | 是不是我加的"停滞自愈"干的 | `停滞复位=0`；RSR 不是 `SFTRESET`(0x01420000) | 排除自愈 |
| ④ | 配置到底写进去没有 | `PERSIST_STAT`：`writes=0 / erase_ok=0`（**任一轮都如此**） | **从未成功落盘** |
| ⑤ | 这个观测面本身可信吗 | 一次 `0x43` 查询 ⇒ `cmds` 精确 +1 | 可信 |
| ⑥ | 主循环停在哪 | `上一轮 最后拍` = 199777 / 226658 / 87739（三次不同运行） | 主循环在那一轮后再没回来 |
| ⑦ | 闲时喂狗健康吗 | `WDT_STAT` 喂狗计数单调涨（一次读数 333334） | 闲时正常 ⇒ 只在落盘期间停摆 |

## 3. 已排除的假设（逐条带证据）

1. **"是停滞自愈/软复位"** —— 排除（§2③）。
2. **"是别的后台任务复位"** —— 排除（§2②，对照组）。
3. **"落盘被跳过、所以没写"** —— 不能解释复位：跳过路径
   （`SHM_U8(ENGINE_RUN)!=0 ⇒ return 1`）返回极快（实测 ~21ms）、**不碰 flash**、不会复位；
   且本轮已确认 `run==0`（不满足跳过条件）。⇒ 跳过不是原因。
4. **"等待循环在 flash 里 ⇒ 擦除期间取指被 stall ⇒ 喂狗指令取不到"** ——
   **已被实验否掉**：给 `fl_wait_qw`/`fl_cyccnt` 加 `.itcm_text` 后（`arm-none-eabi-nm`
   显示 `fl_cyccnt@0x000015bc`、`fl_wait_qw@0x000015c8`，均在 ITCM；`objdump` 确认循环体
   字面量也在该函数内部、`wdt_feed` 已内联无独立符号）**仍然复位**。
5. **"喂狗频次不够"** —— 已把 `fl_wait_qw` 改成**每轮迭代都喂**
   （仍在超时预算内、超预算即停喂），**仍然复位**。

## 4. 已尝试的修复（两次，均无效；代码保留在 `18c4946` 以便复跑）

| # | 改动 | 依据 | 实测 |
|---|---|---|---|
| 1 | `fl_wait_qw` 内"有界喂狗"：超时预算内喂，超预算停喂 | 看门狗职责是"抓 CPU 卡死"，不该给**合法长操作**设上界；停喂则保证"真卡死仍会复位" | **仍复位** |
| 2 | `fl_wait_qw`/`fl_cyccnt` 进 ITCM | 项目早有定案"擦 flash 会 stall 取指"（当初只把**向量表+ISR**搬进 ITCM） | **仍复位** |
| 3 | `PERSIST_BLOCK_TICKS` 2.5s → **8s**（= flash.c 的擦除超时预算） | 清空窗口必须 ≥ 该操作**自己的**超时预算，否则 3s 的擦除会在 2.5s 处被停滞自愈复位 | 顺带修掉一个**潜在**的二次缺陷 |

## 5. 尚未解释的（诚实清单）

1. **为什么落盘开始约 200ms 后看门狗就到期**：等待循环已在 ITCM 且每轮喂狗，
   闲时 ISR 喂狗也健康 —— 但落盘一开始，喂狗就停摆。**机制未定案。**
2. **擦除到底有没有开始/完成**：`g_fl_err_stage`、`g_fl_err_sr1/cr1/cnt`
   （flash 驱动自己的诊断面）**目前不可从外部读走** ⇒ 等于闭着眼修。这是下一个要补的面。
3. **复位与擦除的先后**：是"擦除把 CPU 卡住"还是"复位先发生、擦除根本没跑"，尚未区分。
4. **`0x43` `mode=1` 的应答形态**：代码是 `ack(r,24)`，实测是 4 字节（§1 末尾的推断未定案）。

## 6. 最强剩余假设 + **判它只需一次 2 秒采集**

**假设**：擦除期间 CPU 从 flash 取指被 stall；而**拍 ISR 的调用树里仍有 flash 代码**
（本项目已知存在跨区调用：`engine_tick(..., engine_scan_flash, ...)`、`mb_tick`、`do_poll`、
`fault_record` 等）⇒ 拍 ISR 触发后卡在某次 flash 取指上**永不返回**
⇒ 主循环（连同 §4-1 加的 ITCM 喂狗循环）**拿不到 CPU** ⇒ 200ms 后看门狗复位。

**为什么这个假设能同时解释"ITCM 修复无效"**：喂狗代码在 ITCM 并没错，错在
**CPU 被 ISR 占着**、根本回不到那段代码。

**判定实验（板子已接好，成本 ~2 分钟）**：
> 用已接线并验证过的逻辑分析仪抓 **CH0 = 拍 ISR 心跳（PB0，常态 10.000 Hz）**，
> 同时发一次 `0x43[1]`。
> * 若落盘期间 **CH0 变平** ⇒ 拍 ISR 真的停了 ⇒ 假设成立（⇒ 修法：擦除期间屏蔽拍中断 /
>   把 ISR 全调用树搬 ITCM / 换介质，见 §9）。
> * 若 **CH0 仍在跳** ⇒ 假设被否，喂狗是被别的东西拦住的（下一步查喂狗闸门
>   `g_wdt_kr_blocked` 与 `wdt_start` 的 `g_wdt_kr_busy` 是否被误置）。

## 7. ★ 验收缺口（本次缺陷能藏这么久的根本原因）

**没有任何一条验收项要求"落盘必须真的写进 flash"。** 验收表盯的是
"命令回 ACK""`dirty` 被清"—— 而这两件事**都不等于写进去了**：

* 跳过路径（引擎 RUN）也回 ACK；
* `dirty` 有**两条**清零路径：`persist.c:350`（写成功后）**和 `main.c:2110`（`0x13 RESET` 使快照失效）**
  ⇒ 一次复位就能让 `dirty` 归零，看起来"保存成功"。
* 判据缺失的直接后果：**我自己就把"读数被复位清零"误读成"落盘成功且很快"**，
  并写进了 `docs/VALIDATE-watchdog.md §11.4` 与一条提交信息 —— 现已就地作废更正。
  ⇒ **判据不存在时人会猜，而猜错不会有提示。**

**建议补的三条验收项（每条都能失败）**：
1. `erase_ok == writes`（代码每次都先擦后写）—— 新增面 `PERSIST_STAT` 已可支撑；
2. `writes` 单调 +1 才算"落盘成功"（ACK/`dirty` 都不作数）；
3. **落盘期间板子不得复位**（比较落盘前后启动次数）。

| 宣称 | 现状 |

## 10. 精确复现步骤

```bash
cd "D:/STM/8.29 AIAutoFactior/9.10 H723newest"

# 0) 烧录并让板子起来（pyocd 会 HALT >200ms 触发一次 IWDG 复位，属已知现象）

python - <<'PY'
import sys,time,struct; sys.path.insert(0,'tools')
from h723_client import Dcl, engine_status, persist_flags
import h723_seq as S
d=Dcl("COM14")
print("run=", engine_status(d)['run'])          # 应为 0；否则先发 0x12 STOP
rt=S.rt_route(S.SRC_WIRE,S.MIRROR,S.DECODE,S.OP_CMP,param_idx=1,div=0)
pl=struct.pack("<HHH",1,3,0)+rt+struct.pack("<4f",0.5,1.,0,0)+struct.pack("<4f",1.5,0,0,0)+struct.pack("<4f",3.,0,0,0)
print("deploy:", d.send(0x10, pl)[0], "dirty=", persist_flags(d)[0])   # 期望 ACK / True
t0=time.time(); st,p=d.send(0x43, bytes([1])); print("persist:", st, len(p), "%.3fs"%(time.time()-t0))
d.close()
PY

# 2) 看判据（关键：writes/erase_ok 应与"真正写成功"一致）
python tools/mgmt.py --read PERSIST_STAT     # 期望 erase_ok == writes（每次落盘 +1）
python tools/mgmt.py --boot                  # 期望 启动次数不变；变了 ⇒ 落盘把板子复位了
```

**已实测的结果**：`persist` 返回 ACK 但 payload 只有 4 字节；启动次数 +1；
之后 `PERSIST_STAT` 全 0；`--boot` 报 IWDG1 复位。
