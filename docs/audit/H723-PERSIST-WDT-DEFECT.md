## 0. 一句话

**每次真实落盘（`0x43[1]`）都会让板子复位一次**（复位源 = IWDG1 看门狗），
此后 `PERSIST_STAT` 的 `writes/erase_ok` 全为 0
⇒ **配置从未真正写进 flash；而现场语义是"操作员按保存 → 机器重启"**。

---

## 1. 现象（可复现）

前置：引擎已停机（`0x38` 读 `run==0`）、配置已标脏（`0x10` 部署后 `0x43` 查询 `dirty=1`）。

```
发 0x43 载荷 [1]  →  客户端在 ≈0.217~0.221 s 收到一个 **4 字节**帧（payload `00 02 F7 0D`）
                     板子启动次数 +1；`--boot` 报 复位原因 = ★ 独立看门狗 IWDG1 复位 (RSR 0x04420000)
                     复位后 PERSIST_STAT 全 0（cmds=0 saves=0 writes=0 erase_ok=0 dirty=0）
```

四次独立尝试的耗时高度一致（0.217 / 0.219 / 0.219 / 0.221 s），与看门狗超时
`DCL_WDT_MS=200`（PR=4 ⇒ 2ms/步 × RLR=99 ⇒ ≈200ms）在同一量级。

★ 注意 `0x43` 的**查询**（空载荷）一切正常：状态 ACK、payload **24 字节**。
而 `mode=1` 按代码应当也回 `ack(r,24)`
⇒ **我们收到的 4 字节帧不是 0x43 的应答**（形状与 `0x01`/启动横幅一致，含能力字 `0x0DF7`）
⇒ 更可能是**复位后新的一轮启动输出**。这一条是推断，但它与"落盘刚开始板子就重启"自洽。

## 3. 已排除的假设（逐条带证据）

1. **"是停滞自愈/软复位"** —— 排除（§2③）。
2. **"是别的后台任务复位"** —— 排除（§2②，对照组）。
3. **"落盘被跳过、所以没写"** —— 不能解释复位：跳过路径
   （`SHM_U8(ENGINE_RUN)!=0 ⇒ return 1`）返回极快（实测 ~21ms）、**不碰 flash**、不会复位；
   且本轮已确认 `run==0`（不满足跳过条件）。⇒ 跳过不是原因。
4. **"等待循环在 flash 里 ⇒ 擦除期间取指被 stall ⇒ 喂狗指令取不到"** ——
   **已被实验否掉**：给 `fl_wait_qw`/`fl_cyccnt` 加 `.itcm_text` 后（`arm-none-eabi-nm`
   显示 `fl_cyccnt@0x000015bc`、`fl_wait_qw@0x000015c8`，均在 ITCM；`objdump` 确认循环体
   字面量也在该函数内部、`wdt_feed` 已内联无独立符号）**仍然复位**。
5. **"喂狗频次不够"** —— 已把 `fl_wait_qw` 改成**每轮迭代都喂**
   （仍在超时预算内、超预算即停喂），**仍然复位**。

## 5. 尚未解释的（诚实清单）

1. **为什么落盘开始约 200ms 后看门狗就到期**：等待循环已在 ITCM 且每轮喂狗，
   闲时 ISR 喂狗也健康 —— 但落盘一开始，喂狗就停摆。**机制未定案。**
2. **擦除到底有没有开始/完成**：`g_fl_err_stage`、`g_fl_err_sr1/cr1/cnt`
   （flash 驱动自己的诊断面）**目前不可从外部读走** ⇒ 等于闭着眼修。这是下一个要补的面。
3. **复位与擦除的先后**：是"擦除把 CPU 卡住"还是"复位先发生、擦除根本没跑"，尚未区分。
4. **`0x43` `mode=1` 的应答形态**：代码是 `ack(r,24)`，实测是 4 字节（§1 末尾的推断未定案）。

## 6. 最强剩余假设 + **判它只需一次 2 秒采集**

**假设**：擦除期间 CPU 从 flash 取指被 stall；而**拍 ISR 的调用树里仍有 flash 代码**
（本项目已知存在跨区调用：`engine_tick(..., engine_scan_flash, ...)`、`mb_tick`、`do_poll`、
`fault_record` 等）⇒ 拍 ISR 触发后卡在某次 flash 取指上**永不返回**
⇒ 主循环（连同 §4-1 加的 ITCM 喂狗循环）**拿不到 CPU** ⇒ 200ms 后看门狗复位。

**为什么这个假设能同时解释"ITCM 修复无效"**：喂狗代码在 ITCM 并没错，错在
**CPU 被 ISR 占着**、根本回不到那段代码。

**判定实验（板子已接好，成本 ~2 分钟）**：
> 用已接线并验证过的逻辑分析仪抓 **CH0 = 拍 ISR 心跳（PB0，常态 10.000 Hz）**，
> 同时发一次 `0x43[1]`。
> * 若落盘期间 **CH0 变平** ⇒ 拍 ISR 真的停了 ⇒ 假设成立（⇒ 修法：擦除期间屏蔽拍中断 /
>   把 ISR 全调用树搬 ITCM / 换介质，见 §9）。
> * 若 **CH0 仍在跳** ⇒ 假设被否，喂狗是被别的东西拦住的（下一步查喂狗闸门
>   `g_wdt_kr_blocked` 与 `wdt_start` 的 `g_wdt_kr_busy` 是否被误置）。

## 7. ★ 验收缺口（本次缺陷能藏这么久的根本原因）

**没有任何一条验收项要求"落盘必须真的写进 flash"。** 验收表盯的是
"命令回 ACK""`dirty` 被清"—— 而这两件事**都不等于写进去了**：

* 跳过路径（引擎 RUN）也回 ACK；
* `dirty` 有**两条**清零路径：`persist.c:350`（写成功后）**和 `main.c:2110`（`0x13 RESET` 使快照失效）**
  ⇒ 一次复位就能让 `dirty` 归零，看起来"保存成功"。
* 判据缺失的直接后果：**我自己就把"读数被复位清零"误读成"落盘成功且很快"**，
  并写进了 `docs/VALIDATE-watchdog.md §11.4` 与一条提交信息 —— 现已就地作废更正。
  ⇒ **判据不存在时人会猜，而猜错不会有提示。**

**建议补的三条验收项（每条都能失败）**：
1. `erase_ok == writes`（代码每次都先擦后写）—— 新增面 `PERSIST_STAT` 已可支撑；
2. `writes` 单调 +1 才算"落盘成功"（ACK/`dirty` 都不作数）；
3. **落盘期间板子不得复位**（比较落盘前后启动次数）。

## ★★★ 9. 卡点已定位到**具体语句**（2026-09-13 19:05，用 ISR 段检查点）

### 9.1 做法（因为调试器抓不到 200ms 窗口）
pyocd 连接要数秒 > 窗口 ~210ms ⇒ 改用**段检查点**：拍 ISR 每过一段就把
`(段号<<28 | 拍号)` 写进 **启动记录 [40]**（AXI，跨复位不丢），启动取证段再把上一轮的搬到 **[41]**。
判据：复位后读 [41] = **上一轮 ISR 最后走完的段** ⇒ 卡点必在它之后。

★ 这个仪器**自己出过两个 bug**，都当场修了（也正是项目铁律"仪器自己也会骗人"的又一例）：
① 没加 `dsb` ⇒ 复位不冲刷写缓冲 ⇒ 最后一次 store 丢失（读出来是"上一拍走完"）；
② 检查点**每拍覆盖** ⇒ 复位后新一轮立刻覆盖它 ⇒ 直接读 [40] 永远只看到"当前这轮" ⇒ 必须加 [41] 的 prev 槽。

### 9.2 结果
```
★★ 上一轮 ISR 最后走完 = ④mb_tick 之后 (拍号=235174)
   上一轮 主循环最后拍  = 235172              ← 两者同一时刻冻住
```
⇒ ④ 之后紧接着的两句是：
```c
ISR_CKPT(4);
hil_out_poll(g_shm, g_tick_count);   ← 卡在这里
do_poll(g_shm, g_tick_count);
ISR_CKPT(5);                         ← 没走到
```
⇒ 而 `hil_out_poll` 只做两件事：`g_hil_out_n++`（DTCM 计数）与 **`hil_out_apply(base)`**。
`hil_out_apply` 里**唯一的 APB 外设访问**是：

```c
TIM_CCR1(TIM3) = duty;               /* ★ 卡点 */
```
（其余是 SHM/AXI 写 —— 而擦除期间 AXI 写**证明正常**：检查点本身就写在 AXI 上，④ 落了 ✓）

### 9.3 为什么这条能对上既有知识
- **hil.c 自己开头就写着**："**未使能时钟的 TIM3_CCR1 ⇒ 整机卡进 Default_Handler**" ——
  即"访问 APB 外设会把这颗芯片**挂住**"在本项目**早有先例**（同族现象）。
- **不是"所有总线都停"**：ISR 入口对 **GPIOB 的心跳写**在擦除期间**成功**（宽度探针置高 ✓），
  而 **GPIOB 在 AHB4、TIM3 在 APB1** ⇒ 卡点精确落在 **"擦除期间 APB1 访问挂住"**。
- 代码里**没有任何地方关 TIM3 时钟**（只有 `hil.c:62` 开），擦除路径也**不碰 RCC**
  ⇒ 所以不是"时钟被关"，而是"**APB1 访问在 flash 擦除期间无法完成**"这一类。

### 9.4 结论与影响
1. **根因链完整**：擦 flash → 拍 ISR 走进 `hil_out_apply` → 写 `TIM3_CCR1`(APB1) 挂住
   → ISR 不返回 → 喂狗停 → 200ms 看门狗复位 → "保存配置"变成"重启机器"。
2. ★ **降级已消除触发器**：现在没有任何擦 flash 的路径（`0x43` 落盘 → NAK）⇒
   该缺陷**不会再发生** ⇒ 这也是"降级"这个决策的直接收益。
3. **若将来要恢复掉电保持**，修法方向（按代价排序）：
   - 把 HIL 输出臂从 ISR 挪到**主循环**（旧 `hil_tick` 就是主循环版，代码还在 ✓ 最小改动）；
   - 或落盘前**先停掉会碰 APB 的输出面**（与"停机维护窗口"方案 B 同族）；
   - 或换 SD 介质（方案 A）—— 但注意 SD 路径自身也有阻塞问题，需单独处理。
4. **仍待补**：上面 3 条中"APB1 为什么在擦除期间挂住"的**芯片级机理**未查（H7 参考手册/勘误表），
   但它不影响结论与修法 —— **判据已经落到一条语句上**。

## ★★★ 10. §9.4 的归因**已作废** —— 真因是 ITCM 落位，不是 APB1（2026-09-13 19:5x）

> ★ 保留 §9 原文不删（它是过程证据），但**结论以下面为准**：
> "卡在 `TIM3_CCR1` 写 / APB1 访问挂住"是**误判**。事故的因果链里，
> **`TIM3_CCR1` 只是一个恰好在 flash 地址上的无辜寄存器**。

### 10.1 真因（静态铁证，可复跑）

```
$ arm-none-eabi-nm -S build/dcl_h723 | grep -i hil_out
000027a0 00000008 t __hil_out_apply.part.0_veneer   ← 跳板, 在 ITCM
08007a14 0000006c t hil_out_apply.part.0            ← ★ 函数实体, 在 FLASH
0000266c 0000001c T hil_out_poll                    ← 在 ITCM
```

```
000027a0 <__hil_out_apply.part.0_veneer>:
    27a0:  ldr.w  pc, [pc]   ; 27a4
    27a4:  .word  0x08007a15        ← 跳到 FLASH
...
8007a3e:  ldr  r2, [pc, #52] → 0x40000434   ← = TIM3_CCR1
8007a50:  vstr s15, [r2]                    ← 写的这条指令**本身就在 FLASH 0x08007a50**
```

**因果链（与 §9 完全相同，只有最后一环不同）**：
落盘 → 擦 FLASH → 拍 ISR 每拍执行 `hil_out_poll` → 它 `b.w` 到 veneer →
veneer `ldr.w pc,[pc]` **跳到 FLASH 里的 `hil_out_apply.part.0`** →
**擦除期间 FLASH 取指被 stall** → ISR 不返回 → 喂狗停 → 200ms IWDG 复位。

**⇒ 不是"APB1 寄存器不能写"，是"那条写指令所在的**代码页**读不出来"。**

### 10.2 为什么 §9.2 那句"AXI 写证明正常"不成立

§9.2 的推理是："检查点写在 AXI 上，④ 落了 ✓ ⇒ 擦除期间 AXI 正常 ⇒ 只能卡在 APB1"。

**漏洞**：`④` 是**擦除开始之前**落下的。它只能证明"擦除前 AXI 可用"，
**完全不能**证明"擦除期间 AXI 可用"。⇒ 这一步把 `ISR_CKPT(5)` 自身（也是 AXI 写）
这个嫌疑人**一键排除了**，而它从未被检验过。

### 10.3 为什么闸门没抓到（6 个自身 bug，逐条已修）

## ★★★ 11. 上板实测结论（2026-09-13 20:xx）—— 真因是 **D3/SRD 域访问**，不是"ISR 卡死"

> 本节全部为**上板实测**（H723ZGT6 + DAPLink + CH340@COM18），判据尽量走**协议通道**。

### 11.1 先修掉一个"仪器骗人"（本轮自己的坑）

`tools/h723_proto.py` 的 `build_frame(cmd, payload)` 在默认 `force_len=None` 时把
**长度字段写成 0**（它只为"无载荷命令"设计）⇒ 我发出的 `0x43[1]`（显式落盘）
**全退化成了 `0x43`（查询）**。改用 `tools/h723_w1.py` 那种写法（`len = len(payload)`）后才正常。

### 11.2 两个必须分开的通道（否则结论会反）

| 观测手段 | 副作用 | 结论 |
|---|---|---|
| `pyocd` 写 `g_persist_dirty`/`RUN` | 核被 **HALT 数百 ms** ⇒ **喂狗停 ⇒ IWDG 复位**（README §10 自己记过） | 我写的状态**全被清掉**，看着像缺陷 |
| `pyocd` 读状态 | `connect_mode=halt` 实测**不复位**（3 次连接启动次数不变） | 可读，但仍不如协议干净 |
| **协议** `0x22`(READ_BURST, 放行 AXI 诊断窗) 读 `BOOT_AXI` | **无** | ★ 采用 |

⇒ 最终判据全部走协议，`pyocd` 只用于烧录。

### 11.3 实测结果（可复跑）

现象：`0x43[1]` 落盘 ⇒ **0.22s 后板子复位**（与 §1 的 0.217~0.221s 同量级）；
启动次数 +1；复位原因 `RCC_RSR = 0x04420000` ⇒ **bit26 = IWDG1RSTF**。

**用 ISR 段检查点（`BOOT_REC[41]` = 上一轮 ISR 最后走完的段）定位，两次独立实验：**

| 实验 | `[41]` 段号 | 该段之后紧接着的动作 | 结果 |
|---|---|---|---|
| A | **⑫** | `wdt_feed()` = 写 `IWDG_KR`（**D3/SRD**） | 卡住 |
| B | **⑥** | `rtc_latch()` → RTC 寄存器（**D3/备份域**） | 卡住 |

**两次卡点不同，但共同点唯一：下一个动作都是 D3/SRD 域的寄存器访问。**

**对照（同一次 ISR 内，均已通过）：**

| 检查点 | 访问对象 | 域 | 结果 |
|---|---|---|---|
| ⑨ | `GPIOB` (AHB4) | D2 | ✓ 通过 |
| ⑩→⑪ | `TIM2_SR` 读+写 (APB1) | D2 | ✓ **通过** |
| ⑪→⑫ / ⑥→⑦ | `IWDG_KR` / RTC | **D3/SRD** | ✗ **卡住** |

⇒ **不是"APB1 访问挂住"**（TIM2 就在 APB1，读写都过了），也**不是"代码取指 stall"**
（§10.4 已把 ISR 可达代码与常量全部搬进 ITCM，本次实测 `[40]` 显示 ISR 能跑到 ⑦ 出口）。
**而是"擦 flash 期间 D3/SRD 域的寄存器访问无法完成"。**

### 11.4 与 ST 官方说法的关系（已查）

ST 社区（H753/H755/H743 同族问题，官方 FAE 回复）：
> *"flash erase alone is **not** causing bus matrix stall"*；影响的是**触碰 flash** 的那条路径
> （*"the cpu will be stalled if it tries to read from a bank which has an erase operation in progress"*）
> 并明确警告：*"**be careful if you have the watchdog activated** … make sure you can finish
> the programming in time"*。

⇒ 官方口径解释的是 §10 那条（**取指/读 flash**），**没有覆盖本节的 D3 现象**。
本节的 D3 结论目前是**本平台实测**（两次独立复现 + 域对照），
**芯片级机理仍待查**（H7 RM0468 的 flash/bus 章节 + D3/SRD 访问约束）。
**但修法不依赖机理**：见 11.5。

### 11.5 结论与修法

**根因链（最终版）**：
```
0x43[1] → 主循环 persist_save → flash_erase_sector（擦 128KB, ~1.5s）
  → 期间 ISR 每拍仍要执行喂狗(IWDG_KR, D3) 与 RTC 镜像(D3)
  → 第一个 D3 访问无法完成 ⇒ ISR 卡住不返回
  → 喂狗停 → 200ms 后 IWDG 复位 → "保存" = "重启机器"，且配置从未落盘
```

**⇒ `persist`（内部 flash）与**看门狗**在本平台是**结构性互斥**的**，
不是"某个函数放错位置"这种可局部修好的问题。

**可选修法（按代价排序，均未实施，需决策）：**
1. ★ **保持降级**（现状）：`0x43[1]` 明确 NAK。**理由已从"不知道"变成"已知且可复述"。**
2. **擦除期间把 IWDG 超时临时放大到 > 擦除时间**（ST 社区建议"擦前先 refresh 一次"）。
   ⚠️ IWDG 一旦启动**无法关闭**，只能改 PR/RLR；而改配置需解锁+同步（`wdt.h` 记过 ~10.1ms 窗口
   与 ISR 喂狗的竞态）⇒ 必须在**停止喂狗**的前提下做，本身又要绕过"喂狗停"。
3. **换介质**（外部 FRAM/EEPROM、SD）—— 需先确认该介质的驱动**是否也访问 D3**。
4. **接受"保存 = 重启"**：若重启本身是可接受的语义，需把配置**先**写好、再看门狗复位后加载。

### 11.6 本轮顺带修掉的真缺陷（独立于 persist，仍然有效）

§10.4 列的 8 处 ITCM 落位（`hil_out_apply` 等）**是真缺陷**，本次实测确认：
ISR 现在能**完整跑到 ⑦ 出口**（`[40] = 0x7...`），不再卡在 `hil_out_apply`。
它影响的不只是 persist —— **任何 flash 操作期间**（OTA/参数区写入）都会咬人。

### 11.7 新增的诊断仪器（保留在固件里）

`main.c` 的 ISR 中新增细分检查点 ⑨⑩⑪⑫⑬（每拍 5 次 AXI store ≈ **5 周期/40000 = 0.0125%**），
把原来"只能落在 ④→⑤ 之间"的粒度细化到**单条语句**：
- ⑨ = `GPIOB` 写后（D2 对照）
- ⑩⑪ = `TIM2_SR` 读写前后（APB1/D2 对照）
- ⑫⑬ = `wdt_feed()` 前后（D3 判定）

读法：`0x22` 读 `BOOT_AXI[41]` 的**高 4 位 = 段号**。全过程不需要调试器。

## 12. 未闭合项的关闭路径（测试方案，2026-09-13 20:xx）

> §11 的"未闭合"有三件：① 机理未定案 ② 假设粒度不够细 ③ 修法未验证。
> 本节给出**每条都能失败**的实验，按代价从低到高。全部只用现有开关 + 现有工具。

### 12.1 先把假设说准（§11 的"D3 域"太粗）

实测地址表（`src/regs.h`）：

| 外设 | 基址 | 总线区 | 实测 |
|---|---|---|---|
| TIM2 | `0x40000000` | APB1 (D2) | ✓ 通过 |
| GPIOB | `0x58020400` | AHB4 (D3) | ✓ 通过 |
| **RTC** | `0x58004000` | **APB4 (D3)** | ✗ 卡 |
| **IWDG1** | `0x58004800` | **APB4 (D3)** | ✗ 卡 |
| **ADC1** | `0x40022000` | D3(映射在 D2 地址区) | **未测** ← 见 L2 |

⇒ **GPIOB 同样在 D3 却通过** ⇒ 不是"D3 域整体不可访问"，
而是 **`0x58004xxx` 这个低速 APB4 区**（RTC/IWDG/WWDG 所在，都跑在 LSI/LSE 独立时钟域）。
★ 修正后的假设：**擦 flash 期间，APB4 的跨时钟域访问无法完成**。

★ 另注：§11 的段 ⑥ 之后其实有**三个**候选（`adc_poll_kick` / `rtc_latch` / `bb_kick`），
现有检查点分不开 ⇒ L2 必须先补细分点。

### 12.2 L1 — 确认"喂狗是唯一障碍"（1 次构建，约 10 分钟）

```bash
bash build.sh -DDCL_PERSIST_SAVE=1 -DDCL_WDT=0     # 去掉看门狗
pyocd flash -t stm32h723xx -O connect_mode=under-reset build/dcl_h723.hex
python build/tmp/verify_persist3.py COM18
```

**判据（缺一不可；每条都能失败）：**
| # | 判据 | 读法 | 成立的含义 |
|---|---|---|---|
| a | **`writes > 0`** | `0x43` 应答 `r[20..24]` | 擦除能完成 ⇒ **喂狗(D3)确实是唯一障碍**（没人复位，ISR 卡住不阻碍主循环擦写） |
| b | 反向：擦除期间 `g_tick_count` **停滞** | `0x22` 读 SHM 两次对比 | ISR 真的卡住了（否则 a 的"成功"是别的原因） |
| c | 掉电语义：`reset` 后 `loaded_n > 0` | `0x43` 应答 `r[12]`/迁移后的 SHM | 配置真的存进去了，不只是"没被复位" |

★ **若 a 不成立** ⇒ 障碍不止喂狗 ⇒ 直接进 L2。
★ **这一步只能证明根因，不是修法** —— ISR 卡住本身仍是缺陷（拍周期断裂）。

### 12.2b ★★★ L1 实测结果（2026-09-13 20:2x）—— **通过，并修正了 §11 的假设**

```bash
bash build.sh -DDCL_PERSIST_SAVE=1 -DDCL_WDT=0 && pyocd flash ... && python build/tmp/L1.py COM18
```

```
0x43[1] 落盘   ⇒ sts=0, 耗时 0.97s
  应答 writes=1  dirty=0  ab=1  nr=128  err=0x0000     ★ 配置真的写进了 flash
启动次数 85 → 85                                          ★ 未复位
ISR 检查点: 本轮段=7 / 上轮段=7                            ★ ISR **没有卡住**
停滞自愈=0   主循环最大间隔=213拍(21ms)   HANG=无  DEFH=无
```

**三条结论：**
1. **判据 (a)(b)(d) 全绿** ⇒ **喂狗路径是唯一障碍**，`persist` 本身完全正常。
2. ★★ **推翻 §11.1 的"擦除期间 APB4 整体不可访问"**：`DCL_WDT=0` 时 **ISR 也跑到了 ⑦ 出口**。
   若 RTC 也卡，就到不了 ⑦ ⇒ **真正的元凶是 `wdt_feed()` 写 `IWDG_KR` 这一个动作**。
   ⚠️ 但 `rtc_latch` 自带降频门，**本次窗口内可能没到相位** ⇒ "RTC 不卡"**尚未证伪**，
   需 L2 的 ⑭⑮ 才能定论（见 12.3）。
3. **擦除端到端只要 0.97s**（此前记的 1.5s 是含 SD 刷盘的总量）
   ⇒ **IWDG 超时放到 2s 就足够覆盖** ⇒ **L3 修法可行性得到实测支持**。

**最终根因链（收敛版）：**
```
擦 flash → ISR 每拍 wdt_feed() 写 IWDG_KR → 该访问在擦除期间无法完成
  → ISR 卡住不返回 → 喂狗停 → 200ms 后 IWDG 复位 → 配置从未落盘
```

★ 副作用提醒：`DCL_WDT=0` 档下板子**无看门狗保护**，实验完须烧回交付档（见 12.6）。

### 12.3 L2 — 把 ⑥ 之后的三个候选分开（1 次构建，纯观测）

在 ISR 里补细分检查点（**只加观测，不改行为** —— 铁律 0）：
```c
ISR_CKPT(14);  adc_poll_kick();      /* ⑭ = adc 之后 */
ISR_CKPT(15);  rtc_latch();          /* ⑮ = rtc 之后 —— ★ APB4 判定点 */
```
**判据**：`BOOT_AXI[41]` 的高 4 位落在 ⑭/⑮/⑦ 哪一个 ⇒ 直接指出是 ADC、RTC 还是 bb_kick。

### 12.4 L3 — 验证修法（1~2 次构建）

**修法（唯一能同时保住"掉电保持"与"看门狗"的形状）：**
> 擦除前把 IWDG 超时**放大到 > 擦除时间**（如 2s），擦完立刻**恢复 200ms**；
> 同时擦除期间**跳过 RTC 刷新**（`rtc_latch` 内部加"擦除窗口内 return"）。

**可行性依据**：`wdt_start()`（`src/wdt.h:223-249`）已有**完整解锁序列**
（`IWDG_KR=0x5555` → 写 PR/RLR → 等 `IWDG_SR` 更新落），照抄成 `wdt_set_timeout_ms()` 即可；
`g_wdt_kr_busy` 闸门已解决"编程期间 ISR 喂狗"的竞态。**这两处都是现成零件。**

**判据（四条全过才算，缺一不可）：**
| # | 判据 | 读法 |
|---|---|---|
| 1 | `writes > 0` | `0x43` `r[20..24]` |
| 2 | **启动次数不变** | `0x22` 读 `BOOT_AXI[0]` |
| 3 | **ISR 检查点 = ⑦** | `0x22` 读 `BOOT_AXI[41]` 高位 |
| 4 | **`g_tick_count` 连续**（确定性未丢） | `0x22` 读 SHM，落盘前后各一次 |

★ **反向判据（最重要，防"把保护关了冒充修复"）：**
> 在**放大超时的窗口内**注入真卡死（`SD_CFG[13]=1` + 魔数）⇒ **看门狗必须仍能复位**。
> 若注入后不复位 ⇒ 这个修法是把"救命的门"改松了，**不能收**。

### 12.4b ★★★ L3 实测结果（2026-09-13 20:5x）—— **通过**

**实现**：`wdt_set_timeout_ms()`（`wdt.h`，照抄 `wdt_start()` 的解锁序列 + `g_wdt_kr_busy` 关闸）；
`persist_save()` 内擦写段开窗、**单一出口**（`out:`，与 `flash_lock` 同处）恢复。
开关 `DCL_WDT_PERSIST_WINDOW`（默认 **8000ms**，`=0` 即改前行为）。

**主档（窗口=8000）结果：**

## ★★★ 13. 落盘被打断的**真实后果**：flash 控制器异常 ⇒ 板子卡在复位入口

> ⚠️ **本节已重写（2026-09-13 21:3x）**。初版把根因写成"`persist_load` 读半擦扇区卡住"，
> **那是错的** —— 见 13.4 的更正说明。现象本身是**真的**，且能用纯协议复现。

### 13.1 现象（纯协议复现，零调试器介入）

对照档（`DCL_WDT_PERSIST_WINDOW=0`）下触发一次 `0x43[1]`：

```
落盘请求发出后 24s 内：0x22 / 0x01 **全部无应答**
（同一时刻的 python 进程没有任何 pyocd 操作 ⇒ 排除了"调试器把核 halt 了"这个混淆源）
```

### 13.2 现场（`connect_mode=halt` 读取，不复位）

```
pc = 0x08007af8     ← ★ Reset_Handler 的**第一条指令** `ldr r0,[pc,#76]` (读 flash 字面量)
lr = 0xFFFFFFFF
sp = 0x20020000     ← 栈顶 ⇒ Reset_Handler 刚设完 SP, **.bss 还没清**
CFSR = 0x00000000   HFSR = 0x00000000     ← **没有任何 fault**
g_stage = 4         ← 上一次启动的残留(.bss 未清 ⇒ 印证"卡在清 .bss 之前")
启动次数 111 → 112
```

**⇒ 它不是 HardFault，也不是看门狗复位 —— 是"读 flash 永不返回"，
CPU 停在 `Reset_Handler` 的第一条 flash 读上。**

### 13.3 结论：这是**平台级**后果，不是软件 bug

```
落盘 → 擦除进行中被打断（看门狗/复位/掉电）
  → FLASH 控制器进入异常态
  → 之后**任何** flash 读都不返回（包括取指、字面量池）
  → 上电即卡在 Reset_Handler, 协议自然无响应
```

**关键判据（两条，都实测过）：**
| 事实 | 证据 | 含义 |
|---|---|---|
| **坏扇区本身无害** | 带着"读返回 `0x00000000`"的扇区 A，板子**稳定运行 25s**：启动次数 111 恒定、`tick` 每 5s 精确 +50100 | `copy_valid()` 的 magic 检查**本来就挡得住** (`0x00000000 ≠ PERSIST_MAGIC`) ⇒ **`persist_load` 没问题** |
| **一次成功的擦除即可恢复** | `python tools/h723_persist.py --wipe` 之后 ⇒ **12 PASS / 0 FAIL** | flash 控制器**可恢复**，不是永久损坏 |

⇒ **唯一的恢复手段是"从外部完成一次成功的擦除"（调试器/编程器）。**
固件内部**无法自救**（它的代码本身就在读不了的 flash 里）。

### 13.4 更正说明（初版错在哪）

初版的推理链是"`g_stage = 4` ⇒ 卡在表装载 ⇒ `persist_load` 读半擦扇区卡住"。
**两处都错了**：
1. `g_stage = 4` 是**上一次**启动的残留（`.bss` 在卡住时还没清），不是"本次卡在这里"；
2. `persist_load` **本来就能容忍**坏扇区（13.3 第一条已实测）。

**⇒ 修法方向随之作废**："把 `persist_load` 改成有界可失败"**解决不了这个问题**
（问题不在它，且"读不返回"无法用 CRC 判据兜住）。
**能做的是预防**：让擦除**不被打断** —— 即 §12 的落盘窗口（已完成）。

### 13.5 对"能否默认开启 `DCL_PERSIST_SAVE`"的影响

**结论不变：不应默认开启**，但理由要改写：

- ~~"persist_load 有 bug 会变砖"~~ ⇒ **不是软件缺陷**
- ✅ **"H7 在擦除过程中失去供电/被打断 ⇒ FLASH 控制器异常 ⇒ 必须用调试器恢复"**
  —— 这是**平台级风险**，与固件写得好不好无关。

**⇒ 项目当初把"内部 flash 持久化"降级掉，从工程判断上是正确的。**
`DCL_WDT_PERSIST_WINDOW` 让"正常落盘"可用，但它**无法覆盖掉电**这一路；
若要在现场用掉电保持，应换**外部介质**（FRAM/EEPROM/SD），
或接受"掉电后需人工用编程器恢复"这一运维前提。
