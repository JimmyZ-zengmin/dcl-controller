# 路由表执行时间的**可算性**：方法、已确立的结构事实、与明确的未算部分

> **这份文档回答一个问题**：路由表程序的执行时间，**哪些部分可以被算出来**？
>
> 它与 `README.md`（TCM 周期确定性实验）的分工：
> · `README.md` 回答"**实测**下来稳不稳" ⇒ 已确立（典型拍 0.02~0.06 cyc 可复现）
> · **本文**回答"能不能**不靠实测**算出来" ⇒ 这是"确定性"能否成为**设计属性**的关键
>
> **本文的纪律**：只写**已经被结构证据支持**的东西。所有"还没算的"单独列在 §5，
> 并且**明确标注它是"未算"而不是"算不出"** —— 这两者完全不同。

---

## 1. 为什么选路由表：它是**为可算性**做的架构选择

常规 PLC 跑的是通用指令流：循环次数不定、间接跳转、递归、动态数据结构。
这四样恰好是通用 WCET 分析**四大难题**的来源。通用 IEC 61131-3 运行时之所以
只能靠"实测最坏值 + 安全系数"，根子就在这里。

**路由表把这四样全砍了**：

| 通用 WCET 难题 | 路由表的情况 |
|---|---|
| 循环边界分析 | **不需要**：19 个原语是定长体，路由表按拍展开成**线性序列** |
| 间接跳转 / 函数指针分派 | **已删除**（本项目刻意去掉间接分派） |
| 递归 | 无 |
| 不可行路径组合爆炸 | 路径数 = 1（线性序列，没有分支合流） |

⇒ **路由表在结构上就是一条"线性指令序列"，正是静态时序分析（STA）最擅长的形态。**

★ 这是本文最重要的一句话：**"可算"不是运气，是架构选出来的。**
所以下面所有工作都不是在"给通用程序硬套分析"，而是在**收割一个已经付过代价的设计决定**。

## 2. 方法：把 FPGA 的静态时序分析搬过来

FPGA 工具**从不跑电路**就知道一个时钟周期够不够。它做四件事：

```
1. 综合 → 逻辑网表（LUT / 进位链 / 触发器）
2. 每个原语有厂商标定的传播延迟（timing model）
3. 沿依赖链累加，取最长 = 关键路径
4. 关键路径 > 时钟周期 ⇒ 时序违例
```

★ 关键在于：**它不是仿真、不是实测、不是拟合。**
它靠 **"原语延迟已知 + 结构已知 ⇒ 路径延迟可沿结构累加"**。

对应到 Cortex-M7：

| FPGA | 本平台对应物 |
|---|---|
| LUT / 进位链 / 触发器 | 指令类（ALU / 乘 / **除** / 加载 / 存储 / 分支） |
| 厂商标定的原语延迟 | **ARM 文档化的指令执行时间**（Cortex-M7 TRM） |
| 网表 = 连接结构 | 反汇编得到的**控制流图 + 数据流图** |
| 关键路径 | 该拍执行的**最长依赖链** |
| 时钟周期约束 | **拍预算**（时基档 0 = 40000 cyc） |

⇒ **本平台的做法应当是**：逐原语取指令序列 → 按文档延迟赋权 → 沿依赖链累加 → 得结构成本。

★ 与"给界留安全系数"的区别（这是本文与既有做法的分界）：

| | 依据 | 门槛 | 能失败吗 |
|---|---|---|---|
| 观测路线 | 跑很多次取 `MAX` | 低 | ❌ 没观测到的更坏情况依然可能发生 ⇒ **假保证** |
| **结构路线（本文）** | 文档延迟 + 依赖链**推**出来 | 高 | ✅ 实测一旦超过界，就是一次真缺陷 |

## 3. 已确立的结构事实（**可复算，与板子无关**）

以下全部由 `build/dcl_h723` 反汇编得到，**不需要连板子**。

| # | 事实 | 数值 | 怎么得到的 |
|---|---|---|---|
| S1 | 扫描体规模 | `engine_scan_itcm` = **599 条指令**，0x0CF0..0x1578 | `objdump -d`（`tools/sta1_disasm.py`）|
| S2 | 扫描体**完全内联** | `prim_exec` **没有独立符号** —— 19 个原语体全部内联进扫描体 | 符号表（900 个符号里无 `prim_exec`）|
| S3 | op 分派是**跳转表** | 3 个 `tbh`：主分派 @0x0DF0（表 @0x0DF4，**18 项**）+ 子表 @0x0F80 / @0x11A0（各 **5 项**）| 表内容按"下一个基本块起址"截断后解析 |
| S4 | **分派语义精确** | `subs r6,#1` → `cmp r6,#17` → `bhi` → `tbh` ⇒ **表项 i 对应 op = i+1**；`OP_DIRECT`(0) 是 fall-through @0x0E56 | 0x0DEA..0x0DF0 的指令序列 |
| S5 | 指令类分布 | fp **220**(36.7%) · `?` 128 · ld 80 · alu 67 · br 57 · st 26 · mul 15 · move 6 | 分类直方图 |
| S6 | **CFG 可自动构建** | **71 个基本块**；`tbh` 目标可从 ELF 表数据精确解析 | `tools/sta10_pathcost.py` |
| S7 | ★ 循环结构 | 回边 = `b.n 0xDE6` @块6（尾块）→ **块3（分派块）**；循环前导 = 块0（44 条，只执行一次）；**每路由共用尾块 = 块6（27 条）** | CFG 打印 |
| S8 | **逐原语入口块可精确切出** | 19/19 个 op 有确定的入口块，大小 **4 ~ 29 条** | 跳转表 + 基本块划分 |
| S9 | 共享结构定量 | 分派块 3 个（含 2 个子表）、尾块 2 个（块6 被 17 个 op 到达） | CFG 可达统计 |

★ **S8 是本节最有价值的一条**：它说明"原语 ↔ 代码区间"的映射是**机器可判定的**，
不是靠人工标注。这意味着**结构量可以每次构建自动重算** —— 这正是 STA 能进构建闸门的前提。

### ★★ 4 个 CFG 陷阱（每一个都曾安静地给出**错误但看着正常**的结果）

这一段是本轮最该保留的东西。**四个坑全部导致"数字照常打印、结论完全错误"**：

| # | 陷阱 | 症状 | 正解 |
|---|---|---|---|
| **T1** | **按地址排序猜布局** | `LPF` 得 255 条、`PID` 7 条、`SR` 区间**为负** | 跳转表**项序 ≠ 代码布局序**；必须按控制流走 |
| **T2** | **`tbh` 没有后继** | 可达图在此断掉 ⇒ "可达 8 条"比自己的入口块（12 条）**还小**（自相矛盾却不报错） | `tbh` 的目标在**表数据**里，必须从 ELF 字节区解析 |
| **T3** | **表长靠猜** | 按固定 40 项读 ⇒ 把普通代码当表项 ⇒ 可达集膨胀到整个函数，**19 个 op 全部变成 283 条**；而 D2 判据**居然还"通过"**（预测值全同 ⇒ 残差只剩常数项）= **假绿** | 表是紧跟 `tbh` 的连续数据，用**下一个基本块起址**截断 |
| **T4** | **在带环图上求"最长路径"** | 尾块 → 分派块 → case → 尾块 构成环；DFS 触到深度上限后**返回 0**，而**不报错** | 环上最长路径**无定义**；必须换口径 |

> **教训（比结论更重要）**：这四类错误的共同形态是
> **"程序不崩、数字照出、结论全错"**。
> 本项目的既有纪律"判据必须能失败"在这里救不了 —— 因为**判据本身在跑，只是输入是错的**。
> 唯一有效的防线是**让每一步都能自相矛盾**：比如"可达条数 ⊇ 入口块条数"这条，
> 就是在 T2 上唯一亮红灯的地方（8 < 12）。⇒ **口径之间要互相约束。**

### 4.2 尝试一：指令类加权最小二乘 ⇒ ❌ **过定参数化，被自己推翻**

用 7 个指令类 + 总条数（8 个特征）在 19 个样本上做最小二乘，再做**留一交叉验证（LOO）**：

| 模型 | 中位 LOO 误差 | 最大 | 平均相对 |
|---|---|---|---|
| 类加权（8 特征） | **29.1 cyc** | 110.4 | 45.6% |
| 基线：只数指令条数（1 变量） | **5.6 cyc** | 64.8 | 13.1% |

而且拟合出的系数含**物理上不可能**的负值（`fp −4.60` / `alu −8.69`）。

⇒ **判据 FAIL 是对的**：8 个特征配 19 个样本是过定参数化，
负系数是过拟合的典型症状。**这条路线不能作为"结构→成本"的证据。**

> ★ 教训：**特征数必须与样本数相称。** LOO 是"能预测"与"只是拟合"的分界，
> 而它在这里直接把"加权"这一层否掉了 —— 而如果只看拟合内残差，它会"看起来很准"。

### 4.3 尝试二：单一结构常数（**零拟合自由度**） ⇒ ❌ 不成立

去掉全部自由度：`K = median(实测_i / 结构量_i)`（只是取中位，不是优化），
预测 `= K × 结构量`。这样残差是**真残差**。

### 4.4 ★★★ 结论：**没有一种"纯结构量"能解释实测成本**（这是本轮的硬结论）

四种口径全部试过，逐条列出（**同一个坑的四种表现**）：

| 结构量 | K | 中位\|残差\| | 最大 | 超25% | 判定 |
|---|---|---|---|---|---|
| 地址序区间（T1 污染） | 6.73 | 30.6 | 190.8 | **13/19** | ❌ |
| **入口块条数**（最干净） | 9.50 | **33.0** | 192.5 | **11/19** | ❌ |
| 可达闭包（T2/T3） | 1.744 | 3.9 | 62.1 | 3/19 | ⚠️ **假绿，见下** |
| 入口→尾块 路径集（T4） | 0.233 | 6.0 | 68.0 | 2/19 | ⚠️ **假绿，见下** |

**★ 后两行是假绿，必须点名**：它们之所以"看起来很好"，是因为
**在循环里，任何一个 case 都能经"尾块 → 分派块"到达其它所有 case**
⇒ 该口径对每个 op 都给出**几乎相同的数**（283 或 330 条）。
一个对谁都一样的预测值，其残差就只剩下"实测均值"这一项 ⇒ 中位残差自然小。
**这不是模型好，这是模型没有区分度。**（D3 的秩相关 ≈ 0 / 0.08 正是这个症状。）

⇒ **根因**：`P(入口) ∩ P⁻¹(尾块)` 里，`P⁻¹(尾块)` **就是整个函数**（谁都能走到尾块）。
所以"每路由执行哪些块"**在纯 CFG 可达性下不可恢复** ——
区分一条路由用的是哪个 case，靠的是**运行期的 op 值**，而那是数据，不是结构。

**⇒ 由此得到一条对方法本身重要的结论：**

> **纯控制流结构量不足以确定逐原语成本。**
> 要往下走，必须引入**数据流/操作数**信息（哪条指令吃哪个寄存器的值），
> 即从"块可达性"升级到**依赖链**（这正是 §2 里 STA 的第三步，也是 §5 的 N2）。

**唯一仍然站得住的弱结论**：入口块条数与实测成本的 **Spearman 秩相关 = 0.639**
⇒ 两者**正相关但不是充分统计量**（11/19 超 25%，且指令数多的 `CNT/EDGE` 明显被高估）。
⇒ "指令条数"这个量**有信息、但不够**。

### 4.5 尝试三：与指令条数无关的**方向**检查 ⇒ ✅ 一条弱但真实的结论

残差符号与入口块大小强相关（块大的 ⇒ 预测高估；块小的 ⇒ 低估），
说明"块条数"与"成本"的关系**不是线性**的，且大块里混有**执行不到的指令**
（条件分支的两侧都被算进了块）——这又一次指向**需要依赖链/路径可行性分析**。

N2/N8/N10 是**方法没做完**，N3/N4/N5 是**只能算界**
（但 FPGA 的 STA 本身算的就是最坏路径，所以这不构成路线问题），
N6/N7/N9 是**需要另外的实验**。

## 6. 一条必须同时修的前提：观测量与要解释的量不是同一个

**目前的实测 `di` 量的是整段 ISR，不是引擎扫描段。**

```
di = 引擎扫描 + bb_kick + adc_poll_kick + rtc_latch + i2c_sm_tick + 数据相关分支
```

⇒ 即使结构模型完美，它解释的也是"ISR 有多长"，而需求要的是**"这个程序要跑多少周期"**。

★ 已有的一条实测支持"这项可以减出来"：黑匣子开关（`0x39` op=4）做对照，
`--bb on/off` 两次测得 **1375.3 vs 1375.5 TB**（标准误 1.8）⇒ **`bb_kick` 每拍净成本 ≈ 0**，
即"逐个关掉拍内工作、看 `di` 变化"这条**减法的路子是可行的、且可控**。

⇒ **在结构模型成形之前或同时**，需要把扫描段单独夹出来（引擎内加一对时间戳）。
否则结构侧算出的数与实测侧的数**不是同一个量**，没法比对。

| **B** | 补全指令分类表（消掉 128 条 `?`） | `?` 应降到 <5%；每条 `?` 必须能被点名 | 未做，**便宜**，离线可做 |
| **A′** | ★ **把口径从"块可达性"升级到"依赖链"** —— 对每个 op 的入口块，沿 def-use 追寄存器/浮点寄存器的依赖，取**最长依赖链**的加权长度 | 依赖链长度与实测成本的 **Spearman 秩相关必须 > 0.8**；若仍 < 0.6 ⇒ 连依赖链也不够，**点名缺的是哪一类信息** | **真正的下一步**；依赖 B |
| **C** | 用 Cortex-M7 **文档延迟**（不是实测）给依赖链赋权 | 结构成本必须 **≤** 实测成本（方向性安全）；出现结构 < 实测 ⇒ 点名缺哪类延迟 | 依赖 A′, B |
| **D** | 把扫描段从整段 ISR 里夹出来（引擎内加一对时间戳） | 夹出的扫描段 + 已测拍内工作 ≈ 原来的 `di`（差 <5%）| 未做；**需烧一次实验档**，与 A′/B/C 无依赖 ⇒ 可并行 |
| **E** | 用 D 的数据重做 C 的比对 | 结构预测 vs 扫描段实测，在若干原语上逐一对齐 | 依赖 C, D |

★ **A′/B/C 完全不依赖板子，可以离线做**（只需要 ELF）。
★ **D 需要烧一次实验档**，属于"观测口径"的修正，可并行。

★ **为什么 A′ 是唯一出路（本轮最重要的方法论结论）**：
"哪条路由被处理"由**运行期的 op 值**决定，那是**数据**不是结构。
所以任何**只看控制流**的结构量（块数、可达集、路径集）都不可能区分原语 ——
必须把"指令吃哪个寄存器的值"这一层**数据流**纳进来，那才是 STA 里"路径延迟累加"的真正对象。

## 8. 这份文档目前**不**主张什么（防止被过度引用）

本文**尚不主张**：

1. ❌ 不主张"每个原语的执行时间已经能算出来" —— §4 的四种口径全部不成立
2. ❌ **不主张"指令条数/代码块大小能解释成本"** —— 入口块口径 **11/19 超 25%**，
   Spearman 仅 **0.639**（§4.4）
3. ❌ 不主张"路由表的可算性已经兑现" —— 目前只兑现到**结构可提取**（S1~S9）
4. ❌ **不主张"可达闭包/路径集口径效果好"** —— 那是**假绿**（§4.4：对每个 op 给出几乎相同的数，
   于是残差只剩常数项）。**这一条尤其要写下来，因为它看起来最漂亮。**

本文**可以主张**：

1. ✅ **结构是完全可提取、可复算的**（S1~S9，含 71 个基本块与 19 个 op 入口块，机器可判定）
2. ✅ **"可算"是架构选择的结果**：路由表把通用 WCET 的四大难题全部绕开（§1）
3. ✅ **方法路线已明确**（FPGA STA 四步对应，§2），且**已证伪三条捷径**
   （地址序布局、指令类加权回归、纯 CFG 结构量）
4. ✅ **未算的部分被明确列出并分类**（§5，10 项），**没有一项被证明"算不出来"**
5. ✅ ★ **纯控制流结构量不足，必须上依赖链**（§4.4）—— 这是一条**方法层面的实质结论**，
   它把下一步从"再试一种结构量"收敛成"去做数据流分析"

> ★ 最后一句是本文最需要的态度：**"还没算"和"算不出来"是两件事。**
> 本文的价值主要在于把前者**逐条列清并给出判据**，而不是给出一个漂亮的总数。
