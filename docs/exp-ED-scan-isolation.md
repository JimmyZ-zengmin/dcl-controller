# E-D 结果：扫描段已从整段 ISR 中夹出（2026-09-18）

> 固件改动：`main.c` 在 `engine_tick()` 调用**前后**各取一次 `tb_cyc()`（那两个读本来就存在），
> 差值写进新 SHM 域 `OFF_SCAN_CYC_*`（`0x3800` 起，`engine.h`）。
> 工具：`tools/exp_ed.py`。

## 1. 结果

| 配置 | 扫描段均值 | 整段 ISR 均值 | **拍内其它工作** | 其它占比 |
|---|---|---|---|---|
| PID div0 n=128（`nrun=128`） | 8315.1 TB | 8790.9 TB | **475.9 TB (952 cyc)** | 5.4% |
| DIRECT div0 n=128（`nrun=128`） | 3877.1 TB | 4351.7 TB | **474.6 TB (949 cyc)** | 10.9% |
| PID div1 n=128（`nrun=13`） | 942.3 TB | 1415.7 TB | **473.4 TB (947 cyc)** | **33.4%** |

★★ **"拍内其它工作"三次测量 = 475.9 / 474.6 / 473.4 TB（极差 2.5 TB = 5 cyc）。**

这是一个**新的、干净的常数**：**每拍固定 474 TB = 948 cyc**，
与程序、原语、条数**全都无关**（三组配置的 op/div/n 各不相同，而它不变）。

### 判据

| 判据 | 结果 |
|---|---|
| **D-1** 扫描段 + 其它 ≈ 整段 | ✅ 恒等式成立（定义如此）；关键是"其它"只有 **5.4%~33.4%** |
| **D-3 ★ 反证** STOP 后扫描段拍数冻结 | ✅ **16724 → 16724**（1.2 s 内不涨）⇒ 夹取点确实在引擎门之后 |
| D-4 `nrun` 与扫描段同批读出 | ✅ 同一 `0x22` 突发 |

★ **D-3 是这一步最重要的判据**：它排除了"夹错位置"（夹到一个与引擎无关的量上）。
若 STOP 后拍数仍在涨，说明夹的是别的东西 —— 而那种错**在数值上看不出来**。

## 2. 这一步修好了什么

**§5.47 记的"观测口径不一致"已经被解掉。**

此前所有实验用 `di`（整段 ISR）去对"结构侧算出的引擎成本"—— **两边不是同一个量**。
现在有了 `OFF_SCAN_CYC_*`，结构侧可以直接对**扫描段**。

而"其它 474 TB"的量级说明了这个错有多要紧：
- 对 PID div0（扫描段 8315）它只占 5.4% ⇒ 影响小
- 对 PID div1（扫描段 942）它占 **33.4%** ⇒ **用 `di` 会比出一个 50% 的假偏差**

⇒ **越是"轻"的程序，用 `di` 的偏差越大。** 这正是为什么轻载下拟合会失真。

## 5. 一个必须记下的教训：**硬编码的 SHM 地址随构建静默失效**

- 加 E-D 的 SCAN 域后 `g_shm` 从 **`0x20004E80`** 移到 **`0x20004EA0`**（+32 字节，正好是新域大小）。
- 而 `tools/h723_tick_ring.py` 与 `tools/exp_ed.py` 里都写着
  `SHM_SEEN = 0x20004E80`（当年**刻意**硬编码，为了让"自证探针"能放在任何帧之前）。
- 症状：工具读到垃圾（`环写=927865394 / tick=0`）⇒ 报 **"板子不健康 ⇒ 判无效"**。
  **而板上完全正常**：`samples` 在涨、`run=1`、`n_routes=128`。
- ⇒ **这是 §5.42「工具的隐含前提会随固件改变而静默失效」的第二次实证**，
  而且这次伪装成了"板子坏了"—— 正是本项目最警惕的那类误归因。

**修法**：地址一律**问 `0x38` 要**（那正是 `0x38` 的用途）。
代价是"自证探针"不能放在 `0x38` 之前 —— 但那个探针的**历史使命已完成**
（它一次就证明了"板子在发帧之前就已在复位态"），结论已进文档，不必再用硬编码换它。

## 6. 与 E-A/E-B/E-C 的关系

E-A~E-C 用的都是 `di`（整段 ISR）。由本步可知：

```
di = 扫描段 + 474 TB（每拍固定，与程序无关）
```

⇒ **那三组实验的结论需要重新解读**：
- `nrun` 的**斜率**（每路由边际成本）**不受影响** —— 474 TB 是常数，对斜率无贡献
  （两侧相减时约掉）⇒ **E-C 的 `m_op` 全表仍然有效**
- 但**截距**被抬高了 474 TB ⇒ E-A 拟合出的 `C_base ≈ 583 TB`
  其实是 **扫描段自身的常数**，而不是"每拍总线固定开销"。
  **这一点在 E-D 之前是分不清的。**

★ 下一版模型应写成：

```
di(t)      = C_scan + m_op × nrun(t) + C_other
             ↑         ↑                ↑
        扫描段常数   每路由边际      474 TB（已实测，三组一致）
```

## 7. ★★ E-E 的前提检查：我点名的那个目标**是错的**

E-E 原计划"把 `read_source()` 的运行期分派改成部署期预解析"，判据是
`C_route` 应下降 **≥15 cyc**。**在设计判据之前我没有读 `read_source` 的实现。**

**读了之后**（`engine.c:223`）：

```c
AINLINE float read_source(uint8_t st, uint8_t si, const float *sm, const float *wm,
                          const uint8_t *base)
{
    switch (st) {
        case SRC_SENSOR: return sm[si & (MAX_SENSORS - 1)];
        case SRC_WIRE:   return wm[si & (MAX_WIRES - 1)];
        case SRC_CONST:  return ((const ParamEntry_t *)(base + OFF_PARAM_TABLE ...))->value_a;
        case SRC_HMI:    return 0.0f;
        default:         return 0.0f;
    }
}
```

- 它是 `AINLINE` ⇒ **内联进扫描体**（与 `prim_exec` 同款，见 S2）
- 它是一个 **4 路 switch** ⇒ 编译成 `cmp / bhi / tbh` + 三个体
  ⇒ **约 3~5 条指令**，不是一个几十周期的间接分派

⇒ **E-E 的判据 E-1（≥15 cyc）建立在错误的数量级上。**
若照原计划做，它**必然失败**，而失败原因与"解释税"假设**毫无关系** ——
这正是本项目最恨的那类结果：**判据口径错 ⇒ 伪装成"被测对象坏"**（§5.41）。

★ **教训（与 §5.44 / §5.49 同族）**：**判据的数值阈值必须来自对被测代码的实际阅读，
不能来自对它的想象。** 我用"猜测的指令条数"定了一个阈值，而没有先反汇编它。

### 从这一读还得到一条**定量**修正

把前导里各段的**实际指令数**（由反汇编读出）与文档占用重估：

| 段 | 指令数 | 占用量级 |
|---|---|---|
| `read_source` 分派 | ~4 | ~5 cyc |
| `period → dv → dt` 三档 | ~4 | ~4 cyc |
| `ACTIVE` 判定 | 2~3 | ~3 cyc |
| `param` / `state` 地址计算 | ~5 | ~6 cyc |
| `wire2_valid` | ~3 | ~3 cyc |
| `_finite_f` × 2 | ~8 | ~10 cyc |
| 分派 + 尾块（写回/推进） | ~25 | ~30 cyc |
| **合计** | **~50** | **~61 cyc/路由** |

★ 这个 **~61 cyc/路由**与 E-C 实测的 **PID `m_op` = 64.0 TB = 128 cyc**、
以及 E-A 的每路由边际 **~60 TB = 120 cyc** 是**同量级**；
而它与"每拍常数 583 TB"**不是一回事**。

⇒ **"解释税"这个说法方向对，但我把它的量级和位置都说错了。**
在那 583 TB 的每拍常数里，**没有任何单独一段是大头**；
它是**几十条零散指令的总和**。

⇒ **E-E 的正确形态应当是"整体重构成执行计划"，而不是"改 `read_source` 一处"**；
而它的收益上界也不再是"15 cyc"，而需要**先算出每段各占多少**再定。

**⇒ E-E 暂停，改为先做 §8 的 E-E1（测量侧），再决定要不要动架构。**

## 8. 下一步：E-E1 —— 用**扫描段**重标定，而不是用 `di`

### 为什么这是当前最高优先级

E-D 刚刚给了我们**正确的观测口径**（扫描段），而 E-A~E-C 的常数**全部是在错误口径下标的**。
在动架构之前，应当先用正确口径把模型重标一遍 —— 因为：

1. **成本极低**：不需要改固件（扫描段域已经在板上），只是把 `h723_tick_ring.py` 的
   读数从 `di`（0x3860/0x3868 那一对）换成扫描段（0x3810/0x380C 那一对）
2. **它可能直接改变结论**：E-C 的 `m_op` 全表虽然**斜率不受 474 TB 常数影响**，
   但**截距**与**逐 op 的 c0_op** 都会平移 ⇒ 需要重标一次才算准
3. **它是 E-E 的前置**：不知道"每段各占多少"，就无法给 E-E 定一个**有依据的**阈值

### 判据（都能失败）

- **E-E1-1** 用扫描段重标的模型，预测**未参与标定**的配置，偏差 ≤ **20 cyc**
  （比 E-A 的 40 TB 判据更严 —— 因为口径干净了，没有 474 TB 的干扰）
- **E-E1-2** 重标后的 `C_scan` 应 ≈ **583 TB**（E-A 在 `di` 口径下拟合出的截距）
  —— ★ 这条**自洽性判据**能验证"474 TB 是常数"这个结论：
  若 `C_scan` 与 583 差很多，说明 474 不是常数
- **E-E1-3** `m_op` 重标后应与 E-C 的值**同量级**（差 ≤15%）
  —— 斜率本不该受常数项影响；若变了，说明 E-C 的取数有问题

### 只有 E-E1 做完之后，E-E 才该定阈值

E-E1 会给出"每拍常数 583 TB 里，逐段各占多少"的**测量侧**下界；
那时 E-E 的判据才有依据可写。

★ **本条与 §7 的关系**：§7 说明 E-E 原判据是错的；E-E1 是**把它修对的第一步**。

## 9. ★★★ E-E1 结果：口径修好，模型第一次**自洽**

24 个配置（2 op × 3 division × 4 n），扫描段与整段**同一次突发**读。

### 9.1 「其它」再次被测出来，而且**比 E-D 更硬**

24 个配置的"其它"= **473.0 ~ 478.6 TB**，极差 **5.6 TB（11 cyc）**。

| | 范围 |
|---|---|
| E-D（3 个配置） | 473.4 ~ 475.9 TB |
| **E-E1（24 个配置）** | **473.0 ~ 478.6 TB** |

⇒ **每拍固定 474 TB（948 cyc），与 op / division / 条数全都无关** —— 这条现在是**硬的**。

### 9.2 ★★ 用扫描段重标，`m_op` **逐位复现 E-C**

| op | 本次 `m`（扫描段口径） | E-C `m`（`di` 口径） | 差 |
|---|---|---|---|
| PID | **64.24** TB/条 | 64.00 | **0.4%** |
| DIRECT | **29.52** TB/条 | 29.51 | **0.0%** |

⇒ **E-E1-3 通过**，而且是"逐位复现"级别的。
★ 这同时反验了一件事：**斜率确实不受那 474 TB 常数影响**（常数相减约掉）。

### 9.3 ★★★ 自洽性：我原来的判据**写错了**，改对之后它成立

**原判据 E-E1-2** 写的是"`C_scan` 应 ≈ 583 TB"（E-A 在 `di` 口径下的截距）。
实测 `C_scan` = **100.5 (PID) / 99.0 (DIRECT)** ⇒ 判据报 ❌ 差 482 TB。

**但这个判据本身是错的。** 让我把账算清：

```
E-A 拟合的是 di（整段 ISR）:
    di = C_base + m × nrun          且实测 C_base ≈ 583 TB

E-D/E-E1 把 di 拆开了:
    di = 扫描段 + 474 TB
    扫描段 = C_scan + m × nrun      且本次实测 C_scan ≈ 100 TB

⇒ 自洽的判据应当是:
    C_scan + 474 ≈ C_base     即   100 + 474 = 574  ≈  583   ✓（差 1.5%）
```

⇒ **修正后的判据成立，误差 1.5%。**

★★ **"474 TB 是常数"这个结论没有被动摇** —— 动摇的是我**自己的判据**：
我把"扫描段的截距"误当成了"整段 ISR 的截距"。
⇒ **这一条与 §5.41「判据口径必须与被测对象自洽」是同一族**：
**换了测量口径，判据的参照值也必须跟着换。**

### 9.4 修正后的模型（第一次三项闭合）

```
di(t)      = C_scan   + m_op × nrun(t)  +  C_other
             ~100 TB     查表            474 TB（24 配置实测, 极差 11 cyc）
             (200 cyc)                   (948 cyc)
```

- **三项全部有实测支撑**
- `m_op` 是 **19 个原语的常数表**（E-C 全表 + 本次复现）
- `C_other = 474 TB` 是**与程序无关的硬常数**（24 个配置一致）
- `C_scan ≈ 100 TB` 是扫描段自身的每拍常数

⇒ **一次标定（38 + 2 个数），之后任何程序的每拍成本都可从 `nrun` 算出。**

### 9.5 留点预测：1/8 超差，且原因已定位

| op | 结果 |
|---|---|
| DIRECT | **0/4 超差** ✅（最大偏差 +6.6 TB）|
| PID | 1/4 超差（n=128, +41.1 TB）❌ |

★ **PID n=128 那一点是"量化伪影"**：div2 下 `nrun` 只有 0 或 1
（实测该点的 `nrun` 读数就是 1），**依赖一个 ±1 量化的自变量去预测 200 TB 的量**，
残差自然落在 20~40 TB 量级。这不是模型错，是**自变量在该点几乎没有分辨率**。

⇒ 诚实记法：**E-E1-1 在 DIRECT 上通过、在 PID 上 1/4 超差，超差点已归因于量化。**
不修判据去让它"通过" —— 而是记下"div2 区的 `nrun` 分辨率不足"这个事实。

### 9.6 新登记：div2 下 `nrun` 是**每拍取整**的伪影源

观察到的 `nrun`（每拍条数）：

| division | n=16 | n=32 | n=64 | n=128 |
|---|---|---|---|---|
| div0 | 16 | 32 | 64 | 128 |
| div1 | 2 | 4 | 7 | 13 |
| **div2** | **0** | **0** | **1** | **1** |

★ div2 下 `nrun` 是 `⌈n/100⌉` 取整 ⇒ **`n=16` 与 `n=32` 的 `nrun` 都是 0**，
但实测扫描段是 82.3 与 102.2 TB（**差 20 TB**）。
⇒ **同一个 `nrun` 下成本不同** ⇒ 说明 `nrun` 在极稀疏区**不是充分统计量**
（那时"有几个桶非空"这件事开始起作用 —— 而在 `nrun ≥ 1` 的区间它被掩盖了）。

★ 这条**登记为未决项**，不强行解释。它也是 E-B 那条"桶数不花钱"结论的**适用边界**：
E-B 是在 `nrun = 1` 下测的（桶数 1/10/100），而**极稀疏区（`nrun < 1`）没测过**。
