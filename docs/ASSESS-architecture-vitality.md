## 1. 三件"我们赌对了"的事（有外部证据）

### 1.1 循环 + 静态 vs 事件驱动 —— 我们的选择正是学界的批评所指

IEC 61499 把功能块改成**事件驱动激活**，学术界的长期批评正是
"事件驱动的 FB 激活会带来可确定性/状态一致性上的麻烦"
（[IEC 61499 vs 61131: A Comparison Based on Misperceptions](https://www.semanticscholar.org/reader/afeb9999fd3848988b5bf54ea9a3c8bdfcfdc2b5) ·
[arXiv 1303.4761](http://arxiv.org/ftp/arxiv/papers/1303/1303.4761.pdf)）。
而 PLC 的立身之本就是**循环执行**（"application code is executed in cycles"，
[Ulm 论文](http://dbis.eprints.uni-ulm.de/id/eprint/1576/1/BA_Goest_2017.pdf)）。

⇒ **我们是这条线的极端版本**：不但循环，而且**没有调度器**、没有任务、逻辑是表。
所以"每拍成本可算"不是优化出来的，是**结构给的**。

### 1.2 "算 WCET"是几十年的难题 —— 我们绕开了它，而不是解决它

WCET 分析有专门的研究社区与年度会议（[WCET 2017 论文集](https://drops.dagstuhl.de/storage/01oasics/oasics-vol057_wcet2017/OASIcs.WCET.2017/OASIcs.WCET.2017.pdf)），
控制回路的 WCET 分解也是被研究过的对象（把 loop WCET 拆成各组件 WCET，
[Lund 论文](https://lucris.lub.lu.se/ws/portalfiles/portal/4564815/627737.pdf)）。

⇒ 我们的做法**不是**更好的静态分析，而是**把问题变小**：
逻辑=静态表 ⇒ 没有间接跳转/递归/动态派发 ⇒ 成本 = `C_other + C_scan(op) + Σ m_op + k×转变`，
每一项**实测标定**，且有一个**会拒绝的门**。★ 诚实：这是**标定**不是纯计算（`docs/exp-EF` 负结果）。

### 1.3 TCM 是 M7 上"确定性"的标准基础设施 —— 但我们把它做成了**判据**

Cortex-M7 的 TCM 用法（ITCM 放热代码、DTCM 放热数据、零等待且无 cache 不确定性）
是厂商文档级别的共识（[Microchip：Cortex-M7 MCU 上的紧耦合存储器](https://microchip.com.cn/newcommunity/index.php?m=Download&a=showfile&id=2878) ·
[ST 应用笔记](https://www.st.com/resource/en/application_note/dm01049271.pdf)）。

⇒ 差异点不在"用了 TCM"，而在 **"ISR 可达闭包 ⇒ 必须落在 ITCM"是构建期机械判据**
（`gate_isr_itcm.py`：4 个真实 ISR 根 / 44 个函数 / 437 个字面量自证），
**而主流 RTOS 生态里这一步通常是纪律 + 手工 `__ramfunc` 标注**（★ 推断，未见到反例）。

## 2. 从现有地基能长出来的七条（**架构生命力**）

每条给：**地基在哪 → 长出来是什么 → 缺什么 → 代价/触发条件**。

### L1 容量动态化（配置期动态 · 运行期静态）
- **地基**：容量已从 `src/engine.h` 派生（C 期）；引擎表已经按 `n_routes/n_params/n_states` 工作。
- **长出来**：一个 34 条路由的程序**不再需要 128 条的地址空间** ⇒ TCM 可以被别的域借用。
- **缺什么**：S1 把上限变构建参数（便宜）· S2 把未用上限声明为可借用 · S3 部署期按需裁（动 23 条断言）。
- **详细方案**：`docs/MEMORY-USAGE.md` §3。触发条件 = E 期。

### L2 多轴 / 多实例
- **地基**：`step.c` 的算法已验证；**ITCM 只用了 22.4%（还空 49.7 KB 连续）**——
  "ITCM 已满"是**过期数字**（`RETRACTIONS` P33，已更正）。
- **长出来**：`step.c` 单例 → 实例化 + ③层做插补 ⇒ 2~4 轴。
- **缺什么**：① 第二编码器（AS5600 地址固定 `0x36` ⇒ I2C mux 或第二总线）② 第二驱动器（**采购**）
  ③ SHM 参数化（若轴数多）。
- **代价/触发**：★ **不急**（用户 2026-09-19）。它会立刻吃掉 ITCM/SHM 余量 ⇒ 与 L1 联动。

### L3 运动学上游：凸轮 / 飞剪
- **地基**：固件斜坡已落地 + ③层能表达曲线（三角波/正弦已验证）+ `sub=17` 斜坡语义已修。
- **长出来**：电子凸轮/飞剪 —— 主从同步 + 每拍查表。
- **缺什么**：**反馈更新率**（当前阻塞式 ~163 Hz / 拍内 ~1 kHz）；
  飞剪要求与线编码器紧同步 ⇒ 需提高编码器采样率或做硬件捕获。
- **★ 这一条是"能表达但撑不住"，如实标注。**

### L4 时序域：多通道 µs 级触发序列
- **地基**：19 原语 + 桶化分档（1/10/64 拍）+ 输出面（DO/PWM/wire）。
- **长出来**：测试/老化设备、点胶/涂布、灌装的**配方化时序**（换型不停机）。
- **缺什么**：几乎没有 —— 这是**当前地基最直接能变现的一格**（见 §3 滩头）。
- **代价**：需要工艺侧的现场验证（我们还没有客户案例）。

### L5 安全子集（不做安全 PLC，做"逻辑安全"）
- **地基**：声明的时间量 = 跑出来的（46 条判据）· 装置配置 fail-closed · 停机安全态已注册。
- **长出来**：把"**声明的时间预算**"当安全论证的一部分（"这一拍一定跑得完"是可证明的，
  而不是"通常跑得完"）。
- **缺什么**：双通道/CRC 黑通道、诊断覆盖率、认证流程 ⇒ **不能宣称是安全控制器**。
- **定位**：作为**安全 PLC 的下层**（外挂安全继电器/安全 PLC 兜人身安全）。

### L6 现场总线接入（②层能力位的推广）
- **地基**：②层已有"**器件即数据**"（下发"每 N 拍读 地址/寄存器/长度 → 写 SENSOR[z]"）。
- **长出来**：把 EtherCAT / CANopen / OPC UA FX 适配器做成**又一个 ②层能力位**
  ⇒ **接现场总线 = 下载一段配置**，而不是改 ③ 层程序。
- **缺什么**：★ 这是**产品化最大的非控制缺口**（我们现在只有 Modbus RTU）。
  生态对手的主战场就在这（EtherCAT 全球节点已超 **8800 万**，
  [ETG 2025 数据](http://dataclouds.cninfo.com.cn/shgonggao/2025/2025-08-28/d244243c833511f09b83fa163e957f7a.pdf#35#3)；
  现场级互操作标准在往 [OPC UA FX](https://www.automaatioseura.fi/site/assets/files/4874/opc_day_finland_2025_peter_lutz.pdf) 走）。

### L7 判据即产品（"出厂验收证据包"）
- **地基**：169 个工具 · 7 道构建闸门 · **撤回台账**（P1~P33）· 交付档指纹 · 台架依赖登记表。
- **长出来**：每台设备随附"**可复跑的验收证据**"（判据清单 + 指纹 + 怎么复跑）——
  在受监管行业这是**可付费的差异**，而对手基本给不出。
- **缺什么**：把工具收敛成面向交付的"一条命令 + 一份报告"（现在偏工程内部视角）。

## 3. 外部坐标下的定位（一句话）

| 阵营 | 周期/确定性口径 | 逻辑可编程性 | 我们的位置 |
|---|---|---|---|
| **PLC**（循环、ms 级） | 事后监视（周期超时进 STOP） | 强（符号化、在线下载**块级**） | **我们更短、可预算**；但生态/网络/安全弱 |
| **RTOS** | 有界**延迟**（优先级 + 有界 ISR） | 代码（重编重烧） | **我们给每拍成本；它给"多久轮到我"** —— 量的不是同一个量 |
| **专用运动控制器** | 伺服环 µs 级 | 参数化（封闭） | **我们让逻辑可热更**；它多轴/插补/驱动更强 |
| **虚拟 PLC / 软件定义**（[S7-1500V vs TwinCAT vs PLCnext](https://industrialmonitordirect.com/zh-hans/blogs/knowledgebase/selecting-a-virtual-plc-s7-1500v-twincat-and-plcnext-control)） | x86/容器，靠 hypervisor 隔离抖动 | 强 | **它是"把抖动关掉"，我们是"不藏抖动"** |
| **FPGA / SoC** | ns 级固定功能 | 不可热更（重新综合） | 逻辑可热更是我们独有 |

**我们的独有格子（两个条件同时满足才成立）**：
**"每拍成本可算 + 有会拒绝的门"** 且 **"控制逻辑是数据、热更 ≤1 拍"**。
⇒ 定位句：**不是更快的 RTOS，也不是通用 PLC 替代品；是"可证明时间预算 + 不停机换型"的控制节点。**

## 4. 会杀死这套架构的三件事（诚实）

1. **把逻辑复杂度推到 ③ 层表达不了**（19 原语、无循环/取模/子程序）⇒ 用户被迫回到固件层，
   热更与静态审计同时失效。★ **这是我们当前真正的天花板。**
2. **把周期往上推**（比如为了省事做成 1 ms）⇒ 与 PLC 正面竞争，失去唯一的物理优势。
3. **把不可信程序放进来** ⇒ 需要 MPU/分区/隔离 ⇒ 架构复杂度跃升，且"成本可算"要重新论证。

## 5. 建议的下一步（按"地基→可长"排序）

1. **L4 时序域**当第一个滩头（地基最直接、缺的最少）——但需要一家真实工艺做验证。
2. **L1 容量动态化 S1**（把上限变构建参数）——便宜，且是 L2 的前置。
3. **L7 验收证据包**——把已有的判据资产变成对外可交付物。
4. **L6 现场总线**是产品化的**最大缺口**，但也是投入最大的；要按客户需求选一条（Modbus TCP → CANopen → EtherCAT）。
5. **L2 多轴 / L5 安全**：不急（用户已定）。
