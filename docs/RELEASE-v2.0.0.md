## 1. 这一版的主线：**DCL 程序持久化全链打通**

在此之前"用这个系统"隐含等于"改固件 + 重新烧录"。本版把**程序变成资产**：

```
写 .dcl 源 → dclc 编译 → 通信上传(0x45/46/47) → 落 SD 卡 A/B 双副本
           → 上电自动装载进引擎          （全程不碰 flash 烧录）
```

新命令：`0x45 PROG_BEGIN` · `0x46 PROG_DATA` · `0x47 PROG_COMMIT` ·
`0x48 PROG_STATUS`(96B) · `0x49 PROG_ERASE` · `0x4A DEVICE_DESC`

**实测**（上机，非推断）：`上传 → 复位` ⇒ `boot_loaded=1`、`0x38 n_routes=7 applied=1` ✓

### 1.1 "上传不能漏错" —— 五道闸

| # | 闸 | 失败处置 |
|---|---|---|
| 1 | 传输层 CRC16 | 拒收 |
| 2 | 清单级 CRC32 + `total_len` | 拒绝 COMMIT |
| 3 | 写完立即回读 `memcmp` | 该副本作废，不更新 seq |
| 4 | A/B 双副本 + 单调 seq | 开机取 seq 大且 CRC 通过者 |
| 5 | ★ **装载前重跑"上传时同一套静态校验"** | **拒绝装载**，保持旧程序；暴露 `prog_state` |

第 5 道是最要命的一条：程序可能在卡上躺几个月，或因**换了一个固件**而失效。
⇒ 上传与装载调**同一个函数**（`prog_validate`），不是两份实现。

### 1.2 SD 分区（日志不再覆盖程序）

`LBA0` 日志头（扩展段 `LOG_END`）· `LBA1..LOG_END` 日志环 · 卡尾 `PROG_A/B` 各 16 块 · 余量。
**旧卡无 `LOG_END` 字段 ⇒ 退化为现状，行为不变、不毁卡**（向后兼容）。

## 2. ★ 破坏性变更（**升级必读**）

> **`0x38 ENGINE_STATUS` 应答：39 → 51 字节**
> 尾部新增 3 个 u32：`uart_ore`（UART 溢出）/ `uart_drop`（接收环满丢弃）/ `frame_bad`（坏帧）。
> **前 31 字节的布局与语义一个字没动** ⇒ 按 `len >= 39` 或按绝对偏移读前 39 字节的客户端**仍然兼容**；
> **只有"长度必须恰好 39"的客户端会失效。**

加这三个量的理由：`RX_RING_SZ=512` 而协议允许 6150 字节载荷，主循环阻塞期间到达的字节会被
**丢弃并截断帧**，而这两个计数原来**只进全局量、不进任何应答面** ⇒ "帧被截断"在协议面上
**完全不可见**。加完之后，"固件拒绝"与"数据没到全"才能分开 —— 否则两者在读数上一模一样。

## 3. 本版修掉的缺陷

| # | 缺陷 | 性质 |
|---|---|---|
| 1 | **交付档下 DO 0..7 是死的** | 切 `DCL_DO_LATCH=0` 时漏了"停掉锁存链"：MDMA 每 100 µs 把恒 0 的影子锁进 `GPIOE_ODR` 低字节 ⇒ PE0~PE7 被静默清零。**观测面完全看不出来**（寄存器读回全对、写计数照涨）|
| 2 | **`0x38` 应答栈越界 11 字节** | 扩长度时只改了写的偏移、没同步改缓冲声明。修法不是"把 40 改成 51"，而是**一个常量同时定缓冲与发送长度**（`ENG_STATUS_LEN`）|
| 3 | `sd_read_block` 早前按 HAL 骨架重写导致整条 SD 路崩 | 保留 IDMA 原实现 + 两处最小修复（只认 `DATAEND`、读完关干净数据通路）|
| 4 | 程序载荷缓冲在 DTCM ⇒ 写超时 | SDMMC 的 IDMA **读不到 TCM 端口** ⇒ 移到 AXI |
| 5 | 程序缓冲撞进黑匣子环 | `BB_SLOTS` 512→960 后环铺满 AXI 中部 ⇒ 加**构建期 `#if/#error`** 守唯一空档 |
| 6 | `SD_TMOUT_DATA` 被挤小 ⇒ 正常批写被判超时 | 超时给够 + 调用方声明阻塞窗口（`block_window_begin/end`）|

## 4. 本版新增的三道**静态**构建闸门

`bash build.sh` 现在**零警告 + 三道闸门**，任一不过即拒绝通过：

| 闸门 | 防的是什么 |
|---|---|
| **ISR 调用树** | ISR 可达却没住 ITCM ⇒ 擦 flash 时拍 ISR 取指被 stall ⇒ 喂狗停 ⇒ 复位（此路径曾活过 4 轮审计）|
| **应答缓冲区越界** | `ack()/put32` 写入长度 > 局部缓冲声明。**同类已犯两次**，且**运行期完全不可见**（读回的字段全是合理值）⇒ 只能静态判 |
| **③层静态判据** | 程序里出现**引脚号/总线地址/寄存器名**。三边权威独立确认（IEC 61131-3 / CODESYS / Zephyr）|

★ 三个工具都**自带 `--selftest` 夹具**与**覆盖度自报**（0 文件/覆盖不足 ⇒ 判据判为**无效**而非"干净"）。
这不是洁癖：其中两个工具**第一版自己就是空判据**（一个函数都没解析到却打印 `[OK]`；
另一个因"引脚名只在注释里"会把合法文档打成违规）。**"0 发现"与"根本没扫"必须能区分开。**

## 5. 回归证据（上机）

**12 套件全跑**，与基线逐项对照；对两处差异做了**对称 A/B**（同板、同判据、同一固定板态，
只差待测改动）：

| 套件 | 改前 `255ec8c` | 改后（本版） |
|---|---|---|
| `h723_w2_probe` | 13 PASS / 1 FAIL | 14 PASS / 0 FAIL |
| `h723_persist` | 7 PASS / 19 FAIL | **7 PASS / 19 FAIL（逐项相同）** |

★ **两处必须说清的事**：

1. **`h723_w2_probe` 本身是非确定的** —— 同一固件连跑三次得到 **13/1、11/3、13/1**。
   ⇒ 它的 PASS 计数**不能当细粒度回归指标**用；只有"**没有新的失败模式**"才是判据。
2. 曾出现 `w2_probe` 11/3 与"表=0 条/7 条"的现象，**根因是板态而非代码**：
   我上一轮为"全链验收"往 SD 上传了 `hiloop.dcl` ⇒ 上电装载 7 路由，
   而该套件的前提是"**空卡 ⇒ bench profile 128 路由**"。
   ⇒ 已把 SD 擦干净，板子留在 **`n_routes=128 / run=1`** 的 bench 态。
   ★ **回归前提（下次跑套件前请照做）**：`0x49 PROG_ERASE` + 复位。

## 6. 已知问题（**均不阻塞发布**）

| # | 项 | 性质 |
|---|---|---|
| 1 | `RX_RING(512)` vs `FRAME_PAYLOAD_MAX(6150)` 的真实上界未知 | 已量化（实测 108% 预算仍未触发）+ 已加观测闸门；**非缺陷** |
| 2 | `0x61` 默认模式下 `tx_len` 恒 0 | `tx_uart` 默认走物理口、发完即清缓冲 ⇒ 需 `0x62 [0][0]` 切缓冲模式才可观测 |
| 3 | 协议应答**不带命令码回显/序号** | 客户端无法区分"这条应答是不是我的"（开机 banner 曾被当成 ACK）⇒ **建议 v2.1 加序号** |
| 4 | `w1` R11 · `w5` 3 项 · `modbus` 10 项 · `audit_m234` M3 3 项 | **均有归因**：测试缺陷 / 设计内 / 需 RS-485 回路。详见 `STATUS-2026-09-16.md` §8.1 |
| 5 | `w2_probe` 非确定（见 §5） | 测试自身性质 |
| 6 | RTC `event_log()` **零调用点** | "事件时间戳"目前**只有 API、没接线**；现状只到"亚秒/日历镜像被刷新、黑匣子取到挂钟" |
| 7 | RTC 亚秒分辨率 **256 Hz（≈3.9 ms）** | 文档曾宣称 1 ms（已四处更正为 256 Hz）。要真 1 ms 需改 `PREDIV_A=31/PREDIV_S=1023` —— **属行为改动，待定** |
| 8 | 能力位仍为 **u16** | 扩 u32 会动 `0x01` 线上格式 ⇒ 留待 v2.1 |

## 7. 明确**不在**本版范围

| 项 | 说明 |
|---|---|
| **GAP-6 通用外设事务 op**（`i2c_start/stop/write/read`、`spi_xfer`）| 契约 §9 **唯一 open 项**。★ 判层结论：**不能做成"引擎扫描原语"** —— 扫描体是表驱动、每拍无阻塞的，而 I2C 事务天然多步且阻塞 ⇒ 正确落法是**②层协议命令**（由主循环/独立状态机驱动），**不动引擎、不动 `OP_MAX`/`OP_COST`**。排在 v2.0.0 之后 |
| GAP-3 能力位 u32 | 同上，动线上格式 |
| `0x39` 诊断族的"临时脚手架"清理 | 定位声明已落到源码与文档；`op=19` 保留为兼容壳 |

## 8. 升级检查清单

1. **读契约 v1**（`docs/REF-program-contract.md`）—— v1 起它是强制基线。
2. **改客户端里 `0x38` 的解析**：允许 `len >= 51`（或继续只读前 39 字节）。
3. 若用 `0x39`：注意**交付固件只有 8 个 op**（`{0,1,2,3,4,17,18,19}`），
   网上流传的 "op=1..19" **不成立**（5..13 只在实验补丁里）。
4. 跑回归前先把 SD 擦干净（`0x49` + 复位）⇒ 板子回到 bench 态。
5. 看门狗武装后**任何 ≥200 ms 的调试器 HALT 都会复位板子** ⇒ 检查一律走协议。
