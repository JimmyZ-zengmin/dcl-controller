# 评估：用 DP83848 走网口，能否"只用 DMA 不占 CPU"

> 2026-09-22 · 用户问："用这个 83848 可以不用 CPU 只用 DMA 实现通信吗？"

## 0. 结论

**"每字节的 CPU 成本归零"做得到；"完全不用 CPU"做不到。**
而且这块板子有一个**很有利的条件**：**D-cache 从来没开** ⇒ 网口最大的坑
（DMA 缓冲一致性）**不存在**。

## 1. 先纠正分工：DP83848 **不做 DMA**

| 件 | 是什么 | 在哪 |
|---|---|---|
| **DP83848** | **PHY（物理层收发器）**：RMII 数字信号 ↔ 双绞线差分 | 板外 |
| **ETH1 MAC + 专用 DMA** | 帧搬运、地址过滤、校验和 | **H723 片内** |

⇒ 准确的问题应该是："**用 H723 的 ETH MAC/DMA + DP83848 当 PHY，能不能只用 DMA**"。

## 2. DMA 能省掉什么（"不用 CPU"的真含义）

| 环节 | 谁做 | CPU |
|---|---|---|
| 数据搬运（缓冲 ↔ 线上） | **ETH DMA**（描述符环） | **0** ✓ |
| 目标地址过滤（"这帧是给我的吗"） | **MAC 硬件** | **0** ✓ |
| IP/UDP/TCP 校验和 | **MAC 硬件（offload）** | **0** ✓ |
| **组/解 ARP / IP / UDP 头** | **必须 CPU** | 几十条指令 |
| **应用逻辑**（读 SHM、组 delta 应答） | **必须 CPU** | 有 |

★★★ **关键差别**：

| | CPU 成本 |
|---|---|
| 串口（即使已改成"入队 + 每圈泵"） | **∝ 字节数**（1040 B 要 pump 1040 次） |
| **以太网 DMA** | **∝ 帧数**（1 个描述符 + 1 次触发） |

⇒ 同样搬 1040 B：**从"1040 次循环"变成"十几条指令"**。

## 3. ★★★ 这块板子上，网口最大的坑**不存在**

H7 做以太网的经典大坑 = **D-cache 一致性**（TX 要 `SCB_CleanDCache`、RX 要
`SCB_InvalidateDCache`；忘了就**静默读到旧数据**）。

**但本项目明确不开 D-cache**（`src/main.c:857` 注释原文）：

> cache 是**确定性**的敌人 —— 命中/未命中取决于程序历史，同一个循环在冷/热两种状态下
> 执行时间不同。本项目的做法是"**热代码进 ITCM，大缓冲留在 non-cacheable 的地址域**"，
> 而不是靠 cache 撞运气。这里的开关只为了把 A/B 实验做完整。

⇒ **网口的 DMA 缓冲不需要 MPU non-cacheable 配置、不需要手工 clean/invalidate** ✓
⇒ 这是这块板子上做网口**最有利的一点**。
★ 而且这个选择本身是对的：**不开 cache = 时序可预测**，正是确定性引擎要的。

（旁证：`grep MPU_ / SCB_EnableDCache / CleanDCache / InvalidateDCache` 在 `src/` 里**全无命中**；
`SCB_CCR` 只在 `main.c` 的 I-cache A/B 实验里被写，且只置 `SCB_CCR_IC`（bit17），不置 `SCB_CCR_DC`（bit16）。）

## 4. 内存也够 —— 而且有个"正好"

| 域 | 大小 | 现状 | 以太网 DMA 能访问？ |
|---|---|---|---|
| ITCM | 64 KB | 用 24.9% | ❌ 不能 |
| DTCM | 128 KB | 用 54%（栈余量 75 KB） | ❌ **不能**（CPU 专用） |
| AXI (D1) | 320 KB | **已铺满 100%**（15 个固定区） | ✅ 能 |
| **D2 AHBSRAM** | **~32 KB** | **完全未动用** | ✅ **能，且是本域** |
| SRAM4 (D3) | 64 KB | 未用 | 仅 BDMA |

⇒ ★★★ **以太网描述符 + 缓冲（~8~16 KB）正好放 D2 域**：
  · **未被动用** ⇒ 不用挤 AXI
  · **是以太网 DMA 的本域** ⇒ 无跨域延迟
  · **不碰内存宪法那 15 个固定区** ⇒ 不动 `memmap.h` 的既有布局

★ 判据（将来做时要加的）：**描述符/缓冲的地址必须落在这段里** ——
  用 `_Static_assert` 钉住，而不是"注释里写着"（本项目的既有做法）。

## 5. 要付的代价（三条，都必须做）

1. **50 MHz REF_CLK**：DP83848 需要它（H7 用 MCO 输出，或 25 MHz 晶振 ×2）
2. **描述符环**：16 B 对齐、物理连续、放对内存域（见 §4）
3. **TCP/IP**：裸机要自己写 ARP/IP/UDP（约几百行），或引 lwIP（**大依赖**，
   而且要占 AXI —— 而 AXI 的 15 个固定区**合计 320.00 KB / 320 KB**，账本出处
   `tools/mem_report.py`（本文件 §4 的表也是从它抄的））

## 6. ★ 我的判断：**先别做网口，因为有个更急的同类问题**

用户的问题本质是"**能不能把数据搬运从 CPU 上摘掉**"。而**同一块板子上，这个问题在 SD 上更急**：

- 实测 **`SD_DIAG[60]` 内部最长耗时 = 467 拍 = 46.7 ms**，`[59]` 落盘最大间隔 = 630 拍 = 63 ms
- ⇒ **SD 落盘是当前主循环最大的阻塞源**（也正是今天 `w2_probe` 时间窗问题的根因）
- ★★ 而 SD 走的是 **SDMMC1，H723 上它本来就支持 DMA**

⇒ ★ **建议顺序**：
1. **先在 SD 上兑现"DMA 不占 CPU"** —— 改动小、收益直接、**验证判据现成**
   （就是今天用的那个对照实验：读/不读时主循环的阻塞变化）
2. **等要"多主机 / Modbus TCP"时再上 DP83848** —— 那时动机是**能力**，不是"省 CPU"

★★ **架构利好**：`DELTA_RING` 是**传输无关**的 ⇒ 换传输层**不用改记录层**
⇒ 先修 SD、后上以太网，**顺序上不冲突**。

## 7. 一句话回答用户

**能 —— 但"不用 CPU"要拆成两半**：
- ✅ **数据搬运、地址过滤、校验和**：100% 可以不用 CPU（DMA + MAC 硬件）
- ❌ **协议头与应用逻辑**：必须 CPU，**但成本 ∝ 帧数，与数据量无关**

**而这个收益不是"网口"给的，是"DMA"给的** ——
所以**最该先摘的果子是 SD（它现在阻塞 46.7 ms）**，不是网口。
