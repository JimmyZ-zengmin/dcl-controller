## 0. 一句话现状

**"用这个系统 = 写 DCL 程序" 这条链现在是通的**：
程序**走通信上传 → 落 SD 卡（A/B 双副本）→ 上电自动装载进引擎**，
全程**不碰 flash 烧录**，且每一环都有能失败的判据。
引擎内核（100 µs 硬拍 / ISR 全在 ITCM / 19 原语 / 热重载 / 下载前静态校验）**未受影响**。

## 1. ★ 新增的对外接口（`0x45`–`0x4A`）

| 码 | 名称 | 载荷 → 应答 |
|---|---|---|
| `0x45` | PROG_BEGIN | `[total_len:u32][crc32:u32][prog_id:u32][prog_ver:u16][min_fw:u16][req_caps:u32]` → `[total_len:u32]` |
| `0x46` | PROG_DATA | `[offset:u32][chunk...]` → `[next_offset:u32]`（**必须顺序、不跳不重**） |
| `0x47` | PROG_COMMIT | 空 → `[rc:u32][budget:u32]` |
| `0x48` | PROG_STATUS | 空 → **96 B**（见 §2） |
| `0x49` | PROG_ERASE | 空 → `[rc:u32]` |
| `0x4A` | DEVICE_DESC | 空 → `[fw:u16][cap_lo:u16][cap_hi:u16][n:u16]` + `n×[device_type:u16][product_code:u16][revision:u16]` |

**`0x48` 的 96 字节布局**（★ 它同时是"程序存储体检表"和"事务对账表"）：
```
+0  part_ok       +4  ab_valid(bit0=A bit1=B)   +8  seq_a      +12 seq_b
+16 crc_a         +20 crc_b                      +24 len_a      +28 len_b
+32 active(0=A 1=B 0xFFFFFFFF=无)                +36 ok_n       +40 fail_n
+44 reject_n      +48 last_rc                    +52 txn_begin  +56 txn_commit
+60 txn_abort     +64 boot_rc                    +68 boot_loaded
+72 deploy_routes +76 deploy_seq
+80..92  ★ 从卡上读回的载荷头 16 字节（判"我到底读回了什么"）
```

## 2. ★★ AXI 真实地图（**320 KB 已用满 —— 加缓冲前必须先看这张表**）

| 区间 | 占用者 | 大小 |
|---|---|---|
| `0x24000000`–`0x24000600` | 引擎诊断结构固定区（`SD_DIAG`/`BB_DIAG`/`SD_CFG`/`BOOT_AXI`）；**协议 `0x20 READ` 的放行窗口** | 1.5 KB |
| **`0x24000600`–`0x24003000`** | ★ **唯一空档** —— 程序存储缓冲在此（`0x24000800` / `0x24002800`） | ≈10.5 KB |
| `0x24003000` / `0x24003100` | MDMA 锁存快照 / 链表节点（`do.c`） | — |
| `0x24004000`–`0x24040000` | 黑匣子环（`BB_SLOTS=960` × 256 B = **240 KB**） | 240 KB |
| `0x24040000`–`0x24050000` | 日志冻结区 `SD_STAGE` | 64 KB |

★ `prog_store.c` 里有**构建期 `#if/#error`**：缓冲地址越出那个空档就**编译不过**。
★ `blackbox.h` 原写"AXI 完全空闲 / 128 KB / 512 槽" —— **三处都是过期的**，已更正。
  **照过期注释找空档的代价是白查一整轮**（缓冲落进环里，每拍被覆写）。

## 3. ★ SD 卡分区（S3）

```
LBA0                     日志头（扩展段 h[112]=LOG_END, h[113]="LEND"）
LBA1 .. LOG_END          日志数据区（环形回卷）
g_sd_prog_a .. +15      程序副本 A（16 块 = 8 KB）
g_sd_prog_b .. +15      程序副本 B
LOG_END = capacity - 1 - 32     ← 由**容量**算出，不是硬编码
```
★ **绝不升 `LOG_VERSION`**（一升版本 `sd_log_open` 就当新卡重建 ⇒ 从 LBA1 覆写毁掉卡上记录）。
★ 旧卡无该字段 ⇒ 不影响任何既有校验（`h[0]/h[1]/h[2]/h[6]` 四条照旧）⇒ 向后兼容。
★ **`s_log_blk` 必须钳位**：旧卡游标可能超出新上限，不钳则 `cap_data - s_log_blk` **下溢**、写飞出卡外。

## 4. 四个真 bug（**都是同族的，看一般化那一列**）

| # | 症状 | 根因 | 一般化 |
|---|---|---|---|
| 1 | 整条 SD 路崩（`blk_this_boot=0, batch_err=3099`） | 我按 HAL 骨架重写 `sd_read_block` ⇒ **它返回的数据是错的** ⇒ 日志头读不对 ⇒ 当新卡重建 | **"半个对齐"比不对齐更坏**：只抄 while 骨架、换掉其下的数据搬运机制（IDMA→手工排 FIFO）= 没对齐前提 |
| 2 | `PROG_RC_WRITE` 写超时 | 缓冲在 **DTCM**，而 SDMMC 的 **IDMA 读不到 TCM 端口** | 外设 DMA 能到哪块内存**按外设成立**，不能按"上次那个能"类推 |
| 3 | 读回载荷头 = `"DLBK"`（`BBLOG_REC_MAGIC`） | 缓冲撞进黑匣子环（960 槽 × 256 B = 240 KB） | **"当前完全空闲"这类注释活不过两周** |
| 4 | 正常批写被判超时 | `SD_TMOUT_DATA` 被我挤到 200 万（≈250 ms） | **超时给够 + 调用方声明阻塞窗口**；挤超时是用判据掩盖慢 |

### 4.1 ★★ 两条**方法学**教训（比 bug 更值钱）
1. **`pyocd halt` 会把核留在停住状态** —— 我据此得到过一整串假结论（"`g_tick_count` 冻结 / ISR 死了 / 板子不复位"）。
   干净 `pyocd reset` 后不发 halt，串口立刻全好。
   **而 `0x48` 的应答本身就带 `txn_*` 计数 ⇒ 根本不需要 SWD。** ⇒ 违反了自己写的第 1 条纪律（观测先走协议内通道）。
2. **构建闸门不要用管道把门**：`build.sh | grep … && flash` —— `grep` 的退出码掩盖构建失败 ⇒ **烧了旧镜像**并据此误判一轮。

### 8.2 ★★ 设计耦合点：**实测推翻了理论 —— 不能宣称"有问题"也不能宣称"余量充足"**

```
src/uart.c:35       RX_RING_SZ        = 512      ← 接收环
src/transport.h:148 FRAME_PAYLOAD_MAX = 6150     ← 协议宣称的最大帧
```

**先把"帧大小受不受环限制"测清（`0x23` 往固件不拥有的 `WIRE[100]` 写，扫 qty）：**

| qty | 50 | 100 | 124 | **125** | **126** | 128 | 160 | 200 | **256** |
|---|---|---|---|---|---|---|---|---|---|
| 帧总长 | 212 | 412 | 508 | **512** | **516** | 524 | 652 | 812 | **1036** |
| 结果 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | **✓ 整帧收到并写对** |

**⇒ 帧大小本身不受环限制** —— 主循环**边收边排空**，环只是延迟缓冲。
（★ 这同时**证明了 `w1 R11` 的 1036 字节帧是完整到达的** ⇒ 它的 NAK 确实是为 NaN ⇒ R11 是测试缺陷，有了实证。）

**再量"阻塞时长 vs 环能吸收多久"（COMMIT 的 SD 落盘为阻塞源）：**

| 载荷 | 块数 | COMMIT 往返 | 占理论预算(44.4 ms) | uart_ore / drop / frame_bad |
|---|---|---|---|---|
| 54 B | 1 | 31.8 ms | 72% | **0 / 0 / 0** |
| 1030 B | 3 | 31.3 ms | 70% | 0 / 0 / 0 |
| 2054 B | 5 | **48.2 ms** | **108%** | **0 / 0 / 0** |
| 4102 B | 9 | **48.4 ms** | **109%** | **0 / 0 / 0** |

**⇒ 阻塞已达理论预算的 108%，却一个字节都没丢。**
⇒ **`512 B ÷ 11.52 B/ms = 44.4 ms` 这个上界是偏保守的**（环的实际可吸收量更大，或有额外的硬件/驱动缓冲）。
⇒ **诚实结论：这是一个"已量化、已加观测闸门"的耦合点，但当前实测没有触发。**
   **既不能说"出问题了"，也不能说"余量充足"** —— 要知道真实上界，得**故意把阻塞拉长**再做一次。

### 8.2.1 ★ 本轮为此补的观测闸门（**这是本节真正的交付**）
`0x38` 的应答从 **39 → 51 字节**，尾部追加：
```
+39  uart_ore     (硬件 ORE 溢出次数)
+43  uart_drop    (软件环满丢弃次数)
+47  frame_bad    (坏帧数)
```
**判据：正常收发下这三个必须恒为 0。非 0 ⇒ 有帧被截断 ⇒ 该次"NAK/无应答"不是固件的判断，
而是数据没到全。**
★ 为什么必须补：这三个量原来**只刷进全局变量、不进任何应答面** ⇒
**"帧被截断"在协议面上完全不可见**（只能 SWD 读 DTCM，而 SWD 会停核）。
这违反本项目自己的纪律"**新观测变量必须能被外部读走**"，也和 `r[38] out_surfaces` 是同一个理由 ——
**把"读数一样、事实不同"的两件事分开。**

### 8.3 更正：注释里的**旧数字**比代码更容易被当成事实
`modbus.c` 里那句"`MB_MAX_FRAME(128, 请求上限)`"**是过期注释**（常量早已升到 255）。已更正，
并写明纪律：**注释里不要写常量字面值，写常量名**（或紧跟 `_Static_assert`）。
★ 本项目已因此白查过一整轮（`blackbox.h` 的"AXI 完全空闲 / 128KB / 512 槽"）。

### 9.5 ★★★ 复核时查出一个**环境级 Git 缺陷**：本机 `refs/remotes/**` 写不进去（静默返回 0）

**发现方式**：复核时 `git status` 报 `[ahead 27]`，但上一条记录说"本地 = origin = dcl" —— 矛盾 ⇒ 直接查。

**结论：两个远程其实都已同步，是**本机远程跟踪引用根本写不进去**。**
```
git ls-remote origin refs/heads/main = 1c203477  ✓   (直连远程，权威)
git ls-remote dcl    refs/heads/main = 1c203477  ✓
但 refs/remotes/{origin,dcl}/main 一直停在 089fd97（两天前）
```

**逐层隔离（四组，只有最后一组异常）**

| 动作 | 结果 |
|---|---|
| `git fetch --all` | 打印 `089fd97..1c20347 main -> origin/main`、`rc=0`；**但 `packed-refs` 值不变、无松散文件** |
| `git rev-parse` / 纯 shell 操作 | 不影响 `refs/remotes` 下已建内容 |
| `git update-ref refs/heads/x HEAD` | **正常**（文件真出现） |
| `git update-ref refs/remotes/origin/foo HEAD` | **`rc=0`，且把 `origin/` 整个目录删掉**（连探针文件一起消失） |

已排除：`.git/config` 格式（`repositoryformatversion=0`，非 reftable）、`hooks`（全是 `.sample`）、
lock 文件（无）、以及"脏目录"（**删掉整个 `refs/remotes` 树重建后再 fetch，依然不写**）。
⇒ **只有"写 `refs/remotes/**`"这一条路静默失败：`rc=0`、无报错、无写入。**

**★ 两条判据修订（已写入长期记忆 §7.2）**
1. **写完引用必须 `git show-ref` 确认真的落进去了** —— 这是唯一可信读法。
2. ★★ **同步状态的权威判据是 `git ls-remote <remote> refs/heads/main`，不是 `git status`** ——
   后者依赖远程跟踪引用，在本机会**永远误报 ahead**。

**治标修法（本机唯一有效，已核验）**：手工写松散引用
```
mkdir .git/refs/remotes/origin                  # dcl 同
printf '%s\n' <hash> > .git/refs/remotes/origin/main
```
⇒ `git status -sb` 立刻变 `## main...origin/main`、`git rev-parse origin/main` = `1c203477` ✓
（操作前已按纪律备份 `../.git_bak_2026-09-16_refs`，13 MB。）

> 这条属于**取证工具链的可靠性问题**，不属于固件缺陷，但**不修会让以后每一轮"是否已推送"的判断都出错**，
> 因此与 release notes 同等对待。

## 10. ★★★ 标准化复核中挖出的两个**真 bug**（2026-09-16 下午，已修 + 已上机 A/B 回归）

> 背景：在做"入口文档回填"的事实核准时，三份并行调研各带回一条硬结论。
> 两条**不是文档问题，是代码问题**。按契约 §2"核心改动必须 A/B + 回归"，两条都做了上机对照。

### 10.1 缺陷 A：交付档下 **DO 0..7 是死的**（`src/do.c`）

**机理**（读码取证，逐条可复核）
1. MDMA 节点 `CTCR=0x00020000`（**byte 尺寸 + 地址固定**）+ `CBNDTR=4`
   ⇒ 4 次字节搬运**全落在 `GPIOE_ODR + 0`** ⇒ 只覆盖 **PE0~PE7**；
2. 源 = `OFF_DO_SHADOW`，而 0 档的 `do_poll()` 走 `#else` 分支**只写 `BSRR`、从不写影子**
   ⇒ **影子恒 0**（冷启 memset 后没有任何写者）；
3. ⇒ 每 100 µs（TIM2_UP）MDMA 把 **0** 锁进 `ODR` 低字节
   ⇒ **CPU 用 BSRR 置起来的 PE0~PE7 会在下一拍被静默清掉**。

★ 这是"DCL_DO_LATCH 切 0 档"的**必要补丁**：当初只算了抖动（3.6 ns vs 54~60 ns），
**没算到"锁存链还在跑、而影子已经没人写"** ⇒ 切档顺手把 DO 0..7 弄死了，
且**观测面上完全看不出来**（寄存器读回全对、`g_do_write_n` 照涨，只是引脚不动）。

**修法**：0 档在 `do_latch_init()` 开头直接 `return` ⇒ 不启用 DMA2/DMAMUX1/MDMA，
也不置 `TIM2.DIER.UDE`（顺带消掉 ~350 万次/秒的 AXI 链表搬运与 AHB4 写）。

### 10.2 ★★ A/B 实测（同一块板 COM21、同一套判据、同一个程序，只有那一处补丁不同）

判据：登记 `GPIO_MASK=0x00FF` → `ACTUATOR[0..7]=1.0` → 等 200 拍 → 连采 `GPIOE_IDR`。
工具：`tools/h723_do_hold_test.py`（★ 看 **`IDR`**，不是 `ODR`）。

| 固件 | `GPIOE_IDR` | 低字节 | 命中 | 判定 |
|---|---|---|---|---|
| **改前（对照，`HEAD~1` 的 `do.c`）** | `0x0F00` | `0x00` | **0/5** | **FAIL** |
| **改后（交付）** | `0x0FFF` | `0xFF` | **5/5** | **PASS** |

★ 对照档 `ODR=0x0F00` —— 高字节 8~11 位完好、**低字节被清成 0**，与上面推出的机理**逐位对上**。
⇒ **判据会失败**（对照实测），**修复使判据通过**（交付实测）—— 这才构成证据。

### 10.3 缺陷 B：`0x38` 应答**栈越界 11 字节**（`src/main.c`，**本轮我自己引入的**）

把 `0x38` 从 39 扩到 51 字节时，**只改了写的偏移，没同步改缓冲声明**：
`uint8_t r[40]` 而 `ack(r, 51)` ⇒ 越界 11 字节写坏调用者栈。
★ 与缺陷 A 同族：**"改了一半"**。
**修法**：不用"把 40 改成 51"（那是同一个坑——一个语义两处存放），
改成 `#define ENG_STATUS_LEN 51u` **同时定缓冲大小与发送长度**。
**验收**：修复后 `0x38` 实测 `ACK len=51`（见 10.2 的表头行）。

### 10.4 ★ 新增**静态**判据并接入构建闸门（族级修复，不是单点修复）

同类缺陷**已犯两次**：`h_pin_pattern()` `r[40]`→`ack(r,68)`（28 B）、本次 `r[40]`→`ack(r,51)`（11 B）。
共同点：**不报错、不崩溃，读回来的字段全是合理值** ⇒ **动态判据永远发现不了**。

- `tools/h723_ackbuf_check.py` —— 静态扫 `ack()/put32()/put16()` 的写入长度 vs 局部缓冲声明；
- 已接进 `build.sh`（与 ISR 调用树闸门同级），**构建期拒绝通过**；
- ★ **该工具第一版自己是"空判据"**：本仓库函数左花括号在下一行 ⇒ 一个函数都没解析到，
  却对任何输入都打印 `[OK] 未发现越界`。**"0 发现"与"根本没扫"长得一模一样。**
  ⇒ 本版强制**自报覆盖度**（覆盖不足即判无效）+ 带 `--selftest` 夹具（造好的红必红、造好的绿必绿）。
- 实测覆盖：**224 个函数 / 22 个带局部缓冲**；当前 1 处越界（即缺陷 B）已修 ⇒ `[OK]`。
  期间修掉 2 处**误报**（`= {...}` 初始化列表被当成写入）。

### 10.5 `DCL_DO_LATCH` 从"假开关"变**真开关**

`src/do.h` 的注释**早就宣称**"可被 CMake `-DDCL_DO_LATCH=0` 覆盖"，
但 `CMakeLists.txt` **从未** `set(... CACHE ...)`、也从未传 `-D`
⇒ 那是个**空头承诺**：CMake 连缓存项都不建，`build.sh` 那节

已接线 + 写进 `build.sh` 的 `DEFAULTS`，现在**能跑 A/B**：

### 7.1 ★★ 更正一条我先前的错误结论 + 一个真的协议缺陷
**我先前写过"`h723_client.Dcl.send()` 会返回假 ACK（帧错位）"—— 查证后这是错的。**
`h723_modbus.Link.xact()` 里有 `if crc16(body) == crc_rx: return …`，也做了 `del buf[0]` 的错位重找。
**它没有撒谎。**

真正发生的事：当时固件在复位循环，串口上不停出现**开机 banner**：
```
c1 00 04 00 | 00 02 f7 0d | f4 c2      ← CRC 完全合法的一条帧
```
而**协议帧里既没有"命令码回显"、也没有序号** ⇒
**客户端无法判断这条应答是不是属于自己刚发出的那条请求** ⇒ banner 被当成了 ACK。
（那轮我看到的 `BEGIN/DATA/COMMIT` 全部 ACK，其实是 banner；固件侧 `txn_*` 恒为 0 才是真话。）

> **⇒ 这是协议层的真缺陷，建议进 v1**：应答里带 **`最近命令码`**（1 字节）或**序号**，
> 让客户端能判"这条应答是我的吗"。现在的口径是"收到任何合法帧就当应答"，
> **任何多余帧（开机 banner、上一条的迟到应答、别的写者）都会污染判据。**

★ 顺带：`h723_modbus.main()` 里已有 `revive_if_dead()`（"M4 sentinel: un-halt the core if a pyocd
session left it halted"）⇒ **"pyocd 会把核留在 halted"这件事项目里早已知道**，我这一轮又踩了一次。
