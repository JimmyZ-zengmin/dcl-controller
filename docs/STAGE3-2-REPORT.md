## 2. ★ 发现 1：成本表**不能照抄**（附实测对照）

S3 的 `op_cost[]` 是 240MHz/ESP32 上的数。本平台实测（`tools/h723_op_sweep.py`，
19/19 原语数据可信，两点法斜率，每个原语的表校验和都与 Python 独立预测逐位吻合）：

| 原语 | S3 @240MHz | **H723 @400MHz/ITCM** | 加速比 |
|---|---|---|---|
| DIRECT | 234 | **56** | 4.18× |
| CMP | 255 | 75 | 3.40× |
| LPF | 312 | 96 | 3.25× |
| **PID** | **337** | **145** | **2.32×** |
| ARITH | 235 | 68 | 3.46× |
| SR | 247 | 78 | 3.17× |

**加速比不是常数**：简单拷贝类 ~4.2×，而 PID 只有 2.3×。
⇒ 若把 S3 的表按 DIRECT 的 4.2× 整体缩放，**PID 会被低估约 1.8 倍** —— 预算门就会
放行会超载的程序。这是"换平台必须重测"的直接实证，不是泛泛的原则。

**全表（cycles/条, ITCM, 全表扫）**：

```
DIRECT 56  CMP 75  HYST 79  CLAMP 75  LPF 96  PID 145  RATE 67  DEADBAND 75
MUX 70  EDGE 88  LUT 89  CNT 77  TIMER 79  ARITH 68  SCALE 67  AND 72  OR 72  NOT 70  SR 78
```

## 3. ★★ 发现 2：预算门在 H723 上**根本不可能被触发**（判据不能失败 = OA23 族）

`MAX_ROUTES`(128) × 最贵原语(145) = **18560 cyc = 拍长的 46%**。
也就是说：**在 128 条上限下，任何合法程序都不可能把拍吃满** —— 预算门永远不触发。

这正是审计里 OA23「判据恒真」的同族形态，只是方向相反（"永远为假的守卫"）。
处理方式不是把门调低（那是凑数字），而是**把它标成"未来的门"并立一条绊线**：

```c
_Static_assert(MAX_ROUTES * OP_COST_MAX_MEASURED <= EXEC_DEPLOY_BUDGET,
   "★ 预算门开始具约束力: 必须实测验证它能拦住超载");
```

- 断言**通过** = "门还不具约束力，无需动作"（现状）
- 断言**失败** = "门现在是真的了，去验证它" —— 触发条件：**路由扩容**或**加入更重的原语**
- 为什么仍要保留这个门：DTCM 能放 ~2000 条路由，**一旦扩容，28×145 立刻越过 26000**。
  到那时它必须被实测验证过，而不是靠一个从没触发过的判据。

> 附带结论：**H723 当前的实际容量约束是 `MAX_ROUTES=128`，不是拍长**。
> 扩容路由数才是提升容量的下一步（S3 的 `verify_capacity` 会在那时才有意义）。

## 4. ★★ 发现 3（严重）：热重载用 libc `memcpy` 会**打崩拍周期**

### 现象（第一版）

| 指标 | 第一版 | 说明 |
|---|---|---|
| 单次热重载 | **71241 cyc = 178 μs** | **比 100 μs 的拍还长** |
| 拍周期 | **1360 ~ 78640 cyc** | 最小 3.4 μs、最大 196 μs —— 拍被打崩 |
| ISR | 49 ~ 78563 cyc | 同上 |

机制：ISR 里做 4800 B 的搬运，耗时超过拍长 ⇒ 定时器下一次事件已经到期，
ISR 一返回就立刻再进一次 ⇒ 拍周期塌成"ISR 长度"量级。这正是阶段 2 审计
H7 那条结论的翻版：**"ISR 必须在拍内跑完"是硬约束，不是建议。**

### 根因

`memcpy`/`memset`（newlib nano）在**按字节拷 + 从 flash 取指**（H7 复位默认
I-cache 关闭）时约 **14.8 cyc/字节**。4800 B × 14.8 ≈ 71000 cyc —— 与实测吻合。

### 修法与复测

| | 第一版 | 修后 | 提升 |
|---|---|---|---|
| 实现 | libc `memcpy`/`memset`（flash） | **ITCM 里的字拷贝循环**（`itcm_wcopy`/`itcm_wzero`） | — |
| `engine_reload_active` 落位 | `0x0800xxxx`（FLASH） | **`0x00000C90`（ITCM）** | — |
| 单次热重载 | 71241 cyc (178 μs) | **1437 cyc (3.6 μs)** | **50×** |
| ISR 峰值 | 78563 cyc | **3332 cyc (8.3 μs)** | 24× |
| 拍周期 | 1360 ~ 78640 | **39986 ~ 40014** | 回到正常 |

★ 教训（写进 `engine.c` 注释）：**热路径上的内存搬运不能交给 libc**，
尤其是"默认关 cache"的 H7。字拷贝进 ITCM 后同样的数据量只需 1/50 的时间。

> 剩下的 28 cyc 极差（70 ns）是阶段 3.1 已量化的**上电瞬态**
> （协议层报告 §3 的隔离实验：零流量 0 cyc / 含启动 22 cyc），不是重载引起的 ——
> 重载那一拍只体现在 `isr_cyc_max`（3332），拍周期本身没被拉长。

## 5. deploy 自检 9/9（判据全部可失败）

CH340 未接线，无法从 PC 侧验证，所以做一个**固件内自检**：用合成载荷驱动
**同一个 `h_deploy`**（不是复制一份逻辑），每例比对调用前后的 `(ok, nak)` 计数器 ——
**只数成功会让"全部被拒"看起来像"没部署过"；只数失败会让"全部放行"看起来像"很严格"**。

| 例 | 载荷 | 期望 | 结果 |
|---|---|---|---|
| 0 | 合法三档程序（128 条 DIRECT，三个源轮转，8 参数/8 状态）| 受理 | ✅ |
| 1 | dst 冲突（两条路由写同一 wire）| 拒 | ✅ |
| 2 | `SRC_HMI`（H723 未实现）| 拒 | ✅ |
| 3 | PID（有状态）挂 0 号 state 槽 | 拒 | ✅ |
| 4 | `div=3`（掩码外）| 拒 | ✅ |
| 5 | 非法 op `0x1F` | 拒 | ✅ |
| 6 | 参数非有限（+Inf）| 拒 | ✅ |
| 7 | 载荷长度不足 | 拒 | ✅ |
| 8 | 全 NONACTIVE → 受理但写入 **0 条**（"空程序"是合法手段）| 受理 | ✅ |

实测：受理 2 / 被拒 7，`deploy_seq = applied_seq = 2`，`reload_lat = 1 拍`。

### ★ 生效确认（偿还 S3 的语义债）

S3 的 `0x10` ACK 是**空载荷** —— 上位机只能知道"受理了"，无法知道"何时生效"。

H723：
- `0x10` ACK 载荷 = `[seq:u16][budget:u32]`（**向后兼容的尾部追加**，S3 自己就用这惯例）
- ISR 真正切换完 ACTIVE 表后写 `APPLIED_SEQ = DEPLOY_SEQ`
- `0x38` 尾部追加 6 B：`[deploy_seq][applied_seq][applied_lat]`
  （前 31 B 与 S3 **逐字节同布局**，旧脚本零改动）

⇒ 「已生效」从**假设**变成**可观测的量**：`applied_seq == deploy_seq` 就是证明，
`applied_lat` 直接给出"受理到生效跨了几拍"（实测 **1 拍**）。

## 6. 顺手抓到的迁移痕迹

| 项 | 来源 | 处理 |
|---|---|---|
| `__asm__ volatile("memw")` | **Xtensa（ESP32）指令**，ARM 上不存在 | 编译报 `bad instruction`，改为 `dsb` |
| `op_cost[]` | S3 的 240MHz 实测值 | **重测**（本报告 §2）|
| `OP_COST_DIV2 = 100` | S3 的 H9 缺陷 | 改为 **64** |
| `EXEC_DEPLOY_BUDGET = 16000` | S3 的 24000 拍预算 | 改为 26000 / 40000 拍 |

> 这几条是同一个模式：**"从旧平台搬过来的数字与指令，语法上过得去，语义上是错的"**。
> 它们不会在编译期报错（除了 `memw`），只能靠"逐项问一句'这个数是在本平台测的吗'"发现。
