## 2. B 段：三档验证（`di` 与扫描段）

用 div0 的两点标定 `(C_scan, m)`，再预测 div1/div2：

| op | `C_scan` | `m` | I-3（≤40 TB）|
|---|---|---|---|
| PID | **121.7 TB** | 64.00 | ❌ 2/8 超差 |
| DIRECT | **99.6 TB** | 29.50 | ✅ 0/8 超差 |

**⇒ `C_scan` 依赖 op**（PID 121.7 vs DIRECT 99.6），**不是一个通用常数**。

★ 这一条**修正了 C_scan 分解那一节的结论**：那里测出 `C_loop = 62.3 TB`，
但那是在**全未激活**（无路由体跑）下测的；
一旦有活跃路由，扫描段的截距升到 **100 ~ 122 TB**。
⇒ **两者不矛盾**：62.3 是"纯循环地板"，100~122 是"含活跃路由时的截距"。
**模型里应当用的是后者。**

### 2.1 两个超差点，都已定位（不是模型崩）

| 点 | 偏差 | 原因 |
|---|---|---|
| PID div1 n=16（`nrun=1`）| **+44.3 TB** | `nrun=1` 处**量化 + 地板**（§2.2）|
| PID div2 n=16（`nrun=1`）| **−91.9 TB** | 同一点的两个极端 ⇒ 说明 `nrun=1` 的读数本身**分辨率不足** |

★ 注意后者的讽刺：**同一个 `nrun=1`，两个 division 实测差 136 TB**（229.9 vs 93.8）。
⇒ **`nrun` 在极稀疏区确实不是充分统计量**（此结论此前已登记, 这里再次印证）。

这正是"相位 64..99 现在可寻址"的预期形状。

## 4. 已更新的东西

`tools/h723_tick_ring.py` 的默认系数（原为 `c0=1200, c_route=121.2`，旧固件 div1 口径）：

```
新默认（PID 口径, di 口径）:
    c0      = (C_scan 121.7 + C_other 474) × 2 = 1191 cyc
    c_route = m_op 64.0 × 2                    =  128 cyc/条
```

★ 该工具量的是 **`di`（整段 ISR）** ⇒ 默认值**含** `C_other`。
要算"引擎本身"，自行减 474 TB。

**验证**：`--prog 5,1,128`（正是标定口径）⇒ **5 项 0 FAIL** ✅
其余组合需显式传 `--c0 / --c-route`（工具的设计如此，非缺陷）。

## 5. 现状：模型（在新固件上）

```
di(t) = C_other(474 TB, 与程序无关)  +  C_scan(op)  +  Σ_ops ( m_op × 该 op 本拍条数 )
                                          ↑ 100~122 TB      ↑ 19 个稳定常数（§1）
```

**三项全部实测**，且 `m_op` 已在**两次独立构建**上复现（≤0.6%）。

### 仍是"标定"档，不是"算"档

`m_op` 与 `C_scan` 仍来自实测。要变成"算"，必须零实测输入地推出它们 ——
**E-F 已排除最直接的一条路**（指令级吞吐下界，比值跨 20×）。

★ 但 §1 的结果让"标定档"**远比之前更有说服力**：
`m_op` 既然是**跨构建稳定**的原语属性，
那么"一次标定、所有程序通用"就不再是假设，而是**有两次独立构建支持的事实**。
