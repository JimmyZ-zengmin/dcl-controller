# 方案：把主循环上的 I/O 搬进 100µs 拍内

> 用户指令（2026-09-12）：**"把在主循环上的、ISR 引擎外的内容搬到引擎内"**。
> 前置答复：① 输入输出链一起搬 ② 输出面引脚由我定 ③ 输入源不清楚（先按现状做）④ 对照实验稍后做。
> 依据：`src/main.c` 主循环（2308-2443）、`src/adc.c`、`src/hil.c`、`src/di.c`、
> `docs/ARCH-H723.md`、`docs/REF-flash-placement.md`、`docs/HARDWARE-PINOUT.md`。
> 本文档**只是方案**，不含代码改动。

---

## 0. 一句话结论

主循环上有 11 项内容，其中**只有 I/O 三件套（`ai_tick` / `di_tick` / `hil_tick`）是"该搬"的**；
其余 8 项要么**物理上不能进 ISR**（flash 擦写、协议、重填表），要么**搬了不划算**（为轮询服务的镜像）。

而 I/O 三件套里，**DI 与 HIL 输出臂可以直接进拍、成本几乎为零**；
**唯一硬障碍是 ADC —— 它单次采样就要 259µs，比 100µs 拍长 2.6 倍，不改造就不可能进拍。**

⇒ 方案 = 「**两件直接搬 + 一件先改造再搬**」。

## 1. 主循环内容分流表（逐项有据）

依据 `main.c:2308-2443`。判据：**能不能进 ISR** = ① 是否阻塞/超拍长 ② 是否与外部时序耦合 ③ 搬进去是否换来确定性收益。

| # | 内容 | 位置 | 判定 | 理由 |
|---|---|---|---|---|
| 1 | `proto_poll()` 协议轮询/解析/分发 | 2310 | **不搬** | 耗时不定（一帧可达数百字节）；命令执行会触发 deploy/落盘等大动作。**协议处理必须留在 ISR 外**（现注释已明说"命令执行在主循环，不在中断里"）|
| 2 | banner 周期打印 | 2311-2319 | **不搬** | 走 UART 阻塞发送（等 TC），进 ISR 直接爆拍 |
| 3 | `g_icache_req` 单向开关 | 2321-2325 | **不搬** | 一次性动作 |
| 4 | `g_persist_req` 免串口落盘 | 2331-2338 | **不搬** | `persist_save` = flash sector erase，**几百 ms**，会 stall 取指（已实测："每次落盘有一段失聪窗口"）|
| 5 | `g_persist_auto` 空闲窗口落盘 | 2353-2364 | **不搬** | 同上；且它的**触发条件只能由上位机给出**（已记录三次"固件自己猜窗口"的失败）|
| 6 | `g_cmd_req` 免串口协议帧 | 2373-2383 | **不搬** | 走 `proto_dispatch`，同 #1 |
| 7 | `g_reinit` 重填表 + 双 checksum | 2385-2396 | **不搬** | 扫全表 + checksum，计算量大；且必须"关扫描门→填→恢复"，**天然是主循环语义** |
| 8 | SHM 计时镜像（7 次写）+ `g_active_routes` 重扫 | 2409-2419 | **可搬但不必** | 现注释已论证：**为"被轮询才需要"的视图付每拍代价不划算**。实测代价约 30 cyc（可忽略），但收益也只是"读得更及时" ⇒ **保持主循环** |
| 9 | `mb_refresh_hold` 通信域镜像（每 100 拍） | 2426 | **可搬但不必** | 64×u16 搬运 + 64 次浮点乘；外部主站读 40001+ 的周期 >> 100µs ⇒ **保持主循环** |
| 10 | `macro_tick` 循环执行 | 2432 | **可选** | ms 级慢动作，自节流后每轮只几条指令。**当前放主循环无害**；若将来要求"ms 级动作也精确锚定相位"，再搬 |
| 11 | **`ai_tick` / `di_tick` / `hil_tick`** | 2435-2437 | **★ 该搬** | **这是用户诉求的正题**：三者都是 I/O，当前由主循环驱动 ⇒ **采样/输出时刻由"主循环跑到哪"决定，不具确定性**。详见 §2 |
| 12 | 栈哨兵巡检 `shm_guard_ok()` | 2440 | **可选** | 32 个字，约 100 cyc。搬进去可让"表区被踩"与拍同步暴露；但不紧急 |
| 13 | `wfi` | 2442 | **保留** | 主循环仍需要（省电 + 让出空闲）|

**结论**：正的搬迁对象 = **#11（I/O 三件套）**，可选 = #10/#12。

## 2. 三件套的逐项解剖（谁能直接搬，谁不能）

### 2.1 `di_tick` —— ✅ **可以直接搬，成本极小**

`di.c:43-66`：4 路引脚 → 读 `GPIO_IDR` → 去抖状态机（`s_last/s_cnt/s_stable`）→ 写 `SENSOR[3..6]`。

- 成本：4 × (读 IDR + 比较 + 计数 + 写 float) ≈ **60 cyc**
- 现在节流 100 拍（10ms）；搬进拍后**建议改为拍计数驱动**（如每 10 拍采一次，去抖窗口由"采样次数"定义而非"时间"）⇒ **语义更硬**
- 无阻塞、无外部耦合 ⇒ **零风险**

### 2.2 `hil_tick` 的**输出臂** —— ✅ **可以直接搬，成本极小**

`hil.c:66-91`：读 `WIRE[HIL_U_WIRE]` → 钳位 → 算 duty → 写 `TIM3_CCR1` → 回写镜像。

- 成本：读 float + 比较 + 除法 + 写寄存器 ≈ **60 cyc**
- **最关键的一点**：`TIM3_CCR1` 已配 `OC1PE`（预装载）⇒ **写入在下一个 PWM 更新事件才生效** —— 这已经天然把输出对齐到 TIM3 网格（1kHz）。搬进拍内后，**"写 CCR 的时刻"也变确定了**（当前是主循环随机时刻写）
- ⚠ 一个必须处理的分裂：**`hil_tick` 里还含 16 次阻塞 ADC**（`hil.c:96-101`）—— 见 §2.4

### 2.3 `ai_tick` —— ❌ **不能直接搬：单次采样 259µs > 拍长 100µs**

`adc.c:82-96` + `adc.c:49` 注释：

```
采样时间 SMP = 810.5 周期 @ adc_ker_ck = 3.125MHz  ⇒  单次转换 ≈ 259µs
adc_read() = 软件触发 ADSTART + 自旋等 EOC（最多 5,000,000 次）
```

**259µs = 103,600 cyc @400MHz，是整拍（40,000 cyc）的 2.6 倍。**
⇒ 直接搬进 ISR，**拍周期会立刻由 ISR 时长决定**（即"拍被拖垮"），
  这正是项目已知的"超载后拍周期由 ISR 时长决定"情形。

**这不是"实现难"，是物理约束。** ⇒ 必须先改造为非阻塞（§3）。

### 2.4 `hil_tick` 的**反馈臂** —— ❌ **同样不能直接搬**

`hil.c:96-101`：`HIL_FB_AVG=16` 次 `adc_read` 循环 ⇒ **16 × 259µs ≈ 4.1ms**！
即当前主循环每 10ms 里有 **41% 的时间**花在阻塞等 ADC 上。搬进拍内更不可能。

### 2.5 当前主循环的 I/O 时间预算（实测口径）

| 项 | 每周期耗时 | 占 10ms 比例 |
|---|---|---|
| `ai_tick` 3 通道 | 3 × 259µs ≈ **777µs** | 7.8% |
| `di_tick` 4 路 | ≈ 60 cyc ≈ 0.15µs | ~0 |
| `hil_tick` 输出臂 | ≈ 60 cyc ≈ 0.15µs | ~0 |
| `hil_tick` 反馈 16 次 | 16 × 259µs ≈ **4.1ms** | **41%** |
| **合计** | **≈ 4.9ms / 10ms** | **≈ 49%** |

⇒ 主循环**近一半时间在等 ADC**。这既是"该搬"的理由，也是"不能硬搬"的理由。

## 3. ADC 非阻塞化 —— 唯一的技术攻坚点

### 3.1 三条路（按代价从低到高）

| 方案 | 做法 | ISR 每拍代价 | 风险 |
|---|---|---|---|
| **A. 拍内状态机**（推荐先做） | ISR 里维护一个小状态机：**启动 → 跨拍等 EOC → 读 DR → 换下一通道**。因单次 259µs ≈ 2.6 拍，用"3 拍后读"即可 | 每拍约 **20~30 cyc**（一次 ISR 检查 + 每 3 拍一次读）| 低。复用现有 `adc_read` 的寄存器操作，只是把"自旋等待"换成"跨拍轮询" |
| **B. ADC + DMA 硬件搬运** | ADC 多通道扫描 + DMA 搬结果数组；ISR 只读数组 | 每拍 **~10 cyc** | 中。要配 DMAMUX + 触发源 + 目的地址（**目的不能是 DTCM** —— DMA1/2 不可达 DTCM，需放 AXI）|
| **C. 定时器硬件触发 + DMA**（最"引擎化"） | TIM 产生 ADC 外部触发（EXTEN），全硬件链路，CPU 完全不参与 | **~0** | 中高。变量最多；但**一旦跑通就是零 CPU 的确定性采样** |

> ★ 三条路都**不改变采样时间**（810.5 周期是为高阻源留的，见 §3.3）。

### 3.2 采样周期语义（比"搬不搬"更重要）

搬进拍内后，"10ms 一次"这个周期该怎么表达？建议：

- **采样周期仍为 10ms，但由拍计数器精确锚定**（如 `tick % 100 == phase`），
  而不是当前 `(tick_now - last) < 100u` 的**相对节流**。
- 两者差别：相对节流 ⇒ 实际间隔 = 100~101 拍（抖动 1%）；**相位锚定 ⇒ 严格 100 拍**。
- 这正是用户理论里的"**时间槽**"——后续可扩展为"每通道各自的采样相位"。

### 3.3 一个可以大幅提速的杠杆（待用户定输入源后启用）

当前 `SMP = 810.5 周期` 是**为自检用内部 40kΩ 上拉驱动而设的最长采样**（`adc.c:69-73` 注释）。
真实输入源阻抗若 ≤ 几 kΩ，采样时间可降到 **8.5~64.5 周期**，则单次转换 ≈ **3~21µs**，
**直接低于拍长** ⇒ 方案 A 可以简化成"当拍启动、当拍读"，甚至可能直接进拍。

⇒ **这是"输入源不清楚"（用户第 3 答）真正卡住的地方**：不是架构问题，是一个
   **源阻抗参数**。参数一确定，方案选择立刻收敛。

## 4. 拍内时间分区设计（用户口述理论的落地）

用户理论：**"上周期末采样搬入、采样前搬出、计算在设定时间"**。

拍内建议相位（与 `h723-core0` 的 ISR 序同构，但保持本工程的分档调度）：

```
拍边界 (TIM 上溢)
 ├─ t0  取 DWT 基准（必须第一条指令）
 ├─ ① 输入回收     MDMA/状态机结果 → SENSOR_MAP     ← "搬入"（消费上周期末的采样）
 ├─ ② 输出锁存     打包 ACTUATOR → AXI 输出字  → DMA2 硬件锁存 ODR   ← "搬出"
 ├─ ③ 路由扫描     分档桶表（div0/div1/div2）      ← "计算在设定时间"
 ├─ ④ 周期 I/O      DI 采样、HIL 输出臂、ADC 状态机推进（按拍相位触发）
 └─ ⑤ ISR 末        ADC kick / MDMA kick             ← "上周期末采样"的发起点
```

**关键性质**：
- ② 的"锁存"由 **TIM 上溢硬件请求 DMA2** 完成 ⇒ 输出沿与拍边界同相，**不经过 CPU**
- ① / ⑤ 成对 ⇒ 输入是"**上一拍末尾**采到、**本拍开头**使用"，**采样与消费严格错开一拍**
- ③ 在中间 ⇒ 计算不被 I/O 打断

## 5. 输出面引脚定案（用户第 2 答："你定"）

### 定案：**DO 面 = GPIOE[15:0]（16 路）**

理由（逐条有据）：

1. **`GPIOE` 在本固件中完全未被使用** —— 全工程唯一提及是 `macro.c:37` 的一句注释
   （"`GPIOEEN=bit4`"）。无冲突。
2. **`h723-core0` 的输出链配方就在 GPIOE 上验证过** ⇒ `M0AR → GPIOE_ODR`、
   `DMAMUX C8 = TIM1_UP`、`M2P+CIRC+32bit+NDTR=1` 可**原样复用**，零试错成本。
3. **16 位恰好落进一个 `u32`** ⇒ 正好回答 `engine.h:120-132` 钉住的定案问题：
   走**选项 ②**（"明确只支持一个端口" + 断言 `mask < (1u<<16)`）——
   **对 SHM 零偏移代价**，且语义与硬件一一对应。
4. 数据来源**用现成的** `OFF_ACTUATOR_STATUS`（64 × f32）：`ACTUATOR[0..15] > 0.5f` → 打包成 u32。
   **不需要新增 SHM 区**。

### 明确不改的（避免一次动两处）

- **心跳继续走 PA8**（LA 的 CH4 已接着）—— 不学 `h723-core0` 把心跳并进输出字，
  因为那会让"拍心跳"与"输出面"耦合，破坏现有的确定性判据。
- `OFF_CTRL_GPIO_MASK` 语义定为：**bit i = 1 ⇒ PEi 由引擎管**（`eng_outputs_safe` 按它清位）。

### ⚠ 待实物确认（唯一的前置条件）

**PE0..PE15 是否都引到板上 2×30 排针。** `HARDWARE-PINOUT.md` 只写了"几乎所有 IO 引出"（`[原理图]`，未实测）。
⇒ 开工第一步：**实测 PE 各脚可写可读**（用现成的 GPIO 自检模式），确认可用的位，
   再决定 DO 位宽（若只引出 8 位，就退到 8 位 + 掩码断言 `mask < (1<<8)`）。

## 6. 输入面方案（用户第 3 答："不清楚"的处理）

**先按现有硬件做，抽象出接口，换源不改架构。**

| 输入 | 引脚 | 现状 | 搬进拍后的形态 |
|---|---|---|---|
| DI ×4 | PC0..PC3 | 主循环 10ms 轮询 | ISR 按拍相位直读 + 去抖（**直接用**）|
| AI ×3 | PA0 / PA1 / PA4 | 主循环 10ms，3 次阻塞读 | ADC 状态机（§3.1 A）→ SENSOR[8..10] |
| HIL 反馈 ×1 | PA5 | 主循环 10ms，16 次阻塞读 | ADC 状态机 → 累加 16 次 → SENSOR[2] |

**接口约定**：I/O 域只认 `SENSOR_MAP` / `ACTUATOR_STATUS`，**不认具体引脚**。
⇒ 将来换输入源（外部 ADC / 编码器 / 总线从站）只换"采样后端"，拍内时序不变。

> 为什么先不引入 MDMA 搬 DI：GPIO 直读本身就是**原子且零延迟**的，MDMA 反而增加一个链路。
> MDMA 的真正价值在 **多字节搬运**（ADC 结果数组、外设 FIFO）——留到方案 B/C 时上。

## 7. 预算核算（结论：**毫无压力**）

实测基线（`docs/REF-flash-placement.md:118`）：混合程序 `isr_max = 11524 cyc`，
**占拍 29.03%，余量 28476 cyc @400MHz**。

搬入后预估增量：

| 项 | 预估代价 |
|---|---|
| DI 采样 + 去抖（每拍） | ≈ 60 cyc |
| HIL 输出臂（每拍） | ≈ 60 cyc |
| DO 打包 + 写 AXI 输出字（每拍） | ≈ 80 cyc |
| ADC 状态机推进（每拍） | ≈ 25 cyc |
| **合计** | **≈ 225 cyc** |

⇒ **占余量 0.8%**。⇒ 预算不是约束；**约束只来自"是否阻塞"**（§2.3/§2.4）。

⚠ 但**ITCM 余量只有 0x68 字节**（`ARCH-H723.md:137`）——搬进来的代码量必须控制，
   **可能需要为新代码腾 ITCM**（例如把非热路径移出 ITCM）。这是**真实的落地风险**，优先级高于预算。

## 8. 分批实施建议

| 期 | 内容 | 风险 | 可验证的判据 |
|---|---|---|---|
| **P1** | **DI + HIL 输出臂搬进拍内**（去掉 10ms 节流 → 拍相位驱动）；`OFF_CTRL_GPIO_MASK` 定案 ②；GPIOE 可用位实测 | 低 | ① DI 变化到 SENSOR 的**延迟从 ≤10ms 降到 ≤采样周期**；② `WIRE[20]` 变化到 `TIM3_CCR1` 的延迟同上；③ `isr_max` 增量 < 200 cyc |
| **P2** | **ADC 非阻塞化（方案 A：拍内状态机）**；`hil_tick` 反馈臂从 16 次阻塞改为"跨拍累加" | 中 | ① 主循环 I/O 占比从 49% 降到 ~0；② ADC 读数与旧路径一致（同一电压下对比）；③ 无 EOC/OVR 错读（现已知连读陷阱） |
| **P3** | **DO 硬件锁存链**（ISR 打包 → AXI → TIM1 UDE → DMA2 S0 → GPIOE_ODR） | 中 | ① LA 实测输出沿抖动（对照 `h723-core0` 的 σ<4.16ns）；② `ACTUATOR` 变化到 PE 引脚延迟 ≤1 拍 |
| **P4** | 可选：ADC 硬件触发 + DMA（方案 B/C）；MDMA 输入链 | 中高 | 零 CPU 采样 |

**建议 P1 与 P2 合并为一次改动**（都属"输入输出链"，且 P2 是 P1 的输入侧对偶），
P3 单独一期（它引入 DMA/DMAMUX 新外设，变量最多）。

## 9. 对照（A/B）设计（用户第 4 答："到时候做实验"）

按项目已确立的纪律（`-DDCL_VTOR_ITCM=0` / `-DDCL_HIL_SAFE=0` 同款），**每期都要有一个
"改前行为"的对照构建**，用**同一套测量方法**打出两份：

| 期 | 编译开关 | 对照档行为 | 交付档行为 |
|---|---|---|---|
| P1 | `-DDCL_IO_IN_ISR=0` | I/O 回主循环 10ms 节流（改前） | 拍内相位驱动 |
| P2 | `-DDCL_ADC_ASYNC=0` | `adc_read` 阻塞自旋（改前） | 拍内状态机 |
| P3 | `-DDCL_DO_DMA=0` | ISR 直接写 GPIO（CPU 写） | DMA2 硬件锁存 |

**判据必须能在对照档上量到 FAIL** —— 否则判据无效，不是"改好了"。
（附带好处：P3 的对照档顺带给出一个"CPU 直写 GPIO"的抖动基线，本身有测量价值。）

## 10. 需要您拍板的三件事

1. **P1+P2 是否合并为一次改动**？（我建议合并，理由是两者是输入/输出的对偶，分开做要动两次 ISR 结构）
2. **GPIOE 的实测前提**：开工前允许我用现成自检模式跑一次 PE 各脚的写读确认吗？
   （不确认就定 16 位，风险是"板子没引出那么多"→ 后期返工）
3. **采样周期是否改为"拍相位严格锚定"**（10ms = 严格 100 拍，去掉 ±1 拍抖动）？
   这是语义变更，会影响现有测试的期望值。

### HIL **输出臂**尚未能进 ISR

**现场**：`PC` 落在某个 `Default_Handler`，`ICSR.VECTACTIVE = 44`，`IABR0 bit28 = 1`，

## B'.2 修法

> **★★ 2026-09-12 中午更正（本节替换当日早间的"256 对齐"结论）**：
> 当晚的"256 对齐"只是**碰巧避开**——上午查 ARM 官方规则才挖到真因：
> **VTOR 的对齐必须是 2 的幂、且 ≥ 4×N（N = 支持的异常总数）**
> （developer.arm.com 102283 原文）。H723：150 IRQ + 16 系统异常 = **166 项**，
> 4×166 = 664 字节 → 向上取 2 的幂 = **1024 字节**。
> - `0x1880`（128 对齐）⇒ 硬件以为表只有 32 项 ⇒ TIM2 索引 44 被掩码成
>   **44 mod 32 = 12**（保留项 → Default_Handler）⇒ 卡死。**CPU 根本没读 slot[44]**。
> - `0x1900`（256 对齐）⇒ 索引 44 < 64 没被掩 ⇒ **纯属运气**；IRQ ≥ 48（索引 ≥ 64）
>   的中断在 256 对齐下全会踩雷——它不是修复，是**埋着的雷**。
> - 0x1880/0x1900 的"一个坏一个好"没有可讲的规律，是掩码算术的巧合。
>
> **真修法**（ld/STM32H723ZG_FLASH.ld，三层，git: 447355b）：
> 1. `.itcm_vectors` 对齐 **1024**，且**钉在 ITCM 末尾**：
>    `_vtor_itcm = ORIGIN(ITCM) + LENGTH(ITCM) - 0x400`（= 0xFC00）——
>    代码从 0x0 向上长，**表位置永不随代码浮动**，一次验证永久有效；
> 2. `ASSERT(_eitcm <= _vtor_itcm)` —— 代码涨进表区时**链接期报错**，不静默上板；
> 3. **拍活体自检**（main.c，`tick_timer_init` 后等 3 tick，不动就 `blink_error(101)`）
>    —— 防"一切取向量失败"，这要在 10 分钟报警，而不是像这次花一个通宵猜。
>
> 实测验收（`_vtor_itcm = 0xFC00`）：`slot[44] @ 0xFCB0 = 0x00000001`（TIM2）、
> `isr_max = 1099 cyc`、A/B 全判据 PASS。

```ld
_vtor_itcm = ORIGIN(ITCM) + LENGTH(ITCM) - 0x400;   /* = 0xFC00, 1024 对齐 */
.itcm_vectors _vtor_itcm (NOLOAD) : { . = . + 1024; _evtor_itcm = .; } >ITCM
ASSERT(_eitcm <= _vtor_itcm, "ITCM code overflow: 热代码吃掉了向量表副本区")
```

**代价**：ITCM 高端留 1KB 给表（0xFC00~0x10000），代码区实际用 6.2KB，余量充足；
越界由链接期 ASSERT 把守，不会静默。
