# exp-ER —— **运动域的「声明时间量」实现了吗**（限时 / 斜坡斜率）

> 一句话：把 E-Q 的方法（**判据里不出现被测常量，只问声明的物理量实现了吗**）搬到运动域，
> 抓出**同一个缺陷家族的第二次复现** —— 斜坡的"拍→ms"早改好了，**正下方 20 行的限时没跟上**。
> 实测：限时在部署条件下流逝 **747 ms/s**（声明 1000）⇒ 声明 2 s 的限时**实走 2.68 s**；
> 而**只要有人在读串口**就变成 990 ms/s。**安全网比声明的松 34%，而且松多少取决于有没有人在看。**

- 工具：`tools/exp_er_motion_time.py`（11 条判据 / 0 SKIP）
- 产物指纹：修复前 `322f6f27…` → 修复后 **`e5a9aaa6…`**（`build/dcl_h723.hex` md5；FLASH 档 `6be7fa83…`）
- 运行记录：`.tmpctl/er_run1.json`（单位错版，见 §7）· `er_run2.json`（修复前）· `er_run3_fixed.json`（修复后）

## §1 为什么做这一条

运动域里有一串"程序里声明的量"，而它们此前的判据强度参差：

| 声明的量 | 既有判据 | 缺口 |
|---|---|---|
| 斜坡 `Hz/s` | `h723_step_ramp_test.py` R3：0→31000 @20000 Hz/s 用时 ≈1.55 s，**容差 ±50%** | 只说"斜率被考虑了"，没量"斜率对不对" |
| **限时 `ms`**（`op=19 sub=4`） | `tools/` 下**没有任何判据量过它的实现值** | 完全空白 |
| 走 N 步 | `h723_step_pulsecount_test.py` P2/P3：脉冲数对得上 | 只判**条数**，不判"声明的时长" |

⇒ 判据的形态与 E-Q 逐条同构：**不问实现，只问声明的物理量**。

| 声明 | 判据 | 观测通道 |
|---|---|---|
| 限时 = `L` 毫秒 | ① 流逝率必须 = **1000 ms/s** ② 到点真的停（`CC1E` 落 0），且停止时刻 − 起点 = `L` | ISR 直写的 tick + `sub=0` 的 112B 状态块 |
| 斜坡 = `S` Hz/s | 从 `f1` 爬到 `f2` 的**实测时长** = `(f2−f1)/S` | `sub=19` 的 `rate_out`/`ramp_active` |
| 斜坡关 | **立即**到位（对照） | 同上 |

时间轴仍用环头里 **ISR 直写**的 `g_tick_count`（E-Q §2.1 的结论：主循环镜像会滞后）；
`1 ms = 10 拍` 这个换算从 `src/engine.h` 的 `TICK_PERIOD_US` **解析**，不手写。

## §2 ★★ 本实验的第二条判据：**同一声明在两种宿主条件下必须给出同一个实现值**

"限时流逝率"在两种条件下各测一次：

| 条件 | 做法 | 实测流逝率 | 声明 2000 ms 的限时实走 |
|---|---|---|---|
| **静默** | 两次读数之间 `sleep 3 s`，**不发任何帧** | **747.1 ms/s**（−25.3%） | **2677 ms** |
| **持续读** | 背靠背读 3 s（169 次） | **990.4 ms/s**（−1.0%） | 2020 ms |

两次独立运行给出同样的数（746/747 与 990/990）。

★ 判据：**两者必须相等（±2%）**。实测差 **24.3%** ⇒ FAIL。
★ 这条之所以是本实验的核心：**真实部署恰好是"静默"那一种**。
  若一个时间量只在被观测时才走准，那么**所有回归都会漏掉它**（回归自己在读串口），
  而现场拿到的是一个**比声明松 34% 的安全网** —— 而且松多少还取决于上位机的轮询节奏。

## §3 根因：`dt / 10u` + `if (dm == 0u) return;`（`src/step.c` 的限时路径）

`step_tick()` 由**主循环**每圈调一次，而主循环一圈 ≈ **0.37 ms ≈ 3.7 拍**。
原实现：

```c
uint32_t dm = dt / 10u;          /* 拍 → 毫秒 */
if (dm == 0u) { return; }        /* ← 3.7/10 = 0 ⇒ 这一圈的时间被整块丢掉 */
```

⇒ `floor(3.7/10) = 0`：**绝大多数圈的时间被整块丢掉**，只有偶尔的长圈（≥1 ms）才走 1 ms。
实测 747 ms/s 与"每圈丢 0.37 ms"的模型一致。

★ 而 `dt > 1000` 的钳位（>100 ms 的长阻塞按 100 ms 计）是**另一个**、**有意**的取舍：
它只会让限时**偏晚**（安全方向），且已在源码里写明。本次的 25% 损失**不是**钳位造成的
（静默窗口里 `dt_max` 只有几百拍量级）。

## §4 ★ 为什么这是"同一个语义两处存放"的**第二次**

同一个文件、**正上方 20 行**的斜坡路径，2026-09-18 已经因为同一个原因改成**余数累加器**：

```c
s_ramp_acc += (uint32_t)((uint64_t)g_step_ramp_hz_s * (uint64_t)dt);
uint32_t dv = s_ramp_acc / 10000u;          /* 10000 拍 = 1 s */
s_ramp_acc -= dv * 10000u;                  /* ← 余数留着 */
```

而**限时这一处没跟上**。与 E-Q 抓到的顺序档 `dt` 表**逐字同族**：

| | E-Q（今天早些时候） | E-R（本次） |
|---|---|---|
| 语义 | `dt`（秒） | 拍 → 毫秒 |
| 已修的那处 | 路由扫描体（`DT_SLOW` 派生） | 斜坡（`s_ramp_acc`） |
| **漏掉的那处** | `engine_seq_tick` 的第二份 dt 表 | `step_tick` 的限时路径 |
| 漏掉那处的后果 | 顺序超时早 36% | 限时流逝慢 25%（实走 +34%） |
| 守护它的断言 | `engine.h` 三条闸门只管路由档那一份 | 无（纯靠判据） |

⇒ 纪律（这次写进 `RULES-DETAIL`）：**发现"同一个量在两处"时，改法不是改另一处，而是消灭另一处。**
★ 本次顺带把全仓的 **拍→ms 换算扫了一遍**：只有两处（斜坡的**对照分支** `#if !DCL_STEP_RAMP_FIX`
与限时这一处）—— 也就是说这一族**已经收敛**，不会再有第三处。

## §5 修法与效果

```c
static uint32_t s_dl_acc = 0u;                 /* 限时的拍余数 (0..9) */
...
if (g_step_deadline_tick == 0u) { s_dl_acc = 0u; return; }
s_dl_acc += dt;                                /* ★ 攒够 10 拍才换 1 ms */
uint32_t dm = s_dl_acc / 10u;
if (dm == 0u) { return; }                      /* 余数留着, 下圈继续攒 */
s_dl_acc -= dm * 10u;
```
并在 `step_set_deadline_ms()` 里把余数清零（否则上一段的 ≤9 拍会漏进新限时）。

| 判据 | 修复前（`322f6f27`） | 修复后（`e5a9aaa6`） |
|---|---|---|
| R1 静默流逝率 = 1000 ms/s ±2% | **747.1** ✗ | **999.7** ✓（−0.03%） |
| R2 持续读流逝率 = 1000 ms/s ±2% | 990.4 ✓ | **1000.0** ✓（+0.00%） |
| R3 两者必须相等 ≤2% | **24.3%** ✗ | **0.0%** ✓ |
| R3b 部署条件下实现限时 = 声明 ±3% | **2677 ms / 2000** ✗ | **2001 ms / 2000** ✓ |
| R4 到点自停 + 停止时刻 = 声明 ±3% | 2045 ms ✓ | **2032 ms** ✓（+1.6%） |
| R5 斜坡爬升时长 = ΔHz/S ±2% | 3.9995 s ✓ | **3.9939 s** ✓（−0.15%） |
| R6 对照: 斜坡关立即到位 | ✓ | ✓ |
| **合计** | **3 FAIL / 11** | **0 FAIL / 11** |

★ 顺带的收获：**斜坡斜率的判据强度从 ±50% 提到 ±2%**（实测 −0.01% ~ −0.15%），
即 `docs/exp-EQ` 里那条"要把余数累加器修好"的结论在运动域**已经成立**（`s_ramp_acc` 是对的）。

## §6 如实登记的**既有 FAIL**（与本次改动无关，附"为什么我能这么说"）

`tools/h723_step_ramp_test.py` 的 **R5**（"斜坡的收益兑现"）本次 FAIL：
突加 vs 斜坡的有效转速都是 1.006（≈1170 rpm）⇒ **提升 +0%**。

- 该判据的前提是旧实测"**突加 31000 Hz ⇒ 只能用到 627 rpm**（比值 0.565，掉步）"；
  现在突加也能到 ~1170 rpm ⇒ **前提在现台架上不成立**（机械/驱动器状态变了）。
- ★ **与本次改动无关的证明**（不是推测）：本次改动整段位于
  `if (g_step_deadline_tick == 0u) { s_dl_acc = 0u; return; }` **之后**，
  而**该套件从不设限时**（`h723_step_ramp_test.py` 里没有 `sub=4`）⇒ 在 `deadline == 0` 时
  新代码与旧代码**行为恒等**。同一轮 `h723_step_pulsecount_test.py` **7 PASS / 0 FAIL**。
- ⇒ 归因：**台架机械状态**，不是固件回归。登记待查（要么重测台架，要么把 R5 改成
  "同一台架上的 A/B"，否则它会随台架状态漂）。

## §7 本次实验自身踩到的两个坑（都值得留）

1. **命令住在 `0x39` 的 sub-op 19 里，不是 `0x19`**
   第一版把 `cmd` 写成 `0x19`（那是另一个 op，读回的是别家的应答）。
2. **载荷必须是 6 字节**：`[19][sub][arg:u32]`。
   第一版只发 5 字节 ⇒ `arg` 落进 `n >= 6u` 的门外 ⇒ **固件静默按 0 处理**
   （命令"发出去了"，值是 0）——症状是"设了 20000 ms 限时，读回 0"。
3. ★★ **单位**：`Δdeadline` 与 `Δtick` 都是 ms ⇒ 商是**无量纲**的，要 ×1000 才是 ms/s。
   第一版漏了这个 ×1000，于是把 **746 ms/s 印成 `0.7 ms/s`**：
   R1 的相对偏差成了 −99.9%（**看起来像"完全不流逝"**），
   而 R3 的 `|差|/1000` 成了 0.02% ⇒ **把 24.3% 的失配读成"完全一致"**。
   ⇒ 两个判据一错一对，正好互相掩护 —— 这就是"**同一个错误模型会同时污染写入与自检**"
   （E-Q §5.78 的同族）在**单位**上的形态。

## §9 边界与未决

1. 限时判据是**单侧**的：实现值允许**偏晚**（`dt>1000` 钳位是有意取舍），但不许偏早、不许差出容差。
2. 静默窗口只有 3 s；更长窗口会把"偶尔的长阻塞"也纳进来（本实验的 `dt_max` 量级说明窗口内没有大阻塞）。
3. **`sub=15`「走 N 步」的"时长"仍未判**：现有 P 组判条数，`h723_motion_calib.py` T3 判频率（±2%），
   但没有人把"**声明的 N 与频率**"合起来对**时间**判一次。登记为下一步。
4. `h723_step_ramp_test.py` R5 的台架归因待查（§6）。
