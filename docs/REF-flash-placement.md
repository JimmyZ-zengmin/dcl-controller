# 参考：flash 落位对取指成本的影响（机制实测）

日期: 2026-09-10 · 平台: STM32H723ZGT6 @400MHz（HSE 25MHz→PLL M5/N80/P1）
上游问题: `AUDIT-H723-stage2.md` H8 —— "flash 落位敏感"此前只有**相关性**，机制未测。
本轮把它做成了机制实验，结论如下。

---

## 0. 一句话结论

> **同一份 2136 字节的机器码（一条指令都没改），只把它在 flash 里的地址挪动 4 字节，
> 扫描 128 条路由的成本就在 `24957 ~ 28827 cyc` 之间变化（极差 15.5%）；
> 19 原语混合程序在 `36967 ~ 41500 cyc` 之间变化（12.3%），
> 而拍长是 **40000 cyc** —— 也就是说"这份程序跑不跑得下"由落位决定。**
>
> 而且成本是地址的**纯函数**：`cost = f(addr mod 32)`，
> 8 个同余类各取两个独立样本，**逐位相同**（16 次独立构建）。

---

## 1. 实验设计：让"落位"成为唯一变量

```
ld/STM32H723ZG_FLASH.ld  新增两个专区:
    .scan_pad    编译期填充 (SCAN_FLASH_PAD 字节, 内容 0x5A)
    .scan_flash  FLASH 版扫描体独占一段, 紧跟填充之后

src/engine.c
    -DSCAN_FLASH_PAD=N  →  在 .scan_pad 里放 N 字节
    engine_scan_flash   →  放进 .scan_flash (section 属性)
    engine_scan_itcm    →  VMA 固定 0x00000000, **完全不受影响** ← 控制组
```

- 填充只改变地址，**不改一条指令**（`.scan_flash` 段大小 16 次构建恒为 2136 B）
- 控制组 `engine_scan_itcm` 落在 ITCM，VMA 固定，其成本 16 次构建**恒为 7225**
  → 若它动了，说明有别的变量混进来，实验作废（本次没有）
- 每次构建都跑完整守卫：表校验和必须等于独立预测 `0x329A37C5`、`ACTIVE=128`、
  栈哨兵完好 —— 16 次全绿，否则该点不算数

复跑：`python tools/h723_pad_sweep.py --pads 0,4,8,12,16,20,24,28,32,40,48,56`

## 2. 实测数据（16 次构建）

| `addr mod 32` | 两个独立样本的地址 | FLASH·全DIRECT | 占拍 | FLASH·19原语混合 | 占拍 |
|---|---|---|---|---|---|
| **16** | `0x08000CD0` / `0x08000CF0` | **24957** | 62.4% | **37115** | 92.8% |
| **12** | `0x08000CCC` / `0x08000CEC` | 26056 | 65.1% | 39526 | 98.8% |
| **0**  | `0x08000CE0` / `0x08000D00` | 26229 | 65.6% | 38953 | 97.4% |
| **8**  | `0x08000CE8` / `0x08000D08` | 26385 | 66.0% | 39209 | 98.0% |
| **4**  | `0x08000CE4` / `0x08000D04` | 27818 | 69.5% | **41500** | **103.8% ★超载** |
| **28** | `0x08000CDC` / `0x08000CFC` | 28043 | 70.1% | 39347 | 98.4% |
| **24** | `0x08000CD8` / `0x08000CF8` | 28553 | 71.4% | 36967 | 92.4% |
| **20** | `0x08000CD4` / `0x08000CF4` | 28827 | 72.1% | 37581 | 94.0% |

```
FLASH·全DIRECT : min 24957  max 28827  极差 3870 = 15.5%
FLASH·混合     : min 36967  max 41500  极差 4533 = 12.3%
ITCM 控制组    : min  7225  max  7225  极差    0   ← 16/16 一样
```

**周期性判据（本实验最强的部分）**：按 `addr mod 32` 分组，每组两个样本
（地址相差恰好 32 B），DIRECT 与混合两列的读数**都逐位相同**：

```
%32 = 0  : 0xCE0 / 0xD00 → 26229 / 26229      混合 38953 / 38953
%32 = 4  : 0xCE4 / 0xD04 → 27818 / 27818      混合 41500 / 41500
%32 = 8  : 0xCE8 / 0xD08 → 26385 / 26385      混合 39209 / 39209
%32 = 12 : 0xCCC / 0xCEC → 26056 / 26056      混合 39526 / 39526
%32 = 16 : 0xCD0 / 0xCF0 → 24957 / 24957      混合 37115 / 37115
%32 = 20 : 0xCD4 / 0xCF4 → 28827 / 28827      混合 37581 / 37581
%32 = 24 : 0xCD8 / 0xCF8 → 28553 / 28553      混合 36967 / 36967
%32 = 28 : 0xCDC / 0xCFC → 28043 / 28043      混合 39347 / 39347
```

⇒ 成本与"页面/历史/cache"无关，是 **`addr mod 32` 的确定函数，周期 32 字节**。

## 3. 机制解释（与器件的取指粒度一致）

H7 的 flash 读数据通路是 **256 位 = 32 字节**一条：
一次取指请求整条取回，跨越 32 字节边界的循环体会多付一次取指请求。
扫描体 2136 字节约 67 条 32 字节行，热点循环每轮跨越的行数随"落位"变化，
于是**同样的指令、同样的执行次数，取指请求次数不同** → 周期数不同。

这也解释了为什么 **I-cache 关掉时效应最大**（每次取指都真的发 flash 请求），
以及为什么 **ITCM 完全没有这个效应**（零等待、无 cache、无 32 字节取指行概念）。

> 口径：本页只声称"成本是 `addr mod 32` 的确定函数，周期 32 字节"（16 次实测）。
> "32 字节 = flash 256 位数据通路"是与器件手册一致的**解释**，
> 若要单独坐实需要厂商级的取指计数（本项目无此仪器）。

## 4. 为什么这条结论比"ITCM 更快"更重要

`AUDIT-H723-stage2.md` H8 之前只能写"换个地址成本就变 5%"（对照组是另一个构建）。
现在是**受控扫描**：16 次构建、唯一变量、控制组零漂移、8 个同余类双样本复现。
由此可以得到三条可用于**工程决策**的推论：

1. **"用 flash 地址算 WCET 预算"是不可能的** —— 预算会随下一次无关改动的落位而变，
   幅度可达 15%，而拍长恰好落在这个摆幅内。
2. **"编译通过 + 实测跑得动"不是证据** —— 本次 16 个点里，
   同一份混合程序有 1 个落点超载（103.8%），其余 15 个都在拍内。
   换一次构建就可能翻面（阶段 2 审计期间真的翻过一次）。
3. **热代码必须进 ITCM 这条从"优化"变成"设计前提"** ——
   ITCM 侧 16 次构建成本恒为 7225，**误差项为零**。

### 4.1 交付固件的现状（值得盯一眼）

当前交付固件里 `engine_scan_flash @ 0x08000CCC`（`%32 = 12` 类），实测：

```
C1 FLASH·混合   eng_min 39426  isr_max 39891  → 占拍 99.73%
                距拍长仅 **109 cyc（0.27%）**；拍周期已出现 24 cyc(60ns) 的零散抖动
C2 ITCM ·混合   eng_min 11436  isr_max 11524  → 占拍 29.03%   余量 28476 cyc
```

也就是说：**交付固件的 FLASH·混合组，距"拍被拉长"只有 109 个周期 ——
加一行无关代码就可能翻面**（同一个程序在 `%32 = 4` 的落点是 103.8% 超载）。
对照 ITCM 版余量 71%。

这不是"当前有问题"，而是"当前**恰好**没事" —— 正是 §4 第 2 条说的：
"编译过 + 实测跑得动"不是证据。

## 5. 工程上怎么用

| 场景 | 做法 |
|---|---|
| 引擎热代码（路由扫描 / 后续的顺序域 / 通信域每拍部分）| **一律进 `.itcm_text`**，不进 flash |
| 表数据 | 进 **DTCM**（`.dtcm_shm`），零等待、不过 AXI（HCLK=CPU/2） |
| 非热代码（初始化、deploy、HMI、诊断）| 留 flash，用 32 字节对齐即可，成本不重要 |
| 落位敏感性自检 | 发布前跑一遍 `h723_pad_sweep.py`（或至少 2~3 个 pad 点），
确认关键路径**不在**摆幅边缘 |
| 预算余量 | 对**必须**留在 flash 的热路径，按"最坏落位"取值（本次 +15%），
不要按某一次实测值 |
