**绑定表语义**：上位机下发"每 N 拍读 `设备地址/寄存器/长度` → 写 `SENSOR[z]`"，由拍内状态机执行。
条目 u32 = `dev<<28 | dst<<24 | len<<16 | reg<<8 | addr7`；`dev=1` 表示通用 I2C 读。
表的校验和是 **FNV-1a 按 32 位字**（与 `bb_map_sum` 同形，**不是按字节**）。

## 3. ★ 破坏性变更（上位机必须处理）

1. **能力字变了**（`0x0DF7` → `0x1DF7` → `0x3DF7` → **`0x7DF7`**；本日三个批次各加一位）。
   ★★ **认口判据必须是"必备位掩码"而不是等值**：`(cap & 0x0DF7) == 0x0DF7`。
   写成 `cap == 0x0DF7` 的实现会在本版**认不到板子**，而症状是"**找不到板子**"（会把人引向接线/驱动方向）。
   本仓库已把 `h723_client.link_alive()` 改成掩码语义；`h723_proto.py` 的 **T1.4 保留等值比较**（那是"宣称=实现"审计，职责不同，**刻意不合并**）。
2. **`0x39 op=22` 的应答结构未变，但语义更严**：`+32` 是引用计数 `refs`，**正常空闲必须 == 0**。
3. `0x38 ENGINE_STATUS` 长度与布局**未变**（仍 51 B）。
4. **`0x48 PROG_STATUS` 从 96 → 104 B**（尾部追加 `boot_seg` / `seg_len`，**前面 96 B 未动**）。
   ★ 任何"长度 == 96"的**等值**判据都会被这次纯追加打红 —— 判据请写 `>= 96`。
5. 绑定表**现在会随程序包持久化**（开机自动恢复）；但 `0x13 RESET` 仍会把它清空
   （复位是运行态语义，恢复发生在**上电装载**）。上位机读回 `DB_REQ_SEQ` 作基准即可。

## 4. ★★★ 本版顺带修掉的**真缺陷**（都是"无报错、只有值是错的"族）

> 这些不是 G6-4 的特性，而是**实现过程中被逼出来的**。它们的存在本身就是本版最重要的产出之一。

| # | 缺陷 | 为什么它会**静默** | 修法 |
|---|---|---|---|
| ① | **在飞事务期间换表** ⇒ 收尾用**新表**的 `dst/len` 解释**旧事务**的数据 | `reject=0`、计数照涨，无任何错误迹象 | **暂存 + 延后 `done_seq`**（收尾之后才是唯一换表点）|
| ② | **事务结果归属不明** ⇒ 另一个使用者插入并完成后，**他的读数被写进我的槽** | 同上 | **归属令牌** `done_req == my`（住在资源处）|
| ③ | ★ **令牌必要但不充分**：`s_status` 是**实时态**，被拒的请求会覆写它 ⇒ "令牌匹配但状态已变" ⇒ **丢弃自己的好数据并计错** | 表现为"计数涨、值不变" | **完成记录** `{req, status, len}`（完成那刻快照、受理即失效），取数只走 `take_result(my,…)` |
| ④ | ★★ **总线门引用计数泄漏**：`i2c_sm_request()` **先占门、后验参**，非法参数分支不放门 | 症状是**所有依赖阻塞路径的判据一起变红**，指向"总线被谁占了"，与真因（一次 `len=9` 的请求）相隔极远 | **先验参、再拿门** |
| ⑤ | ★★★ **延迟释放在丢释放**：受理新请求时把"待释放"清 0 ⇒ 上个事务的那次释放被丢掉 ⇒ **引用计数每次泄漏 1** | 实测累积 **`refs=61`**、`owner=SM` 冻结、状态机 idle、表为空 ⇒ **AS5600 永久饿死**；且表现为**跑测顺序依赖**（`dev_bind` 之后 G6-2 全红、单跑全绿）| **配对计数**（完成 +1、主循环 `while` 还清）+ 主循环**引用计数对账**（自愈并计入 `g_i2c_ref_leak_n`）|
| ⑥ | **一个槽两个语义**：`DB_ERR_N` 被"轮询失败"与"上传被拒"共用；`DB_LAST_ERR` 被两个**数值重叠**的码空间共用 | "err 在涨"**无法解释** ⇒ 判据作废 | 拆成 `ok_n / err_n / skip_n / rej_n` + `reject` / `last_err` 两个独立槽 |
| ⑦ | **序号不单调不挡** ⇒ 重放一张旧表就把现场**打回旧配置** | 旧表字段全合法、crc 也对 | 有符号差判回退；**且不回退 `done_seq`** |
| ⑧ | **工具认口是等值比较**（见 §3.1）| 加一位 ⇒ 所有工具一起认不到板子 | 必备位掩码 |

★ **⑤ 一处修复消掉了三个看起来无关的症状**（`refs` 泄漏 / 跑测顺序依赖 / `dev_bind_test` 只能跑到 53-1-2）。
★★ **抓到 ④⑤ 的是"为可解释性加的观测"**：`refs` 计数（G6-2 专为泄漏准备）与 `skip_n` 计数。
**"为可解释性加的计数器，会顺手把静默故障变成可读指纹"** —— 本版第十次印证。

## 7. 升级指引（上位机）

### 7.1 必须改的（不改就会"找不到板子"）
1. **认口判据用必备位掩码**：`(cap & 0x0DF7) == 0x0DF7`。**不要写等值** ——
   能力字随版本增长（`0x0DF7 → 0x1DF7 → 0x3DF7 → 0x7DF7`），等值判据会让你以为"板子没响应"。

### 7.2 帧归属 v2（GAP-12，**建议所有新代码都开**）
```
协商    0x05 FRAME_MODE [mode:u8]   1=进入 v2 / 0=回到 v1     ★ 它的应答**永远用 v1 帧**
v2 请求 [C2][CMD][SEQ][LEN:2][payload][CRC:2]      CRC 覆盖 [CMD][SEQ][LEN:2][payload]
v2 应答 [C3][CMD][SEQ][STS][LEN:2][payload][CRC:2] CRC 覆盖 [CMD][SEQ][STS][LEN:2][payload]
能力位  DCL_CAP_FRAME_V2 = 0x4000
读设备侧模式  0x39 op=24 sub=0 → 8B: [mode:u32][v2_frames:u32]
```
**不开 v2 的代价（有实测）**：v1 应答里**没有命令字段**，客户端只能"收到任何合法帧就当应答"；
本轮实测到密轮询 `0x22` 读 1 个字时读到 `0x1DF70200` = **一次 `0x01` 的应答**。
★ 最坏巧合：`0x22` 读 1 个字的应答**也是 4 字节** ⇒ **连长度判据都分不开**。
**四条规则**（不遵守就会出错）：① `0x05` 的应答**永远用 v1**（否则握手无解）
② v2 从**下一帧**起生效 ③ 帧模式是**逐链路状态** ⇒ `0x13 RESET` 与上电都会回 v1，
**你的客户端在 RESET 后必须也退回去**（否则设备等 v2、你发 v1 ⇒ 链路失联）
④ 序号**只回显、不强制顺序**（本版不做重传窗口 → 你可以自由选序号，设备不判顺序）。
⑤ ★★ **你的客户端退出（含异常退出）时必须把模式复位回 v1** —— 实现方式：放 `finally`，
   发一条 **v1** 的 `0x05 mode=0`。**不复位的后果（我自己踩到过）**：设备留在 v2 ⇒
   之后所有用 v1 的工具**全部 `TIMEOUT`**，症状是"板子没响应"，会把人引向接线/驱动方向。
   ★ 救场命令（**记这一条就够了**）：
   `python tools/h723_frame_attrib_test.py --reset-mode`
   —— 它用 v1 发 `0x05 mode=0`，而按规则①**它的应答强制 v1** ⇒ 一定收得回来。
   ★ 这也解释了规则①为什么必须存在：它不只让**握手**可解，还让**退出**成为可能。

### 7.3 接一个新器件（GAP-6，不用改固件）
写 `DB_ENTRIES[8]` → 算 **FNV-1a（按 32 位字）** → 写 `DB_CRC` → `DB_PERIOD` → **最后**递增 `DB_REQ_SEQ`；
轮询 `DB_DONE_SEQ == DB_REQ_SEQ` 判定已生效（**拒绝也会回 done_seq，除序号回退那一种**）。
★ **每次提交前先读回 `DB_REQ_SEQ` 当基准，不要自己维护计数器**。
理由（两条都对）：`0x13 RESET` 会把它归 0；`0x10 DEPLOY` 等路径也各自有语义。
★ 而**"装载恢复绑定表"本身不会推进 `req_seq`** —— 本条实现的第一版会（每次恢复 +1），
后果很隐蔽：上位机自维护序号时**第一次恢复后就撞号**，而 `dev_bind_submit()` 在 `req==done` 时
**静默 return** ⇒ **之后每条判据都在旧表上跑 ⇒ 全假 PASS 且没有任何症状**。已在固件里修掉
（装载走 `db_validate_apply(0)`，**绝不触碰 `REQ_SEQ`/`DONE_SEQ`**）。详见 §6 #7。

### 7.4 绑定表随程序包持久化（GAP-11）
程序包上传时**不用你操心**：固件在 `0x47 COMMIT` 里自动把当前绑定表作为**载荷尾部 48 B 段**附加落盘，
**开机自动恢复**。`0x39 op=23 sub=0` = **重新执行开机装载**（程序 + 绑定表）⇒ 返回 `[rc][loaded]`。
`0x48` 尾部追加 `+96 boot_seg`（0=无段/1=恢复/2=段坏）与 `+100 seg_len`（0 或 48）。

### 7.5 读结果与看计数
- 读结果看 `SENSOR[dst]`；**失败时该槽保留旧值**（不是 0）—— 不要把它当成"读到 0"。
- 诊断计数**分开看**：`ok_n` 执行成功 / `err_n` 器件或通信故障 / `skip_n` 调度现象 / `rej_n` 上传被拒 /
  `load_ok_n`+`load_bad_n` 绑定表装载结果。★ 别把它们合成一个"错误数"：
  **一个计数只回答一个问题**，混在一起，"err 在涨"这条判据就无法解释。

### 8.2 上机验收（5 套 + 1 条泄漏判据，共 126 条；板子在 COM21）

## 9. 这一版把"一致性"交给了机器（C 线）

**背景**：两轮独立审计查出 **5 处"契据 vs 实现不一致"**，全部是**人能发现、机器发现不了**的。
★★ 而"**契据写了、代码没做**"比"完全没做"**更危险** —— 下一个人会照契据去改，从而**改坏**。

**做法**：`docs/claims.md`（契据的可执行摘要，**八类**主张）+ `tools/ref_claims_check.py`（**构建第 5 道闸门**）。
| 类 | 机检什么 |
|---|---|
| **A 结构** | 契据声称的符号必须在代码里存在；`OFF_*` 还须被 `_Static_assert` 守住 |
| **B 拒绝码** | 定义 + **被赋值** + 有判据读到它；缺判据必须 `--allow-uncovered <理由>` |
| **C 能力位** | 定义 + 并入 `IMPL` + 不在 `NOTYET` |
| **N 留位** | 定义了但**故意不实现**的位（"留位 ≠ 实现"要被显式记住）|
| **C2 完整性** | `transport.h` 里**定义了的每个位都必须被分类**为 C 或 N —— 否则闸门看不见它 |
| **D 文档漂移** | `docs/**` 里的 `文件:行号`：被引符号是否还在该文件（标"过时"横幅的文档跳过）|
| **E 判据存在性** | 契据的"能失败的判据表"每一条，必须能在验收脚本里 grep 到 `record("…")` |
| **N 留位** | 定义了但**故意不实现**的位（"留位 ≠ 实现"要被显式记住）|
| **C2 完备性** | `transport.h` 里**定义了的**每个位都必须被分类为 C 或 N —— 否则闸门看不见它 |
| **F 门面一致性** | ① 表格行**不得自相矛盾**（现状说"已完成"、状态列写"未完成"）② 提到"实现字/能力字"的行，**末值必须等于代码的 `IMPL`**；③ **门面里的本地链接必须指向真实文件**。★ 补它的原因：原闸门只管"契据⇄代码"，**管不到发布说明/GAP 表/README** —— 本日真的出现过 **6 处过期状态**，而**门面写错比没写更坏** |
