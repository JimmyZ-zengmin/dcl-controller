## 1. 一句话

**契约里"接一个新器件 = 写一段程序"这句话，在本版之前是兑现不了的**（源码事实：③层程序无法发起任何 I2C 事务，
见契约 §3.7.1）。本版把它变成**兑现得了**的：接新器件 = **上传一段配置**。

## 2. 新增（对外）

| 件 | 内容 |
|---|---|
| **能力位** | `DCL_CAP_DEVBIND = 0x1000` ⇒ 实现字 **`0x0DF7` → `0x1DF7`** |
| **SHM 新域** | `OFF_DEV_BIND = 0x7300`（80 B）：具名设备绑定表，**上位机可写**（走现成 `0x23 WRITE_BURST`，**不加新命令码**）|
| **自述** | `0x4A DEVICE_DESC` **尾部追加**一块（`n_devbind/槽数/ops 位图/SHM 偏移`）；`0x64 SYS_MANIFEST` 新增 `I2C_XACT` 与 `DEV_BIND` 两条目录项 |
| **状态码** | `I2C_SM_ST_STOLEN = 7`（事务结果被后一个事务覆盖 ⇒ 不得当成功）|
| **新工具** | `tools/h723_dev_bind_test.py`（上机验收，**只走协议**）· `h723_dev_bind_test_selftest.py`（**离线**变异自测）· `h723_i2c_leak_check.py`（引用计数泄漏判据）|

**绑定表语义**：上位机下发"每 N 拍读 `设备地址/寄存器/长度` → 写 `SENSOR[z]`"，由拍内状态机执行。
条目 u32 = `dev<<28 | dst<<24 | len<<16 | reg<<8 | addr7`；`dev=1` 表示通用 I2C 读。
表的校验和是 **FNV-1a 按 32 位字**（与 `bb_map_sum` 同形，**不是按字节**）。

## 3. ★ 破坏性变更（上位机必须处理）

1. **能力字变了**（`0x0DF7` → `0x1DF7`）。
   ★★ **认口判据必须是"必备位掩码"而不是等值**：`(cap & 0x0DF7) == 0x0DF7`。
   写成 `cap == 0x0DF7` 的实现会在本版**认不到板子**，而症状是"**找不到板子**"（会把人引向接线/驱动方向）。
   本仓库已把 `h723_client.link_alive()` 改成掩码语义；`h723_proto.py` 的 **T1.4 保留等值比较**（那是"宣称=实现"审计，职责不同，**刻意不合并**）。
2. **`0x39 op=22` 的应答结构未变，但语义更严**：`+32` 是引用计数 `refs`，**正常空闲必须 == 0**。
3. `0x38 ENGINE_STATUS` 长度与布局**未变**（仍 51 B）。
4. 绑定表是 **RAM-only**：`0x13 RESET` / 上电 / deploy 装载都会清空（见 §6 已知问题）。

## 4. ★★★ 本版顺带修掉的**真缺陷**（都是"无报错、只有值是错的"族）

> 这些不是 G6-4 的特性，而是**实现过程中被逼出来的**。它们的存在本身就是本版最重要的产出之一。

| # | 缺陷 | 为什么它会**静默** | 修法 |
|---|---|---|---|
| ① | **在飞事务期间换表** ⇒ 收尾用**新表**的 `dst/len` 解释**旧事务**的数据 | `reject=0`、计数照涨，无任何错误迹象 | **暂存 + 延后 `done_seq`**（收尾之后才是唯一换表点）|
| ② | **事务结果归属不明** ⇒ 另一个使用者插入并完成后，**他的读数被写进我的槽** | 同上 | **归属令牌** `done_req == my`（住在资源处）|
| ③ | ★ **令牌必要但不充分**：`s_status` 是**实时态**，被拒的请求会覆写它 ⇒ "令牌匹配但状态已变" ⇒ **丢弃自己的好数据并计错** | 表现为"计数涨、值不变" | **完成记录** `{req, status, len}`（完成那刻快照、受理即失效），取数只走 `take_result(my,…)` |
| ④ | ★★ **总线门引用计数泄漏**：`i2c_sm_request()` **先占门、后验参**，非法参数分支不放门 | 症状是**所有依赖阻塞路径的判据一起变红**，指向"总线被谁占了"，与真因（一次 `len=9` 的请求）相隔极远 | **先验参、再拿门** |
| ⑤ | ★★★ **延迟释放在丢释放**：受理新请求时把"待释放"清 0 ⇒ 上个事务的那次释放被丢掉 ⇒ **引用计数每次泄漏 1** | 实测累积 **`refs=61`**、`owner=SM` 冻结、状态机 idle、表为空 ⇒ **AS5600 永久饿死**；且表现为**跑测顺序依赖**（`dev_bind` 之后 G6-2 全红、单跑全绿）| **配对计数**（完成 +1、主循环 `while` 还清）+ 主循环**引用计数对账**（自愈并计入 `g_i2c_ref_leak_n`）|
| ⑥ | **一个槽两个语义**：`DB_ERR_N` 被"轮询失败"与"上传被拒"共用；`DB_LAST_ERR` 被两个**数值重叠**的码空间共用 | "err 在涨"**无法解释** ⇒ 判据作废 | 拆成 `ok_n / err_n / skip_n / rej_n` + `reject` / `last_err` 两个独立槽 |
| ⑦ | **序号不单调不挡** ⇒ 重放一张旧表就把现场**打回旧配置** | 旧表字段全合法、crc 也对 | 有符号差判回退；**且不回退 `done_seq`** |
| ⑧ | **工具认口是等值比较**（见 §3.1）| 加一位 ⇒ 所有工具一起认不到板子 | 必备位掩码 |

★ **⑤ 一处修复消掉了三个看起来无关的症状**（`refs` 泄漏 / 跑测顺序依赖 / `dev_bind_test` 只能跑到 53-1-2）。
★★ **抓到 ④⑤ 的是"为可解释性加的观测"**：`refs` 计数（G6-2 专为泄漏准备）与 `skip_n` 计数。
**"为可解释性加的计数器，会顺手把静默故障变成可读指纹"** —— 本版第十次印证。

## 5. 验证证据（全部可复跑）

**构建**：零警告 + **三道静态闸门**全绿（ISR 调用树 / 应答缓冲区越界 / ③层静态判据）。

**上机（只走协议，零 pyocd）**：
| 套件 | 结果 |
|---|---|
| `h723_dev_bind_test.py` | **55 PASS / 0 FAIL / 1 SKIP**（SKIP = `dst=16` 死码，**刻意**）|
| `h723_i2c_sm_test.py`（G6-1）| 10/10 |
| `h723_i2c_gate_test.py`（G6-2）| 全 PASS |
| `h723_i2c_shm_test.py`（G6-3）| 全 PASS |
| `h723_i2c_leak_check.py` | PASS（非法请求后 `owner=0 / refs=0`）|

**最硬的两条判据**：
- `T5.4`：绑定表写出的 `SENSOR[7]` 与 **SHM 事务区独立读回**的值**相同**（3347）
  ⇒ 兑现 `i2c_bb.h:8` 的纪律"**两条独立路径对上才算数**"。
- `T6`：改绑到不存在的从机 ⇒ `err_n` **必须涨**（证明判据非空），而 `SENSOR` **仍是哨兵**
  （"没读到"没有伪装成"值=0"）。

**判据自身的对照**（`_selftest.py`，离线可跑）：六种注入（不校验 crc / reset 漏登记 / 失败写 0 /
拒绝不回 `done_seq` / 提交未被调用 / 缺能力位）+ **立即换表**，**每一种都让对应判据变红**；
**立即换表**的指纹是 `13.0` = AS5600 首字节 `0x0D` 按**新表** `len=1` 落进**新表** `dst=15`
⇒ "用错 lane"有了**对照实验**，不只是"跑通了"。

**决定性 A/B（同板 / 同判据 / 只差那一处改动）**：
| | `dev_bind_test` 收尾的 `op=22` | AS5600 阻塞路径 |
|---|---|---|
| 修复 ⑤ 之前 | `owner=2(SM)`、**`refs=56~68`** | **饿死**（`tx` 不涨）|
| 修复 ⑤ 之后 | **`owner=0`、`refs=0`** | **恢复**（`tx` 1 s 内 2158→2340）|

## 6. 已知问题（**均不阻塞本版**，但必须知道）

| # | 项 | 性质 |
|---|---|---|
| 1 | **绑定表不持久化**（契约 §3.8.5 未落地）| `prog_store`/`transport`/`manifest` 里**没有**该字段 ⇒ **RAM-only，掉电即失**。每次上电后必须重新下发 |
| 2 | ★★ **应答不带归属**（无命令码回显/序号）| 客户端"收到任何合法帧就当应答"。**本版拿到一个解码过的现场实例**：`SENSOR[15]` 的读回值位型 `0x1DF70200` = **`0x01 GET_VERSION` 的载荷**；且 `0x22` 读 1 个字的应答**也是 4 字节**，长度都分不开。⇒ **v1 首选**（GAP-12）|
| 3 | `h723_seq` 的 **T28.B1** 失败（26/1）| **判据缺陷**（非本版引起）：期望"起点 `WIRE[0]` 空闲"，而 bench profile 把 `SENSOR[0]`（AS5600 RAW=3347）镜像到 `WIRE[0]` ⇒ 序贯器起步就推 2 步。`--wipe` 后仍复现。**修法 = 换一个没有 bench 路由写入的 WIRE 槽** |
| 4 | `h723_i2c_shm_test` 的 **S5** 偶发（`TICKS=2` 而非 3）| **未定案**：SM 早已 idle，无法归因到 pending/release；倾向"测试观测窗口太紧"（`TICKS` 是**稳定性质**，不是瞬时性质）|
| 5 | **`0x39 op=7`（重新校时）在交付固件里不存在** | 时基死在协议面上**无法自证** —— 但本版时基已是 **TIM5**（`op=21` 可读健康度），影响已大幅降低 |
| 6 | `DB_RC_DST(6)` / `DB_RC_NOSEQ(8)` 是**死码** | 编码层就不可达。**保留**（冗余自检层）但**不得**当"已验证的拒绝路径"记账（契约 §3.8.4 末段）|

## 7. 升级指引（上位机）

1. **改认口判据为掩码**（`(cap & 0x0DF7) == 0x0DF7`）—— 不改就会"找不到板子"。
2. 要接新器件时：写 `DB_ENTRIES[8]` → 算 **FNV-1a(按字)** → 写 `DB_CRC` → `DB_PERIOD` → **最后**递增 `DB_REQ_SEQ`；
   轮询 `DB_DONE_SEQ == DB_REQ_SEQ` 判定已生效（**拒绝也会回 done_seq，除序号回退那一种**）。
3. 读结果看 `SENSOR[dst]`；**失败时该槽保留旧值**（不是 0）——不要把它当成"读到 0"。
4. 诊断计数分开看：`ok_n` 执行成功 / `err_n` 器件或通信故障 / `skip_n` 调度现象 / `rej_n` 上传被拒。
