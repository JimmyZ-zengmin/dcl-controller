# 周期内通讯时间窗详细设计

> **版本**: v1.0 | **日期**: 2026-07-16
> **核心思想**: 在100μs固定时间表中，通讯作为一等公民参与规划，而非"有空再传"的尽力而为模型

---

## 一、背景：为什么需要通讯时间窗

### 1.1 火车模型回顾

DCL引擎采用**严格规划的固定时间表**（火车模型），而非传统主循环的尽力而为模型：

```
100μs周期 = 一列火车的时刻表
  各组件 = 乘客（路由扫描、ADC、通讯）
  余  量 = 发车前的预备时间
  违  约 = 乘客没赶上火车 → 下一班
  CCR4 match (97.5μs) = 铁定发车，不等任何人
```

传统嵌入式的通讯做法（主循环中轮询）在DCL架构中不适用，因为：
- 主循环优先级低于ISR，只有在ISR间隙才能执行
- 主循环的可用时间不确定，ISR负载波动时，通讯可能被无限推迟
- 无法保证通讯的延迟确定性

**解决方案**：把通讯作为固定时间片嵌入ISR时间表，每周期获得确定的执行时间。

### 1.2 设计目标

| 目标 | 要求 | 验证方法 |
|------|------|---------|
| **零违约** | 通讯窗口在任何情况下不超过分配的1200cyc | 最坏路径测试（全命令同时到达） |
| **确定性延迟** | PC命令响应 < 200μs（2个周期） | 示波器测量CMD→ACK时间 |
| **零侵入** | 监控数据打包不影响引擎计算结果 | PERIOD_MIN在执行监控前后不变 |
| **MAC并行** | 位时序由MAC硬件处理，CPU不参与 | CPU窗口内仅操作描述符 |

## 二、时间表设计

### 2.1 完整时间表

```
TIM1_CLK = 120MHz → 1 tick = 8.3ns
ARR = 11999 → 周期 = 12000 ticks = 100μs
CCR4 = 11700 → DMA触发点 = 97.5μs

  cyc范围    时间范围     行为                   CPU耗时
 ─────────────────────────────────────────────────────────────
  0-400      0-3.3μs     路由扫描                35原语 < 400cyc
  400-600    3.3-5μs     ADC/传感器处理           ~200cyc
  600-1800   5-15μs      ★ 通讯窗口              ~1200cyc
  1800-2000  15-16.7μs   余量A (防违约缓冲)      200cyc
  2000-11700 16.7-97.5μs 余量B (lwIP后台处理)    9700cyc
  11700-12000 97.5-100μs DMA SHADOW→ODR          硬件自动
```

### 2.2 通讯窗口内部子时间片

通讯窗口（600-1800 cyc，共1200 ticks = 10μs）的精细分配：

```
  600-750    (150cyc, 1.25μs) ETH RX描述符环检查
              检查RX DMA描述符 → 有新帧？→ 取header → 校验MAGIC
  
  750-1050   (300cyc, 2.5μs)  0xC0帧命令解析
              READ/WRITE即时执行 → 写WIRE_MAP → 构造响应
              MONITOR/MONITOR_STOP更新订阅表
              
  1050-1350  (300cyc, 2.5μs)  监控数据打包入TX队列
              从snap_ring取订阅数据 → 打包0x31帧 → enqueue TX
              
  1350-1500  (150cyc, 1.25μs) ETH TX描述符环处理
              检查TX desc空闲 → 启动DMA发送 → 更新统计
  
  1500-1800  (300cyc, 2.5μs)  余量 (防窗口溢出)
              预留用于突发负载 (批量WRITE_BATCH等)

  总占用: 1200 cyc = 10μs (占周期的10%)
```

> **关键规则**：达到1800 cyc后，不论是否处理完毕，立即退出通讯窗口。
> 未完成的操作（如未解析完的帧）丢弃，等待下一周期。
> 这保证了通讯窗口的**硬截止**，永远不会侵犯后续时间片。

### 2.3 时间线图示

```
0μs      5μs      10μs     15μs     20μs                      97.5μs   100μs
│        │        │        │        │                         │        │
├─路由──├ADC────★通讯窗口──┤余A├───────────余量B────────────────├DMA输出┤
                │

```

## 三、通讯窗口操作规范

### 3.1 TX流程（发送数据）

```
通信窗口入口 (600cyc)
    │
    ├─[Step 1] 检查TX DMA描述符环
    │   └─下一个可用描述符索引 tx_tail = (tx_tail + 1) & (TX_RING_SIZE-1)
    │
    ├─[Step 2] 有数据要发送？
    │   ├─YES → 从TX队列取出待发送帧
    │   │       帧格式: [len:2B][payload...] (预打包)
    │   │   └─填充TX描述符: buffer_addr = 帧地址, length = 帧长
    │   │   └─清TX描述符OWN bit → 通知MAC发送
    │   │
    │   └─NO  → 跳过
    │
    └─[Step 3] 统计 TX 计数 + 字节数
```

**限制**：每周期最多发送1-2帧（~160字节），避免占用过多窗口时间。
大块数据（烧录、OPC UA响应）通过主循环拼接后，在余量B中入列TX队列。

### 3.2 RX流程（接收数据）

```
通信窗口入口 (600cyc)
    │
    ├─[Step 1] 检查RX DMA描述符环
    │   └─读取 rx_head 描述符 → 检查OWN bit
    │       ├─OWN=0 (MAC已完成接收) → 有新的以太网帧
    │       └─OWN=1 (MAC正在接收)  → 无新帧，退出
    │
    ├─[Step 2] 解析以太网帧头
    │   └─检查目的MAC是否匹配 / 广播帧
    │   └─检查 EtherType = 0x0800 (IPv4)
    │
    ├─[Step 3] 解析IP/UDP/TCP头 (简易校验)
    │   └─UDP:502 → 检查端口 → 提取payload → 输入到命令解析器
    │   └─TCP:502 → 检查序列号 → 提取segment数据 → 输入到TCP状态机
    │       (注意: TCP完整状态机在余量B执行, 窗口内只做数据后移)
    │
    ├─[Step 4] lwIP协议处理(轻量)
    │   └─输入数据到lwIP → lwIP处理 → 输出数据到TX队列
    │   (注: 窗口内只做简单处理, 复杂状态机在余量B的polling中)
    │
    └─[Step 5] 归还RX描述符给MAC
        └─设置OWN bit → 移动 rx_head
```

**优化设计**：TCP状态机分拆

| 阶段 | 执行时机 | 工作内容 | 时间限制 |
|------|---------|---------|---------|
| RX数据上传 | 通讯窗口(ISR) | 从DMA desc拷贝数据到lwIP input buffer | 200cyc |
| TCP协议处理 | 余量B(主循环) | ACK/重传/窗口管理/序列号重组 | 不限(但需总<97.5μs) |
| TX数据下发 | 通讯窗口(ISR) | 从lwIP output取出数据 → 填充TX desc | 150cyc |

### 3.3 命令分类与执行策略

| 命令 | 窗口内执行内容 | 耗时 | 延迟 |
|------|--------------|------|------|
| READ (0x20) | 读WIRE_MAP → 构造响应帧 → enqueue TX | ~100cyc | **1周期 (100μs)** |
| WRITE (0x21) | 解析参数 → 写WIRE_MAP → 响应ACK | ~100cyc | **1周期** |
| WRITE_BATCH (0x22) | 批量写(最多32个float) | ~300cyc | **1周期** |
| START/STOP/RESET | 改引擎状态标志 | ~50cyc | **1周期** |
| MONITOR (0x30) | 更新订阅表(信号索引列表) | ~150cyc | **1周期** |
| MONITOR_STOP (0x31) | 清订阅表 | ~50cyc | **1周期** |
| PING (0x40) | 回PONG | ~30cyc | **1周期** |
| DEPLOY (0x10) | [不直接执行] 数据入列，主循环拼接 | 0(窗口内) | ~10ms(完整) |

**窗口内命令优先级顺序**：
```
1. PING (最轻量, 保活)
2. READ/WRITE/WRITE_BATCH (用户交互, 响应速度敏感)
3. MONITOR/MONITOR_STOP (配置变更)
4. START/STOP/RESET (控制命令)
5. DEPLOY (不消耗窗口, 数据入列到主循环缓冲区)
```

### 3.4 窗口超时保护

```c
// 通讯窗口入口
void comm_window_isr(void) {
    uint32_t deadline = TIM1->CNT + 1200;  // 1800 cyc截止
    
    // 窗口内预留300 cyc余量，硬截止点在1500 cyc开始检查
    while (TIM1->CNT < deadline - 300) {
        if (rx_frame_available()) {
            handle_rx_frame();
        }
        if (tx_queue_not_empty()) {
            send_tx_frame();
        }
        // ... 其他操作 ...
    }
    // 到达1500 cyc后，只做最紧急的TX发送
    if (TIM1->CNT < deadline) {
        drain_tx_queue();  // 尽最大努力发
    }
    // 超过1800 cyc → 立即退出，未处理帧丢弃
}
```

## 四、lwIP裸机集成方案

### 4.1 lwIP运行模式

裸机lwIP有两种模式，我们采用**混合模式**：

```
通讯窗口 (ISR)             余量B (主循环)
─────────────────────────────────────────────────
DMA desc检查              lwIP periodic polling
RX数据上传                 TCP ACK/重传
TX desc填充                窗口管理
轻量帧解析                 序列号重组
                            连接管理
                            DEPLOY数据拼接
```

**关键配置**：
```c
// lwipopts.h 核心配置
#define NO_SYS                  1       // 裸机模式
#define LWIP_NETCONN            0       // 禁用API (不依赖RTOS)
#define LWIP_SOCKET             0       // 禁用socket API
#define LWIP_TCP                1       // 启用TCP
#define LWIP_UDP                1       // 启用UDP
#define MEM_SIZE                (8*1024) // 内存堆大小
#define TCP_MSS                 1460    // TCP最大段大小
#define TCP_SND_BUF             (2*TCP_MSS) // 发送缓冲区
#define TCP_WND                 (4*TCP_MSS) // 接收窗口
#define CHECKSUM_GEN_IP         1       // 硬件不支持IP校验和
#define CHECKSUM_GEN_TCP        1       // 硬件不支持TCP校验和
#define CHECKSUM_GEN_UDP        1
```

### 4.2 裸机lwIP的polling调度

```c
void main_loop(void) {
    init_hardware();       // 时钟/GPIO/ETH/RTT/CAN
    init_lwip();           // lwIP初始化
    init_engine();         // 引擎初始化
    HAL_TIM_Base_Start_IT(&htim1);  // 启动100μs ISR
    
    while (1) {
        // ★ 余量B时间 — CPU在此处执行，ISR随时抢占
        // ISR结束继续从这里执行
        
        // lwIP协议处理
        ethernetif_input(NULL);     // 处理RX队列中的所有数据
        tcp_tmr();                  // TCP定时器（保活/重传）
        
        // 其他协议
        canopen_poll();
        // (Modbus, OPC UA等将来)
        
        // DEPLOY数据拼接（非窗口内, 不影响引擎）
        if (deploy_in_progress) {
            assemble_deploy_data();
        }
        
        // IWDG喂狗
        HAL_IWDG_Refresh(&hiwdg1);
    }
}
```

### 4.3 中断分配

| 中断 | 优先级 | 触发 | 处理内容 |
|------|--------|------|---------|
| TIM1_UP | 最高(0) | 100μs | 引擎核心 + 通讯窗口 |
| ETH_IRQ | 中(1) | MAC事件 | 仅清中断标志，数据在通讯窗口处理 |
| DMA2_Stream5 | 中(2) | SHADOW→ODR完成 | 状态更新 |

> **ETH不直接在中断中处理数据**：ETH IRQ只作标志清0，实际的RX/TX数据在下一个通讯窗口中由ISR处理。这避免了中断嵌套破坏100μs时序。

## 五、监控数据流设计

### 5.1 推流模型

采用**UDP推流**而非TCP推流，因为：
- 监控数据允许丢失（丢一帧不致命）
- UDP无重传开销，延迟更低
- TCP的ACK处理浪费窗口时间
- 控制命令（READ/WRITE）仍走TCP，保证可靠性

```
PC端 (IDE)                     H723 (监控推流)
    │                               │
    │  TCP:502 → MONITOR(0x30)      │ 订阅阶段(TCP)
    │        [count][idx0][idx1]... │
    │←────── [stream_id][period]    │
    │                               │
    │  UDP:503 ← 监控数据流          │ 推流阶段(UDP)
    │   每周期: [0x31][sid][seq]     │
    │           [payload:80B]       │
    │                               │
    │  TCP:502 → MONITOR_STOP       │ 取消订阅
```

### 5.2 推流帧格式

```
UDP Payload (每周期推一次):
┌─────────────────────────────────────────────┐
│ [TYPE=0x31:1B] 帧类型标识                     │
│ [STREAM_ID:1B] 流ID (支持多订阅)              │
│ [SEQ:4B]       序列号 (每帧+1, 检测丢包)       │
│ [CYCLES:4B]    当前SAMPLES (周期计数)          │
│ [N:2B]         本次推送的信号数量               │
│ [DT0:4B]       第1个信号值 (float/uint32)     │
│ [DT1:4B]       第2个信号值                     │
│ ...                                            │
│ [DTn-1:4B]     最后1个信号值                   │
│ ─────────────────────────────────────────── │
│ 典型: 20个float + header = 84字节/周期         │
│ 带宽: 84B × 10kHz = 840KB/s = 6.72Mbps       │
└─────────────────────────────────────────────┘
```

### 5.3 订阅管理

```c
#define MAX_MONITOR_SIGNALS 64   // 最多监控64个信号

typedef struct {
    uint16_t wire_offset;        // WIRE_MAP内偏移(字节)
    float    last_value;         // 上次值(用于变化检测)
} MonitorSignal;

typedef struct {
    uint8_t    active;           // 是否激活
    uint32_t   period_cycles;    // 推送周期(默认1=每周期)
    uint32_t   seq_counter;      // 序列号
    uint8_t    signal_count;     // 信号数量
    MonitorSignal signals[MAX_MONITOR_SIGNALS];
} MonitorStream;
```

**变化检测优化**：如果信号值无变化，可减少推送频率（默认每周期推，无变化时每10周期推一次），减少CPU和带宽开销。

### 5.4 带宽推算

| 配置 | 每帧大小 | 每秒帧数 | 带宽 | UDP线速率 |
|------|---------|---------|------|----------|
| 10个float (保守) | 54B | 10000 | 540KB/s | 4.3Mbps |
| 20个float (推荐) | 84B | 10000 | 840KB/s | 6.7Mbps |
| 64个float (最大) | 264B | 10000 | 2.6MB/s | 21Mbps |
| 64个float, 100Hz | 264B | 100 | 26KB/s | 0.2Mbps |

**推荐配置**: 20个float/周期, 10kHz → 840KB/s ≈ 6.7Mbps (占用100Mbps的6.7%)

## 六、烧录（DEPLOY）数据流

### 6.1 流程设计

烧录使用TCP:502可靠传输，数据在通讯窗口外围处理（不影响引擎时序）：

```
PC IDE (dcl_hardware.py)           H723 (固件)
    │                                    │
    │  1. TCP连接 :502                    │
    │───────────────────────────────────→│  建立控制通道
    │                                    │
    │  2. DEPLOY_INIT (准备)              │
    │── [0x10][len:4096][crc32] ────────→│  销毁路由表 (STOP状态)
    │                                    │
    │  3. DEPLOY_DATA (分片, ~2640B)      │
    │── [0x11][seq:2B][data:512B] ──────→│  数据入列到SDRAM缓冲区
    │── [0x11][seq:2B][data:512B] ──────→│  (主循环复制, 不占窗口)
    │── ...                              │
    │── [0x11][seq:2B][data:last] ──────→│
    │                                    │
    │  4. DEPLOY_COMMIT (验证+写入)       │
    │── [0x12][expected_crc32] ────────→│  禁止ISR → 写DTCM → 校验
    │←────── [ACK/ERROR] ───────────────│  启动ISR → 报告结果
    │                                    │
    │  5. 验证                            │
    │── [0x20][addr][len] ─────────────→│  READ验证写回数据
    │←────── [data] ────────────────────│
```

### 6.2 时序分析

| 步骤 | 瓶颈 | 耗时估计 | 对比pyocd |
|------|------|---------|----------|
| DEPLOY_INIT | 网络延迟 | ~100μs | - |
| 分片发送 (2640B / 512B=6片) | TCP速率 + 主循环复制 | ~2ms | - |
| DEPLOY_COMMIT (写DTCM) | 内存复制 + CRC | ~100μs (MCU本地) | - |
| READ验证 | 往返1周期 | ~200μs | - |
| **总耗时** | | **~3ms** | **~2s (pyocd)** |

> 提速: pyocd的SWD 10MHz vs 以太网100Mbps, 三个数量级的差距 (1.25MB/s vs 12.5MB/s)

## 七、错误处理与边界

### 7.1 窗口溢出处理

```
通讯窗口入口 (600 cyc)
    │
    ├─正常: 窗口内完成所有操作 → 退出 → 进入余量A
    │
    └─异常: 窗口内操作超时 → 硬截止 (1800 cyc)
         │
         ├─RX丢帧: 未解析的帧丢弃 → 下一周期重新接收
         │  TCP: 对端重传 (lwIP自动处理)
         │  UDP: 丢就丢了 (监控无伤大雅)
         │
         ├─TX阻塞: 未发送的帧留在队列 → 下一周期发送
         │  风险: 队列满 → 丢弃最老帧 → 更新丢弃计数
         │
         └─统计: comm_window_overflow++
```

### 7.2 TCP连接管理

| 场景 | 处理 |
|------|------|
| PC断开 | 检测到FIN/RST → 清除订阅 → 保留监听socket |
| 重连 | accept新连接 → 恢复监听指令 |
| 心跳超时 | 30s无PING → 断开（释放资源） |
| 多个PC同时连接 | 仅支持1个控制连接, 第二个拒绝 |

### 7.3 ETH初始化异常处理

| 场景 | 处理 |
|------|------|
| PHY未连接 | 检测Link状态 → 不启用TCP, 回退UART通信 |
| 地址冲突 | 检查MAC地址唯一性 (预留配置接口) |
| DMA描述符错误 | MAC复位 → 重新初始化描述符环 |
| TX死锁 | 检测TX desc全满, 超时 → 复位ETH MAC |

## 八、验证方法与标准

### 8.1 验证指标

| 指标 | 目标 | 测量方法 |
|------|------|---------|
| **通讯窗口抖动** | < 50cyc (< 0.4μs) | 在窗口入口/出口反转GPIO, 示波器测量 |
| **命令响应延迟** | < 300μs (3周期) | PC发送→接收ACK时间戳差 |
| **监控推流失帧率** | < 0.1% | PC端序列号连续性检查 |
| **窗口溢出率** | < 0.01% (100周期中最多1次) | `comm_window_overflow` 计数器 |
| **PERIOD_MIN不变** | 等于不开通讯时的值 | 打开/关闭通讯对比PERIOD_MIN |
| **烧录总耗时** | < 10ms | PC端计时 |

### 8.2 验证步骤

```
Step 1: GPIO标记法 (示波器)
  ├─ PE5: ISR入口
  ├─ PE6: 通讯窗口开始
  ├─ PE7: 通讯窗口结束
  ├─ PE8: 余量A/违约标记
  └─ 示波器: 测量PE6高电平宽度 = 通讯窗口执行时间
    
Step 2: 延迟测量
  ├─ PC: t0 = time()
  ├─ PC→H723: WRITE帧
  ├─ PC: 接收ACK, t1 = time()
  └─ 延迟 = (t1 - t0) / 2 (减去单向网络延迟)
    
Step 3: 窗口溢出压力
  ├─ PC: 每秒1000次WRITE
  ├─ 观察 comm_window_overflow 计数器
  └─ 观察 PERIOD_MIN 是否异常
    
Step 4: 回归测试
  ├─ 开通讯: 引擎运行 + 监控推流 + 随机命令
  ├─ 关通讯: 仅引擎运行
  └─ 对比PERIOD_MIN/EXEC_MAX, 确认相等
```

### 8.3 通过标准

```
✅ 通讯窗口执行时间 ≤ 1150 cyc (留50cyc余量)
✅ 命令响应延迟 < 300μs (非高压场景)
✅ 监控失帧率 < 0.1%
✅ 窗口溢出率 = 0 (正常情况下)
✅ PERIOD_MIN 变化 < 10cyc (< 0.1μs, 属于正常抖动)
✅ DEPLOY 2640B 总耗时 < 10ms
```

## 九、内存开销

| 模块 | 内存 | 位置 | 说明 |
|------|------|------|------|
| ETH DMA描述符环 | 1KB | DTCM | 8 TX + 8 RX 描述符 |
| ETH DMA buffer | 3KB | DTCM | 每个描述符~1.5KB buffer |
| lwIP内存堆 | 8KB | DTCM | `mem_malloc` 区域 |
| lwIP TCP控制块 | 2KB | DTCM | TCP_PCB + 监听PCB |
| 监控订阅表 | 1KB | DTCM | 64信号 × 6字节 |
| 监控TX队列 | 2KB | DTCM | 双缓冲(当前帧+下一帧) |
| DEPLOY缓冲区 | 4KB | AXI-SRAM | 暂存烧录分片数据 |
| **合计** | **~21KB** | | DTCM ~17KB + AXI-SRAM 4KB |

> DTCM总容量 = 64KB (0x20000000-0x2000FFFF)
> 通讯子系统占用 ~17KB (26.5%), 剩余47KB供路由表/参数表/状态表使用

## 十、与现有UART协议的兼容过渡

| 阶段 | UART | TCP | 说明 |
|------|------|-----|------|
| P0 (当前) | ✅ 主力 | ❌ 无 | DEBUB/USART2 + RTT |
| P1-1 | ✅ 保留 | ✅ 新增 | 双通道并行, TCP优先 |
| P1-2 | ❌ 移除 | ✅ 主力 | 完全切换到以太网 |

过渡期注意事项：
1. UART和TCP同时监听，PC端自动选择可达通道
2. 同一帧协议(0xC0)确保指令集兼容
3. 监控数据从RTT→UDP迁移，IDE端需兼容两种源

## 附录：典型操作微时序

### READ命令 (最快路径)

```
cyc 600: ISR进入通讯窗口
cyc 650: RX DMA desc → 发现TCP数据 → 提取payload
cyc 700: 0xC0帧解析 → CMD=0x20 (READ), 参数: 地址=0x0300, 长度=20
cyc 750: 从WIRE_MAP[0..19]读取20个float (80字节)
cyc 800: 封装响应帧 [0xC0][ACK][96B payload][CRC]
cyc 850: 填充TX desc → 启动DMA发送
cyc 900: 通讯窗口继续(监控打包等)
cyc 1800: 退出通讯窗口
```

### 窗口溢出场景

```
cyc 600: 通讯窗口开始
cyc 750: RX发现3个TCP段 (命令堆积)
cyc 750-1500: 解析+执行+响应 → 耗时750cyc (远超正常300cyc)
cyc 1500: 通讯窗口超时预警
cyc 1500-1800: 只做TX desc填充 (丢弃剩余未解析帧)
cyc 1800: 硬截止 → 剩余2个未处理帧丢弃
cyc 1801+: 引擎继续路由扫描等 (无影响)
```
