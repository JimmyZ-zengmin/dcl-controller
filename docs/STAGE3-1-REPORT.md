## 1. 做了什么

| 文件 | 内容 |
|---|---|
| `src/transport.h/.c` | **逐字沿用** S3 的 `uart_protocol.h/.c`（52 行状态机 + CRC16-CCITT）。唯一新增是末尾的 **H723 平台段**：`DCL_FW_VERSION_H723 = 0x0200` 与 `DCL_CAP_H723_IMPL` |
| `src/uart.h/.c` | H723 USART1 驱动：PA9=TX / PA10=RX（AF7）、115200 8N1、RXNE 中断 + 环形缓冲、发送轮询等 TC |
| `src/regs.h` | 新增 USART1 寄存器定义（**逐条标注权威来源行号**，见文件注释）+ `RCC_APB2ENR` + `NVIC_IPB` 字节访问 |
| `src/main.c` | 协议分发（`GET_VERSION` / 未知命令 NAK）、上电横幅、回环自检、**`obs_anchor()` 统一锚定**、8 个新编译期开关 |
| `tools/h723_proto.py` | PC 侧 6 用例测试（**含异常路径**：CRC 错、长度超限、分片、连发） |

### 1.1 为什么必须逐字沿用协议

`MIGRATE-H723.md` 阶段 3 的验收标准写的是「**20 套回归全绿，脚本零改动**」。
上位机脚本是既有资产 —— 帧格式 / 命令码 / CRC 多项式 / 长度上限**一个字节都不能动**，
否则 S3 那 20 套套件全部失效。所以 `transport.c` 除 include 名外一字未改：
搬的是**已被 20 套回归 + Modbus LA 外部验证跑过的资产**，重写只会引入新缺陷面。

### 1.2 「宣称 = 实现」在能力位图上的落点（本阶段最有价值的设计）

S3 报 `cap = 0x07FF`（11 项全有）；**H723 只报 2 位**：

```
DCL_CAP_H723_IMPL = DCL_CAP_MULTICYCLE | DCL_CAP_VERINFO   = 0x0021
```

`transport.h` 里**逐条列出未声明的 9 项与原因**（HOTRELOAD 未实现 / PERSISTENT 未实现 /
RESET 命令不存在 / SEQ 未移植 / FORCE 未实现 / COMM 未移植 / HMI 是留位 / AI 未接 …）。

好处是双向的：旧上位机看到 cap 后**优雅降级**，不会去调不存在的命令然后拿到 TIMEOUT
而误判「固件挂了」；而那份「未声明清单」本身就是**上线检查表的雏形** ——
每落地一项删一行、加一位，两处必须同步，否则就是「报了没实现的」或「实现了却不报」。

## 2. 字节级证据（可手工复核）

### 2.1 波特率

| 项 | 推算 | 实测 |
|---|---|---|
| BRR 公式 | `round(PCLK2 × 16 / baud)`，PCLK2 = 100 MHz | — |
| 值 | `100e6×16/115200 = 13888.889` → **13889 = 0x3641** | `g_uart_brr = 0x3641` ✓ |
| 实际波特率 | `100e6/(868 + 1/16) = 115199.1` | 误差 **0.0008%**（容限 2%）|

### 2.2 上电横幅帧（LA 可用它直接对账）

`GET_VERSION` 响应，`fw=0x0200 cap=0x0021`：

```
C1 00 04 00 | 00 02 21 00 | D8 AC
│  │  └─len─┘ └─payload─┘ └crc┘
│  └ sts=ACK
└ SYNC(MCU→PC)
```

CRC16-CCITT 覆盖 `[sts][len][payload]`（**不含 SYNC**），手算 = `0xACD8` → 线上先低后高 = `D8 AC`。
固件计数佐证：`g_uart_tx_bytes = 10 × g_banner_count`（实测 200 = 10 × 20 ✓）。

### 2.3 外设寄存器状态（pyocd 直读）

| 寄存器 | 值 | 判读 |
|---|---|---|
| `USART1_CR1` | `0x0000002D` | UE=1 TE=1 RE=1 RXNEIE=1 OVER8=0 ✓ |
| `USART1_BRR` | `0x00003641` | ✓ |
| `USART1_CR2/CR3` | `0` / `0` | 1 停止位、无流控 ✓ |
| `GPIOA_MODER` | PA9[19:18] = `10` | 复用模式 ✓ |
| `GPIOA_AFRH` | AFSEL9[7:4] = `7` | **AF7 = USART1** ✓ |
| `GPIOA_PUPDR` | PA9[19:18] = `01` | 上拉 ✓ |
| `USART1_IRQHandler` 落位 | `0x00000bec` | **在 ITCM**（每字节都走的热路径）✓ |
| NVIC 优先级 | USART1 = `0x80`，TIM2 = `0` | 外设**永不抢拍** ✓ |

## 3. ★ 本阶段唯一需要诚实标注的项：拍周期抖动

阶段 1/2 的结论是「拍周期极差 **0** 个 CPU 周期」。加协议层后**这个数字变了**，
所以做了隔离实验（每次改动都单独构建 + 单会话读回）：

| 构建 | 拍周期极差 | 采样窗口 |
|---|---|---|
| **A** 仅 USART 初始化，**零流量** | **0 cyc** | 5122 拍 |
| **B** 每 20 ms 一帧（稳态，清统计后 3 s） | **4 cyc = 10 ns** | 3 s 内 150 帧 |
| **B** 每 20 ms 一帧（累计，未清统计） | 26 cyc = 65 ns | 含启动 |
| **交付固件** 仅上电一帧 | 22 cyc = **55 ns** | 31131 拍 |

**可以说的结论**：

1. **UART 外设本身不干扰拍**：A 组零流量下极差为 0，与阶段 1/2 完全一致。
2. **稳态持续流量只带来 10 ns**：B 组在 50 帧/秒的持续流量下，极差 4 cyc。
3. 偏差出现在**上电/启动那一次阻塞发送**的窗口内，之后不再增长
   （B 组清统计后只剩 4 cyc，说明那 26 cyc 里的一次性成分来自启动）。
4. 量级评估：55 ns / 100 μs = **0.055%**，仍远优于 MIGRATE 的验收线
   「拍周期 100 μs ± < 0.1 μs」。

**★ 不能说的（归因纪律）**：上述是**相关性**，机制**未直接测量**。
「启动窗口为什么比稳态窗口影响大」目前只有合理解释（阻塞访问外设寄存器期间，
拍中断的入口延迟会变化），**没有直接证据**。
把它变成机制的唯一办法是做**分段统计**：在 ISR 里记录「入口时主循环是否处于阻塞发送中」
并分类累计 min/max —— 但这本身要给 ISR 加分支（会扰动被测量），
须先把分支做成 ITCM 里的极简形式。**列为未决**。

### 3.1 顺带纠正的一处误判（方法论）

排查过程中两次读到 `GPIOA_IDR.PA9 = 0`（空闲应为高）与 `USART1_ISR.TXE = 0`，
一度怀疑「PA9 被外部拉低」。用**决定性实验**否掉了：在单会话内把 PA9 改成
GPIO 推挽输出，驱动高→低→高，`IDR` 正确跟随（1→0→1）⇒ **引脚完全正常**。

真正的原因是**确定性的采样打在确定性的发送上**：
两次会话都用了 `sleep 400`，而横幅周期恰好 20 ms，`400 ms = 20 × 20 ms` ——
采样点正好落在每帧发送窗口的起点。**「确定性」在这里反过来咬了一口**：
固定延时采样会与固定周期的发送长期同相。
教训：排查时**不要让采样时刻与周期性事件共振**（换一个非整数倍的延时）。

## 4. ★★ 第三次撞到同一个坑 → 做了结构性修复

「只被静态初始化、代码里无人读也无人写的全局，会被 `--gc-sections` 回收、从符号表消失」
这个坑在 H723 上**已经是第三次**：

| # | 变量 | 触发条件 |
|---|---|---|
| ① 阶段 2 | `g_isr_itcm` | 只在声明处初始化 |
| ② 阶段 3.1 | `g_selftest_state` | `UART_SELFTEST=0` 时无人写 |
| ③ 阶段 3.1 | `g_banner_count` | `BOOT_BANNER=0 && 周期=0` 时无人写 |

前两次是"发现一次绕一次"。这次改成**结构性防护**：新增 `obs_anchor()`，
把**全部 64 个观测变量**读一遍（volatile 读 → 链接器看得见引用 → 一个都不会被回收），
在 main 里调用一次。配套纪律写进注释：**新增观测变量必须在这里加一行**。
验证：`nm` 符号数 = 64，与 `OBS` 声明数一致。

## 5. 未完成项（都卡在「需要动线」，不是软件问题）

### 5.1 PC 直连（`tools/h723_proto.py` 的 6 个用例）

**需要接线**：CH340 与板子调试口 H1：

| CH340 | 板子 H1 脚 | 板子信号 |
|---|---|---|
| RXD | **6** | PA9 = USART1_TX |
| TXD | **5** | PA10 = USART1_RX |
| GND | 任一 GND | 共地 |

接好后一条命令即可：`python tools/h723_proto.py`

脚本设计了 6 个**可失败**的用例（只测 happy path 是无效的 —— 一个永远回固定字节的
假固件也能过）：

| 用例 | 判据 |
|---|---|
| T1 版本协商 | ACK + fw=0x0200 + cap=0x0021 |
| T2 未知命令 0x99 | **NAK 且载荷 = `bad cmd`**（证明命令分发真在跑）|
| T3 CRC 故意写错 | **无响应**（证明 CRC 真在查）|
| T4 长度超上限 | **无响应**（证明解析器会丢弃非法长度）|
| T5 逐字节慢发 | 仍正确解析（证明是流式状态机）|
| T6 连发两帧 | **收到两帧**（证明帧间状态机复位正确）|

### 5.2 LA 外部复核 PA9 波形

**现象**：CH1 抓到的信号被 UART 解码器解成**连续 `0x00` + framing 错误**，
每个"字节"长度 82.437 μs（= 9.5 位，位宽正确）但极性/帧结构不对；
事件间隔不规则（0.28 / 0.42 / 0.55 ms，并周期性出现 6.667 ms 静默）。

**已排除的**：
- LA 本体正常 —— 同一次会话下 CH4（PA8）测出 100.0000 μs、众数 95.9%，完全正确
- 固件侧正确 —— §2.3 的寄存器全绿 + PA9 驱动实验 1→0→1
- 引脚无外部短路 —— 驱动实验证否

**因此**：最可能是 **CH1 探针没接在 PA9 上**（接到了别的网络 / GND 附近），
或该跳线接触不良。请核对：**LA CH1 → 板子 H1 第 6 脚**（丝印以板上为准）。

## 6. 复跑方式

```bash
bash build.sh                                   # 交付固件 (上电横幅一次)
bash build.sh -DDCL_BANNER_PERIOD=20            # 每 20ms 一帧 (LA 抓取用)
bash build.sh -DDCL_UART_SELFTEST=1             # 上电回环自检 (需 PA9↔PA10 短接)
bash build.sh -DDCL_BOOT_BANNER=0               # 完全无流量 (拍抖动对照组 A)

python tools/h723_proto.py                      # PC 侧 6 用例 (需 CH340 接线)
```

回环自检 `-DDCL_UART_SELFTEST=1` 的价值：**把 PA9 与 PA10 短接**（H1 的 6 脚与 5 脚相邻），
固件上电自发改一帧 `PC→MCU` 请求，看它能否从 RX 回来并通过 CRC ——
这是**不需要 PC** 就能证明「RX 通路 + CRC + 解析器」三者工作的唯一内部手段。
自检期会**只计数不分发**，否则回环收到的请求会被再次应答，变成回声风暴。
