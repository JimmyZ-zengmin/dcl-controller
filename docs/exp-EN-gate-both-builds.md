### 2.1 原 `TIMEOUT` 的根因：**FLASH 镜像根本没有被写进板子**

`pyocd flash` 的**正常输出**是：
```
programmed 69632 bytes (68 pages), skipped 0 bytes
```
而那次失败时是：
```
programmed 0 bytes (0 sectors), skipped 69632 bytes (68 pages)
```
⇒ **`skipped 69632` = 板上的内容与要写的完全一致 ⇒ 什么都没写。**

★ 这说明**当时板上并不是我那份 FLASH 镜像**。佐证：能力字读回来是 **`0x0001`**，
而 `DCL_CAP_H723_IMPL` 是**无条件的 `0x7DF7`**（`transport.h:257`，
且 FLASH 档 ELF 里确实含 `0x7DF7` —— 直接反汇编确认）。
**`0x0001` 只可能是另一个镜像。**

重新构建 + 重新烧录（这次 `programmed 69632 bytes`）后，能力字 = **`0x7DF7`** ✓。

### 2.2 ★ 教训：`skipped` 不是"成功"的同义词

> **`programmed 0 bytes` + `skipped N bytes` 表示"什么都没做"，而不是"已经是最新的"。**
> 它有两种可能，而**输出分不出来**：
> ① 板上确实已经是最新镜像（无害）
> ② 板上是**别的东西**，而 pyocd 的计算/比较出了问题（有害）
>
> ⇒ **凡是要断言"板上是哪一档"，必须另找一个可读的证据**（如能力字），
>   不能靠 `pyocd flash` 的退出码或 `skipped`。

★ 这与本项目"**'设了就算'必错**"（`MEMORY.md` 第 6 条）是同一族：
这次是"**烧了就算**"。

### 2.3 修复后的 FLASH 档实测

**逐 n 扫描（纯 PID / 纯 DIRECT）**：

| n | DIRECT | PID |
|---|---|---|
| 1 | ACK 247 | ACK 432 |
| 32 | ACK 7904 | ACK 13824 |
| **64** | **ACK 15808** | **NAK `exec budget exceeded`** |
| 128 | **NAK `exec budget exceeded`** | NAK |

★ **`n=1` 即反推出 FLASH 档的**每条成本**：`budget/1 = 247`（DIRECT）/ `432`（PID）
—— 与 `k_op_cost_flash[]` 的 `247 / 432` **逐位相符**。

**N-4 边界精确**：纯 PID 最大可接受 **60 条**（`60×432 = 25920 ≤ 26000`）,
**61 条**（`61×432 = 26352 > 26000`）被拒。**一条之差翻转** ⇒ 门边界精确。

### 2.4 ★★★ O-1：转变项**真的进了门**（决定性实例）

**判据设计**：找一条"**纯可加会放行、含转变项被拒**"的程序 ⇒ 只有转变项能解释。

**构造要点**：交替两个**成本接近**的 op，使"每次交替"**净变贵**：
```
LPF(269) vs MUX(269) ⇒ 差 0 ⇒ 每次交替净增 25 cyc（只花不省）
```

**结果**：

```
n=90, LPF/MUX 逐个交替（转变数 89）
    纯可加视角 = 24210 ≤ 26000    ← **有余量, 会被放行**
    含转变项   = 26435 >  26000    ← 超了
    固件       = **NAK**           ← 门按含转变项的那个数拒了
```

**反证（成对）**：
```
纯 LPF × 90 ⇒ ACK 24210
纯 MUX × 90 ⇒ ACK 24210
```
⇒ **同样条数、同样每条成本、只改排列，判定翻转** ⇒ **只有转变项能解释。**

**⇒ 若没有这一项，这个已超载的程序会被放行。**（E-L 实测该形状的真实代价确实更高。）

★ 顺带：`blocks=2` 的窗口里，固件返回 **20395 = 20370（纯可加）+ 25×1**；
`blocks=60` 返回 **21845 = 20370 + 25×59** —— **逐位吻合**。
