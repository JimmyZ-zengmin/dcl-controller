## 1. ✅ 交付档（`BOOT_SEL=1`）：通过，且转变项在跨类型混合程序上精确

| 配置 | 转变数 | budget | 结果 |

### ★ 逐位核对（手算 = 实测）

```
全 PID        : 128 × (145 + 0)                    = 18560  ✓
全 DIRECT     : 128 × ( 56 + 0)                    =  7168  ✓
混合(半半)     : 64×145 + 64×56 + 1×25              = 12889  ✓
严格交替       : 64×145 + 64×56 + 127×25            = 16039  ✓
```

★ **严格交替那行是新的证据**：E-M 只验过"1 次转变"的配置（`64 PID + 64 DIRECT`）。
本步的**127 次转变**横跨**两个 op 类型逐条交错**，`16039 = 7168 + 127×25 + 4096` ——
**转变项在多类型、多转变的混合程序上也精确成立。**

★ 同时确认**交付档的门确实不具约束力**：4/4 全部 ACK，
与 `engine.h` 绊线断言的预期一致（`128×145 = 18560 ≤ 26000`）。

## 2. ❌ FLASH 档（`BOOT_SEL=0`）：**未能测** —— 但原因已定位到"不是门"

FLASH 档构建成功（`RC=0`，警告 0，hex `aa3ef974…`），烧录后：

| 配置 | 结果 |
|---|---|
| 全 PID ×128 | **NAK: TIMEOUT** |
| 全 DIRECT ×128 | **NAK: TIMEOUT** |
| 混合（半半）| **NAK: TIMEOUT** |
| 严格交替 | **NAK: TIMEOUT** |
| **1 条 DIRECT** | **NAK: TIMEOUT** |
| 3 条 PID | ACK（budget 1296）|
| 4 条 PID | ACK |

### 2.1 ★ 为什么这不是"门"的行为

1. **`TIMEOUT` 不是 `NAK <文案>`** —— 门拒绝时 `engine_prog_budget` 路径会回
   `NAK "exec budget exceeded"`（2026-09-18 的超载实验实测过）。
   这里连应答都没有 ⇒ **帧根本没被受理**，不是被门拒。
2. **`1 条 DIRECT` 也被 TIMEOUT** —— 门对 1 条的成本是 `56 ≤ 26000`，
   **不可能**拒它。
3. **能力字 = `0x0001`**（交付档是 `0x7DF7`）⇒ 这一档的**能力/协议面与交付档不同**，
   `h723_proto.py` 的 T1.4（宣称=实现）在它上面本来就会 FAIL。
   ⇒ 部署路径上的**帧长预算/能力门**与交付档不一致。

⇒ **结论：这是 FLASH 档自身的部署路径问题，与本次的转变项无关。**
（本步**没有**让它变成一条"已验证"的结论。）

### 2.2 已知的相关配置

`tools/h723_build_variants.sh` 里 FLASH 档是
`-DDCL_BOOT_SEL=0 -DDCL_LOOP_RESET=0`，且 `build.sh` 默认带
`-DDCL_MB_BUILD_BUDGET=32`。
⇒ 一个**未验证的候选**：FLASH 档下部署路径的帧预算/大小上限不同 ⇒ 大载荷被丢弃。

**★ 这需要单独一轮排查，本步只把它登记下来。**
