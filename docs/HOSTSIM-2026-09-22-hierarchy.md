> 触发：用户实测反馈 **「你写的程序现在一直在往复跑，但是我电脑的上位机页面停不了，
> 我点击停，短暂停了后电机又开始跑了。你这里层级关系没处理好，并且上位机与板子之间做的不是很系统。
> 然后是你说的上位机 PC 这里反馈的数据不是很好的问题，你说能不能依靠提升反馈频率解决呢」**
>
> 本文记录：三个缺陷的根因 · 系统化改造的落点 · 实测数据 · 以及"提频"问题的实测答案。

## 一、三个缺陷（按"隐蔽度"排序）

### 缺陷 1 —— `do_GET` 被误删：**新代码从未上线**（最隐蔽）

**现象**：`curl /stop` 返回 **index.html**（而不是 JSON）。看起来像"路由前缀没匹配上"。

**真因**：上一次编辑 `bridge.py` 时，`do_GET` 的**方法头被连带吃掉**，
它原来的 body（`/wave` / `/state` / index.html 回退）被并进了 `_ctl`。
⇒ 磁盘上的文件里 **`H` 类没有任何 HTTP 入口符号**。

| 检查手段 | 结果 |
|---|---|
| `py_compile` / `ast.parse` | **PASS**（语法合法、类合法、函数合法） |
| 跑着的旧进程 | **一切正常**（`/state` 照常出数据） |
| 只有新加的路由 | 失效 |

⇒ ★ **"语法过了" ≠ "结构在"**；**"文件改过了" ≠ "改动生效了"**。
缺的是"被框架回调的**名字**"，语法检查**原理上**抓不到。

**修复**：补回 `def do_GET(self): return self._ctl(self.path)`。

### 缺陷 2 —— 层级"自说自话"（用户指正的核心）

实测抓到的原始状态：

```
src_mode = scaffold      ← 上位机**自己记的意图**（"我发过什么"）
mosrc    = program       ← 板子**实读的实际**（sub=14 的 +0）
ap_hz    = 483           ← 电机正在转
```

**两者矛盾，而界面只显示前者** ⇒ 人看到的是**错的**，下一条命令就打在没人听的路上。

⇒ 这是本项目 §〇 第 6 条（**"设了就算"必错**）在上位机侧的实例：
**上位机也必须"目标值 vs 读回值"核对**，不能只记"我发了什么"。

### 缺陷 3 —— HTML `id` 重复：运动源选择**永远失效**

我在控制面板加了 `<select id="src">`，而 HUD 的 `<h3>` 里**早就有一个** `id="src"`。
`document.getElementById` 只返回**第一个** ⇒ `$('src').value` = `undefined`
⇒ 请求变成 `/motion?src=undefined` ⇒ 后端落到 `scaffold` 分支。

⇒ **语法合法、运行不报错、控制台干净**，症状只有一行"层级源=scaffold"。
与缺陷 1 **同一族**：**结构性缺陷不会自己喊**。

## 二、"停了又跑"的完整机制

**不是"停止命令没发"**，而是**打在了一条没人听的路上**：

| 层 | 停机权威 | 旧版 `/motion?on=0` 做了什么 |
|---|---|---|
| 脚手架直控 | `sub=1 0` + `sub=6` | ✓ 发了 |
| **③层程序面** | **`wire[10]=0`** | ✗ **没发** |

而固件的机制决定了"没发"的后果：

```c
/* src/step.c —— step_service_motion() */
if (g_motion_src != STEP_MOT_SRC_PROGRAM) { return; }        // 脚手架模式直接返回
...
if (hz == s_mot_hz && dir == s_mot_dir && en == s_mot_en && lim == s_mot_lim) { return; }
```

- `sub=1 0` ⇒ `step_set_rate(0)` ⇒ **脉冲停了几拍**（这就是用户看到的"短暂停了"）
- 但③层程序**每拍（100 µs）**跑，`wire[10]` 仍是 1 ⇒ 输出 `wire[12]=hzf≠0`
- `step_service_motion` 的"变化"判定 = **请求值 vs 上次请求值** ⇒ 又触发 `step_set_rate(hz)`
- ⇒ **脉冲被拉回来** —— 必然"停了又跑"，且**不自愈**

**修复**（`/stop` 通用急停，两条路一起打）：

```python
CMDQ.append(("wire", 10, 0.0))   # 程序面使能 = 0  ← 关键
CMDQ.append(("pin", 1, 0))       # 脚手架频率 = 0
CMDQ.append(("pin", 6, 0))       # 安全态
```

★ 顺序不能反：**先把两条路的使能关掉，最后才 `sub=6`**。

★ 语义要点：**程序面模式下 `wire[10]` 是唯一停机权威**；
`sub=1`/`sub=6` 只是"外加一记"，会在 100 µs 内被程序面覆盖。
但**停机语义不能依赖当前运动源** —— 所以两条都打。

## 三、系统化改造（`/state` 的层级对账字段）

| 字段 | 来源 | 意义 |
|---|---|---|
| `src_intent` | 上位机（`/motion?src=`） | **我以为**在打哪条路 |
| `src_dev` | 板子（`sub=14 +0`） | **板子实际**在跑哪条路 |
| `src_match` | 二者比较 | ★ **一致性判据**（不一致 ⇒ UI 标红） |
| `wire_ena` | 镜像槽 26 = `wire[10]` | 程序使能**实读**（"停了又跑"能一眼定位） |
| `wire_req` | 镜像槽 28 = `wire[12]` | ③层程序写的请求频率**实读** |
| `stop_t/stop_ok/stop_msg` | `/stop` 后自动读回 | ★ **"发了命令" ≠ "停下了"** |

★ `wire[10]` 的实读值**免费**：镜像槽 16..31 就是 `wire[0..15]`（打底时 `(OFF_WIRE, 16)` 决定），
而 `wire[10]`（镜像槽 26）**没被 `DELTA_MASK_DEF_LO` 屏蔽** ⇒ 无需额外一次 `0x22`。

**前端**：运动源下拉（`id="msrc"`）· 急停按钮标红 · `Esc`/空格快捷键 · 层级面板 · 停机验证行。

**接口纪律修正**（"上位机与板子之间不系统"的根）：
- 原来 `elif kind == "wire" and shm:` ⇒ **`shm` 未知时整条命令被静默丢弃**
- 原来 `d.send(..., expect_len=None)` 的返回值**从不检查** ⇒ 固件 `sub=3` 的 fail-closed NAK
  在上位机侧变成"发了但没反应"（与"驱动器坏了"同形）
⇒ 现在：**不丢弃 · 看应答 · 被拒要能看见**。

## 四、实测（全部带反向判据）

### 4.1 急停闭环

```
停机前:  ap_hz=788   wire[10]=1.00   wire[12]=793.91   mosrc=program
t+0.5s   ap_hz=0     wire[10]=1.00   wire[12]=793.91   停机中…
t+1.0s   ap_hz=0     wire[10]=0.00   wire[12]=0.00     停机中…   ← 使能门关闭
t+2.0s   ap_hz=0     wire[10]=0.00   wire[12]=0.00     stop_ok=True 已停住（连续 1.0 s 无脉冲）
t+7.1s   ap_hz=0     wire[10]=0.00   wire[12]=0.00     stop_ok=True ← ★ 全程不反弹
```

**反向判据**：从急停态重新开跑（`src=program`）⇒ `ap_hz` 0 → 392 → 766 ✓
（否则说明这个"停"把系统弄死了）

### 4.2 层级对账能失败

③ 恢复                intent=program  dev=program   match=True   ap=584

## 五、"提升反馈频率能解决吗" —— 实测答案

### 5.1 记录口径：**已经无损，提频无收益**

`/wave` 用**累积量口径**（点数 ÷ 总跨度）给出权威点数率：

```
点数 n=900   span=29461 拍   平均间隔 32.8 拍
⇒ rate_pt = 305 Hz
```

★ 旧 note 写「`d_tick_med≈100` ⇒ 100 Hz」—— **两处都过期**：
- 实测 `d_tick_med=22` 拍
- ★ 更要命的是**口径错**：用中位反推得 **454 Hz**，而真值 **305 Hz** ⇒ **高估 1.5 倍**
  （分位数不免疫长尾，§〇 第 10 条）

⇒ 位置数据是**全量无损**的（`Δkicks==Δtick` 且 `Δrec+Δskip==Δkicks`，零丢拍已在
`REGRESS-2026-09-22-delta-ring.md` 证过）。**这是"记录"，提频不会让它更全。**

### 5.2 桥接轮询率：**提频有效但已到顶**（实测）

| `--hz` | 实测 `rate` | 说明 |
|---|---|---|
| 25（旧默认） | **9.8 Hz** | 每轮额外 `sleep 40 ms` = **纯浪费** |
| 200（新默认） | **13.8 Hz**（n=16，中位 12.9） | **+41%** |

★ **再往上提 `--hz` 无效** —— 瓶颈已从 `sleep` 变成**协议地板**：

```
每轮 ~5 条命令（sub=26 / tick / sub=14 / 0x38 / HIL 写）
每条 ~10 ms 固定往返开销（读 1 字也要 10 ms，96.5% 是固定开销）
⇒ 单轮地板 ≥ 50 ms ⇒ 上限 ≈ 16~20 Hz
```

⇒ ★★ **这条实验本身就是"提升反馈频率"的上限证据**。
（实测抖动 11~21 Hz 是正常的：`sub=26` 应答长度 = 16+16n 字节，运动越快往返越久。）

### 5.3 根因不在采样率，在「开环推进 + 滞后」

HIL 位置环的实测现象：目标 60 mm 时 `pos` 31.5 → **42.3（过冲）** → 回拉 → **在 38~42 振荡**。

```
③层程序每 100 µs 跑，而 wire[50] 每 ~70 ms 才更新一次
⇒ 在这 70 ms 里，程序看到的位置是**冻结的**，却仍按 kp×|err| 一路推
⇒ 等效"每 70 ms 才闭环一次" ⇒ 带宽上限 ≈ 5 Hz，且**天然过冲**
```

提频只把"冻结窗口"从 100 ms 缩到 70 ms ⇒ **缓和，不根治**。
而且 PC 在环的**相位滞后**（读 → 算 → 写 ≈ 3 个往返）**不会因提频缩短**。

### 5.4 正解（按收益排序，★ 标注验证状态）

| # | 方案 | 收益 | 状态 |
|---|---|---|---|
| ① | **板内多圈位置积分器** ⇒ ③层每拍有新鲜位置，带宽 5 Hz → ~500 Hz | 最大 | ★★ **未验证** |
| ② | **减每轮命令数**（5 → 3）⇒ 地板 50 → 30 ms | 轮询 +60% | 可算，未实测 |
| ③ | **改协议形态**（设备单向主动推 / 批量） | 唯一能破"逐次往返" | 需改固件 |

#### 关于 ① 的**诚实边界**

DCL **有** `ADD` 原语（`ARITH_MODE = dict(ADD=0, SUB=1, MUL=2, ...)`），
**但 `examples/` 里 8 处 `ADD` 全是 `ADD x FROM a BY=b`（两个不同信号），
没有一处"自引用累加器"**。

⇒ **不能假设 `ADD acc FROM acc BY=d` 能累积**：
若引擎求值是"读槽 → 算 → 写槽"，它读到的就是刚写的值 ⇒ **不累积**。

**该做的下一个最小实验**（**不用改固件**，只换 `.dcl`）：

```dcl
ADD     acc     FROM acc BY=one      # 测: 自引用有没有跨拍状态
OUTPUT  o_acc   TO wire[60] FROM acc
ADD     ref     FROM one BY=one      # ★ 对照: 应恒 2（证明"读数"本身没坏）
OUTPUT  o_ref   TO wire[61] FROM ref
```

- `wire[60]` 单调涨 ⇒ **有状态**，① 可行（走 ③ 层，无需 A/B 回归）
- `wire[60]` 恒 1 ⇒ **无状态**，① 只能走板内主循环累加（**要改固件** ⇒ A/B + 12 套回归）

★ 这就是 §〇 第 18 条：**"能做"与"能验收"是两件事** —— 先证明"可算"，再谈性能。
