## 1. H1（P2）哨兵不可失败 —— 同 OA23 族

### 现象
`g_table_ck` 被定义为"填表后 `路由[0].op`"，工具读了但从**未断言**。而
`k_mixed_ops[0] == OP_DIRECT == 0`，profile 0（全 DIRECT）的 `route[0].op` 也是 0：

```
profile 0 → 路由[0].op = 0x00 (DIRECT)
profile 1 → 路由[0].op = 0x00 (MIXED[0] 恰好也是 DIRECT)   ← 同值!
```

⇒ 这个哨兵**在"混合程序"这一组上恒等于 0**，"表换成功了"与"表根本没换"给出同一个读数。
**判据不具备可失败性** —— 与 OA23（`verify_ai` 判据恒真）同一根因。

### 修复
改为**整表 FNV-1a 校验和**，覆盖 `op / flags / src_type / state_offset` 四个字段：

```c
uint32_t engine_table_checksum(const uint8_t *base);   /* engine.c */
```

并在测量工具里**用 Python 复刻 `engine_fill_tables` 的逻辑独立重算期望值**再比对 ——
这不只是"表变了"的证据，而是"表内容正确"的正向证据。

### 复验（`build/stage2_run4_audit_final.txt`）

```
profile 0 → 预测校验和 0x329A37C5, ACTIVE 128 条
profile 1 → 预测校验和 0xE6021511, ACTIVE 128 条
profile 2 → 预测校验和 0x806C1845, ACTIVE 128 条

实测: 校验和 0x329A37C5 ← A/B1/B2/D1/D2/F1/F2/F3
      校验和 0xE6021511 ← C1/C2
      校验和 0x806C1845 ← E
✓ 三种 profile 的校验和互不相同 → 哨兵具备可失败性
```

**11 组全部与独立预测逐位吻合**（不是"看起来合理"，是"必须相等"）。

## 2. H2（P2）缺"引擎真算过"的正向证据

扫描函数返回校验和 `g_eng_ck`，但工具**读了从不比对**。若 `fill_tables` 把
`ROUTE_FLAG_ACTIVE` 写坏，所有路由会被 `continue` 跳过 —— 耗时变小，但**不会报错**。
（这就是 S3 "静默恒假"那一族的形态。）

### 修复
不引入每路由开销（会污染已公布的绝对数值）：
- **H1 的整表校验和覆盖了 `flags` 字段** ⇒ 128 条全 ACTIVE 是**被证明过**的（预测值一致）
- 新增 `g_active_routes` 并逐组断言 `== 128`
- 把 `eng_cyc_min` 必须 > 0、且随 n 线性增长（两点法斜率非 0）作为"真在跑"的补充

## 3. H3（P3）SHM 头部 64 字节无人设防 —— 同 OA20 族

第一版偏移表**从 0x40 开始定义**，`0x00-0x3F` 既无名字也无断言；
而 S3 的 OA20 正是"MB 区一条断言都没有，于是控制块从 32B 扩到 40B 踩进 RX 缓冲无人发现"。

### 修复
按 S3 的**原偏移**把控制块区 / 计时区显式命名（`OFF_CTRL_MAGIC` … `OFF_CTRL_N_SEQ`），
并补上正向 + 反向断言：

```c
_Static_assert(OFF_CTRL_N_SEQ + 8 <= OFF_SENSOR_MAP, "SHM: 控制块区越界 (0x00-0x3F)");
_Static_assert(OFF_CTRL_MAGIC + 4 <= OFF_CTRL_N_SEQ + 8, "SHM: 控制块字段溢出 0x40");
_Static_assert(OFF_TIMING_LAST_EXEC + 4 <= OFF_CTRL_GPIO_MASK + 4, "SHM: 计时区与 GPIO_MASK 重叠");
```
现在断言链从 `0x00` **无缝覆盖到 `SHM_SIZE`**。

## 4. H4（P3）SHM 与栈之间没有堤

`.dtcm_shm` 之上就是栈可下探的区域，此前**没有任何保护**：栈一旦溢出，
会静默覆写路由表 —— 而且症状会伪装成"控制逻辑不对"，排查成本极高。

### 修复
在 `_shm_end` 之上铺 128 字节魔术字（选在 `_shm_end` 而不是 `_estack` 附近，
因为那是"表被踩"的**第一现场**），主循环每 100μs 巡检一次：

```c
#define SHM_GUARD_MAGIC 0xC0DEAD42u
void shm_guard_paint(void);
int  shm_guard_ok(void);
```
实测 `g_guard_ok = 1`（11 组全绿）。

## 5. H5（P3）未实现源被 `default` 静默吞掉 —— 同 M1 族

`read_source()` 里 `SRC_HMI` 落进 `default: return 0.0f`。
后果：一个引用了未实现源的路由，表现与"这条路由恒定输出 0"**完全一样**（S3 的 M1：
AND/OR 第二输入落在 `wire[0]` → 静默恒假）。

### 修复
把 `SRC_HMI` **显式列出**并标注"未实现 + deploy 必须拦截"：

```c
case SRC_HMI:    return 0.0f;   /* ★ 阶段 4 落地前, deploy 校验必须在源头拒绝 */
default:         return 0.0f;
```
**未决**：deploy 侧拦截属阶段 3/4 工作，已登记。

## 6. H6（P2）冷启动清理出现两个入口 —— 同 OA16/17/19/21 族

`cold_start_reset()` 与 `engine_fill_tables()` 各自 `memset(SHM_SIZE)`。
现在两者等价所以无害，但这正是 S3 那组"清理清单补丁式增长"的起点形态：
一旦 `fill_tables` 的行为与"清零"分离（比如将来只重填部分区），
"新增域登记到哪"就有了两个答案。

### 修复
`engine_fill_tables()` 改为**先调 `cold_start_reset()`**，并写明约定：
base 必须是 `g_shm`；若要第二块表区，必须回 `cold_start_reset` 登记，不允许绕过。

## 7. H7（口径）"硬拍与负载完全解耦"是过度宣称 ★

旧报告与 README 写过：

> 拍周期 11 组全部极差 0 ⇒ **硬拍与负载完全解耦**

审计途中该结论被**自己推翻**：本轮加了 H1–H6 的代码后，FLASH·混合程序组
从 38923 cyc 涨到 **41166 cyc（102.9% 拍）**，于是：

```
C1 FLASH 全表128·19原语轮转·IC关
   eng_min = 41166 cyc  (最坏占拍 104.64%)   ← ★超载
   拍周期: min 41334 / max 41910  极差 576 cyc = 1440 ns   ← 不再是 40000 整!
```

**正确口径**：
> 拍周期与引擎负载解耦，**前提是 ISR 在拍内跑完**。
> 一旦超载，拍周期改由 ISR 时长决定，**而且不再确定**（实测极差 576 cyc ≈ 1.4 µs）。

这不是"报告写错了一个数字"，而是**判据的方向错了**：
"极差 0"是"没超载"的**结果**，不是"解耦"的**证明**。旧版把它当成了证明。

### 修复
- 工具新增**超载判定**并显式区分两句话；②表里对 >100% 的行打 `★超载`
- 报告与 README 的口径同步反转

> 附注：这也解释了为什么必须**按组复位拍周期统计** —— 全局累计会把
> 某组超载的 41334 混进所有组的 `min`，让"解耦"看起来更假。

## 8. H8（P3）"flash 落位敏感"—— 证据加强，机制仍未直接测量

旧报告的措辞是"同一 flash 函数换个地址成本变 5%"，那是**相关性**（对照组是另一个构建）。
审计期间又积累了两个数据点，摆幅比原来更大：

| 构建 | B1 FLASH·全DIRECT | C1 FLASH·混合 | 说明 |
|---|---|---|---|
| A 阶段 2 初次交付 | 26229 (65.8%) | 38923 (97.3%) | — |
| C 审计修正（加 checksum/guard）| 27818 (69.8%) | **41166 (102.9%)** | ★超载 |
| D 审计修正 + BOOT_* 旋钮（**交付固件**）| 26229 (65.8%) | 38813 (97.0%) | — |
| （对照）ITCM·全DIRECT | — | 7225 / 7225 / 7225 | 三次构建**逐位不变** |

**同一个引擎、同一份扫描机器码，FLASH 版成本在 38813–41166（±3%）之间摆动，
而拍长恰好是 40000 cyc —— 落在摆幅正中间。** 也就是说：
**"这个程序能不能跑得下"由构建的代码布局决定，而不是由程序本身决定。**
ITCM 版三次构建一字不差。

**但机制仍未直接测量**（诚实标注）。可能的机制：无 I-cache 时每次取指都要发 flash 请求，
循环体跨越 128/256 位取指行的方式随落位变化。**验证方案（下一步，可复跑）**：

```
加 -DSCAN_FLASH_PAD=N 编译期旋钮 → 在 engine_scan_flash 之前插入 N 字节
→ 扫描 N ∈ {0,16,32,...} 测 C1 成本 → 得到"落位 vs 成本"曲线
→ 若呈周期性台阶 = 取指行边界机制成立；若随机 = 另有他因
```
在测出这条曲线之前，本报告**只写"成本取决于落位"，不写"因为取指行边界"**。

## 9. 由审计派生的工位/工具坑（3 条，都很贵）

### 9.1 ★ `connect_mode=under-reset` 不带 `-c reset` ⇒ 核心被按在复位态

症状极具误导性：读回的是**陈旧 SRAM**，看起来像"固件行为异常"：
- `g_tick_count` 在两个会话间**完全不变**（"引擎停了！"）
- `g_per_cyc_max` 出现 `0xFD7A1A92` 这种垃圾值（"抖动 10 秒？！"）
- `g_eng_cyc_min` 读 0

**判据**：先读 `DHCSR(0xE000EDF0)`，`bit1 C_HALT`/`bit17 S_HALT`。
**正解**：会话里先 `-c reset -c "sleep 300"` 再读写（本项目所有测量工具都是这个模式，
所以工具一直是对的，是我临时手写的会话踩了坑）。

### 9.2 `la_tick_freq.py` 默认**会复位板子** ⇒ 测非默认配置必须 `--no-reset`

该脚本的 `[1] 复位板子 → 固件自由运行` 是默认行为。我用它测"运行期写入的配置"时，
每次复位都把配置清掉 → 三次抓取全部返回 100.0000 µs（骨架态），
一度被误读为"LA 与 DWT 矛盾"。
**正解**：`--no-reset`（该参数本来就有）。**教训：外部仪器测试前先确认脚本没有副作用。**

### 9.3 pyocd 会话结束后核心被 HALT，运行期配置不跨会话

⇒ "用外部仪器测某个非默认配置"这件事，靠调试器写变量**不可靠**。
**正解**：加**编译期启动默认**（`-DBOOT_PROFILE/BOOT_GATE/BOOT_SEL`，已加进 CMake + `build.sh` 透传），
让固件上电即处于被测配置 —— 调试器完全不参与。

> 顺带修好了 `build.sh` 不能透传 cmake 参数的问题（现在 `bash build.sh -DXXX=Y` 可用）。
