# 双核缓存一致性问题

> 状态：**已修复** — 根因非 MPU 配置缺失，而是 ROM 缓存 API 的不当使用
>
> 修复日期：2026-06-17

---

## 一、问题现象

核心1 ISR 和核心0 监测代码读取共享内存时，看到未初始化的随机值（天文数字）。但核心1 启动前`core1_init`里直接读是正确的：

```
[CORE1] DEBUG: ROUTE[2].param_idx=2                    ← 正确
[CORE1] DEBUG: PARAM[2]=(2.0,0.1,0.1,28.0)           ← 正确

ISR 启动后：
  WIRE[0]=  0.000    (应为 25~26)                     ← 垃圾
  WIRE[2]=52931769592671370000.000                    ← 垃圾
  PID→-0, Kp=-218.7                                   ← 垃圾
```

---

## 二、根因

**ESP32-S3 双核各自拥有独立的 L1 数据缓存，没有硬件缓存一致性协议。**

```
核心0 (PRO_CPU)              核心1 (APP_CPU)
┌──────────────┐            ┌──────────────┐
│ D-Cache      │            │ D-Cache      │
│ SENSOR[0]=26 │            │ PARAM[2]=2.0 │
│ WIRE[0..] =0 │            │ WIRE[0..] =26│
└──────┬───────┘            └──────┬───────┘
       │                           │
       └─────────┬─────────────────┘
                 │
          ┌──────┴──────┐
          │  SRAM (RAM) │  ← 物理内存，两边缓存不一致
          └─────────────┘
```

### 具体数据流故障

1. **SENSOR_MAP[0]**: 核心0 DHT22任务写入 → 仅存核心0缓存 → 核心1 ISR从自己的缓存读取 → 读到0（旧值）

2. **WIRE_MAP**: 核心1 ISR写入 → 仅存核心1缓存 → 核心0监测从自己的缓存读取 → 读到0（旧值）

3. **PARAM_TABLE**: 核心1 `build_test_routes`写入 → 仅存核心1缓存 → 核心0监测从自己的缓存读取 → 读到随机值

## 三、已尝试的方案（均失败）

### 3.1 `esp_cache_msync()` (ESP-IDF v6.x API)

```c
#include "esp_cache.h"
esp_cache_msync((void*)SHARED_MEM_BASE, SHARED_MEM_SIZE,
    ESP_CACHE_MSYNC_FLAG_DIR_C2M | ESP_CACHE_MSYNC_FLAG_TYPE_DATA);
```
- 需要添加 `esp_mm` 组件依赖
- 编译通过，但写入/无效化操作未生效

### 3.2 `Cache_WriteBack_Addr()` / `Cache_Invalidate_Addr()` (ROM API)

```c
#include "rom/cache.h"
Cache_WriteBack_Addr(uint32_t addr, uint32_t size);
Cache_Invalidate_Addr(uint32_t addr, uint32_t size);
```
- 在核心0写SENSOR_MAP后调用 `WriteBack` → 核心1仍读不到
- 在核心1ISR前调用 `Invalidate` → 核心1仍读到旧值
- 怀疑: 这些ROM函数在ESP32-S3上可能不完全有效

### 3.3 `Cache_Invalidate_DCache_All()` (全缓存清空)

```c
Cache_Invalidate_DCache_All();
```
- 导致核心1崩溃 (`LoadProhibited`)
- 原因: 把栈和程序的缓存也清了，后续printf调用读到被破坏的数据

### 3.4 路由表完全在核心1侧构建（同核读写）

- `build_test_routes()` 在核心1 `core1_init` 中调用
- ISR在同一核心读取 → 理论上应该有效
- 但 SENSOR_MAP 仍由核心0写入，核心1看不到

## 四、正确方案：MPU 禁用共享内存区域缓存

**原理**: 配置 ESP32-S3 的 MPU (Memory Protection Unit) 或 Cache Controller，使 `0x3FCA0000 ~ 0x3FCB0000` (64KB) 对数据访问不可缓存。两个核心都直接读写物理 SRAM。

### 4.1 相关代码位置

| 文件 | 关键行 | 说明 |
|------|--------|------|
| `firmware/components/core0/core1_isr.c` | 第 291~430 行 | `build_test_routes()` 写路由表 |
| `firmware/components/core0/core1_isr.c` | 第 448~452 行 | `core1_init()` 中的缓存操作 |
| `firmware/main/main.c` | 第 31~34 行 | DHT22 任务写 SENSOR_MAP |
| `firmware/main/main.c` | 第 184~186 行 | 监测循环读共享内存 |
| `firmware/components/core0/shared_mem.h` | 全部 | 共享内存结构定义 |

### 4.2 ESP32-S3 MPU/缓存配置方向

需要在**启动早期**（`app_main`之前或`app_main`最开头）配置：

```c
// 方向1: 使用 cache_hal (ESP-IDF v6.x)
#include "hal/cache_hal.h"
#include "hal/cache_ll.h"
// 禁用 0x3FCA0000~0x3FCB0000 的数据缓存

// 方向2: 使用 MMU
#include "esp_mmu.h"
// 将此区域映射为 non-cacheable

// 方向3: 直接操作 Xtensa CACHEATTR 寄存器
// 将对应地址范围的 cache attribute 设为 bypass
```

### 4.3 临时折衷 → 已由 §7 彻底解决

原 `SENSOR_MAP[0] = 25.0f` 硬编码默认值保留（作为 DHT22 启动前的初始值），但根本原因已由 §7 的 heap 分配修复解决。`SENSOR_MAP[0]` 现在由 DHT22 任务正常更新，ISR 能正确读取。

## 七、修复记录 (2026-06-17)

### 7.1 根因修正

经过深挖 ESP-IDF v6.0.1 源码 (`cache_ll.h`, `cache_hal.c`, `soc.h`, `ext_mem_defs.h`, `esp_cache_msync.c`)，发现**之前的"缓存一致性"诊断有误**：

**ESP32-S3 内部 DRAM (0x3FC88000~0x3FD00000) 不由 D-Cache 缓存。** D-Cache 只处理外部 PSRAM 地址 (0x3C000000~0x3E000000)。共享内存基址 `0x3FCA0000` 落在内部 DRAM 范围，本身就是 non-cacheable。

这意味着：
- `Cache_WriteBack_Addr(0x3FCA0000)` → cache_hal 判定地址不可缓存 → **无操作**
- `Cache_Invalidate_Addr(0x3FCA0000)` → cache_hal 判定地址不可缓存 → **无操作**
- `esp_cache_msync(0x3FCA0000)` → 返回 `ESP_ERR_NOT_SUPPORTED` → **无操作**

配置 MPU 禁用缓存是**无效的**——因为该区域本来就不可缓存。

### 7.2 真正的 Bug

1. **ROM `Cache_WriteBack_Addr` 有已知 bug**（`CONFIG_ESP_ROM_HAS_CACHE_WRITEBACK_BUG=y`），ESP-IDF 打了补丁但仅修复了对齐/冻结问题

2. **`main.c:176` 的 `Cache_Invalidate_Addr(SHARED_MEM_BASE, 64KB)` 是最危险的**——如果 Core 0 对共享内存有脏缓存行（理论上不该有，但 PSRAM 混用场景下可能发生），Invalidate 会**直接丢弃脏数据不做 WriteBack**，导致 param_tuner_task 写入的 PARAM_TABLE 新值被丢弃

3. **缺少跨核写屏障**——即使内部 DRAM non-cacheable，Xtensa LX7 仍有写缓冲 (store buffer)。Core 0 写入 PARAM_TABLE/SENSOR_MAP 后不做 `MEMW`，核心1 ISR 可能在几个周期内看不到新值

### 7.3 实际修改

#### `core1_isr.c`
- 删除 `#include "rom/cache.h"`
- 删除 `Cache_WriteBack_Addr()` / `Cache_Invalidate_Addr()` 调用
- `build_test_routes()` 后添加 `__asm__ volatile("memw")` 排空写缓冲
- ISR 末尾（心跳++后）添加 `MEMW` 确保 WIRE_MAP/ACTUATOR 对核心0可见

#### `main.c`
- 删除 `#include "rom/cache.h"`
- DHT22 任务：`SENSOR_MAP[0] = temp` 后添加 `MEMW`
- param_tuner_task：`PARAM_TABLE[2].value_d/a` 写入后添加 `MEMW`
- hot_switch_task：`ROUTE_STAGING`/`PARAM_STAGING` 写入后、`reload_flag=1` 前添加 `MEMW`
- 监控循环：删除每 3 秒的 `Cache_Invalidate_Addr(SHARED_MEM_BASE, 64KB)` 调用（这行最危险）

### 7.4 验证方法

无需示波器，烧录后观察串口：

1. `WIRE[0]` 应显示 DHT22 真实温度（如 25.3），不是 0.000
2. `WIRE[2]` PID 输出应在合理范围，不是天文数字
3. PID 的 Kp 显示应匹配 PARAM_TABLE[2].value_a 最新值
4. param_tuner_task 每 15s 切换设定值，WIRE[2] 应立即响应
5. CCOUNT 抖动应保持 <1000ns，PASS
