## 3. ★★★ 但第一版判据我**写错了周期** —— 值得单独记

**第一版**把 div2 的预测写成 **1.28 = 128/100**，实测 **2.0000** ⇒ 报 FAIL (+56%)。

**错在哪**：我按"周期 100 拍"算，而**扫描器选相位用的是 `tick % 64`**
⇒ **一个完整周期是 64 拍，不是 100 拍**。

实测桶表（修复后，div2 n=128）：
```
cnt2[0..31]  = 2, 2, 2, …   (32 个)
cnt2[32..63] = 2, 2, 2, …   (32 个)
cnt2[64..99] = 0 …          (36 个)
sum = 128 ;  每个相位恰好 **2** 条
路由表相位直方图: 64 个取值, 每个 **恰好 2** 条
```

⇒ 每拍 `nrun = cnt2[tick % 64] = 2`（**每一拍都是 2，没有空拍**）
⇒ 吞吐 = **128 条 / 64 拍 = 2.00** ✓

★ **正确的一般式**：
```
吞吐 = (总条数) / (相位数)        ← 相位数 = 扫描器实际用的那个模数
     div0: n/1   ·  div1: n/10  ·  div2: n/64
对"条数 = 相位数 × k"的整齐配置, 吞吐直接 = k
```

★ **教训**：
1. **"周期"这个量的载体是"扫描器实际用的模数"，不是"标称周期拍数"。**
   修缺陷时我把 `% 100` 改成 `% 64`，**周期随之从 100 拍变成 64 拍** ——
   而我在写判据时仍按 100 算。**改了行为却没改判据的参照值**（§5.41 同族，本次是第三次）。
2. 实测与预测**都是精确整数**（128.0000 / 12.8001 / 2.0000 / 1.0000）这一点本身
   就是强证据：**这类量没有噪声**，偏差 0.00% 是真命中，不是我放宽了判据。

## 4. 这一条同时定死了 §7.4 的"残留代价"该怎么表述

`docs/exp-EH-bucket-contradiction.md` §7.4 写的是：
> 相位数 64 与周期 100 拍不整除 ⇒ 每周期执行 1 或 2 次（抖动 2×）…… **（这个表述需要修正）**

**由本步实测**：扫描器用 `% 64`，而 64 个相位**每个都有 2 条** ⇒
**每一拍都跑 2 条，没有空拍、没有抖动。**

⇒ 真正的残留代价不是"抖动"，而是：
- **`div2` 的实际周期是 64 拍（6.4 ms），不是标称的 100 拍（10 ms）**
  —— 因为扫描器用 `% 64`
- 于是 `DT_SLOW = 0.01f`（10 ms）**与实际的扫描周期 6.4 ms 不一致**
  ⇒ 跑在 div2 上的 `TIMER` / `LPF` / `RATE` / `PID` 用的 `dt` **偏大 56%**

★★ **这才是那个缺陷的真正残留**：修复止住了"丢路由"，
但**"标称周期 10 ms"与"实际扫描周期 6.4 ms"仍然不一致**。
⇒ 彻底修需要把 phase 字段扩到 7 位（100 个相位可寻址），
使**扫描周期真正等于 100 拍**。这条已登记（§7.5），**现在它的优先级上升了** ——
因为它不只是"抖动"，而是**`dt` 语义错误 → 控制律参数全部偏 56%**。
