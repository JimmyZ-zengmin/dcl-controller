# 阶段 2 报告 — ITCM / DTCM 落位 + 路由扫描移植 + 同镜像 A/B 实验

日期: 2026-09-10 · 项目: 9.10 H723newest
平台: STM32H723ZGT6 @ **400MHz**（HSE 25MHz → PLL M=5/N=80/P=1 → HCLK 200 / TIMxCLK 200）
目标: 把 esp32-core0 的**路由扫描**移植过来，并把阶段 1 提出的假设
（"flash 常驻热代码的 WCET 不可预算 ⇒ 必须搬 ITCM"）变成可复跑的实验。

---

## 0. 一句话结论

> **同一个引擎、同一份机器码，放在 FLASH 里跑是 203.6 cyc/路由；放在 ITCM 里跑是 56.0 cyc/路由。
> 128 条全表扫：FLASH 26229 cyc（占拍 65.8%），ITCM 7225 cyc（占拍 18.3%）。
> 换成 19 原语混合程序，FLASH 版冲到 98.9% 拍占用（几乎锁死），ITCM 版只用 29.0%。**

而且这次不是"换个固件再测一次"——是**同一个镜像、同一次上电、同一个调用点**，
两份实现**逐字节相同的机器码**（已用 `build/dcl_h723.bin` 与在线 SWD 读回双向验证）。

## 2. ★ 实验设计：为什么这次的 A/B 是可信的

阶段 1 的对比（86/95/98 cyc）是**跨构建**的 —— 换了固件就换了环境，
严格说不能把差异全归给"取指路径"。阶段 2 把这个问题彻底解决：

```
engine.c 里一个宏 DEFINE_ENGINE_SCAN(FN, ATTR) 实例化两次:

    engine_scan_flash(uint8_t *base, uint32_t n)   → .text      (0x08000660)
    engine_scan_itcm (uint8_t *base, uint32_t n)   → .itcm_text (0x00000248)
```

两条独立证据证明这份机器码是**同一份**：

| 证据 | 方法 | 结果 |
|---|---|---|
| 静态 | `objcopy -O binary` 后切片逐字节 diff | **2136 B 全同** |
| 在线 | SWD 同时读两个函数首 64 字 | **64/64 相同** |

再配合**运行期选择器**（`g_engine_sel` / `g_engine_gate` / `g_n_routes` /
`g_table_profile`），整套 11 组配置在**一条 pyocd 命令链、一次上电**里跑完：

| 排除掉的混淆因素 | 手段 |
|---|---|
| 温度 / 电压 / 上电状态 | 单会话，同一次上电 |
| 编译器差异 | 同一个宏、同一个 `.o`、同一份机器码 |
| 调用点差异 | 同一行 `sel ? scan_itcm : scan_flash`，同一个 `bl` 位置 |
| 时钟差异 | 全程 400MHz，末尾 DWT 标定复核 |
| "gcc 把两份折叠成一份" | CMake `-fno-ipa-icf`（否则 A/B 作废）+ nm 尺寸核验 |

> **必须配 `-fno-ipa-icf`**：GCC 的 IPA-ICF 会把内容相同的函数折叠成一个，
> 两份实例只剩一份 —— 实验会"看起来正常但结论无效"。

## 4. ★ 关键实验一：I-cache 对照（决定性）

H7 复位后 **L1 I-cache 默认关闭** —— 也就是说 B1/C1/D1 那几组测的是
"flash 且**没有** cache"的最坏情况。为了不被质疑"你只是没开 cache"，
实验里加了一个单向开关（`g_icache_req` → 主循环执行
`ICIALLU → DSB → ISB → CCR.IC=1`，ARM ARM 标准序列），并**在同一会话内**复测：

```
FLASH: IC关 26229 cyc → IC开 8164 cyc   (加速 3.2 倍)
ITCM : IC关  7225 cyc → IC开 7225 cyc   (变化 0.0% —— 逐位相同)
```

**这两行就是整个阶段 2 的核心证据。**

- FLASH 版的成本**取决于一个引擎不控制的全局状态变量**（cache 内容）。
- ITCM 版的成本**与 cache 状态无关**（7225 = 7225，一位不差）。

而且即使把 cache 打开，FLASH 版仍然要 **62.69 cyc/条**，**仍高于 ITCM 的 56.02**。
（差额来自：① 长跳转 veneer ② flash 取指仍要经 AXI，而 HCLK = CPU/2。）

### 4.1 诚实的边界：这次没测到"cache 抖动"

所有组的 `eng_min == eng_max`（除 E 组外极差 ≤ 5 cyc），**包括 I-cache 打开后的 FLASH 版**。
原因很朴素：本微基准是一个 2136 B 的紧循环，工作集完整装得进 16 KB L1 I-cache，
没有别的东西来驱逐它 —— 所以它这一轮的时序是稳的。

**但这正是风险所在**：真实固件里 cache 由通信域、顺序域、HMI、热重载、printf 共同瓜分，
"这一轮稳"不能推广成"任何程序任何时刻都稳"。ITCM 的价值不是"更快"，
而是**把这条依赖整个移除**——这件事上表已经直接证明（7225 与 cache 状态无关）。

## 5. ★ 关键实验二：同一函数换个 flash 地址，成本变 5%

为了把"外壳放哪里"也干净地测一次，用 `ISR_ITCM` 编译期开关构建了第二个镜像
（**唯一差异 = `TIM2_IRQHandler` 所在段**，扫描体两份实例照旧都在）：

| 配置 | 外壳在 FLASH（`ISR_ITCM=0`）| 外壳在 ITCM（`ISR_ITCM=1`）| 差 |
|---|---|---|---|
| A 骨架 | **160 cyc** | **44 cyc** | **3.6×** |
| B1 FLASH 扫描 | 24986 cyc | 26229 cyc | +1243 (+5.0%) |
| B2 ITCM 扫描 | 7344 cyc | 7225 cyc | −119 (−1.6%) |
| F1 FLASH 扫描 · IC开 | 8190 cyc | 8164 cyc | ≈ 持平 |
| F2 ITCM 扫描 · IC开 | 7296 cyc | 7225 cyc | ≈ 持平 |

两类信息：

1. **外壳本身**：44 vs 160 cyc —— 中断外壳（入口 + 清标志 + 统计 + 出口）在 ITCM
   里便宜 3.6 倍。这是最纯粹的"取指路径"效应。

2. **`engine_scan_flash` 的地址只挪了 0x250 字节（0x08000660 → 0x080008B0），
   同一份机器码的成本就从 26229 变成 24986（±5%）。**
   —— 这正面证实了阶段 1 的观察："flash 常驻代码的 WCET 被对齐/取指主导"。
   而且它说明**用 flash 地址算预算是不可能的**：换一次编译、加一行无关代码，
   预算就要重算。

（B2 的 119 cyc 差异来自调用侧：`ISR_ITCM=0` 时调用点也在 flash，
要经 flash 里的 veneer 再跳进 ITCM，这一小段被包在测量区间内 —— 是调用方的账，不是 ITCM 体的。）

这是"硬拍与负载解耦"的直接证据。`g_per_cyc_*` 现在**按组复位**后再统计：

| 配置 | 周期 min | 周期 max | 极差 |
|---|---|---|---|
| A 骨架 | 40000 | 40000 | **0** |
| B1 FLASH 128 DIRECT（65.8% 占用）| 40000 | 40000 | **0** |
| C1 FLASH 128 混合（**98.86% 占用**）| 40000 | 40000 | **0** |

**11 组全部 0 极差**（< 2.5 ns）。引擎占满 98.86% 的拍，下一个拍的入口时刻一位不差。

> 之前一次运行看到的 11~23 cyc 极差，来自"清统计时序 + I-cache 切换那一拍"的

## 8. 与 esp32-core0 对照

| | ESP32-S3 | STM32H723 · ITCM |
|---|---|---|
| CPU | LX7 @240MHz | M7 @400MHz |
| 空拍骨架 | 49 cyc = **204 ns** | 44 cyc = **110 ns** |
| 单条路由（DIRECT）| 234 cyc = **975 ns** | **56.0 cyc = 140 ns** |
| 128 条全表扫 | — | 7225 cyc = **18.1 μs**（占拍 18.3%）|
| 周期计数分辨率 | 4.17 ns | **2.5 ns** |

单条路由便宜 **7 倍**（975 ns → 140 ns）。这不是"新引擎"，是同一套语义换了个平台。

### 8.1 成本谱（ITCM）

| 程序形态 | cyc/条 | 128 条占拍 |
|---|---|---|
| 骨架（无路由）| — | 0.11% |
| 全 DIRECT（最轻）| 56.0 | 18.3% |
| 19 原语轮转（混合，真实程序）| 89.2 | 29.0% |
| 全 PID（最重）| 119.3 | 44.8% |

⇒ **ITCM 下 128 条满表的最坏形态（全 PID）也只吃掉 44.8% 拍**，
留 55% 给通信域/顺序域/热重载 —— 这正是 S3 的 `EXEC_DEPLOY_BUDGET` 想要的余量。
对照 FLASH：连"全 DIRECT"都要 65.8%，混合程序 98.9%（等于锁死）。

### 8.2 算法自身的抖动（ITCM 也没法消）

E 组（全 PID）`eng_min=15275 / eng_max=17831`，极差 **2556 cyc**。
这是 **PID 条件积分（anti-windup）分支的数据依赖**造成的，不是取指问题 ——
ITCM 消除了**取指路径**的不确定性，消不掉**算法本身**的不确定性。
预算模型里 `GATE_COST` / `OP_COST` 这类保守加权仍然必要。

## 9. 途中踩的 5 个坑（全部已记档）

### 9.1 ★ 指针相等的自检会被编译器**折叠**

第一版 `shm_layout_ok()` 写的是：

```c
if ((uintptr_t)g_shm != (uintptr_t)_shm_start) return 0;   /* ← 恒真 */
```

结果整函数被编译成 `movs r0,#0; bx lr` —— **恒返 0**。
原因：C 标准保证"不同对象地址不同"，GCC 因此能在**不知道地址数值**的情况下
断定两个不同符号的地址不相等（`.tmp/t.c` 最小复现，GCC 7.3.1 `-O2`）。

**修法**：把两个地址都过一遍 `volatile` 全局，编译器就"证"不出来了；
并且把权威比对交给外部工具（Python 读回 `g_shm_addr` / `g_shm_start_addr` 与 ELF 符号三方对齐）。
教训与项目纪律一致：**自检如果不具备"可失败性"，它就是装饰**（同 OA23 的哨兵教训）。

### 9.2 `--gc-sections` 也会吃掉"只被静态初始化"的全局

`g_isr_itcm = ISR_ITCM;` 只在声明处赋值、固件内无人读写 → 所在段被整段回收，
从符号表消失，外部读不到。
`__attribute__((used))` **只管 GCC 层，管不住链接器** —— 必须在代码里真读或真写它一次。
（阶段 1 的 `g_isr_mode` 同款，这次又踩了一次，已写进 `main.c` 顶部注释。）

### 9.3 `pyocd read32 ADDR LEN` 的 LEN 是**字节**不是字

- `read32 0x0` → 1 字
- `read32 0x0 8` → 仍然是 1 行（4 字，按 16 字节行取整）
- `read32 0x0 256` → 64 字（16 行）

教训：凡是"带长度的读"都要先用一个已知值反测定标，别照名字猜语义。

### 9.4 pyocd 输出带 **ASCII 转储列**，正则必须把它剥掉

行格式：`20000008:  0000002b                    |...+|`

阶段 1 的脚本用无锚点 `re.match` 侥幸没事；这里加了 `$` 行尾锚点后
**一行都匹配不到**（解析出 0 个值）。现在统一先按 `|` 切掉 ASCII 列。

### 9.5 清统计的**时序**会污染 `isr_min`

第一版命令序列是"先清统计，再写 gate"：
两条 SWD 写之间隔着若干拍（100μs/拍），这些"gate 还是旧值"的拍把
`g_isr_cyc_min` 拉成了骨架值（实测差 ~26000 cyc）。

**修法**：先定好 gate → `sleep 30` 让状态分离 → 再清统计 → 再采样。
配套：`g_per_cyc_*` 也必须**按组复位**，否则全局累计会把 I-cache 切换那一拍的
一次性扰动混进所有组的 `max`。

## 11. 下一步（阶段 3）

阶段 2 把"表 + 扫描"落到 DTCM/ITCM 并证明了预算可行性。阶段 3 接的是
**表达完整性与部署链**（对应 MIGRATE 阶段 3/4）：

1. **桶化分档**（div/phase 三档 + 桶表）—— 现在还是"全表扫、不分档"；
   S3 的 OA15 桶化可把每拍遍历从 O(全表) 降到 O(本拍激活子集)
2. **deploy 路径**：0x10 写 staging → 热重载 memcpy → 生效确认
   （S3 的"ACK=已受理 ≠ 已生效"那笔语义债，在 H723 上一步到位）
3. **USART1 通信域**（Modbus RTU 从站）—— 阶段 2 的 `SRC_HMI` 目前返回 0，是留位
4. **顺序域 Sequencer v0**
5. 把 `tools/` 的 Python 回归脚本从 S3 平移过来（协议不变 ⇒ 脚本一行不改）

**平台纪律（沿用 S3 收口）**：新增代码必须同时提供可复跑验证；
涉及新"域"必须登记到冷启动复位；涉及新内存区必须补 SHM 布局断言。
