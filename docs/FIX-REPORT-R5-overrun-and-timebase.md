# 修复报告 R5 — 超预算计数 `ov`（审查二级 #5）+ 一个连带发现：**时基可被调试器静默停掉**

## 0. 一句话

`ov`（超预算次数）原来是**在 0x38 里直接填 0** 冒充"没超预算"，让 S3 套件 T9 的
`ov == 0` 那一半**不可能失败**（空判据）。现在它是**真计数**并配了真实配置的
"能失败"对照（**18343 次 vs 0 次**）。
**但在做对照的过程中发现一个更重的问题**：`DWT_CYCCNT` 会被 pyocd 会话**静默停掉**，
而固件只在启动时使能一次 ⇒ 此后**一切 DWT 计时判据（含 `ov`、`pmin/pmax`、`emin/emax`）
都会静默变成 0，而其它观测量全部正常**。这属"配置全对但功能不可用"的同族，见 §3。

## 1. `ov` 的实现（本项本体）

| 位置 | 改动 |
|---|---|
| `engine.h` | 新增 `OFF_TIMING_OVERRUN = 0x3850`（**与范本同址**；0x18..0x33 那块在 H723 已排满，范本本就把 OVERRUN 单独放这里）+ 对齐/不重叠 `_Static_assert` |
| `engine.h` | 新增 `EXEC_BUDGET_CYCLES = 32000u`（拍长 40000 的 80%；范本同名量是 20000/24000 = 83%，同口径不同数值） |
| `main.c` ISR | `if (di > EXEC_BUDGET_CYCLES) g_isr_overrun++;`（`di` 是 ISR 执行时长，**已有**，成本一次比较） |
| `main.c` | `stats_reset()` 清 `g_isr_overrun`（与范本 `core0_engine_start` 清 OVERRUN 同语义：只反映本次 RUN 段） |
| `main.c` | 主循环镜像到 SHM `0x3850`；`0x38` 的 `put32(r+27, 0u)` → `put32(r+27, g_isr_overrun)` |
| `tools/h723_jitter.py` | 新增 **T0d** 判据（在任何 RESET 之前读，反映"自本次上电累计"） |

★ **为什么把它和 `EXEC_DEPLOY_BUDGET` 分成两个常量**（这是本项目踩过四次的"一常量两用"）：
`EXEC_DEPLOY_BUDGET`(26000) 是**下载期静态门**（预测：程序预算超它 ⇒ 拒绝 deploy）；
`EXEC_BUDGET_CYCLES`(32000) 是**运行期动态判据**（实测：本拍真跑超它 ⇒ 计数 +1）。
一个管"能不能下发"，一个管"跑起来有没有超"。合并会让改动其中一处**静默改变另一处的语义**。

## 3. ★★ 连带发现：`DWT_CYCCNT` 可被调试器**静默停掉**

### 现象（实测两次，间歇出现）
跑完任何 pyocd 会话之后，`0x38` 读回：`pmin=0 pmax=0`（周期统计死的），
而 `emax=7685`（exec 统计活的）、`samples` 正常增长 ⇒ 只有周期路径坏了。

### 机制（由代码结构 + 板上读数反推，自洽）
1. ISR 尾部 `g_per_prev = t0;` 在**门之外**，每拍都写 ⇒ `g_per_prev == 0` **当且仅当 `t0 == 0`**。
   板上实测 `g_per_prev = 0` ⇒ **ISR 入口那一刻 `DWT_CYCCNT` 读到 0**。
2. 而 `di = t1 - t0 = 7685`（非 0）⇒ 出入口读 0、出口读到真值。
3. ⇒ 两者只有一种自洽解释：**CYCCNT 在某段时间里不计数（读回常数 0）**。
   `di = 0` 会让 `g_per_glitch_n` 每拍 +1（该项目**已有**的"时钟不连续"计数器）。
4. 固件的 `dwt_enable()`（置 `DEMCR.TRCENA` + `DWT_CTRL.CYCCNTENA` + 清 CYCCNT）
   **只在启动时跑一次**；pyocd 会话结束后**没人再使能** ⇒ 时基保持死的，
   直到下一次真正的复位。

### 为什么这条很重
* **凡是"写一次就算"的状态，都必须有可被外部读走的判据** —— 这正是本项目反复强调的铁律，
  而**时基本身**是个漏网的状态：它一旦被停，**所有 DWT 类判据都会静默读 0**，
  而 `samples`/协议/表/桶**全部正常** ⇒ 症状是"看起来一切正常，只是时间量都是 0"。
* 它**正好落在 `ov` 判据的前提上**：时基死了 ⇒ `di=0` ⇒ `ov` 永远不可能 > 0
  ⇒ "ov == 0" 在那时**又变回空判据**。所以本项与 §1 是强耦合的。

### 建议的处置（**未擅自实施，待定**）
1. **把时基活性暴露出来**：`g_per_glitch_n`（时钟不连续次数）已经是现成的量，
   应作为**任何 DWT 计时宣称的伴生判据**（`glitch == 0` ⇔ 时基在整段里是活的），
   最好随 `0x38` 尾部一起读走。
2. **自愈**：连续 N 拍读到 `di == 0` 就重新 `dwt_enable()` 一次 —— 但要小心，
   自愈会掩盖"有人动了调试口"这件事，所以**自愈必须配一个计数**（自愈了几次）。
3. **验收脚本的纪律**：凡用 DWT 读数做结论的脚本，应先断言 `glitch == 0`，
   否则**拒答**（本项目的"拒答"惯例）。
