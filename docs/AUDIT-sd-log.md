# AUDIT-sd-log —— 专用裸介质"每拍落盘"日志的端到端验收

日期: 2026-09-12　提交: `495e47e`(变化才记) / `e0d7b6d`(判据改造) / `1c230dc`(通道映射)

---

## 1. 这块是什么

H723 把每一拍的输入/输出快照写成 256B 记录, 连续落到一张**专用裸 SD 卡**上
(无文件系统, LBA0 = 头部, LBA1.. = 数据区环形回卷)。出问题后把卡插到 PC,
用 `tools/sd_log_read.py` 直读 (ctypes 设备句柄, **不需要管理员权限**) 分析。

记录格式 (见 `src/blackbox.h`):

| 字 | 内容 |
|----|------|
| [0] | magic `"DLBK"` |
| [1] | **tick** —— 这一排数据是哪一拍的 (10kHz 引擎拍号) |
| [2] | seq —— 记录序号 (**每次上电从 0 重计**) |
| [3] | ctrl —— `run<<24 \| n_routes` (只有这两个字段) |
| [4..63] | 60 个数据槽, 含义由**通道映射表**决定 |

## 2. 记法: "变化才记"

每拍仍算**完整 256B 全量状态**, 但与"上一条**已写出**记录"逐槽按位比 ——
全同则该拍不写、不占环槽。因此:

- 每条记录仍是全量 + 自带 tick ⇒ 两条之间的所有拍值**必然相同**
  ⇒ PC 按 tick 可**逐拍精确复原** (等价于阶梯重建)。省的只是"重复", 不是"数据"。
- **优雅退化**: 程序若真每拍都变, 就退化成逐拍全量 = 原行为,**不会更差**。
- 诚实的边界: 映射表之外的通道**根本不记** —— 这是"选择", 不是"近似"。
  数据若真不可压缩, 任何设计都救不了。

## 3. 判据 (关键是第 [2] 条能失败)

```
python tools/sd_log_read.py --verify            # 退出码做闸门
python tools/sd_log_read.py --csvin x.csv --verify   # 离线核一个已导出的 CSV
```

| # | 判据 | 通过条件 |
|---|------|----------|
| 0 | tick 严格递增 | 0 违反 |
| 1 | seq 逐条 +1 (丢包会前跳) | 0 跳变 |
| 2 | **相邻记录 60 槽(按位比)全同** | **必须 == 0** |

★ [2] 是唯一"能失败"的判据。历史上工具只报 "tick 连号比例", 而连号率低
**是设计如此** —— 高也说明不了、低也说明不了, 等于没有判据。

**对照构建 (证明 [2] 真能失败)**: 拿改法之前的逐拍全量数据打同一套判据 ——
`3765/4095 = 91.94% FAIL`、`7553/8191 = 92.21% FAIL`。两条对照都失败
⇒ 判据有效 ⇒ 交付数据判 PASS 才有意义。

## 5. 通道映射 (为什么不是"把记录放大到 256 通道")

记录里 4 字头 + 60 数据字 = 正好 64 字 = 256B, 之前只用了 48 个 —— **白扔 12 个**,
而且"记哪 16+16+16 路"是写死的**盲切**。

做法: 60 槽, 每槽由映射表一项 `(seg<<16) | idx` 决定
(0=SENSOR 0..63, 1=WIRE 0..127, 2=ACTUATOR 0..63, 3=空槽恒 0)。
映射表随**日志头**落卡 (`h[16..75]` + 魔数 `h[76]` + FNV 校验 `h[77]`)
⇒ **数据自带"这一列是哪一路通道"**, PC 端按它标列名。

**为什么不放大记录**:

```
缓冲条数 = 环字节 / 记录字节
丢包风险 = "一次 SD 卡内写抖动窗口内产出的条数 > 槽数"
```

256B → 1040B 使槽数 960 → **236 (÷4)**, 同时通道变多、活跃度上升、产出也升 ——
**双重恶化**: 实测最坏卡顿 220 ms, 变化率 15% 时 236 槽只够 **157 ms ⇒ 丢包立刻回来**。
**保持小记录才是鲁棒性来源: 扩通道靠"选得准", 不靠"装得下"。**

**不升 `LOG_VERSION`**: 升了会让 `sd_log_open` 判"版本不符" ⇒ 当新卡重建 ⇒
`s_log_blk` 归零 ⇒ **从 LBA1 覆写, 把卡上已有的 4.1 GB 记录逐步毁掉**。
改用挂独立魔数: 旧固件读新头照常续写, 新固件读旧头自动退回默认表, **两个方向都不动已有数据**。

**"默认表零行为变化"是量出来的, 不是声称的**:

- 默认表 = 旧的 16/16/16 槽序 ⇒ 记录应逐字节相同
- 板上回读 `0x24000390` = **48** (绑到 48 路, 12 空槽)
- 板上回读 `0x24000394` = **0xC4C65F49**, 与 PC 端独立实现算出的期望值**逐位相同**
  ⇒ 固件与上位机跑同一张表、同一算法
- 旧固件 40,000 条记录抽检: `[52..63]` 预留字**全为 0** ⇒ 新固件"显式写 0"结果相同

**改通道 = 只改 `src/blackbox.c` 的 `s_bb_map_def[]` 一张表再烧一次**;
记录尺寸 / 环 / 块结构 / PC 解析全不动。

## 7. 已知的坑 (留给下一个人)

1. **`seq` 每次上电归零** ⇒ 卡上历史跨多次上电, "相邻两条 seq 差 1" 这个不变量
   **只在上电段内成立**。工具必须**按物理顺序读(绝不按 seq 排序)** + **先切上电段**
   (`split_boots()`), 只判最后一段。曾因越读 256 块 + 残留排序, 报出
   "512 处跳变 + 512 处 tick 倒退" 的**假 FAIL** (512 = 越界的记录数)。
2. **假判据的味道是"过于整齐"**: 两个独立指标给出同一个可疑整数时, 先怀疑窗口/切分。
3. **证据属于哪一次改动, 用时间戳对撞**: `证据文件 mtime` vs `含该改动的固件构建时间`。
   同名导出文件会被静默覆盖 —— 导出物应带来源标识(起止 tick/seq、条数)。
4. **越界映射槽的"宣称≠实现"**: 固件把越界 `(seg, idx)` 当空槽(恒 0),
   PC 端必须用**同一套越界判定**(0..63 / 0..127 / 0..63), 否则会出现
   "PC 说这列是 `WIRE200`、实际恒 0"。越界一律标 `BAD*` 并报警。
5. **读固件全局量之前先 `-c reset` 再 `-c "sleep 400"`, 收尾必须 `-c go`**;
   不要在"按着复位的会话"里读 SRAM (读回的是陈旧值)。

## 8. 后 12 个槽: 绝对时间 / 通信 / DO / 强制 (2026-09-12 追加)

记录里 4 字头 + 60 数据字 = 64 字 = 256 B **本来就刚好用满**; 之前只用了前 48 个,
后 12 个当"预留"白扔。现在按用途分配 (段号见 `src/blackbox.h`):

| 槽 | 段 | 内容 |
|----|----|------|
| 48 | TIME 0 | `RTC_TR` 时分秒 (BCD) —— **这一拍是几点** |
| 49 | TIME 1 | `RTC_DR` 年月日 (BCD) |
| 50 | COMM 0 | Modbus `frames_rx` 完整帧数 |
| 51 | COMM 1 | `frames_tx` 发出响应数 |
| 52 | COMM 2 | `err_crc` CRC 校验失败 |
| 53 | COMM 3 | `err_exc` 异常响应数 |
| 54 | COMM 4 | 状态机首字 `state\|slave\|rx_len\|rx_pos` (第一版实测 = 0x00000100, 从站号 1 ✓) |
| 55 | DO 0 | `DO_SHADOW` 打包位图 = **真正锁存到引脚的电平** |
| 56..59 | FORCE 0..3 | 强制位图 128 bit —— 哪几路被强制过 |

**为什么不记通信帧本身**: RX/TX 各 256 B 是帧级瞬态, 塞不进 256 B 记录, 记下来也会被
下一帧覆盖。**该记的是"通不通"的标量**, 帧内容走协议 `0x61` 读回。
**为什么通信标量指向 `MbCtrl_t` 而不另建镜像**: 单一真值, 不制造两份会漂移的状态。
偏移用 `__builtin_offsetof` 从结构体类型取, 并加 `_Static_assert`(实测 9/13/17/21, packed)。

**绝对时间: 一个被自己代码清掉的量 (重要教训)**

- 现象: `TR` 精确等于"上电后几秒"(109s/109.3s、64.8s/63s、32.5s/31s、12.2s/11s)
- 诊断区 (`OFF_RTC_DIAG` @ SHM+0x4A00) 抓到的现场:
  ```text
  dg[0] BDCR(未动手前) = 0x00008103   LSEON|LSERDY|RTCSEL=01|RTCEN=1  ← 备份域保住了
  dg[1] RTC_ISR        = 0x00000027   RSF=1 ⇒ 影子寄存器每秒都在更新 ⇒ 日历在走
  dg[2] 被清之前的 TR  = 0x00000052   (52 秒) ← 日历里本来有值
  dg[3] 走的路径       = 2            ← 判 INITS 得 0, 走了"全新初始化"
  ```
- **根因: `RTC_ISR.INITS` 在这套上读回 0, 不是可用的"日历已在跑"判据。**
  照它判 ⇒ 每次上电都把已经走着的 `TR` 写成 0 ⇒ 绝对时间退化成"上电后几秒"。
- 修法: 判据换成**直接证据** —— `RCC_BDCR.RTCEN=1 && RTCSEL=01` (时钟源在 + RTC 使能)
  + `TR` 的 BCD 合法性; 且全新初始化时**不再无条件清零**, 老值有效就保留。
- 修后 A/B (同场景): 修前 `dg[2]=52s` → TR=0; 修后 `dg[2]=18s` → **新 TR=20s
  (而 uptime 只 2.06s)**, 即**日历跨软复位继续走**。
- 判据: 环 dump 960 条跨 **1.132 秒**, `TR` **恰好 2 个取值** (0x40→0x41) ⇒ **1 Hz 整**。
- **诚实的边界**: 没有备份电池时掉电期间时间不走 ⇒ 复位后是"从原值继续"(冻结),
  不是真实日期; 且 `DR` 仍是没设过的哨兵 `0x00000100` (2000-01-00)。
  要真实日期需要在某处**设时**一次 —— 这是下一步, 不在本次范围。

**位域一律抄官方 device header** (`D:/STM/tools/lxb_ref/.../stm32h723xx.h`):
`LSEON=0 LSERDY=1 RTCSEL=[9:8] RTCEN=15 BDRST=VSWRST=**16**` (`BDRST_Pos` 在 H7 上
被别名到 `VSWRST_Pos`) —— 代码从不碰第 16 位, 已对过。
