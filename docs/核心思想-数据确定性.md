# 核心思想（四）：数据是哪一刻的——采样时刻，同样由硬件锁存

> 「核心思想系列」的第四篇，也是确定性闭环的**输入侧拼图**。
> [零抖动篇](核心思想-零抖动方案.md)讲输出边沿为什么稳，[确定性篇](核心思想-确定性.md)讲计算为什么准点，[低周期篇](核心思想-低周期.md)讲为什么快。本篇讲一件被前三篇跳过的事：**输入数据是哪一刻的**。
> 它不要你懂 ADC 时序，只要接受一个区分：**「读到数据」和「数据是哪一刻的」是两件事。**

---

## 引子：控制工程师的追问

调一个 PID，数据从传感器流进控制器，每个人心里都悬着同一个问题——

> 「我这个 ADC 值，到底是**哪个时刻**采的？是我中断进去那一瞬间吗？还是刚才？还是上上个周期？」

传统程序回答不了这个问题。因为在「定时器中断 + 中断里现采现读」这条经典路径里，**采样时刻和 CPU 的时刻绑在一起**：

- 中断进去的那一刻才开始发起采样 → 采样时刻 = 中断响应时刻，跟着 CPU 的抖动一起抖；
- 采样要等转换完成，转换没结束你就去读了 → 读到的是**上一次**的旧值，而你**不知道它是上一次的**；
- DMA 搬运和 CPU 读取谁先谁后没有约定 → 数据可能是一半新的、一半旧的。

结果就是：**数据时效是玄学**。你说不清数据是哪一刻的，就说不清控制环的相位延迟是多少，控制器建模、相位补偿全是拍脑袋。这是确定性控制里最隐蔽、也最容易被忽略的一环。

DCL 要解决的，正是这件事。

---

## 第一层：病根不在「读得慢」，在「读和采绑在一起」

把零抖动篇那句话翻过来，就是这一篇的核心：

- 零抖动篇：**不让 CPU 决定输出时刻** → 输出时刻由硬件锁存，CPU 只负责把值算好放在那里；
- 本篇：**不让 CPU 决定采样时刻** → 采样时刻由硬件锁存，CPU 只负责去读结果。

如果采样由一块**不受 CPU 影响的硬件**在固定时刻完成、搬好，CPU 什么时候去读都无所谓——**读到的数据是哪一刻的，由硬件决定，和 CPU 的调度抖动无关。**

**输入侧确定性的本质，是「解耦采样与读取」，而不是「把读取也变确定」。**

这和零抖动是同一个思想、同一个镜像：**输出时刻不由 CPU 定，采样时刻同样不由 CPU 定。**

---

## 第二层：在 STM32H723 上怎么落地

H723 把「解耦」焊死在硬件里，CPU 全程不在采样现场：

```
独立硬件链路（采样与计算解耦）：
   TIM1_TRGO（周期内硬件触发，上升沿）
        → ADC1 自动启动转换（EXTSEL=10 → TIM1_TRGO）
        → DMA2 Stream1 循环搬运 ADC1_DR → DTCM（ADC_RAW）
        → ISR 入口 CPU 只需读 ADC_RAW → 换算 → SENSOR_MAP[0]
```

关键点在于：**从 TIM1 触发到数据躺进 DTCM，CPU 完全不在场。** 触发是定时器的，转换是 ADC 的，搬运是 DMA 的——全程硬件，没有任何软件参与、没有任何分支。

ISR 里只剩下读结果这一件事：

```c
uint32_t raw = *(volatile uint32_t *)(ADC_RAW_BASE);   /* 读最近一次搬完的采样值 */
SENSOR_MAP[0] = (float)raw * (3.3f / 4095.0f);        /* 换算成工程值 */
```

因为采样发生在**上一个周期**（TIM1_TRGO 触发 → ADC 转换 → DMA 搬运，全在硬件侧完成），ISR 在第 N 周期读到的采样值，就是**第 N-1 周期**的——一拍延迟，语义清清楚楚。

> 代码位置：`firmware/h723-core0/Src/main.c` —— `ADC1_CFGR = DMAEN | CIRC | EXTSEL=10(TIM1_TRGO)`（第 1780 行附近）、`ADC1_CFGR2 = EXTEN=01`（上升沿触发）、DMA2 Stream1 配置段，以及 `TIM1_UP_IRQHandler` 入口的读取逻辑。架构愿景见 `docs/00-vision/FUTURE-ROADMAP.md` Level 1（DMA 数据路由）。

## 第三层：两种数据，两种语义（这个区分很重要）

引擎里跑着**两种不同时间语义**的数据，别混为一谈：

**① 传感器 / ADC 输入 —— 上一周期的采样快照（一拍延迟）**
`SENSOR_MAP` 在 ISR 入口写一次，本周期内不再变化。所有路由读到的都是同一份、同一时刻的采样值——**数据是哪一刻的，答案是确定的：上一个周期。**

**② 内部 WIRE 信号 —— 本周期流式传播（拓扑序）**
`WIRE_MAP` 是中间计算量。ISR 顺序扫描路由表，生产者路由先算、写完 `WIRE_MAP`，消费者路由后算、读到的就是**本周期**刚产生的新值。编译器用 **Kahn 拓扑排序**（`ide/compiler/dcl_compiler.py`，含循环依赖检测）保证"生产者先于消费者"——所以 WIRE 是流式的，不是快照。

那"数据撕裂"怎么避免？——不是靠快照，是靠**根本没有并发**：引擎单线程流式执行、ISR 不被抢占、系统里没有第二个写者。撕裂这个 bug 在架构上就不存在，而不是碰运气躲过去的。

## 镜像对照：零抖动 vs 数据确定性

| | **零抖动（输出侧）** | **数据确定性（输入侧）** |
|---|---|---|
| 问题 | 输出边沿**何时**翻转？ | 输入数据是**哪一刻**的？ |
| 病根 | 算和出绑在一起 | 读和采绑在一起 |
| 解法 | CPU 不负责输出时刻 | CPU 不负责采样时刻 |
| 硬件链 | TIM1_CC4 → DMA → GPIOE_ODR | TIM1_TRGO → ADC → DMA → DTCM |
| 锁定时刻 | 周期末尾（~97.5 μs） | 上一周期采样 |
| 结果 | 输出抖动 < 10 ns（实测） | 数据时效精确（一拍延迟） |

加上[确定性篇](核心思想-确定性.md)（计算侧无不确定源）和[低周期篇](核心思想-低周期.md)（计算侧能多快），确定性闭环终于完整：

> **数据是哪一刻的、周期是多长、输出何时翻转——全部由硅回答，软件只在中间算数。**

---

## 为什么值钱（控制工程师视角）

1. **数据时效可建模**：周期 N 的输出基于周期 N-1 的采样，总延迟 = 一拍采样 + 计算 + 一拍输出，可以精确写进离散传递函数（那一个 `z⁻¹` 因子）。控制器设计不再是玄学——这在工业控制里是刚需。
2. **采样时刻由硅保证**：采样不受中断延迟、总线竞争、cache miss 影响——输入侧的确定性和输出侧完全对称。CPU 这边的抖动，被隔离在"不碰数据时刻"的路径上。
3. **一致性是架构的，不是运气的**：同一周期所有路由看到同一份传感器快照、按拓扑序消费 WIRE，数据的一致性由设计保证，不依赖"恰好没被抢占"的运气。

---

## 诚实边界

1. **一拍延迟是设计语义，不是 bug**——但它确实给反馈环增加了一拍相位延迟。离散控制器本来就要处理一拍延迟（数字控制器天然如此），语义一致、可建模，不隐藏。
2. **采样率 = 控制周期**：每周期一次采样。如果周期压得太短，传感器和 ADC 的物理上限跟不上（低周期篇提过"控制器快了，传感器反而跟不上了"）——采样语义不变，但数据的信息量受物理约束。
3. **当前实现**：输入侧已硬件化（TIM1_TRGO + DMA 循环，达成 FUTURE-ROADMAP Level 1 的输入半边）；完整 DMA 数据路由（输入 + 输出全硬件接管）是演进方向——WIRE 中间量目前仍是 CPU 流式计算。
4. **通道数**：当前固件接的是 ADC1 单通道（`SENSOR_MAP[0]`）。多传感器扩展有容量（`MAX_SENSORS = 64`）但固件侧尚未接多通道——照实讲，不夸大。

---

## 一句话总结

> **数据是哪一刻的？不是"刚才"，是"上一个周期"——由硅回答，不归 CPU 管。**
