## 4. ★★ 端到端跑出来的真 bug：`CTU` 缺第二输入（dclc 既有缺陷）

**现象**：`deploy 被拒: NAK — this op needs wire2 source`，整份程序无法下发。

**定位**：把编译器生成的路由逐条打出来（`dclc.compile_stmts(...)`），
唯一一条"需要第二输入却没给"的是 `CTU → OP_CNT`：

```
#21 op=11(CNT) ch=22 wire2=None valid=False   ← 就是它
```

**机制**：`dclc` 在 `CTU`/`CTD` 不写 `R=`/`LD=` 时把 `wire2` 设为 `None`（无第二输入）。
而固件对**双输入原语**（AND/OR/ARITH/SR/**CNT**）要求第二输入必须有效 ——
这是 H723 **A3 审计故意收紧**的判据，用来拦"漏给第二输入"导致的静默语义错误。
⇒ **S3 侧碰不到**（S3 的双输入校验只拦 AND/OR，A3 才补上 ARITH/SR/CNT）。
**这是被"校验器收紧"照出来的潜藏编译器缺口** —— 收紧校验的收益当场兑现了。

**修法选在编译器，不放宽固件**：IEC 语义里"不接复位端"= 复位输入恒为假
⇒ 用一根**恒 0 的 wire** 接上，语义等价；不放宽固件，因为放宽会同时牺牲 AND/OR/ARITH 的保护。
实现：`Sym.zero_wire()` 惰性分配、全程序共用（只多 1 条路由 + 1 个参数）。
**收紧 > 放宽。**

★★ **这条也解释了为什么"端到端"必须单独验**：协议层 12/12、引擎 27/27、persist 26/26 全绿，
但"一份带 `CTU` 的文本程序"根本下不进板子。**组件全绿 ≠ 系统可用。**

## 5. ★★ 今天一整轮故障的复盘：CH340 的 `RTS` 直连到 `NRST`

**症状**（看起来极像固件挂了）：串口 0 字节 + **SWD 非复位 attach 也失败**
（`SWD/JTAG communication failure (WAIT ACK)` / `No cores were discovered`）。

**排除过程**（每一步都用可读回的量，不靠猜）：

| 检查 | 结果 | 推论 |
|---|---|---|
| 拍计数 500ms 内 319 → 5329 | 10.02 kHz | **固件在跑** |
| `HFSR` / `CFSR` / `BFAR` | 全 0 | **没有 HardFault** |
| `under-reset` 连接 | 成功 | 目标可恢复 |
| `halt`（不复位）连接 | 失败 | 与"目标是否复位"强相关 |

**根因**（用户提供关键信息后确认）：CH340 的 `RTS` 被接到了板子的 `RST`。
而 **pyserial/驱动在打开串口时会 assert RTS** ⇒ **NRST 被按住** ⇒
串口收不到（板子在复位里）**且** SWD 非复位 attach 也挂（复位线被外部驱动）。
两个接口同时失效 ⇒ 症状指向"固件/探针坏了"，**排查方向被完全带偏**。

**拆掉那根线后**：SWD 恢复 5/5，串口恢复 ACK。**一次因果关系，两个症状。**

**工程结论（写给未来的自己）**：
1. **直连 `RTS→NRST` 是错的接法**。要做"PC 复位板子"（S3 套件 T15 的重启半段），
   正确做法是 **`RTS` ——100nF—— `NRST`**（交流耦合：只有电平跳变产生一个短脉冲，
   稳态按不住板子），并确认 RTS 输出是 **3.3V 而不是 5V**（5V 直灌 3.3V 的 NRST 有隐患）。
2. 工具侧已加防御（`open_serial()` 打开后立刻释放 RTS/DTR）—— 即使将来再有人这么接，
   也不会"一打开串口就把板子按死"。
3. ★★ **"无响应"类判据必须先证链路活性，且要能区分"两个接口同时失效"这种共同根因。**
   串口 + SWD **同时**不通，最可能的原因是它们**共用**的东西（复位线/供电/USB），
   而不是固件 —— 因为固件的故障通常只影响它自己那一路。

## 6. 本轮判据自身修过的四处（都属于"我的测试成了故障源"）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 4/4 FAIL：`PermissionError(13)` | 工具自己开着 COM14，又 fork 出 `dclc.py` 去开同一个口（**Windows COM 独占**，项目已记录过的坑） | `Session.release()/reopen()`：跑子进程前释放串口 |
| 2 | A3 FAIL：停留步 0.657 s | 采样起点落在停留步中间 ⇒ **首段是被截断的部分段** | 丢掉第一段再判读 |
| 3 | A4 偶发 FAIL | 采样是 PC 侧 0x22 往返，Windows 上单次可抖动几十 ms ⇒ 按 8~13ms 卡会随机失败 | 改成抗抖动的"瞬时步显著短于停留步"；严格计时交给 A3/A5 |
| 4 | D1 FAIL：`sensor[4]=0` | 判据**假定了接线状态**（要求四条 DI 都必须悬空为 1），而工位上 PC1 正是被拉了 GND | 值域+稳定性判据；下游译码按**实测** DI 值推算期望 ⇒ 与接线无关 |

★ 模式：**判据失败时，先问"是不是我的测试/测量把它弄成这样的"**。
这四条里有三条是测量方法缺陷，只有 §4 那条是**真缺陷**。
