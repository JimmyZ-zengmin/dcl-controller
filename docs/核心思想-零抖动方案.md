# 核心思想：我们是怎么把 GPIO 抖动做到近乎为零的

> 这是写给**第一次点进这个仓库的人**看的。
> 如果你只想知道"这堆代码到底牛在哪"，读这一篇就够了。它不要你懂 STM32，只要你能接受一个朴素的直觉：**让输出不抖，不是让计算不抖，而是让计算和输出彻底分开。**

---

## 引子：一个让人睡不着的问题

很多人玩 MCU 控制，都会卡在同一个地方——

> 「我明明用定时器触发了中断，为什么示波器上看 GPIO，每一帧的边沿还是歪歪扭扭、前后晃动几十纳秒甚至几百纳秒？」

这不是你代码写得烂。这是**传统做法的结构性宿命**。

在「定时器中断 + 在中断里算完直接写 IO」这条经典路径里，**「CPU 算完的那一刻」就是「输出生效的那一刻」**。而 CPU 算出结果的那一刻，本身就是会抖的：中断什么时候真正进、总线那一刻有没有被别的主设备抢走、cache 有没有 miss 一下……这些不确定性会**原封不动地传导**到你的输出引脚上。

我在 ESP32 上实测过：输出抖动的峰峰值 **462 ns**，恰好等于 ISR 入口的抖动。CPU 入口抖多少，引脚就跟着抖多少。你超频、你优化、你把中断优先级拉满，都只是在**减小**这个数，永远消不掉——因为抖动源就在链路正中间。

DCL 要解决的，正是这件事。

---

## 第一层：病根不在「算得慢」，在「算和出绑在一起」

先把刚才那句话翻过来想：

> 如果我们**不让 CPU 去决定输出时刻**，而是让 CPU 只负责「把值算好放在那里」，再由一块**不受 CPU 影响的硬件**在固定时刻把值「锁存」到引脚上——那 CPU 那点抖动，还重要吗？

不重要了。因为输出时刻已经不在 CPU 手里。CPU 早算完一帧、晚算完一帧，只要它在「锁存时刻」之前交卷，引脚翻不翻、何时翻，完全由硬件决定。

**根除抖动的本质，是「解耦计算与输出」，而不是「把计算也变确定」。**

这是整个 DCL 引擎最值钱的一句话。它把问题从「让 544 MHz 的 CPU 跑得绝对准时」（几乎不可能）降维成了「让一块定时器在固定时刻搬一个数」（硬件天生擅长）。

---

## 第二层：在 STM32H723 上怎么落地

思路清楚了，剩下的就是把「解耦」焊死在芯片上。H723（Cortex-M7，544 MHz）给了我们需要的全部零件：

```
ISR 里（会抖，但无关紧要）：
   计算 → 把结果写进 SHADOW_GPIO（DTCM 里的一个影子缓冲，无 timing 要求）

独立硬件链路（绝对准时）：
   TIM1 在周期末尾(CC4≈97.5μs)产生匹配事件
        → DMAMUX 把它路由到 DMA2 Stream5
        → DMA 硬件把 SHADOW_GPIO 搬到 GPIOE_ODR
        → 引脚在同一刻翻转，零抖动
```

关键点在于：**从 SHADOW 到引脚这一步，CPU 完全不在场**。它是定时器事件触发 DMA、DMA 直接写 GPIO 输出数据寄存器，全程 4 个 AHB 周期，没有任何软件参与、没有任何分支、没有任何「这一拍会不会慢」的疑问。

PWM 输出走的是同一条哲学，只是零件换了一下：TIM1 的比较值写在**预装载影子寄存器**里，由更新事件（UEV）在固定时刻统一装载。你看不到「写 CCR 的瞬间生效」，你看到的是「下一个周期边界统一生效」——所以 PWM 边沿也是零抖动。

> 代码位置：`firmware/h723-core0/Src/main.c` 的 `TIM1_UP_IRQHandler`（SHADOW 写入在 ISR 末尾）与 DMA/DMAMUX 配置段。更完整的推导见 `docs/reference/核心0-抖动根除与1μs周期方案.md`。

## 第三层：解耦要成立，得有三个支柱撑着

「CPU 只要在锁存前交卷就行」——这句话要为真，必须保证 CPU **永远**赶在锁存时刻之前算完。DCL 用三件事把这个保证焊死：

**① 硬件定时锚点**
周期不是靠 RTOS 调度「尽量准」，而是 TIM1 硬件定时器硬强制 100 μs。时间锚点不在软件里，在硅里。

**② DTCM 零等待内存**
路由表、传感器值、中间信号线全放在 DTCM（128 KB 零等待），不放在带 cache 的 SRAM。好处有两重：一是不存在 cache miss 导致的偶发卡顿；二是**根本避开了多核缓存一致性那类噩梦**（H723 单核 + DTCM，连「缓存一致性」问题都不会发生）。详见 `docs/reference/缓存一致性问题.md`——那篇是踩坑记录，看完你会庆幸自己没在多核上折腾这个。

**③ 路由表无动态分支**
引擎跑的不是「程序」，是一张静态路由表。每条路由 = 「源 → 原语 → 目标」，顺序扫描、没有 `if`、没有函数调用、没有运行时分支。执行时间在**编译期就能预算**，不会突然出现一次 M7 分支预测失败（约 12 周期惩罚）把你整帧节奏打乱。

三件事合在一起，结论很硬：**计算侧最坏情况执行时间可预算，且稳稳小于锁存前的余量**。解耦成立。

## 诚实边界：别把「测量抖动」和「输出抖动」混为一谈

讲到这里，必须停一下，把话讲老实——否则这篇就变成吹牛了。

仓库 README 里写的「**~37 ns 周期抖动**」，测的是 **ISR 入口到入口**的周期抖动（含离群 ~144 ns）。它反映的是 CPU 那一侧的不确定性：中断响应、总线竞争、偶发的离群。

但**物理引脚上的输出抖动，实际是 < 0.5 ns**（只受晶振精度与那 3.5 ns 锁存延迟影响）。

这两句话不矛盾，它们说的是两件事：

- **周期抖动 ~37 ns** = CPU 侧「我这一帧什么时候开始算」在抖；
- **输出抖动 < 0.5 ns** = 引脚「我这一帧什么时候翻转」被硬件锁死，不抖。

灵魂一句（也是本项目最想对外讲清楚的认知）：

> **周期测量的抖动 ≠ 输出的抖动。测量值暴露的是 ISR 入口的变化，但输出时刻由硬件锁存决定，与入口无关。**

所以「0 抖动」在这里的诚实含义是：**物理输出的边沿抖动趋近于零（<0.5 ns）**，而 CPU 侧那 37 ns 的抖动，已经被我们「隔离」到了一条不碰引脚的路径上，对控制结果无影响。

至于为什么还比 Beckhoff / B&R 差 4–8×：那是 MCU 方案的物理天花板（晶振与锁存延迟，对上人家更硬的时钟树与专用时序逻辑），不是实现问题。照实讲，不美化。

---

## 一句话总结

> **DCL 不追求「让 CPU 算得绝对准时」，而是「让 CPU 根本不负责输出时刻」。计算随便抖，输出由硬件在固定节拍锁存——抖动因此变得无关紧要。**

如果你看懂了这一句，你就看懂了这个项目 80% 的含金量。剩下 20% 在 `docs/reference/核心0-抖动根除与1μs周期方案.md`（含 1 μs 周期的前沿探索）和 `docs/JITTER-MEASUREMENT.md`（可复现的测量方法）里。
