## 1. 分层（规范）

```
┌──────────────────────────────────────────────────────────────────────┐
│ ① 引擎核心 Engine Core   烧录 (build.sh → pyocd flash)                │
│   boot / TIM2 硬拍 / ISR / 引擎扫描 / 19 原语 / 外设驱动 / 协议栈      │
├──────────────────────────────────────────────────────────────────────┤
│ ② 外设能力 Peripheral Capability   随①发布, **版本化 + 能力位**        │
│   A 引擎内置: DI / AI / DO / PWM / SD / RTC                           │
│   B 具名设备: as5600 / tb6600 …  (vendor, product, revision)          │
│   C 通用事务: i2c / spi / uart 事务                                   │
├──────────────────────────────────────────────────────────────────────┤
│ ③ DCL 程序 Program       **通信上传 + 持久化到 SD**                    │
│   路由表 + 参数 + 状态 + (顺序域)                                     │
├──────────────────────────────────────────────────────────────────────┤
│ ④ 程序工程 Project       上位机侧: .dcl 源 + manifest + 编译产物       │
└──────────────────────────────────────────────────────────────────────┘
```

### 1.1 层间判据（**决定某个需求放哪一层，用这张表，不要凭习惯**）

| 问题 | 放哪层 |
|---|---|
| 它是"**怎么算**"（逻辑 / 连续 / 顺序）？ | **③ 程序** |
| 它是"**和外设怎么说话**"？ | **② 外设能力**（通用事务 op 或具名设备）—— **不是**新驱动 |
| 它需要**新的每拍行为 / 新的实时保证**？ | **① 核心**（必走 A/B + 全套回归） |
| 它只是"**给上位机看的量**"？ | 进 SHM + `obs_anchor()` 登记 —— **不是**加协议 op |

### 1.2 每层的"允许 / 禁止"

| 层 | 允许 | 禁止 |
|---|---|---|
| ① | 改寄存器、改 ISR、加原语、加输出面 | 承载"用户逻辑"；承载"上位机随手要的观测" |
| ② | 被程序**按名字 + 版本**引用 | 让程序直接出现**引脚号 / 总线地址 / 寄存器地址** |
| ③ | 用 19 原语 + 顺序域 + 具名设备 | 直接碰硬件；假设"核心一定支持某个能力"（须声明） |
| ④ | 编译、打包、版本管理 | 把"编译期能查出的错"留到运行期 |

## 2. ① 引擎核心

- **交付形式**：烧录。`bash build.sh`（**零警告闸门** + **ISR 调用树闸门**）→ `pyocd flash`。
- **变更纪律**：任何核心改动必须 ① 配 A/B 对照 ② 跑全部套件 ③ 判据能失败。
- **对外契约**（这三样是核心对外的全部承诺）：
  1. `fw_ver`（现 `DCL_FW_VERSION_H723 = 0x0200`）
  2. **能力位**（现 u16，**v1 起扩 u32**，见 §3.3）
  3. **命令表 + SHM 布局** —— ★ **SHM 布局以 `src/engine.h` 为唯一权威**；
     任何"第二份偏移表"（文档或脚本）都只是引用，**不一致以 `engine.h` 为准**。

## 3. ② 外设能力

### 3.1 ★ 边界定义（**本文最重要的一条**）

> **程序（③层）里不得出现任何物理引脚号、总线地址或寄存器地址。**

这一条同时被三边独立确认：IEC 61131-3（逻辑/硬件两分）·
CODESYS（*"application POUs **never** reference physical I/O addresses"*，物理映射只出现在 I/O Mapping POU）·
Zephyr（*"设备树是硬件信息的唯一真相源，驱动代码不应包含任何具体的引脚号、地址"*）。

**可执行判据**：对 ③层的源文本/产物做一次静态扫描 —— 若出现 `P[A-H]\d+`、`P[E]\d+`、`0x4`/`0x5` 开头的地址字面量 ⇒ **拒绝编译**。

### 3.2 能力的三种形态

| 形态 | 例子 | 程序怎么用 | 新增成本 |
|---|---|---|---|
| **A 引擎内置** | DI(4) / AI(3) / DO(16) / PWM / SD / RTC | 走 `SENSOR` / `ACTUATOR` / `WIRE` 槽 | 改核心（重回归） |
| **B 具名设备** | `as5600`（角度）、`tb6600`（步进） | 按**名字**引用具名槽 | 加一个设备驱动 + 登记 |
| **C 通用事务 op** | `i2c_start/stop/write/read`、`spi_xfer`、`uart_tx/rx` | 在**设备驱动内部**用；若要开放给程序，须标注"厂商专属、不保证跨平台" | 加一条通用原语（一次，长期受益） |

★ **C 是"支持新传感器"的正确答案** —— 有了 C，"接一个新器件"= **写一段程序**，
而不是"改固件 + 重新烧录 + 全套回归"。（本项目 I2C 那次走的是"专用驱动 + 专用诊断命令"，
即形态 B 的临时做法 ⇒ 见 §9 GAP-6。）

### 3.3 每个能力必须具备的身份四元组（照抄 CiA 301 的 `0x1018 Identity Object`）

| 字段 | 说明 |
|---|---|
| `device_type` | 能力类别（对应 CiA `0x1000`） |
| `vendor_id` | 厂商（本平台 = 固定值） |
| `product_code` | 该设备/能力的编号 |
| `revision` | **该能力的版本**（行为变了必须升） |

⇒ **能力位从 u16 扩到 u32**，每一位对应一个 `(device_type, product_code)`，并补 `I2C / SPI / SD / RTC / CAN / ETH`。

### 3.4 新增一个能力的流程（5 步，缺一不可）
1. **判层**（§1.1）—— 能做成 C 就不要做成 B，能做成 B 就不要动 ①。
2. **定义身份四元组 + 占用一个能力位**。
3. **实现 + 加"能失败的判据"**（例如：能力位没置而程序要求它 ⇒ 上传期必须被拒）。
4. **进 `ARCH-H723.md` 命令表/能力位表**（★ 现状：能力位表**滞后**，见 GAP-7）。
5. **在设备描述里登记**（见 §3.5）。

### 3.5 设备描述（我们的 ESI 等价物）
一份**机器可读**的表（JSON 即可），列出：`fw_ver` / 能力位 / 具名设备清单（四元组）/
每个设备可用的槽号或 op 号。**上位机在编译与上传时读它做预检。**

### 3.6 ★★★ 通用事务 op 的**落地约束**（GAP-6 判层结论，2026-09-16）

> 起因：GAP-6 一度被描述为"**由主循环/独立状态机驱动的协议命令**"。
> **那个说法与核心理论冲突**，而且错在一个我们**自己早就写下过答案**的地方。此处定案。

**结论：通用外设事务（I2C/SPI）的正确形态 = 「照 `adc_poll` 的范式，做成拍内每拍推进一步的状态机」**，
不是"主循环里跑一段阻塞事务"。

| 若按"主循环驱动阻塞事务" | 冲突 |
|---|---|
| 无标价、无静态门、无动态门 | ❌ **公理④ 时间预算是一等公民** —— 与当初判 macro 为 B 档（非实时）**是同一条理由** |
| 挂在主循环上（一圈实测 **0.37 ms**（2026-09-16 **直接实测**；原 1.28~1.54 ms 是**反推值**，已作废），拍是 100 µs） | ❌ §8-4 / 实验七条"**别把实时量挂到主循环上**" |
| "每拍必须发生"的事务落进分支/服务环 | ❌ **不变量 3**（每拍必须发生的动作不得挂在分支里） |
| 与已有 `as5600` 驱动**共用同一条 I2C 总线** | ❌❌ **公理② 单写者** —— 一条总线两个写者。本项目**已因此栽过两次**（`TIM3` 两个驱动者 → C1；**SD 卡两个写者**：日志从 LBA1 回卷 + `sd_dump_write` 写 LBA3000000）|

**⇒ 四条硬约束（缺一条就是重犯）：**
1. **拍内推进**：状态机在 ISR 里每拍走一步（`PLAN-dcl-standardization.md` §4.4-C 的原话：
   "**前提是先把它从主循环搬走 —— 改成'每拍由 ISR 推进的状态机'或'独立 DMA 驱动的引擎'**"）。
2. **标价 + 预算门**：每步进 `OP_COST`/静态门/动态门（公理④）。
3. ★ **总线独占门**：任何时刻只有**一个** owner 能驱动该总线；`as5600` 这类具名设备与通用事务
   **必须走同一个门**（公理②）。
4. ★ **就绪门**：事务**跨拍** ⇒ 程序面拿到的是"**上一次的结果 + 就绪标志**"，
   **不能假设"发命令即得值"**。照 `adc_poll` 的 `s_adc_ready` 做；跨拍状态用 u32（不变量 7）。

**★ 已有的成功先例（这就是为什么它可行）**：`adc_poll` 处理的正是同一类问题 ——
**单次转换 259 µs > 拍长 100 µs**，做法是"启动 → 等 3 拍 → 读 → 下通道"的**跨拍非阻塞状态机**，
跑在拍内、进预算（`CORE-ENGINE.md` §3.1）。I2C 事务没有任何理由做不到。

**★ 连带项（GAP-6 落地时必须同步处理）**：本约束一旦成立，**macro 的 C 档用途即被替代**
—— `PLAN-dcl-standardization.md` §4.4-C 说的"要先把 macro 从主循环搬走"这件事，
可以由"通用事务状态机"直接承担 ⇒ **macro 的 C 档路线应正式关闭**，§4.4 的三档结论需相应更新。

**⇒ 仍存在的真实取舍（不掩饰）**：事务跨拍 ⇒ **单次读有延迟**（I2C 400 kHz 读 2 B 约数十拍）。
这不违反确定性（延迟有**可计算上界**），但**程序面必须显式处理异步**（约束 4）。
把这条写进契约，是为了避免"看起来能立刻取到值"的幻觉。



### 3.6.1 ★★ 这条规则的**适用边界**（2026-09-16 读源码 + 实测后补 —— 防止把自己的规则过度套用）

§3.6 的立论是"**主循环一圈 **0.37 ms**(2026-09-16 直接实测; 原 1.28~1.54 ms 系反推, 已作废)，而拍是 100 µs**" ⇒ **实时量不能挂主循环**。
但"外设事务"并不都实时。判据应当是**两问**：

| 问 | 是 ⇒ | 否 ⇒ |
|---|---|---|
| ① 它处在**控制回路**里吗（结果要在拍内参与运算）？ | **必须拍内状态机**（§3.6） | 主循环服务即可 |
| ② 它把主循环堵到**可测**的程度吗？（判据见下） | 必须拍内 | 主循环服务即可 |

②有**现成判据**：`WDT_STAT` 的 `loop_gap_max_undecl`（**未声明**的停拍数）与 `ISR 超预算次数`。

**实测（2026-09-16，交付档；AS5600 属"10 ms 轮询 + 两次阻塞读 ≈450 µs"）：**
```
loop_gap_max_undecl = 0 拍      ← 没有任何"未声明"的停顿
ISR 最长 = 422 tick = 2.11 µs   ← 预算 80 µs（用了 2.6%）
超预算 = 0 次
```
⇒ **AS5600 这类"服务型器件"留在主循环，是本项目架构所允许的**（§1.2-4 原文"服务性动作 → 主循环"），
  **它不是 §3.6 要治的病**。

★ 这条边界的价值：**不要因为写了一条规则，就把所有东西都往拍内塞** ——
  **判据应当由测量决定，而不是由规则的措辞决定**（本项目反复吃过的"过度声称"）。

**★★★ 2026-09-16 直接实测更正**（用户要求"先看最新源码再判断"后发现的）
本规则长期引用的"主循环一圈 **1.28~1.54 ms**"是**反推值**，不是量出来的 ——
它出自 `docs/audit/h723_limit_tick_probe.py`：由"截止拍递减率 649 次/秒"配合 `k=1` 与
`floor(dt/10)` 的**假设**推得。**直接测量**（读 `WDT_STAT[8]` = `g_loop_hb` 的增量）：

```
空载            : 2709 圈/秒  ⇒ 一圈 369 µs
引擎 RUN        : 2685 圈/秒  ⇒ 一圈 372 µs
                  （同期 samples = 10.16 kHz ⇒ 拍本身是准的，不是时基问题）
```

⇒ **主循环一圈 ≈ 0.37 ms，且与负载无关**；与 100 µs 的拍相差 **3.7 倍**（原写"13~15 倍"）。
★ **规则本身不变**（370 µs ≫ 100 µs ⇒ 实时量仍不能挂主循环），但**立论用的数字错了约 4 倍**。
★★ 教训（同族，值得单列）：**"反推的量"必须与"直接量的量"对账** ——
  反推里只要有一个假设不成立（这里的 `k` 与 `floor(dt/10)`），一个错数就会**穿遍所有文档与记忆**。
  ⇒ 凡进入判据或文档的关键数字，**要能指出它是"量的"还是"推的"**；推的必须标注假设。

### 3.7 GAP-6 实施方案与验收判据（`[已定]`，2026-09-16）

**现状事实（已侦察，非推测）**
- 现有 I2C = **位翻转**（`src/i2c_bb.c`），PB10=SCL / PB11=SDA，**已按引脚参数化**
  （`i2c_bb_select()`），事务函数已通用（`addr7/reg/buf/n`）。
- 它是**阻塞**的：`dly()` = 400 次 NOP ⇒ 半位 ≈ 4.5 µs ⇒ **100 kHz**，
  一次 2 字节读 ≈ **250 µs** ⇒ 目前挂在**主循环**（10 ms 节流）。
- 总线当前**健康**：`0x39 op=18` 实测 `tx = i2c_ok = 313404 / err=0 / nak=0`（**31 万次零错误**）。

**实施顺序（★ 关键：状态机必须先行，否则就是违反 §3.6）**

| 步 | 做什么 | 验收 |
|---|---|---|
| **G6-1** | **拍内状态机**（`src/i2c_sm.c`）：把嵌套循环的位翻转改写成**可恢复**的状态机，**每拍推进一个"相位"**（START/字节/REPEAT-START/STOP），每拍周期开销**有界** | 上机：状态机读 AS5600 的 RAW ANGLE **与阻塞路径的值一致**（两条独立路径对上才算数 —— `i2c_bb.h:8` 原文） |
| **G6-2** | **总线独占门**：`as5600` 与通用事务**必须走同一个门**；占用中再请求 ⇒ 明确 BUSY（**能失败的判据**）| ✅ **已完成**：门住在**资源处**（`i2c_bb.c` 的 `i2c_bus_acquire/release`，**带引用计数**），阻塞路径与状态机共用同一道门；`i2c_bb_*` 拿不到门返回 `I2C_BB_ERR_BUSY`、状态机返回 `GATE_BUSY`。判据 `tools/h723_i2c_gate_test.py`（`0x39 op=22` 人工占用使判据**可执行**）**实测 5/5 PASS**：占用期 SM 请求被拒（`gate_n`+1、`busy_n`+1）· 阻塞路径不受影响（`tx` 照涨 `nak=0`）· 释放即恢复（读数与阻塞路径一致）· **占用有界自动释放** · 静息 `owner=0 refs=0`（无引用计数泄漏）。★ 首跑 G2/G5 双 FAIL 暴露真 bug：**单一 owner 无法表达"有几层在用"** —— 阻塞路径 `acquire/release` 成对，`as5600_poll` 一次读就把别人的占用放掉了（> 单一 owner 只能表达"谁在用"）| ✅ **closed** |
| **G6-3** | **SHM 事务区** + `req_seq/done_seq` 握手 | ✅ **已完成**：`OFF_I2C_XACT = 0x7200`，**64 B**（比原计划的 256 B 小 —— 实际字段只用到 64B），含 3 条 `_Static_assert`（越界 / 尺寸 / 与 `PERSIST_STAT` 重叠）。字段：`MAGIC`('IXAC' 区存在自证) / `REQ_SEQ`(单调非0) / `DONE_SEQ` / `STATUS` / `PHASE` / `TICKS` / `LAST_OK_SEQ` / `REQ`(打包 addr·op·reg·len) / `DATA[8]` / 6 个计数器。握手由主循环的 `i2c_shm_service()` **每圈**执行；`obs_anchor()` 已登记全部新观测量。★ 判据 `tools/h723_i2c_shm_test.py` **实测 6/6 PASS**：`MAGIC` 自证 · 经 SHM 读数与阻塞路径一致(3347) · ★ **就绪门 `IX_TICKS=6+n=8`**（事务跨拍，"写完即得值"不成立）· ★ **序号幂等**（重写同一 seq 不再发起）· ping 也走通 · 阻塞路径无污染（`nak=0 err=0`）。★ 实测踩坑：服务调用初版被写在 `每 100 拍` 的分支里 ⇒ 延迟放门被拖到 **10ms**、握手分辨率也只有 10ms（与注释不符）⇒ 已挪到**循环顶层** | ✅ **closed** |

**本轮的 G6-1 只做"诊断面"**：先用 `0x39` 诊断族（**已声明为临时脚手架、不属架构**）触发与读回，
**不动程序面**。理由：**在状态机被证明之前，不得把它挂上契约面** —— 否则就是把未验证的东西写进契约。

**每拍时间账（必须算清，公理④）**：拍 = 100 µs = 40000 cyc，执行预算 32000 cyc。
状态机按 **400 kHz** 设计（位周期 2.5 µs ⇒ 一位 ≈ 1000 cyc）⇒ **一拍推一个字节**
（9 位 ≈ 9000 cyc ≈ 预算 28%）；AS5600 一次 2 字节读 ≈ **6 拍 ≈ 600 µs**
（现状 250 µs ⇒ 用 2.4× 延迟换"**无阻塞 + 每拍有界**"）。★ 若 400 kHz 上机不稳，
退到"一拍半字节"，代价是延迟翻倍 —— 两者都由 G6-1 的判据裁决，不靠猜。

**★ 必须同时说清的取舍**：状态机让单次事务**跨拍** ⇒ **必须给程序面一个就绪门**
（照 `adc_poll` 的 `s_adc_ready`）。**禁止**让程序假设"发请求即得值"。

#### 3.7.2 ★★★ "结果归属"必须显式携带（2026-09-16 落地 G6-4 时挖出，**两层同一个病**）

本状态机只有**一个** `s_rbuf`/`s_status`/`s_len`，而使用者有**两个**
（`i2c_shm_service` 与 `dev_bind_service`）⇒ 收尾方必须能回答"**这个结果是我的吗**"。
本项目的三段演进（每段都真的错了一次）值得完整留档，因为它是**缺陷族**：

| 版本 | 判据 | 为什么不够 |
|---|---|---|
| v1 | `i2c_sm_status() == OK` | 只证明"**有人**成功了"，不证明"**是我**"。别人插入并完成 ⇒ **他的读数写进我的槽** |
| v2 | 加归属令牌 `done_req == my` | 令牌**必要但不充分**：`s_status` 是**实时态**，一个**被拒**的请求（门忙/BADARG）会覆写它 ⇒ "令牌匹配但状态已变" ⇒ 收尾方**丢弃自己的好数据并计错** |
| **v3（当前）** | **完成记录** `{done_req, done_status, done_len}`：完成那刻快照、**受理新请求即失效**；取数走 `i2c_sm_take_result(my,…)` | 取结果**不再依赖任何实时字段** |

实现约束（**改这里时必须同时满足**）：
1. `i2c_sm_done_req()` / `i2c_sm_done_status()` / `i2c_sm_take_result(my,…)` 是唯一取数口；
   `i2c_sm_result()` 保留，但也已改为**完成记录的薄封装**（旧实现按实时态取数 —— **已删除，别恢复**）。
2. **受理请求时立刻 `done_req = I2C_SM_DONE_NONE`**（"从这一刻起没有结果可取"）——
   同时堵住"新事务读到一半就改掉 `s_rbuf`"的窗口。
3. 新状态码 **`I2C_SM_ST_STOLEN = 7`**：结果被后来者覆盖 ⇒ **不得当成功**，由使用者重发/重试。
   SHM 事务区据此回 `IX_STATUS=7`，**但仍然回 `done_seq`**（判据必须能终止）。
4. `i2c_xact_reset()` 要把完成记录**置空**（新纪元不该继承上一轮的"刚完成"）。
   ★ `g_i2c_sm_req_n` 本身**不清**（累计量；清它反而造出"序号回绕"的假象）。

#### 3.7.3 ★★ 资源泄漏：**不要为一个你准备拒绝的请求去占用资源**（2026-09-16 上机实测）

`i2c_sm_request()` 原实现是"**先 `i2c_bus_acquire()`、再校验参数**"，而三条"参数非法"分支
直接 `return 0` —— **不放门** ⇒ **引用计数泄漏** ⇒ `owner` 永久卡在 `SM`、阻塞路径再也拿不到总线。
⇒ 症状（实测）：`0x39 op=22` 读回 `owner=2` **冻结不变**、`refs != 0`，而状态机早已 idle；
**之后所有依赖阻塞路径的判据一起变红**（AS5600 轮询、G6-2 的 G1/G4/G5、G6-3 的 S6），
而错误方向指向"总线被谁占了"，与真因（一次参数非法的请求）相隔很远。
⇒ 修法（结构性）：**先验参、再拿门**。判据：制造一次 `len=9` 的请求 ⇒ `IX_STATUS==5(BADARG)`
且 **`refs == 0` / `owner == 0`**（`0x39 op=22 +32`）。
★ 抓到它的是 G6-2 **专为这类泄漏准备**的 `i2c_bus_refs()` 计数 —— 又一个
"为可解释性加的观测，顺手抓住静默故障"的实例。
★ 一般化：**"成对释放"靠人记迟早会漏** ⇒ 用结构性写法（先验后占），不要靠纪律。

### 3.7.1 ★★★ 为什么"raw 事务协议命令"兑现不了契约的承诺（读源码后定案）

契约 §3.2-C 的原话是："有了 **C 通用事务 op**，'接一个新器件' = **写一段程序**。"
**读源码后确认：这个形状兑现不了那句话。**

| 事实（引自源码） | 后果 |
|---|---|
| ③层（DCL 程序）能做的只有：路由表里 `src → op → dst`，`src/dst` 是 **SHM 槽**（SENSOR/WIRE/ACTUATOR），`op` 是 **19 个原语之一**（`engine.h:758-776`；部署校验 `engine.c:844-850` 的白名单）| **程序没有任何机制"发起一次 I2C 事务"** —— 它只能读槽 |
| 因此加一条 `0x4B I2C_XACT` 协议命令 | 收益落在**上位机/调试工具**，**不是**"程序能用新器件" ⇒ **不构成兑现** |
| `as5600` 现在是**具名设备形态**：驱动读寄存器 → 写 `SENSOR[0]/[1]`（`as5600.c:44-47`）| ⇒ **它已经能被程序用**（`SENSOR x FROM sensor[0]`）。**这才是"程序能用器件"的真实形态。** |

**⇒ 真正能兑现的是「数据驱动的具名设备绑定」**：上位机下发一张表
> "每 N 拍读一次 `设备地址 / 寄存器 / 长度` → 写进 `SENSOR[z]`"

由**拍内状态机**执行（§3.6 的形态）。于是：
- "接一个新器件" = **上传一段配置**（不改固件、也不写代码）✓ **兑现了承诺**；
- 同时天然满足 §1.5 红线 1：**地址在②层的设备描述里，不在程序里** ✓；
- 且复用已有机制：`SENSOR` 槽 + 就绪门 + 总线独占门，**不需要新原语**（不动 `OP_MAX`/`OP_COST`）。

**⇒ 因此：**
1. **`0x4B/0x4C`（raw 事务）若要保留，归入诊断/调试工具**（或并入 `0x39` 脚手架族），
   **不作为契约面** —— 契约面给的是"**设备绑定**"，不是"裸事务"。
2. **G6-5（迁移 as5600）降级为可选**：它的前提被实测否定（§3.6.1）。
   ★ 但**它的副产品有价值**：迁移后 as5600 会**走设备绑定那条路**（同一个拍内状态机），
     于是"绑定表"机制立刻有一个**真实用户**在跑 —— 那是**验证机制**的正确方式（不是自测）。
     ⇒ 若做 G6-4，则 G6-5 应作为 G6-4 的**验收载体**一起做。



### 3.8 ★★★ 具名设备绑定表（G6-4 落法，2026-09-16）—— **"接一个新器件 = 上传一段配置"**

#### 3.8.1 定位（放哪一层）
- **不是** ③层程序的一部分：程序只能读写 SHM 槽（§3.2）。绑定表是 **②层外设能力的配置面**。
- **但它的生命周期跟着 ④层程序包走**（3.8.5）：绑定只在"配合读它的那段程序"时有意义。
- **形态照 `bb_map_bind()`**（`blackbox.c:161-193`）：**打包 u32 条目 + 一次性解析 + 非法兜底 +
  段内范围校验 + 与 PC 共用的表校验和 + 有效槽计数**。
  ★ **唯一差异：本表"上位机可写"**（`bb_map_def` 是 `static const`，改它要重烧核心 ⇒ 那等于"换机器"）。

#### 3.8.2 条目格式（u32，打包）
| 位 | 字段 | 含义 |
|---|---|---|
| [7:0] | `addr7` | I2C 7 位地址（≤0x7F）|
| [15:8] | `reg` | 寄存器地址 |
| [23:16] | `len` | 读取字节数（**1 或 2**）|
| [27:24] | `dst` | 目标 SENSOR 槽（0..15）|
| [31:28] | `dev` | 设备码：**0 = 空槽** · **1 = 通用 I2C 读**（厂商专属、不保证跨平台）|

- 具名设备由**字段组合**表达，不新增设备码：AS5600 RAW ANGLE = `addr7=0x36, reg=0x0C, len=2`
  （**"具名设备"就是它的地址+寄存器**，与 §3.2-B 的 `as5600` 是同一个东西的两种形态）。
- 值转换（确定、可测）：`len=1 ⇒ (float)b[0]`；`len=2 ⇒ (float)((b[0]<<8) | b[1])`（**大端**，与 AS5600 一致）。

#### 3.8.3 提交块（PC 写 / 服务方读）
| 偏移 | 字段 | 写者 | 语义 |
|---|---|---|---|
| +0 | `magic` 'DBND' | 固件启动写 | 区存在自证 |
| +4 | `n_valid` | **服务方回填** | **有效槽数**（登记数）|
| +8 | `crc` | **PC 写** | 条目 8×u32 的 **FNV-1a**（与 `bb_map_sum` 同算法）|
| +12 | `req_seq` | **PC 写** | **单调非 0**；改表后必须递增 |
| +16 | `done_seq` | 服务方写 | `== req_seq` 即本次已生效 |
| +20 | `reject_why` | 服务方写 | 拒绝原因码（3.8.4）|
| +24 | `period_ticks` | PC 写 | 两次**发起**之间的最小间隔（拍；钳 1..1000，默认 10 = 1 ms）|
| +28 | `lanes_ok_n` | 服务方写 | **实际执行**的成功轮询次数（执行数）|
| +32..63 | `entries[8]` | PC 写 | 8 个条目 |
| +64 | `lanes_err_n` | 服务方写 | **轮询失败**次数（**只回答"器件/通信出了什么事"**）|
| +68 | `last_err` | 服务方写 | 最近一次**轮询**状态码（`I2C_SM_ST_*`）|
| +72 | `lanes_skip_n` | 服务方写 | **轮空**次数（总线门忙 / 事务被别的使用者取走 —— **调度现象**）|
| +76 | `rej_n` | 服务方写 | **表被拒**次数（**上传面**；`reject_why` 只给最近一次的**码**，给不了"发生了几次"）|

★ **两个观测量** `n_valid`（登记数）与 `lanes_ok_n`（执行数）—— 照输出面注册表的既有理由：
  要能区分"**没登记**"与"**登记了没跑**"。

★★ **三个计数必须分开（"一个计数只回答一个问题"）**：
  `lanes_ok_n` = 真的执行成功 · `lanes_err_n` = **器件或通信**故障 ·
  `lanes_skip_n` = **调度**现象（总线被占 / 结果被抢） · `rej_n` = **上传面**被拒。
  混在一起时，"err 在涨"这句话**无法解释**（既可能是器件坏，也可能是有人占了总线）
  ⇒ 判据退化成"看看再说"。同族先例：`g_safe_mask_nonzero` 与 `g_safe_mask_oob` 拆成两个量。
  ★ 另注：`reject_why`（`DB_RC_*` 0..8）与 `last_err`（`I2C_SM_ST_*` 0..7）
  **两个码空间数值重叠** ⇒ 必须各占一个槽；混用一个槽时 `last_err=2` 分不出是
  "序号非单调"还是"事务成功"（第一版实现就是这么错的）。

#### 3.8.4 拒绝规则（★ 照 `SRC_HMI` 先例：**不认可就拒绝，绝不静默**）
| 码 | 条件 | 处置 |
|---|---|---|
| 0 | 接受 | 生效 |
| 1 | `crc` 不符 → **"半个表"最危险** | 拒绝，**保持上一次生效的绑定** |
| 2 | `req_seq` 非单调（**回退/重放旧表**）| 拒绝，**且不回退 `done_seq`** |
| 3 | `dev` 非法（> 1）| 拒绝 |
| 4 | `addr7 > 0x7F` | 拒绝 |
| 5 | `len` 为 0 或 > 2 | 拒绝 |
| 6 | `dst > 15` | **不可达（死码）** —— 见下方说明 |
| 7 | 运行期：设备 **NAK** / **SCL 卡死** | **不拒绝绑定**，计入 `lanes_err_n` 并**保留上一次的值** |
| 7* | 运行期：**总线门忙** / 事务**结果被抢** | **不拒绝绑定**，计入 `lanes_skip_n`（**不是 err** —— 见下）|

★ **接受**时也回写 `reject = 0`（"最近一次提交被接受"）—— 于是上位机只需读一个槽就能区分
  "刚被拒"与"刚被接受"，不必依赖别的量（**代价**：`reject` 是"最近一次"的快照，
  **不是**累计量 —— 累计次数看 `rej_n`。一个计数只回答一个问题）。
★ 拒绝时**绝不半装载**（与 §7 闸5 同一条纪律），并把原因码写进 `reject_why` 供外部读走。

★★ **码 6 与码 8 目前是死码，必须如实标注**（`tools/h723_dev_bind_test.py` 的 T4 把它**判为 SKIP 而不是 PASS**）：
  · 码 6：`dst` 只占 `[27:24]` 共 **4 bit** ⇒ 编码层就把值掩进 0..15，`if (dst > 15u)` **永不成立**。
  · 码 8：`req_seq == 0` 在函数入口就被"尚未提交"提前返回挡掉，走不到拒绝分支。
  ⇒ 保留这两条**不是**缺陷（它们是"解码后自检"的冗余层，将来条目格式改宽就自动生效），
    但**不能**把它们当"已验证的拒绝路径"记账 —— 一个永远不触发的判据看起来像"这条很干净"，
    实际是**从没被走到**（本项目对"空判据"的既有教训）。T4 另配了 `addr7=0x7F & dst=15`
  的**正对照**，证明"不是什么都拒"。

★★ **码 2 必须真的实现，不能只留常量**（第一版只留了常量 ⇒ 一个真缺陷）：
  一张**旧表 + 旧序号**字段全合法、crc 也对 ⇒ 只看合法性就会被**无条件接受并整表替换**，
  **把现场打回旧配置**；而没有任何观测量会说"这是一张旧表"（`reject=0`、`n_valid` 合法、
  `done_seq` 跟上了）。⇒ 判据 = **有符号差** `(int32_t)(req_seq - done_seq) < 0`（天然处理 u32 回绕）。
  ★ 回退被拒时**不回 `done_seq`**：它代表"当前已生效的最新号"，回退它会破坏单调性；
    上位机只须看 `reject != 0 && done_seq != req_seq` 即可判定并**终止等待**。
★ **拒绝也必须回 `done_seq`**（`req_seq == done_seq` 是上位机的"已处理"判据）——
  否则上位机分不清"还在等"与"被拒了"，判据永远等下去（**判据必须能终止**）。
  ★★ **唯一例外 = 码 2（序号回退）**：那时**不能**回 `done_seq` —— 它代表"当前已生效的最新号"，
  回退它会把单调性一起破坏。上位机对该情形用 `reject != 0 && done_seq != req_seq` 判定。
  （这两条**字面上看着冲突**，所以这里显式点明边界；契约的自相矛盾会让下一个照它改的人改坏。）

#### 3.8.5 生命周期：**随程序包走** ✅ **已落地（2026-09-16，GAP-11）**

**落法**：绑定表作为**载荷尾部一段 48 B**（不是扩副本头 —— 因为副本头有 `hdr_sum` 覆盖结构布局，
扩它会**让所有老副本的校验和失配**；而 `prog_validate` 用 `n < need` 判，**载荷允许尾部扩展**）。
```
段 = [0..3]"DBND" | [4..7] seg_len=48 | [8..11] period | [12..15] fnv(按32位字, over entries[8]) | [16..47] entries[8]
载荷 = [6B counts][routes][params][states][48B 段(可选)]
```
- **无绑定 ⇒ 不附加段** ⇒ 老包（以及"当前没有绑定"的新包）行为与从前**逐字节相同**。
- 附加收益：这一段**白拿"不能漏错"五道闸的全部保护**（帧 CRC16 / 清单 CRC32 / 写后回读 / A+B seq / 装载前重跑静态校验）。
- ★★ **恢复走"与上传同一套校验"**：`dev_bind_unpack()` 把段写回 SHM 后调 **`dev_bind_submit()`**
  （= 上传路径用的同一个函数），段内非法条目会以 `DB_REJECT` 如实报出 ⇒ 闸5 的同款纪律。
- 可观测：`DB_LOAD_OK_N`(+80) 恢复成功数 · `DB_LOAD_BAD_N`(+84) 段坏被拒数（区已扩到 **0x60 = 96 B**）。
- ★ **可自动化验收**：新增 `0x39 op=23 sub=0` = **重新执行开机装载**（返回 `[rc][loaded]`），
  它调的是 `prog_boot_load_apply()` —— **与开机同一条代码路径**（真断电仍需人工做一次）。
  判据见 `tools/h723_devbind_persist_test.py`（上机 **32 PASS / 0 FAIL / 0 SKIP**）。

**§3.8.5 的验收判据（每条都能失败；登记在 `docs/claims.md` 的 `E 3.8.5-*`）**
| # | 判据 | 怎么让它红 |
|---|---|---|
| 1 | 表**从段里**恢复（`n_valid`/`period`/`entries` 逐字段 == 上传前）| 固件不恢复 ⇒ `n_valid=0` |
| 2 | ★★ **反空判据**：先把**活表换成空表**（`period=20`）再重装载 ⇒ "恢复"必须来自段，不可能来自"现状" | 若恢复只是"没动现状"，这条会暴露它 |
| 3 | 恢复后**真的在轮询**（`ok_n` 或 `err_n` 在涨）| 只恢复字段没生效 ⇒ 计数不动 |
| 4 | ★ 老包**不凭空多 48 B**（落盘长度 == `6+(nr+np+ns)*16`）| 恒定附加空段 ⇒ 长度不符 |
| 5 | ★ 段坏但**程序照常装载**（绑定表不是程序正确性的必要条件）| 段坏连程序一起拒 ⇒ 红 |
| 6 | 段坏的拒绝**可观测**（`DB_LOAD_BAD_N` +1 且 `DB_REJECT == DB_RC_CRC`）| 静默拒绝 ⇒ 不可观测 |
| 7 | 连发两次 `op=23` **幂等**（表状态一致、`req_seq` 不被打乱）| 每次重装载都动握手 ⇒ 红 |

★★ **本节落地时抓到的一个真坑（值得一般化）**：`dev_bind_unpack()` 第一版每次恢复都
`DB_REQ_SEQ + 1u` 并复用 `dev_bind_submit()`，而 `submit` 在 `req == done` 时**静默 return**
⇒ 上位机若自己维护序号，**第一次恢复后就撞号** ⇒ 之后每条判据都在**旧表**上跑 ⇒
**全假 PASS 且没有任何症状**。
⇒ 修法：抽出 `db_validate_apply(seq)`（上传与装载**共用同一份校验**），
装载走 `seq = 0` ⇒ **绝不触碰 `REQ_SEQ`/`DONE_SEQ`** —— 那两个字段属于**上位机握手**。
★ 一般化：**内部路径不得扰动对外协议的握手状态**；且"共用校验"要共用**校验**，不必共用**握手**。

★ **已知边界（如实标注）**：`0x39 op=23` 与开机走同一函数，但它**绕过了 `sd_init` 与掉电时序**
⇒ 它**不能替代**"真断电重上电"那一次人工验收（`--verify-only` 就是为那一次准备的）。
- 绑定表进 `.dclp` 的 **manifest**；与程序**同批**落 SD 的 A/B 副本；开机装载**一并恢复**。
- 理由：绑定只在"配合读它的那段程序"时有意义；分开存 ⇒ 必然出现"**程序是新的、表是旧的**"
  —— 正是本项目反复栽的"**一个语义两处存放**"。
- 兼容：旧程序包无该字段 ⇒ `n_valid = 0`（无绑定），行为不变。
- ★★ **实现状态（2026-09-16 核对）**：`prog_store.c` / `transport.c` / `manifest` **里没有任何相关字段**
  ⇒ **本节是"契据已写、代码未做"**。当前的绑定表是 **RAM-only、掉电即失**（与 `macro` 的 v0 边界同类）。
  ⇒ 在补上之前，**任何"绑定会持久化"的说法都是错的**；调用方每次上电后必须重新下发。
  （这一条由第二轮独立审计逐文件核对得出 —— 契据与实现不一致**必须显式标注**，
  否则下一个照契据改的人会以为它已经生效。）

#### 3.8.6 执行（谁在什么时候跑）
- **发起**在**主循环**：SM 空闲 + 距上次 ≥ `period_ticks` ⇒ 对**一个槽**发起（**round-robin**）。
- **推进**在**拍 ISR**（G6-1 状态机，跨 ~8 拍）。
- **收尾/写槽**在**主循环**：完成即把值写进 `SENSOR[dst]`。
- ★ 依据 **§3.6.1 的边界**：这是**服务型**动作（10 ms 级轮询、结果只进 SENSOR 槽）⇒ 主循环合规；
  唯一进拍内的是状态机相位推进本身。
- ★ **总线独占门**（§3.6 约束③）与 `as5600` 共用；被占用时本轮**连发起都不发起**，
  本轮机会作废并计入 `lanes_skip_n`（**不是** `lanes_err_n` —— 见 §3.8.3 末段）。
  ★ 为什么"连发起都不发起"：门本身能拒，但硬去撞会**每小时数千次**必然失败，
  且把"总线忙"计成 db 的 err ⇒ 判据退化。写法与 `main.c` 里 AS5600 那处**同源**。

★★ **两条"会静默错数据"的路径（都已在实现里挡住，且各留判据）**：

① **在飞事务期间**不得换表 —— **暂存 + 延后 `done_seq`**。
   换表会同时重置 round-robin 游标，而收尾代码用的是**当时的** `s_idx` 去查**新的** lane 表：
   新表槽数更少 ⇒ 越界读；更多 ⇒ 同一个 `s_idx` 指向**另一个器件** ⇒ 读数写进**另一个** `SENSOR[dst]`。
   两种都**无任何错误迹象**（`reject=0`、计数照涨）。⇒ 收尾之后（旧 lane 已用完、新 lane 尚未被引用）
   才是唯一的换表点；等待**有界**（在飞事务最多 `6+n` 拍 ≈ 800 µs）⇒ 判据仍能终止。

② **事务结果归属**必须核对 —— 只看 `status == I2C_SM_ST_OK` **不够**。
   它只能证明"**有人**跑完了一次全 ACK 的事务"，证明不了"**那一次是我发的**"。
   本状态机只有一个 `s_rbuf`，而使用者有两个（本表与 §3.7 的 SHM 事务区 `i2c_shm_service`）
   ⇒ 另一个使用者**可以在收尾之前插入并完成**，把他的读数留在 `s_rbuf` 里，
   于是按 OK 收尾就会把**别人的数据**写进我的 `SENSOR[dst]`。
   ⇒ 令牌 `i2c_sm_done_req()`（**住在资源处** `i2c_sm.c`，不是在各调用点）：
     发起成功后记下 `my = g_i2c_sm_req_n`；收尾时要求 `done_req == my`，否则**丢弃并重发**
     （计入 `lanes_skip_n`），绝不把别人的值当成功用。
   ★ 这是本项目 §4.5 铁律的又一次应用：**守卫必须住在资源的定义处** ——
     放在调用点会随调用者增多而静默穿透（现在两个，将来三个）。

#### 3.8.7 能力位与自述（★ 三处必须同步，"宣称 = 实现"）
- 新增 **`DCL_CAP_DEVBIND = 0x1000`**（H723 扩展位，与 `DCL_CAP_MACRO` 同款做法）。
  实现字由 `0x0DF7` 变为 **`0x1DF7`**。
- `0x4A DEVICE_DESC` **尾部追加**一块（不改前面任何字节，旧上位机按 `n_dev` 读完就停 ⇒ 逐字节兼容）：
  `[n_devbind=1 u16][槽数 u16][ops 位图 u16 (bit0=通用 I2C 读)][SHM 偏移 u32 OFF_DEV_BIND]`。
- `0x64 SYS_MANIFEST` 增加 **`DEV_BIND`** 与 **`I2C_XACT`** 两个条目（地址 + 字数 + kind）。
- 目的：让上位机**在编译/上传期**就能预检"这台机器支不支持设备绑定、表在哪、几个槽"。

★★ **加能力位这件事本身暴露了一个潜伏缺陷（已修）**：
  工具侧认口原先是 `cap == 0x0DF7` **精确等值**（`h723_client.link_alive()`）⇒ 只要固件新增
  **一位**，**全部工具的认口一起坏**，而症状是"找不到板子"（会把排障引向接线/驱动方向）。
  ⇒ 已改为**必备位掩码**语义：`(cap & expect_cap) == expect_cap`。
  判据：`cap=0x1DF7, expect=0x0DF7` 必须为真；`cap=0x0DF7, expect=0x1000` 必须为假。

## 4. ③ DCL 程序

### 4.1 组成
路由表（≤128 条 × 16B）+ 参数（≤128 × 16B）+ 状态（≤128 × 16B）+（顺序域 ≤8 实例 × 64 步）。

### 4.2 上传协议（**v1 起改为事务式**）

```
BEGIN  [total_len:u32][crc32:u32][manifest_len:u16]
DATA   [offset:u32][chunk...]                       × N
COMMIT [prog_id:u32][prog_ver:u16]
```

★ 为什么要事务式：现行 `0x10` 的**满配载荷刚好等于最大帧载荷**
（`6 + 128×16×3 = 6150 = FRAME_PAYLOAD_MAX`）—— **一个字节余量都没有**，
塞不进版本号/清单/CRC（见 GAP-2）。

### 4.3 程序包 `.dclp`（④层产出，v1 起）

```
manifest:
  prog_id / prog_ver / author / created_at
  min_fw_version          ← 低于此版本 ⇒ 拒绝上传
  required_caps (u32)     ← 缺位 ⇒ **上传期**拒绝
  required_prims[]        ← 用到的原语；核心缺哪个 ⇒ 拒绝
  n_routes / n_params / n_states / payload_len / crc32
program.bin               ← 引擎载荷
source.dcl                ← 可选，源文本
```

### 4.4 装载
开机自动装载持久介质上的程序。**装载时必须重跑"上传时同一套静态校验"**
（现行 10 道门 + `engine_route_validate` 13 项）——**不过就不装载**，并暴露 `prog_state` 原因码。

### 4.5 失效语义（沿用项目已有的好范式）
> **任何"不满足"必须在上传期或装载期失败；禁止在运行期静默给一个恒 0 的合法值。**

（先例：`SRC_HMI` 未实现 ⇒ **下载期显式拒绝**，而不是给恒 0。见 `ARCH-H723.md` §4.3。）

## 5. ④ 程序工程
`.dcl` 源 → `tools/dclc.py` → `program.bin` + `manifest` → 打包成 `.dclp` → 上传。
**编译期就要能查出的错（引脚名、缺能力、版本不符），绝不留给运行期。**

## 6. SD 分区契约（规范）

| 区 | LBA | 写者 | 内容 |
|---|---|---|---|
| `LOGHDR` | 0 | `sd_log` | 日志头（`h[0..15]` + 扩展段含 `LOG_END`） |
| `LOG` | 1 … `LOG_END` | `sd_log` | 黑匣子环形数据区 |
| `PROG_A` | `PROG_A` … `+N-1` | `prog_store` | 程序副本 A |
| `PROG_B` | `PROG_B` … `+N-1` | `prog_store` | 程序副本 B |
| 保留 | … `cap-1` | — | 余量 |

**规则**：
1. ★ **日志的活动范围受 `LOG_END` 限制**（写进日志头扩展段）。
   **旧头无该字段 ⇒ 退化为现状（`cap-1`），行为不变、不毁卡** ⇒ 向后兼容。
2. **每区一个写者**（§9 红线 2）。`LOG` 只由 `sd_log` 写，`PROG_*` 只由 `prog_store` 写。
3. 分区边界**由容量计算、写进头部**，不硬编码在代码里。
4. 程序副本大小 `N = ceil(最大载荷 / 512) + 1`（+1 块放副本头：`magic/seq/crc32/payload_len`）。

## 7. ★ "不能漏错" —— 五道闸（规范）

| # | 闸 | 判据（**必须是能失败的**） | 失败处置 |
|---|---|---|---|
| **1** | 传输层 CRC16（已有） | 帧被篡改/截断 ⇒ 坏帧 | 拒收，报错 |
| **2** | 清单级 CRC32 + `total_len` | 分片重组后长度或 CRC 不符 | 拒绝 `COMMIT` |
| **3** | **写完立即回读比对** | 读回 ≠ 写入 | 该副本作废，**不更新 seq** |
| **4** | **A/B 双副本 + 单调 seq** | 任意时刻掉电 ⇒ 至少一份完整 | 开机取 seq 大且 CRC 通过的那份 |
| **5** | ★★★ **装载前重跑上传时同一套静态校验** | 校验不过 ⇒ 拒绝装载 | **保持旧程序运行**，绝不半装载；暴露 `prog_state` |

★ 每道闸的"对照"（证明它真的会红）：
① 故意改一个字节；② 故意截断一片；③ 在写入缓冲里翻一位；④ 在写 A 的中途断电；
⑤ 手工把卡上程序改坏一位，看是否拒绝装载且 `prog_state` 报原因。

## 8. 判据与实验纪律（与 `.workbuddy/memory/MEMORY.md` §九一致）

1. **观测入口优先级**：系统自带协议/接口 → 无副作用探针 → 外部仪器 → **调试器（最后手段）**。
2. **凡 DWT 派生量，判据必须含"时基在走"**（`0x39 op=7`，Δ=0 判无效）。
3. **能用协议表达的，一律不用 pyocd**；用了必须显式恢复并**核对**已恢复。
4. **每拍必须发生的动作不得挂在分支/主循环里**（主循环一圈实测 **0.37 ms**（2026-09-16 **直接实测**；原 1.28~1.54 ms 是**反推值**，已作废），拍是 100 µs）。

## 9.4 ★★★ 帧归属 v2（GAP-12 closed，2026-09-16）

**问题**（有解码过的现场实例）: v1 应答是 `[0xC1][STS][LEN:2][payload][CRC:2]` ——
**里面没有命令字段** ⇒ 客户端只能"**收到任何合法帧就当应答**" ⇒ 一条杂帧（开机 banner /
上一条的迟到应答 / **另一个进程的应答**）会被当成自己的答案。
实测: 密轮询 `0x22` 读 1 个字时读回的位型是 `0x1DF70200` = **`0x01` 的应答载荷**。
★ 最坏巧合: `0x22` 读 **1 个字** 的应答**也是 4 字节**，与 `0x01` 的**完全相同** ⇒ **连长度判据都分不开**。

**落法（全部只追加，v1 一字不改）**
```
v1 请求 [C0][CMD][LEN:2][payload][CRC:2]       CRC 覆盖 [CMD][LEN:2][payload]
v1 应答 [C1][STS][LEN:2][payload][CRC:2]        CRC 覆盖 [STS][LEN:2][payload]
v2 请求 [C2][CMD][SEQ][LEN:2][payload][CRC:2]   CRC 覆盖 [CMD][SEQ][LEN:2][payload]
v2 应答 [C3][CMD][SEQ][STS][LEN:2][payload][CRC:2]
                                                CRC 覆盖 [CMD][SEQ][STS][LEN:2][payload]
协商    0x05 FRAME_MODE [mode:u8]   1=进入 v2 / 0=回到 v1；能力位 DCL_CAP_FRAME_V2=0x4000
```
**四条必须一起遵守的规则**（都是"不做就会出错"的）：
1. **`0x05` 的应答永远用 v1 帧**（`s_ack_v1_once`）。否则握手无解 ——
   客户端发 `0x05` 时还不知道该按哪种格式读回执。
2. **v2 从"下一帧"起生效**，不是当帧。
3. **帧模式是"逐链路"状态、不是 SHM 域** ⇒ `0x13 RESET` 与上电**都必须显式回 v1**。
   ★ 不复位的后果：设备还在等 v2 帧、客户端已退回 v1 ⇒ **整条链路失联**，
   而症状是"板子不响应"（会把人引向接线/驱动方向）。
4. **序号只回显、不强制顺序**（不做重传窗口、不做重复丢弃）——
   归属是 GAP-12 要的，顺序属下一版；把它做成"强制"会让"连发同一 SEQ"被静默拒绝。

**验收**：`tools/h723_frame_attrib_test.py`（**18 PASS / 0 FAIL**）。
★ 该工具**自己实现 v2 组帧与 CRC**，不调 `h723_client` —— 因为要判的是"固件的 v2 对不对"，
两边共用一份有 bug 的代码会**互相验证**（本项目铁律：两条独立路径对上才算数）。
| # | 判据 | 怎么让它红 |
|---|---|---|
| 1 | ★ 未协商 ⇒ v1 应答与本工具**独立构造**的期望帧**逐字节相同** | 动了 v1 格式 ⇒ 不符 |
| 2 | ★ `0x05` 的应答是 v1（含 `[mode][caps_hi]`） | 回执用 v2 发 ⇒ 老客户端读不懂 |
| 3 | ★★ **陈旧应答可辨识**：连发 A、B 只读一次 ⇒ 必须是 A 的；**把第一条当 B 的核对必须不匹配** | 帧里没有 CMD/SEQ ⇒ 两个方向都无法成立 |
| 4 | ★ 协商**可逆**（回 v1 后与第 1 条逐字节相同） | 回不去 ⇒ 老客户端被打断 |
| 5 | 连发 3 条**同一 SEQ** ⇒ 三条都应答且回显同一 SEQ | 固件偷偷加强制 ⇒ 后两条被拒 |
| 6 | ★ `0x13 RESET` 后用 **v1** 请求能通且 `op=24` 报 mode=0 | 不复位 ⇒ RESET 后链路失联 |

**已知边界（如实标注）**
- **没有重传窗口/重复丢弃**：SEQ 不携带"期望值"，设备不做顺序判定。⇒ 它只解决**归属**。
- **没有"按 SEQ 重排"**：应答顺序仍等于请求顺序（设备是单线程顺序处理）。

**★ 落地时顺带填掉的一个越界风险**：`s_txbuf` 原声明正好 = v1 帧长（payload+6），
而 v2 应答是 payload+8 ⇒ **会越界写 2 字节**。已按 `FRAME_TOTAL_MAX_V2` 声明并加 `_Static_assert`。
（同族："固定缓冲 + 更大的帧"。）
