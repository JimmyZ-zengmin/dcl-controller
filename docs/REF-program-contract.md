## 0. 三条**不可协商**要求

| # | 要求 | 检验方式 |
|---|---|---|
| **R1** | **程序必须能走通信上传，且上传后必须正确** | §7 的五道闸**逐条**有能失败的判据 |

## 1. 分层（规范）

```

├──────────────────────────────────────────────────────────────────────┤
│ ② 外设能力 Peripheral Capability   随①发布, **版本化 + 能力位**        │
│   A 引擎内置: DI / AI / DO / PWM / SD / RTC                           │
│   B 具名设备: as5600 / tb6600 …  (vendor, product, revision)          │
│   C 通用事务: i2c / spi / uart 事务                                   │
├──────────────────────────────────────────────────────────────────────┤
│ ③ DCL 程序 Program       **通信上传 + 持久化到 SD**                    │
│   路由表 + 参数 + 状态 + (顺序域)                                     │
├──────────────────────────────────────────────────────────────────────┤

└──────────────────────────────────────────────────────────────────────┘
```

### 1.1 层间判据（**决定某个需求放哪一层，用这张表，不要凭习惯**）

| 问题 | 放哪层 |
|---|---|
| 它是"**怎么算**"（逻辑 / 连续 / 顺序）？ | **③ 程序** |
| 它是"**和外设怎么说话**"？ | **② 外设能力**（通用事务 op 或具名设备）—— **不是**新驱动 |
| 它需要**新的每拍行为 / 新的实时保证**？ | **① 核心**（必走 A/B + 全套回归） |
| 它只是"**给上位机看的量**"？ | 进 SHM + `obs_anchor()` 登记 —— **不是**加协议 op |

### 1.2 每层的"允许 / 禁止"

| 层 | 允许 | 禁止 |
|---|---|---|
| ① | 改寄存器、改 ISR、加原语、加输出面 | 承载"用户逻辑"；承载"上位机随手要的观测" |
| ② | 被程序**按名字 + 版本**引用 | 让程序直接出现**引脚号 / 总线地址 / 寄存器地址** |
| ③ | 用 19 原语 + 顺序域 + 具名设备 | 直接碰硬件；假设"核心一定支持某个能力"（须声明） |
| ④ | 编译、打包、版本管理 | 把"编译期能查出的错"留到运行期 |

## 2. ① 引擎核心

- **交付形式**：烧录。`bash build.sh`（**零警告闸门** + **ISR 调用树闸门**）→ `pyocd flash`。
- **变更纪律**：任何核心改动必须 ① 配 A/B 对照 ② 跑全部套件 ③ 判据能失败。
- **对外契约**（这三样是核心对外的全部承诺）：
  1. `fw_ver`（现 `DCL_FW_VERSION_H723 = 0x0200`）
  2. **能力位**（现 u16，**v1 起扩 u32**，见 §3.3）
  3. **命令表 + SHM 布局** —— ★ **SHM 布局以 `src/engine.h` 为唯一权威**；
     任何"第二份偏移表"（文档或脚本）都只是引用，**不一致以 `engine.h` 为准**。

## 3. ② 外设能力

### 3.1 ★ 边界定义（**本文最重要的一条**）

> **程序（③层）里不得出现任何物理引脚号、总线地址或寄存器地址。**

这一条同时被三边独立确认：IEC 61131-3（逻辑/硬件两分）·
CODESYS（*"application POUs **never** reference physical I/O addresses"*，物理映射只出现在 I/O Mapping POU）·
Zephyr（*"设备树是硬件信息的唯一真相源，驱动代码不应包含任何具体的引脚号、地址"*）。

**可执行判据**：对 ③层的源文本/产物做一次静态扫描 —— 若出现 `P[A-H]\d+`、`P[E]\d+`、`0x4`/`0x5` 开头的地址字面量 ⇒ **拒绝编译**。

### 3.2 能力的三种形态

| 形态 | 例子 | 程序怎么用 | 新增成本 |
|---|---|---|---|
| **A 引擎内置** | DI(4) / AI(3) / DO(16) / PWM / SD / RTC | 走 `SENSOR` / `ACTUATOR` / `WIRE` 槽 | 改核心（重回归） |
| **B 具名设备** | `as5600`（角度）、`tb6600`（步进） | 按**名字**引用具名槽 | 加一个设备驱动 + 登记 |
| **C 通用事务 op** | `i2c_start/stop/write/read`、`spi_xfer`、`uart_tx/rx` | 在**设备驱动内部**用；若要开放给程序，须标注"厂商专属、不保证跨平台" | 加一条通用原语（一次，长期受益） |

★ **C 是"支持新传感器"的正确答案** —— 有了 C，"接一个新器件"= **写一段程序**，
而不是"改固件 + 重新烧录 + 全套回归"。（本项目 I2C 那次走的是"专用驱动 + 专用诊断命令"，
即形态 B 的临时做法 ⇒ 见 §9 GAP-6。）

### 3.3 每个能力必须具备的身份四元组（照抄 CiA 301 的 `0x1018 Identity Object`）

| 字段 | 说明 |
|---|---|
| `device_type` | 能力类别（对应 CiA `0x1000`） |
| `vendor_id` | 厂商（本平台 = 固定值） |
| `product_code` | 该设备/能力的编号 |
| `revision` | **该能力的版本**（行为变了必须升） |

⇒ **能力位从 u16 扩到 u32**，每一位对应一个 `(device_type, product_code)`，并补 `I2C / SPI / SD / RTC / CAN / ETH`。

### 3.4 新增一个能力的流程（5 步，缺一不可）
1. **判层**（§1.1）—— 能做成 C 就不要做成 B，能做成 B 就不要动 ①。
2. **定义身份四元组 + 占用一个能力位**。
3. **实现 + 加"能失败的判据"**（例如：能力位没置而程序要求它 ⇒ 上传期必须被拒）。
4. **进 `ARCH-H723.md` 命令表/能力位表**（★ 现状：能力位表**滞后**，见 GAP-7）。
5. **在设备描述里登记**（见 §3.5）。

### 3.5 设备描述（我们的 ESI 等价物）
一份**机器可读**的表（JSON 即可），列出：`fw_ver` / 能力位 / 具名设备清单（四元组）/
每个设备可用的槽号或 op 号。**上位机在编译与上传时读它做预检。**

### 3.6 ★★★ 通用事务 op 的**落地约束**（GAP-6 判层结论，2026-09-16）

> 起因：GAP-6 一度被描述为"**由主循环/独立状态机驱动的协议命令**"。
> **那个说法与核心理论冲突**，而且错在一个我们**自己早就写下过答案**的地方。此处定案。

**结论：通用外设事务（I2C/SPI）的正确形态 = 「照 `adc_poll` 的范式，做成拍内每拍推进一步的状态机」**，
不是"主循环里跑一段阻塞事务"。

| 若按"主循环驱动阻塞事务" | 冲突 |
|---|---|
| 无标价、无静态门、无动态门 | ❌ **公理④ 时间预算是一等公民** —— 与当初判 macro 为 B 档（非实时）**是同一条理由** |
| 挂在主循环上（一圈实测 **1.28~1.54 ms**，拍是 100 µs） | ❌ §8-4 / 实验七条"**别把实时量挂到主循环上**" |
| "每拍必须发生"的事务落进分支/服务环 | ❌ **不变量 3**（每拍必须发生的动作不得挂在分支里） |
| 与已有 `as5600` 驱动**共用同一条 I2C 总线** | ❌❌ **公理② 单写者** —— 一条总线两个写者。本项目**已因此栽过两次**（`TIM3` 两个驱动者 → C1；**SD 卡两个写者**：日志从 LBA1 回卷 + `sd_dump_write` 写 LBA3000000）|

**⇒ 四条硬约束（缺一条就是重犯）：**
1. **拍内推进**：状态机在 ISR 里每拍走一步（`PLAN-dcl-standardization.md` §4.4-C 的原话：
   "**前提是先把它从主循环搬走 —— 改成'每拍由 ISR 推进的状态机'或'独立 DMA 驱动的引擎'**"）。
2. **标价 + 预算门**：每步进 `OP_COST`/静态门/动态门（公理④）。
3. ★ **总线独占门**：任何时刻只有**一个** owner 能驱动该总线；`as5600` 这类具名设备与通用事务
   **必须走同一个门**（公理②）。
4. ★ **就绪门**：事务**跨拍** ⇒ 程序面拿到的是"**上一次的结果 + 就绪标志**"，
   **不能假设"发命令即得值"**。照 `adc_poll` 的 `s_adc_ready` 做；跨拍状态用 u32（不变量 7）。

**★ 已有的成功先例（这就是为什么它可行）**：`adc_poll` 处理的正是同一类问题 ——
**单次转换 259 µs > 拍长 100 µs**，做法是"启动 → 等 3 拍 → 读 → 下通道"的**跨拍非阻塞状态机**，
跑在拍内、进预算（`CORE-ENGINE.md` §3.1）。I2C 事务没有任何理由做不到。

**★ 连带项（GAP-6 落地时必须同步处理）**：本约束一旦成立，**macro 的 C 档用途即被替代**
—— `PLAN-dcl-standardization.md` §4.4-C 说的"要先把 macro 从主循环搬走"这件事，
可以由"通用事务状态机"直接承担 ⇒ **macro 的 C 档路线应正式关闭**，§4.4 的三档结论需相应更新。

**⇒ 仍存在的真实取舍（不掩饰）**：事务跨拍 ⇒ **单次读有延迟**（I2C 400 kHz 读 2 B 约数十拍）。
这不违反确定性（延迟有**可计算上界**），但**程序面必须显式处理异步**（约束 4）。
把这条写进契约，是为了避免"看起来能立刻取到值"的幻觉。



## 4. ③ DCL 程序

### 3.7 GAP-6 实施方案与验收判据（`[已定]`，2026-09-16）

**现状事实（已侦察，非推测）**
- 现有 I2C = **位翻转**（`src/i2c_bb.c`），PB10=SCL / PB11=SDA，**已按引脚参数化**
  （`i2c_bb_select()`），事务函数已通用（`addr7/reg/buf/n`）。
- 它是**阻塞**的：`dly()` = 400 次 NOP ⇒ 半位 ≈ 4.5 µs ⇒ **100 kHz**，
  一次 2 字节读 ≈ **250 µs** ⇒ 目前挂在**主循环**（10 ms 节流）。
- 总线当前**健康**：`0x39 op=18` 实测 `tx = i2c_ok = 313404 / err=0 / nak=0`（**31 万次零错误**）。

**实施顺序（★ 关键：状态机必须先行，否则就是违反 §3.6）**

| 步 | 做什么 | 验收 |
|---|---|---|
| **G6-1** | **拍内状态机**（`src/i2c_sm.c`）：把嵌套循环的位翻转改写成**可恢复**的状态机，**每拍推进一个"相位"**（START/字节/REPEAT-START/STOP），每拍周期开销**有界** | 上机：状态机读 AS5600 的 RAW ANGLE **与阻塞路径的值一致**（两条独立路径对上才算数 —— `i2c_bb.h:8` 原文） |
| **G6-2** | **总线独占门**：`as5600` 与通用事务**必须走同一个门**；占用中再请求 ⇒ 明确 BUSY（**能失败的判据**）| ✅ **已完成**：门住在**资源处**（`i2c_bb.c` 的 `i2c_bus_acquire/release`，**带引用计数**），阻塞路径与状态机共用同一道门；`i2c_bb_*` 拿不到门返回 `I2C_BB_ERR_BUSY`、状态机返回 `GATE_BUSY`。判据 `tools/h723_i2c_gate_test.py`（`0x39 op=22` 人工占用使判据**可执行**）**实测 5/5 PASS**：占用期 SM 请求被拒（`gate_n`+1、`busy_n`+1）· 阻塞路径不受影响（`tx` 照涨 `nak=0`）· 释放即恢复（读数与阻塞路径一致）· **占用有界自动释放** · 静息 `owner=0 refs=0`（无引用计数泄漏）。★ 首跑 G2/G5 双 FAIL 暴露真 bug：**单一 owner 无法表达"有几层在用"** —— 阻塞路径 `acquire/release` 成对，`as5600_poll` 一次读就把别人的占用放掉了（> 单一 owner 只能表达"谁在用"）| ✅ **closed** |
| **G6-3** | **SHM 事务区** `OFF_I2C_XACT = 0x7200`（256 B，含 `_Static_assert`）+ `req_seq/done_seq` 握手 | 布局断言通过；`obs_anchor()` 登记 |
| **G6-4** | **协议面** `0x4B I2C_XACT` / `0x4C I2C_STATUS` + **能力位** + **设备描述条目**（身份四元组） | 缺能力位/版本不符 ⇒ **上传期拒绝** |
| **G6-5** | **迁移 as5600 到状态机**（阻塞实现保留为对照路径，直到 G6-1 判据稳定） | 迁移前后 `tx/ok` 与读数一致 |

**本轮的 G6-1 只做"诊断面"**：先用 `0x39` 诊断族（**已声明为临时脚手架、不属架构**）触发与读回，
**不动程序面**。理由：**在状态机被证明之前，不得把它挂上契约面** —— 否则就是把未验证的东西写进契约。

**每拍时间账（必须算清，公理④）**：拍 = 100 µs = 40000 cyc，执行预算 32000 cyc。
状态机按 **400 kHz** 设计（位周期 2.5 µs ⇒ 一位 ≈ 1000 cyc）⇒ **一拍推一个字节**
（9 位 ≈ 9000 cyc ≈ 预算 28%）；AS5600 一次 2 字节读 ≈ **6 拍 ≈ 600 µs**
（现状 250 µs ⇒ 用 2.4× 延迟换"**无阻塞 + 每拍有界**"）。★ 若 400 kHz 上机不稳，
退到"一拍半字节"，代价是延迟翻倍 —— 两者都由 G6-1 的判据裁决，不靠猜。

**★ 必须同时说清的取舍**：状态机让单次事务**跨拍** ⇒ **必须给程序面一个就绪门**
（照 `adc_poll` 的 `s_adc_ready`）。**禁止**让程序假设"发请求即得值"。

## 4. ③ DCL 程序

### 4.1 组成
路由表（≤128 条 × 16B）+ 参数（≤128 × 16B）+ 状态（≤128 × 16B）+（顺序域 ≤8 实例 × 64 步）。

### 4.2 上传协议（**v1 起改为事务式**）

```
BEGIN  [total_len:u32][crc32:u32][manifest_len:u16]
DATA   [offset:u32][chunk...]                       × N
COMMIT [prog_id:u32][prog_ver:u16]
```

★ 为什么要事务式：现行 `0x10` 的**满配载荷刚好等于最大帧载荷**
（`6 + 128×16×3 = 6150 = FRAME_PAYLOAD_MAX`）—— **一个字节余量都没有**，
塞不进版本号/清单/CRC（见 GAP-2）。

### 4.3 程序包 `.dclp`（④层产出，v1 起）

```
manifest:
  prog_id / prog_ver / author / created_at
  min_fw_version          ← 低于此版本 ⇒ 拒绝上传
  required_caps (u32)     ← 缺位 ⇒ **上传期**拒绝
  required_prims[]        ← 用到的原语；核心缺哪个 ⇒ 拒绝
  n_routes / n_params / n_states / payload_len / crc32
program.bin               ← 引擎载荷
source.dcl                ← 可选，源文本
```

### 4.4 装载
开机自动装载持久介质上的程序。**装载时必须重跑"上传时同一套静态校验"**
（现行 10 道门 + `engine_route_validate` 13 项）——**不过就不装载**，并暴露 `prog_state` 原因码。

### 4.5 失效语义（沿用项目已有的好范式）
> **任何"不满足"必须在上传期或装载期失败；禁止在运行期静默给一个恒 0 的合法值。**

（先例：`SRC_HMI` 未实现 ⇒ **下载期显式拒绝**，而不是给恒 0。见 `ARCH-H723.md` §4.3。）

## 5. ④ 程序工程
`.dcl` 源 → `tools/dclc.py` → `program.bin` + `manifest` → 打包成 `.dclp` → 上传。
**编译期就要能查出的错（引脚名、缺能力、版本不符），绝不留给运行期。**

## 6. SD 分区契约（规范）

| 区 | LBA | 写者 | 内容 |
|---|---|---|---|
| `LOGHDR` | 0 | `sd_log` | 日志头（`h[0..15]` + 扩展段含 `LOG_END`） |
| `LOG` | 1 … `LOG_END` | `sd_log` | 黑匣子环形数据区 |
| `PROG_A` | `PROG_A` … `+N-1` | `prog_store` | 程序副本 A |
| `PROG_B` | `PROG_B` … `+N-1` | `prog_store` | 程序副本 B |
| 保留 | … `cap-1` | — | 余量 |

**规则**：
1. ★ **日志的活动范围受 `LOG_END` 限制**（写进日志头扩展段）。
   **旧头无该字段 ⇒ 退化为现状（`cap-1`），行为不变、不毁卡** ⇒ 向后兼容。
2. **每区一个写者**（§9 红线 2）。`LOG` 只由 `sd_log` 写，`PROG_*` 只由 `prog_store` 写。
3. 分区边界**由容量计算、写进头部**，不硬编码在代码里。
4. 程序副本大小 `N = ceil(最大载荷 / 512) + 1`（+1 块放副本头：`magic/seq/crc32/payload_len`）。

## 7. ★ "不能漏错" —— 五道闸（规范）

| # | 闸 | 判据（**必须是能失败的**） | 失败处置 |
|---|---|---|---|
| **1** | 传输层 CRC16（已有） | 帧被篡改/截断 ⇒ 坏帧 | 拒收，报错 |
| **2** | 清单级 CRC32 + `total_len` | 分片重组后长度或 CRC 不符 | 拒绝 `COMMIT` |
| **3** | **写完立即回读比对** | 读回 ≠ 写入 | 该副本作废，**不更新 seq** |
| **4** | **A/B 双副本 + 单调 seq** | 任意时刻掉电 ⇒ 至少一份完整 | 开机取 seq 大且 CRC 通过的那份 |
| **5** | ★★★ **装载前重跑上传时同一套静态校验** | 校验不过 ⇒ 拒绝装载 | **保持旧程序运行**，绝不半装载；暴露 `prog_state` |

★ 每道闸的"对照"（证明它真的会红）：
① 故意改一个字节；② 故意截断一片；③ 在写入缓冲里翻一位；④ 在写 A 的中途断电；
⑤ 手工把卡上程序改坏一位，看是否拒绝装载且 `prog_state` 报原因。

## 8. 判据与实验纪律（与 `.workbuddy/memory/MEMORY.md` §九一致）

1. **观测入口优先级**：系统自带协议/接口 → 无副作用探针 → 外部仪器 → **调试器（最后手段）**。
2. **凡 DWT 派生量，判据必须含"时基在走"**（`0x39 op=7`，Δ=0 判无效）。
3. **能用协议表达的，一律不用 pyocd**；用了必须显式恢复并**核对**已恢复。
4. **每拍必须发生的动作不得挂在分支/主循环里**（主循环一圈实测 **1.28~1.54 ms**，拍是 100 µs）。
5. **一个语义一处存放**；一个常量一个语义；一个 SHM 槽 / 一张卡**一个写者**。
6. 判据必须能失败，并配对照证明它会红。

### 9.1 ★ 实施过程中挖出并修掉的四个真 bug（**留档，因为它们是"同族"的**）

| # | 症状 | 根因 | 一般化 |
|---|---|---|---|
| 1 | 整条 SD 路崩（`blk_this_boot=0, batch_err=3099`） | 我按 HAL 骨架重写 `sd_read_block` —— **返回的数据是错的** | **"半个对齐"比不对齐更坏**：换掉骨架之下的数据搬运机制（IDMA→手工排 FIFO）而不同时对齐其前提 |
| 2 | 写超时 `PROG_RC_WRITE` | 缓冲在 **DTCM**，而 SDMMC 的 **IDMA 读不到 TCM 端口** | 外设 DMA 能到哪块内存是**按外设**成立的，不能按"上次那个能"类推 |
| 3 | 读回的载荷头是 `BBLOG_REC_MAGIC "DLBK"` | 缓冲地址撞进黑匣子环（`BB_SLOTS` 512→960 ⇒ 环 240KB 铺满 AXI 中部） | **"当前完全空闲"这类注释活不过两周** ⇒ 容量断言要么 `_Static_assert`，要么集中成唯一地图 |
| 4 | 正常批写被判超时 | `SD_TMOUT_DATA` 被我往小里挤（200 万 ≈ 250ms） | **"超时给够 + 调用方声明阻塞窗口"** 才是正解；挤超时是用判据掩盖慢，会连带杀掉正常路径 |

★ 另外两条**方法学**教训（已写进 `memory/` 与用户级 memory）：
- **`pyocd halt` 会把核留在停住状态** ⇒ 一连串"tick 冻结/ISR 死了"的结论全是假的。`0x48` 的应答本身就带计数，**根本不需要 SWD**。
- **构建闸门不要用管道把门**（`build.sh | grep && flash`）—— `grep` 的退出码掩盖构建失败，会烧旧镜像。
