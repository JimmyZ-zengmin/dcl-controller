## ★ 方法论 (写进 README 与 skill)
- **频率/时序类结论必须用 LA 外部证据** —— SWD 在 CPU 跑不住时会失步,
  会给出完全错误的结论 (曾据此误判"300~340MHz 断崖", LA 实测 450MHz 正常)
- 用 SWD 读"运行态"寄存器前**不要先 reset** —— `pyocd reset halt` 会把 RCC 打回复位默认值
- 测频工具判据: 跳变数 < 200 一律判"没在跑"(否则少量跳变也会算出"正确频率")

### ★★ 关键发现: flash 常驻 ISR 成本被"代码布局/取指"主导

- ★**权威标定**: 拍周期 40000 cyc ÷ LA 实测 100.0000us = **400.00 MHz**
  → 内部计数频率被外部仪器独立确认 (比 nop 循环硬得多)

## 阶段 2 完成 (提交 5ef63c3) — ITCM/DTCM 落位 + 路由扫描 + 同镜像 A/B

### ★★ 核心结论 (阶段 1 的假设被证实)
同一份 **2136 B 逐字节相同**的扫描机器码 (一个宏实例化两次, `-fno-ipa-icf` 保住),
**同一次上电 / 同一个调用点 / 运行时选择器切换**:

| | FLASH | ITCM |
|---|---|---|
| 单条路由 (全DIRECT) | 203.6 cyc | **56.0 cyc** |
| 128 条全表扫 | 26229 cyc (占拍 **65.8%**) | **7225 cyc (18.3%)** |
| 128 条 19原语混合 | 38923 cyc (占拍 **98.9%** 近锁死) | 11419 cyc (29.0%) |
| 128 条 全PID | — | 15275 cyc (44.8%) |

- 空拍外壳: ITCM **44 cyc** vs FLASH **160 cyc** (3.6×)
- 单条路由 56.0 cyc = 140ns (对照 S3 234 cyc = 975ns → 快 7 倍)

### ★ 关键实验一: I-cache 对照 (决定性, H7 复位默认 IC 关闭)
- 开 IC 后 FLASH 26229 → **8164** (3.2×);  ITCM 7225 → **7225 (逐位相同)**
- ⇒ FLASH 成本取决于**引擎不控制的全局状态变量** (cache 内容);
  ITCM 与该状态无关。即使开着 cache, FLASH 仍 62.69 cyc/条 > ITCM 56.02
- ★诚实边界: 本微基准工作集 2136B 完整装进 16KB L1I, 所以**这次没测到 cache 抖动**
  (所有组 min==max)。ITCM 的价值是"把依赖整个移除", 不是"实测到抖动"

### ★ 关键实验二: 同一 flash 函数换个地址成本变 5%
- `ISR_ITCM` 编译期开关做外壳 A/B; 顺带发现 `engine_scan_flash` 地址从
  0x08000660 → 0x080008B0 (挪 0x250B), 同一份机器码 26229 ↔ 24986 (±5%)
- ⇒ 正面证实阶段 1: **flash 常驻热代码的 WCET 无法预算**

### ★ 拍周期: 11 组全部极差 0 (含占拍 98.9% 那组)
- 引擎占满 98.86% 拍, 下一拍入口时刻一位不差 ⇒ 硬拍与负载完全解耦
- LA 外部复核 (满载 98.9%): 100.0000us, 众数 96.1%, 极差 63ns(=LA 量化极限)
- ★之前看到的 11~23cyc 极差来自 ICIALLU/DSB 那一拍的一次性扰动;
  `g_per_cyc_*` 改为**按组复位**后消失

### ★ 可复现性: 两次独立上电跑完整矩阵, 所有 eng_min 逐位相同

### ★ 踩坑 (5 个, 已写进 README 纪律 7~10 + 代码注释)
1. ★★**指针相等的自检会被 GCC 折叠**: `(uintptr_t)g_shm != (uintptr_t)_shm_start`
   被折成恒返 0 (minimal repro in `.tmp/t.c` 确认, GCC 7.3.1 -O2)。
   原因: C 标准保证不同对象地址不同 → GCC 无需知道数值即可判定不等。
   修法: 取值路径过 `volatile`; 权威比对交给外部工具 (本项目两者都做)
2. **`--gc-sections` 吃"只被静态初始化"的全局**: `g_isr_itcm` 只在声明处赋值 →
   整段被回收, 符号消失。`__attribute__((used))` **只挡 GCC 层, 挡不住链接器** →
   必须在代码里真读/真写一次
3. **`pyocd read32 ADDR LEN` 的 LEN 是字节不是字** (`read32 0x0 256` → 64 字);
   且输出带 ASCII 转储列 → 正则必须先按 `|` 切掉 (加 `$` 锚点会一行都匹配不到)
4. **清统计与写配置的时序**: "先清统计再写 gate" → 中间夹进的拍把 `isr_min`
   污染成另一个配置的值 (实测差 ~26000 cyc)。正解: 先定 gate → sleep 30 → 再清
5. **多字变量 (u64 sum) 必须逐字读** —— 少读一个字让整条解析链错位

## 19:0x-19:4x H8 闭环: flash 落位机制实测坐实 (提交 09c05ef)

### 手段
- `-DSCAN_FLASH_PAD=N`: 在 engine_scan_flash 之前插 N 字节填充
  (链接脚本新增 `.scan_pad` / `.scan_flash` 两专区; .scan_flash 独占一段)
  → **只挪地址, 不改一条指令** (段大小 16 次恒 2136 B)
  → ITCM 版 VMA 固定 0x0 作控制组
- 工具加 `--sweep` (4 组快跑) / `--json` (供批量汇总)
- `tools/h723_pad_sweep.py`: 一键 构建+烧录+测量+汇总 (默认 10 点 ≈3 分钟)

### 结果 (16 次独立构建)
| | min | max | 极差 |
|FLASH·全DIRECT | 24957 | 28827 | 3870 = **15.5%** |
|FLASH·混合 | 36967 | 41500 | 4533 = 12.3% (拍长 40000 → 一个落点 **103.8% 超载**) |
|ITCM 控制组 | 7225 | 7225 | **0** (16/16 逐位相同) |

### ★★ 成本 = f(addr mod 32), 周期 32 字节
8 个同余类各取两个独立样本 (地址相差恰好 32B), DIRECT 与混合读数**都逐位相同**:
%32=16 → 24957/24957 · 12 → 26056/26056 · 0 → 26229/26229 · 8 → 26385/26385
%32= 4 → 27818/27818 · 28 → 28043/28043 · 24 → 28553/28553 · 20 → 28827/28827
解释: H7 flash 读通路 **256 位 = 32 字节一条**, 跨界循环体每轮多付一次取指请求
(本页只声称"是 addr mod 32 的确定函数"; 256 位解释与手册一致但需厂商级取指计数才算坐实)

### 工程推论 (比"ITCM 更快"重要) + 交付现状

② "编译过 + 实测跑得动"不是证据 —— 16 落点里 1 个超载, 换构建可能翻面
③ 热代码进 ITCM 从"优化"升级为**设计前提** (ITCM 侧误差项为零)
