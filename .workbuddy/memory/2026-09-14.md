## 1. ★★★★★ 抖动三方对照实验 —— 根因定位：MDMA 影子锁存每拍覆盖 GPIOE_ODR

### 实验目标（用户提出）
测"引脚信号变化的时刻与时钟的误差"，**同时**要三样：
① LA 抓引脚内容并核对 ② 固件侧测"写引脚时刻"的抖动 ③ LA 测引脚边沿抖动。

### 接线（官方原理图 PDF 核对 + 用户确认丝印无误）
| LA | 板子 | U10 脚号 |
|---|---|---|
| CH0..CH6 | PE0..PE6 | **21 / 24 / 20 / 17 / 18 / 15 / 16**（★ 左右列交错，中间夹 PB8/PB9）|
| CH7 | PA8 | 47 |
★ **CH340 串口变成了 COM14**（原 COM18）—— 接线拔插导致重新枚举。
★ **官方芯片引脚号 ≠ 排针孔序号**（LQFP144: PE2..PE6 = 芯片脚 1..5, PE0/PE1 = 141/142, PA8 = 100）。

### ★★★ 根因（链条完整，已自证）
**`do_latch_init()` 把 MDMA ch0 配成 `SHM 的 OFF_DO_SHADOW → GPIOE_ODR`，触发源
`DMA2_S0_TC` ⇒ 每拍搬一次。而 `GPIO_MASK=0` 时 `do_poll` 早退、从不更新 shadow
⇒ shadow 恒 0 ⇒ 每拍把 GPIOE_ODR 覆盖成 0。**

⇒ 症状：ISR 里写的码型**在下一个拍边界被抹平**，引脚上只剩极窄脉冲
（LA 侧表现为"疑似噪声的随机跳变" —— CH0 有 1210 个跳变而非 0，正是"写-清"竞态产物）。
★ 这是**"两个写者写同一个寄存器"**的典型，与 `do.h` 文件头警告的"macro 不要写 PE"同族
—— 只是这次的第二个写者**藏在 MDMA 里**，代码里看不到。

**修法**：开启诊断时**停 MDMA ch0**（写 `0x5200004C` = 0）⇒ 实测 **ODR == val，6/6 完全一致** ✓

### 新增诊断命令 `0x39 PIN_PATTERN`
- `[op:u8]`：0=关 / 1=开(清统计 + **停 MDMA**) / 2=读回
- 开启后**拍 ISR 内**往 PE0..PE6 输出 `g_tick_count & 0x7F`（0..127 递增），并记录
  "写 BSRR **之后**"的 DWT 时刻（相邻间隔 min/max）—— 量的是"**写引脚的时刻**"；
  与 LA 测的"引脚真实边沿"是**两个量**，两者之差 = 寄存器→引脚的延迟（本次想首次量化）。
- op=2 应答 40B：on/wr_n/min/max/last/val + **ODR低8位 / MODER低16 / AHB4ENR + 自写自读**

### ★★★ 方法论教训（两条，都是"观测欺骗/改变被测对象"）
1. **pyocd 在 `connect_mode=halt` 下读 AHB4 外设寄存器不可信**：
   GPIOA/E 读回 `0xABFFFFFF` / `0xFFFFFFFF`、`RCC_AHB4ENR` 读回 0 —— **全是垃圾**。
   （★ 这**正是**项目纪律里记过的那条，我又踩了一次。）
   ⇒ 判"写入是否生效"必须**固件自读 + 协议上报**，不能靠调试器。
2. **"板子在复位循环"是测量假象**：我每执行一次 `pyocd ... -c go` 就复位一次板子，
   于是"启动次数 9→10→11 一直涨"。**纯串口观察 ⇒ 启动次数恒定 18 ⇒ 根本没复位。**
   ⇒ 读运行期状态**必须用不改变状态的通道**（铁律 0）。

## 3. ★★★★★ 持久测试（60 s，不用 LA）：81.7 万样本零异常

### 动机
用户要求"测板子引脚出现毛刺的数量，先搞 1 min"。**不用 LA** ⇒ 只能用固件。
★ 概念澄清（必须写在前面）：**固件测不到"引脚上的电气毛刺"**（那是接线拾取的外部现象），
但能测**拍间隔异常** —— 而 LA 侧看到的毛刺恰好表现为"异常短的间隔"，所以这是可行替代。

### 实现（`0x39` 应答扩到 64 B）
把 min/max 升级为**五档直方图**（正常拍长 40000 cyc，±100 cyc = ±250 ns 为正常带）：
```
b_short : < 39000        b_low  : 39000..39899
b_ok    : 39900..40100   ← 正常带
b_high  : 40101..41000   b_long : > 41000
```
★ 动机：**一个极端样本就能把极差拉成几万 ns，而看不见它有多少个** ——
分档同时回答"多严重"与"多频繁"。这是 LA 那次（0.117% 毛刺把极差从 166 ns 拉成 50 µs）的固件版修法。

### ★ 结果（60 s，817318 次写）
```
wr_n = 817318  (= 81.7 s × 100 µs/拍)

<39000            0        0.0000%
39000-39899       0        0.0000%
```

### ★★★ 结论（这条把之前"尚未收口的矛盾"解决了）
| 测量面 | 异常率 | 说明 |
|---|---|---|
| **固件侧**（写寄存器时刻）| **0 / 817318 = 0.0000%** | 81.7 万样本零异常, 极差仅 175 ns |

★ 这独立证实了 09-11 报告里"PA8 上的窄毛刺（不是固件输出）"的判断。
★ 同时说明：**之前那个"固件 min/max = 145 ns"应改用稳健口径**

  （不是毛刺），两边现在可以对齐了。

## 4. ★★★ 追问"175 ns 是不是问题" —— 精细分档给出答案

### 用户的质疑（问得对）
"极差只有 175 ns 这个不是问题吗？"

### ★ 先纠正概念：**极差 ≠ 典型抖动**
81.7 万个样本里只要有 2~3 个偏离，极差就成了那个数。原来的正常带设成 **±250 ns 太粗**，
能报出极差却**看不出典型值有多集中** ⇒ 收紧到 **±25 ns** 重测。

### ★ 结果（60 s，620041 个样本）
```
< -100ns (严重短)   3       0.0005%   ← ★ 175ns 的极差就是这 3 个造出来的
-100..-25ns         483     0.0779%
★ ±25ns 正常带       619061  99.8419%   ← 99.84% 集中在这里
+25..+100ns         494     0.0797%
> +100ns            0       0.0000%
极值 min=39959(-102ns) max=40029(+72ns) 极差 175ns
```

### ★★★ 结论：**175 ns 是「偶发极值」，不是「持续抖动」**
- **典型抖动：>99.84% 落在 ±25 ns 内**（高度集中）
- 偶发：0.16% 在 ±25~100 ns；**只有 3 个样本 >±100 ns**
- ⇒ **极差 175 ns 完全由那 3 个样本决定**，不代表系统常态

### ★ 那 ±25 ns 本身是问题吗？—— 要看它在设计里的位置
**DCL 的核心设计原则就是"计算随便抖，输出由硬件在固定节拍锁存"**：
- `SHADOW_GPIO` 的写入**无 timing 要求** ⇒ CPU 这 ±25 ns **不进入输出指标**
- 引脚的真实输出时刻由 **DMA 锁存**决定 ⇒ LA 实测 σ ≤ 12 ns（量化极限）
⇒ **这个 25 ns 不是缺陷，是设计允许的**（README"零抖动方案"的立足点）。
★ 但**我们这次实验停掉了 MDMA**（为了拿到 PE 输出），此时是 CPU 直写 ——
  那种模式下 ±25 ns 会传到引脚；**交付配置（MDMA 锁存）不会**。

### 工具改进（已提交）
`0x39` 的分档阈值从 ±100cyc(±250ns) 收紧到 **±10cyc(±25ns)**，并保留 ±40cyc(±100ns) 档
⇒ 一次就能区分"典型抖动"与"偶发极值"。★ 这是"分档比 min/max 有信息量"的实证。

## 5. ★★★★★ 用户纠错：不该停 MDMA —— "那是我们的灵魂"

### 用户的批评（完全正确）
> "怎么可以把 MDMA 停了呢？你不知道我们原先的输入计算，计算结果打包，
>   硬件定时器触发搬运输出是我们的灵魂吗？怎么可以关掉测试"

### ★ 我的原则性错误
为了让 PE 显示码型，我**直接写 `GPIO_BSRR`**，并为了绕开"MDMA 每拍把 ODR 覆盖成 0"
而**把 MDMA ch0 停了**。这等于：
- **把"计算与输出解耦"这条核心设计原则关掉**（TIM 触发 → MDMA → GPIO 硬件锁存）
- 然后拿"关闭后的结果"当数据 ⇒ **先把被测对象拆掉再测它**

### ★★★ 正确修法（已改）
**真正的问题只是"影子缓冲是空的"** —— `GPIO_MASK=0` 时 `do_poll` 早退、从不写 shadow
⇒ MDMA 每拍搬 0。所以：
1. **诊断改为写 `OFF_DO_SHADOW`**（不是写 BSRR）—— 让 MDMA 照常搬运
2. **`0x39 op=1` 改为"确保 MDMA 使能"(EN=1)**，不再停它
⇒ 测的才是**交付配置**。

**验证（影子锁存链路正常，6/6 完全一致）**：
```
val(写进shadow) ODR(MDMA搬来的)
87  (0x57)      0x57 ✓      114 (0x72) 0x72 ✓
124 (0x7C)      0x7C ✓      58  (0x3A) 0x3A ✓
88  (0x58)      0x58 ✓      116 (0x74) 0x74 ✓
```

### ★ 交付配置 vs CPU 直写（60 s 各一盘，样本均 ~62 万）
| | **交付配置**（写 shadow + MDMA）| CPU 直写 BSRR（**错误做法**）|
|---|---|---|
| ±25 ns 内 | **98.7884%** | 99.8419% |
| ±25~100 ns | **1.2110%** | 0.1576% |
| > ±100 ns | 0.0006% | 0.0005% |
| 极值 | min=-118ns / max=+98ns（极差 215ns）| min=-102ns / max=+72ns（极差 175ns）|

### ★★★ 结论：交付配置下"写影子时刻"的抖动**反而更大**，而这**不是缺陷**
- **原因**：写 `BSRR` 是**外设写**（AHB4，路径固定）；写 `SHADOW` 是 **AXI 内存写**
  ⇒ 会与 **MDMA 搬运**及其它总线主设备**争抢 AXI** ⇒ 时刻更飘
- **★ 但这正是"解耦"存在的理由**：`SHADOW` 的写入**无 timing 要求**，
  引脚的输出时刻由 **MDMA 硬件锁存**决定，与 CPU 何时写完影子**无关**
  ⇒ LA 实测引脚 σ ≤ 12 ns（量化极限）与此 1.2% 的写时刻抖动**可以并存且不矛盾** ✓
- ★ 这条对比是"**计算与输出解耦**"价值的**直接实证**：
  同一系统里，软件侧抖动 1.2%、硬件锁存后的输出抖动 < 量化极限。

## 6. ★★★★ 交付配置下的**引脚**抖动（16 MS/s, MDMA 锁存生效）

### 用户的关键追问
> "你测试到的是写影子的抖动？**我要的是引脚得到的抖动**，怎么做"

★ 回答：**固件测不到引脚电平**（CPU 只知道自己写了什么）⇒ **引脚抖动只能用外部仪器（LA/示波器）**。

### 采集（24 MS/s 失败 ⇒ 降级到 16 MS/s 成功）
- **24 MS/s + 2 通道：仍 ReadTimeout**（设备状态累积，原版 Logic 特性）
- **16 MS/s + 2 通道：成功** ⇒ 1912 个跳变

### ★ 结果
```
PE0 引脚(经 MDMA 锁存):  中位数 100.000000 µs   σ 62.23 ns   极差 375 ns   离群 0
PA8 引脚(CPU 直写):      中位数 100.000000 µs   σ 29.45 ns   极差 250 ns   离群 0

16 MS/s 量化网格 62.5 ns ⇒ 量化理论 σ 18.0 ns
```

### ★★★ 反直觉的发现：**MDMA 锁存路径的抖动比 CPU 直写更大**
| 通道 | 输出路径 | σ | 扣除量化后真实 σ |
|---|---|---|---|
| **PA8** | **CPU 直写**（`pin_set` 在 ISR 内固定位置）| 29.45 ns | √(29.45²−18²) ≈ **23 ns** |
| **PE0** | **MDMA 影子锁存**（定时器触发 + DMA 搬运）| 62.23 ns | √(62.23²−18²) ≈ **60 ns** |

**⇒ "解耦"在这个配置下并没有把输出抖动变小，反而更大（60 ns vs 23 ns）。**

★ 可能机制（待验证，不要当成结论）：
  MDMA 的触发链是 `DMA2_S0_TC → MDMAMUX → MDMA 搬运`，其**触发/仲裁延迟本身有抖动**，
  且会与其它 AXI 主设备（ADC/DMA、CPU 取指）**争抢总线** ⇒ 锁存时刻反而比"CPU 直写外设寄存器"更飘。
  （CPU 直写 AHB4 外设是固定路径，不经过 AXI 仲裁。）

### ★★ 与旧版本"输出抖动 < 10 ns"的关系
**本次实测 60 ns，与那个"<10 ns"差了 6 倍** ⇒ **独立佐证了旧结论站不住**
（旧版无实测记录；本线用外部仪器测出的是 60 ns 量级）。

### ⚠️ 但这次的分辨率**不够**
- **16 MS/s 的量化网格 = 62.5 ns**，而 σ 就是 62/29 ns ⇒ **σ 只有 1 个网格的量级**
- ⇒ **要给出可信结论必须回到 24 MS/s**（网格 41.7 ns），或更少通道换更高采样率
- ⇒ 现在 24 MS/s 失败（设备掉线/状态累积）⇒ **需拔插 USB / 重启 Logic2 后重采**

### 待办
1. **拔插 LA 后重采 24 MS/s**（2 通道），确认 PE0 σ 是否仍是 ~60 ns
2. 若确认 ⇒ 这是一个**重要结论**：本平台的 MDMA 锁存路径**没有**优于 CPU 直写
   （与设计预期相反，需要查 `do.h` 的"TSEL 触发待调"那条遗留项）
3. 若要真正对比"解耦收益"，应同时测 **影子写时刻（固件）** 与 **引脚边沿（LA）** 并给出关系

## 7. ★★★★★ 机制定位：MDMA 触发链是**七级串联**，且与 ISR 在拍边界**同时争总线**

### 用户的机制推断（正确，且比我的"AXI 仲裁"泛论精确）
> "100us 内，输入采样有留时间，计算有留时间，输出也有留时间，
>   **唯一可能有问题的应该是输出后的时间没有留时间空闲**，
>   也可能有其他的机制在争抢，比如 sd 记录运行数据"

### 代码核实（`do.c` 的 `do_latch_init()`）
```c
DMAMUX1_C8 = DMAMUX_REQ_TIM2_UP;   /* ① 请求源 = TIM2 更新事件(拍边界) */
DMA2_Stream0: P2M + CIRC + 1 个字  /* ② 哑传输(绝不动外设), TC 脉冲输出 */
DMA2S0_CR = TCIE|DIR=P2M|CIRC|word | EN
MDMA ch0 节点:
  nd[2] CSAR = SHADOW        nd[3] CDAR = GPIOE_ODR
  nd[6] CTBR = MDMA_REQ_DMA2S0_TC | SBUS   /* ③ 等 DMA2_S0 完成 */
  nd[5] CLAR = 指回自身 ⇒ 链表循环(EN 常开, 永续)
```

### ★★★ 完整触发链 = **七级串联**
```
TIM2 更新事件(拍边界)
 → ① DMAMUX1 路由
 → ② DMA2_S0 搬 1 个字
 → ③ 传输完成(TC)
 → ④ MDMAMUX 路由
 → ⑤ MDMA 搬 4 字节
 → ⑥ 写入 GPIOE_ODR
 → ⑦ 引脚翻转
```
**每一级都要过总线/仲裁** ⇒ 抖动**逐级累积**。
而 CPU 直写 GPIO 只是**一条 store 指令**（走 AHB4 固定路径）⇒ 这解释了 **60 ns（MDMA）vs 23 ns（CPU 直写）**。

### ★★★ 用户指出的关键："输出后的时间没有留时间空闲"
```
拍边界(TIM2_UP) 到来
   ├─ 硬件侧: DMA2_S0 → MDMA → ODR   ← 要抢总线
   └─ 软件侧: ISR **立刻**开始执行     ← 取指/访存也抢总线
        ⇒ 两者在拍边界**同时发生** ⇒ 争抢 ⇒ 7 级链被拖长
```
⇒ **不是"锁存机制不好"，而是"锁存链与 ISR 争同一段总线时间"**。
★ 用户还提到 **SD 记录运行数据**也会参与争抢（`sd.c` 用 SDMMC 的 IDMA）。

### ★ 可验证的改进方向（未实施）
1. **错开时间**：把 MDMA 触发点从"拍边界"移到拍内某处（避开 ISR 启动窗口）
   —— 但触发源是 `TIM2_UP`，要换触发需改 `DMAMUX1_C8` 的请求源（如 `TIM2_CC4`）
2. **降争抢**：关掉 SD 日志 / 限制其它 AXI 主设备，看抖动是否下降（**最省事的验证**）
3. **对照实验**：让 ISR 在入口故意空转 N 个周期，若 σ 下降 ⇒ 直接证明是"争抢"而非"链长"

### 待办（优先级）
1. ★ **拔插 LA 重采 24 MS/s** 确认 60 ns（当前 16MS/s 网格 62.5ns，σ 只有 1 格，不够）
2. **关 SD 日志对照**：同一采集下比对 σ（直接验证"争抢"假设）
3. 若确认争抢为主因 ⇒ 再评估"换触发源错开窗口"的收益

## 10. ★★★ 修正版实验："输出后让路"**没有效果**（结论：这条路不通）

### 先修了我自己的一个 bug
第一版忙等写的是 `while ((DWT_CYCCNT - d0) < n) {}` —— **每轮都读 DWT**，
而 **`DWT_CYCCNT` 是 CoreSight 组件、读它要过总线** ⇒ 忙等本身在**抢总线**，
"让路"变成"更加争抢"（那轮数据：基线 58.79 → 延时档 64.93 ns）。
⇒ 改成**纯 NOP 循环**（NOP 在 ITCM 取指+执行，不产生数据访问）。
★ 注意单位随之改变：每轮 ≈ 3 cyc，故 `g_isr_delay_cyc` 现在按"轮数"解释。

### ★ 修正版结果（16 MS/s, 0.5 s, 样本 5300+）
| 延时档 | 通道 | σ(ns) | 扣真σ | 极差(ns) |
|---|---|---|---|---|
| 0 (基线) | PE0(MDMA) | 67.43 | 65.0 | 375 |
| 0 (基线) | PA8(CPU) | 27.79 | 21.2 | 188 |
| **800轮 ~2µs** | PE0(MDMA) | **63.78** | 61.2 | **375** |
| **800轮 ~2µs** | PA8(CPU) | 30.90 | 25.1 | 188 |

### ★★★ 判定：**没有效果**
- PE0 σ 只降 3.6 ns，而**该测量本身的波动就有 ±7 ns**
  （历次基线：52.74 / 58.79 / 62.23 / 67.43）
- **极差完全一样（375 ns）**
⇒ **"把输出后的 ISR 尾巴推后 2 µs" 对引脚抖动无显著影响。**

### ★★ 由此得到的新判断（比原假设更精确）
**如果存在总线争抢，它的位置不是"ISR 后段"，而是"拍边界那一瞬间"** ——
那里有**三方同时**动作：
```
拍边界(TIM2_UP)
  ├─ DMA2_S0 搬 1 字（为产生 TC 脉冲）
  ├─ 这些 TC 立刻触发 MDMA 搬 shadow → ODR
  └─ ISR 同时进入（取指 + 第一次访存）
⇒ 三者抢同一段总线 ⇒ 抖动在**链的头部**产生, 不在尾部
```
⇒ 所以我推"尾部"当然没用。**要验证就该动"头部"**：
- 关 SD 日志（减少 AXI 主设备）
- 或换触发源（`DMAMUX1_C8`: `TIM2_UP` → `TIM2_CC4`），把锁存点整段移出拍边界

### 设备边界（本轮实测）
| 配置 | 结果 |
|---|---|
| 2ch @ 24 MS/s, 0.1 s | ✅ |
| 2ch @ 24 MS/s, 0.5 s | ❌ ReadTimeout |
| 2ch @ 16 MS/s, 0.5 s | ✅（样本 5300+，够用）|
⇒ 16 MS/s 是当前稳定可用的档位；24 MS/s 只适合短采集。

## 11. ★★★ 双时间表落地 + 黑匣子对照（方案①）：**关掉它无效**

### 双时间表（`docs/ARCH-TIMELINE-CPU-MDMA.md`，已提交）
按用户要求"**新建 CPU 调用表 + MDMA 搬运表，让两条时间线不互相干涉**"，
从源代码逐行提取（含行号 + 资源类型）。

**★ 做表时发现两件事：**
1. **干涉的根源是结构性的**：表 B（MDMA 链）的起点 `TIM2_UP` 与表 A（ISR 入口）
   **是同一个事件** ⇒ 两条线**必然在 t=0 相交**，不是"可能干涉"。
2. **ISR 里有**两个** AXI 写手**（之前只注意到一个）：
   - `do_poll`（#8，行 1335）→ 写 SHM 影子
   - **`bb_kick`（#10，行 1404）→ 写黑匣子环形缓冲** ← 第二个，位于"输出之后"

⇒ 第 2 点也解释了为什么"推后 ISR 尾巴"没用：**真正的干涉在 t=0，不在尾巴。**

### 方案①：关黑匣子（去掉 ISR 内第二个 AXI 写手）
新增 `0x39 op=4 [on]` 控制 `g_bb_off`，在 `bb_kick` 调用处早退。

**结果（16 MS/s, 0.5 s, 样本 5500+）**
| 黑匣子 | 通道 | σ(ns) | 扣真σ | 极差(ns) |
|---|---|---|---|---|
| 开（基线）| PE0(MDMA) | 72.09 | 69.8 | 438 |
| **★关** | PE0(MDMA) | **71.81** | 69.5 | 375 |
| 开（基线）| PA8(CPU) | 26.35 | 19.2 | 188 |
| ★关 | PA8(CPU) | 31.41 | 25.7 | 125 |

### ★★★ 判定：**无影响**
**PE0 的 σ 只动 0.3 ns（72.09 → 71.81），样本 5500+ ⇒ 不是波动。**
⇒ **"减少一个 AXI 写手（黑匣子）"对 MDMA 锁存抖动没有帮助。**

### ★★ 由此得到的新判断（指向方案②）
- 抖动**不主要来自**"与 `bb_kick` 的 AXI 争抢"
- ⇒ 剩下两个可能：
  **(a) MDMA 链自身**的固有时延抖动（七级串联，每级的仲裁/同步延迟）
  **(b) 与"ISR 入口那一刻"的争抢**（`DMA2_S0` + MDMA + ISR 取指/首访存同时）
- **方案②（换触发源 `TIM2_UP` → `TIM2_CC4`）正好能区分这两者**：
  - 换了之后 σ 下降 ⇒ 是 (b)，且**两条时间表被真正分开**（用户的目标达成）
  - 换了之后 σ 不变 ⇒ 是 (a)，抖动是链的固有属性 ⇒ 要另想办法（如改用 CPU 直写或缩短链）

### 待办
1. ★ **做方案②**（换触发源）：需要查 DMAMUX1 的 `TIM2_CC4` 请求号 + 配置 TIM2 的 CC4
2. 每档重复 2~3 次确认（本轮已有 5500+ 样本，重复性可接受）

## ★★★ 方案②实测：寄存器全对，引脚不动 —— 并由此推翻"七级触发链"

### 先修掉一个**空判据**（否则后面所有抖动数据都不可信）
现象：`g_ppat_wr_n` 涨到 101 万，而 `min/max/last/first` **全是 0**、五个分档计数**全是 0**。
根因**不是统计代码**（分档条件是穷尽的）：`tp = DWT_CYCCNT` **恒为 0** ⇒
`if (g_ppat_prev != 0u)` 这个门**永远进不去**。
真因是本项目**自己记录过**的陷阱（`modbus.c:79` / `faultlog.h:75`）：
**pyocd 会话退出时调试域断电 ⇒ DWT 寄存器复位 ⇒ `CYCCNTENA` 被清，之后再没人打开它。**
⇒ 新增 `0x39 op=7` = 重新 `dwt_enable()` + 清统计，并**返回两次 CYCCNT 读数**，
   把"时基在不在走"变成**可失败的判据**（`Δ=0` 就判定本次统计无效）。
   实测 Δ=1694 ⇒ 修复后分档立刻有数据（`0/20/3255/21/0`）。
★ 教训：**凡 DWT 派生的观测量，必须配一条"时钟在走"的判据**，否则它是个永远通过的空判据。

### 方案②第一次实现**静默失效**：一个绑定跨了两个寄存器，我只改了一半
`DMAMUX1_C8` 从 22(TIM2_UP) 改成 21(TIM2_CH4) **不够** ——
定时器的 DMA 请求还被 `TIMx_DIER` 逐位门控：`UDE`(bit8) 管 `TIM2_UP`，`CC4DE`(bit12) 管 `TIM2_CH4`。
而 `do.c:176` 只置了 `UDE` ⇒ **切到 CC4 后那个请求根本不会产生**。
修法：`trig_source_apply()` 必须**同时**改路由（DMAMUX）与门控（DIER）。
★ 同族教训对照：以前是"**一个常量两用**"（请求上限≠响应上限），这次是"**一个语义两处存放**"。

### 修好之后：寄存器自证全绿，引脚行为**纹丝不动**
`op=6` 读回：`DMAMUX1_C8=21`、`DIER=UIE,CC4DE`、`SR.CC4IF=1`（CC4 事件确实在产生）。
但 LA 实测 `PE0 − PA8` 相位：sel=0 **+119.7 ns**，sel=1 **+121.6 ns**。
**判据是形状判据**（真移到拍内 50 µs，相位必须变成 ±50 µs）—— 不受噪声/量化影响。

### 用新加的原始注入口做四个"否决性"实验
| 拆掉什么 | 锁存还活着吗 |
|---|---|
| `DMAMUX1_C8=0` + `DIER` 无 DMA 使能位 | **照常工作** |
| `DMA2_S0_CR` 的 `EN` 清零 | **照常工作** |
| `MDMA CTBR.TSEL` 扫 0…15 | **全部照常工作** |
| `MDMA_CH0_CCR` 的 `EN` 清零 | **停** ⇒ 写入者确实是 MDMA |
⇒ **MDMA 不消费任何请求源，它在自己循环。** 所谓"七级触发链"不成立。

### 决定性实验：一拍写两次影子 + NOP 扫掠
| NOP 轮数 | `PE0 − PA8` |
|---|---|
| 0 | +0.12 µs |
| 800 | +3.35 µs |
| 1600 | +6.32 µs |
| 3200 | +12.28 µs |
| **1600 但只空转不写** | **+0.13 µs（不动）** ← 对照 |
斜率 3.9 ns/轮，线性。⇒ **锁存时刻 = CPU 最后一次写影子 + 0.12 µs。**
⇒ **输出引脚时刻由 CPU 决定，定时器对输出时刻没有贡献。**
（"每拍只一个边沿"也解释通了：`pat(T-1)^1` 与 `pat(T)` 的 bit0 相同（+1 会翻转 bit0），
 所以第一次锁存不产生边沿，边沿只出现在第二次锁存处。）

### 其他配套测量
- ISR/`do_poll`/`engine_scan_itcm` 地址全在 ITCM（0xE4/0x25E0/0xC94）⇒ NOP 循环**零总线流量**，
  "刷 AXI 把 MDMA 饿住"的解释不成立 ⇒ 排除"争抢"解释。
- 清 `DMA2_LIFCR` 后 TCIF0 **37.6 µs 内不重现、196 µs 内重现** ⇒ DMA2_S0 约**每拍一次 TC**。
- `PE0 − PA8` 延迟分布：**125 ns ± 45 ns**（尖峰，非均匀 ⇒ 不是自由跑的均匀相位）。
- LA 网格：16 MS/s ⇒ 62.5 ns；24 MS/s ⇒ 41.67 ns（用时间戳整除性反推，**不能**用"最小相邻间隔"猜）。
- Original Logic 的 `wait_capture` 会 `ReadTimeout`，**但数据可能已拿到**；
  不过那种档会出现 37.7/61.1 µs 的异常短间隔（USB 丢数据）⇒ **必须做完整性检查后再用**。

## ★★★★ 架构评估 + 一个**已上传稳定代码里的功能缺陷**：16 路 DO 只有 8 路可用

用户问"作为一个控制器，我们的架构存在什么问题"。评估文档：
`docs/ASSESS-architecture-as-controller-2026-09-14.md`（P0/P1/P2/P3 分级 + 每条给
"证据→影响→建议动作"，并标注 `[实测]`/`[推断]`/`[待核实]`）。**未提交**，等用户先看。

### 评估过程中新发现的硬缺陷（P0-1，`[实测]`）
新加锁存宽度探针 `0x39 op=14`（写影子 → 等锁存 → 读回 ODR），结果：

| 写入影子 | 锁存后 ODR | 判定 |
|---|---|---|
| 0x0001 / 0x0080 / 0x00FF | 同值 | ✓ |
| **0x0100** | **0x0000** | ✗ |
| **0x8000** | **0x0000** | ✗ |
| **0x0101** | **0x0001** | ✗ 高字节被丢 |
| **0xFFFF** | **0x00FF** | ✗ 只剩低 8 位 |

`0x0101→0x0001` 排除了取值巧合 ⇒ **干净的按字节截断**。
根因：`do.c` 把 MDMA 的 `CTCR` 配成 **byte 尺寸**(SSIZE/DSIZE=00) + 地址固定 +
`CBNDTR=4` ⇒ 等于"把影子低字节往 ODR 低字节写 4 遍"。
而 `do.h` 的 `DCL_DO_LATCH` 默认 **1** ⇒ **CPU 的 BSRR 直写通路已被关掉**。
⇒ `DO_COUNT=16` / `PE8~PE15` 在板子上实接出去（HARDWARE-PINOUT 35~44 脚）
   ⇒ **一半 DO 通道永远无法置 1**，且**不报任何错**。
⇒ 本项目"配置全对≠功能可用"的**第 5 次**同族实例。
修法：SSIZE/DSIZE 改 word(32 位)（节点 `nd[0]` 与主寄存器两处）；
验收判据就是 `op=14`：`0xFFFF` 必须读回 `0xFFFF`、`0x0101` 必须读回 `0x0101`。
★ 位域不要照注释推，抄官方 device header 再实测交叉验证。

### 评估里其余要点（详见文档）
- **P0-2** 输出不锚定（MDMA 自循环）⇒ 引脚时刻=CPU 写影子+0.12µs，比 CPU 直写还差 45ns；
  修好后顺带拿到 **P0-3 "输出帧"语义**（全通道同时原子生效）。
- **P1-1** 空判据家族已 4 次 ⇒ 架构级建议：**每个观测量自带 validity 位**；
  评审门："构造不出失败情形的判据不算判据"。
- **P1-3** σ 档间波动 52~91ns（近 2 倍）⇒ 控制器主指标应是 **max（WCET）**，不是 σ；
  `max=40063cyc(+157ns/1.7M 样本)` 才是该进规格书的数。
- **P2-1** 有顺序表、**没有 AXI 资源预算表** ⇒ 三次"分离时间线"全在猜。
  先量 **MDMA 自循环吃掉的 AXI 带宽**（`[待核实]`，关 `CCR.EN` 前后对比协议往返延迟）。
- **P2-2** 安全态完全靠软件 ⇒ ISR 一卡安全输出也下发不了；H7 单核上限 SIL-2；
  建议安全输出走**独立硬件通路**（外部看门狗 + 硬件关断）而不是追认证。
- **P2-3** 模拟量的主要矛盾是**缺模拟前端**，不是 ADC 位数（实测 ENOB≈10.1）。
- **P2-4** EtherCAT 必须走 ESC；Modbus 状态机在硬拍 ISR 内应改为 DMA+IDLE、解析挪主循环。

## ★★★★ P0-1 已修复并验收：16 路 DO 的锁存通路（按"建议顺序"第 1 步）

```
CBNDTR = 2    (两个字节: SHADOW+0→ODR+0 = PE0~PE7;  SHADOW+1→ODR+1 = PE8~PE15)
```

## ★★★★★ P0-2 诊断完成：MDMA 的请求线 `mdma_str[8]` 自己常高

### 权威依据（RM0468，本地 PDF 提取，逐字）
- `§14.5.12 MDMA_CxTBR`（p.610）：`Bits 5:0 TSEL[5:0]: Trigger selection.
  This field selects the hardware trigger (RQ) input for channel x.
  **The ACK is sent on the ACK output having the same index value.**
  When SWRM bit is set, this bit field is ignored.`
  ⇒ **TSEL 是 `mdma_str[n]` 的线号（1:1），只有 6 位（0~33）。**
- `§14.3.3`：MDMA 单次请求搬多少由 `TRGM[1:0]` 选：buffer / block / repeated block /
  **complete channel data（直到 CLAR 为空）**。
- `§14.3.3` 还有一条关键说明：请求若来自 DMA1/DMA2，则"外设寄存器访问被替换为对该 DMA
  所用内存缓冲的访问" ⇒ MDMA 的请求确实可以来自 DMA 流。

### 实测结论（判据全部健全：写0⇒ODR==0 且 写1⇒ODR==1，否则样本作废）
1. **源重定向**：`CSAR` 换成另一块 DTCM 常量(0x2000002C) ⇒ ODR 变成那块常量的值、
   **不再跟随影子** ⇒ **确实是 MDMA 在做 CSAR→CDAR 的搬运**（源说了算）。
2. **目的重定向**：`CDAR` 换成 GPIOB_ODR ⇒ GPIOE_ODR 不再跟随 ⇒ 写入者确实走 CDAR。
   （读回 `CSAR/CDAR` 时低位在递增 ⇒ 读到它时正在搬运当中，自身即是"一直在搬"的证据。）
3. **TSEL 有选择性**：扫 0~33，**只有 `TSEL=8` 会搬**；0/1/5/6/7/9/20/40/63 全都不搬。
   且 CTBR 写入确实生效（回读一致）。
4. **整座桥与它无关**（健全判据下重做）：`DMAMUX1_C8=0` / `DMA2_S0_CR.EN=0` /
   `DIER` 去掉 UDE|CC4DE / 清 `TCIF0` —— **四项全部无效**，延迟都还在 ~120 cyc。
5. `CLAR=0` ⇒ 通道跑完一次**自清 EN**，之后不再搬（与"EN 是唯一开关"一致）。
6. `DMA2_S0` 的 TC 速率 ≈ **10~40 µs**（与 ~300 ns 的锁存延迟差三个数量级，对不上）。

⇒ **`do.c` 注释里的 `TSEL=8 = DMA2_Stream0_TC` 是错的**；"七级触发链"不成立。
⇒ 锁存之所以"随时跟得上影子"，是因为 `mdma_str[8]` 这条请求线**自己就是常高的**，
   与我们在 DMA2/DMAMUX/定时器上做的一切都无关。

### 一个**判据漏洞**（差点再次误判）—— 值得记牢
第一版延迟探针只验了"写 1 ⇒ ODR == 1"，**没验"写 0 ⇒ ODR == 0"**。
当 ODR 卡在 1 时（通道已停），"写 1"会立刻看到 ODR==1 ⇒ **假通过**，还给出很小很漂亮的延迟。
⇒ 因此"清 TCIF0 / 拆桥不影响"的**第一轮排除全部作废**，本轮用健全判据重做。
★ 同族：这就是"判据不能失败 = 判据不存在"的第 N 次实例 —— 这次是**我自己**的判据。

### 修复选项（需要用户决策，因为涉及"灵魂"取舍）
- **A（推荐，最省）**：`-DDCL_DO_LATCH=0` —— 回到 CPU 直写。
  收益：`GPIO_BSRR` **一次 32 位写覆盖全部 16 路**（同样是原子的"输出帧"）、
  σ 26 ns（优于锁存的 60 ns）、**消掉 ~3.5M 次/秒的 AHB4 写负载**与 MDMA 的 AXI 链表流量。
  ★ 关键是：**"输出由硬件锚定"这个性质今天本来就不存在**（锁存也是 CPU 定时的）⇒ **不损失任何东西**。
- **B**：保留锁存但每拍重新武装（`CLAR=0` 一次性 + ISR 置 `EN`）⇒ 仍然是 CPU 定时，无收益。
- **C**：换一个能受控的请求线 —— 扫描显示 0~33 里没有一条跟随 DMA2_S0 ⇒ **桥接思路不可行**。

LA 测引脚有两个硬伤: 网格 62.5ns ⇒ 量化 σ 就 25ns; 而同配置档间 σ 波动 40ns ⇒ 幅度判据不可复现。
⇒ 在固件里累積 **偏差** `e = d − 40000` 的 `Σe` 与 `Σe²` (u64), 用 `0x39 op=16` 读回,
   DWT 2.5ns 分辨率, 上位机算 σ。**两轮读数完全一致** —— 这才叫判据。

| 档 | σ(写入间隔) | 两轮 | min/max 极差 |
|---|---|---|---|
| **1 档** 影子+MDMA锁存 | **5.2 cyc = 13.0 ns** | 5.2 / 5.2 | 94 cyc = 235 ns |
| **A 档** CPU 直写 | **1.4 cyc = 3.6 ns** | 1.4 / 1.4 | 62~75 cyc = 155~188 ns |

★ 口径: A 档那次写**就是写引脚** ⇒ σ 直接是**引脚**抖动(3.6ns);
  1 档那次写只写**影子** ⇒ 引脚还要叠加 MDMA 采样环节(LA 实测 PE0 σ≈60ns / `PE0−PA8`=125±45ns)。
⇒ **引脚抖动: A 3.6ns vs 1 ~54~60ns, 差约 15 倍。**
★ 附带解释: 1 档连"写影子"本身都比写 BSRR 抖 3.6 倍(13.0 vs 3.6ns) ——
  怀疑是 **MDMA 经 AHBS 持续读 DTCM 与 CPU 的 DTCM 写发生仲裁**;
  而 AHB4 的 BSRR 写是 posted write, 时间戳不受后续总线竞争影响。

### 为什么切 0 档**没有功能损失**
- `GPIO_BSRR` 一次 32 位写覆盖 16 路 ⇒ "输出帧"原子性同样成立（已用 `op=14` 验收 9 个向量）
- 输出沿还**提前 ~300ns**（不再等 MDMA 采样）
- 顺带消掉 ~350 万次/秒的 AHB4 持续写 + MDMA 的 AXI 链表流量
- ★ 关键: "输出由硬件锚定"在 1 档**本来就不存在**（P0-2 已证）⇒ **无损失可谈**
