# 2026-09-17 —— 闭环步进 阶段 2：**失速边界与斜坡收益（已证）**

> 接 `2026-09-16.md` 末尾"下一步 = 阶段 2"。那篇记的阶段 0/1 与总根因已完成，本篇只记阶段 2。

## 一、阶段 2 的结论（一句话）

**电机在 1~60 kHz 全频段跟随脉冲的"线性度" ≤0.5%（无随速度增长的丢步）；
但从静止"突加"到 >16500 Hz 必失速** ⇒ **"失速边界"与"斜坡收益"从 ⛔未证 变 ✅已证**（PLAN §4 表已改）。

★ **不许说成"绝对跟随精度 ≤0.5%"** —— 存在一个 **−1.6% 的固定比例因子，归属不可分**：
静态标定 counts/step = 2.6017，而 1/8 微步名义值是 2.56 ⇒ 用 2.6017 算"电机慢 1.6%"、
用 2.56 算"恰好 1.000" ⇒ **分不开"AS5600 角度刻度误差"与"驱动器微步刻度误差"**。

## 四、闭环标定：把结论的两条地基单独量出来（`build/_spr_calib.py`）

全部**零时间假设**（`走 N 步` → `TIM4_CNT` 硬件脉冲 + AS5600 **绝对**角）：

| 判据 | 结果 |
|---|---|
| C2 步/圈 | `counts/step` 中位数 **2.6017 ⇒ 1574.4**（名义 1600，−1.6%），6 行峰峰 **0.91%**，正反对称 |
| C3 脉冲率 | 8000/24000/60000 ⇒ −1.36% / +0.05% / +1.01% |
| **C4 拍长** | **99.95 µs（−0.05%）** ⇒ 100 µs 被**独立反解确认** |
| **C5 频率量化** | `rate_actual = 1e6/floor(1e6/f)`，**7/7 精确命中** |

**★ 新规则（已进 MEMORY §5.16）：脉冲周期被量化到 1 µs。**
反推 ARR = 200000/25000/8200/5000/3200/2400/2000 —— **全是 200（=1 µs@200 MHz）的整数倍**。
⇒ 24000⇒24390(+1.62%)、60000⇒62500(+4.17%)、80000⇒83333(+4.17%)。**周期整除的档精确**。
⇒ **用频率做定量结论必须引 `rate_actual`，不要用请求值** —— 否则会把量化误差当成"电机没跟上"。
★ 这条模型把阶段 2 表里**所有非 1.000 的部分逐行解释掉**（24000⇒+1.6%、28000⇒+2.0%、60000⇒+4.2%
  对实测 1.015/1.018/1.040；40000/50000/20000 周期整除 ⇒ 0.998~1.000）。

## 五、过程中修掉的三个真缺陷（都是我自己的协议/工具）

1. **`走 N 步` 的 N=65535 撞 TIM4 的 ARR(0xFFFF)** ⇒ CNT 回绕、到点判据**周期性漏判** ⇒ 多跑 ~11 圈
   （血证：`65535 步 @60000 Hz` 表观只有 **5193 Hz** = 60000/11.5）⇒ **N 必须 ≤ 60000**。
2. **解卷绕的前提被我自己违反**：脚本写"每程 <180°"却用 N=1400（=315°）⇒ 走错分支，得
   `0.346 counts/step` ⇒ **那是垃圾行不是数据**。⇒ **N < 800 才有效**。
3. **`span` 由槽数算**（见 §二）⇒ 已改成由 tick 算。

## ① `g_step_ena_mismatch_n` 涨到 327616 后冻结 —— **定案：不是野写者**

**真因**：上位机把 `GPIO_MASK` 换掉了。两处 deliberate 注入：
- `tools/h723_do_hold_test.py:97` ⇒ `0x00FF`（只登记 PE0..PE7）
- `tools/h723_w1.py:386` ⇒ `0x7FC00000`（`&0xFFFF = 0`）
⇒ `do_poll` 的管辖范围不含 bit9 ⇒ **PE9 从此没人驱动**，冻结在旧电平 ⇒ 与
`g_step_ena_pin_intent` 永久不一致 ⇒ 主循环每圈 +1。**327616 / 1.2s ≈ 1747 量级一致**（对照档实测 +1747）。

★ 教训：那个数只回答了"不对了多少次"，**没回答"谁把它弄成这样的"** ⇒ 被误读成"有别的代码在驱 PE9"。
⇒ **一个计数只能回答一个问题**（§4.6 的又一次代价）。

## ③ 失步自动检测 + 恢复正常转动（`examples/h723_step_stall_recover.dcl`，**编译通过**）
判据 = `dem>0` **且** `|每拍角度增量| < 0.25×期望`（期望 = `dem×2.56e-4` counts/拍），`TON` 去抖 200 ms；

### 写程序时暴露的三条 DCL 口径 + 一个**架构级静默失效**
- `THR=` 只认**数字字面量**（CONST/信号都不行）⇒ 拿算出来的量当门限要先 `SUB` 再比 0
- `BY=` / `FROM` 只认**已声明的 CONST 名或信号**（内联字面量报"未定义信号"）
- `CONST` 字面量**不认科学计数法**（`1.0e-4` 报语法错误）
- ★★★ **`dclc` 自动分配会撞上固件保留槽**：`SEL der = wire[65]` —— 而 `WIRE[65]` 是**固件每拍写的
  运动镜像** ⇒ 值每拍被覆写（"程序在写槽、硬件一动不动"老族）。
  ⇒ 修：`dclc.py` ① 自动分配**跳过** `FW_RESERVED_WIRES` ② 显式 `OUTPUT TO wire[n]` 落到保留槽**报错**
  ③ **保留集从 `src/step.h` 自动读**（`STEP_MOT_SLOT_*_AP`）⇒ 两边不可能漂移。
  ★ 而"一律禁用 ≥64"是**过度保守**：实测固件只占 64/65，而引擎里 **`SEL` 吃 4 个 wire 槽、`CONST` 占 1 个**
  ⇒ 60 行的程序在 `wire[0..63]` 里就溢出。**约束应是"别碰保留集"，不是"不能用高区"。**
- ★ 我新写的"step.h 与内置表一致"检查**第一版就误报**（比了整个字典，描述串不同也报"不一致"）
  ⇒ 改成只比键集合（误报会被使用者关掉，比没有更坏）。
