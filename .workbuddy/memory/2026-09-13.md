## 性能对标分析（用户提问: 我们的 485 性能如何 / 对比主流 PLC / 怎么提升）

**核实过的对标事实**: 西门子 CM 1241 (S7-1200 的 RS-485 模块) 官方波特率范围
**300–115200 bps** —— 即主流中端 PLC 的 RS-485 上限就是 **115.2 k**，与我们同级。

**结论: "太差"不成立。** 同级波特率下线速是物理决定的(都 11,520 B/s);
而主流 PLC 的 Modbus 从站响应是 **ms 级且受扫描周期支配**(典型 1–10ms),
我们在 100µs 拍里推进、不依赖大循环 ⇒ 中小帧响应理论上更快更确定。

**★ 唯一真正落后主流的地方(要指出)**:
`MB_TICK_BUDGET=4` 让 **BUILD 和 TX 都按 4 字节/拍分摊** ⇒
- 8B 帧: 静默 400µs + 组装 0.7ms = **1.1ms 协议开销**, 占该事务 (2.5ms) 的 **44%**
- 133B 帧: 静默 400µs + 组装 **3.3ms** = 3.7ms, 占 (15.9ms) 的 23%
主流 PLC 一次把整帧推出去, 没有这种分摊 ⇒ **大响应偏慢是我们的真短板**。
(核实: 133B 事务实测 17.9ms = 请求 0.69 + 静默 0.4 + 组装 3.3 + 线上 11.5 + USB ~2 ⇒ 对得上)

**提升清单(按性价比)**:
1. **波特率 → 921600**(改动极小: 把 `USART2_BRR_115200` 变成可配常量; CH340 支持 921.6k/2M)
   ⇒ 8B 往返从 1.69ms 降到 **0.21ms**, 一步超过"主流 115.2k"。
2. ★ **按长度提前判帧**: 0x03/0x06/0x10 的**请求长度可由功能码+qty 确定** ⇒
   不必等满 3.5 字符静默就能判定帧完整 ⇒ 省掉那 **400µs**(小帧占比很大)。
3. ★ **组装/发送改用"本拍剩余预算"**而不是死磕 4 B/拍 ⇒ 8B 从 7 拍→1 拍, 133B 从 33 拍→2~3 拍。
   ★ 前提: 必须保住 WCET 上界(铁律) ⇒ 用"剩余预算 + 可观测的预算统计", 不是"不限量"。
4. 工程债(不是性能): **从站响应延迟(最后一字节→第一响应字节)从未单独量过**;
   多站/网络未验(只挂过 1 个 dongle); 无 921.6k/1M 档。
5. 若目标真是"跟上控制拍" ⇒ 换接口 (CAN-FD ~30µs/帧 / 以太网), 不是提速串口。

### ★★ 我上一轮的错误结论 (必须记住的教训)
"模块 TTL 侧接反" **是错的, 已作废**。它的依据是"485 收发器驱动总线时会**本地回显**到
自己的 TXD", 但**多数半双工收发器在 DE=1 期间会禁用接收, 本来就不回显**
⇒ "板子发时 PD6 不动"**不能**证明接错脚。
⇒ **教训: 判据所依赖的器件特性必须先被独立验证, 不能在推理里当公理用。**
  (这与 BRR"算得对但公式错"、TLE"ORE 未清"是同一条: 前提错, 推理再干净也没用。)

### 另修两个**测试工具**缺陷 (曾把正确行为判成 FAIL)
- `mb_master_test.py`: 写区地址少加 1 (`0x9C80`=40064 落只读区) ⇒ 固件的**正确拒绝**
  被读成"写不进去"; 且写只读区的异常判据写死 `0x83`, 而该项发 **0x06** (应为 `0x86`)
  ⇒ 该项**永远 FAIL**。
  ⇒ 同族铁律: 判据里写死的常量必须与"这一项实际发什么"对上。
�现路径: 干净固件里每轮扫描固定多出 1 字节 0x00 + 1 次 FE，一眼看出是自造的。
   修法: 恢复顺序 = AF 选择 → PUPDR 上拉 → **最后**才接 AF。
   ⇒ 通用教训: **诊断动作的"复原顺序"也会造出被测信号**；先置低（输入+下拉）后复原时，
     PUPDR 必须早于 MODER。
2. **扫 GPIOA 时不能边扫边打印** —— 观察窗 USART1_TX 就是 PA9，把它设成输入的那一刻起
   打出去的字全丢在空气里（第一版 16 行 PAxx 一行都没回来）。⇒ 采样结果先存本地、
   恢复之后再统一打印。
3. `build.sh` 的"生效开关"清单正则 `[A-Z_]*` **不含数字** ⇒ `DCL_MIN_UART2` 漏列。
   而这一段的目的正是"别被 CMake 缓存骗"，漏一个开关就是留一个静默洞。已修为 `[A-Z0-9_]*`。
