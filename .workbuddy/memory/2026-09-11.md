# 2026-09-11 · ★★★ 串口卡点结案: USART1 BRR 公式错 16 倍

## 一句话
困扰三轮的"串口完全不通"**不是接线问题** —— 是 `BRR` 公式写错 16 倍,
实际波特率 7200 而非 115200。修完后**双向全通 + 协议栈 12/12 PASS**。

---

## ★★ 根因 (P1, 两处同源)

```c
/* 错 (原代码) */
s_brr = (pclk2_hz * 16u + baud / 2u) / baud;
/* 对 */
s_brr = (pclk2_hz + baud / 2u) / baud;
```

USART 默认 **OVER8=0 (16 倍过采样)**, 此时 `BRR = fCK / baud` **就是分频值本身**。
乘 16 那套写法属于 OVER8=1 场景, 套错了地方。

| | BRR | 实际波特率 |
|---|---|---|
| 修复前 | `0x22B9` = 8889 | 64e6/8889 = **7199** |
| 修复后 | `0x022C` = 556 | 64e6/556 = **115108** |

8889/555 = **16.02**。

### 为什么极隐蔽 (三重伪装)
1. **寄存器全"正确"**: CR1=0x0D (UE|RE|TE) / ISR=0x006000D0 (**TXE=1, TC=1**) /
   GPIO AF 全对 / DWT 递增 (核在跑) / RCC 位全对 ⇒ 所有"配置类"检查全绿
2. **TC=1 是假的安心**: 它说明移位器空闲 —— 因为字节**确实推出去了**,
   只是节拍是 7200
3. ★★ **`uart.c` 注释里有一条自洽的假验证**:
   > `100MHz × 16 / 115200 = 13889 = 0x3641`, 误差 0.0004%

   数字**算得没错**, 但它是"16 倍分频"的值。这条注释用它"证明"公式正确,
   **反而把错误锁死了三轮** (第一轮怪接线 / 第二轮怪线材 / 第三轮怪驱动)
4. **现象与"线没接上"完全一样**: PC 侧 0 字节 ⇒ 常规排障路线永远查不到固件

---

## ★★ 定位手法 (可复用, 本次真正的突破)

### 第一步: 四组对照 — 把"接线"与"固件"彻底解耦
用 **SWD 直接写 GPIOA_MODER/BSRR 手摇 PA9** (核心 halt 也能翻), 同时听 PC 串口:

| 组 | PA9 状态 | COM14 收到 |
|---|---|---|
| A | 恒低不动 | **0 字节** |
| B | 手摇方波 | **13 字节** |
| C | 恒高不动 | **0 字节** |
| D | 手摇(重复) | **13 字节** |

- 若 A/C 也有字节 ⇒ 是悬空噪声, 之前所有"收到"都是假的
- 若 B/D 收不到 ⇒ 线断/接错脚, 与固件无关
- 实测 **B/D 有、A/C 无** ⇒ **线是通的**, 因果在线本身 ⇒ 剩下的只能是固件

**这一步的价值**: 它把"双向都不通"这个笼统现象, 收敛成"线没问题"这个确定结论,
从而把搜索空间从"接线+线材+驱动+固件"缩到只有固件。

### 第二步: 读 BRR, 一眼结案
`USART1_BRR = 0x22B9` vs 期望 `0x22B`, 当场定性。

### ★ 教训: "配置全对" ≠ "功能可用" 的第三次复现, 且最隐蔽
- A1 (NVIC_ISER 位移溢出): GCC **会**报警告, 只是被噪声淹没
- N1 (CRC 覆盖少一字节): 至少能在固件内部查到
- **本次**: 编译器**完全无话可说** —— 语法/类型/逻辑都合法, 只是数学错 16 倍

## 本轮新增的判据设计经验

1. **"能一次决定"优于"能扫描"** —— 上一轮做逐脚碰线扫描是**盲猜**
   (前提是脚位未知); 脚位已知后盲扫毫无意义。真正缺的是**一次决定**的判据
2. **判据用"内容匹配"而非"字节数/有无电平"** —— 噪声和波特率不匹配都会产生字节,
   但产生不出 `"MIN UART"` 这个串。`tools/h723_wire_probe.py` 按此设计
3. **四组对照(恒低/摇动/恒高/再摇)** 是判定"信号归属"的通用武器 ——
   只有"动时有、静时无"才能排除悬空噪声
4. ★ **一次性的打开瞬态不可采信**: 第一轮 COM14 收到 443 B 全 `0x00`, 之后完全消失
   (再测 0 B)。若不识别这个特征, 会据此编出"线接上了但数据不对"的错误结论
5. **别急着烧固件测** —— 先读寄存器看板子现状 (本轮先读 IDCODE/RCC 才动手)

## W2.1-W2.3 完成 (Force 域) · 提交 376d2ed

### 交付
- SHM: `OFF_FORCE_MASK=0x47F0`(u32[4]) / `OFF_FORCE_VAL=0x4800`(f32[128]) /
  `OFF_RSVD_EXEC_TAIL=0x4A00`(0xA0)。三段**精确相接**，断言用 `==` 不用 `<=`
- ISR: `engine_force_apply()` 拍首覆写 (ITCM) + 扫描宏内写端屏蔽
- `eng_force_clear()` → deploy / RESET 联动
- 命令 `0x24 FORCE`；能力位 `DCL_CAP_FORCE=0x0080`，`IMPL=0x00B3`
- 工具 `tools/h723_w2_probe.py` (**免串口**)

### ★★ 抓出三个真 bug（都在"配置全对、效果为零"族）
1. `engine_fill_tables()` **从不写 N_ROUTES** → 该路径下恒 0 →
   `h_start_w1` 的 F11 预算兜底**被静默跳过**（W1 那条判据在 profile 路径下
   从未真正走到过）。修：装载路径也要维护这个量。
2. force 覆写第一版写在 `engine_tick()` 内 → ISR 有**两条扫描路径**，
   `BOOT_SCAN_MODE=0` 走全表扫 ⇒ force 完全不生效，而 SHM 里 fmask/fval 全对。
   修：提成独立 `engine_force_apply()`，在两条路径**之外**统一调用。
   ⇒ 纪律：**凡"每拍都必须发生"的动作不能挂在某条分支里**。
3. `engine_fill_tables()` 经 `cold_start_reset()` 清掉 `ENGINE_RUN` →
   运行期 reinit 后**永久停摆**（双门 `gate && RUN` 恒不成立）。
   实测：阶段 2 回归 15 组从第 3 组起全 0。修：填表只动配置域，保存/恢复运行态。

### 验证
- `h723_w2_probe.py` **13 PASS / 0 FAIL**
- 关键手法：用**非零强制值**（7.5 → 3.25）。OA9 事故的判据盲区正是"测试全用 0.0"
- wire[3] 轨迹：1.5(路由) → 7.5(强制) → 3.25(换值) → 1.5(释放**精确**恢复)
- 强制期间路由持续写它但值纹丝不动 ⇒ 写端屏蔽生效
- 回归 `h723_stage2_read.py`：15/15 守卫 ✓、5 种校验和互异、拍周期恒 40000、
  分档收益 2.52~2.58×、ITCM 全表 7161 cyc（基线一致）

### ★ 新踩坑（跨项目通用）
- **pyocd 默认 connect_mode 在芯片进 WFI 后会 SWD 失步**
  （"Device entered sleep" / memory transfer failed / AP#0 IDR 读失败）
  ⇒ **必须 `-O connect_mode=under-reset`**；代价是每次连接都 reset，
    所以全部用例必须塞进**一条命令链**
- **pyocd 3.x 的 `read32` 输出没有 `0x` 前缀**
  （格式 `20003acc:  3fc00000`）—— 解析器按 `startswith("0x")` 匹配会恒 0 个字，
  工具会自己报"读回不足"。判据要能失败，但不能因**解析器**而失败
- **`g_reinit` 路径的副作用面积**：任何"整段清零"的单一入口被运行期调用时，
  都要问一句"它清掉的量里有没有运行态"
