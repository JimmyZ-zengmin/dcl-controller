
## SD 卡 (SDMMC1) 驱动打通 —— 14 处偏离逐条对齐权威实现 (提交 f3b960b)

**收口结果 (pyocd 直读 0x24030000 诊断区)**: 识别 11 步全过 / 写 **256/256** 块 /
回读 256 块**逐字 0 不符** / marker 0x600D。1-bit @25MHz。

**方法**: 把商家已验证例程 (`9.SDMMC-SD卡基本数据读写`, 驱动移植自 STM32H743-EVAL
= 官方 HAL/LL) 当**权威实现**, 逐句比对, 找出 14 处偏离。每处都能单独让初始化卡死。

**★ 最有价值的 5 条 (都能当通用教训)**:
1. **WAITRESP 长响应是 `0b11`, 不是 `0b10`**:
   `SDMMC_RESPONSE_LONG = SDMMC_CMD_WAITRESP` (整个 2 位掩码), 不是 `_WAITRESP_1`。
   用 0b10 (未定义编码) 时 CMD2 的 136bit 响应不被完整接收 ⇒ 残余位撞坏下一条
   CMD3 ⇒ **CMD3 永远 CCRCFAIL**, 误以为卡坏了。查"编码"一定要查 HAL 暴露的
   **语义宏** (RESPONSE_LONG), 不要自己按位推。
2. **R3 (ACMD41 的 OCR) 没有 CRC 字段** ⇒ CCRCFAIL 属正常完成。
   `SDMMC_GetCmdResp3` 只认 CTIMEOUT, 且**不要求 CMDREND**。把 CCRCFAIL 当错误
   ⇒ 初始化永远停在 ACMD41。**"响应类型决定要不要看 CRC"**。
3. **必须等 `CPSMACT` 落下** —— HAL 的 `CMDACT` 就是 `STA bit13 = CPSMACT`。
   见标志就返回 ⇒ 响应未收完/下一条命令撞上一条。
4. **数据通路总开关是 `CMD.CMDTRANS`, 不是 `DCTRL.DTEN`**; 且 `CMD_CLEAR_MASK`
   **故意不含 CMDTRANS** ⇒ 整写 CMD 寄存器会把它抹掉。
   **数据搬运交给 IDMA** (IDMABASE0 + IDMACTRL=1), CPU 喂 FIFO 实测 TXUNDERR。
5. **诊断区必须先清零**: 不清零时"没写过"和"写成垃圾"外观一样, 我据此编出过
   两个错误结论 (把随机残留读成"合法值")。**自检判据要能失败。**

**★ SD/卡特有**:
- H723 SDMMC **无 CLKEN 位**, 时钟随 POWER 上电输出; `CLKDIV>16 不出时钟`的旧结论
  **作废**(实测 CLKDIV=125=400kHz 正常) —— 改用**上电自检扫描分频**把结论写进诊断区。
- 识别期 **1-bit** (`HAL_SD_InitCard` 用 BUS_WIDE_1B), 我们一开始全程 4-bit。
- GPIO **必须上拉** (PC8-12/PD2 = `0x1555<<16` / `1<<4`)。
- ACMD41 **不要带 S18R (bit24)** —— 板无 1.8V 电平转换、也不会发 CMD11。
- **R1 的错误位在 RESP1 里, 不在返回码里**: ACMD6(2) 返回的 R1=0x920 无任何错误位,
  但卡实际没切 4-bit。⇒ 凡 R1 命令都要 `RESP1 & SDMMC_OCR_ERRORBITS(0xFDFFE008)`。
- **本卡的 DAT1..3 不工作**: 4-bit 读第 0 块即 DCRCFAIL (与时钟无关, 6.25MHz 同样),
  双端一起回 1-bit 后 256/256 逐字全对。CID = `0x00343253 44313647`
  (厂家 ID=0x00, OID="42", 均非 SD 协会正规值) ⇒ **疑似非原厂卡**。
  数据期固定 **1-bit @25MHz** (3.125MB/s, 128KB=41ms, 够用)。
- 黑匣子落盘: LBA **3000000** 起 256 块 (128KB), 避开盘头分区表。PC 端需按**物理盘**
  直读 (`\\.\PhysicalDriveN`), 普通卷访问读不到 1.46GB 偏移处。
**DO 面 = GPIOE[15:0] (16 路)**, 四条理由:
1. **GPIOE 在本固件中完全未使用** (全工程唯一提及是 `macro.c:37` 一句注释) — grep 确认
2. `h723-core0` 的输出链配方**就在 GPIOE 上验证过** (M0AR→GPIOE_ODR / DMAMUX C8=TIM1_UP / M2P+CIRC+32bit+NDTR=1) ⇒ 原样复用
3. **16 位恰好落进一个 u32** ⇒ 正好给 `engine.h:120-132` 钉住的定案走**选项 ②**
   ("只支持一个端口" + 断言 `mask < (1<<16)`) ⇒ **对 SHM 零偏移代价**
4. 数据源用现成 `OFF_ACTUATOR_STATUS`: `ACTUATOR[0..15] > 0.5f` → 打包 u32, **不需新增 SHM 区**
★ 明确不改: **心跳继续走 PA8** (LA CH4 已接) — 不学 h723-core0 把心跳并进输出字,
  否则把"拍心跳"与"输出面"耦合, 破坏现有确定性判据。
⚠ **唯一前置**: PE0..PE15 是否都引到 2×30 排针 (`HARDWARE-PINOUT.md` 只写"几乎所有 IO", `[原理图]` 未实测)
  ⇒ 开工第一步实测 PE 各脚写读; 若只引出 8 位就退到 8 位 + 断言 `mask < (1<<8)`。

### 预算核算 (结论: 毫无压力)
实测基线 `REF-flash-placement.md:118`: 混合程序 **`isr_max = 11524 cyc` = 占拍 29.03%, 余量 28476 cyc**。
搬入后增量预估: DI 60 + HIL 输出臂 60 + DO 打包 80 + ADC 状态机 25 ≈ **225 cyc = 余量 0.8%**。
⚠ **真正的落地风险不是预算, 是 ITCM 余量只有 0x68 字节** (`ARCH-H723.md:137`) ⇒ 新代码可能要腾 ITCM。

### 分批实施
- **P1** DI + HIL 输出臂进拍 (相位驱动, 去掉 10ms 相对节流) + GPIO_MASK 定案 ② + PE 实测
- **P2** ADC 非阻塞化 (方案 A) + 反馈臂改跨拍累加 ⇒ 主循环 I/O 占比 49% → ~0
- **P3** DO 硬件锁存链 (AXI + TIM1 UDE + DMA2 S0)
- **P4** 可选: ADC 硬件触发 + DMA / MDMA 输入链
建议 **P1+P2 合并** (输入输出对偶, 分开要动两次 ISR 结构), P3 单独 (引入 DMA/DMAMUX 新外设, 变量最多)。

### ① PE 可用位实测 —— **16/16 全可用, 0 可疑** ⇒ 定案②成立
新工具 **`tools/h723_pe_probe.py`**: halt 态配 PE0..15 推挽输出 → 4 个 ODR pattern

★ **踩坑 (判据写错, 不是硬件错)**: 第一版判"恢复后 MODER 应 == 0" ⇒ 实测 0xFFFFFFFF
被判"未恢复"。**STM32H7 的 GPIO MODER 复位默认就是 0xFFFFFFFF (全 analog)**, 与 F4 的 0
不同。⇒ 改成"对比**配置前的基准值**", 不假设复位值。

### ② `OFF_CTRL_GPIO_MASK` 定案 = **选项②, 端口取 GPIOE[15:0]**

`g_safe_mask_oob`(**高16位非0 = 越界写, 独立计数**)。理由: 一个计数只回答一个问题。

**⇒ 核心判据⑤ 是"搬进拍内"的直接证据** (交付必须增 / 对照必须恒 0), 且**两档都全 PASS**。

### ④ ⚠️ **未决项: HIL 输出臂进不了 ISR** (如实记录, 未冒充完成) —— **同日已解决, 见本文末尾**
只要在 TIM2 ISR 里调用 `hil_out_poll`, **整机就卡进 Default_Handler**, 而:
| 试过的形态 | 结果 |
|---|---|
| 放 flash (链接器自动 veneer 的 `BL`) | 卡 |
| 放 flash + `long_call` (`BLX`; 常量池地址**带 thumb 位, 已逐一核对**) | 卡 |
| 放 ITCM (与 ISR 同区, 直接 `BL`) | 卡 |
| **函数体改成空实现 (只剩 `bx lr`)** | **仍卡** |
| `di_poll` / `adc_poll` 用**完全相同**的机制 | **一切正常** |

**已排除的假设** (都有实测数据): 跨区 BL 范围 / veneer 缺失 / `long_call` 未生效 /
函数内容 / 缺"硬件就绪门" / ITCM 溢出 / 向量表内容 / 常量池 / 函数位置 / 断点假阴性。
**现场**: `PC` = 某个 `Default_Handler`, `ICSR.VECTACTIVE = 44`, `IABR0 bit28 = 1`,
`CFSR/HFSR = 0`, `PRIMASK/BASEPRI = 0`, **但 `slot[44] = 0x00000001` (TIM2_IRQHandler)
且 `TIM2_SR.UIF` 从未被清、`g_stage` 从未写成 7、`tick_count = 0`** ⇒ 三证表明
`TIM2_IRQHandler` 从未被执行, 而 IRQ 28 却是"活跃"的。**机制未明, 列为待查。**
⇒ **处置**: `hil_out_poll` 留在主循环 (`hil_tick`), 注释里写明"尚未进 ISR"。

### ⑤ ★★ 两条可复用的硬教训 (写进代码注释了)
1. **`static const` 函数指针数组会被 `-O2` 常量传播成直接 `BL`** ——
   源码改了、编译零警告, 但 `pyocd flash` 报 `programmed 0 bytes, identical N bytes`
   (**产物一模一样**)。**⇒ 用声明上的 `__attribute__((long_call))`, 不要用函数指针数组。**
2. **ELF 产物没有扩展名** (`build/dcl_h723`, 不是 `.elf`) —— objdump 报 "No such file"
   时先 `ls` 确认文件名, 别怀疑路径转换。**且 objdump 要 Windows 路径 + 无空格目录**
   (拷到 `%TEMP%\a.elf` 最省事)。

## ★★★★ 4 节的"未决项"**已解决** —— 真因是**向量表的落位** (2026-09-12 同日)

用户提示 **"退一步看整体, 视野大了你应该也看得清楚一些"** ⇒ 我停止在 `hil_out_poll`
**内部**找原因 (veneer/常量池/thumb 位/就绪门/ITCM 落位…连续查了十几轮), 改用
**等长替代 + 纯体积对照** 做整体剥离 ⇒ 一轮定论。

### ★★ 真因 (一句话)
> **`_vtor_itcm = 0x1880` 时整机卡死; `0x1800` 和 `0x1900` 都正常。**
> 与"调用谁 / 函数放哪 / 函数体做什么 / 用 BL 还是 BLX"**全都无关**。

### ★★★ 证据链 (10 个构建, 全部真机实测)
| # | 实验 | `_eitcm` | `_vtor_itcm` | 结果 |
|---|---|---|---|---|
| 1 | 基线 (ISR 只加 di_poll+adc_poll) | ≤0x1800 | **0x1800** | **正常** |
| 2 | +hil_out_poll 调用 | 0x1808 | **0x1880** | **卡死** |
| 3 | 同 2 但 long_call (BLX) | 0x1808 | 0x1880 | 卡死 |
| 4 | 同 2 但函数放 ITCM (同区 BL) | 0x1808 | 0x1880 | 卡死 |
| 5 | 同 2 但函数体**空实现** (bx lr) | 0x1808 | 0x1880 | 卡死 |
| 6 | **等长替代**: 换成 `di_poll` 的调用 | 0x1808 | 0x1880 | **卡死** ← 与符号无关 |
| 7 | **纯体积对照**: 换成 4 条 nop (8B, 无调用) | 0x1808 | 0x1880 | **卡死** ← 与调用无关 |
| 8 | **推过阈值**: +200B nop | 0x18C8 | **0x1900** | **正常** |
| 9 | 重现 #7 的 8 字节 + 向量表 **256 对齐** | 0x1808 | **0x1900** | **正常** |
| 10 | **修后交付档** (hil_out_poll 回 ISR) | 0x1808 | 0x1900 | **正常** |

### ★ 修法
`ld/STM32H723ZG_FLASH.ld`: `.itcm_vectors` 对齐 **128 → 256**。
**代价**: ITCM 多留 ≤128 字节对齐填充 (当前 `0x1808 → 0x1900`, 空隙 248B)。
相对"随时可能因 8 字节增删而卡死", 可以忽略。

### ★★★ 必须记住的一条 (比修法更重要)
**ARMv7-M 的 spec 只要求 VTOR 128 字节对齐。**
⇒ **256 是本板实测出来的经验值, 不是规范要求** ⇒ **换板子/换型号/换批次都要重验**。
(这属于项目已知的"平台特性"家族: "本平台对代码体积敏感" ARCH §0.3 + T26 记的
"加 200 字节就改变上电行为" —— **本次把这个家族的一个具体机制钉死了**。)

### ★★ 修复后的交付验收 (A/B 双档全 PASS)
| 判据 | DUT (输入段+输出臂都在 ISR) | CTRL (IO 在主循环) |
|---|---|---|
| 存活 (tick/heartbeat 增量) | +9017 | +9010 |
| 拍周期 pmax | 40008 cyc | 40008 cyc |
| `g_per_glitch_n` (时基) | 0 | 0 |
| **`isr_max`** | **1111 cyc** | **218 cyc** (基线) |
| **`g_adc_sm_done`** | **2493 → 4747 单调增** | **0 → 0** |
| 超时 / 越界 | 0 / 0 | 0 / 0 |
⇒ **输入输出链都已进 100µs 拍内, ISR 成本增量 = 893 cyc = 拍预算的 2.2%。**

### ★★ 两条方法论 (比结论值钱)
1. **"某个东西一加就坏"时, 先证明"换个别的东西加进去会不会一样坏"**
   —— 等长替代 + 纯体积对照, 一轮就把"函数问题"与"平台问题"分开。
   我在 `hil_out_poll` 内部查了十几轮, 却一直没做这件最朴素的事。
2. **单点深挖会让人丧失整体视野** —— 用户一句"退一步看整体"直接点破。
   整体对照表 (三个 I/O 函数的差异) 一行就能看出"位置/体积"是唯一没被动过的变量。

## ① 查到的资料 (三条互证, 都指向 ECC)

# ★★★★ 2026-09-12 中午: 真因确认 (查资料查出来的) + 三层修复, 问题关门

## ★★★★ 真因: **VTOR 对齐不足, 硬件取向量时拿对齐值做掩码**

**ARM 官方规则** (developer.arm.com 102283, 一字不差):
> *"the offset, in bytes, must be aligned to: a power of 2. a minimum of 128 bytes.
>   **a minimum of 4×N, where N is the number of exceptions supported.** The minimal
>   alignment is 128 bytes, which allows for 32 exceptions... **To use more interrupts,
>   you must adjust the alignment by rounding up to the next power of two.**"*

**H723 的账**: 150 IRQ + 16 系统异常 = **166 项** → 4×166 = 664 字节 → 向上取 2 的幂 =
**1024 字节** ⇒ H723 的向量表必须 **1024 对齐**。我们一直用 128 —— 只够 32 项, 差 5 倍。

**mask 机制** (这解释了此前所有"矛盾"):
- `VTOR = 0x1880` (128 对齐) ⇒ 硬件以为表只有 32 项 ⇒ 取索引 44 时 **44 mod 32 = 12**
  ⇒ 读的是 **slot[12] (保留项 → Default_Handler)** ⇒ 卡死。**CPU 从头到尾没读过 slot[44]**
  —— 所以表内容、VTOR、ITCM 代码、RAMECC、fault 全对却照样死。
- `VTOR = 0x1800` (1024 对齐) ⇒ 不掩码 ⇒ 正确。
- `VTOR = 0x1900` (256 对齐) ⇒ 索引 44 < 64 没被掩 ⇒ **"正常"纯属运气**;
  任何 **IRQ ≥ 48 (索引 ≥ 64)** 在 256 对齐下都会被掩到错位 —— 256 对齐是**埋着的雷**。
- EXP-E (64 位全宽初始化 + 0x1880 仍卡) 也顺理成章: 不管表怎么写, 取向量都被掩到 slot[12]。
- ECC / RAMECC / veneer / 跨区调用 / long_call / 函数位置 —— **全部与此无关**, 前面十几轮
  排查都是在错误的框架里打转。

## ★★ 三层修复 (全部真机验证通过, [PIN] 全判据 PASS)
1. **对齐 → 1024**: `ld/STM32H723ZG_FLASH.ld` 里 `.itcm_vectors` 重写 (根因修复)。
2. **表钉在 ITCM 末尾**: `_vtor_itcm = ORIGIN(ITCM)+LENGTH(ITCM)-0x400` = **0xFC00**,
   与代码大小**彻底解耦** (代码从 0x0 向上长, 表位置永不变 ⇒ 不再"每次改代码都买落位彩票")。
   配套 **linker ASSERT**: `ASSERT(_eitcm <= _vtor_itcm, "ITCM code overflow...")`
   —— 代码涨进表区在**链接期**报错, 不再静默上板。
3. **拍活体自检** (main.c, `tick_timer_init()` 之后): 等 3 个 tick, 不动 ⇒ `blink_error(101)`。
   防的是**一切取向量类失败** (表位置/表内容/掩码/换板) —— 这条要在 10 分钟报警,
   而不是像这次花一个通宵猜。
- **验收实读**: `VTOR = 0xFC00`, `0xFCB0 (slot[44]) = 0x00000001 (TIM2_IRQHandler)`,
  `0xFC00 = 0x20020000 (初始 SP)` ✅; `isr_max = 1099 cyc`, 全判据 PASS。
- ITCM 报告显示 100% 是**地址空间覆盖** (表钉在高端), 实际代码 6.2KB, 余量 58KB,
  且有 ASSERT 守门 —— 不是真溢出。

## ★★ 给下次的自己
- **"向量表对齐 ≥ 4×异常数、取 2 的幂"是 ARM 架构规则, 不是经验值** —— 之前
  "256 是实测经验值, 换板要重验"的说法**作废**, 正确说法: **按芯片的 IRQ 数算对齐**。
- **中断号越高的外设 (FDCAN/以太网/SDMMC) 越容易踩掩码雷** —— 以后启用任何
  IRQ ≥ 48 的外设前, 先确认表对齐 ≥ 1024 (现在是 0xFC00, 恒安全)。
- **启动期自检 (等 N 个 tick) 是查"取向量失败"的最便宜判据**, 任何带 ITCM 向量表
  副本的工程都值得加一条。

## SD 卡 (SDMMC1) 驱动打通 —— 14 处偏离逐条对齐权威实现 (提交 f3b960b)

**收口结果 (pyocd 直读 0x24030000 诊断区)**: 识别 11 步全过 / 写 **256/256** 块 /
回读 256 块**逐字 0 不符** / marker 0x600D。1-bit @25MHz。

**方法**: 把商家已验证例程 (`9.SDMMC-SD卡基本数据读写`, 驱动移植自 STM32H743-EVAL
= 官方 HAL/LL) 当**权威实现**, 逐句比对, 找出 14 处偏离。每处都能单独让初始化卡死。

**★ 最有价值的 5 条 (都能当通用教训)**:
1. **WAITRESP 长响应是 `0b11`, 不是 `0b10`**:
   `SDMMC_RESPONSE_LONG = SDMMC_CMD_WAITRESP` (整个 2 位掩码), 不是 `_WAITRESP_1`。
   用 0b10 (未定义编码) 时 CMD2 的 136bit 响应不被完整接收 ⇒ 残余位撞坏下一条
   CMD3 ⇒ **CMD3 永远 CCRCFAIL**, 误以为卡坏了。查"编码"一定要查 HAL 暴露的
   **语义宏** (RESPONSE_LONG), 不要自己按位推。
2. **R3 (ACMD41 的 OCR) 没有 CRC 字段** ⇒ CCRCFAIL 属正常完成。
   `SDMMC_GetCmdResp3` 只认 CTIMEOUT, 且**不要求 CMDREND**。把 CCRCFAIL 当错误
   ⇒ 初始化永远停在 ACMD41。**"响应类型决定要不要看 CRC"**。
3. **必须等 `CPSMACT` 落下** —— HAL 的 `CMDACT` 就是 `STA bit13 = CPSMACT`。
   见标志就返回 ⇒ 响应未收完 / 下一条命令撞上一条。
4. **数据通路总开关是 `CMD.CMDTRANS`, 不是 `DCTRL.DTEN`**; 且 `CMD_CLEAR_MASK`
   **故意不含 CMDTRANS** ⇒ 整写 CMD 寄存器会把它抹掉。
   **数据搬运交给 IDMA** (IDMABASE0 + IDMACTRL=1), CPU 喂 FIFO 实测 TXUNDERR。
5. **诊断区必须先清零**: 不清零时"没写过"和"写成垃圾"外观一样, 我据此编出过
   两个错误结论 (把随机残留读成"合法值")。**自检判据要能失败。**

**★ SD/卡特有**:
- H723 SDMMC **无 CLKEN 位**, 时钟随 POWER 上电输出; `CLKDIV>16 不出时钟`的旧结论
  **作废**(实测 CLKDIV=125=400kHz 正常) —— 改用**上电自检扫描分频**把结论写进诊断区。
- 识别期 **1-bit** (`HAL_SD_InitCard` 用 BUS_WIDE_1B), 我们一开始全程 4-bit。
- GPIO **必须上拉** (PC8-12/PD2 = `0x1555<<16` / `1<<4`)。
- ACMD41 **不要带 S18R (bit24)** —— 板无 1.8V 电平转换, 也不会发 CMD11。
- **R1 的错误位在 RESP1 里, 不在返回码里**: ACMD6(2) 返回 R1=0x920 无任何错误位,
  但卡实际没切 4-bit。⇒ 凡 R1 命令都要 `RESP1 & SDMMC_OCR_ERRORBITS(0xFDFFE008)`。
- **本卡的 DAT1..3 不工作**: 4-bit 读第 0 块即 DCRCFAIL (与时钟无关, 6.25MHz 同样),
  双端一起回 1-bit 后 256/256 逐字全对。CID = `0x00343253 44313647`
  (厂家 ID=0x00, OID="42", 均非 SD 协会正规值) ⇒ **疑似非原厂卡**。
  数据期固定 **1-bit @25MHz** (3.125MB/s, 128KB=41ms, 够用)。
- 黑匣子落盘: LBA **3000000** 起 256 块 (128KB), 避开盘头分区表。PC 端需按**物理盘**
  直读 (`\\.\PhysicalDriveN`), 普通卷访问读不到 1.46GB 偏移处。

## SD 卡 (SDMMC1) 驱动打通 —— 14 处偏离逐条对齐权威实现 (提交 f3b960b)

**收口结果 (pyocd 直读 0x24030000 诊断区)**: 识别 11 步全过 / 写 **256/256** 块 /
回读 256 块**逐字 0 不符** / marker 0x600D。1-bit @25MHz。

**方法**: 把商家已验证例程 (`9.SDMMC-SD卡基本数据读写`, 驱动移植自 STM32H743-EVAL
= 官方 HAL/LL) 当**权威实现**, 逐句比对, 找出 14 处偏离。每处都能单独让初始化卡死。

**★ 最有价值的 5 条 (都能当通用教训)**:
1. **WAITRESP 长响应是 `0b11`, 不是 `0b10`**:
   `SDMMC_RESPONSE_LONG = SDMMC_CMD_WAITRESP` (整个 2 位掩码), 不是 `_WAITRESP_1`。
   用 0b10 (未定义编码) 时 CMD2 的 136bit 响应不被完整接收 ⇒ 残余位撞坏下一条
   CMD3 ⇒ **CMD3 永远 CCRCFAIL**, 误以为卡坏了。查"编码"一定要查 HAL 暴露的
   **语义宏** (RESPONSE_LONG), 不要自己按位推。
2. **R3 (ACMD41 的 OCR) 没有 CRC 字段** ⇒ CCRCFAIL 属正常完成。
   `SDMMC_GetCmdResp3` 只认 CTIMEOUT, 且**不要求 CMDREND**。把 CCRCFAIL 当错误
   ⇒ 初始化永远停在 ACMD41。**"响应类型决定要不要看 CRC"**。
3. **必须等 `CPSMACT` 落下** —— HAL 的 `CMDACT` 就是 `STA bit13 = CPSMACT`。
   见标志就返回 ⇒ 响应未收完 / 下一条命令撞上一条。
4. **数据通路总开关是 `CMD.CMDTRANS`, 不是 `DCTRL.DTEN`**; 且 `CMD_CLEAR_MASK`
   **故意不含 CMDTRANS** ⇒ 整写 CMD 寄存器会把它抹掉。
   **数据搬运交给 IDMA** (IDMABASE0 + IDMACTRL=1), CPU 喂 FIFO 实测 TXUNDERR。
5. **诊断区必须先清零**: 不清零时"没写过"和"写成垃圾"外观一样, 我据此编出过
   两个错误结论 (把随机残留读成"合法值")。**自检判据要能失败。**

**★ SD/卡特有**:
- H723 SDMMC **无 CLKEN 位**, 时钟随 POWER 上电输出; `CLKDIV>16 不出时钟`的旧结论
  **作废**(实测 CLKDIV=125=400kHz 正常) —— 改用**上电自检扫描分频**把结论写进诊断区。
- 识别期 **1-bit** (`HAL_SD_InitCard` 用 BUS_WIDE_1B), 我们一开始全程 4-bit。
- GPIO **必须上拉** (PC8-12/PD2 = `0x1555<<16` / `1<<4`)。
- ACMD41 **不要带 S18R (bit24)** —— 板无 1.8V 电平转换, 也不会发 CMD11。
- **R1 的错误位在 RESP1 里, 不在返回码里**: ACMD6(2) 返回 R1=0x920 无任何错误位,
  但卡实际没切 4-bit。⇒ 凡 R1 命令都要 `RESP1 & SDMMC_OCR_ERRORBITS(0xFDFFE008)`。
- **本卡的 DAT1..3 不工作**: 4-bit 读第 0 块即 DCRCFAIL (与时钟无关, 6.25MHz 同样),
  双端一起回 1-bit 后 256/256 逐字全对。CID = `0x00343253 44313647`
  (厂家 ID=0x00, OID="42", 均非 SD 协会正规值) ⇒ **疑似非原厂卡**。
  数据期固定 **1-bit @25MHz** (3.125MB/s, 128KB=41ms, 够用)。
- 黑匣子落盘: LBA **3000000** 起 256 块 (128KB), 避开盘头分区表。PC 端需按**物理盘**
  直读 (`\\.\PhysicalDriveN`), 普通卷访问读不到 1.46GB 偏移处。

## ★ PC 端取证 + 两个重要发现 (2026-09-12 晚, SD 卡插到电脑后)

**工具**: `tools/sd_read_raw.py` —— 用 **ctypes `CreateFileW`/`SetFilePointerEx`/`ReadFile`**
直读 `\\.\PhysicalDriveN`。**不需要管理员权限**(Python 内置 `open()` 对设备句柄会报
`Errno 22 Invalid argument`, 不能用)。E: → `PhysicalDrive2` 用
`IOCTL_STORAGE_GET_DEVICE_NUMBER` 映射。

**① SD 写卡路径 = 真通 (独立通路确认)**
卡上 LBA 3000000 起 128KB, 与**直接从芯片导出的 AXI 环**(pyocd 读 0x24004000) **逐字一致**。
这比固件自证的"回读校验 0 不符"强一档 —— 因为是另一条独立通路取的证据。

**② ★★ 但黑匣子实际没在录 (飞行记录仪是假的)**
AXI 环 512 槽里**只有第 0 槽是真快照** (tick=0, SENSOR=`0,0.5,1.0,1.0`, WIRE=`0,0.25,0.004,1.5`)，
其余 511 槽全是**线性计数器** (`0x1039,0x103a,0x103b…` 跨整个 256B 槽) = SRAM 残留。
⇒ **`bb_kick` 的 MDMA ch1 每拍搬运只成功了 1 次**, 之后静默失败。
`sd_dump_blackbox` 忠实地把这份"只有 1 槽有效"的 SRAM 复制到了卡上 —— **复制没错, 源头是空的**。
待办: 查 MDMA ch1 (0x52000080) 重复软触发为什么只生效一次
(疑似需在每次 kick 前重写 CCR/CIFCR 序列, 或 CBSIZE/CTCR 需重设)。

**③ ★★ "回读校验通过" ≠ "卡是好的" (新增判别纪律)**
扩容假卡(wrap-around)会把超容量的写入回卷覆盖到开头 ⇒ **写什么读回什么, 自校验永远自洽**。
本次是"从芯片独立取源数据再比"才看出内容异常。判真假指纹:
读 LBA 1/2/4/8/16/32GB 处与 LBA 0 比 —— **LBA 62,500,000 (=32GB) 读回 == LBA 0 的内容
⇒ 地址空间在 32GB 处回卷**。
另: 扫"自己写入的唯一签名"是否出现在低地址, 出现在低地址即 = 卡在回卷。
**一张会回卷的卡比一张拒绝挂载的卡危险得多: 它会安静地伪造"一切正常"。**

**④ 卡为什么要求格式化 (Windows 的事实)**
- 物理盘 **LBA 0 不再是分区表, 而是从 0 开始的线性计数器** (`00000000 01000000 02000000 …`)。
- 前 64MB **只有 72 个非零扇区** (即 LBA 0..71 那 36KB 计数器), 72 起全 0
  ⇒ **卡上没有任何文件系统元数据** ⇒ Windows 看不到文件系统, 只能提示格式化。
- **我们的写入没有覆盖 MBR**: 扫 1,048,750 / 1,950,000 / 2,800,000 / 2,900,000 等
  常见回卷点, 都没有我们数据的第二份。
- **仍未定论**: 那 36KB 计数器是谁写的。注意它与 AXI SRAM 的残留是**同一种图案**
  (AXI word j = j-7; 卡 word i = i ⇒ 卡上 36KB == AXI 字节 [0x1C, 0x901C))。
  两个待查方向: ① 卡出厂就是这样(从未格式化过); ② 某次操作/工具写的。
- 卡的其他可疑点: 报 **31.27 GB** 但 CID 产品名是 **"SD16G"**; CID 厂家 ID=**0x00**、
  OID="42" 都不是 SD 协会正规值; **4-bit 数据线不工作**。

**⑤ 给我自己的纪律**
- 读物理盘取证: 用 ctypes 设备句柄, 别用 `open()`。
- **读数之前先 `reset` 让固件真跑完**, 否则读到上一轮中间态 (本次据此误判过两次)。
- 诊断区**先清零**, 否则"没写过"与"写成垃圾"无法区分。

## ★★ 飞行记录仪 (bb_kick) 真因修复 —— MDMA 每拍只搬 0 字节 (2026-09-12 夜)

**症状**: AXI 环 512 槽里只有第 0 槽是真快照, 其余全是陈旧 SRAM (一个线性计数器)。
引擎确实在跑 (g_tick_count 在涨, bb_kick 计数 30720), 但环一个字不变。

**定位手段 (关键)**: **pyocd 读不了 0x5200_xxxx / 0x5802_xxxx 外设区 —— 全返回 0**
(实测连 SDMMC1 的固定版本寄存器 `IPVR` 都读回 0 ⇒ 那些 0 是**读失败不是真值**)。
所以 MDMA 状态只能**由固件自己读出来放进 SRAM** (`BB_DIAG @ 0x24030100`), 再让 pyocd 读 SRAM。
顺手做了一条**寄存器活性自检** (写 0xABCD 到 CBNDTR 再读回) —— "判据必须能失败"。

**权威位域 (逐条核 stm32h723xx.h, 之前注释里有两处错)**:
- `CTCR`: SINC[1:0] / DINC[3:2] / SSIZE[5:4] / DSIZE[7:6] / **TLEN[24:18] = 字节数-1, 只有 7 位
  ⇒ 上限 128 字节** / **TRGM[29:28]** (不是 [17:16]) / SWRM(30)
- ST HAL: `MDMA_BUFFER_TRANSFER=0` / `MDMA_BLOCK_TRANSFER=TRGM_0` / `_REPEAT_BLOCK_TRANSFER=TRGM_1` /
  `_FULL_TRANSFER=TRGM`。**"每请求搬一个 block(=BNDT 字节)"要用 TRGM=01。**
- 通道寄存器组基址 = `MDMA_BASE + 0x40*(n+1)` (全局寄存器占 0x00..0x3F) ⇒ ch1 = 0x52000080 ✓
  (blackbox.c 原来的基址注释是对的, 别改)

**真因 (两条, 都在 bb_kick)**:
1. **`CBNDTR` 只在 bb_init 写过一次** —— MDMA 传输后 BNDT 被减到 0 且**不会自动重装**;
2. **`EN=1` 期间 CSAR/CDAR/CBNDTR 的新值不被接受**(影子寄存器) ⇒ 后续 kick 写的地址全被忽略。
   证据: 自观测读到 `CBNDTR=0` / `CISR=0`(无完成标志) / `CESR=0`(无错误) / `CCR=1`(EN 挂着),
   而 CDAR 停在 512 拍之前的旧值。
   ⇒ 只有 `bb_init→bb_kick(0)` 的第一次搬运成功 —— **这正好解释了"环里只有第 0 槽是真快照
   (tick=0 + boot 时真实 SHM 浮点值)"**。
3. 附带: TLEN 写 255 只有低 7 位有效 ⇒ 实际 128 字节; 改用 **TRGM=01 block + BNDT=256**。

**修法 (每拍固定序列)**: `CCR=0`(关通道, 允许改寄存器) → `CIFCR=0x1F` → 写 CSAR/CDAR/**CBNDTR=256**
→ `dsb/isb` → `CCR=1` → `CCR |= SWRQ`。

**验证 (pyocd 读 SRAM, 全是独立证据)**:
- 活性: CBNDTR 写 0xABCD 回读 0xABCD; AHB3ENR bit0=1
- CTCR 回读 `0x51FC00AA` (SWRM=1 / TRGM=01 / TLEN=127 / SSIZE=DSIZE=word / SINC=DINC) ✓
- 环槽 word0 = **连续 tick**: `0xA01A, 0xA01B, 0xA01C, 0xA01D…` ✓
- 完整快照: tick + `SENSOR[1]=0x3F000000(0.5)` + WIRE/ACTUATOR + 控制字 `0x01000080`(run=1,seq=128) ✓

**遗留**: `sd_dump_blackbox` 的落点 `LBA 3000000` **在卡文件系统的中间** ⇒ 会破坏卡上文件
(而旧注释写的"写在卡的末尾区"与代码不一致 = 宣称≠实现)。建议改成按 CSD 算容量后写**卡末尾**。

**待修**: sd_init 在**板子上没插卡**时诊断区是 `[0]=2 / [20]=0xBAD1` (分频自检全失败) —— 符合预期。

## SD 落盘提速 (2026-09-12 夜, 提交 eb356e5) —— 需求 2.56MB/s

**需求来源**: 用户要"每一拍都落盘"。一拍 256B × 10kHz = **2.56 MB/s 持续**。

**吞吐杠杆 (按性价比)**:
1. **单块 CMD24 → 多块 CMD25 + CMD12 STOP** —— 必须做。单块每块都要命令+响应+
   等卡内部编程, 实测只有 ~0.3MB/s。已实现 `sd_write_multi()` (IDMA 连续喂)。
   ★ 多块写**只能等 DATAEND** —— `DBCKEND` 是每块结束都置位, 用它会在第 1 块误判成功。
   ★ CMD12 必须 `CMDSTOP=1 且 CMDTRANS=0` (照 `SDMMC_CmdStopTransfer`)。
2. **25 → 50 MHz** (SDMMC_CK = ker_ck/(2×CLKDIV), CLKDIV=2→1) + **CMD6 切 High Speed**
   ⇒ **1-bit 就有 6.25 MB/s, 已经够 2.56**。不需要非上 4-bit。
3. 4-bit (×4: 25MHz=12.5 / 50MHz=25) —— 舒服但非必需; 目前 4-bit **读**是坏的, 待查。
4. kernal clock 100→200MHz (DIVQ1 4→2) 是 2 的前置余量。
5. 记录瘦身 256B→64B (×4) 或降采样 (×N) —— 产品取舍, 兜底。

**★ 已落地的实验设施 (换档不必重编译)**:
- SRAM 配置字 `0x24002000`, 调试器**复位前预写**, 固件读一次即清:
  `[0]`数据期 CLKDIV(默认2) / `[1]`=1 发 CMD6 切 HS / `[2]`=1 只测写(跳过回读校验)
- 落盘耗时用**拍计数**(100us/拍)测, main 计时 → `sd_set_perf()` → 诊断区:
  `[30]`数据期CLKCR `[31]`CMD6的R1 `[32]`CLKDIV `[33]`耗时拍 `[34]`写成块数
- 吞吐: **MB/s = 块数 × 5.12 / 拍数**
- 一键 A/B: `tools/sd_perf_ab.py` (跑 25MHz默认 / 25MHz+HS / 50MHz+HS / 50MHz默认)

**★ 判据纪律(自己踩的)**: 计时**必须只覆盖写**。原本 sd_set_perf 把 256 次单块读的
回读校验也算进耗时 ⇒ 量出来的是"写+读"不是写速度。已加 `[2]`=1 只测写。

**★ 4-bit 读失败的嫌疑方向 (卡为正品, 故是我们这边的问题)**:
- 现象: 4-bit 写 256/256 全过(卡自身 CRC 不报错 ⇒ **主机→卡方向 4 条线都通**),
  4-bit 读第 0 块必 DCRCFAIL 且与时钟无关; 双端一起回 1-bit 后读 256/256 逐字全对。
  ⇒ 坏的是**卡→主机方向的多通道接收采样**, 不是接线、不是频率余量。
- 嫌疑: `CLKCR.SELCLKRX`(接收时钟选择, bits[21:20], 默认 00) / 多通道采样余量。
- ⏳ 待测。

1. **必须先发 `CMD23 SET_BLOCK_COUNT` 把块数告诉卡**。不告诉时: 主机侧 `DLEN` 到点

2. **多块写只能等 `DATAEND`**: `DBCKEND` 是每块结束都置位 ⇒ 用它第 1 块就误判成功。
3. **★★ 落盘前必须"冻结快照"**: RAM 环是**活的**(引擎每 100us 覆写), 边写边比对活环
   = 拿会动的靶子当判据 ⇒ 实测报过 **182/256 块"不符"的假警报**(改黑匣子之前它"通过"
   只是因为那时环是静止的)。冻结到 `0x24024000` 后写与校验对着同一份静止数据。
   **这也是"每拍连续落盘"的必要机制**: 落盘内容必须是某一时刻的一致快照。

**+ 失败路径必须把卡和数据通路收干净** (清 CMDTRANS/IDMA + CMD12 STOP), 否则毒化后续。

**AXI SRAM 布局重排 (2026-09-12)**:
```
0x24000000 低 16KB 预留
0x24000200 SD_DIAG (56 字)      0x24000300 BB_DIAG (40 字)     0x24000400 SD_CFG (3 字)
0x24001000 SD 校验 scratch (512B)
0x24003000 / 0x24003100  do.c 锁存快照 / MDMA 链表节点  ← 勿动
0x24004000 + 128KB  黑匣子 RAM 环 (512 槽 × 256B, 活的)
0x24024000 + 128KB  **SD 冻结区** (落盘前把环整体拷过来)
```

## ★★ 每拍连续落盘日志 (2026-09-12 深夜, 提交 ef716c9)

**用户决定**: 回卷覆盖最旧 + 这张卡当**专用记录介质**(不建文件系统)。

**架构**:
```
ISR(10kHz) → 256B 快照写进 RAM 环(512 槽 = 51.2ms 缓冲)
主循环 sd_log_poll() → 逐槽冻结到 0x24024000 → CMD23+CMD25 追加(回卷)落盘
卡上  LBA0 = 头部块 (DLOG 魔数/几何/写指针/tick/seq/丢包/回卷标志)
      LBA1 .. 容量-1 = 数据区 (每 512B 块 2 条 256B 记录, 环形)
PC    tools/sd_log_read.py 按物理盘直读(免管理员) → 带 tick 列的表 / CSV
```

**★ 每条记录自带"是哪一拍"的标注** (blackbox.h): `[0]magic "DLBK" [1]tick [2]seq [3]ctrl`
+ SENSOR[16]/WIRE[16]/ACTUATOR[16]。PC 端不靠对齐也能逐条解析；回卷后凭 seq 找最新、
凭 tick 对齐时间。

**★★ 关键调参 (实测踩出来的, 别凭感觉设批次大小)**:
- 批量 **16KB/批** ⇒ 命令+编程延迟把吞吐压到追不上产量(2.56MB/s) ⇒ **每 15s 丢 1.8 万条**;
- 改成 **256 条 = 64KB/批** ⇒ 丢包 **107/15s (0.07%)**, 吞吐 **2.57MB/s = 正好等于产量**;
- 且 `sd_log_poll` 每轮必须**连续追到追平** (上限 8 批) —— 一轮只写一批同样追不上。

**容量**: CSD v2 的 `C_SIZE` = CSD[69:48] = `(RESP2&0x3F)<<16 | RESP3>>16`;
容量 = (C_SIZE+1)×512KB。实测 **61,067,264 块 = 31.27GB, 与 Windows 报的完全一致** ✓。
按产量写满一圈 ≈ **3.4 小时**。

**自观测 (SD_DIAG @0x24000200)**: [45]1=续写/2=新建 [46]C_SIZE [47]下一块LBA
[48]累计条数 [49]累计丢包 [50]已回卷 [51]批次数 [52]头部刷新次数 [53]最近rc
[55]poll次数 [56]最大待落盘(判据: 是否 >512 ⇒ 环被冲) [57]本次丢包 [58]本次块数

**⚠ 已知残留**: 0.07% 丢包来自极少数瞬时落后 (max avail 到过 600 > 512 = 环容量)。
若要彻底消除 ⇒ 把 RAM 环从 512 槽(128KB)扩到 768 槽(192KB, 冻结区缩到 32KB)。

## ★★ 黑匣子第二层 bug: AXI SRAM 上电不清零 ⇒ 随机配置字 (2026-09-12 深夜, 提交 98bdc5e)

**症状**: 环里每槽**只有前 64 字节**是当拍数据, 后 192 字节恒为陈旧 SRAM。

**★★ 真因 (和它骗过我的方式)**:
`SD_CFG` 落在 **AXI SRAM**, 而 AXI 段在链接脚本里是 **`(NOLOAD)` —— 上电不清零**。
⇒ `BB_CFG[7]` 含随机垃圾 ⇒ **每一拍随机走 MDMA 路径(只搬 16 字)而不是 CPU 拷贝**;
⇒ `BB_CFG[4]` 也随机 ⇒ 我先做的那套"扫 10 组 CTCR 找搬运长度"**扫的全是随机值**,
   得出"与配置无关, 一律 32~64 字节"的假结论, 并据此做了错误的架构改动。

**⇒ 通用教训 (跨项目)**: **随机 SRAM 会伪装成"配置没效果"。**
凡"放在非零初始化区(NOLOAD)的一次性配置/状态", 必须加**魔数门**或显式清零。
本项目已有"诊断区先清零"的纪律, 但只加在 SD_DIAG 上, 漏了 SD_CFG —— 同一个坑第二次踩。
修法: `SD_CFG[15] == 0xF00DBEEF` 才认; 取走即清。调试器预写时连魔数一起写。

**★★ 我被自己的"部分判据"骗了两次, 记录在案**:
1. **"环里 tick 连续"就宣布黑匣子修好** —— 那只验证了**前 4 个字节**。
   ⇒ 判据必须覆盖**整个被声明修复的范围**, 不能挑一个容易过的字段。
2. **"回读 256 块逐字全对"** —— 比的是"卡 == 一个本身就残缺的环", 两边一致但都错。
   ⇒ **自校验只能证明"搬运没坏", 不能证明"内容对"**; 内容对必须拿**第三方源**(SHM 原文)比。

**修法**: 快照搬运默认 **CPU 字拷贝** (256B ≈ 130 拍 = 100us 拍预算 0.3%)。
MDMA ch1 保留但由魔数门选择。**判据: 能简单做对的, 别用复杂做错。**

**验证 (哨兵法: 环整片填 0xDEADBEEF, 数"变了几个字" = 实际搬运长度)**:
修前 16 字/槽 → 修后 **64 字 = 256B 全写**, 且 WIRE[0..3] = 0, 0.25, 0.004, 1.0
与直接读 SHM 的 WIRE_MAP[0..3] **逐字一致** ✓

**顺带确认的事实**:
- 真实 SHM 基址 = **0x200082A0** (`s_bb_shm` 指针, 别再用旧值 0x20008220);
  SHM 三段偏移: SENSOR_MAP 0x40 (64×f32) / ACTUATOR_STATUS 0x140 (64×f32) /
  WIRE_MAP 0x240 (**128**×f32) —— 记录里只带各 16 个 = **截断**, 待按需扩/裁剪。
- `.dtcm_shm` 也是 NOLOAD ⇒ 未登记区段留垃圾 (WIRE 的高位段就是)。
- PC 端读卡: 日志头 + tick 标注 + 容量 61,067,264 块 全部正确 ⇒ **SD/日志链路是faithful的**,
  唯一的问题在快照生成那一段。

## 事故: pyocd 只读会话把核心停住, 白等一分钟 (2026-09-12 深夜, 提交 a8fcf75)

**现象**: 让用户把 SD 卡插进板子等~1 分钟再拔出; 读卡发现**日志一个字节都没新增**。

**真因**: 我最后一次 pyocd 会话是**只读**(read32)且没带 reset ——
"connect_mode=halt" 连上即 halt, **命令结束后核心仍是 HALT**。板子从那时起就没跑过。
证据: g_tick_count 冻在 26162 (reset 后才重新开始涨)。

**★ 纪律 (项目备忘里早有, 我还是踩了)**:
- 只读会话也会停核。**凡需要板子接着跑的会话必须显式 `-c "reset"` (或结尾 `-c "go"`)**。
- 读到"什么都没变"时, **第一个要排除的就是"核心是不是停了"** ——
  读一个必然在变的量 (g_tick_count) 两次数值比一下, 这是最便宜的活性判据。
- 要**保留**运行期状态再读 ⇒ 用 `-c "go"` 收尾, 不要开头 reset。

**随事故暴露的真问题**: sd_log_open 只在开机调一次 ⇒ **卡插晚了就永远不记录**。
修法: 加 sd_reopen_log(), 由调试器预写 SD_CFG[8]=1 + 魔数 [15] 触发, 主循环取走即执行。
★ 明确**不做**固件自定时重试 —— sd_init 阻塞约 1s, 固件猜窗口必错 (g_persist_req 三次血证)。

**顺带确认**: 拍频 = 10 kHz (reset + 2s ⇒ tick +21069) ⇒ 产量 2.56 MB/s 符合设计。

## ★★ 飞行记录仪闭环 (2026-09-12 深夜) —— "每拍落盘 + tick 标注"端到端验证通过

**PC 端定量核查 16384 条连续记录**:

4. 卡片现在是**专用裸介质**(无文件系统), Windows 会一直提示格式化 —— 这是设计如此。

## 降丢包 (2026-09-12 深夜) —— 环 512->768 槽 + 刷头移出关键路径

**丢包的机制 (判据)**: avail > BB_SLOTS, 即"落后量超过环能吸收的量"。
先算账: 平均消费 14,243 槽/s > 产量 10,000 槽/s ⇒ **跟得上**;
而观测 [56] 最大待落盘 661 ⇒ **丢包 100% 来自瞬时卡顿**(SD 卡某次编程尾巴变长),
不是稳态能力不足。这决定了修法: **不是提速, 是加大吸收量 + 消掉自己造的卡顿。**

**改了三处**:
1. 环 512 -> **768 槽** (128KB->192KB): 吸收量 51.2ms -> 76.8ms。
   布局: 环 0x24004000+192KB / 冻结区 0x24034000+64KB / 低 16KB(诊断+scratch+do.c)不变。
   ★ 768 不是 2 的幂 ⇒ 槽索引用取模 (在主循环, 除法可接受; ISR 里仍只用比较+自增)。
2. **刷日志头移出关键路径**: 单块写要等一整段卡编程(几 ms); 插在追赶途中正好把
   avail 推过环容量 ⇒ 丢包。改成"攒够次数 + 本轮没写出去东西"才刷。
3. 简化吞吐自检 (原来要冻 128KB, 超出新的 64KB 冻结区), 并**删掉回读自校验**:
   自校验只能证明"搬运没坏", 证明不了"内容对"; 拿活环当靶子更会报假不符(182/256)。
   内容正确性交给"日志 + PC 读卡"这条第三方通路。

**待实测**: 需要卡在板子上跑 30s 对照 (上次 22s 丢 764 条 = 0.238%)。

## ★★ 变化率实测 -> 决定黑匣子记法 (2026-09-12 深夜)

**问题**: 用户问"96 B 够不够"。先量"实际用多少通道", 再量"数据多久变一次"。

**① 通道审计 (tools/shm_channel_audit.py)**: SHM 三段 (SENSOR 64 / ACTUATOR 64 / WIRE 128)
**全部被清零**(cold_start_reset 覆盖到了), 所以"垃圾值=未使用"这个判据在这里失效;
而且当前跑的是**测试程序**(SENSOR=0,0.5,0.1508,1… ACTUATOR 全 0) ⇒ **不能代表真实程序的通道数**。

**② 变化率统计 (固件内统计, 与上一拍逐通道比)**:
| 量 | 值 |
| 总拍数 | 224,345 |
| 有变化的拍数 | **16,802** ⇒ **变化率 7.49%** |
| 变化通道总数 | 18,258 ⇒ **平均一次只变 1.09 个通道** |

**⇒ 结论: 96 B 不够 (只能带 20 个通道, 而 SHM 有 256 个); 但正确解法不是缩记录, 是换记法。**

| 逐拍全量 256B (现状) | 2.56 MB/s | 96 ms | 48 |
| 缩到 96B | 0.96 MB/s | 250 ms | **20 (要砍)** |

- PC 端按"变化点 + tick"可**逐拍精确复原**(等价逻辑分析仪的阶梯重建);
- **优雅退化**: 若程序真的每拍都变, 就退化成"逐拍全量" = 现状, 不会更差。

  但只要"变化率 × 记录长度 < 拍内带宽", 缓冲就够。**数据本身若真不可压缩, 任何设计都救不了。**

**新增工具**: tools/shm_channel_audit.py (量各段通道占用) — 注意其"垃圾值"判据在本工程失效

## ★★★ 变化才记 落地 (2026-09-12 深夜) —— 丢包与卡顿同时解决

**做法 (关键设计决定)**: **不做变长记录**, 而是"**内容没变就不写**":
每拍仍算全量快照, 与"上一条**已写出**记录"的 48 个值 + 控制字逐项比; 全同则该拍不写、不占环槽。
=> 每条记录仍是**完整 256B 全量状态 + 自带 tick** ⇒ 两条之间的所有拍值**必然相同**
   ⇒ PC 端按 tick 可逐拍精确复原 ⇒ **数据无损, 省的只是重复**。
=> 记录格式/环结构/块结构/PC 解析**全不用改** (风险最小, 收益已拿到)。

**实测 25 秒对照**:

| 落盘块数 | ~134,000 | **10,368** (13x 少) |
| 记录数/总拍数 | = 拍数 | 20,896 / 274,316 = **7.62%** (与实测变化率 7.49% 吻合) |
| 最大待落盘 | 637~946 | **256** |
| **丢包** | 300~18,000 | **0** |
| 最大卡顿 [60] | 130 ms | **20.6 ms** |
| 慢轮询 [61] | 72 | **1** |
=> **卡顿跟着掉下来**: 批次数少 13 倍 ⇒ 撞上卡内部写抖动的时间窗口少得多。**丢包与卡顿一起解决。**

**★ 优雅退化**: 若程序真每拍都变 ⇒ 退化成"逐拍全量" = 原行为, 不会更差。
**★ 诚实的边界**: 7.62% 是当前静态测试程序的活跃度; 真实程序(带 PID/抖动输入)会更高。
   判据: 只要"变化率 x 记录长度 < 每拍可用带宽", 缓冲就够。数据若真不可压缩, 任何设计都救不了。

**PC 端**: tools/sd_log_read.py 已说明"tick 跳变是设计如此", 并新增"平均每条记录覆盖 N 拍"。

  · p=7.6% 时 1.26s 缓冲; p=15% 时 236 槽只够 **157ms** < 实测最坏卡顿 220ms ⇒ **丢包回来**
- **结论: 保持小记录才是鲁棒性来源。** 扩通道的正解不是放大记录, 而是:
  (a) **通道映射表**: 记录里 4 个字头 + 60 个数据字 = 正好 64 字 (现在只用了 48, 白扔 12 个)
      ⇒ 表头块(LBA0)存"槽 -> SHM 通道"的映射, PC 按映射标列名
  (b) 若要**全通道覆盖** ⇒ 另开一路**低频全量关键帧流**(1 次/秒 × 1040B = 1KB/s, 占比 0.02%),
      与增量环完全解耦, 不动增量通路
- **待用户定**: 是否做 (a)。属"顺手扩大范围", 按铁律先问。

**⑦ 仍未做 (需用户配合)**: 把卡插电脑, 用新判据核**变化才记的真实卡上数据** —— 这才是"对端视角"。

## 485 接线: 用户给出实际模块丝印 (2026-09-13 00:33)

- **`RXD/TXD` 是 MCU 视角** ⇒ 与板子**直连**: 模块 TXD→**PA2**, RXD→**PA3**; 不通就对调。
- **最高频漏项: 模块没供电** —— USB转485 引出 `5V` 就是给对端模块用的。
  VCC 二选一: 板子 3.3V (电平安全, 但 5V-only 的 MAX485 可能不工作) 或 USB485 的 5V
  (一定能跑, 但 TTL 输出是 5V ⇒ 建议 TXD→PA3 串 1k)。**两处不可同时接。**
- **PA2/PA3 的 5V 容忍性未确认** (官方数据手册不在本机, `find` 只找到一块 TFT 的)。
  ⇒ 结论里如实标注"未确认", 不替用户赌。
- 已写进 `docs/HARDWARE-PINOUT.md` §6.1。

## ★ 5V 容忍性查清 + 485 双向都不通的诊断 (2026-09-13 00:4x)

**★ PA2/PA3 = 5V 容忍 —— 从官方数据手册确认, 不再"未确认"**
- 来源: `D:/STM/work/.../Hardware Official Documentation/stm32h723zg.pdf` = **DS13313 Rev 5**,
  第 60 页引脚表 (用 **pymupdf 按词坐标还原表格行** —— 单元格级抽取会丢掉行上下文)。
- **PA2 = `FT_ha` / PA3 = `FT_ha`** ⇒ 5V 容忍; 图例: `FT`=5V tolerant, `TT`=3.3V tolerant。
  对照: PA5 = `TT_ha` (仅 3.3V), PA9 = `FT_u`。
- 手册还标注 **PA2=`USART2_TX(boot)` / PA3=`USART2_RX(boot)`** ⇒ 与固件配置一致 ✓
- ⇒ 485 模块 5V 供电**不需要串限流电阻**。边界: FT 只在数字模式成立 (模拟输入不得超 VDDA)。

**★ 485 首次联机: 两个方向都不通**
- 板子从 PA2 真发一条应答: **生成了** (`Δframes_tx=+1`, 用 0x62[1][1] + 0x60 注入驱动),
  但 485 口收回 **0 字节**。
- PC→板子: `Δframes_rx=0`。
- ⇒ 板子侧排除, 嫌疑集中在**共用部分: A/B 接反** 或 **未共地**。
- 用户的接线: USB485(A/B/GND/5V) ↔ 485TTL(A+/B+/GND/VCC/GND/RXD/TXD), VCC 接 USB485 的 5V。

**★ 方法论收获 (已补进 skill `uart-link-debug`)**: 
- "**两个方向同时死 ⇒ 先查共用部分**" 这条在 485 上非常有效 (A/B 极性是唯一能同时打死双向的)。
- 用**协议口命令板子主动发** (`0x62 [1][1]` + `0x60` 注入) 可以在**不需要用户动线**的情况下
  测出"板子→模块→总线→PC"这半条 ⇒ 双向解耦不用拆线。

## ★ "不接 VCC 模块却亮灯" = 寄生供电 —— 反而证明了三件事 (2026-09-13 00:41)

**用户观察**: 485 转 TTL 模块的 **VCC 悬空**、只把 **GND 接到板子** ⇒ **模块的灯亮了**,
USB 转 485 模块的**蓝灯也亮**。

**判读**: 这是典型的**寄生供电 (phantom powering)** —— 电流经某条信号线/总线的
ESD 钳位二极管灌进模块的 VCC 轨 (VCC ≈ 3.3V 或总线电平 − 0.7V)。它反过来说明:

1. ✅ **GND 通了** (没回路不会亮)
2. ✅ **A/B 已连到总线, 而且 dongle 在驱动总线** (否则没有源给总线供电)
3. ✅ 大概率**至少有一根 TTL 信号线也连着** (PA2 空闲高电平也能经模块输入脚二极管灌电)

**⇒ 物理连接其实是在的。** 那"两个方向都不通"就更能被**A/B 极性反了**解释 ——
A/B 反接不影响直流 (照样寄生供电), 但会把数据整个反向 ⇒ 两端都解不出帧。
与之前"发请求时偶收 1 字节 0xff"的痕迹吻合。

**⚠ 纪律**: 寄生供电是**非工作状态** (芯片欠压、LED 微亮), 结果不可信, 长期这样还可能伤模块。
⇒ **VCC 必须接上再测。** 保持 VCC = USB 的 5V (PA2/PA3 已是 FT_ha, 5V 安全);
不要改成 3.3V —— 那会引入"5V-only 芯片欠压"这个新变量。

**可以让用户做的一个判别实验 (10 秒)**: 只拔掉 **A/B 两根**, 保留 GND + TTL 线。
- 灯还亮 ⇒ 电是从 **TTL 侧(板子 PA2)** 灌进去的 ⇒ **TXD→PA2 这根线确认是通的**
- 灯灭 ⇒ 电是从**总线**灌的 ⇒ 说明 dongle 在给总线供电 (A/B 通)

## ★★ 关键突破: 板子的数据**确实过总线到了 dongle** (2026-09-13 00:5x)

**测试** (新加的 `rs485_probe.py --board-tx`): 让板子连续从 PA2 真发应答, 同时**只读** COM15。
**结果: 18 次注入 → 485 口收到 18 个 `0x00`, 一一对应; 空闲期 0 字节。**

**为什么这是突破**: 该模式**从不往 COM15 写**, 所以那 18 字节只可能来自总线
⇒ **板子→模块→A/B→dongle 这条物理通路是活的!** 之前"0 字节"是因为当时只发了一次、
或接线状态不同 (用户中间改过线)。

**并且两条推论**:
1. **空闲期干净 ⇒ 差分空闲极性正确 ⇒ A/B 没接反**
   (若接反, dongle 空闲时会持续看到"起始位" ⇒ 会灌出一大片 0x00, 而不是 0)
   ⇒ **上一轮"A/B 反了"的第一嫌疑降级**, 这里是实测否掉的。
2. 每次发送只框出**一个 `0x00`** ⇒ 数据到了但**电平劣化**(只能框出"低电平一个字节时长")
   ⇒ 与"模块 VCC 悬空、被寄生供电、驱动能力远低于规格"**完全吻合**。

**⇒ 当前状态不可信: 用户此刻没接 VCC。必须先接回 VCC 再测。**
**⇒ 判断顺序修正**: 不是 A/B 极性, 而是"**先保证模块在规格内供电**"。

**新增工具能力**: `rs485_probe.py --board-tx N` (板子连发 + 监听, 可同时看 LED) —— 
这是"**不需要用户动线就能测板子→PC 半条**"的复用手段 (0x62[1][1] + 0x60 循环注入)。

## ★ 同一测试两次结果不同 ⇒ 中间状态变了 (2026-09-13 00:46)

**同一个 `--board-tx` 测试, 6 分钟内给了两个不同结果:**
| 时刻 | 注入次数 | 485 口收到 | 当时状态 |
|---|---|---|---|
| 00:5x | 6 s / 18 次 | **18 字节 `0x00`** (1:1) | 模块 **VCC 悬空** (寄生供电) |
| 00:46 | 15 s / 43 次 | **0 字节** | (用户中间动过线/供电) |

同时刻其它事实: 固件侧 `frames_rx=43 frames_tx=43` ⇒ **板子 43 次都发出来了**;
总线**空闲 2 秒静默** (没被顶住); PC→板子 `Δframes_rx=0`; 双向全 0。

**★ 纪律**: **同一判据两次结果不同 ⇒ 先确认"被测对象的物理状态变了没有"**,
不要在两种状态下混着下结论。这也是"非侵入式观测"的另一面 ——
**用户的每一次动手都在改变被测对象**, 必须把"状态"当成实验条件记录下来。

**新假设 (待验)**: 模块的**驱动器可能一直使能** (非自动收发 / DE 常高)
⇒ 与 dongle 的驱动器在**半双工总线上互相打架** ⇒ 两个方向全死;
而 VCC 悬空时模块驱动太弱、顶不住总线 ⇒ 板子的数据"漏"出来一点, 恰好框成一个 `0x00`。
⇒ 判别实验: **只把 VCC 拔掉**, 其它不动, 复跑同一测试 —— 若"1 字节 0x00"复现, 假设成立。

## ★★ 自环测试工具 + 负对照抓出"frames_rx 两种字节源都算" (2026-09-13 01:0x)

**用户提出的怀疑**: "板子通信是在 100µs 内抽时间做的, 是不是代码问题?"

**先用数字回答**: **不是**。
| 量 | 值 | 标准要求 | 结论 |
|---|---|---|---|
| 每拍处理字节 | 4 (`MB_TICK_BUDGET`) | 115200 只需 1.15 字节/拍 | 3.5× 余量 |
| 每拍吞吐 | 40 kB/s | 11.52 kB/s | 够 |
| 帧间隔判据 | 4 拍 = 400 µs (`MB_SILENT_TICKS`) | 3.5 字符 = 304 µs | 合规 |
关键: **位时序全在 USART 硬件里, 固件只搬字节** ⇒ "切片"是**速率上限**, 不改线上波形。
只要缓冲不溢出, 与标准设备完全互通。

**但"是不是板子侧的问题"必须实测** —— 于是做了 `--loopback` (PA2↔PA3 短接自环):
- pyocd **读不了外设**又验证了一次: GPIOA 读回 `0xABFFFFFF`(陈旧 SRAM 特征值),
  USART2 三个寄存器读回全 0 ⇒ 按既定口径"返回 0 是读失败不是真值", **不能据此说 USART2 没使能**。
  ⇒ 外设只能**功能性**验证。
- 自环的时序技巧: `0x60` 注入会把 `src` 置成隧道模式, 回环字节只有 `src=0` 时才被读走
  ⇒ 用 **qty=125 (255B 应答, 约 6.4ms 推完)**, 注入后**立刻把 src 切回物理口**抢到尾巴。

**★★ 负对照抓到判据漏洞**: 第一版用 `Δframes_rx` 判定 ⇒ **无短接也报"成功"**。
根因: **`frames_rx` 两种字节源都计数**(隧道注入 + 物理口各算一帧), 那 +1 只是我注入的帧自己。
⇒ 换成 `Δerr_crc + Δerr_exc` —— **注入的请求是合法帧, 永远不会产生这两个量**,
   回环回来的应答被当请求解析才会产生 ⇒ 换成它之后负对照正确 FAIL ✓

**新增能力**: `rs485_probe.py --loopback --proto COMxx`
(负对照已跑通: 未短接 ⇒ FAIL; 短接 ⇒ 应 PASS)

## ★★ 把 Modbus 物理口换到 PD5/PD6 (用户要求"用2个干净的脚") (2026-09-13 01:1x)

**动机**: 用户坚持"接线没错" ⇒ 唯一还没排除的是 **PA2/PA3 本身有问题**
(引脚损伤 / 板上丝印认错 / 被片上其它功能占用)。

**做法**: USART2 有**备用引脚**, 只换脚、协议一个字不改。
- 官方 AF 表确认 (DS13313 Rev5 **p68** AF7 列, 按引脚顺序):
  PD3=USART2_CTS / PD4=USART2_RTS / **PD5=USART2_TX** / **PD6=USART2_RX** / PD7=USART2_CK;
  PD6 行明确标 `FT_h` (5V 容忍)。
- 按项目既定的 **A/B 开关写法** (照 DCL_VTOR_ITCM):
  `CMakeLists.txt` 加 `set(DCL_MB_UART_ALT "1" CACHE STRING ...)` + `-DMB_UART_ALT=...`;
  `build.sh` 的 DEFAULTS 加 `-DDCL_MB_UART_ALT=1`; `modbus.c` 用 `MB_UART_ALT` 选引脚。
  换回 PA2/PA3 = 只改一个开关。

**★ 顺手补了一个"沉默杀手"**: `mb_uart_enable()` 原来**自己不开 GPIO 时钟** ——
对未开时钟的外设写入会被硬件**静默丢弃**(读回 0, 不报错)。
PA 的时钟碰巧被 `pin_out_init(PA8)`(main.c:2228) 早开; **PD 的时钟只在 sd_init 里开,
而 sd_init 在 mb_uart_enable 之后** ⇒ 不自己开就必然失败。现在两种映射都自己开时钟。
**★ 另加 RX 内部上拉**: 线上没驱动时读成空闲(高), 而不是悬空拾噪 (与 uart.c 对 PA10 同口径)。

**★ 修掉 modbus.h 里的一个真陷阱** (也是本次编译失败的根因):
```c
#define MB_UART_GPIO_PORT   'A'   /* 仅文档用途 */
#define MB_UART_TX_PIN      2
#define MB_UART_RX_PIN      3     /* 注释还写"本批次不接收"—— 早就过时, 代码明明在收 */
```
`'A'` 是**字符常量 65**, 看着像端口号、真拿去用就是错的; 又与 modbus.c 新增宏**重名**
⇒ `error: "MB_UART_GPIO_PORT" redefined`。三个都撤掉, 引脚真值统一到 modbus.c 一处。

**验证**: 构建零警告, `DCL_MB_UART_ALT = 1`, 烧录确实编程 41984 字节;
烧后协议口 + 通信域仍正常 (0x62 回 `00 01 04`; 0x60 注入后 frames_rx/tx 各 +1)。

**★ 关于用户让跑的"PD5↔PD6 自环"**: **不跑** —— 上一轮已查明该判据**结构性失效**
(FSM 发送期间不拉 RX; 只剩 1 字节且 rx_len<4 会被丢弃)。再跑只会产出一个误导性 FAIL。

## ★★★ LA 抓到实锤: 整条 485 链路是好的, 锅在"模块 TXD → 板子 RX"那一段 (2026-09-13 01:2x)

**做法**: 用户把 LA 接到 485-TTL 模块的 RX/TX 上 ⇒ 我一次性抓 **8 个通道**
(1 MHz, 0.3 s, 导出 raw CSV 数跳变), 同时 PC 在 COM15 持续发 **0x55** (规整方波, 好认)。

**结果**:
| 通道 | 跳变数 | 首/末电平 |
|---|---|---|
| **Channel 0** | **44,679** (0.389 s, 114.8 kHz 跳变率) | 1→0 |
| Channel 1..7 | **0** | 恒 1 |

**间隔统计 (决定性)**: 中位数 **9.00 µs**, **100% 落在 8.68 µs ±15% 内**;
最多的两个值 **9.0 µs × 29656 / 8.0 µs × 15020** = 1 MHz 采样对 8.68 µs 位宽的量化。
0x55 每字节 10 次跳变 × ~16 kB/s ≈ 160 k 跳变/s ⇒ 预期 0.3 s ≈ 48 k, 实测 44.7 k ✓
⇒ **Channel 0 上就是我这串 0x55 @115200, 波特率分毫不差。**
(顺带: 这一次同时**验证了 LA 时基** —— 真正的阳性对照。)

**⇒ 这意味着**:
- USB转485 dongle 发送 ✓
- **A/B 差分对通、极性正确** ✓ (否则数据不可能还原成规整方波)
- 485转TTL 模块**供电正常、接收正常、TTL 输出正常** ✓
- 数据确实到了模块的 TTL 输出脚(TXD 或 RXD 之一, 带数据的那根必是**输出**) ✓

**⇒ 故障被锁死在"模块带数据那根脚 → 板子 RX(PD6)"这**一根**线上。**
最可能的两条:
