## ★★★★ AS5600 打通 (2026-09-15) —— 卡点是**我自己的位掩码 bug**

### 结果
```
组0 (PB10=SCL, PB11=SDA): ACK=1 ✓  RAW_ANGLE=2818 (247.7°)
组1 (接反): ACK=0     组2/3 (PB6,7 / PB8,9): 无上拉无应答
输出通路自检: 拉低读回 0x0000 ✓  释放读回 0x0C00 ✓
STATUS(0x0B)=0x0B → MH=1 (磁场太强); 之前读 AGC(0x1A)=0x8007 (AGC≈7, 接近最小)
```

### 根因（与 `CTCR=0x00020000` 同族：**位偏移错一位**）
`GPIO_MODER / PUPDR / OSPEEDR` 是**每引脚 2 位**；`OTYPER / ODR / IDR / BSRR` 是**每引脚 1 位**。
我图省事只写了一个 `as_pair_mask() = (1<<10)|(1<<11)`，然后
`GPIO_MODER |= as_pair_mask()` → **实际改的是引脚 5 的两个位**，PB10/PB11 **从未切成输出**
⇒ 线一直是输入、被模块上拉拉高 ⇒ I2C 的 **START 条件根本不成立** ⇒ 永远收不到 ACK。
★ 现象与"器件不应答"**一模一样**，害我往硬件上猜了三轮（供电电压/PGO/DIR）。
修法：拆成 `as_bit_mask()`(1位/引脚) 与 `as_2bit_mask()` / `as_moder_out()`(2位/引脚)。

### ★★ 抓住它的那个判据（值得复用）
**"输出通路自检"：把引脚驱动到低，再读 IDR，期望读到 0。**
前几轮只看了"有没有上拉、有没有 ACK"，**从没验证过自己能不能拉低** ——
这是本项目"凡写进去就不再读一眼的配置都违规"的又一实例。**加上它，一轮就定位了。**

### 接线结论（已实测）
`5V`→板 +5V、`GND`→板 GND、`SCL`→PB10(U9 pin44)、`SDA`→PB11(U9 pin42)、
`PGO` **悬空**（接 GND 会进编程模式）、`DIR`→GND。
★ 磁铁太近（MH=1, AGC≈7）⇒ 间隙调到 1~2mm。

## 正式 I2C 驱动落地 (2026-09-15) —— 新增 4 个源文件 + 两个新教训

### 交付
- `src/i2c_bb.{h,c}` — 位操作 I2C 主机 (引脚可配置、有界等待防挂死、NAK/卡死计数、
  **`i2c_bb_selftest()` 输出通路自检**)。
- `src/as5600.{h,c}` — AS5600 驱动：读 RAW ANGLE(0x0C/0x0D) + STATUS(0x0B)，
  写 `SENSOR_MAP[0]`(原始值) 与 `[1]`(度数)；**读失败时保留上次值，不写 0**
  （把"没读到"伪装成"角度=0"会让闭环跑飞）。
- `main.c`: 主循环每 10ms 调 `as5600_poll()`；`op=17` 上电诊断(4 组引脚对扫描)、
  `op=18` 运行态读回。CMakeLists 加了两个源文件。
- **架构决定**：不上硬件 I2C。实测需求只有 10ms 读 2 字节(≈250µs，占主循环 2.5%)，
  不值得引入 `TIMINGR/ANFOFF/H7 errata` 一堆新失败面。★ 将来预算吃紧再换，那时有判据可对照。

### 验收 (走 COM21 串口，CH340 已恢复)
`ok_n` 3 秒 +279 ⇒ **93.0 次/秒**(期望 100)；`err_n=0`；I2C 事务 186/s = 93×2 ✓ 自洽；
`raw=2944 (258.75°)`、`STATUS=0x27 MD=1`。读数 6 秒内**不抖**(只有 1 个不同值)。

### ★★ 新教训 1：**"模运算当调度器"会让周期任务跑多次**
`if ((g_tick_count % 100u) == 0u) as5600_poll();` —— 主循环**一拍内转很多圈**，
命中那一拍里会**反复调用** ⇒ 实测 190/s(期望 100)。改成**边沿触发**:
`if ((int32_t)(g_tick_count - s_next) >= 0) { s_next = g_tick_count + 100u; ... }`
(无符号减法天然处理回绕)。★ 同族: 凡"用取模做节拍"的地方都要查一遍。

### ★★ 新教训 2：**8 位寄存器不能用 16 位读法解码**（我又踩了"宽度"这一族）
我用 `as_read16(0x0B)` 读 STATUS，返回值是 `[0x0B, 0x0C]` 两个字节拼成的 16 位数
⇒ 解码时把 **0x0C(角度高位)** 当成了状态的高字节，于是把 `0x270B` 读成"MH=1 磁场太强"，
还让用户去调磁铁间隙。**正确单字节读**下 `STATUS=0x27` ⇒ **MD=1 磁场正常**。
★ 与 `CTCR=0x00020000`(宽度/偏移错)、`MODER` 掩码错 是**同一族**，这已经是第三次。
  ⇒ 规矩：**读寄存器前先确认它的宽度**；多字节读出来的量, 解码必须逐字节对齐地址。

## 步进脉冲源 + DO 面接通 (2026-09-15) —— 软件就绪, 安全态已验证

- `hil.c`: 输出臂开头 `if (g_step_owns_tim3) return;` —— **同一引脚的排他使用必须显式串行化**，

## ★★ 电机不转的定案 —— "A 0.116V / B 4.5V / C 5V" 判读

### 三个读数
| 点 | 位置 | 读数 | 期望 |
|---|---|---|---|
| A | PA6（U9 pin19）对 GND | **0.116 V** | 500Hz/50% ⇒ DC 档读**平均值** ≈1.65V |
| B | TB6600 `PUL−` 对 GND | **4.5 V** | 接通时应被光耦 LED 钳到 ~1.0~1.5V |
| C | TB6600 `PUL+` 对 GND | **5 V** ✓ | 稳定 +5V |

### 判读（两条独立结论）
1. **测量时脉冲已经停了**（A=0.116V ≈ 静态低）。限时 60s 到点自动 `step_stop_safe()`
   ⇒ CC1E=0 ⇒ AF 引脚回到非激活态(低)。**所以这次测量没在"脉冲在跑"的条件下做**，
   不能用它判断"PA6 有没有输出"。⇒ 这是**限时机制**（正确行为）造成的假象，不是故障。
2. ★★★ **A 与 B 本来是同一根线的两端，测出来差 4.4V ⇒ 这条通路没连通。**
   更细一层: PA6=0V 时若线是通的，光耦 LED 会被 +5V 经内部限流电阻正向点亮，
   `PUL−` 必然被钳在 LED 正向压降附近(~1.0~1.5V)。实测 4.5V ⇒ **几乎没有电流流过光耦**
   ⇒ 断线 / 插错端子。（4.5V 而非 5V，符合"`PUL−` 悬空、仅经内部电阻+LED 挂到 +5V，
   10MΩ 表头形成微弱分压"。）

⇒ **结论: PA6 → TB6600 `PUL−` 这根线没接通（或插进了旁边的端子）。与软件无关** ——
   软件侧三件套已自证: `PA6_MODER=2(AF)` + `AFRL[PA6]=2(TIM3)` + `TIM3_CNT` 在跑 + `CCER.CC1E=1`。

### ★★★ 为此新增的判据工具: **PA6 静态电平探针**（`0x39 op=19 sub=7/8/9/10`）

**为什么必须新增**: 万用表 DC 档量 500Hz 方波读的是**平均值(≈1.65V)** ⇒
"线通(被 LED 钳到 ~1.2V)"与"线断(浮空 ~4.5V)"在表上只差一点点，判不了；
而且"脉冲还在不在跑"本身还是个变量（带限时）。
⇒ 把 PA6 **从 TIM3 上摘下来**、输出**确定的静态电平**，读数就没有任何歧义:

```
python tools/h723_stepper_test.py probe high   # PA6 → GPIO 输出 3.3V
python tools/h723_stepper_test.py probe low    # PA6 → GPIO 输出 0V
python tools/h723_stepper_test.py probe af     # 还原 TIM3_CH1 (CC1E=0, 仍无脉冲)
python tools/h723_stepper_test.py probe od 1   # PA6 输出类型改为**开漏** (候选修复)
```

判定表（在 **U9 pin19** 与 **TB6600 `PUL−`** 两处对 GND 各量一次）:

| U9 pin19 (high/low) | `PUL−` (high/low) | 结论 |
|---|---|---|
| 3.3 / 0 | ~2~4 / ~1.0~1.5 | ✅ 线通、端子对 |
| 3.3 / 0 | **4.5 / 4.5 不动** | ✗ **线断 / 插错端子** ← 当前最可能 |
| 3.3 / 0 | 0 / 0 | ✗ `PUL−` 被短到 GND |
| 本身不是 3.3/0 | — | ✗ U9 pin19 认错了 / **板载摄像头座器件拉住 PA6**（PA6 网络名亦为 `DCMI_PIXCLK`，见 `HARDWARE-PINOUT.md` §4.1） |

★ 探针**零风险**: 进入前先 `step_set_rate(0)` 关 CC1E（保证无脉冲），只切
`MODER/AFRL/OTYPER/PUPDR`，不碰别的资源；`probe af` 完整还原。已实测三档切换正确。

### ★★★ 顺带修掉的真 bug: `0x39 op=19` 应答**栈越界 28 字节**

`h_pin_pattern()` 里声明 `uint8_t r[40]`，而该分支写到 `r+64..r+67`、`ack(r, 68u)`
⇒ **栈上越界写 28 字节**。它不报错、不崩，只会把调用者的局部量/保存寄存器写坏 ——
正是本项目最恨的"运行期行为不对、却查不出谁写坏的"形态。
★ 最阴的一点: 读回来的 17 个字段**全是合理值** ⇒ 越界在观测面上**完全看不见**。
判据只能来自"数一数最多写到哪个偏移"这种**静态**检查。
⇒ 已改 `uint8_t r[80]`，顺带把应答扩到 76B（尾部加 `GPIOA_ODR` / `GPIOA_OTYPER`，供探针回读）。

## ★★★★ 更正上一条判读 —— 是**软件侧**，不是接线（2026-09-15 晚）

### 用户给的完整现象（推翻了前一条结论）
`DIR− = 3.4V`、`ENA− = 3.4V`、所有 `+` 端 = 5V、`PUL− = 4.5V`；
**换了一根线，结果完全一样**。

### 先立一个物理硬约束
**推挽输出不可能把自己脚上的电平抬到 VDD 以上。**
`PUL− = 4.5V > 3.3V` ⇒ 那一刻 **MCU 根本没在驱动这个脚**（高阻），
4.5V 是外面经"驱动器内部电阻 + 光耦 LED"把脚拉上去的。
⇒ 那 4.5V **不是"断线"的证据**，而是"**脚是高阻**"的证据。前一条结论作废。

### 新增的硬判据: `GPIOx_IDR`（引脚**真实**电平，与谁在驱动无关）
`h_pin_pattern` 的 `op=19` 应答尾部加 `GPIOA_IDR`(bit6) / `GPIOE_IDR`(bit8..11)。
比对 **ODR 与 IDR**：

| ODR | IDR | 含义 |
|---|---|---|
| 0 | 0 | 我们在驱动低 ✓ |
| 1 | 1 | 我们在驱动高 ✓ |
| **0** | **1** | ★★ **不是我们在驱动** —— 高阻 + 外部上拉 |

### 实测（芯片自读，无万用表参与）
| 状态 | MODER | CC1E | **IDR(PA6)** |
|---|---|---|---|
| `probe high`（GPIO 输出 3.3V） | 1 | 0 | **1** ✓ |
| `probe low`（GPIO 输出 0V） | 1 | 0 | **0** ✓ |
| **`probe af`（TIM3 AF，无脉冲）** | 2 | 0 | **1** ⇒ **高阻** |
| AF + 500Hz 脉冲（`idrwatch`） | 2 | 1 | **0 出现 38 次 / 1 出现 49 次** ⇒ **真的在翻转** |

### ⇒ 两条结论
1. **☆☆☆ PA6 在"AF 模式 + CC1E=0（无脉冲）"时是高阻，不是低电平。**
   于是"没脉冲"时 `PUL−` 会浮到 ~4.5V —— 极易被误判成"断线 / 插错端子 / 软件没输出"。
   **本次就是这么被带偏的。**
2. **脉冲其实一直都在出**：CC1E=1 时 IDR 同时出现 0 和 1 ⇒ AF2/TIM3 通路接到了引脚上。
   ⇒ **"MODER=AF + AFRL=2 + CNT 在跑 + CC1E=1" 这四件套读回全绿，之前被当成"引脚必然在翻转"，
     而真正能证明的只有 IDR。**（这次四件套恰好是对的，但当时它并没有证明力。）

### ★★★ 新的判据纪律
- **凡"引脚在无脉冲时读不到电平"，不能推出"引脚不工作"** —— 必须**在有脉冲时**判，
  且判据用 **IDR**（引脚真实电平），不用"寄存器配置"。
- ★ 万用表量"某个信号端"时，**必须同时知道那一刻引脚在被驱动还是高阻**。
  否则 4.5V 这种数既像"断线"又像"高阻上拉"，**根本不可区分**。
- ★ 这正是本项目"配置全对 ≠ 功能可用"的又一次：这次连"功能可用"的**观测手段**本身也是错的。

### 下一步（待办）
- 用 `probe high`（PA6 推挽 3.3V，形态与 `DIR−/ENA−` 完全相同）让用户量 `PUL−`：
  **3.4V = 通路好 / 4.5V = 通路断**。这是唯一可比的口径。
- 若通路好 ⇒ 电机不转的原因转向 **§2.2"3.3V 高电平关不断 5V 光耦"**（LED 在 3.3V 仍有电流
  ⇒ 驱动器看到"一直导通"⇒ 不计数）⇒ 修法 = **PA6/PE8/PE9 改开漏**。

### ★★★ 我的回应（`docs/audit/H723-MOTION-QUALITY-RESPONSE.md`，新建）

**① D2 根因更正 —— 不是"时钟/分频按错"，是 `step_tick()` 每次调用取整**

    uint32_t dm = dt / 10u;    /* dt ≈ **主循环一圈**, 不是固定的 1ms */

- **判据**：固定倍率的时钟错**只能给恒定倍率**；但实测倍率**随主机负载变 21%** ⇒ 直接排除。
- 取整 ⇒ 累计**永远 ≤ 真实** ⇒ **只会慢、永不快**；丢多少取决于"一圈多长" ⇒ 随轮询变。
- ★★ **零运动实测**（`g_step_deadline_tick` 的递减与 `CC1E` 无关 ⇒ 不开脉冲也能量）：

  | 档 | 实测/秒 | 反推一圈 |
  |---|---|---|
  | 静默 | 648.9（−35.1%） | 15.4 拍 = **1.54 ms** |
  | 密轮询 | 789.1（−21.1%） | 12.8 拍 = **1.28 ms** |

  两档都落在 `k = floor(dt/10) = 1` ⇒ 指纹就是"**每次记 1 ms，真实过了 1.3~1.5 ms**"。
  `dt_max = 684 < 1000` ⇒ **未撞钳位**，钳位不是成因。
- **修法（两行）**：限时改成 **目标拍号**，用一次减法判到期，**不做除法**：
  `s_dl_tick = tick_now + ms*10; if (armed && (int32_t)(tick_now - s_dl_tick) >= 0) 到期;`

**② D3 机制 —— 顺序 × 一个值两个语义**（原文只有现象，没机制）

  `cmd_units` 是 `d.limit(units)` → `d.rate(500)`，**两条独立帧，中间隔着主循环**。
  小限时在 `rate()` 到达**之前**就被吃光；吃光走 `step_stop_safe()`，它把 `tleft` 置 **0 = 不限时**（C4）
  ⇒ 紧接着的 `rate(hz)` **无限跑**，直到下一条命令。
  ★ 零运动复现（全程 `ENA=0` ⇒ 驱动器失能 ⇒ 轴保证不动）：`CC1E=1` 而 `tleft=0`、`stop_n` +1 ✓

**③ D2 / D3 是同一个函数的两面** ⇒ 一次改动（目标拍号 + 独立 `armed` 位）同时收掉 **D2 + C4 + D3**，
   并为 D4（固件内计数/定位）打下正确的时间基。

### ★ 读架构文档后查到的五条硬事实（决定标准能不能立）
1. **★★★ "程序持久化"现在是不成立的**：交付档 `DCL_PERSIST_SAVE=0`，
   `0x43` 保存**明确 NAK**（`main.c:2686`）。原因：擦 128KB 内 flash 时 **ISR 卡死 210.6 ms**
   ⇒ 喂狗停 ⇒ 看门狗复位 ⇒ 旧行为是"点保存 = 重启机器且没落盘"。降级处置正确，但**功能确实没有**。
2. **★★★ 满配程序刚好等于最大帧载荷**：`6 + 128×16×3 = 6150`，而 `FRAME_PAYLOAD_MAX = 6150`
   ⇒ **一个字节余量都没有** ⇒ 加不进版本/CRC/清单/program_id。
3. **★★ 三个程序模型并存且规则不同**：路由表(`0x10`, ISR, 可热更, 不要求 STOP) /
   顺序域(`0x44`, ISR, **不热重载**, 必须 STOP) / macro(`0x41`, **主循环**驱动, 落盘口径未决)
   ⇒ macro 的循环挂主循环 = **与 D2/D4 同一条病**。
4. **★★ 能力位里没有"外设"这一类**（只有 MULTICYCLE/HOTRELOAD/PERSISTENT/…/AI/MACRO）
   ⇒ 程序**无法声明"我要 I2C"**，上位机**无法在上传期拒绝** ⇒ 违反本项目自己的判据纪律
   （"未实现的能力必须在下载期失败" —— `SRC_HMI` 已是好范式）。
5. **★ 架构里已埋了正解但没做**：macro VM 有 `0x20-0x23 SPI **未迁移 → -4**`
   ⇒ **"通用外设事务 op"的思想早就有**。I2C 本可做成 macro 的通用事务 op，
   那样"支持新传感器"=写一段程序，而不是改固件。实际却是写了专用驱动 `as5600.c` +
   专用诊断命令 `0x39 op=17/18` —— **恰好绕过了这条分界**。
