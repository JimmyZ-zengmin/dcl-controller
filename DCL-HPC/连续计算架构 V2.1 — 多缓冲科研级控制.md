# DCL-HPC — 科研级连续计算架构 V2.1

> **DCL-HPC (High Precision Controller)**：DCL 控制器体系中的**高端系列**，面向科研级精密控制。
> 前代（V1.x）为通用工业控制器，V2.x 为**超标量计算架构**——CPU 自由循环连续计算，DMA 独立搬运，两者通过多缓冲解耦。
> 状态：**前沿研究**（未实现，基于 DTCM 双端口 + 多缓冲 + MDMA 能力分析）

| 维度 | V1.x (通用工业) | V2.x (科研级) |

| 难度 | 常规嵌入式开发 | **硬件/内存协同设计** |

## 1. 双设计哲学

> DCL-HPC 不追求"用更快的 ISR 替代 ISR"，而是**完全放弃"时间同步"范式，转向"时间与内容解耦"**。
> 这决定了 V2.1 的两个独立方向——它们可以同时存在，互不干扰。

### 1.1 方向一：急速响应 → 已独立成文

> 方向一的完整技术方案（含伺服电流环应用、硬件选型、市面对比）已独立为：
> [`伺服驱动器 — V2.1 连续电流环架构.md`](伺服驱动器%20—%20V2.1%20连续电流环架构.md)

**核心思路：不在乎输出时刻的精确度，在乎输入到输出的最短路径。**
CPU 不再"等触发"——传感器数据到 CPU 的时间 ≈ 从 DMA 写完 DTCM 到 CPU 下一次 LDR 的时间 (~6ns)。

流式输出：DMA 持续搬走 SHADOW，CPU 可能在算但 DMA 搬走的是"上次算完的旧值"——每次 PWM 周期都输出"当前已知的最优值"。

**适用场景：** 伺服电流环、力控制、碰撞检测、传感器融合、高频扰动补偿。

---

### 1.2 方向二：时间硬周期（精密脉冲模式）

**本质：输出边沿的抖动必须由晶振保证（<10ns），但内容可以是"不完整的"。**

这与方向一形成对照：

| | 方向一（急速响应） | 方向二（时间硬周期） |
|------|----------------|-------------------|
| 追求 | 延迟低 | 时间准 |
| 内容 | 必须是最新 | 旧值也接受 |
| 触发 | 越快越好 | 精确到 ns |
| 典型 | 伺服电流环 | 激光振镜、脉冲发生器 |

**DMA 自己保证时间，不需要 CPU：**

```
DMA 触发时间点（硬件定时器决定，抖动 = 晶振 < 1ps）:

  T=0ns      T=200ns    T=400ns    T=600ns    T=800ns    T=1000ns
  ↓          ↓          ↓          ↓          ↓          ↓
  [搬SHADOW]  [搬SHADOW]  [搬SHADOW]  [搬SHADOW]  [搬SHADOW]  [搬SHADOW]
  内容=A      内容=B      内容=C      内容=C      内容=D      内容=E
  ↑ CPU 写完  ↑ CPU 写完  ↑ CPU 写完  ↑ CPU 没写完  ↑ CPU 写完  ↑ CPU 写完
                              但 DMA 仍然准确在 600ns 时刻触发
                              搬走的是 400ns 时刻的值 C (重复)
```

**← 边沿抖动 = 0（硬件级）**
**↑ 内容"年龄" = 不定（由 CPU 进度决定）**

这意味着输出信号的频率/相位的确定性完全由硬件锁存，不受 CPU 计算进度影响：

```
激光开光点要求在 T=200.000ns ± 1ns 处翻转 → DMA 硬件保证
开光时输出的脉宽要求精确 150.000ns → DMA 硬件保证
但这个脉冲的"幅度"是 150ns 还是 151ns 不重要
重要的是边沿位置精确到 <10ns
```

**适用场景：**
- 激光振镜控制 / 精密脉冲发生器
- PWM 载波同步 / 多轴同步锁存
- 任何输出边沿精度 > 输出内容精度的场景

---

### 1.3 两方向共存：同一个硬件，两种人格

DCL-HPC 不需要在两者之间二选一——同一个硬件可以同时服务两个方向：

```
                         ┌─────────────────────────┐
                         │ TIM2_CH1 @ 100ns          │──→ DMA: 输出电压/电流
                         │ (方向二: 时间硬周期)        │     内容可能是上一轮计算值
                         │                            │
  ADC → 三缓冲 → CPU 算 →┤ TIM2_CH4 @ 900ns          │──→ DMA: 更新 SHADOW 输出
  (方向一: 急速响应)      │ (方向一: 数据更新时刻)      │     (只在这个点写入新值)
                         │                            │
                         │ 方向一决定了"响应有多快"     │
                         │ 方向二决定了"输出有多准"     │
                         │ 两者通过三缓冲互不干扰       │
                         └─────────────────────────┘
```

### 1.4 与 V1.x ISR 引擎的决定性差异

V1.x 的 ISR 引擎的时间确定性无可置疑——它由晶振+PLL+定时器+硬件中断响应保证。但它的代价是 **CPU 在 ISR 之外的"空转时间"完全浪费了**。

V2.1 用如下方式弥补"没有 ISR 强制打断"的缺失：

| 保障层面 | 机制 | 确定性来源 |
|---------|------|----------|
| **输出时间** | DMA 由 TIMx 硬件触发 | **晶振 < 1ps** |
| **CPU 进度** | 每 1024 条路由查一次 TIM2_CNT | **被动检查，不打断** |
| **卡死兜底** | DMA 持续输出最后一次写入值 | **硬件独立于 CPU** |
| **外部监控** | PE2 每次 DMA 完成时硬件翻转 | **示波器可视** |

**结论：V2.1 的"时间确定性"不是靠强制打断实现的，而是靠"输出路径纯硬件化 + 被动进度检查 + 三缓冲内容隔离"的三层设计。**

## 2. 核心洞察：TTM（Time-Triggered Memory）模型

### 2.1 从"同步触发"到"异步隔离"

传统实时控制系统的思维定式：

```
采样 → 中断 → 计算 → 输出 → 等待下一个采样
         ↑ 所有操作同步在一个时钟节拍上
```

DCL-HPC 打破这个定式：

```
DMA ──→ [ADC_BUF_A] ──→ CPU 读 ──→ [SHADOW_A] ──→ DMA ──→ GPIO
        [ADC_BUF_B]             ←── 永远是不同缓冲区       [SHADOW_B]
        [ADC_BUF_C]                                            [SHADOW_C]
         ↑ 三缓冲输入                 ↑ 三缓冲输出
```

**核心思想**：CPU 和 DMA **不需要知道对方在做什么**，因为它们操作的是不同的内存地址。这是通过**多缓冲 + 指针轮换**实现的物理隔离。

### 2.2 DTCM 双端口的正确理解

STM32H723 的 DTCM 两个端口物理独立：

```
                  CPU(D-bus)                DMA(AHB矩阵)
                  │ 64-bit 零等待               │ AHBS路径
          ┌───────┴───────┐          ┌─────────┴─────────┐
          │  DTCM Port 0  │          │   DTCM Port 1     │
          │ (CPU D-bus)   │          │ (M7 AHBS)          │
          └───────┬───────┘          └─────────┬─────────┘
                  └──────────┬─────────────────┘
                             │
                          DTCM RAM
```

**端口级是零仲裁的**（CPU 和 DMA 各走一个物理端口），但需要注意：

- **DMA 访问 DTCM 的路径**：DMA2 → D2 AHB矩阵 → D2→D1桥 → AXI矩阵 → M7 AHBS → DTCM Port 1
- 这条路径有**多级总线仲裁**，但仲裁的是**传输请求**，不是**DTCM 访问**
- 一旦请求到达 DTCM Port 1，访问就是独占的，不影响 CPU 在 Port 0 的访问
- **多缓冲策略彻底消除了地址级竞争**——CPU 和 DMA 操作的 DTCM 地址不同，即使路径存在仲裁，两者也不会等待对方

| CPU 在做什么 | DMA 在做什么 | 地址冲突？ | 端口冲突？ |
|-------------|-------------|-----------|-----------|
| 读 ADC_BUF_C (Port 0) | DMA 写 ADC_BUF_A (Port 1) | ❌ 不同地址 | ❌ 零冲突 |
| 写 SHADOW_C (Port 0) | DMA 读 SHADOW_A (Port 1) | ❌ 不同地址 | ❌ 零冲突 |
| 读 WIRE_MAP (Port 0) | DMA 写 WIRE_MAP (Port 1) | **⚠ 同地址** | ❌ 端口独立 |
| 读 TIMING 区 (Port 0) | MDMA 搬日志 (Port 1) | ❌ 不同地址 | ❌ 零冲突 |

> **只有 CPU 和 DMA 访问完全相同的 DTCM 地址时，才可能因 SRAM bank 内部仲裁出现单周期等待。** DCL-HPC 的多缓冲策略保证了这种情况在关键路径上**不会发生**。

## 3. 架构总览

### 3.1 与 V1.x 的直观对比

```
V1.x (多速率共振调度):

  TIM2 (1μs) ─── ISR ─── CPU 算一点 ─── 退 ISR ─── 等下一个 1μs ─── ISR ...
                 ↑                     ↑
             160ns 开销          计算时间片 < 840ns
             CPU 被中断夺走      CPU 工作在"片段模式"


V2.1 (DCL-HPC 连续计算 + 多缓冲):

  CPU: [算][算][算][算][算][算][算][算][算][算][算][算]... 永不停止
         ↕ 读 ADC_BUF_C  ↕ 写 SHADOW_C
         ←── 永远操作"安全"缓冲区 ──→

  DMA: ══ADC→BUF_A══ADC→BUF_B══ADC→BUF_C══ADC→BUF_A══→ (输入循环)
       ══SHADOW_A→GPIO══SHADOW_B→GPIO══SHADOW_C→GPIO══→ (输出循环)
       
  定时器: TIM(UIE=0): 仅 DMA 触发, 不产生中断
```

### 3.2 与"流水线工厂"类比

```
                    ┌──────────────────────────────────┐
                    │         DCL-HPC 计算核心           │
                    │                                  │
  原料库 ←─── DMA ──┤  ┌──────┐ ┌──────┐ ┌──────┐  ├─── DMA ───→ 成品库
  (ADC_BUF_A)       │  │BUF_C │ │BUF_B │ │BUF_A │  │            (SHADOW_A)
  (ADC_BUF_B)       │  └──────┘ └──────┘ └──────┘  │            (SHADOW_B)
  (ADC_BUF_C)       │    CPU 从 BUF_B 取料            │            (SHADOW_C)
                    │    CPU 往 SHADOW_C 投料          │
                    │    CPU 不受 DMA 节奏影响          │
                    └──────────────────────────────────┘

  R_in (原料供应) ≠ R_cpu (加工速度) ≠ R_out (出货速度)
  三者通过三缓冲隔离，完全解耦
```

## 4. 无中断连续计算模型

### 4.1 CPU 代码结构

```c
// DCL-HPC V2.1 — 无中断连续计算 + 多缓冲版本
// 所有定时器 UIE=0 (不开中断)
// 所有 I/O 由 DMA 完成
// CPU 永远操作"安全"缓冲区

// 三缓冲指针轮换 (由 DMA 完成或在主循环末尾切换)
volatile uint32_t *active_adc_buf;    // CPU 当前读哪个输入缓冲区
volatile uint32_t *active_shadow_buf; // CPU 当前写哪个输出缓冲区

void continuous_compute_loop(void) {
    while (1) {
        /* 1. 读输入 — 从"安全"缓冲区读 (DMA 此刻正在写另一个) */
        uint32_t raw_adc  = *active_adc_buf;
        uint32_t wire_val = WIRE_MAP[src_idx];
        
        /* 2. 计算 — 纯 DTCM 运算 */
        uint32_t result = compute(raw_adc, wire_val, param);
        
        /* 3. 写输出 — 写到"安全"缓冲区 (DMA 此刻正在读另一个) */
        *active_shadow_buf = result & 0xFFFF;
        TIM1_CCR1         = result >> 16;
        
        /* 4. 继续 — 没有等待, 没有检查, 没有 WFI */
    }
}
```

### 4.2 没有 ISR 意味着什么

| 开销项 | V1.1 (有 ISR) | V2.1 (无 ISR) |
|--------|---------------|---------------|
| 中断压栈/出栈 | 40-160ns/次 | **0** |
| Cache 污染 | 每次 ISR 刷 | **0** |
| 中断延迟抖动 | ~150ns | **0** (确定性=CPU周期级) |
| CPU 利用率 | ~60% | **接近 100%** |
| 计算时间片 | 840ns/μs | **全部可用** |
| 代码复杂度 | ISR + 主循环分离 | **单循环**

### 4.3 定时器的角色变化

V2.1 中的定时器**不再是"中断源"**，而是**纯粹的 DMA 触发源**：

```c
// 所有定时器 UIE=0 — CPU 永远不会被中断
TIM1_DIER = (1 << 12);       // CC4DE=1 (DMA), UIE=0 (不开中断)
TIM2_DIER = (1 << 8);        // UDE=1 (DMA), UIE=0 (不开中断)
```

定时器只做两件事：
1. 触发 DMA 搬运（输入/输出）
2. 触发 ADC 转换（TIM1 TRGO OC4REF）

## 5. 三缓冲内存管理 ⭐

这是 DCL-HPC 的核心创新——用**三重缓冲区**彻底消除 CPU 和 DMA 的地址竞争。

### 5.1 为什么三缓冲而不是乒乓

| 特性 | 单缓冲 | 乒乓缓冲 | **三缓冲** |
|------|--------|---------|----------|
| CPU 与 DMA 竞争 | ⚠ 高 (同地址) | ✅ 无 (轮换地址) | ✅ 无 |
| 计算超时一次 | ❌ 输出空/旧数据重读 | ⚠ 输出空(错过交换) | ✅ 仍有上一周期结果 |
| 计算超时连续两次 | ❌ 灾难 | ❌ 灾难 | ❌ 灾难 |
| 内存开销 | 最小 | 2× | 3× |
| 复杂度 | 低 | 中 | 中 |

**三缓冲的价值：在计算偶尔超时的情况下提供一次"松弛"**。对于科研级控制器，一次输出空洞可能意味着丢掉一个控制周期，而三缓冲保证即使计算偶尔慢一拍，输出仍然有数据可用。

### 5.2 输出三缓冲（SHADOW_A / SHADOW_B / SHADOW_C）

```
状态轮转：

  ┌──────────────→ Tcycle N ──────────────→ Tcycle N+1 ──────────────→
  │
  │  CPU 写 SHADOW_A    CPU 写 SHADOW_B    CPU 写 SHADOW_C
  │  DMA 读 SHADOW_C    DMA 读 SHADOW_A    DMA 读 SHADOW_B
  │  SHADOW_B 就绪      SHADOW_C 就绪      SHADOW_A 就绪
  │
  └────────────────────────────────────────────────────────→

表格:

  周期        CPU 写入      DMA 读出      就绪(待下一次DMA读)
  Tcycle N    SHADOW_A     SHADOW_C      SHADOW_B ← 上一周期结果
  Tcycle N+1  SHADOW_B     SHADOW_A      SHADOW_C ← 上上一周期结果
  Tcycle N+2  SHADOW_C     SHADOW_B      SHADOW_A ← 上上上一周期结果
                                         (3周期深度→1周期松弛)
```

**如果计算超时：**

```
  正常流程:
  Tcycle N:   CPU 算完了 → 写 SHADOW_A → DMA 下次读 SHADOW_A
  Tcycle N+1: CPU 算完了 → 写 SHADOW_B → DMA 下次读 SHADOW_B

  超时一次 (Tcycle N+1 CPU 没完成):
  Tcycle N:   CPU 算完了 → 写 SHADOW_A → DMA 读 SHADOW_A          
  Tcycle N+1: CPU 还在算  → SHADOW_A 未更新 → DMA 读 SHADOW_B (旧数据) ✅
  Tcycle N+2: CPU 算完了 → 写 SHADOW_A → DMA 读 SHADOW_C (更旧数据但没空洞) ✅
  
  DMA 永远有数据可搬，不会出现输出空洞。
```

### 5.3 输入三缓冲（ADC_BUF_A / ADC_BUF_B / ADC_BUF_C）

```
  周期        DMA 写入      CPU 读取      就绪
  Tcycle N    ADC_BUF_A    ADC_BUF_C     ADC_BUF_B ← 上一周期采样
  Tcycle N+1  ADC_BUF_B    ADC_BUF_A     ADC_BUF_C ← 上上周期采样
  Tcycle N+2  ADC_BUF_C    ADC_BUF_B     ADC_BUF_A ← 上上上周期采样
```

**与单缓冲的区别：**

```
单缓冲 (V1.x 方式):
  DMA 写 ADC_RAW → 覆盖旧值 → CPU 读 ADC_RAW → 读到的是最新值 (任何时候)
  ⚠ CPU 有可能在 DMA 正在写的过程中读到半更新的值

三缓冲 (V2.1 方式):
  DMA 写 ADC_BUF_A (独占)    → CPU 读 ADC_BUF_C (就绪, 稳定)
  CPU 切换指针: → 读 ADC_BUF_A
  DMA 写 ADC_BUF_B (新的"空闲"缓冲区)
  → CPU 永远读到已完成写入的缓冲区, 不存在部分更新问题
```

### 5.4 指针切换策略

最简单的实现——**CPU 主循环末尾切换**：

```c
// 三缓冲索引 (0, 1, 2)
volatile int cpu_write_idx = 0;   // CPU 当前写哪个 SHADOW
volatile int cpu_read_idx  = 0;   // CPU 当前读哪个 ADC_BUF

// DMA 端索引由硬件决定 (DMA 循环写入固定的三个地址)
#define SHADOW_A  (DTCM_BASE + 0x00E0)
#define SHADOW_B  (DTCM_BASE + 0x00E4)
#define SHADOW_C  (DTCM_BASE + 0x00E8)

#define ADC_BUF_A (DTCM_BASE + 0x0060)
#define ADC_BUF_B (DTCM_BASE + 0x0064)
#define ADC_BUF_C (DTCM_BASE + 0x0068)

// 输出 DMA 触发: 轮流读 SHADOW_A/B/C
// 输入 DMA 触发: 轮流写 ADC_BUF_A/B/C

void compute_and_switch(void) {
    // 读当前输入
    uint32_t adc = read_adc_buf(cpu_read_idx);
    
    // 计算
    uint32_t result = compute(adc, ...);
    
    // 写当前输出
    write_shadow_buf(cpu_write_idx, result);
    
    // 切换指针 (CPU 控制的仲裁点)
    cpu_read_idx  = (cpu_read_idx + 1) % 3;   // 切到新的输入缓冲区
    cpu_write_idx = (cpu_write_idx + 1) % 3;   // 切到新的输出缓冲区
}
```

### 5.5 内存布局

DTCM 中三缓冲区的分配：

```
DTCM 0x20000000
├── ENGINE_TIMING (0x00-0x3F)   — 引擎状态/诊断
├── ADC_RAW 三缓冲              — 输入三缓冲
│   ├── 0x0060: ADC_BUF_A      ← DMA 当前写入 (或空闲)
│   ├── 0x0064: ADC_BUF_B      ← DMA 当前写入 (或空闲)  
│   └── 0x0068: ADC_BUF_C      ← DMA 当前写入 (或空闲)
├── SHADOW 三缓冲               — 输出三缓冲
│   ├── 0x00E0: SHADOW_A       ← DMA 当前读取 (或就绪)
│   ├── 0x00E4: SHADOW_B       ← DMA 当前读取 (或就绪)
│   └── 0x00E8: SHADOW_C       ← DMA 当前读取 (或就绪)
├── SENSOR_MAP (0x0100-0x01FF) — 换算后的传感器值 (单缓冲, CPU 独占写)
├── WIRE_MAP (0x0300-0x12FF)   — 通讯总线 (单缓冲, DMA/ETH 写)
├── ENGINE REGION (0x1300-)     — 引擎专用数据
└── PROGRAM REGION (0x1700-)   — DCL 程序数据
```

**关键原则**：
- CPU 读/写的缓冲区 **与 DMA 读/写的缓冲区不同**
- CPU 切换指针的时机是**唯一的仲裁点**——在 store 指令完成后
- WIRE_MAP 等 CPU 和 DMA 都可能访问的区域使用**单缓冲 + 生产者/消费者模型**

## 6. DMA 子周期调度

### 6.1 触发架构

```
TIM2 (1μs 基础节拍, UIE=0)

  0ns    100ns   200ns   ...   900ns   1000ns
  │       │       │             │       │
  CH1@24  CH2@72  CH3@120       CH4@216 UPDATE
  │       │       │             │       │
  DMAMUX  DMAMUX  DMAMUX        DMAMUX  DMAMUX
  ↓       ↓       ↓             ↓       ↓
  DMA     DMA     DMA           DMA     DMA
  SHADOW  ADC→    CPU触发       ADC→    ADC→BUF_C
  _A→GPIO BUF_B   TIM1_CCR2    BUF_A   (循环)
```

### 6.2 DMAMUX 路由表

| DMAMUX 请求 | 触发源 | DMA 流 | 作用 | 周期 |
|------------|-------|--------|------|------|
| TIM2_CH1 | TIM2_CC1 | DMA1_S0 | SHADOW_A→GPIO 输出 | 1μs |
| TIM2_CH2 | TIM2_CC2 | DMA1_S1 | ADC_BUF_B 输入搬运 | 1μs |
| TIM2_CH3 | TIM2_CC3 | DMA1_S2 | 计算同步触发 | 1μs |
| TIM2_CH4 | TIM2_CC4 | DMA2_S5 | ADC_BUF_A → DTCM | 1μs |
| TIM2_UP | TIM2_UEV | DMA2_S3 | ADC_BUF_C 循环切换 | 1μs |
| TIM1_CC4 | TIM1_CC4 | DMA2_S1 | 100μs 硬周期输出 | 100μs |
| ADC1 | ADC1_EOC | DMA1_S4 | ADC 原始数据搬运 | 异步 |

### 6.3 多定时器级联（100ns 级别）

当目标周期低至 100ns 时，单个 TIM2 只有 240 ticks @240MHz，4 个通道不够用：

```
TIM3 主循环 (100ns × 10 = 1μs):

  CH1@24ns  CH2@48ns  CH3@72ns  CH4@96ns → TRGO → 触发 TIM4
  SHADOW_B   SHADOW_C  ADC_BUF_C ADC_BUF_A

TIM4 子循环 (1μs):

  CH1@125ns    CH2@250ns    CH3@500ns    CH4@750ns
  批量刷新    批量刷新     批量刷新      批量输出
```

这样在 1μs 内产生 4 + 4 = 8 个不同的触发点。

### 6.4 EtherCAT 通讯集成

> V2.1 架构面向的最重要现场总线——EtherCAT。EtherCAT 对硬件实时性要求极高，但 V2.1 的 DMA 纯驱动模型可以与之兼容。

#### 6.4.1 EtherCAT 硬件处理链

```
物理层:     LAN9252 (外部 ESC 芯片)
              │
              ├── 中断线 → DMAMUX 请求输入 (非 CPU 中断)
              ├── SPI/并行总线 → DMA 读写 ESC DPRAM
              ├── DC SYNC → 硬件比较器输出 → TIMx 从模式输入
              └── PDO 事件 → DMAMUX → DMA 读 DPRAM → DTCM
```

**关键原则：ESC 芯片（LAN9252）承担了绝大部分实时工作，CPU 只需要通过 DTCM 读写数据。**

#### 6.4.2 PDO 数据交换（DMA 轮询模式）

```
LAN9252 IRQ 线 ──→ DMAMUX 请求 ──→ DMA2 Stream X
                                           │
                             自动读取 ESC 的 DPRAM 到 DTCM
                                           │
                              ┌────────────────────────────┐
                              │  DTCM: ETHERCAT_PDO_BUF    │
                              │  ← CPU 读最新 PDO 值       │
                              │  ← DMA 写最新 PDO 值       │
                              │  (不关持续搬运，同在 DTCM)   │
                              └────────────────────────────┘
                                           │
                              CPU 下次 while(1) 迭代读到
                              从 PDO 触发到 CPU 读到: ~50ns

DMAMUX 配置参考:
  // 假设 LAN9252 IRQ 输出接到 DMAMUX 请求输入端
  // 根据实际接线配置 DMAMUX 请求 ID
  DMAMUX1_CHxCR = LAN9252_DMAMUX_REQ_ID;
  DMA2_SxCR = (M2P | CIRC | PL_HIGH | MSIZE_32BIT);
  DMA2_SxPAR = &LAN9252_DPRAM;           // ESC 数据寄存器
  DMA2_SxM0AR = &ETHERCAT_PDO_DTCM;      // → DTCM
  DMA2_SxNDTR = PDO_SIZE_WORDS;
  DMA2_SxFCR  = DMDIS;                    // 直通模式, 最小延迟
```

#### 6.4.3 分布式时钟（DC）

```
EtherCAT DC 同步不需要 CPU 参与——LAN9252 内部 DC 单元独立运行。

  DC SYNC 信号由 ESC 硬件产生:
    → 接 TIMx 的从模式触发器 (TRGI)
    → TIMx 自动与 EtherCAT 全局时间同步
    → CPU 读 TIMx_CNT (1 cycle) = 读 EtherCAT 全局时间

  CPU 不需要中断，不需要检查——TIMx 自己与 ESC 硬件同步。
  在 V2.1 中: CPU 读 TIMx_CNT 即得全局时钟，零开销。
```

#### 6.4.4 PDO 完整性保护

```
风险: DMA 正在写 PDO_BUF 时 CPU 读到 "半更新" 数据。

解决方案:
  1. 单缓冲 + DMA 传输完成标志:
     while (DMA2_SxNDTR != 0) {}  // 等传输完成 (但会阻塞 CPU)
     // 不适用于 V2.1 的连续计算模型

  2. 三缓冲 (推荐):
     DMA 轮换写 PDO_BUF_A/B/C
     CPU 读当前 "非 DMA 正在写" 的缓冲区
     → 与输入/输出三缓冲完全相同的策略

  3. DMA 完成事件 → DMAMUX 触发 CPU 检查:
     非中断方式, 用 TIMx 捕获事件来标记 "数据就绪"
     CPU 在循环中检查就绪标志位 (2 cycles)
```

#### 6.4.5 EtherCAT 状态机（CPU 被动检查）

```
EtherCAT 主站要求从站在特定时间内响应状态切换。

  V2.1 实现:
    ESC 芯片内部状态机自行运转
    CPU 只需读 ESC 状态寄存器 (通过 DMA 持续搬入 DTCM)
    CPU 写命令寄存器 (通过 DMA 持续搬出)
    状态切换不要求特定时刻——主站给出足够时间窗

  CPU 循环中检查:
    if (ecat_state != ECAT_OPERATIONAL) {
        // 非运行态: 限制输出, 执行状态切换逻辑
        ecat_fsm_step();
    }
```

#### 6.4.6 EtherCAT 周期时序验证

```
EtherCAT 主站帧 (每 100μs 或更短):

  LAN9252 接收帧 ──→ 硬件解析 PDO ──→ 置位 IRQ 线
                                              │
        ┌── 传统路径: IRQ → EXTI → ISR → 读 DPRAM (~2μs)
        │
        └── V2.1 路径: IRQ → DMAMUX → DMA → DTCM
                                          │
                              CPU 下次迭代读到 (≤50ns)

PDO 数据准备好到 CPU 算完输出:
  DMA 写 DTCM    : ~17ns
  CPU 下次 LDR    : ~25ns (迭代中)
  CPU 算 PDO 值    : ~50ns (几条指令)
  写 SHADOW       : ~5ns
  DMA 搬 SHADOW→GPIO: ~17ns
  ─────────────────────────
  总延迟 ≈ 114ns  <<  EtherCAT 要求的 10μs ✓
```

#### 6.4.7 局限性

| 问题 | 严重性 | 缓解 |
|------|--------|------|
| LAN9252 IRQ → DMAMUX 需要硬件兼容 | 中 | 确认 H723 DMAMUX 的外部请求输入是否引出到 GPIO |
| PDO 完整性需三缓冲 | 低 | 与输入/输出共享三缓冲策略 |
| DC 同步精度依赖硬件走线 | 低 | SYNC 信号走差分走线, 远离开关电源 |
| EtherCAT 启动时需状态机同步 | 低 | 被动检查, 不影响实时路径 |

## 7. MDMA 定位分析 ⭐

### 7.1 MDMA 是什么

STM32H7 的 MDMA（Master DMA）位于 D1 域，直接挂在 AXI 总线上：

```
              ┌───────── D1 Domain ─────────┐
              │                             │
              │  CPU ─── AXI ─── MDMA       │
              │               │             │
              │               ├── DTCM (AHBS)│
              │               ├── AXI SRAM  │
              │               ├── FLASH     │
              │               └── D2/D3 桥   │
              │                             │
              └─────────────────────────────┘
                        │
              ┌─────────┴─────────┐
              │   D2 Domain       │
              │   DMA2 / DMAMUX   │
              │   └──→ →D2→D1桥→ →→ AHBS → DTCM │
              └───────────────────┘
```

### 7.2 DMA2 vs MDMA 对比

| 特性 | DMA2 | MDMA | 结论 |
|------|------|------|------|
| **位置** | D2 域 (AHB) | D1 域 (AXI) | |
| **启动延迟** | ~4 cycles (8ns) | **~15 cycles (31ns)** | DMA2 胜 |
| **最小传输** | 1 字节 | **8 字节 (64-bit)** | DMA2 胜 |
| **触发源** | DMAMUX1 (TIM CHx 直连) | **软件 / LPTIM / DMAMUX2** | DMA2 胜 (更灵活) |
| **DTCM 路径** | D2 AHB→桥→AXI→AHBS | **AXI 直连→AHBS** (少一级桥) | MDMA 略优 |
| **突发传输** | 1-4 字 | **1-128 字 (64/128-bit)** | MDMA 胜 |
| **Linked-list** | ❌ 不支持 | **✅ 原生支持** (DMA chaining) | MDMA 胜 |
| **适用场景** | 精准定时触发 | 大批量后台搬运 | 互补 |

### 7.3 MDMA 在 DCL-HPC 中的角色

**✅ 适合 MDMA：**
- **批量日志搬运**：历史数据从 DTCM → AXI SRAM（供上位机读取）
- **Linked-list 批量预处理**：多个 DMA 任务链式执行，在后台准备数据
- **大块内存初始化**：程序加载、数据表初始化（128-bit 带宽）
- **AXI SRAM ↔ DTCM 数据交换**：利用 D1 域直连，减少跨域开销

**❌ 不适合 MDMA：**
- **子周期触发输出**：启动延迟 31ns 占 100ns 窗口的近 1/3
- **ADC 数据搬运**：需要 DMAMUX 的灵活定时触发，MDMA 不支持 TIM CHx 直连
- **1μs 以下的周期性传输**：启动延迟 + 最少 8 字节的粒度太重

### 7.4 推荐策略

```
DMA2 (D2 域, 4cyc 启动):         MDMA (D1 域, 15cyc 启动):
  TIM_CHx 触发 → SHADOW→GPIO       后台批量: 日志/历史数据搬移
  TIM_CHx 触发 → ADC_BUF 循环       程序加载时的大块初始化
  DMAMUX 灵活路由                    Linked-list 多阶段任务
  → 实时控制路径                     → 非实时后台路径

两条路径完全独立, 互不干扰。
```

## 8. 三速率独立运行

### 8.1 数学描述

```
R_in  = 输入数据刷新率
        ADC:   1 / 3.28μs  ≈ 305 kHz
        WIRE:  1 / 1μs     ≈ 1 MHz
        数字IO: 1 / 50ns   ≈ 20 MHz

R_cpu = CPU 计算迭代率
        简单路由: 1 / 50ns  ≈ 20 MHz
        复杂 PID: 1 / 200ns ≈ 5 MHz

R_out = 输出更新率
        GPIO: 由 TIMx_CH4 决定, 1 / 100ns = 10 MHz
        PWM:  由 TIM1 决定, 1 / 100μs = 10 kHz
```

**核心关系：R_out 独立于 R_in，R_cpu 独立于两者。**

三缓冲使这三个速率完全解耦——每个都有自己的缓冲区，不需要同步。

### 8.2 对控制质量的影响

对于**数字 IO 控制**（振镜、步进、脉冲发生器）：
- 输入变化率可以很慢（位置指令每 1ms 更新一次）
- 但输出以 100ns 分辨率执行脉冲序列
- 在指令之间做**微步插值**

对于**模拟控制**（PID、滤波器）：
- ADC 每 3.28μs 提供新样本（输入三缓冲中总是有最新的）
- PID 每 100ns 算一次（用相同的 ADC 值连算 32 次）
- 输出 PWM 以 100ns 分辨率更新

### 8.3 流水线深度与延迟

```
输入 DMA 搬运 → CPU 读 → 计算 → CPU 写 SHADOW → DMA 输出搬运
  ↑
  ADC_BUF_A 就绪     SHADOW_B 就绪
  (DMA 已写完)         (DMA 下次触发时搬走)
```

典型延迟：3.3-4.0μs（ADC 采样 → GPIO 输出）
但输出更新率不受影响——每 100ns 一次。

### 9.1 CPU 能力表

| 周期 | CPU 周期 (480MHz) | 能做什么 | 局限性 |
|------|------------------|---------|-------|

| 25ns | 12 cyc | 不足以做有用控制 | ❌ 需硬件加速 |

### 9.2 100ns 级别（48 cyc）能做多少

```c
// 100ns 内的典型循环体 (48 cyc):
    LDR  r0, [adc_buf]      // 1 cyc: 读 ADC 输入 (DTCM 零等待)
    LDR  r1, [wire_map]     // 1 cyc: 读 WIRE 输入
    MUL  r2, r0, scale      // 1 cyc: 缩放
    ADD  r3, r1, r2         // 1 cyc: 合并
    CMP  r3, threshold      // 1 cyc: 比较
    IT   GT
    MOV  r3, max_val        // 1 cyc: 钳位
    STR  r3, [shadow_buf]   // 1 cyc: 写输出到 SHADOW
    STR  r3, [timer_ccr]    // 1 cyc: 写 PWM
    B    loop               // 3 cyc: 循环
                            // ───────────
                            // ~12 cyc ≈ 25ns 实际执行
                            // 剩余 36 cyc ≈ 75ns 用于指令预取/解码流水线
```

### 9.3 推荐工作区

```
              ┌──────────────────────────────────────────┐
              │     ❌ <12cyc → 只够存/取, 做不了控制      │
              │     12-24cyc: Cortex-M7 实操下限            │
    实践下限───│──────────────────────────────────────────│
              │     24-48cyc (50-100ns): 纯数字IO + 简单逻辑│

              │     96-240cyc (200-500ns): 舒适(所有运算)   │
              │     240+cyc (>500ns): 非常宽松              │
              └──────────────────────────────────────────┘
```

## 10. 输入输出模型

### 10.1 输入模型

| 输入类型 | 缓冲方式 | 更新方式 | 更新时间 | CPU 读取 |
|---------|---------|---------|---------|---------|
| ADC 采样 | **三缓冲** | DMA1 Stream1 轮流写入 A/B/C | 3.28μs/次 | `active_adc_buf[idx]` 指针读 |
| WIRE 数据 | 单缓冲 | ETH/UART DMA | 1-10μs | `WIRE_MAP[i]` 直接读 |
| 数字输入 | 单缓冲 | DMA 读 GPIO_IDR→DTCM | 100ns-1μs | `*GPIO_BUF` 直接读 |

ADC 三缓冲的读取流程：

```c
// CPU 端: 读"就绪"缓冲区
uint32_t adc_value = *(volatile uint32_t *)(ADC_TRIPLE_BASE + cpu_read_index * 4);

// DMA 端: 写"空闲"缓冲区 (由 TIM_CHx 触发)
// DMAMUX 路由到 DMA1_S1, 目标地址 = ADC_TRIPLE_BASE + dma_write_index * 4
// DMA 写完自动递增 index

// CPU 和 DMA 的 index 永远不同
```

### 10.2 输出模型

| 输出类型 | 缓冲方式 | CPU 写入 | 硬件输出时刻 |
|---------|---------|---------|------------|
| GPIO | **三缓冲** | 写 `SHADOW_A/B/C` | DMA 在 TIM2_CH1 或 TIM1_CC4 触发时搬运 |
| PWM | 单缓冲 | 写 `TIM1_CCR1/2/3` | TIM1 下次 UPDATE 硬件自动锁存 |
| 高速脉冲 | 三缓冲 | 写 SHADOW | 每 100ns 由 DMA 触发输出 |

### 10.3 CPU 与 DMA 的正确操作序列

```
CPU 写 SHADOW 的正确流程 (确保 DMA 不会读到半更新的值):

  1. CPU 计算完结果
  2. CPU 保证当前 SHADOW 已经写完成 (STR 已 retire)
  3. CPU 切换指针 (下次 DMA 触发时读"旧的完成缓冲区")
  4. DMA 在 TIM_CHx 触发时, 从固定地址读, 不受指针切换影响

  → 无 data race, 无半更新状态
```

## 11. 实施路线

### Phase 0：验证多缓冲模型（已取消，直接进入 Phase 1）

> ~~验证 DTCM 双端口是否零仲裁~~ → 已通过架构分析确认：
> - 端口级零仲裁是物理特性
> - 三缓冲进一步消除地址级竞争
> - 直接进入 Phase 1，不做零仲裁测试

### Phase 1：实现输出三缓冲（1 周）

```
目标: 在现有 100μs 代码上增加输出三缓冲

步骤:
  1. 在 DTCM 中分配 SHADOW_A/B/C (三个 4 字节地址)
  2. 修改 DMA2_Stream5 为三缓冲模式:
     - DMAMUX 新增一个请求: TIM1_TRGO → DMA2_S5 三缓冲切换
     - 或使用 DMA 的 Linked-list (如果 H723 支持)
  3. 修改 CPU 主循环: 计算完成后切换 SHADOW 写入地址
  4. 用 GPIO 翻转验证: 
     - PE2 = 高表示 CPU 写 SHADOW_A, 低表示写 SHADOW_B
     - 示波器观察: DMA 输出 GPIO 的时序是否稳定

验证:
  - DMA 输出 GPIO 的边沿抖动 < 10ns (与单缓冲一致)
  - CPU 主循环不停顿 (三缓冲不影响计算连续性)
  - 故意加入延时模拟超时 → 输出降级到旧数据, 无空洞
```

### Phase 2：去掉 ISR 改为自由循环（1 周）

```
目标: 关闭 TIM1_UIF, ISR 代码移到 while(1)

步骤:
  1. TIM1_DIER.UIF = 0 (关中断)
  2. TIM1_DIER.CC4DE = 1 (保留 DMA 触发)
  3. ISR 代码移到 main() while(1)
  4. 保留 DMA2_Stream1 (ADC→DTCM) 和 Stream5 (SHADOW→GPIO)
  5. 验证: 100μs 周期下行为一致

风险:
  - 计算量 > 100μs 时, DMA 触发时 SHADOW 还没更新
  - 三缓冲缓解: DMA 读到的是上一周期结果, 不是空洞
```

### Phase 3：输入三缓冲 + 子周期 DMA 触发（2 周）

```
目标: ADC 输入也改用三缓冲, TIM2 子周期触发

步骤:
  1. 分配 ADC_BUF_A/B/C 三个缓冲区
  2. 修改 DMA2_Stream1: 轮流写入三个地址
  3. TIM2: CH1-CH4 配置触发点 (100ns, 300ns, 600ns, 900ns)
  4. DMAMUX 路由: TIM2_CH1→SHADOW DMA, TIM2_CH4→ADC DMA
  5. CPU 主循环: 从 active_adc_buf 读, 写 active_shadow_buf

验证:
  - 示波器量 GPIO 输出边沿: 抖动 < 10ns?
  - ISR 条目: 0 (确认 CPU 从未被中断)
  - DWT 统计: CPU 100% 时间在计算 (无等待)
```

### Phase 4：压周期（2 周）

```
目标: 逐步降低 TIM2 ARR

步骤:
  1. TIM2 ARR = 239 → 1μs (基线, 验证三缓冲 + DMA 子周期)
  2. TIM2 ARR = 119 → 500ns (验证计算量够用)
  3. TIM2 ARR = 47  → 200ns (推荐起点, 验证循环体紧凑)
  4. TIM2 ARR = 23  → 100ns (极限, 纯数字 IO)
  5. TIM2 ARR = 11  → 50ns  (探索性, 可能失败)

每步验证:
  - CPU 能在周期内完成一次计算迭代
  - DMA 能在子周期点正确触发
  - GPIO 输出抖动 < 10ns
  - 无 DMA 传输出错 (可检查 DMA 中断标志)
```

### Phase 5：MDMA 后台集成（1 周，可选）

```
目标: 引入 MDMA 做批量后台搬运

步骤:
  1. 配置 MDMA Channel 0: DTCM → AXI SRAM (日志)
  2. 软件触发 MDMA, 不占用 CPU cycles
  3. 验证: MDMA 运行时不影响主循环性能
  4. 比较: 有/无 MDMA 时的 CPU 迭代率
```

## 13. 风险与应对

| 风险 | 严重性 | 缓解措施 |
|------|--------|---------|
| CPU 连续超时两次 → 三缓冲耗尽 | **高** | 看门狗; 计算量保持 50% 余量; 监控 `cpu_write_idx` 滞留时间 |
| DMA 三缓冲切换与 CPU 指针不同步 | 中 | 指针切换放在原子段 (关中断或 STR 后 DSB) |
| 调试困难 (无 ISR 断点) | 高 | 保留一个调试用 GPIO 翻转 (条件编译); 用 DMA 的 FIFO 做 trace |
| MDMA 与 DMA2 争 AHBS 接口 | 中 | 错开时间窗口; MDMA 只在背隙时间触发 |
| 输入三缓冲 → 数据年龄延迟 | 低 | 加一个"数据新鲜度"标志; 另 3.28μs 的年龄对 100μs 控制周期微不足道 |
| DMAMUX 通道数不够 (只有 16 个) | 中 | 复用触发; 级联定时器; MDMA Linked-list |
| **EtherCAT PDO 完整性** | 中 | 三缓冲策略保护; DMA 完成标志辅助验证 |
| **过流保护响应** | **高** | 不能依赖软件; 需外部硬件比较器直驱 PWM 刹车; H723 内置 COMP 可用 |
| **CPU 卡死后输出失控** | **高** | IWDG 独立看门狗; CPLD/辅助 MCU 做独立安全监控 |
| **急停信号响应延迟** | **高** | DMAMUX 直驱 → DMA 写 SHUTDOWN 寄存器 (非中断路径, <100ns) |
| **调试困难 (无 ISR 断点/无周期边界)** | **高** | DMA trace buffer + 条件编译 GPIO + 示波器实时观察; 可考虑保留调试用 TIMx 中断 (条件编译) |
| **EtherCAT DC 同步** | 低 | ESC 硬件自处理; CPU 只读 TIMx_CNT |
| **编码器读数完整性** | 中 | DMA 持续搬 TIMx_CNT → DTCM; CPU 读到一半更新时下次迭代自然读到新值 |
| **位置控制周期不均匀** | 低 | TIM2_CNT 被动检查 + 分频执行; 位置控制本身对周期均匀性不敏感 |
| **伺服电流环的积分 windup** | 中 | dt 自适应 PI + 积分限幅 + TIM2_CNT 超时检测 |

#### 13.1.1 功能完整性评估

| 功能域 | V2.1 评估 | 说明 |
|--------|----------|------|
| **电流环 PI** | ✅ **优于传统** | dt 自适应, ADC→CCR ~50ns 延迟 |
| **FOC 变换** | ✅ **等同** | ADC 注入组同步三相同步采样 |
| **速度估算** | ✅ **更优** | TIM2_CNT ns 级时间戳, 优于固定周期 M/T 法 |
| **位置控制** | ✅ **等同** | 分频执行, 时间精度由 TIM2_CNT 保证 |
| **PWM 输出** | ✅ **等同** | 影子寄存器硬件锁存, CPU 写入时刻不重要 |
| **EtherCAT PDO** | ⚠ **可行** | DMAMUX + DMA 轮询, 需三缓冲保护完整性 |
| **EtherCAT DC** | ✅ **ESC 硬件** | CPU 只需读 TIMx_CNT, 零开销 |
| **编码器接口** | ✅ **DMA 即可** | TIM 编码器模式 + DMA 定期搬计数值 |
| **故障停机 (STO)** | ❌ **需外部硬件** | 安全回路不能依赖软件, 需 CPLD 或硬件继电器 |
| **过流保护** | ⚠ **需 COMP** | H723 内置模拟比较器可直驱 PWM 故障输入 |
| **急停信号** | ⚠ **需 DMAMUX 直驱** | DMAMUX 请求输入直接触发 DMA 写 SHUTDOWN |
| **固件烧录** | ✅ **等同** | 通过工程通道 (以太网 TCP:502) |
| **调试/监控** | ⚠ **需设计** | 无 ISR 断点, 需 DMA trace buffer + 外部示波器 |
| **CPU 卡死恢复** | ⚠ **IWDG 兜底** | 输出波形不变 (DMA 独立), 但需 IWDG 复位恢复计算 |
| **安全完整性 (SIL)** | ❌ **目前不可** | 无 ISR = 无安全认证路径; 需要 CPLD 补充安全层 |

**核心判断**：实时控制路径完整，安全路径需外部硬件补充。V2.1 的定位是＂高性能计算架构＂而非＂安全架构＂——两者可以共存于同一硬件平台，通过 H723 + CPLD 的分工实现。

> DCL-HPC V2.1 架构对硬件有明确的约束条件。以下列出满足架构需求的最小硬件配置和推荐配置。

### 14.1 MCU 核心需求

| 需求 | 必需程度 | 理由 | STM32H723ZG 满足情况 |
|------|---------|------|--------------------|
| **DTCM 双端口** | **绝对必需** | CPU D-bus vs AHBS 并发访问，是 V2.1 的根本前提 | ✅ Port0 + Port1 物理独立 |
| **DMAMUX** | **绝对必需** | TIMx CHy 任意路由到任意 DMA 流，子周期调度的核心 | ✅ DMAMUX1, 16 通道 |
| **DMA2** | **绝对必需** | M2P 模式触发输出、P2M 模式搬运输入，全速连续运行 | ✅ 8 Stream, 3 个请求 |
| **DMA CIRC 模式** | **绝对必需** | 输出三缓冲需要 CIRC 模式自动轮换地址；不关持续搬运依赖 CIRC 连续运行 | ✅ DMA_SxCR.CIRC 支持 |
| **主频 ≥400MHz** | **必需** | 100ns 周期 = 48 cyc @480MHz，更低频率下周期或被压缩 | ✅ 480MHz VOS0 |
| **TIMx 输出比较** | **必需** | 子周期触发点需要 CH1-CH4 独立输出比较 | ✅ TIM2 有 4 CH |
| **DWT CYCCNT** | **强烈推荐** | CPU 内省：测量迭代时间、检查进度 | ✅ 标配 |
| **FPU (浮点)** | **视算法** | 如果需要浮点 PID/FOC 则需要 | ✅ 单精度 FPU |
| **HRTIM** | **可选** | 如果追求 184ps 分辨率 PWM 输出则需要 | ✅ H723 支持 |
| **ADC 注入组** | **伺服必需** | 三相同步采样需要 Injected Group 同时触发多通道 | ✅ 支持 |
| **COMP (比较器)** | **安全必需** | 过流保护不能等 CPU, 需硬件比较器直驱 PWM 刹车 | ✅ 内置 2 路 COMP |
| **32-bit 定时器** | **启动序列必需** | TIM2 是 16-bit (~273μs 溢出), 秒级定时需 TIM5(32-bit) | ✅ TIM5 可用 |
| **IWDG** | **安全必需** | CPU 卡死后的最终恢复手段 | ✅ 标配 |

#### 14.1.1 不关持续搬运（DMA 饱和模式）硬件约束

```
DMA 不关持续搬运 = TIMx_UDE + DMA CIRC 模式

硬件链:
  TIM2_ARR=0 (每 4.16ns 溢出一次)
    → TIM2_UEV (UDE=1 触发 DMA 请求)
      → DMAMUX 路由到 DMA Stream
        → DMA 传输 ~17ns/次
          → 下次 DMA 触发时 TIM2 已经再次溢出
            → DMA 永远在忙 → "不关持续搬运"

约束条件:
  1. TIMx 必须支持 UDE (DMA 触发使能): ✅ 所有 STM32 TIM 都支持
  2. TIM2_ARR 可以设为 0: ✅ ARR 取值范围 0-65535
  3. DMA 传输时间 > TIMx 溢出间隔: ✅ 17ns vs 4.16ns, 饱和条件成立
  4. DMAMUX 请求线不能丢失: ✅ CIRC 模式自动重载, 无丢失
```

**结论：STM32H723ZG 是 DCL-HPC V2.1 的最小可行平台。** 所有必需特性都已具备。

#### 14.2.1 伺服电流环硬件数据链

```
ADC 注入组同步采样 (Iu/Iv/Iw, 单次触发→3 通道顺序转换)
  ↓ JDR1/JDR2/JDR3 锁存结果
DMA1_Stream1 CIRC 不关持续搬运 → DTCM 固定地址
  ↓ (每 ~3.28μs 一组新数据)
[DTCM ADC_RAW] ← CPU 每次迭代读此地址
  ↓ (~5ns 读到)
CPU 算 FOC + PI → 写 TIM1_CCR1/2/3
  ↓ (影子寄存器, 下次 PWM UPDATE 锁存)
PWM 硬件输出 → 驱动功率级

总延迟: ADC 转换 (3.28μs) + CPU 读+算 (~50ns)
       ≈ 3.33μs ← 电流环等效带宽 ~48kHz
```

DCL-HPC V2.1 的核心创新是**三缓冲 + 无中断连续计算 + DMA 子周期触发**的协同设计：

```
                 ┌──────────────────────────────────────┐
                 │        DCL-HPC V2.1 核心特征            │
                 │                                        │
                 │  ① CPU 自由循环: 永不中断, 永不等待      │
                 │  ② 三缓冲: CPU/DMA 永远不同地址          │
                 │  ③ DMA 子周期: 100ns 分辨率触发          │
                 │  ④ MDMA 后台: 批量搬运不干扰实时路径     │
                 │  ⑤ TTM 模型: 时间触发内存隔离             │
                 └──────────────────────────────────────┘
```

与 V1.x 的决定性差异：

| V1.x (通用) | V2.x (科研级) |
|------------|--------------|
| "周期由 ISR 决定" | "周期由 CPU 循环体决定" |
| "输入输出在特定时刻同步" | "输入输出通过多缓冲异步隔离" |
| "CPU 在 ISR 中工作" | "CPU 永远是主循环, DMA 是后台" |
| "周期降低受 ISR 开销限制" | "周期降低受 CPU 指令数限制" |
| "100ns → 不可能 (Cortex-M7)" | "100ns → 可能 (48cyc 够做一次控制)" |

**DTCM 双端口 + 三缓冲 + DMAMUX + 无中断设计 = 100ns 周期在 STM32H723 上可行。**

这就是 DCL 控制器从**通用工业级**到**科研级精度**的跃迁路径。
