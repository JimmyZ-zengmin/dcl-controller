# DCL — 确定性控制运行时（STM32H723 / Cortex-M7）

**一个用「静态路由表」替代「程序」的裸机控制运行时。**
没有 RTOS、没有调度器、没有 `while(1)` 大循环。全系统只有一个 **100 µs 的硬件定时硬拍**；
拍内按拓扑序扫描一张**编译期生成的静态路由表**，逐条完成「读源 → 算原语 → 写目标」，结果直接落到
GPIO / PWM / 通信。表里没有动态分支、热代码全部住在零等待 ITCM，**每拍花多少周期是编译期就能算出的量**。

**一次烧录，控制逻辑可以反复下发覆盖 —— 热更新 ≤ 1 拍。**

## 30 秒：它能干什么

| | 一句话 | 怎么自己验 |
|---|---|---|
| **接一个新器件 = 上传一段配置** | 不用改固件、不用重烧：下发"每 N 拍读 设备/寄存器/长度 → 写 `SENSOR[z]`" | `python tools/h723_dev_bind_test.py --port COMxx` → **52/0/1** |
| **配置随程序包持久化** | 上传程序包时自动带上绑定表，**开机自动恢复**；老包行为逐字节不变 | `python tools/h723_devbind_persist_test.py --port COMxx` → **32/0** |
| **应答带归属** | 应答回显 `CMD+SEQ`，客户端能判"这条是不是我的"（不再吃错帧）| `python tools/h723_frame_attrib_test.py --port COMxx` → **18/0** |
| ★★★ **闭环跑在 DCL 程序里** | 位置环整条在 ③ 层**每拍**执行（**100 µs**），**不是 PC 在环**（PC 在环只有 13.5 Hz）| 见下节「闭环步进」 |

```bash
bash build.sh                                       # ① 构建（6 道闸门，任一不过即失败）
pyocd flash -t stm32h723xx -O connect_mode=under-reset build/dcl_h723.hex   # ② 烧录
python tools/h723_proto.py --port COMxx             # ③ 探活 → 预期 12/0
bash tools/h723_full_regress.sh                     # ④ 一键全量回归（20+ 套件串行 + 末尾探活）
```

★ **认口按能力字**（不要认"第一个 CH340"），且判据用**必备位掩码** `(cap & 0x0DF7) == 0x0DF7`
—— 能力字随版本增长（`0x0DF7 → 0x1DF7 → 0x3DF7 → 0x7DF7`），**等值判据会让你以为"板子没响应"**。
★ **串口是独占资源**：同一时刻只允许一个进程用（并发会让两边都读到串帧）。

### 它长什么样（**全部用 DCL 原语** —— 没有 `ABS`/`MOD` 也能凑出最短弧）

```
SENSOR ang FROM sensor[1]                            # AS5600 角度 0..360
ADD a2 FROM ang BY=-360 ; GE wrap ang≥180 ; SEL fbk  # ★ 折到 [-180,180) ⇒ 最短弧
SUB err FROM tgt BY=fbk                              # 带符号误差
MUL eneg err×(-1) ; MAX eab = |err|                  # ★ 用 MAX 凑绝对值
MUL raw = kp×|err| ; LIMIT hz0 [60, 3000]            # ★ 先对**正幅值**钳位
GE drv |err|>0.5 ; MUL hz = hz0×drv                  # 误差带内 ⇒ 0（自停）
GE dpos err≥0 ; LOGIC dneg = NOT dpos                # ★ 方向由误差符号定（双极性）
OUTPUT hz/dneg/one/lim → wire[12..15]                # 运动请求（**程序面**）
```

**怎么跑**（★ 中间那步是必需的，见 §5 的"反馈源"）：
```bash
python tools/dclc.py examples/h723_step_bounded_position.dcl      # 编译 + 上传 + START
python tools/h723_as5600_bind.py --port COMxx                     # ★ 部署会清掉反馈绑定 ⇒ 必须写回
# 然后 op=19 sub=13 arg=1 切到程序面（默认 0 = 脚手架直控，既有行为不变）
```

### 实测（真机 · 单轴 · 空载 · 8 细分 1600 步/圈 · 24 V）

| 指标 | 实测 | 说明 |
|---|---|---|
| **控制周期** | **100 µs**（20000 拍 @ 200 MHz）| 环整条在 ③ 层**每拍**执行 |
| **环内输出抖动** | **σ = 3.6 ns** | 从"算完"到"引脚翻转" |
| **拍周期抖动** | 19990 ~ 20008 拍 ⇒ **跨度 90 ns** | ★ 与上一条**不是同一个量**（见上文「抖动有三个口径」）|
| **到位精度** | **0.08°**（目标 320° ⇒ 停在 319.92°）| 编码器 1 LSB = 0.088° ⇒ **贴着物理分辨率** |
| **到位保持** | **峰峰 0.000°**（12 点 × 0.5 s）| 误差带自停 ⇒ `hz=0`，不抖、不发热 |
| **长跑速率精度** | 6743.1° / 6750.0° = **−0.1%** | `h723_stepper_motion.py longrun 500 60` |

### ★★ 这个控制**是什么水平**（拿数字对标，不吹）

| 维度 | 本项目（**片内 DCL 程序**）| 工业伺服 / 运动控制器 | 同一块板走 **PC 在环** |
|---|---|---|---|
| **位置环频** | **10 kHz**（100 µs）| 1 ~ 20 kHz | **13.5 Hz**（命令通路 26.3 命令/s）⇒ **差 ~700 倍** |
| **输出确定性** | σ 3.6 ns | — | 受 USB / OS 调度影响 |
| **位置精度** | ±1 LSB（0.088°）| 取决于编码器 | 同硬件，但环慢 ⇒ 1 Hz 轨迹跟随误差 **±25°**（22° 是纯滞后）|
| **轨迹规划** | ❌ **没有**（无加减速、无插补）| ✅ 梯形 / S 曲线、多轴插补 | ✅（PC 算）|
| **电流环** | ❌ 驱动器是**开环电流**（TB6600）| ✅ | ❌ |
| **失速边界** | 突加 **627 rpm** / 带斜坡 **~1100 rpm**；17000 Hz 起原地抖动 | 高得多 | 同硬件 |

**⇒ 一句话定位**：
**环频与确定性已经是"工业伺服级"（10 kHz / 3.6 ns），但运动功能只是"点到点定位级"**
—— 没有轨迹规划、没有多轴、没有电流环，**失速点是硬边界**。
⇒ 它证明的是：**"把闭环从 PC 搬进片内程序面"这件事成立，且环频立刻提升约 700 倍**；
**不**声称它已经是一台运动控制器。

**能力边界（★ 分三级写 —— "没做"、"要扩架构"、"硬件真的缺"是三件事，不要混成一句"做不到"）**

| 级 | 项 | 能不能解 | 怎么解（含代价） |
|---|---|---|---|
| **A** | **轨迹规划（加减速 / 斜坡限幅）** | ⚠️ **已实现，但收益尚未证实** | ③ 层每拍执行 ⇒ 用 `PID` 的 **I 项当积分器**就可造斜坡；或固件加一个"每拍改 `ARR`"的**斜坡原语**（比 UEV 中断便宜得多）。★ 现在缺它的代价很实：**突加 627 rpm vs 带斜坡 ~1100 rpm ⇒ 被砍 47%**。<br>**落地（`op=19 sub=17 arg=Hz/s`，0=关）**：挂在 `step_set_rate()`（**唯一**频率写入口）⇒ 脚手架与程序面**同时**获得限幅；推进在主循环，落地走**轻量路径**（只写预装载 `ARR`/`CCR1`，**不关 `CC1E`、不写 `EGR.UG`**）⇒ 不切断脉冲、不污染"走 N 步"的计数。**默认 0 ⇒ 既有行为逐位不变**。<br>★ **上机现状（`h723_step_ramp_test.py` 3 PASS / 2 FAIL）**：**斜坡真的在爬**（中间值 701/9685/21085）、**停永远是立即**、**默认关零变化** —— 三条已验。<br>⚠️ **两条未定案，且都是"判据要重设计"而非功能缺陷**：① R3 斜率用时（实测 0.22 s vs 期望 1.55 s）—— **我的采样本身把主循环从 0.37 ms 拖到 ~26 ms**，期望值必须用**实测 dt** 反推；② R5 收益（突加与斜坡比值**都是 1.006 ≈ 1170 rpm**）—— **该频率下突加也不掉步**，测不出差异；★ 且这与套件 `ramp 31000` 的 **627 rpm** **矛盾**，**待查**。⇒ **所以本项写"未证实"，不写"已兑现"** |
| **A** | **"走 N 个脉冲自停"** | ✅ **已实现并上机验证**（`h723_step_pulsecount_test.py` **7 PASS / 0 FAIL**）| ★★★ **正解：不需要中断、不需要 RCR** —— 让**另一个定时器硬件数脉冲**：`TIM4` 的 ITR 表含 **`ITR2 = TIM3`**，配成"**外部时钟模式 1**"后 **`TIM4_CNT` 每来一个 TIM3 更新事件 +1** ⇒ 它**就是**已发脉冲数（连线全在芯片内部，不占引脚、不用接线）⇒ **零中断 / 零 DMA / 零 ITCM**。到点由主循环停脉冲（**多走的步数被 `TIM4_CNT` 精确记录，是可读回的已知量**）。<br>★ **我曾在 README 里写过另一条方案并称其"能解"，那是错的**：`UEV → DMA(NDTR=N) → 目的 = CCER.bit0 的位带别名` —— 因为**每次搬运写的都是同一位** ⇒ **第 1 个脉冲就把 `CC1E` 清掉**，只走 1 步就停。**已改**。<br>★ v2 的"硬件精确停"：`TIM4` 的 CC 比较事件 → **一次 DMA** 把 0 写进 `TIM3_CCR1`（普通 DMA，**不需要 MDMA**）。<br>**上机实测（`op=19 sub=15/16`）**：下 `N=1000` @500 Hz ⇒ **硬件计数 1001 步（多走 1 步 = 主循环停的延迟，已知量）**、`done_n` +1、到点后 `rate=0`/`CC1E=0`；**两条独立路径对上**：硬件计数 1001 vs 编码器换算 1019.9（差 **18.9 步**，正是"基准读数→step 下发"之间 36 ms 通信延迟 × 500 Hz = 18 步）。`N=100000` **钳到 65535**；没有脉冲时下 N ⇒ **NAK + 可读原因**|
| **A** | **多圈行程** | ✅ 能 | **③ 层做圈数累加器**（跨 0/360 就 ±1 圈）—— DCL 原语够（比较 + `SR`/`CTUD` + 加减）|
| **A** | **±180° 奇异点** | ✅ 能 | 用一个 `SR` 双稳态**记住上一次方向**，奇异点上沿用它（避免来回抖）—— 一行逻辑 |
| **B** | **多轴** | ⚠️ 能，但要**扩架构** | 硬件够（H723 有 `TIM1/2/3/4/5/8/15/16/17`）⇒ 要把 `step.c` 从**单例扩成实例化**；**插补放 ③ 层**（每拍算各轴增量 —— 正是程序面擅长）|
| **C** | **电流环** | ❌ **硬件缺**，非软件可补 | 台架上的 **TB6600 只有 PUL/DIR/ENA，没有电流环接口** ⇒ **须换驱动器**。★ 但本架构**能接**（走 ② 通用事务 op / CAN）⇒ 这是**选型**，不是架构缺陷 |

★ 一句话：**A 类是"还没做"，B 类是"要扩架构"，只有 C 类是真的硬件缺**。
**⇒ 不声称现在是一台运动控制器；但也不把"没做"说成"做不到"。**

## 它解决什么问题（为什么不是又做一个 PLC）

工业场景里拿"确定性"，主流两条路：

| 路线 | 怎么拿确定性 | 代价 |
|---|---|---|
| **PLC / 软 PLC** | 把周期拉到 ms 级，用长周期"藏住"抖动 | 响应慢；要做 µs 级闭环就得换路线 |
| **本运行时** | **不藏**：拍固定 100 µs，**每拍成本编译期可算**，热代码在 ITCM | 需要"编译期就确定"的设计纪律 |

**它靠三件事做到**：① 硬拍驱动（TIM2，实测抖动 σ 在**个位数 ns**）·
② 静态拓扑 + 零等待 ITCM（无 cache 不确定性）· ③ 通信下发 + SD A/B 持久化（改逻辑不重烧）。

**它明确不是什么**（详见 [`SUPPORTED-SCOPE.md`](docs/SUPPORTED-SCOPE.md) §3）：
不是实时 Linux / 不是通用 PLC 替代品 / **不承诺"发请求即得值"**（事务跨拍，必须用就绪门）/
**不承诺内部 flash 掉电保持**（已按设计降级 ⇒ 持久化一律走 SD）/
**不承诺"输出由硬件锚定"**（该说法已被实测推翻：引脚时刻 = CPU 最后一次写 + 0.12 µs）。

## ★★ 铁律 0 —— 非侵入式交互（**先读这条**）

> **观测不得改变被测对象。** 与单片机交互/观测时**优先走协议内通道**；
> 凡会改变目标状态的手段（HALT、复位、关时钟、改 DWT、留运行期配置），**只在协议通道表达不了时才用**，
> 且用完必须**显式恢复**并**核对已恢复**。

**为什么排第 0**：它的代价是"**静默的假故障**" —— 观测动作把目标推进到另一个状态，
而症状看起来像"固件坏了 / 新代码写错了"，**排查方向会被整轮带偏**。
本项目有 6 条纪律都是它的个案（例：`pyocd` 会话会**静默停掉 `DWT_CYCCNT`**，于是所有计时量读 0 而其余一切正常）。
完整血证见 [`docs/README-full-legacy.md`](docs/README-full-legacy.md) 的「铁律 0」节。

## 怎么保证"能信"（本系统最值得看的部分）

1. **构建 6 道闸门**（任一不过即失败）：零警告 · ISR 调用树（ISR 可达 ⇒ 必须住 ITCM）·
   应答缓冲区越界（静态）· ③层静态判据（程序不得出现引脚号/地址/寄存器名）·
   **契据可机检**（8 类主张：结构 / 拒绝码 / 能力位 / 留位 / 完备性 / 文档漂移 / 判据存在性 / **门面一致性**）。
2. **每条判据都能失败**：配了变异体（注入固件缺陷看判据是否变红）· 反空判据 · 逐字节比对。
3. **"覆盖不到"判 SKIP，不是 PASS**；闸门"覆盖不足"判**无效**，不是"干净"。
4. **未覆盖项必须显式声明**（`--allow-uncovered <理由>`）—— 不允许沉默地留着。
5. **改契据/门面而不同步 `docs/claims.md` ⇒ 构建会红** —— 这一步把"忘了同步"
   从"下一个人照错的做"变成"构建过不去"。

## ★★ "抖动"在本项目有**三个不同的量**（别混用、别相减）

这个词被指过三件互不相同的事。**口径不同 ⇒ 放一起比大小是错的。**

| # | 名称 | 实测值 | 量的是**哪个时刻** | 权威源 |
|---|---|---|---|---|
| ① | **输出抖动 σ**（同一拍内的执行确定性） | **3.6 ns**（CPU 直写档，为**引脚**本身） | **拍内**：从"算完"到**引脚真的翻转** | [`docs/ASSESS-architecture-as-controller-2026-09-14.md`](docs/ASSESS-architecture-as-controller-2026-09-14.md) |
| ② | **拍周期抖动**（跨拍的调度确定性） | `period_min/max` = **19990 / 20008 拍**（拍 = 5 ns @200 MHz）⇒ **跨度 90 ns（±45 ns）** | **跨拍**：这一拍**什么时候开始** | [`docs/STEPPER-DEMO.md`](docs/STEPPER-DEMO.md)（`0x38` 的 `period_min/max`）|
| ③ | **1 档（影子 + MDMA）引脚抖动** | 写影子 **13.0 ns** → **引脚 54~60 ns** | 同 ①，但经 MDMA 锁存 | 同 ① |

**① 与 ② 不能相减**：① 是"输出时刻**在拍内**漂多少"，② 是"拍与拍**之间**隔多久漂多少"。
（② 的 90 ns 跨度对速度环的影响：Δt 抖动 90 ns / 环周期 100 µs ⇒ **0.09%**。）

### 影子寄存器 → 引脚：**现在是 CPU 在写，不是 MDMA**

`DCL_DO_LATCH = 0`（**交付档**）⇒ `do_poll()` 用**一次 32 位 `GPIO_BSRR` 直写** ——
**那次写就是写引脚**。`= 1` 才走"影子 + MDMA 定时锁存"，**保留作"改前行为"对照档**。

### 为什么 **CPU 直写反而小 15 倍** —— 已定案

实测：**0 档引脚 σ ≈ 3.6 ns** ／ **1 档引脚 σ ≈ 54~60 ns**（LA 实测 `PE0` σ≈60 ns）。
根因**不是"MDMA 慢"**，而是**那条锁存链没有按设计工作**：

- `MDMA CTBR.TSEL` 扫遍 0…15 **全部照常工作** ⇒ **通道在自循环，不消费任何请求源**
  ⇒ **引脚时刻 = CPU 最后一次写影子 + 0.12 µs**
  ⇒ 设计承诺的"**输出时刻由硬件定时器锚定**"**未达成**，MDMA 只贡献了延迟与额外不确定度。
- 附带一层更细的解释：**连"写影子"本身都比写 BSRR 抖 3.6 倍**（13.0 vs 3.6 ns）——
  怀疑是 **MDMA 经 AHBS 持续读 DTCM，与 CPU 的 DTCM 写发生仲裁**；
  而 **AHB4 的 BSRR 写是 posted write**，时间戳不受后续总线竞争影响。

⇒ **决策：默认 0 档**。切 0 档**无功能损失**（`BSRR` 一次写覆盖 16 路 ⇒ 原子"输出帧"同样成立），
输出沿还**提前 ~300 ns**，并消掉 ~350 万次/秒的 AHB4 写。
